## 1. 从单体到分布式与微服务的演进动因
### 1.1 核心原理
- **业务维度**：单机容量撞天花板（CPU/内存/连接数），流量增长不能只靠换更强的机器；各模块发布节奏不同，单体必须整体回归、整体部署。
- **组织维度**：康威定律——架构映射组织沟通结构；团队变大后，单体仓库的合并冲突与联调排队成本高于拆分带来的运维成本。
- **技术维度**：水平扩展需要服务无状态化（会话外置）、数据可切分（分库分表）、故障可隔离（独立进程与线程池），拆开后每个模块可按自己的容量曲线扩容。
- **边界条件**：分布式是"用一致性与运维复杂度换可扩展性、故障隔离"；QPS 不过万、团队不足十人时，模块化单体通常是更优解。
### 1.2 面试问答
**Q1：为什么单体不够用？请从业务、组织、技术三个维度说。**
A：结论是三条压力线同时逼近：业务上发布粒度与单机资源受限，组织上沟通成本随人数快速上升，技术上无法局部扩容/局部容错/局部回滚。边界：若只有流量压力这一个问题，读写分离 + 缓存 + 加机器往往能再撑很久，不必上微服务。
**Q2：拆成微服务后多了哪些新问题？**
A：把本地函数调用换成不可靠的网络调用，于是新增：超时与重试、幂等与重复请求、部分失败、分布式事务、注册发现与健康检查、链路追踪与日志聚合、配置与版本治理、灰度发布。一句话：分布式把"单点确定性"换成了"全局概率性"。
**Q3：拆分粒度怎么定？**
A：按业务能力（业务边界）拆，不按技术分层拆；判断标准是"是否独立变化、是否有独立容量曲线、能否由 5~8 人小团队端到端负责"。边界：拆得过细会出现长调用链与大量跨服务事务，通常先拆核心域（交易、支付、库存）。
**Q4：微服务一定更快吗？**
A：单请求延迟通常更差（多一跳网络 + 序列化 + 服务发现），但整体吞吐、发布速度与故障隔离更好。正确问法是"瓶颈在单请求延迟还是整体吞吐与迭代速度"，取舍案例见 [系统设计案例集](./05-系统设计案例集.md)。
### 1.3 高频追问与陷阱
- 陷阱一：把微服务等同于分布式。单体部署多实例也是分布式；微服务强调的是业务边界与独立交付。
- 陷阱二：只谈收益不谈成本。成熟答法必须包含"新增了什么复杂度、用什么兜底（网关、熔断、链路追踪、配置中心）"。
### 1.4 示例（演进路径与新增问题清单）
```text
单体多实例   → 局部故障即全站故障、发布耦合
垂直拆分     → 跨域调用、跨库事务、数据冗余
微服务+中间件 → 注册中心可用性、MQ 重复与乱序、缓存与 DB 一致、分布式事务、全链路压测
服务网格/云原生 → Sidecar 接管流量治理（见 07-工程化与DevOps）
每一级台阶都要先补齐可观测性（日志/指标/链路），否则故障定位成本指数级上升。
```
### 1.5 一句话速记
> 分布式不是更快的架构，而是"用一致性复杂度换取横向扩展与故障隔离"的架构。

## 2. CAP 定理的准确表述与 CP/AP 选型
### 2.1 核心原理
- Brewer 2000 年提出猜想，2002 年由 Gilbert 与 Lynch 形式化证明。**C** 指**线性一致性**（读能返回最近一次成功写入的值，而非 ACID 的 C）；**A** 指**每个非故障节点收到的请求都必须在有限时间内返回非错误响应**（不要求最新数据，也不等于 99.99% SLA）；**P** 指网络分区（消息丢失或延迟任意长）下系统仍继续运行。
- **为什么"三选二"不严谨**：① P 是网络的客观属性而非可选设计，真实多机系统里分区一定会出现；② 只有在**分区发生期间**才需要在 C 与 A 之间取舍，未分区时二者可同时满足；③ 分区期间也不是非黑即白，可以在"部分可用（降级）"与"部分一致（有限延迟）"之间连续取舍。
- **CA 为什么不成立**：要求"既线性一致又不拒绝任何请求"必须假设网络永不分区，多机部署下该假设必破；所谓 CA 系统实际是单机/主备强一致，代价是分区即不可用。
- **CAP 与延迟**：CAP 只约束分区期间；不分区时的取舍是"延迟 vs 一致性"，由 **PACELC** 补齐——Partition 时在 A/C 之间选，Else 时在 Latency/Consistency 之间选。强一致必须等多数派确认，跨地域 RTT 决定延迟下限。
### 2.2 面试问答
**Q1：CAP 的准确表述是什么？**
A：在存在网络分区的前提下，系统无法同时保证线性一致性与每个非故障节点的请求都得到非错误响应。答题时必须先纠正三个字母的准确含义，再补一句"分区是暂时的，恢复后要能收敛"。
**Q2："三选二"为什么是错的？**
A：三者地位不对等：P 必须默认接受，真正的问题是分区期间 C 与 A 的二选一，而非三者中挑两个。答"我们是 CA 系统"会被追问分区时怎么办，正确回答是多机下不存在真正的 CA。
**Q3：CP 与 AP 怎么选？举几个系统。**
A：依据是"读到旧数据的业务代价"与"拒绝服务的业务代价"对比：钱和库存宁可不服务也不能读错（CP），点赞数/商品列表宁可为旧也要能返回（AP）。系统例子见下表，注意**同一系统不同配置、不同操作可能落在不同侧**。
**Q4：分区发生时系统该怎么做？**
A：进入受限模式：多数派继续服务（可降级），少数派拒绝服务；同时记录分区期间的写与冲突（版本号、向量时钟或业务规则）；恢复后做冲突检测与收敛（读修复、反熵、对账补偿）。若业务无法定义冲突合并规则，就不要允许分区双写，宁可走 CP。
### 2.3 高频追问与陷阱
- 陷阱一：把 CAP 的 C 说成 ACID 的 C，或把 A 说成"高可用 SLA"。必须主动区分。
- 陷阱二：说"选了 AP 就不管一致性"。AP 仍需承诺最终收敛并给出时间窗 SLA（如"分区恢复后 5s 内一致"）。
- 追问："ZooKeeper 是 CP 吗？"主流结论是 CP（写为线性一致、过半才可写）；争议点是 ZK 默认读走本地副本、只保证顺序一致、可能读到旧值，说清"写 CP、读顺序一致"更稳，详见 [ZooKeeper与分布式协调](../04-中间件/06-ZooKeeper与分布式协调.md)。
### 2.4 示例（典型系统取舍对照表）
| 系统 | 默认倾向 | 关键机制 | 分区/故障时表现 |
| --- | --- | --- | --- |
| ZooKeeper / etcd / Consul | CP | ZAB 或 Raft + 多数派 | 少数派不可写，损失 A |
| Nacos | AP/CP 可切换 | 临时实例 Distro(AP)、持久实例 Raft(CP) | 按实例类型区分，2.x 无常驻全局开关，以官方文档为准 |
| Eureka | AP | 异步复制 + 客户端缓存 + 自我保护 | 仍对外服务，可能返回过期实例列表 |
| Redis Cluster | AP（默认） | 主从异步复制 + 故障转移 | 主宕机可能丢未同步写，`WAIT` 可提高同步强度 |
| MySQL 主从 | AP（默认） | binlog 异步复制 | 主宕机可能丢事务；半同步/MGR 提升为偏 CP |
| Kafka | 可调 | ISR + `acks` + `min.insync.replicas` | `acks=all` 且 ISR 不足则拒绝写（偏 CP），`acks=1` 偏 AP |
```java
// Redis 提升写同步强度的代价：一致性上升、可用性与延迟下降（参数语义以官方文档为准）
Long acked = jedis.waitReplicas(2, 100);   // 等 2 个副本确认，最多阻塞 100ms
if (acked != null && acked >= 2) { /* 已落多数副本，可用于强一致读 */ }
else { /* 副本确认不足：降级为可能读到旧值 */ }
```
### 2.5 一句话速记
> CAP 不是三选二，而是"P 是前提，分区期间在 C 与 A 之间取舍，不分区时在延迟与一致性之间取舍（PACELC）"。

## 3. BASE 理论与 ACID 对比
### 3.1 核心原理
- **BA（基本可用）**：允许损失部分可用性——响应变慢（兜底数据、排队）、功能降级（关非核心功能）、限流丢请求。
- **S（软状态）**：允许存在中间状态（"支付中""冻结中"），且该状态会由定时任务、补偿、对账自行推进，不需要用户再次触发。
- **E（最终一致）**：无新写入时所有副本最终收敛。必须量化：收敛时间窗（如 ≤5s）、收敛手段（读修复/反熵/对账）、不一致期间的业务可接受性。
- ACID 与 BASE 不是对错关系，而是约束强度不同的两个坐标系；工程上常见"核心链路 ACID + 跨域链路 BASE"：扣款与流水在同库用本地事务，跨服务用 TCC/消息最终一致补齐，详见 [分布式事务](./02-分布式事务.md)。
### 3.2 面试问答
**Q1：ACID 与 BASE 的区别一句话说？**
A：ACID 追求强一致与即时正确，代价是并发度低、跨节点难维持；BASE 追求可用性与性能，把"立即一致"放宽为"最终一致"，代价是中间态与补偿逻辑。必须补一句"BASE 的 E 要能给出收敛时间窗与对账校验，否则只是不管了"。
**Q2：ACID 四特性放到分布式下分别出什么问题？**
A：原子性无法靠单库事务跨服务实现，需 2PC/TCC/消息；一致性（约束）跨库外键与唯一约束失效，需应用层或异步校验；隔离性跨库无法加锁，靠乐观锁、版本号或串行化队列；持久性依赖 fsync，跨副本要同步复制才不丢，代价是延迟。
**Q3：基本可用具体怎么做？**
A：三种手段——降级（返回缓存/默认值/历史数据）、限流排队（返回稍后重试）、功能裁剪（关评论、积分等旁路）。降级必须可观测、可通过配置中心动态开关，并有文案兜底。
**Q4：最终一致的"最终"是多久？怎么验证？**
A：由业务定义 SLA，技术上用三层保证：机制层（复制间隔、MQ 消费延迟、补偿频率）、监控层（复制延迟、消息堆积、对账差异指标告警）、兜底层（定时对账 + 差异自动修复 + 人工工单）。无法给出收敛上界的场景不属于最终一致，而是"人工介入一致性"。
### 3.3 高频追问与陷阱
- 陷阱一：把 BASE 说成不需要一致性。它只是放宽了时间维度，放弃了即时一致。
- 陷阱二：说"用了 MQ 就是最终一致"。必须回答消息重复、乱序、丢失、堆积分别怎么处理——落到幂等、顺序键、死信、对账。
- 注意区分三个"C/E"：ACID 的 C（约束）、CAP 的 C（线性一致）、BASE 的 E（最终一致），主动区分是加分点。
### 3.4 示例（ACID 与 BASE 对比表）
| 维度 | ACID | BASE |
| --- | --- | --- |
| 原子性 | 要么全成功要么全回滚（Undo/Redo 日志） | 用 TCC Cancel、消息补偿、对账修复替代全局回滚 |
| 隔离性 | MVCC + 锁保证事务互不干扰 | 无跨库隔离，靠乐观锁版本号、单键串行、业务防重 |
| 一致性 | 事务前后约束立即成立 | 降为最终一致：允许中间态，靠收敛机制达成 |
| 持久性 | 提交即持久（fsync + 副本） | 异步复制下可能丢最近写（可配半同步） |
| 可用性与性能 | 强事务与锁带来阻塞，扩容困难，单机性能高 | 无锁、可降级、可水平扩展，跨节点吞吐更高 |
| 一致性时间窗 | 0（提交即一致） | 非 0，需业务定义（如 ≤5s）并监控验证 |
| 典型实现 | 单库事务、MySQL MVCC（见 [MySQL事务锁与MVCC](../02-数据库/02-MySQL事务锁与MVCC.md)） | TCC/Saga/本地消息表、Redis 异步复制（见 [Redis高可用与缓存治理](../02-数据库/05-Redis高可用与缓存治理.md)） |
```java
// BASE 的"软状态 + 补偿"骨架：先落中间态，再由补偿任务推进到终态
@Transactional
public void createOrder(OrderCmd cmd) {
    orderMapper.insert(Order.of(cmd, OrderStatus.PAYING));              // 软状态：支付中
    outboxMapper.insert(Outbox.of(cmd.orderId(), "PAY_REQUESTED"));     // 本地消息表：与业务同库同事务
}
// 补偿任务：扫描超时 PAYING 订单 -> 查支付结果 -> 推进为 PAID 或关闭并回滚库存
```
### 3.5 一句话速记
> ACID 是"立刻正确"，BASE 是"可用优先、允许中间态、承诺最终收敛"，选哪个取决于不一致时间窗内业务能否承受。

## 4. 一致性模型谱系与业务映射
### 4.1 核心原理
- **线性一致性（Linearizability）**：最强，等价于单副本的原子读写语义，并尊重**实时序**——A 在 B 开始前已完成，则所有人看到的顺序必须 A 先于 B。
- **顺序一致性**：存在所有节点认同的全局全序，且每个进程自己的操作在该全序中保持程序顺序，但不要求与真实时间对齐，因此比线性一致弱。
- **因果一致性**：只要求有因果关系的操作（同进程程序序、读到即因果、传递闭包）被所有节点按同一顺序观察；并发操作可不同顺序。因为不需要全局协调，它在网络分区期间仍可用，是 AP 系统可实现的最强一致性之一。
- **最终一致性**：无新写入时副本最终收敛；工程上还要叠加会话语义：读己之写、单调读、单调写、写读依从。
- **强度排序**：线性一致 > 顺序一致 > 因果一致 > 会话语义（读己之写/单调读）> 最终一致；越强意味着协调越多、延迟越高、分区时可用性越低。
### 4.2 面试问答
**Q1：线性一致与顺序一致的区别？**
A：顺序一致只约束"全局全序 + 各进程程序序"，线性一致额外约束实时序。举例：A 写完并收到响应后，B 立刻读——顺序一致系统允许返回旧值（只要全局顺序自洽），线性一致必须返回新值。另外线性一致是单对象语义，不等于事务隔离。
**Q2：因果一致为什么比最终一致强，又比线性一致便宜？**
A：它额外禁止因果倒挂（看到回复必看到原评论）；实现只需随写携带依赖元数据（向量时钟或依赖列表），不需要全局协调，所以分区期间仍可写。代价是元数据存储与依赖同步。
**Q3：下单后立刻查订单查不到，怎么解决？**
A：给用户会话提供读己之写：① 写后一段时间内该用户读走主库；② 会话粘滞同一副本；③ 记录写入位点/版本号，副本追赶到位点前阻塞或读主库；④ 刚写对象写入本地缓存（短 TTL）。按用户维度生效，避免全局打主库。
**Q4：为什么最终一致系统还要强调单调读？**
A：否则请求被随机路由到不同延迟副本，用户会看到"时间倒流"（已发货又变待发货），体验差且易触发重复操作。实现：按用户哈希固定副本，或客户端记录已见版本号，遇到更低版本时重试或拒绝展示。
### 4.3 高频追问与陷阱
- 陷阱一：把线性一致当可串行化。二者正交：一个约束单对象实时顺序，一个约束多对象事务等价串行（两者兼具叫严格可串行化）。
- 陷阱二：宣称"我们强一致"却不区分范围。正确说法是"单 key/单分片内线性一致，跨分片退化为最终一致"（如 Redis Cluster 多 key 命令要求同槽）。
- 追问："etcd 的读是线性的吗？"答：默认线性一致读（走 Raft ReadIndex），也可显式降级为串行读走本地副本；细节以官方文档为准。
### 4.4 示例（一致性模型与业务映射）
| 一致性模型 | 核心保证 | 协调成本 | 典型系统/机制 | 适合场景 |
| --- | --- | --- | --- | --- |
| 线性一致 | 单副本语义 + 实时序 | 高（多数派，读也需确认） | etcd 默认读、ZK 写、Raft 提交读 | 余额与库存扣减、分布式锁、配置下发、选主 |
| 顺序一致 | 全局全序 + 程序序 | 中 | ZK 读、日志定序 | 日志顺序消费、事件溯源、审计顺序 |
| 因果一致 | 只保因果顺序 | 中低（随写带依赖） | COPS、部分 Cassandra 变体 | 评论与回复、聊天消息、好友动态 |
| 读己之写 / 单调读 | 用户维度保证 | 低（会话路由/固定副本） | 主库路由、位点等待、版本号校验 | 下单后查订单、订单状态列表、进度条 |
| 最终一致 | 无新写则收敛 | 最低（异步复制） | Redis 主从、MySQL 异步从库、MQ 消费 | 点赞数、浏览量、排行榜、报表、搜索索引 |
### 4.5 一句话速记
> 一致性模型是从"单副本幻觉"到"最终收敛"的强度阶梯，业务站在哪一级只取决于"读到旧值会不会亏钱或误导用户"。

## 5. 分布式提交协议：2PC 与 3PC
### 5.1 核心原理
- **2PC 流程**：XA 规范中由 TM（协调者）与多个 RM（资源管理器）协作。**阶段一 Prepare**：TM 广播 prepare，RM 执行事务操作但**不提交**、写 undo/redo 日志并**持有锁**，之后回复 yes/no；**阶段二**：全部 yes 则 TM 写 commit 日志并广播 commit，任一 no 或超时则广播 rollback。
- **四个固有问题**：① 同步阻塞——准备后持锁等待最终决定，锁时长 ≈ 网络 RTT + 最慢参与者的提交时间；② 协调者单点——TM 在做出决定之后、通知之前宕机，RM 进入 in-doubt 状态且锁不释放；③ 不一致窗口——决定已做出但只送达部分 RM，出现部分提交、部分未提交；④ 不抗网络分区——两侧可能各自行动并产生分歧。
- **3PC 与它的问题**：在 2PC 前插入 **CanCommit**（只询问能力、不加锁），再 **PreCommit**（执行并持锁），最后 **DoCommit**，并给参与者**超时自决权**（进入 PreCommit 后未收到 DoCommit 则默认提交）。它缓解了阻塞，但分区下仍可能出现"一侧按超时提交、一侧按未预提交回滚"的决策分裂，根因是**超时不能代表多数同意**。
- **工程结论**：一致性靠多数派共识（Raft/Paxos，见第 6 节），可用性靠业务补偿（TCC/Saga/本地消息表），因此纯 3PC 落地很少，详见 [分布式事务](./02-分布式事务.md)。
### 5.2 面试问答
**Q1：2PC 最大的问题是什么？**
A：同步阻塞叠加协调者单点。原因是准备阶段之后参与者必须先持锁等待最终决定，而决定权集中在 TM 手上，TM 宕机则参与者的锁与连接被挂住且无法超时释放。数据感：锁持有时长通常等于全网 RTT 加最慢参与者提交时间，跨机房易达几十毫秒，长事务下锁等待与死锁概率显著上升（见 [MySQL事务锁与MVCC](../02-数据库/02-MySQL事务锁与MVCC.md)）。
**Q2：为什么 2PC 会出现数据不一致？**
A：因为"做出决定"与"决定送达"不是原子的。TM 写下 commit 日志后才广播，广播过程中宕机则已收到消息的 RM 提交、未收到的仍按未提交处理，全局状态矛盾且无法通过回滚修复。兜底手段是 TM 高可用 + 决策日志持久化 + RM 定期查询未决事务（`XA RECOVER`）+ 对账补偿。
**Q3：3PC 解决了什么？为什么仍然不安全？**
A：解决了"参与者无法决策导致的长阻塞"，仍不安全是因为分区时两侧可能按不同规则决策（超时提交 vs 未预提交回滚），导致不一致。它只降低阻塞概率、不提供一致性保证，且多一轮交互使延迟更高。
**Q4：把协调者做成集群是不是就解决了？**
A：只解决可用性，不解决决策一致性——集群化后必须选主并保证同一事务只有一个决策，这本身需要多数派共识来定序并持久化决策日志；参与者的持锁时间也不会因协调者集群化而缩短。Seata AT 是"本地事务已提交 + 全局锁 + undolog 反向补偿"，并非数据库层 XA 强一致。
### 5.3 高频追问与陷阱
- 陷阱一：把 2PC 当通用强一致方案。它牺牲可用性且不抗分区，只适合小范围、低并发场景。
- 陷阱二：忽略 prepare 阶段已经持锁。被问"2PC 为什么慢"，第一句就该说锁与阻塞。
### 5.4 示例（2PC 与 3PC 对比表）
| 维度 | 2PC | 3PC |
| --- | --- | --- |
| 阶段划分 | Prepare → Commit/Abort | CanCommit → PreCommit → DoCommit |
| 何时加锁 | Prepare 执行操作即持锁 | CanCommit 不加锁，PreCommit 才持锁 |
| 协调者宕机 | 参与者全部阻塞并持锁，无超时自决 | 参与者超时后可自行决策，阻塞大幅减少 |
| 分区下一致性 | 可能部分提交、部分回滚 | 仍可能决策分裂（一侧提交一侧回滚） |
| 延迟 | 交互轮次少 | 多一轮交互，延迟更高 |
| 落地程度 | 高（XA、部分数据库与中间件） | 低（多被 Raft 类共识替代） |
### 5.5 一句话速记
> 2PC 的命门是"决定权集中 + 参与者持锁阻塞"，3PC 只减轻阻塞，一致性必须靠多数派共识或业务补偿。

## 6. 共识算法：Paxos 与 Raft
### 6.1 核心原理
- **Paxos 角色与两阶段**：Proposer 提案、Acceptor 投票并记忆（通常 2F+1 个，容忍 F 个故障）、Learner 学习结果。**阶段一 Prepare/Promise**：Proposer 用全局唯一递增编号 n 发 `Prepare(n)`，Acceptor 承诺不再接受编号小于 n 的提案，并返回已接受过的最大编号提案；收到**多数派** Promise 后进入阶段二。**阶段二 Accept/Accepted**：若 Promise 中带有已接受值，必须提出其中编号最大的那个值，发 `Accept(n, v)`，被多数派接受即视为选定。
- **安全性与活性**：任意两个多数派必然相交，加上"承诺不接受更小编号"，保证已选定值不会被改写；两个 Proposer 交替提高编号会**活锁**，靠随机退避或稳定 leader（Multi-Paxos）解决。**FLP 不可能性**说明纯异步网络下不存在既保证安全又保证终止的确定性共识算法，工程实现依赖部分同步假设（超时）+ 随机化。
- **Raft 的三个子问题**：① **Leader 选举**——follower 在随机化选举超时（论文建议 150~300ms，以官方文档为准）内未收到心跳则 term+1、自投票并广播 `RequestVote`（带 lastLogIndex/lastLogTerm），获多数票成为 leader 并周期发心跳；② **日志复制**——leader 追加本地日志并并行发 `AppendEntries`（prevLogIndex/prevLogTerm + 条目 + leaderCommit），**多数派**复制成功才推进 `commitIndex` 并 apply 到状态机（`applyIndex` 单调不可回退）；③ **安全性约束**。
- **Raft 四条安全性质**：日志匹配性质（同 index 同 term 相同则之前条目全部相同）；选举限制（候选人日志必须不落后于多数派，保证已提交条目不被覆盖）；leader 只提交本任期日志（旧任期条目即便在多数派上也可能是未提交的，需先提交一条本任期条目如 no-op 间接提交）；状态机安全（同 index 不会 apply 不同条目）。
- **成员变更与 ZAB**：稳妥做法是单节点变更（一次一个，任何时刻不会出现两个不相交的多数派）或联合共识两阶段（先 `C_old,new` 同时满足新旧两个多数派，再 `C_new`）。ZooKeeper 的 ZAB 与 Raft 思路相近但崩溃恢复流程不同，细节以官方文档为准（见 [ZooKeeper与分布式协调](../04-中间件/06-ZooKeeper与分布式协调.md)）。
### 6.2 面试问答
**Q1：Paxos 的核心思想一句话说清？**
A：多数派交叉 + 编号承诺——Acceptor 承诺不再接受更小编号的提案，因此任何被多数派接受的提案都会被后续 Proposer 在阶段一发现并原样沿用，无人能改写已选定值。边界：Basic Paxos 只对一个值达成一致，要做复制日志需要 Multi-Paxos。
**Q2：Raft 选举流程与随机超时的作用？**
A：follower 超时 → term+1 变 candidate → 自投票并广播 RequestVote → 获多数票成为 leader 并周期发心跳。随机超时是为了打破选票分裂、避免活锁：同时竞选时最先超时的节点更可能先集齐选票。选举限制保证日志滞后的节点不会当选，这是不丢已提交数据的核心保障。
**Q3：为什么 Raft 不能直接提交之前任期的日志？**
A：因为"多数派持有"不等于"已提交"。旧任期条目被复制到多数派但尚未提交时 leader 崩溃，新 leader 可能用自己的日志覆盖它。因此 leader 必须先在本任期提交一条自己的日志（如 no-op），当它被多数派确认时，之前的条目才被间接提交。
**Q4：Raft 与 Paxos 的区别与取舍？**
A：Paxos 更理论最小化，只定义达成一致的抽象，选举、日志连续性、成员变更都留给实现；Raft 用强 leader、连续日志与明确的选举/成员变更规则换取可实现性与可理解性，代价是 leader 压力更大、写入延迟受 leader 位置影响。落地共识组件多数团队直接选 etcd。
**Q5：为什么多数派是 2F+1？拜占庭容错呢？**
A：因为需要"任意两个多数派必相交"：N=2F+1 时多数派大小 F+1，任意两个 F+1 集合至少共享一个节点，而该节点对同一任期内的两个提案不会都赞成，因此最多 F 个节点故障仍只有一个值被选定。若节点会伪造消息（拜占庭故障）则需 3F+1 并使用 PBFT 类算法，普通业务系统不用。
### 6.3 高频追问与陷阱
- 陷阱一：把 Paxos 当选举算法。它解决的是"对一个值达成一致"，选举只是其应用之一且需要额外机制。
- 陷阱二：说"term 越大数据越新"。term 只用于识别过期信息，数据新旧看 lastLogIndex/lastLogTerm。
- 追问："为什么一般部署 3 或 5 个节点？"答：3 容忍 1 个故障、5 容忍 2 个，容错增长远慢于成本增长，且节点越多写延迟越大；4 节点容错数与 3 节点相同，不划算。
### 6.4 示例（Paxos 与 Raft 对比表）
| 维度 | Paxos（Basic / Multi-Paxos） | Raft |
| --- | --- | --- |
| 目标 | 先对一个值达成一致，再扩展为日志 | 直接以复制状态机日志为目标 |
| Leader | 非必需（Multi-Paxos 引入稳定 proposer） | 强 leader，写必须经 leader |
| 日志顺序 | 提案可乱序完成，需额外机制处理空洞 | 连续日志，不允许空洞 |
| 选举 | 协议未规定，由实现决定 | 协议内规定：term + 随机超时 + 多数票 |
| 成员变更 | 未规定 | 单节点变更 / 联合共识 |
| 安全论证与落地 | 证明完备但理解门槛高（Chubby 等） | 五条安全性质清晰，etcd/Consul/TiKV 事实标准 |
### 6.5 一句话速记
> Paxos 用"多数派交叉 + 编号承诺"保证安全，Raft 用"强 leader + 任期 + 随机超时"把同一份安全性做成可实现的工程协议。

## 7. Quorum/NWR 与一致性哈希分片
### 7.1 核心原理
- **NWR 公式**：N 个副本，写需 W 个确认，读需 R 个响应。`W + R > N` 时读写集合必然相交，交集副本包含最近一次成功写，配合版本号取最新即可提供强一致读；`W + R <= N` 时读写集合可能不相交，只能最终一致（靠读修复与反熵收敛）。`W > N/2` 时可容忍 `N - W` 个副本故障。
- **Quorum 的边界**：它保证"读不会读到比最近一次成功写更旧的值"，但**不能替代事务隔离**，也不解决并发覆盖写冲突（需要 CAS、版本号或事务），并与时钟语义无关。
- **一致性哈希**：哈希空间成环（如 0~2^32-1），节点与 key 都映射到环上，key 顺时针归属第一个节点；增删节点只影响相邻区间，扩容**平均迁移约 K/n**（K 为总数据量，n 为节点数），而取模哈希扩容时几乎全量迁移。
- **虚拟节点**：物理节点少时分布易倾斜，且单节点故障会把压力全压给后继节点；给每个物理节点映射 100~1000 个虚拟节点散布环上即可均匀化并把故障影响打散。虚拟节点是负载均衡参数，与副本数是两个维度。
### 7.2 面试问答
**Q1：N=3、W=2、R=2 是什么一致性？**
A：多数派强一致。因为 2+2>3，读集合与写集合必相交，交集副本保存了最近一次成功写；同时容忍 1 个副本故障。若改成 W=1、R=1，则 2<=3，可能读到旧值，只能提供带收敛窗口的最终一致。
**Q2：Quorum 能提供线性一致吗？**
A：需要额外条件：写必须等 W 个确认、读必须等 R 个响应并取版本最新、写操作要有全局顺序或版本号。若允许并发覆盖写，Quorum 只能保证读到某个已成功写版本、无法解决冲突，所以准确说法是"读不会更旧"，线性一致还需实时序约束。
**Q3：为什么扩容时迁移量是 1/n？**
A：均匀分布下每个节点负责 K/n 数据；新增节点只接管环上一段区间，故迁移量约为 K/n（n 为新增后的节点数）。对比取模哈希：节点数从 n 变 n+1 时几乎全部 key 归属改变，迁移比例约为 n/(n+1)，表现为大规模搬迁与缓存全量失效。
**Q4：数据倾斜怎么解决？**
A：三层手段——虚拟节点打散分布；热点 key 加盐拆成子 key（读时聚合或用本地缓存兜住，代价是范围扫描失效）；按实际 QPS 动态迁移虚拟节点或槽。另注意分片键选择比哈希算法更重要，跨分片查询要靠异构索引或宽表解决，详见 [MySQL调优主从与分库分表](../02-数据库/03-MySQL调优主从与分库分表.md)。
### 7.3 高频追问与陷阱
- 陷阱一：把一致性哈希当万能药。它只解决迁移量，不解决热点与跨片事务。
- 陷阱二：把虚拟节点当副本。vnodes 是负载均衡手段，副本数（N）才决定容错。
- 追问："Redis Cluster 为什么不是一致性哈希？"答：它用固定 16384 个槽（`CRC16(key) mod 16384`）+ 客户端重定向（MOVED/ASK），以槽为迁移单位，跨槽多 key 操作需同槽或用 hash tag；思路是"缩小一致性范围换取可用性与性能"，见 [Redis数据结构与核心原理](../02-数据库/04-Redis数据结构与核心原理.md)。
### 7.4 示例（NWR 配置对照表，N=3）
| 配置 | W+R 与 N | 一致性 | 故障容忍 | 特点 |
| --- | --- | --- | --- | --- |
| W=2, R=2 | 4 > 3 | 多数派强一致 | 1 个副本 | 均衡，最常见 |
| W=3, R=1 | 4 > 3 | 强一致（写全确认） | 无（任一副本故障即不可写） | 写可用性最差，读最快 |
| W=1, R=3 | 4 > 3 | 强一致（读全确认） | 读过程中任一故障即失败 | 写极快，读最慢 |
| W=1, R=1 | 2 <= 3 | 最终一致 | 2 个副本 | 性能最高，可能读到旧值 |
| W=1, R=2 | 3 = 3 | 不保证（边界情形） | 2 个副本 | 需版本号与读修复兜底 |
### 7.5 一句话速记
> 副本层面用 `W+R>N` 换强一致，分片层面用一致性哈希 + 虚拟节点换"扩容只搬约 1/n 数据且负载不倾斜"。

## 8. 服务发现与健康检查
### 8.1 核心原理
- **服务发现的四件事**：注册（实例启动写入 IP、端口、权重、版本、机房等元数据）、发现（消费方获取实例列表并负载均衡）、健康检查（判定实例是否可服务）、变更通知（上下线后尽快让消费方感知）。
- **推模式 vs 拉模式**：拉模式实现简单、客户端可缓存、注册中心压力可控，但感知延迟 = 拉取间隔 + 剔除超时；推模式实时性好，但需维护大量长连接且存在推送风暴与丢失。工程实践是"长连接推送变更 + 客户端本地缓存 + 定时全量拉取兜底"。
- **健康检查三层**：TCP 探活只证明端口在监听（进程卡死时内核仍能完成握手，不足以判断业务可用）；HTTP 探活检查状态码与关键依赖，注意不要因下游抖动误判自身；业务探活最准但成本高、易误判。K8s 对应 liveness（重启）/readiness（摘流量）/startup（启动保护），见 [Docker与Kubernetes](../07-工程化与DevOps/02-Docker与Kubernetes.md)。
- **时间账**：故障感知时间 ≈ 心跳周期 × 失败判定次数 + 剔除延迟。例如心跳 30s、连续 2 次失败加 30s 剔除延迟时，最坏情况下消费方可能持续调用失效实例 90s 以上，因此客户端必须配合主动探测、熔断与重试其他实例。
### 8.2 面试问答
**Q1：Eureka、Nacos、Consul、ZooKeeper、etcd 怎么选？**
A：Spring Cloud Alibaba 体系选 Nacos（AP/CP 按实例类型、注册与配置一体）；K8s 环境用 etcd + Service/EndpointSlice；要强一致与多数据中心服务网格选 Consul；Eureka 已进入维护模式，新项目一般不首选；ZooKeeper 适合分布式协调（锁、选主、元数据），不适合大规模服务注册。
**Q2：Eureka 的自我保护机制是什么？**
A：当心跳丢失比例超过阈值（官方默认约 15%，以官方文档为准）时不再剔除实例，避免"注册中心自身网络抖动"被误判为"大量实例宕机"而清空服务列表。它体现 AP 取向：宁可返回过期实例（靠熔断与重试兜底），也不要错误摘除健康实例。
**Q3：ZooKeeper 临时节点怎么实现服务下线？**
A：实例创建 EPHEMERAL 临时节点并维持会话（session timeout 以配置为准），进程崩溃或断连超时后 ZK 自动删除节点并触发 Watch。注意 Watch 是一次性的，客户端必须重新注册；实例多时写与通知放大（羊群效应），因此更适合协调而非大规模注册。
**Q4：为什么消费方不能完全信任注册中心列表？**
A：列表存在陈旧窗口：实例宕机到剔除之间有超时与剔除延迟，AP 注册中心可能继续返回旧实例，推送也可能丢失。因此要三层兜底——客户端本地缓存 + 定时刷新 + 启动不因注册中心不可用而失败（fail-static）；调用层熔断、超时、重试其他实例；服务端优雅下线（先摘流量再退出，避免流量打到正在关闭的进程）。
### 8.3 高频追问与陷阱
- 陷阱一：认为"注册中心挂了全站就挂"。必须强调客户端缓存与 fail-static：注册中心短暂不可用只影响新变更感知，存量调用继续。
- 陷阱二：随意调大心跳间隔。间隔越大故障感知越慢，应按业务可容忍的宕机时间反推配置。
- 追问："元数据有什么价值？"答：支撑就近路由（同机房优先）、灰度（按版本标签）、权重分流与金丝雀发布，这是注册中心优于"配置文件写死 IP"的关键。
### 8.4 示例（注册中心对比表）
| 组件 | 一致性 | 健康检查 | 变更通知 | 典型场景与备注 |
| --- | --- | --- | --- | --- |
| Eureka | AP | 客户端心跳（默认 30s）+ 租约过期剔除（默认 90s）+ 自我保护 | 客户端定时拉增量 | Spring Cloud Netflix 老项目，已维护模式 |
| Nacos | AP（临时实例）/ CP（持久实例） | 心跳（默认 5s）+ 服务端健康检查 | gRPC 长连接推送 + 拉取兜底 | Spring Cloud Alibaba 首选，注册 + 配置一体 |
| Consul | CP | TCP/HTTP/脚本/TTL 多类型检查 | 阻塞查询/长连接 | 多数据中心与服务网格 |
| ZooKeeper | CP | 临时节点 + 会话超时 | Watch（一次性，需重注册） | 分布式锁/选主/元数据，不适合大规模注册 |
| etcd | CP | Lease 租约续约 | Watch 长连接 | K8s 控制面存储，强一致、watch 高效 |
### 8.5 一句话速记
> 服务发现的核心不是"注册"，而是"多久能感知故障"与"注册中心挂了业务还能不能跑"这两道时间与可用性题。

## 9. 分布式时序与时钟
### 9.1 核心原理
- **物理时钟不可靠**：石英振荡器存在**时钟漂移**（典型 10~100 ppm 量级，即每天误差可达约 1~8.6 秒，以硬件规格为准）；NTP 同步本身有误差且可能**跳变**——`ntpdate` 类工具是步进调整（时间瞬跳），`ntpd`/`chronyd` 默认渐进式 slew；虚拟机时钟还受宿主机负载、CPU 调度与热迁移影响。
- **危害清单**：用 wall clock 算耗时可能得到负值或超大值；定时任务在时间回拨后重复执行或漏触发；按时间戳排序的事件出现因果倒挂；Snowflake ID 因回拨产生重复；缓存 TTL、证书有效期、日志顺序异常。
- **Lamport 逻辑时钟**：本地事件 `C = C + 1`，接收消息时 `C = max(C_local, C_msg) + 1`。性质：若 `a → b` 则 `C(a) < C(b)`，但反之不成立，所以它只能**给事件定序**（配合进程 ID 打破并列），不能判断并发。
- **向量时钟**：每个节点维护长度为 N 的向量，发送时携带整个向量，接收时逐分量取 max 再自增自身分量；若 `V1 <= V2`（各分量都不大于）则因果先于，若互有分量大于对方则说明**并发冲突**——这是它比 Lamport 强的地方，代价是空间 O(N)。
- **工业实践**：Spanner 用 TrueTime（GPS + 原子钟，提供带不确定区间的时间，提交时等待区间过去以确定全局顺序）；CockroachDB 等用**混合逻辑时钟 HLC**（物理时间 + 逻辑计数）兼顾近似真实时间与因果。多数业务系统用"业务唯一 ID + 版本号"规避对物理时钟的强依赖。

### 9.2 面试问答
**Q1：为什么分布式下不能靠时间戳判断先后？**
A：因为各机器时钟不同步且有漂移与跳变，时间戳只能作为近似参考。判断"A 是否因果先于 B"要用 Lamport 或向量时钟；要按业务时间排序应在**产生事件的源头**打时间戳（或用中心化时间服务加不确定区间），而不是在接收端重新取时间。
**Q2：Lamport 时钟与向量时钟的区别？**
A：Lamport 能保因果定序但不能识别并发，空间 O(1)；向量时钟能识别并发冲突，空间 O(N)。工程上"需要排序用 Lamport/HLC，需要冲突检测与多副本合并用向量时钟或版本向量"。
**Q3：Snowflake ID 的时钟回拨怎么处理？**
A：分层处理：小幅回拨（如小于 5ms，可配置）自旋等待时钟追上；回拨较大则**拒绝发号并告警**，绝不能继续用旧时间戳发号；增强方案是启动时用 ZooKeeper/etcd 记录上次使用的最大时间戳，发现本机时间更早就拒绝启动，或拆出"回拨位/序号扩展"；根本方案是改用号段模式（DB/Redis 批量取号）或 ULID 等不依赖本地时钟的方案，细节见 [分布式锁与分布式ID](./03-分布式锁与分布式ID.md)。
**Q4：`System.currentTimeMillis()` 与 `System.nanoTime()` 怎么用？**
A：算耗时用 `nanoTime()`（单调时钟，不受 NTP 调整影响，不会出现负耗时），表示业务时间点用 `currentTimeMillis()`/`Instant`。边界：`nanoTime` 起点任意，不能跨进程比较，也不能持久化。
**Q5：时钟跳变对定时任务有什么影响？**
A：可能重复执行或漏执行——基于绝对时间判断"每天 00:00 执行"时，回拨会让条件再次满足，前跳则会跳过触发点。防护：调度用单调时钟算间隔；任务本身幂等并使用分布式锁；用"执行记录（业务日期唯一键）"去重，批处理记录已执行区间而非依赖当前时间。

### 9.3 高频追问与陷阱
- 陷阱一：认为"机器都装了 NTP 就没有时钟问题"。NTP 有误差、有跳变，虚拟机还会漂移，设计上必须假设时钟可能跳跃。
- 陷阱二：用时间戳做幂等键或"时间戳越大越新"的 LWW 冲突解决。前者会因回拨碰撞，后者会丢失并发写且依赖时钟质量。
- 追问："为什么不用全局自增 ID 保证顺序？"答：单点会成为瓶颈与故障点；中心化发号器（DB 号段、Redis INCR）提高吞吐但需考虑持久化——Redis 未持久化时重启会导致号段回退并可能产生重复，故要"号段 + 持久化 + 单调性校验"。

### 9.4 示例（时钟与定序方案对比表）
| 方案 | 依赖 | 判因果 | 识别并发冲突 | 成本 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| 物理时钟（NTP） | 时钟同步质量 | 否（仅近似） | 否 | 极低 | 日志时间、业务时间点、TTL |
| 单调时钟（nanoTime） | 无 | 否 | 否 | 极低 | 耗时统计、超时控制、限流窗口 |
| Lamport 逻辑时钟 | 计数器 | 是（单向保序） | 否 | O(1) | 事件全序、日志定序 |
| 向量时钟 | 向量 + 节点集合 | 是 | 是 | O(N) | 多副本冲突检测与合并（Dynamo 系） |
| HLC 混合逻辑时钟 | 物理 + 逻辑 | 是 | 否 | O(1) | 分布式数据库时间戳（近似真实时间 + 因果） |
| TrueTime | GPS + 原子钟 | 是（有区间） | 否 | 极高（专用硬件） | 全球强一致数据库，提交等待不确定窗口 |
| Snowflake / 号段 | 本地时钟 / DB | 否 | 否（仅唯一） | 低 | 分布式唯一 ID（必须处理时钟回拨） |

### 9.5 一句话速记
> 物理时钟只能"近似对齐"：因果顺序靠逻辑时钟、冲突检测靠向量时钟、唯一 ID 靠抗回拨设计。

## 10. 幂等设计的七种实现手段
### 10.1 核心原理
- **幂等定义**：同一操作执行一次与执行多次，对系统状态的最终影响相同。分布式下重复来源有四类：客户端超时重试、网关/Nginx 重试（见 [Nginx与网关限流](../04-中间件/05-Nginx与网关限流.md)）、MQ 重复投递与重平衡（见 [Kafka深度剖析](../04-中间件/02-Kafka深度剖析.md)）、补偿任务或人工重复触发。
- **七种手段（按成本从低到高）**：① 唯一索引/去重表（幂等键建唯一索引，插入冲突即视为重复）；② 数据库 upsert（`INSERT ... ON DUPLICATE KEY UPDATE` / `INSERT IGNORE`）；③ 乐观锁版本号（`UPDATE ... WHERE version = ?`，影响行数为 0 即失败）；④ 状态机（前置状态校验 + 单向流转，"已支付"不能再次支付）；⑤ Token 机制（先申请一次性凭证，提交时原子校验并删除）；⑥ 全局唯一 ID 判重（订单号、流水号作为业务唯一标识）；⑦ 分布式锁（把并发改串行，锁内"判重 + 执行"，见 [分布式锁与分布式ID](./03-分布式锁与分布式ID.md)）。
- **幂等键设计原则**：必须由业务语义构成（如"订单号 + 操作类型 + 业务版本"），保证同一次业务动作在任意重试路径上得到同一个键；并且**必须有唯一约束或原子 CAS 兜底**——"先查后写"在并发下一定存在竞态窗口。
- **边界条件**：幂等只保证"重复执行不产生额外副作用"，不保证"跨长时间窗的重复提交"（用户第二天再次支付属于新业务动作），也不解决并发下的顺序问题（乱序更新仍需版本号或队列串行）。
### 10.2 面试问答
**Q1：接口重复请求导致重复扣款，怎么处理？**
A：用业务唯一键做幂等并以唯一约束兜底，不依赖应用层"先查后写"。做法是上游在发起时携带幂等键（或由订单号派生），服务端把"幂等键 + 操作类型"写入去重表或业务表唯一键，冲突时返回上一次的处理结果而不是报错。边界：写入去重记录与业务执行必须在同一事务或可补偿，否则会出现"去了重但业务没执行"。
**Q2：为什么"先查后写"不能保证幂等？**
A：因为查询与写入不是原子的：两个并发请求可能都查到"不存在"，然后都执行扣款。解法是让**判重与执行落在数据库同一原子操作里**（唯一索引、CAS、`INSERT IGNORE` 后按影响行数分支），或用分布式锁串行化（代价是性能与锁失效风险）。
**Q3：Token 机制与唯一索引的区别？**
A：Token 是前置一次性凭证：服务端先发 token（存 Redis/DB），提交时**原子校验并删除**（推荐 Lua 脚本把校验与删除合并，或按 `DEL` 返回值判断），因此天然挡重放，代价是多一次交互与额外存储，适合提交类表单与秒杀下单。唯一索引是后置兜底，零额外交互但只能在落库时拦截。工程上常见组合：Token 挡前端重复提交，唯一索引挡漏网重放。
**Q4：MQ 重复消费怎么做到幂等？**
A：消费端幂等加顺序键。① 业务幂等（唯一键/状态机/CAS）是根本；② 幂等键用业务键（订单号）而非 offset，因为重平衡后 offset 语义会变；③ 需要顺序时按业务键分区串行（Kafka 同 partition 有序），避免乱序更新；④ 失败进死信队列并对账补偿，不能让"跳过"变成静默丢数据。
### 10.3 高频追问与陷阱
- 陷阱一：把分布式锁当幂等方案。锁只是让并发排队，锁内逻辑若不判重，第二次请求照样重复执行；锁超时还会让串行失效。
- 陷阱二：幂等键用时间戳或自增 ID。时间戳受回拨影响、自增 ID 每次请求都不同，都会让幂等失效。
- 追问："去重表数据怎么清理？"答：按幂等窗口保留（如 7 天）并用 TTL 或分区表按天删除，确保清理发生在业务可容忍窗口之后。
### 10.4 示例（去重表 + 冲突即返回首次结果）
```sql
CREATE TABLE idempotent_record (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  biz_key     VARCHAR(128)    NOT NULL COMMENT '业务唯一键：订单号+操作类型',
  result      VARCHAR(512)    DEFAULT NULL COMMENT '首次执行结果，供重复请求直接返回',
  create_time DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_biz_key (biz_key)        -- 唯一约束是幂等的最后一道防线
) ENGINE = InnoDB;
```
```java
try { recordMapper.insert(new IdempotentRecord(bizKey, null)); }     // 冲突即重复请求
catch (DuplicateKeyException e) { return recordMapper.findByBizKey(bizKey).getResult(); }
Object result = doBiz();                                            // 首次执行
recordMapper.updateResult(bizKey, JSON.toJSONString(result));
```
### 10.5 一句话速记
> 幂等的本质是"用业务唯一键把重复请求折叠成一次"，判重与执行必须原子化——唯一索引或 CAS 兜底，锁与 Token 只是辅助。

## 11. 分布式系统典型故障模式
### 11.1 核心原理
- **六种典型故障**：网络分区（消息丢失或延迟任意长，导致脑裂与双写）、超时与重试放大（一次慢请求被多级重试成数倍流量）、级联失败（下游拖垮上游线程池与连接池）、惊群与缓存击穿（热点数据大量并发回源）、脑裂（分区两侧各自选主并写入）、时钟跳变（定时任务重复、ID 重复、TTL 提前失效）。
- **三条放大通道**：① 重试通道——指数退避 + 抖动、重试次数上限、只重试幂等操作、设置总体重试预算，并配熔断快速失败；② 资源池通道——按依赖做舱壁隔离（独立线程池/信号量）、限制连接与排队上限、超时必须显式设置且小于上游超时；③ 心跳通道——多数派仲裁避免双主、用 fencing token 让旧主恢复后无法再写。
- **脑裂根因与解法**：根因是"两侧都认为自己可用"（分区 + 无仲裁 + 心跳超时自决策）。解法是任何写决策都必须经过多数派或外部仲裁（Raft 多数派、ZK/etcd 租约、共享存储 CAS、带 fencing 的 STONITH），并用幂等与去重降低双写的不可逆损失。
- **惊群根因与解法**：根因是大量请求同时发现缓存失效并同时回源。解法是单飞（SingleFlight）互斥重建、逻辑过期（后台异步刷新、读返回旧值）、热点探测与本地缓存、空值缓存加随机 TTL 防雪崩。
### 11.2 面试问答
**Q1：线上突然大量超时，排查与止损顺序是什么？**
A：先止损、再定位、后复盘。① 止损（分钟级）：限流与降级开关、扩容关键依赖、熔断异常依赖；② 定位（按链路）：看大盘（QPS、RT 分位、错误率、线程池与连接池水位、GC、慢查询、缓存命中率、MQ 堆积），用链路追踪找**首个异常节点**而非报错最多的节点；③ 根因：慢查询与缺索引、锁等待、连接池耗尽、缓存击穿、消息堆积、发布变更；④ 复盘补监控、容量、降级预案与压测。
**Q2：下游依赖挂了，为什么熔断而不只是重试？**
A：重试会把"下游慢"放大成"上游线程池满"，形成级联失败；熔断在错误率超阈值后快速失败，把资源让给健康链路并给下游恢复空间。配合关系是：超时（单次上限）→ 重试（少量、退避、幂等）→ 熔断（连续失败直接拒绝）→ 限流与降级（保护自身与下游），详见 [高并发高可用架构设计](./04-高并发高可用架构设计.md) 与 [CICD与监控告警](../07-工程化与DevOps/03-CICD与监控告警.md)。
**Q3：怎么在架构上避免脑裂？**
A：让"写权限"必须获得多数派或外部仲裁：用 Raft/ZAB 类共识做选主（少数派无法写）；用共享存储或注册中心的租约与 CAS 保证同一时刻只有一个主；对旧主复活用 fencing token（下游校验单调递增令牌）拒绝其写入。反面案例是"主备 + 心跳超时自动提升"却无仲裁。
**Q4：超时时间怎么定？**
A：按被调方 P99 延迟设定（经验值是 P99 的 1.5~2 倍，需按业务实测校准），并且**上游超时必须大于下游形成超时预算递减**，否则重试放大不可避免；再配合重试上限与熔断，避免"重试风暴"。
### 11.3 高频追问与陷阱
- 陷阱一：只答"加重试"或只答"加熔断"。成熟答法要讲清超时/重试/熔断/隔离/限流如何组合，并强调重试必须幂等。
- 陷阱二：把"注册中心挂了感知不到"当不可解问题。要答客户端本地缓存 + fail-static + 定时刷新。
### 11.4 示例（故障模式与防护对照表）
| 故障模式 | 典型成因 | 现象 | 防护手段 |
| --- | --- | --- | --- |
| 网络分区 | 机房/交换机故障、跨区专线抖动 | 节点互不可达，主从各写 | 多数派仲裁、租约 + fencing token、少数派拒绝写 |
| 超时与重试放大 | 无重试上限、重试不幂等、多级重试叠加 | QPS 倍增、下游被打挂 | 指数退避 + 抖动、重试预算、只重试幂等操作、熔断 |
| 级联失败 | 共享线程池/连接池被慢调用占满 | 上游线程池满、健康检查失败被摘流量 | 舱壁隔离、超时预算、熔断快速失败、限流兜底 |
| 惊群 / 缓存击穿 | 热点 key 同时失效、大量并发回源 | DB QPS 尖刺、RT 飙升 | SingleFlight 互斥重建、逻辑过期、本地缓存、随机 TTL |
| 脑裂（双主写） | 心跳超时自动提升且无仲裁 | 同一记录被两侧覆盖、数据错乱 | 多数派选主、ZK/etcd 租约、STONITH、下游 fencing 校验 |
| 时钟跳变 | NTP 步进调整、虚拟机漂移、闰秒 | 任务重复或漏跑、ID 重复、TTL 异常 | 单调时钟算耗时、幂等 + 执行记录、抗回拨 ID、时钟监控 |
### 11.5 一句话速记
> 分布式故障的本质是"局部问题被重试、资源池与心跳超时放大"，因此防护要点是给每条放大通道设上限并快速失败。

## 12. 分布式系统设计答题框架
### 12.1 核心原理
- **四步框架**：**定要求 → 选方案 → 谈兜底 → 谈度量**。顺序不能乱：先问清需求（一致性、可用性、延迟、规模、读写比例），再选技术栈，最后才谈容错与验收指标。
- **第一步定要求**要问出四个数：一致性要求（强一致还是最终一致、不一致窗口多长）、可用性目标（SLA）、延迟目标（P99）、数据规模与增长；再问清楚读写比例、幂等与顺序要求。
- **第二步选方案**按维度对号入座：数据模型决定存储（关系型/KV/搜索/时序）；容量决定分片（分片键 + 一致性哈希或预分片）；一致性决定副本与共识（单主 + 半同步、多数派共识、NWR 可调）；流程复杂度决定事务方案（本地事务 + TCC/Saga/消息最终一致），详见 [分布式事务](./02-分布式事务.md)。
- **第三步兜底**要给出具体开关与机制：超时/重试/熔断/隔离/限流/降级、幂等键与去重、对账与补偿任务、故障演练与容量压测、多机房容灾（说明同城双活与异地多活的一致性代价）。**第四步度量**要落到指标：RT 分位、错误率、可用性、复制延迟、MQ 堆积、对账差异数。
### 12.2 面试问答
**Q1：面试官说"设计一个分布式订单系统"，你怎么开口？**
A：先问需求再给方案，不要直接上技术栈。可以这样开场："我先确认几个关键点：订单量级与峰值 QPS、一致性要求（库存能不能超卖）、可用性目标、能接受的不一致窗口、是否需要跨机房容灾。"确认后再按四步框架展开。
**Q2：为什么必须给出一致性要求？**
A：因为一致性要求决定了整套架构：要求强一致就得用多数派共识或单主同步复制（延迟上升、少数派不可用）；可接受最终一致就能用异步复制与消息补偿（吞吐更高、成本更低）。不给要求就选方案，等于在凭感觉堆技术名词。
**Q3：需求从最终一致变成强一致，你怎么改答案？**
A：把"异步复制 + 消息补偿"换成"多数派共识 + 同步确认"，代价是延迟上升、分区期间少数派不可用（CAP 取舍），并把跨分片写收敛到单分片或引入协调者；同时说明降级策略从"允许短暂旧数据"改为"拒绝服务或降级写"。
**Q4：兜底和度量部分怎么讲才不空？**
A：兜底要给"可执行动作 + 开关 + 责任人"：例如"库存服务超时 200ms、重试 1 次且幂等、错误率 5% 熔断 10s、降级返回'下单人数过多'并通过配置中心开关控制"。度量要给"指标 + 阈值 + 验收方式"：例如"跨机房复制延迟 P99 < 1s、对账差异为 0、压测下单峰值 5 万 QPS 且 P99 < 300ms"。
### 12.3 高频追问与陷阱
- 陷阱一：一上来就报技术栈（Redis、Kafka、分库分表），被追问"为什么"就崩。先讲约束再讲选型才能自洽。
- 陷阱二：只讲正常流程，不讲失败路径与降级。面试官最想听的是"挂了会怎样、怎么发现、怎么恢复"。
- 追问："如果面试官质疑你的方案？"答：把分歧点落回约束（一致性、延迟、成本三者不可兼得），给出"在什么条件下我会改成方案 B"，展示权衡而不是争对错，更多开放题思路见 [场景设计与开放题](../08-面试实战/03-场景设计与开放题.md)。
### 12.4 示例（可直接背诵的答题模板）
```text
【第一步 定要求】量级（峰值 QPS/数据量）、一致性（强一致或最终一致 + 不一致窗口）、可用性（SLA）、延迟（P99）、读写比例、幂等与顺序要求；先说"我按 X 万 QPS、允许秒级最终一致设计，若要求强一致我会改 Y"。
【第二步 选方案】存储（分片键 + 分片数）、副本与共识（单主半同步 / Raft 多数派）、读写路径（缓存 + DB + 索引）、流程一致性（本地事务 + TCC/Saga/消息最终一致）、ID 与幂等（唯一索引 + 业务幂等键）。
【第三步 谈兜底】超时（P99×1.5~2）、重试（退避 + 幂等 + 上限）、熔断、隔离、限流、降级开关、对账补偿、演练与容灾。
【第四步 谈度量】RT 分位、错误率、可用性、复制延迟、MQ 堆积、对账差异数；说明最终一致的收敛时间窗如何验证。
【收尾】"需求若变成强一致，我会把 A 换成 B，代价是延迟上升、分区时损失少数派可用性 —— 这是 CAP 的取舍。"
```
### 12.5 一句话速记
> 分布式设计题的高分结构是"先定一致性要求 → 再选方案 → 再谈兜底与开关 → 最后给指标与验收方式"，全程体现取舍。

## 自测题（含答案要点）
1. **CAP 里的 C 指什么？为什么"三选二"不严谨？** 答：C 指线性一致性（不是 ACID 的 C，也不是"高可用"）；P 是网络的客观属性而非可选项，未分区时 C 与 A 可同时满足，准确表述是"分区期间只能在 C 与 A 之间取舍"。
2. **什么是 PACELC？补上了 CAP 的哪个缺口？** 答：Partition 时在 A/C 之间取舍，Else（不分区）时在 Latency/Consistency 之间取舍；补上了 CAP 未覆盖的"无分区场景"，解释了强一致必然带来更高延迟。
3. **BASE 三要素是什么？与 ACID 最关键的差异？** 答：基本可用、软状态、最终一致；最关键差异是一致性时间窗从 0 变成非 0，因此引入中间态与补偿、对账机制。
4. **线性一致与顺序一致的区别？线性一致等于可串行化吗？** 答：顺序一致只要全局全序 + 各进程程序序，线性一致还要尊重实时序；线性一致是单对象语义，与事务级的可串行化正交，两者兼具叫严格可串行化。
5. **因果一致为什么比最终一致强、又比线性一致便宜？** 答：它额外禁止因果倒挂（看到回复必看到原评论），实现只需随写携带依赖或向量时钟，不需要全局协调，所以分区期间仍可用。
6. **2PC 的同步阻塞与不一致分别怎么产生？3PC 为什么仍不安全？** 答：阻塞来自准备阶段后参与者持锁等待协调者决定；不一致来自"决定已做出但只送达部分参与者"。3PC 用 CanCommit 与超时自决减少阻塞，但分区时两侧可能一侧提交一侧回滚，根因是超时不能代表多数同意。
7. **Paxos 阶段一为什么要求 Acceptor 返回已接受过的值？** 答：让 Proposer 沿用可能已被选定的值（取编号最大的那个），配合"不再接受更小编号"的承诺，保证已选定值不被改写。
8. **Raft 中"已提交"如何定义？为什么不能仅凭多数派副本数提交旧任期日志？** 答：条目被多数派复制且 leader 推进 commitIndex 才算已提交；旧任期条目即便在多数派上也可能被持有更高任期日志的新 leader 覆盖，故需先提交一条本任期条目（如 no-op）间接提交。
9. **N=3 时 W=2,R=2 与 W=1,R=1 分别是什么一致性？** 答：前者 4>3，读写集合必相交，多数派强一致且容忍 1 个副本故障；后者 2<=3，可能读到旧值，只能最终一致（靠读修复收敛）。
10. **一致性哈希与虚拟节点各解决什么？扩容迁移量是多少？** 答：一致性哈希把扩容迁移量降到约 K/n，虚拟节点解决分布倾斜与故障压力集中；Redis Cluster 用的是固定 16384 槽而非一致性哈希。
11. **重复请求导致重复扣款怎么做幂等？为什么"先查后写"不行？** 答：用业务唯一键（订单号 + 操作类型）配合唯一索引、CAS、状态机、Token 等手段；"先查后写"存在竞态窗口，并发下两个请求可能都查到"不存在"，必须让判重与执行原子化。
12. **Lamport 时钟、向量时钟、Snowflake 各解决什么问题？时钟回拨怎么处理？** 答：Lamport 保因果定序但不能识别并发；向量时钟能识别并发冲突（空间 O(N)）；Snowflake 生成唯一 ID 但依赖时钟。回拨小则自旋等待，回拨大则拒绝发号并告警，或用 ZK 记录上次时间戳、改用号段模式。
13. **线上大面积超时的排查顺序？脑裂与惊群分别怎么防？** 答：先止损（限流/降级/扩容/熔断），再定位（指标 + 链路追踪找首个异常节点），最后复盘补监控与容量；脑裂靠多数派仲裁 + 租约 + fencing token，惊群靠 SingleFlight 互斥重建 + 逻辑过期 + 本地缓存。

## 背诵卡片
1. CAP 的 C = 线性一致性，A = 非故障节点必须有限时间内响应，P = 网络分区的客观属性。
2. CAP 不是三选二：P 是前提，只有分区期间才在 C 与 A 之间取舍。
3. 不分区时的取舍是"延迟 vs 一致性"，即 PACELC 的 Else 分支。
4. 真实多机系统不存在 CA，所谓 CA 实际是单机或放弃分区容忍。
5. CAP 只约束分区期间，分区恢复后要靠读修复与反熵收敛。
6. AP 不等于放弃一致性，而是承诺最终收敛，且必须给出时间窗。
7. BASE = 基本可用 + 软状态 + 最终一致。
8. ACID 的一致性窗口是 0，BASE 的一致性窗口由业务定义并有对账验证。
9. 一致性强弱：线性一致 > 顺序一致 > 因果一致 > 会话语义 > 最终一致。
10. 线性一致约束单对象实时序，可串行化约束事务等价串行，二者正交。
11. 读己之写靠主库路由、粘滞会话、位点等待或本地缓存实现；单调读是为了防止时间倒流。
12. 同一系统不同配置可能落在 C/A 不同侧：Kafka 看 acks 与 min.insync.replicas。
13. Redis Cluster 默认 AP（主从异步复制），故障转移可能丢最近写；MySQL 异步复制同理。
14. 2PC 两阶段：Prepare（执行并持锁、投票）+ Commit/Abort；三宗罪是阻塞、协调者单点、不一致窗口。
15. 3PC 增加 CanCommit 与超时自决，减少阻塞但不解决分区不一致。
16. 要一致性靠多数派共识（Raft/Paxos），要可用性靠 TCC/Saga 等业务补偿。
17. Paxos 角色：Proposer、Acceptor（2F+1）、Learner；值被多数派接受即选定。
18. Paxos 承诺"不再接受更小编号"，因此已选定值不会被改写；活锁靠随机退避或稳定 leader 解决。
19. FLP 说明纯异步网络下无法同时保证安全与终止，工程上用超时与随机化绕过。
20. Raft 三件套：Leader 选举、日志复制、安全性约束；随机选举超时避免选票分裂。
21. Raft 日志匹配性质：同 index 同 term 相同则之前条目全部相同。
22. Raft 只提交本任期日志，旧任期条目靠提交本任期条目间接提交；成员变更用单节点变更或联合共识。
23. Quorum：W+R>N 可读最新（强一致），W+R<=N 只能最终一致；N=3、W=2、R=2 容忍 1 个副本故障。
24. 一致性哈希扩容迁移量约 K/n，取模哈希几乎全量迁移；虚拟节点解决倾斜，与副本数是两个维度。
25. 故障感知时间 ≈ 心跳周期 × 失败判定次数 + 剔除延迟。
26. 注册中心要配客户端本地缓存与 fail-static；ZK 临时节点靠会话超时实现"进程死即下线"，但 Watch 一次性。
27. TCP 探活只证明端口在监听，不代表业务可用；探活接口必须轻量且无副作用。
28. 物理时钟会漂移与跳变，算耗时用单调时钟 nanoTime；Snowflake 必须处理时钟回拨。
29. 幂等七手段：唯一索引/去重表、upsert、乐观锁版本号、状态机、Token、全局唯一 ID 判重、分布式锁。
30. 幂等键必须来自业务语义，判重与执行必须原子化；故障防护组合是"超时 → 退避重试（幂等）→ 熔断 → 隔离限流降级"。
