## 1. 系统设计通用答题框架与评分点
### 1.1 核心原理

1. **需求澄清**：功能需求 3~5 条、非功能需求（QPS/延迟/可用性/数据量/一致性）、明确不做什么。
2. **规模估算**：峰值 QPS = 均值 × 3~10；存储 = 日增条数 × 单条大小 × 保留天数；机器数 = 峰值 QPS ÷ 单机承载。
3. **核心 API**：3~5 个关键接口，写清方法、路径、入参出参、幂等键。
4. **数据模型**：核心表的唯一键、索引、分片键，说明存 MySQL 还是 Redis 及原因。
5. **高层架构**：接入层（DNS/CDN/Nginx/网关）→ 应用层（无状态集群）→ 中间件层（Redis/MQ/ES）→ 存储层（分库分表/对象存储），一层一句话。
6. **核心流程**：挑 1~2 条关键链路讲时序，说清同步还是异步、写哪里读哪里。
7. **瓶颈与优化**：先找单点、热点 key、热点行、慢 SQL、连接数上限，再给缓存、分片、异步、批量、降级手段。
8. **容错与演进**：限流、熔断、降级、重试、幂等、超时、对账、监控告警，以及数据涨 10 倍后的扩容路径。
9. **取舍说明**：每条关键决策说清"选了什么、放弃了什么、什么条件下改回"。

### 1.2 面试问答

**Q1：为什么必须先澄清需求？**
A：题干永远信息不足，不同假设导出完全不同的架构（日增 100 万单单库够用，日增 10 亿单必须分库分表），只问会改变设计决策的问题。

**Q2：估算算错会直接挂吗？**
A：不会因不精确挂，但因"不敢估"或量级差千倍挂；口算用 1 天≈10^5 秒近似并声明示例假设，目的是验证架构选择，口径参见 [04-高并发高可用架构设计.md](./04-高并发高可用架构设计.md)。

**Q3：数据模型给到什么粒度？**
A：给核心表的关键字段、唯一键、索引、分片键，并说明哪个约束保证幂等、哪个字段让 90% 查询命中单分片；非核心表一句话带过。

**Q4：架构图怎么用文字讲？**
A：按请求流向讲"CDN 回源 Nginx 做七层限流 → 网关鉴权路由 → 无状态服务 → 先读 Redis 未命中回源 MySQL"，并主动说明哪些组件是单点、如何多实例，限流实现见 [05-Nginx与网关限流.md](../04-中间件/05-Nginx与网关限流.md)。

**Q5：瓶颈怎么找？**
A：按四率（带宽、连接、CPU、磁盘 IO）加三热（热点 key、热点行、热点分片）找，按"最先被打满"排序讲，通常顺序是 DB 写入 → Redis 带宽 → 应用 CPU → 网络。

**Q6：取舍与演进怎么讲？**
A：每条决策说清"选了什么、放弃什么、触发条件是什么"，至少准备三组：强一致 vs 高吞吐、推 vs 拉、精确 vs 近似；演进要给阈值（如单表超 2000 万行就分片），原理见 [01-分布式理论与CAP-BASE.md](./01-分布式理论与CAP-BASE.md)。
### 1.3 高频追问与陷阱

- 一上来就画图、只堆技术名词不讲选型理由、不做容量估算，都会被判为工程思维不足。
- 不提幂等、不提异常链路（缓存击穿、MQ 重复、主从延迟），是支付与库存题最致命的漏项。
- 回避取舍、不提监控运维与降级开关，等于交付一个不能上线的设计。

### 1.4 示例

| 评分点 | 权重 | 达标表现与扣分点 |
| --- | --- | --- |

## 2. 短链系统设计
### 2.1 核心原理

短链是读多写极少的 KV 服务：发号（雪花/号段）→ 62 进制生成短码 → MySQL 唯一索引存映射 → Redis 扛读 → 302 跳转，点击统计走异步埋点。
规模估算（示例假设）：日新增 1000 万条、读写比 1:100 → 跳转峰值约 1.2 万 QPS，单条 500B、日增 5GB，MySQL 按 short_code 哈希分 16 片足够。

### 2.2 面试问答

**Q1：短码怎么生成、如何防遍历？**
A：用"雪花/号段 ID → 62 进制"，6 位可表示 568 亿、7 位约 3.5 万亿，天然无冲突且长度可控；防遍历对 ID 做异或洗牌混淆，见 [03-分布式锁与分布式ID.md](./03-分布式锁与分布式ID.md)。

**Q2：跳转为什么用 302 而不是 301？**
A：301 被浏览器长期缓存后请求不再回源，点击统计与风控失效；302 每次都回服务端可统计可拦截，性能代价靠本地缓存加 Redis 兜住，仅"纯跳转且无需统计"的链接用 301。

**Q3：映射怎么存、怎么防穿透？**
A：Redis 为主存、MySQL 为权威（short_code 唯一索引），读链路本地缓存 → Redis → DB 回填；不存在的短码用布隆过滤器或空值缓存挡住，避免批量无效短码打穿 DB，分片策略见 [03-MySQL调优主从与分库分表.md](../02-数据库/03-MySQL调优主从与分库分表.md)。

**Q4：点击量与 UV 怎么统计？**
A：跳转链路只写 Redis（点击 INCR、UV 用 HyperLogLog 近似，误差约 0.81%），定时批量落统计表；要求精确 UV 时按 uid 用 Bitmap（1 亿人约 12.5MB/天），并与 DB 对账修正。
### 2.3 高频追问与陷阱

- 同域 vs 独立域名：同域省成本但每请求带主站 Cookie、被拉黑会连累主域，对外推广用独立短域名做风险隔离。
- 答不出短码长度与容量的关系，或忽略过期与回收（到期短码能否复用、是否需要自定义别名）。
- 把统计写成同步链路，把跳转 P99 从几毫秒拉到几十毫秒。

### 2.4 示例

```sql
CREATE TABLE t_short_link (
  short_code   VARCHAR(10)  NOT NULL COMMENT '62进制短码，唯一',
  long_url     VARCHAR(2048) NOT NULL,
  long_url_md5 CHAR(32)     NOT NULL,
  expire_time  DATETIME     DEFAULT NULL COMMENT 'NULL 表示永久',
  status       TINYINT      NOT NULL DEFAULT 1,
  PRIMARY KEY (short_code),
  KEY idx_md5 (long_url_md5)
) COMMENT='按 short_code 哈希分 16 片';
```
### 2.5 一句话速记

**发号加 62 进制出短码、Redis 扛读 MySQL 兜底、302 保统计、HLL/Bitmap 算 UV、独立域名做风险隔离。**

## 3. 秒杀/抢购系统设计
### 3.1 核心原理

秒杀是分层削峰：前端静态化 + 按钮置灰 + 验证码 → CDN → 网关限流防刷 → Redis Lua 预扣 → MQ 异步下单 → DB 扣减落库，全程要求幂等、限购、不超卖不少卖、可降级。
规模估算（示例假设）：10 万件库存、1 秒涌入 50 万请求 → 峰值 50 万 QPS，Redis 单分片约 10 万 QPS，故按库存 key 分片并把网关限流压到 5 万 QPS 再放行。

### 3.2 面试问答

**Q1：怎么同时防超卖和少卖？**
A：Redis Lua 原子判断并预扣（含"是否已抢"标记）挡住无效请求，DB 用 `UPDATE stock SET num=num-1 WHERE id=? AND num>0` 兜底防超卖；少卖靠延迟消息关单回补加活动结束对账（Redis 余量 vs DB 余量 vs 订单数）修正。

**Q2：同一用户重复抢怎么办？**
A：一人一单用 Redis Set 前置拦截、DB `uk(activity_id, user_id)` 唯一索引作最终防线；判定与扣减放在同一个 Lua 脚本里，避免"扣了库存没记用户"的部分失败，插入冲突按"已参与"返回。

**Q3：为什么用 MQ 异步下单？**
A：预扣成功即视为"抢到"，创建订单可异步、可限速、可重试，把峰值削平；MQ 需同步刷盘加多副本防丢，消费端用订单号唯一索引幂等，前端返回"排队中"再轮询结果，见 [01-消息队列与RocketMQ.md](../04-中间件/01-消息队列与RocketMQ.md)。

**Q4：如何防黄牛、怎么做预案？**
A：风控用设备指纹 + IP/UID 频控 + 答题验证码 + 实名限购 + 收货地址去重，规则热更新并灰度；上线前全链路压测，准备限流阈值、降级开关与队列水位告警，超阈值直接返回"活动火爆"。
### 3.3 高频追问与陷阱

- 只说"用 Redis 扣库存"，答不出 Redis 扣减成功但下单失败、Redis 宕机后如何恢复库存。
- 忽略 MQ 至少一次投递带来的重复消费，消费端没有幂等约束。
- DB 层用 `SELECT ... FOR UPDATE` 抢锁，高并发下连接池瞬间被打满。

### 3.4 示例

```sql
CREATE TABLE t_seckill_order (
  order_no    VARCHAR(32) NOT NULL COMMENT '雪花ID转业务订单号',
  activity_id BIGINT      NOT NULL,
  user_id     BIGINT      NOT NULL,
  goods_id    BIGINT      NOT NULL,
  status      TINYINT     NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已取消',
  create_time DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (order_no),
  UNIQUE KEY uk_activity_user (activity_id, user_id) COMMENT '一人一单最终防线'
) COMMENT='按 user_id 分片';
```
### 3.5 一句话速记

**网关限流挡峰、Lua 原子预扣、MQ 异步下单、DB 条件更新兜底、延迟消息关单回补、结束对账防少卖。**

## 4. IM 即时通讯系统设计
### 4.1 核心原理

主线是长连接 + 路由 + 可靠投递：客户端与 Netty/WebSocket 连接网关保持长连，网关维护 uid → 网关路由，逻辑服务落库后推给接收方所在网关，离线消息落表待上线拉取。
规模估算（示例假设）：DAU 500 万、人均 50 条 → 日投递 2.5 亿条、峰值约 8700 QPS；单机维持 5 万~10 万长连接，故网关约 50~100 台。

### 4.2 面试问答

**Q1：长连接为什么选 WebSocket/Netty？**
A：轮询浪费带宽且延迟取决于间隔，WebSocket 全双工带心跳与二进制帧，Netty 单机可稳载数万到十万连接；边界是心跳 30 秒、空闲踢除、连接数水位告警，跨机房就近接入并同步路由表。

**Q2：消息怎么保证不丢、不重？**
A：客户端 ACK + 服务端消息表持久化 + 超时指数退避重发，接收端按服务端下发的 msg_id（雪花 ID）去重，见 [03-分布式锁与分布式ID.md](./03-分布式锁与分布式ID.md)。

**Q3：离线消息与消息有序怎么处理？**
A：离线消息落离线表，上线时按会话拉取并上报本地最大 seq，只返回更大的；有序只需会话级 seq 单调递增（Redis INCR 或 DB 行锁生成），全局有序代价过高且无必要。

**Q4：群聊用写扩散还是读扩散？**
A：小群（约 ≤500 人）写扩散，读路径极快；万人群读扩散，在线成员推送加未读聚合，并限制大群发言频率，群内消息按会话 seq 各存一份。
### 4.3 高频追问与陷阱

- 只说 Netty 高性能，答不出单机连接上限、每连接内存占用与心跳参数。
- 在线状态放单机内存：应放 Redis（uid → 网关地址）并 TTL 加心跳续期。
- 多端登录与重发都会产生重复消息，缺少 msg_id 唯一约束就会重复展示。

### 4.4 示例

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| msg_id | BIGINT | 雪花 ID，客户端幂等键，唯一索引 |
| session_id | BIGINT | 会话 ID，与 seq 组成联合主键 |
| seq | BIGINT | 会话内递增序列号，保序与增量拉取 |
| content | TEXT | 消息体，超长内容存对象存储只留引用 |
| status | TINYINT | 0 未读 1 已读，已读回执按会话聚合更新 |
### 4.5 一句话速记

**Netty 长连接加 Redis 路由表、消息表加 ACK 重发保不丢、msg_id 去重、会话级 seq 保序、小群推大群拉。**

## 5. Feed 流/朋友圈设计
### 5.1 核心原理

Feed 是收件箱模型：先写进关注者的时间线（推）或读时聚合（拉），生产上用推拉结合，时间线存 Redis ZSet（score = 时间戳）并按 score 游标分页。
规模估算（示例假设）：DAU 2000 万、人均关注 200 人、人均发 1 条 → 纯写扩散日写 40 亿条，因此必须对粉丝数超阈值的大 V 改走读扩散。

### 5.2 面试问答

**Q1：推模式、拉模式怎么选？**
A：纯推写放大 O(粉丝数)，大 V 一条要写百万次；纯拉读时聚合慢且热点明显；生产用推拉结合：粉丝数 < 10 万走推、≥ 10 万走拉，读时把大 V 新内容与自身时间线归并排序。

**Q2：时间线怎么存、怎么分页？**
A：ZADD key score=timestamp member=feedId，用 ZREVRANGEBYSCORE 游标翻页（禁用 offset，避免插入新内容导致重复或漏读）；单 key 只留最近约 1000 条防大 key，历史回源 DB。

**Q3：大 V 问题怎么解？**
A：大 V 内容单独缓存（本地加 Redis），"大 V 列表"维护在配置中心且阈值可动态调整，读时间线时合并拉取；大 V 发帖同时写自己的发件箱供别人拉取。

**Q4：去重与排序怎么做？**
A：member 用 feedId 天然去重（取消关注再关注会重复写）；排序用时间加权重的复合 score，权重由互动率异步打分回写，不阻塞读路径，策略变更要能灰度，缓存治理见 [05-Redis高可用与缓存治理.md](../02-数据库/05-Redis高可用与缓存治理.md)。
### 5.3 高频追问与陷阱

- 新用户冷启动时间线为空，需回源活跃内容做填充。
- 不限制时间线长度，单 ZSet 上百万成员造成大 key 与慢查询。
- 分页用 offset，插入新内容后出现重复或漏读。

### 5.4 示例

| 维度 | 推模式 | 拉模式 | 推拉结合 |
| --- | --- | --- | --- |
| 写成本 | O(粉丝数) | O(1) | 折中可控 |
| 读成本 | O(1) | O(关注数) 聚合 | 低 |
| 大 V 友好度 | 差 | 好 | 好 |
| 结论 | 普通用户 | 大 V | 生产首选 |
### 5.5 一句话速记

**普通用户推、大 V 拉、ZSet 存时间线、score 游标翻页、限长防大 key、权重排序异步回写。**

## 6. 订单系统与支付设计
### 6.1 核心原理

两条主线是状态机与资金安全：状态迁移必须显式合法（待支付→已支付→已完成／已关闭／退款中→已退款），所有外部回调都要验签加幂等；超时关单与支付回调是并发冲突最激烈的点。
规模估算（示例假设）：日订单 500 万、峰值 3000 TPS，单条订单含明细约 2KB → 日增 10GB，订单表必须按 user_id 分片。

### 6.2 面试问答

**Q1：订单状态机怎么设计？**
A：用"状态 + 事件 + 合法迁移"驱动，更新带前置状态条件：`UPDATE t_order SET status=1 WHERE order_no=? AND status=0`，受影响行数为 0 说明状态已变需幂等返回，避免回调与关单互相覆盖，事务语义见 [02-分布式事务.md](./02-分布式事务.md)。

**Q2：支付回调怎么做幂等？**
A：验签 → 渠道流水号唯一索引去重 → 状态机条件更新 → 同事务写账务流水；严禁在回调里做发货发券等耗时动作，重活丢 MQ，重复回调直接返回成功。

**Q3：超时关单怎么实现？**
A：优先 RocketMQ 延迟消息（精度高、不必轮询全表，延迟级别以官方文档为准），兜底用时间轮加 Redis ZSet 或按 create_time 索引分片扫描；关单成功后必须回补库存与优惠券。

**Q4：对账怎么做？**
A：T+1 三方对账（本地账、渠道账、清算账），差异分四类处理：本地多单补单、渠道多单补记、金额不符挂账人工、状态不符以渠道为准修正，全部落差错表驱动跟进。
### 6.3 高频追问与陷阱

- 只用订单号唯一索引防重，忽略同一笔支付可能带来不同订单号的重复入账（应按渠道流水号）。
- 关单与支付并发时不校验状态，出现"已支付但订单被关闭"，资金与货不一致。
- 回调里同步发货发券，渠道重试导致业务被重复触发。

### 6.4 示例

```sql
CREATE TABLE t_order (
  order_no    VARCHAR(32)  NOT NULL COMMENT '业务订单号，唯一',
  user_id     BIGINT       NOT NULL,
  amount      DECIMAL(10,2) NOT NULL,
  status      TINYINT      NOT NULL DEFAULT 0 COMMENT '0待支付 1已支付 2已关闭 3退款中 4已退款 5已完成',
  expire_time DATETIME     NOT NULL COMMENT '关单时间点',
  version     INT          NOT NULL DEFAULT 0 COMMENT '乐观锁',
  PRIMARY KEY (order_no),
  KEY idx_user_status (user_id, status),
  KEY idx_expire (status, expire_time)
) COMMENT='按 user_id 分片；幂等靠 order_no 唯一索引 + 渠道流水号唯一索引';
```
### 6.5 一句话速记

**状态机加条件更新防并发、渠道流水号防重复入账、延迟消息关单回补、T+1 三方对账兜底资金。**

## 7. 订单表分库分表与分布式 ID
### 7.1 核心原理

分库分表要回答三个问题：分片键选谁、分几片、怎么查。订单有用户维度（我的订单）与订单号维度（客服、支付回调）两条链路，故采用"user_id 分片 + 订单号内嵌基因"，分片算法用 hash 取模，扩容走双写加校验。
规模估算（示例假设）：5 亿行订单、单行 1.5KB → 约 750GB，单库建议 ≤500GB、单表 ≤2000 万行，因此至少 8 库 64 表。

### 7.2 面试问答

**Q1：分片键用 user_id 还是 order_id？**
A：以 user_id 为主分片键，因为 C 端最高频查询是"我的订单"，必须单分片命中；订单号查询靠基因法或"订单号 → 用户"映射表兜住低频场景。

**Q2：基因法怎么做？**
A：生成订单号时把 `user_id % 分片数` 的低位拼进订单号，使订单号与分片路由强绑定，免维护映射表也免广播查询；分片数要一次规划足够（如 1024 个逻辑分片映射到 N 个物理库）。

**Q3：跨片分页与聚合怎么办？**
A：禁止跨片深分页（LIMIT 1000000,10 会把所有分片拖垮），改为按用户或时间收敛条件；管理端报表与多条件检索走 ES 或离线数仓，见 [04-Elasticsearch搜索与调优.md](../04-中间件/04-Elasticsearch搜索与调优.md)。

**Q4：扩容迁移怎么做？**
A：双写 → 历史数据迁移 → 校验（行数、抽样字段、金额汇总）→ 按用户灰度切读 → 停双写，全程保留回滚开关，方案细节见 [03-MySQL调优主从与分库分表.md](../02-数据库/03-MySQL调优主从与分库分表.md)。
### 7.3 高频追问与陷阱

- 忘记唯一约束在分片后只是"分片内唯一"，全局唯一要靠雪花趋势唯一或去重表。
- 用 order_id 分片却按 user 查，只能广播查询，性能灾难。
- 逻辑分片预留太小，后续只能双倍扩容，迁移量巨大。

### 7.4 示例

| 查询场景 | 分片键与路由 | 说明 |
| --- | --- | --- |
| 我的订单列表 | user_id 直接命中单库 | 高频，必须快 |
| 订单详情（有订单号） | 基因法解析分片 | 免映射表 |
| 客服按手机号查 | 映射表或 ES | 低频，可容忍慢 |
| 运营报表统计 | 离线数仓 | 不查线上库 |

```text
【分片路由】分片号 = hash(user_id) % 1024；物理库 = 分片号 / 128，物理表 = 分片号 % 128
【订单号生成】雪花 ID（时间 + 机器位）拼接 user_id 低 10 位，可反推分片
```
### 7.5 一句话速记

**user_id 分片、订单号嵌基因、逻辑分片预留到 1024、禁跨片深分页、双写迁移加校验。**

## 8. 排行榜系统设计
### 8.1 核心原理

排行榜是"带权有序集合的 TopN 查询"，Redis ZSet 是首选：ZINCRBY 加分、ZREVRANGE 取 TopN、ZREVRANK 查名次，均为 O(logN)。设计要点是分段榜（日/周/总）、分片榜、实时与离线合并、名次精确或近似。
规模估算（示例假设）：DAU 100 万、人均 20 次积分变动 → 日 2000 万次更新、峰值约 700 QPS；单 ZSet 100 万成员约几十 MB，可用但要监控大 key。

### 8.2 面试问答

**Q1：为什么用 ZSet 而不是 MySQL 排序？**
A：`ORDER BY score DESC LIMIT 100` 在千万行上必然 filesort，且高频更新带来行锁与写放大；ZSet 写入与取 TopN 都是对数级，归档榜再落库或数仓。

**Q2：日榜、周榜、总榜怎么组织？**
A：同一份数据写多套 key（rank:daily:20240501、rank:weekly:2024W18、rank:total），用 Pipeline 批量提交减少 RTT；日榜设 TTL 自动清理，周榜定时合并日均值生成。

**Q3：榜单分页与名次怎么给？**
A：TopN 精确、长尾近似：ZRANGE 的 offset 控制在 1000 以内，超出范围返回"约第 N 名"，或用分段桶记录分数区间与人数估算名次。

**Q4：热点与大 key 怎么防？**
A：Top100 缓存在应用本地（秒级过期），ZSet 按赛区或品类分片，成员数超阈值触发归档；Redis 故障后按 DB 或数仓重算重建榜单，见 [04-Redis数据结构与核心原理.md](../02-数据库/04-Redis数据结构与核心原理.md)。
### 8.3 高频追问与陷阱

- 只用 ZSet 不落库，Redis 故障后榜单无法重建。
- 忽略并发加分顺序，同一用户高频加分应先在应用内累加再批量回写。
- 作弊清分后忘记同步清理缓存，需要提供"重算并覆盖"通道。

### 8.4 示例

| 方案 | 写入 | TopN 查询 | 名次查询 | 结论 |
| --- | --- | --- | --- | --- |
| Redis ZSet | O(logN) | O(logN+M) | O(logN) | 实时榜首选 |
| MySQL ORDER BY | 高（索引维护） | 慢（深翻页） | 极慢 | 仅归档 |
| 离线数仓 | 批量 | 快 | 快 | T+1 榜 |
### 8.5 一句话速记

**ZSet 做实时榜、多周期多 key、TopN 精确长尾近似、本地缓存抗热点、定时归档可重建。**

## 9. 附近的人/地理位置服务
### 9.1 核心原理

LBS 先把二维坐标转成可前缀匹配的 GeoHash 或网格做粗筛，再算精确距离排序：Redis GEO 用 GEOADD/GEOSEARCH 做在线半径查询，ES 用 geo_point 做距离过滤与排序，MySQL 只能用矩形边界加经纬度联合索引粗筛。
规模估算（示例假设）：1 亿用户、每人 1 条位置、上报间隔 60 秒 → 约 170 万次/秒写入不可接受，故上报降频到 5 分钟且只维护活跃用户位置。

### 9.2 面试问答

**Q1：GeoHash 是什么、要注意什么？**
A：GeoHash 把经纬度交替二分编码成字符串，前缀相同表示邻近，可在字符串上做范围匹配；必须注意边界问题：相邻两点可能前缀不同，所以查询要覆盖当前格子加周围 8 个格子。

**Q2：Redis GEO 还是 ES geo_point？**
A：服务端在线检索用 Redis GEO（单命令完成半径查询并返回距离，延迟极低），需要与标签、价格、评分组合过滤、分页与聚合时用 ES geo_point，见 [04-Elasticsearch搜索与调优.md](../04-中间件/04-Elasticsearch搜索与调优.md)。

**Q3：只用 MySQL 怎么做"附近 5 公里"？**
A：先用 `lat BETWEEN ? AND ?` 与经度差按 cos(纬度) 修正后的 `lng BETWEEN` 走联合索引粗筛，再对候选集（限几百条）算 Haversine 精确距离并 ORDER BY。

**Q4：位置更新与隐私怎么处理？**
A：位置只写内存态 Redis 并定期快照，用户可关闭可见性或开隐身；对外只展示"距离 300 米"这类模糊值，不返回精确坐标，并保留授权与审计记录。
### 9.3 高频追问与陷阱

- 漏掉 GeoHash 边界问题，只查当前格子会丢掉隔壁格子里的点。
- 粗筛后忘记做精确距离过滤，返回的结果实际超出请求半径。
- 位置全量常驻单个 Redis key，造成大 key 与阻塞。

### 9.4 示例

| GeoHash 长度 | 单元宽 × 高 | 适用场景 |
| --- | --- | --- |
| 5 位 | 约 4.9km × 4.9km | 附近 5 公里 |
| 6 位 | 约 1.2km × 0.61km | 街道级筛选 |
| 7 位 | 约 153m × 153m | 精确到楼栋 |
### 9.5 一句话速记

**GeoHash 前缀找邻居、Redis GEO 做在线半径、ES 做条件组合、MySQL 矩形粗筛加 Haversine 精算。**

## 10. 优惠券与库存扣减设计
### 10.1 核心原理

优惠券有四个实体：券模板（规则）、券批次（发行量与有效期）、用户券码（领取结果）、核销记录。难点与秒杀同源：发券不超发、一人一单、一券一用，方案是 Redis 预扣加 DB 唯一索引加超时释放。
规模估算（示例假设）：单活动发 100 万张券、瞬时领取峰值 5 万 QPS → Redis 预扣抗峰、DB 异步批量落库，用户券表按 user_id 分片。

### 10.2 面试问答

**Q1：领券怎么防超发？**
A：Redis DECR 或 Lua 原子预扣，DB 侧用 `UPDATE ... SET remaining=remaining-1 WHERE batch_id=? AND remaining>0` 兜底，最后对账；预扣成功而落库失败必须回补 Redis 量并告警，避免少发。

**Q2：一人一张怎么保证？**
A：唯一索引 `uk(batch_id, user_id)` 是最终防线，Redis Set 只做前置快速拦截；插入冲突要捕获并按"已领取"返回，不要抛 500，幂等设计见 [02-分布式事务.md](./02-分布式事务.md)。

**Q3：券怎么和订单绑定？**
A：下单时锁券（状态改锁定并写 order_no，条件更新防并发抢用同一张券），支付成功后置已使用，取消或关单则释放；券释放要回补活动库存并记录流水。

**Q4：券过期怎么处理？**
A：逻辑过期加懒清理加定时扫描：查询时判断 expire_time，定时任务按 expire_time 索引分批更新状态，过期记录保留用于审计与运营分析。
### 10.3 高频追问与陷阱

- 只信 Redis 计数不落库，Redis 重启后库存与券全部丢失。
- 券状态机缺失，领券、锁券、核销、作废、过期互相覆盖造成脏数据。
- 叠加与互斥规则分散在多处，优惠计算口径不一致。

### 10.4 示例

```sql
CREATE TABLE t_user_coupon (
  coupon_no   VARCHAR(32) NOT NULL COMMENT '券码，雪花生成，唯一',
  user_id     BIGINT      NOT NULL,
  batch_id    BIGINT      NOT NULL,
  status      TINYINT     NOT NULL DEFAULT 0 COMMENT '0未使用 1已锁定 2已使用 3已过期 4已作废',
  order_no    VARCHAR(32) DEFAULT NULL COMMENT '锁定时写入',
  expire_time DATETIME    NOT NULL,
  PRIMARY KEY (coupon_no),
  UNIQUE KEY uk_batch_user (batch_id, user_id) COMMENT '一人一单最终防线',
  KEY idx_user_status (user_id, status),
  KEY idx_expire (status, expire_time)
) COMMENT='按 user_id 分片';
```
### 10.5 一句话速记

**Redis 预扣防超发、唯一索引防重复领、锁券绑单防重复用、过期懒清理加定时扫、全程对账。**

## 11. 点赞、评论与计数系统
### 11.1 核心原理

点赞是高频写加去重加计数的组合：Redis Set 或 Bitmap 存去重关系并原子计数，异步落库，DB 用 `uk(content_id, user_id)` 兜底；评论是树形结构，需在查询效率与写入复杂度之间选模型。
规模估算（示例假设）：单条热门内容 100 万赞，一个 Set 存百万成员属大 key 风险，故热点内容改用 Bitmap（按 uid 偏移）或分片 Set。

### 11.2 面试问答

**Q1：点赞怎么去重且计数准确？**
A：用 Lua 把 SADD（返回 1/0 判断首次）与 INCR 合成原子操作，异步落库；DB 唯一索引兜底，计数值必须以 DB 或定时重算任务校准，见 [04-Redis数据结构与核心原理.md](../02-数据库/04-Redis数据结构与核心原理.md)。

**Q2：取消点赞怎么处理？**
A：SREM 与 DECR 也放同一个 Lua 里保证原子，并保证计数不小于 0；DB 侧用逻辑删除更稳妥，取消后再点赞仍走"首次点赞"分支。

**Q3：评论树怎么存？**
A：产品通常只展示两级，用 parent_id 加 root_id 一次查询组装即可；需要任意层级时按下方三模型对比选择，路径枚举适合层级固定，闭包表查询最优但写放大。

**Q4：热点计数怎么抗？**
A：应用本地按秒聚合增量再批量提交，或按 uid 取模拆成 N 个计数 key 读时求和，避免单 key INCR 打满单个 Redis 分片。
### 11.3 高频追问与陷阱

- 点赞关系与计数分离却无对账，关系 1000 条而计数 1200，用户立刻能发现。
- 用 Set 存百万级成员，属大 key，操作会阻塞 Redis 单线程。
- 评论列表递归查 parent_id，必须限制层数或改一次查询组装。

### 11.4 示例

| 树形模型 | 查子树 | 插节点 | 适用 |
| --- | --- | --- | --- |
| 父子 ID | 递归，慢 | O(1) | 两级展示 |
| 路径枚举 | 前缀 LIKE，较快 | O(1) | 层级固定 |
| 闭包表 | 最快 | 写放大 | 深树高频查 |
### 11.5 一句话速记

**Set/Bitmap 去重、Lua 原子计数、异步落库加定时重算、评论两级展示、热点拆 key 聚合。**

## 12. 消息通知系统设计
### 12.1 核心原理

通知系统是模板渲染加多渠道分发加可靠投递：上游发通知事件（业务幂等键、模板、参数），系统渲染内容后按用户偏好与优先级选渠道，写发送记录表异步投递，用回执更新状态。
规模估算（示例假设）：日通知 1 亿条、峰值 1 万 QPS → 必须走 MQ 削峰，并对用户级与渠道级限流（短信成本高且有运营商频控）。

### 12.2 面试问答

**Q1：模板怎么设计？**
A：模板表加参数占位符渲染，模板与渠道解耦；模板变更要版本化并支持灰度，渲染只允许白名单变量防注入，渲染失败走兜底文案。

**Q2：多渠道怎么抽象与降级？**
A：定义统一 ChannelSender 接口（发送、查询、回执）按渠道实现并注册到工厂，新增渠道不改业务代码；渠道故障按优先级降级（Push 降站内信、短信重试转人工），策略在配置中心可开关。

**Q3：怎么保证不重复发？**
A：业务幂等键（bizType + bizId + userId + channel）加发送记录唯一索引：Redis Set 短 TTL 做快速拦截，DB 唯一索引做最终防线，覆盖 MQ 重投、重试与人工补发。

**Q4：投递状态与重试怎么做？**
A：发送记录表记录待发送、已发送、已送达、失败，渠道回执更新状态；重试用指数退避限 3 次，超限进死信表由定时任务或人工处理，指标告警见 [03-CICD与监控告警.md](../07-工程化与DevOps/03-CICD与监控告警.md)。
### 12.3 高频追问与陷阱

- 不做用户级限流，营销短信被狂发引发投诉与成本失控。
- 同步发短信导致接口 RT 被渠道方拉长，业务线程池被打满。
- 只记录"已提交"不记录"已送达"，用户说没收到时无法排查。

### 12.4 示例

| 渠道 | 成本 | 到达率 | 适用 |
| --- | --- | --- | --- |
| 站内信 | 极低 | 取决于活跃 | 全量通知 |
| Push | 低 | 中（受系统限制） | 活跃用户 |
| 短信 | 高 | 高 | 验证码、重要提醒 |
| 邮件 | 极低 | 低 | 报表、账单 |
### 12.5 一句话速记

**模板加参数、渠道接口抽象、幂等键去重、用户加渠道双限流、发送记录留痕、回执驱动重试。**

## 13. MySQL 到 ES 的数据同步与搜索服务
### 13.1 核心原理

搜索服务遵循"DB 做权威事实、ES 做检索"：业务数据先落 MySQL，再通过同步链路写 ES，由 ES 承担关键词、过滤、排序、高亮、聚合，深分页用 search_after，ES 挂了可从 DB 全量重建。
规模估算（示例假设）：商品 5000 万条、单条索引 1KB → 约 50GB，按每分片 30GB 上限规划 3~5 个主分片，副本再占一倍磁盘。

### 13.2 面试问答

**Q1：三种同步方案怎么选？**
A：优先 binlog 订阅（Canal）加 MQ：双写会污染业务代码且无事务保证、任一侧失败即不一致，binlog 与业务解耦、按行变更天然有序且可重放；需开 ROW 格式并注意主从切换导致的位点变化，消息侧见 [01-消息队列与RocketMQ.md](../04-中间件/01-消息队列与RocketMQ.md)。

**Q2：怎么保证最终一致并可恢复？**
A：按主键分区顺序消费、幂等写入、用 update_time 或版本号做条件覆盖（旧值不覆盖新值），每日抽样比对条数与关键字段，大面积不一致时按主键区间全量重建并走别名切换零停机。

**Q3：索引与分片怎么设计？**
A：按查询维度设计映射：keyword 用于精确过滤与聚合、text 配 IK 分词用于全文检索，时间序列用索引模板加按月滚动索引与别名；分片数按数据量与写入量估算，过多会放大查询协调开销，细节见 [04-Elasticsearch搜索与调优.md](../04-中间件/04-Elasticsearch搜索与调优.md)。

**Q4：深分页与职责边界怎么定？**
A：深翻页用 search_after（需稳定唯一排序键如 update_time + id），from + size 深翻会让每个分片各取 N 条再归并；价格、库存等强一致字段仍回 MySQL 取，ES 只承担检索。
### 13.3 高频追问与陷阱

- 直接说"双写就双写"，答不出 DB 成功而 ES 失败如何补偿（需本地消息表或 MQ 补偿）。
- 把 ES 当权威存储，忽略它可能丢数据、必须以 DB 为准重建。
- 用 `LIKE '%关键词%'` 或 MySQL 全文索引硬扛搜索，数据量与相关性排序都不够用。

### 13.4 示例

| 同步方案 | 业务侵入 | 一致性 | 结论 |
| --- | --- | --- | --- |
| 同步双写 | 高 | 弱（可能半成功） | 不推荐 |
| MQ 异步 | 中 | 最终一致 | 轻量场景可用 |
| binlog 订阅 | 无 | 最终一致且可重放 | 生产首选 |
| 定时全量 | 无 | 延迟大 | 仅兜底重建 |

```text
【同步链路】业务写 MySQL → binlog(ROW) → Canal 解析 → MQ 按主键分区保序
          → 消费者幂等加版本号条件更新 → Bulk 写 ES → 失败进重试队列
【查询链路】关键词 → ES 检索（filter + sort + highlight + 聚合）→ 取主键集合
          → 回 MySQL 取强一致字段 → 组装返回
```
### 13.5 一句话速记

**DB 为权威、binlog 加 MQ 异步同步、幂等与版本号防乱序、对账加全量重建、深分页用 search_after。**

## 14. 系统设计临场表达的 10 条建议与常见减分项

### 14.1 核心原理

得分不只来自方案本身，也来自表达是否可跟随、是否主动暴露风险：面试官无法在 45 分钟内验证方案的线上表现，只能通过结构、取舍、边界与风险判断你的工程成熟度，因此表达本身就是评分项。

### 14.2 面试问答（10 条可背诵表达建议）

1. **结论先行**：先说"我按 X 层设计、核心链路是 A→B→C、瓶颈在 D"，再逐条展开理由。
2. **先澄清再动手**：用 1 分钟确认功能 3 条、非功能 3 条与明确不做什么，避免答偏方向。
3. **主动估算**：给出 QPS、存储、机器数的数量级并声明是示例假设，让架构选择有依据。
4. **画图用嘴**：按请求流向分层描述，一层一句话，边讲边确认"这一层要不要深入"。
5. **每条选型给理由与放弃项**：如"选 RocketMQ 而非 Kafka，因为需要事务消息与延迟消息"。
6. **主动讲异常链路**：缓存击穿、MQ 重复、主从延迟、渠道超时，各给一句应对手段。
7. **主动讲取舍**：至少三组，如一致性 vs 吞吐、推 vs 拉、精确 vs 近似，并说明触发变更的条件。
8. **给数字也给触发条件**："单表超 2000 万行就分片""QPS 到 5 万就加缓存层"。
9. **不确定就说明假设**："这里我假设 X，若不成立要改成 Y"，不要硬编，也不要沉默。
10. **收尾做总结与演进**：用 30 秒复述架构、瓶颈与下一步演进，把话语权交回面试官。

### 14.3 高频追问与陷阱（10 条常见减分项：现象 → 正确做法）

1. 上来就画架构图 → 先用 1 分钟澄清功能、非功能与明确不做的边界。
2. 只堆技术名词 → 每个组件都给出"为什么用它、放弃了什么"。
3. 不做容量估算 → 给出 QPS/存储/机器数量级，并声明是示例假设。
4. 不提幂等 → 说清幂等键（订单号、渠道流水号）与对应的唯一索引。
5. 只讲正常流程 → 主动补异常链路与限流、熔断、降级、重试策略。
6. 忽略一致性边界 → 说明缓存/ES 与 DB 的延迟窗口、对账机制与可接受性。
7. 回避取舍问题 → 明确讲"放弃什么换来什么、什么条件改回"，不绕开。
8. 不提监控运维 → 给出核心指标、告警阈值、灰度与开关方案。
9. 数字前后矛盾 → 统一口径（均值/峰值、单机/集群）并复述校验一次。
10. 沉迷细节超时 → 单点深入控制在 2 分钟内，先保全局再回答追问。

### 14.4 示例

```text
【45 分钟表达脚本（示例假设）】
0-5 分钟   澄清：功能 A/B/C；峰值 5000 QPS、P99<200ms、可用性 99.9%，先不做多机房
5-9 分钟   估算：日请求 5000 万、峰值约 5000 QPS；单条 1KB、日增 50GB、年增 18TB，必须分片
9-17 分钟  API 与模型：3 个接口 + 2 张核心表，强调唯一索引与分片键
17-29 分钟 架构与流程：分层描述 + 写入与查询两条链路时序
29-37 分钟 瓶颈与优化：DB 写入是瓶颈，先加缓存与异步，再按 user_id 分片
37-43 分钟 容错取舍：限流熔断、幂等、对账；取舍为一致性让位于吞吐
43-45 分钟 总结：当前方案扛 5 倍流量，10 倍时改哪里、怎么演进
```

### 14.5 一句话速记

**结论先行、澄清在前、估算给量级、选型讲取舍、异常主动提、收尾讲演进——别只堆名词与只讲正常流程。**

## 自测题（含答案要点）

1. **系统设计九步框架是什么？** 要点：需求澄清 → 规模估算 → 核心 API → 数据模型 → 高层架构 → 核心流程 → 瓶颈优化 → 容错演进 → 取舍说明。
2. **需求澄清与估算的口径？** 要点：功能 3~5 条、非功能（QPS/延迟/一致性/数据量）、明确不做什么；峰值 = 均值 × 3~10，存储 = 日增 × 单条 × 天数。
3. **短码怎么生成、容量多大？** 要点：雪花/号段 ID 转 62 进制，6 位约 568 亿、7 位约 3.5 万亿；跳转用 302 保统计，对外用独立域名做隔离。
4. **秒杀如何不超卖不少卖？** 要点：分层防护加 Redis Lua 原子预扣，DB 条件更新兜底防超卖；延迟消息关单回补加活动结束对账防少卖。
5. **秒杀幂等怎么保证？** 要点：订单号唯一索引加 `uk(activity_id, user_id)` 一人一单，消费端幂等，冲突按"已参与/已下单"返回。
6. **IM 怎么不丢不乱、群聊怎么扩散？** 要点：消息表 + ACK + 超时重发 + msg_id 去重，会话级 seq 保序；小群写扩散、大群读扩散加在线推送。
7. **Feed 推拉怎么结合？** 要点：粉丝数低于阈值走推、大 V 走拉，读时归并；时间线存 ZSet 按 score 游标分页，限长防大 key。
8. **超时关单有哪些方案？** 要点：RocketMQ 延迟消息优先、时间轮加 Redis ZSet 或按索引分片扫描兜底，关单后回补库存与券。
9. **支付回调与对账怎么做？** 要点：验签、渠道流水号唯一索引、状态机条件更新、同事务写流水；T+1 三方对账并把差异分四类处理。
10. **分片键怎么选、扩容怎么做？** 要点：user_id 分片、订单号内嵌基因、逻辑分片预留 1024；扩容走双写、迁移、校验、灰度切读。
11. **排行榜为什么用 ZSet？** 要点：ZINCRBY/ZREVRANGE/ZREVRANK 均 O(logN)，多周期多 key，TopN 精确长尾近似，本地缓存抗热点，定时归档可重建。
12. **LBS 三种存储怎么选？** 要点：Redis GEO 做在线半径、ES geo_point 做条件组合与分页、MySQL 矩形粗筛加 Haversine 精算；GeoHash 要查相邻 8 格。
13. **优惠券怎么防超发与一人一张？** 要点：Redis 预扣加 DB 条件更新，`uk(batch_id, user_id)` 防重；下单锁券绑订单号，超时释放，过期懒清理加定时扫。
14. **点赞与通知怎么保证不重复？** 要点：Lua 原子去重计数加定时重算；通知用 bizType+bizId+userId+channel 幂等键加发送记录唯一索引，回执驱动重试。
15. **MySQL 同步 ES 怎么做？** 要点：Canal binlog 加 MQ 按主键分区保序、幂等与版本号覆盖、对账与全量重建；深分页用 search_after，强一致字段回 MySQL。

## 背诵卡片

1. 系统设计九步：澄清、估算、API、模型、架构、流程、瓶颈、容错、取舍。
2. 需求澄清三问：功能要什么、非功能要多少、明确不做什么。
3. 估算口径：峰值 = 均值 × 3~10；单机 QPS 常按 1000~5000 估（示例假设）。
4. 1 天约 86400 秒，口算按 10^5 秒近似，量级正确即可。
5. 短码 62 进制：6 位 568 亿、7 位 3.5 万亿。
6. 跳转用 302 保统计与风控，纯静态链接才用 301。
7. 短链存储：Redis 扛读、MySQL 兜底、布隆过滤器防穿透、异步埋点统计。
8. 短域 vs 同域：对外推广用独立域名做风险隔离。
9. 秒杀分层：前端置灰与验证码 → CDN → 网关限流 → Redis 预扣 → MQ 下单 → DB 扣减。
10. 秒杀不超卖靠 Lua 预扣加 DB 条件更新，不少卖靠超时回补加对账。
11. 秒杀幂等：订单号唯一索引加一人一单唯一约束，消费端必须幂等。
12. 秒杀上线前要全链路压测，并准备限流阈值、降级开关与水位告警。
13. IM 长连接选 Netty/WebSocket，网关维护 uid → 网关路由。
14. 消息不丢 = 消息表 + ACK + 重发 + msg_id 去重。
15. 有序只需会话级 seq 递增，全局有序代价过高。
16. 小群写扩散、大群读扩散、混合场景推拉结合。
17. Feed 时间线用 ZSet 存，score 取时间戳，游标分页禁用 offset。
18. 单个时间线只留最近约 1000 条，防大 key。
19. 订单状态必须显式合法迁移，更新带前置状态条件。
20. 支付回调幂等键是渠道流水号，不是订单号。
21. 超时关单首选延迟消息，定时扫描只做兜底。
22. 资金最终一致靠 T+1 三方对账与差错分类处理。
23. 分片键选 user_id，订单号内嵌基因以便定点路由。
24. 逻辑分片一次规划足够大（如 1024），避免频繁重分片。
25. 扩容走双写、迁移、校验、灰度切读，并保留回滚开关。
26. 排行榜用 ZSet：加分、取 TopN、查名次都是对数级。
27. GeoHash 查询必须覆盖相邻 8 个格子，避免边界漏点。
28. LBS 在线检索用 Redis GEO，条件组合与分页用 ES geo_point。
29. 领券防超发 = Redis 预扣 + DB 剩余量条件更新 + 对账。
30. 券的五态：未使用、已锁定、已使用、已过期、已作废。
31. 点赞去重用 Set/Bitmap，计数异步落库并定时重算校正。
32. 评论树：两级用 parent_id 加 root_id，深树用闭包表，层级固定用路径枚举。
33. 通知幂等键建议 bizType + bizId + userId + channel，渠道要抽象与降级。
34. MySQL 是权威、ES 是检索层，同步优先 binlog 订阅，深分页用 search_after。
