## 1. 分层架构与每层优化

### 1.1 核心原理

请求穿过 **接入层 → 网关层 → 应用层 → 中间件层 → 存储层**，设计原则是“上游挡、中间缓、下游削”，扩容只扩最紧的那一层。接入层（DNS/GSLB、LVS/Nginx、CDN、WAF）负责分发与防护；网关层（Gateway/Kong/APISIX）统一路由、鉴权、限流、灰度；应用层承载业务且必须无状态才能水平扩容；中间件层（RocketMQ/Kafka/Redis）解耦削峰；存储层（MySQL/Redis 集群/ES）有状态、扩容成本最高，目标是让它少扛。

### 1.2 面试问答

**Q1：你怎么判断该优化哪一层？**A：先定位瓶颈层——接入层看带宽与连接数，网关看 QPS/RT，应用看 CPU/GC/线程池队列，中间件看堆积量，存储看慢查询与 IOPS；原则是“就近拦截”（CDN > 本地缓存 > Redis > DB），边界是拦截不能改语义，价格与库存必须回源校验。
**Q2：为什么网关和应用都要限流？** A：网关按 IP、AppKey、接口做租户级粗限流挡刷量，应用按商品、用户做资源级细限流保核心业务；只做一层会误伤或漏伤，两层限流键必须不同维度，否则重复计数。
**Q3：为什么应用必须无状态、存储层是终点？**A：无状态才能任意实例处理任意请求、秒级扩缩容（会话外置 Redis、文件外置对象存储、定时任务改分布式调度）；存储层扩容需迁移并保一致，所以要用缓存、读写分离、分库分表、异步化削减落到 DB 的请求，示例假设单分片数据量偏差应小于 20%。
**Q4：CDN 能解决什么、不能解决什么？** A：CDN 卸载静态资源（图片、JS、CSS、页面骨架），降低带宽与回源 QPS；动态接口仅当“同一 URL 返回同一结果”才可缓存，命中率不足时回源会放大流量，必须设 TTL 与源站限速，具体参数以 CDN 厂商官方文档为准。

### 1.3 高频追问与陷阱

- 追问“加了缓存 QPS 没涨”：先看命中率与 RT 构成，命中率高而 RT 不降说明瓶颈在线程池或下游，不在 DB。
- 陷阱：木桶效应——线程池、连接池、DB 连接任一打满，QPS 即掉到该池容量水平。

### 1.4 示例

| 层次 | 典型技术与优化手段 | 扩容方式 |
| --- | --- | --- |
| 接入层 | DNS/GSLB、LVS/Nginx、CDN、WAF；静态化、黑名单 | 加节点带宽（近线性） |
| 网关层 | Gateway/Kong/APISIX；鉴权缓存、令牌桶、连接复用 | 无状态水平扩（近线性） |
| 应用层 | Spring Boot/Tomcat；无状态化、池隔离、本地缓存 | 无状态水平扩（近线性） |
| 中间件层 | RocketMQ/Kafka/Redis；加分区、批量消费 | 加 Broker/分区（受分区数限制） |

### 1.5 一句话速记
分层高并发口诀是“上游挡、中间缓、下游削”，扩容只扩最紧的那一层。

## 2. 容量评估与性能指标

### 2.1 核心原理

容量评估回答三个数：峰值 QPS、实例数、余量。核心公式是 **峰值 QPS = 日活 × 人均请求数 ÷ 86400 × 峰值系数**、**实例数 = 峰值 QPS ÷ 单机 QPS × 冗余系数（1.5~2）**、**并发数 = 峰值 QPS × 平均 RT（利特尔法则）**。指标上 QPS 看吞吐、RT 看延迟、TP99/TP999 看长尾，必须一起看。

### 2.2 面试问答

**Q1：QPS、TPS、并发数、RT 是什么关系？**A：QPS 是每秒请求数（一次请求可能含多次 DB 查询），TPS 是每秒完成的事务数（一次下单成功）故 TPS ≤ QPS，并发数是同一时刻正在被处理的请求数；关系为 并发数 = QPS × RT，边界是必须在同一统计窗口内取值。
**Q2：TP99 和平均 RT 哪个反映体验？** A：TP99 更能反映：示例假设 100 个请求中 99 个 10ms、1 个 1000ms，则平均 RT = 19.9ms 看着健康，但 TP99 ≈ 1000ms，说明 1% 用户卡了一秒；均值被快请求稀释即长尾效应，均值用于容量计算、分位用于体验与 SLA。
**Q3：峰值 QPS 与实例数怎么算？** A：示例假设日活 300 万、人均 50 次、峰值系数 4 → 均值 ≈ 1736 QPS、峰值 ≈ 6944 QPS（大促系数 10 时 ≈ 17360）；单机压测 500 QPS、冗余系数 2 → 7000÷500×2 = 28 台；冗余覆盖 GC 波动、依赖抖动与发布期实例减少，边界是 DB/Redis 先撑不住时加应用实例无意义。
**Q4：单机 QPS 怎么测，压测为何要隔离数据？** A：单接口用 wrk/JMeter 摸上限并盯 CPU/GC/线程池队列，再做混合场景与全链路压测（需多台施压机，防网卡或端口耗尽）；压测会写数据污染真实库存与订单，必须给流量打标后路由到影子库表、影子 Topic 与带前缀影子 Key，外部依赖 Mock，并有一键关闭与清理开关。

### 2.3 高频追问与陷阱

- 追问“RT 从 50ms 优化到 25ms 的收益”：同 28 台机器 QPS 翻倍等于省一半机器，反之 RT 翻倍等于容量减半。
- 陷阱：只看 QPS 达标不看错误率与 TP99，属于假达标。
### 2.4 示例

| 指标 | 示例假设取值 | 用途 |
| --- | --- | --- |
| 日活 × 人均请求数 | 300 万 × 50 | 估算总量 |
| 均值 QPS | ≈1736 | 常态容量基线 |
| 日常峰值系数 | 3~5（取 4） | 估日常峰值（≈6944） |
| 大促峰值系数 | 10 以上（示例假设） | 估活动容量（≈17360） |

### 2.5 一句话速记
峰值 QPS = 日活 × 人均请求 ÷ 86400 × 峰值系数；实例数 = 峰值 QPS ÷ 单机 QPS × 冗余系数；并发数永远等于 QPS × RT。

## 3. 缓存体系与一致性

### 3.1 核心原理

缓存分三层：**本地（进程内、纳秒级、容量小）→ Redis（亚毫秒级、跨实例共享）→ CDN（边缘、TTL 驱动）**；一致性的本质是 DB 为权威源、缓存是副本，所以用“失效（删除）”而非“更新”通知缓存，并用 TTL 兜底。本地缓存放小、热、可容忍秒级不一致的数据（配置、字典、热点基础信息，示例假设单机 ≤100MB），Redis 放库存、会话、计数等需主动失效的数据，CDN 放静态资源。

### 3.2 面试问答

**Q1：更新 DB 后删缓存还是更新缓存？**A：推荐先更新 DB 再删除缓存——删除是惰性重建、天然幂等，而更新缓存要保证两次写的先后顺序，并发下易写入旧值；边界是删除失败要靠消息重试或 TTL 兜底。
**Q2：不一致窗口怎么来的、怎么缓解？** A：先更新 DB 再删缓存时，“删缓存之前”若有读请求把旧值回填就会长期不一致；缓解手段是延迟双删（延迟需大于一次读回填耗时，示例假设 200~500ms）、binlog 订阅异步失效（Canal）或强一致数据直接读主库，这套方案仍不是强一致。
**Q3：本地缓存与 Redis 二级缓存如何一致？**A：短 TTL 兜底（窗口等于 TTL、最简单）、MQ 广播失效（毫秒级但依赖 MQ，实例多时需加随机抖动防惊群）或版本号校验（本地侧落后则回源）；边界是广播失败必须靠 TTL 兜底。
**Q4：穿透、击穿、雪崩分别怎么处理？** A：穿透（查不存在数据每次打 DB）用空值缓存或布隆过滤器（有假阳性）；击穿（热点 Key 过期瞬间回源）用互斥重建或逻辑过期；雪崩（大量 Key 同时过期或 Redis 不可用）用 TTL 随机抖动、多级缓存兜底、集群高可用加熔断降级，细节见 [../02-数据库/05-Redis高可用与缓存治理.md](../02-数据库/05-Redis高可用与缓存治理.md) 与 [../02-数据库/04-Redis数据结构与核心原理.md](../02-数据库/04-Redis数据结构与核心原理.md)。

### 3.3 高频追问与陷阱

- 追问“Redis 挂了怎么办”：本地缓存继续服务、限流保护 DB、非核心功能降级；绝不能无脑重试打满连接池。
- 陷阱：以为设了 TTL 就一致——TTL 窗口内仍是脏数据，业务必须评估能否接受。
### 3.4 示例

| 维度 | 本地缓存（Caffeine） | Redis 集群 / CDN |
| --- | --- | --- |
| 延迟与容量 | 纳秒级 / ≤100MB（示例假设） | Redis 亚毫秒 / 数十 GB；CDN 10~50ms / TB 级 |
| 一致性 | 各实例独立，最难一致 | Redis 单点权威易失效；CDN 靠 TTL，最弱 |

### 3.5 一句话速记
本地挡热点、Redis 挡高频、CDN 挡静态；写数据永远“先写 DB 再删缓存”，一致性靠 TTL 与失效广播兜底。

## 4. 异步化与解耦

### 4.1 核心原理

异步化把“用户等待时间”与“系统处理时间”解耦：主链路只做校验、预占与入队（毫秒级），发券、积分、通知、落库交给 MQ 或线程池。三种方式：线程池（进程内并行、重启即丢）、MQ（跨服务、持久化、可重放）、事件驱动（Spring Event，进程内广播）。代价是可观测性变差、事务边界模糊、幂等责任转移。

### 4.2 面试问答

**Q1：线程池核心参数怎么定？**A：CPU 密集型取核数 + 1，IO 密集型可从 2×核数起步并压测校准（示例假设，非普适公式）；maxPoolSize 应对突发但会推高下游压力，queueCapacity 太长会排队超时、太短会触发拒绝，拒绝策略线上常用 CallerRunsPolicy 背压；边界是必须用有界队列，无界队列会让 maxPoolSize 失效、请求排队到超时且可能 OOM。
**Q2：为什么用 MQ 削峰，边界在哪？**A：MQ 把瞬时峰值转成队列缓冲、消费端匀速消费，让下游只承受稳态压力；所需缓冲 ≈ 峰值 QPS × 持续时间 − 消费 TPS × 持续时间（示例假设峰值 5 万 QPS 持续 2s、消费 2000 TPS → 积压约 96,000 条），边界是积压时长须在业务容忍内、消息不能丢、消费端要按分区并行并满足顺序。
**Q3：本地事务与发消息如何一致？** A：本地消息表（业务与消息同事务写入，再由任务投递并标记状态）或事务消息（先发半消息、本地提交后回查确认投递）；边界是 MQ 为至少一次语义，消费端必须幂等，更多方案见 [./02-分布式事务.md](./02-分布式事务.md)。
**Q4：异步化后必须补哪些能力？** A：四件事——traceId 通过 MQ Header/MDC 贯穿（异步池要包装 MDC）、消费端用唯一键加去重表或 Redis setnx 做幂等、设置最大重试次数与死信队列、结果通过轮询或推送通知用户，绝不能让用户无声等待。

### 4.3 高频追问与陷阱

- 追问“异步返回成功后业务失败怎么办”：回答状态机 + 补偿——接口返回“已受理”、订单置处理中，失败则置失败并退款，前端按状态展示。
- 陷阱：消息体过大（带整个订单对象）应改为只传 ID 加必要字段、消费端回查。
### 4.4 示例

| 方案 | 可靠性 | 延迟 | 主要代价 |
| --- | --- | --- | --- |
| 线程池 / @Async | 重启即丢 | 微秒~毫秒 | 队列积压、上下文丢失 |
| Spring Event | 不持久化 | 微秒级 | 无重试、无回溯 |
| MQ（RocketMQ/Kafka） | 持久化 + 重试，至少一次 | 毫秒~秒级 | 幂等、顺序、运维复杂 |

```text
异步下单时序：请求 → 前端置灰/答题 → 网关防刷限流 → Redis Lua 预扣（记 requestId 流水）
→ 发 MQ（userId/skuId/requestId）→ 立即返回“排队中” → 消费端幂等校验 → 建单（DB 唯一索引兜底）
→ 扣 DB 库存 → 更新订单成功 → 前端轮询或推送取结果 → 超时（示例假设 30s）置失败并回补库存
```

### 4.5 一句话速记
异步化把等待变成排队，前提是幂等、状态机与可观测性三件套齐全，否则省下的 RT 会以数据不一致的形式还回来。

## 5. 限流算法与集群限流

### 5.1 核心原理

限流四要素：限流对象（维度）、阈值（速率）、算法（怎么计数）、限流后行为。固定窗口简单但有临界问题，滑动窗口平滑但开销大，漏桶输出绝对匀速但不允许突发，令牌桶按速率补令牌、桶容量决定突发上限，兼顾平均与突发，是生产首选。单机限流保本机、集群限流保下游，二者必须配合。

### 5.2 面试问答

**Q1：四算法的区别与选择？** A：固定窗口每窗口清零、允许边界双倍突发；滑动窗口按时间片或 ZSet 统计、精度可调但内存与计算开销大；漏桶恒定速率放行、下游最稳但浪费空闲容量；令牌桶兼顾平均与突发且参数可调，生产首选，边界是桶容量设太大等于没限流。
**Q2：固定窗口的临界问题有多严重？**A：示例假设阈值 100 QPS、窗口 1 秒，攻击者在前一秒最后 10ms 发 100 个、下一秒前 10ms 再发 100 个，两窗口各自都未超限，但 20ms 内实际进来 200 个请求、瞬时速率是阈值的 10 倍；对策是滑动窗口、令牌桶或把窗口切细。
**Q3：单机与集群限流怎么配合？**A：单机（Guava RateLimiter、Sentinel 单机流控）零网络开销，阈值取集群阈值 ÷ 实例数；集群（Redis + Lua、Sentinel 集群流控、网关集中限流）速率精确但每次请求有 Redis 往返与单点风险；工程做法是网关做集群级粗限流、应用做单机级细限流。
**Q4：Redis + Lua 集群限流要注意什么？** A：用 Lua 保证“取令牌 + 回填时间戳”原子性，时间取 Redis 服务端时间避免时钟漂移；Key 必须设 TTL；明确 Redis 不可用时 fail-open（放行保可用）还是 fail-fast（拒绝保下游），核心写链路一般 fail-open 并加单机限流兜底；Cluster 下多 Key 需同 slot（hash tag）。

### 5.3 高频追问与陷阱

- 追问“限流和熔断的区别”：限流是主动控制入口速率（预防），熔断是被动切断故障依赖（止损），二者配合不能互替。
- 陷阱：用 tryAcquire 带超时预消费取令牌会导致线程堆积，必须配合超时与熔断；限流键基数不能爆炸（用 requestId 做键等于没限流）。

### 5.4 示例
```java
// 令牌桶核心逻辑：按速率补令牌，桶容量限制瞬时突发（生产直接用 Guava RateLimiter/Sentinel）
public final class TokenBucket {
    private final double ratePerSec, capacity;   // 速率=限流阈值；桶容量=可容忍突发量
    private double tokens;                       // 当前令牌数
    private long lastRefillNanos;                // 上次补充时间
    public TokenBucket(double ratePerSec, double capacity) {
        this.ratePerSec = ratePerSec; this.capacity = capacity;
        this.tokens = capacity; this.lastRefillNanos = System.nanoTime();
    }
    public synchronized boolean tryAcquire() {
        long now = System.nanoTime();
        double refill = (now - lastRefillNanos) / 1_000_000_000.0 * ratePerSec;
        tokens = Math.min(capacity, tokens + refill);   // 多余令牌丢弃
        lastRefillNanos = now;
        if (tokens >= 1.0) { tokens -= 1.0; return true; }
        return false;
    }
}
```

| --- | --- | --- | --- |
| 固定窗口 | 边界双倍突发 | 实现最简单、内存极小 | 临界问题 |
| 滑动窗口 | 平滑受限 | 精度可调、无临界 | 内存与计算开销大 |
| 漏桶 | 绝对匀速 | 下游最平稳 | 浪费空闲容量、排队延迟 |
| 令牌桶 | 允许桶容量内突发 | 兼顾平均与突发，首选 | 参数需调优 |


```lua
-- Redis 集群令牌桶（原子）：KEYS[1]=Key ARGV[1]=速率 ARGV[2]=桶容量 ARGV[3]=当前时间(秒)
local key, rate = KEYS[1], tonumber(ARGV[1])
local capacity, now = tonumber(ARGV[2]), tonumber(ARGV[3])
local bucket = redis.call('HMGET', key, 'tokens', 'ts')
local tokens, ts = tonumber(bucket[1]), tonumber(bucket[2])
if tokens == nil then tokens = capacity; ts = now end   -- 首次访问：桶满
tokens = math.min(capacity, tokens + math.max(0, now - ts) * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, 60)   -- 空闲回收
return allowed
```

### 5.5 一句话速记
计数器简单但有临界、漏桶最稳但浪费、令牌桶兼顾突发是首选；单机保本机、集群保下游，阈值必须满足 Nginx ≥ 网关 ≥ 单机×实例数。

## 6. 熔断降级与隔离

### 6.1 核心原理

熔断解决依赖故障传染：下游错误率或 RT 超标时继续调用只会耗尽本服务线程与连接，于是主动切断、快速失败，给下游恢复时间。降级是熔断触发后的动作——返回兜底数据而非抛异常；隔离是不让一个故障点影响其他功能。三者关系是隔离缩小故障域、熔断感知并切断故障、降级保住核心功能。

### 6.2 面试问答

**Q1：熔断状态机怎么转？** A：三态——Closed 正常放行并统计，窗口内错误率（示例假设 50%）或慢调用比例超阈值转 Open；Open 期间所有调用直接失败、时长由休眠窗口决定（示例假设 10s）；休眠结束进 Half-Open 放行少量探测请求（示例假设 5~10 个），达标回 Closed、否则回 Open；边界是必须设最小请求数，否则低流量下一次失败就打开熔断器。
**Q2：Hystrix、Sentinel、Resilience4j 怎么选？** A：Hystrix 已停止维护（2018 年起维护模式，官方不再开发新特性），新项目不应选；Sentinel 规则维度最全（流控、熔断、热点参数、系统自适应、集群流控）且控制台与动态规则完善，是 Java 微服务主流；Resilience4j 函数式、无侵入、轻量，适合 Spring Boot 3 与函数式风格，生态见 [../03-框架/05-SpringCloud微服务体系.md](../03-框架/05-SpringCloud微服务体系.md)。
**Q3：熔断阈值与降级粒度怎么定？** A：阈值四件套——统计窗口（示例假设 10s）、最小请求数（示例假设 20）、错误率阈值（示例假设 50%）、慢调用 RT 阈值与比例（示例假设 500ms 且占有比超 50%），且要按下游 SLA 定；降级分三级：P0 核心（下单、支付）不降级只限流，P1 重要（详情、列表）降级到静态兜底，P2 非核心（推荐、评论、积分）直接关闭。
**Q4：线程池隔离与信号量隔离的区别？** A：线程池隔离为每个依赖分独立线程池、调用在独立线程执行，支持超时中断，代价是线程切换开销与更多线程资源（示例假设每依赖 10~20 线程）且需显式传播 ThreadLocal/MDC；信号量隔离只用计数器限并发、在调用者线程执行，开销极小但无超时中断能力，适合高吞吐快依赖。

### 6.3 高频追问与陷阱

- 追问“熔断打开后流量去哪了”：由降级逻辑承接并告警通知值班，下游长时间未恢复要触发人工预案（切换备用依赖）。
- 陷阱：降级返回兜底数据但不埋点，无法统计降级流量、复盘缺数据；交易金额与库存不能降级为假数据，只能快速失败。

### 6.4 示例

| 框架 | 隔离方式 / 线程模型 | 规则动态 | 维护状态 |
| --- | --- | --- | --- |
| Hystrix | 独立线程池 / 信号量 | 需 Archaius，较繁琐 | **已停止维护** |

```text
熔断状态机：Closed 统计错误率与慢调用比例 → 超阈值转 Open（直接降级、不发起真实请求）
→ 休眠窗口结束转 Half-Open（示例假设放行 5 个探测请求）→ 达标回 Closed，否则回 Open
```

### 6.5 一句话速记
隔离缩小故障域、熔断感知并切断故障、降级保住核心功能；Hystrix 已停维护，Sentinel 规则最全、Resilience4j 最轻量。

## 7. 超时、重试与幂等

### 7.1 核心原理

超时是防止线程被无限拖住的最后闸门（规则：上层超时 = 本层处理 + 下游预算 + 缓冲，且要传递全局 deadline），重试是提高最终成功率的补偿（指数退避 + 抖动 + 上限），幂等是重试成立的前提。核心约束是**上游超时必须小于下游超时之和**，且禁止重试与禁止超时过短必须同时考虑。

### 7.2 面试问答

**Q1：超时链路预算怎么算？** A：示例假设总预算 1000ms：网关 950ms → 订单 800ms → 库存与优惠各 200ms（实设 150ms 留 20% 缓冲）→ 支付 300ms；规则是每层预算 = 上层预算 − 本层处理时间 − 缓冲，并行调用按最慢分支加缓冲设上限，边界是必须在 Header 传递剩余时间，否则下游会用完整超时导致链路总耗时超标。
**Q2：为什么要指数退避加抖动？** A：固定间隔重试会让失败请求同时涌入形成重试风暴，把刚恢复的下游再次打挂；指数退避让间隔递增（示例假设 100/200/400ms），抖动叠加随机量（如 ±30%）把请求在时间上打散；边界是必须设最大次数与最大总耗时且不超过上游预算。
**Q3：哪些场景绝对不能重试？** A：非幂等写操作、已超时且结果不确定的请求（可能已成功）、明确的业务错误（参数错误、余额不足）、限流或熔断返回的拒绝（应遵守 Retry-After）；边界是读操作、带唯一键的幂等写与配合幂等的 MQ 消费可以重试。
**Q4：幂等怎么做？** A：四层保障——业务唯一键（订单号、requestId）由上游生成并在入口强制携带、DB 唯一索引兜底（`UNIQUE KEY uk_request_id`，冲突即视为重复，最可靠）、去重表或 Redis setnx 前置快速拦截、状态机校验（已支付订单不允许再次支付）；边界是 Redis 会过期失效，DB 唯一索引必须保留。

### 7.3 高频追问与陷阱

- 追问“下游超时了怎么判断成功没有”：靠主动查询确认或下游提供幂等查询接口，绝不能直接重试。
- 陷阱：重试用 AOP 统一包裹却没排除非幂等方法；重试次数写死 3 次且不区分错误类型；示例假设三层各重试 3 次最坏放大 27 倍。
### 7.4 示例

```text
超时预算示例：用户端 1000ms → 网关 950ms（留 50ms 鉴权转发）→ 订单服务 800ms（留 150ms 编排）
→ 库存 200ms（实设 150ms，留 50ms 缓冲）→ 支付 300ms（超时后走查询确认，不重试）
```

```sql
-- 数据库乐观锁扣减：影响行数 = 1 成功，= 0 表示库存不足（必须走索引）
UPDATE stock SET available = available - #{num}, version = version + 1
WHERE sku_id = #{skuId} AND available >= #{num};
```

### 7.5 一句话速记
超时逐层递减留缓冲，重试指数退避加抖动且只放在边界层；重试的前提是幂等，幂等靠唯一键加 DB 唯一索引双重兜底。

## 8. 热点数据与读写一致性

### 8.1 核心原理

热点数据指访问量远高于平均水平的数据（爆款商品、明星微博），带来两个问题：单 Key 打爆单个 Redis 分片（Cluster 以 Key 为单位分片）与缓存过期瞬间流量直冲 DB。处理分两步：先发现（实时 TopN 统计、网关日志、Sentinel 热点参数），再治理（本地缓存、Key 加随机后缀打散、拆分大 Value、逻辑过期）；读写一致性要解决主从延迟导致的“写后读不到”。

### 8.2 面试问答

**Q1：怎么发现热点？** A：网关/Nginx 日志按 URL 与参数做秒级 TopN；应用内用滑动窗口或 Count-Min Sketch 做本地探测（Sentinel ParamFlow 即此类思路）；Redis 侧 `redis-cli --hotkeys` 有性能开销、应在从库或低峰执行，具体以官方文档为准；业务侧可预知（运营标记秒杀商品），边界是探测有延迟，可预知热点必须提前预热打标。
**Q2：热点 Key 怎么打散？** A：加随机后缀（`hot:sku:1001` 变 `hot:sku:1001:{0..9}` 十份副本，读随机选、写同步更新或写后广播失效）；拆分 Value（大 Hash/大 List 按业务拆小，示例假设单 Value ≤10KB）；本地缓存加广播失效把读流量从 Redis 卸载，边界是副本数与一致性成本成正比，写频繁的热点不适合多副本。
**Q3：主从延迟导致写后读不到怎么办？**A：对一致性敏感的读强制走主库（下单后查订单、支付后查状态）；会话粘性加延迟窗口（示例假设写完 1s 内该用户读主库）；读从库时带 binlog 位点或版本号、未追平则回主库；边界是强制走主会增加主库压力，必须只对刚写过的 Key 生效，复制原理见 [../02-数据库/03-MySQL调优主从与分库分表.md](../02-数据库/03-MySQL调优主从与分库分表.md)。
**Q4：缓存与 DB 的最终一致怎么保证？** A：写 DB 后删缓存（Cache-Aside）→ binlog 订阅异步再删一次覆盖并发窗口 → 所有缓存设 TTL 作为最终兜底 → 定期对账比对库存与金额并修复差异；边界是最终一致窗口要向业务明示（示例假设秒级），金额与库存的强一致校验必须在 DB 层完成。

### 8.3 高频追问与陷阱

- 追问“一个 Key 能扛多少 QPS”：取决于单分片能力与 Value 大小，Redis 单实例十万级 QPS 是常见经验值（以官方基准与自身压测为准），但热点 Key 集中在单分片，扩分片无效、必须打散。
- 陷阱：所有缓存统一 30 分钟过期形成人为雪崩；本地缓存热点数据却配长 TTL 导致价格、库存不一致事故；多级缓存失效顺序必须与回填相反（先本地、再 Redis、最后 DB），否则旧值会被回填扩散到全局。

### 8.4 示例

| 手段 | 解决问题 | 一致性代价 | 适用场景 |
| --- | --- | --- | --- |
| 本地缓存（Caffeine） | 读流量卸载 Redis | 短 TTL 或广播失效，秒级不一致 | 读写比 >100:1 的热点基础信息（示例假设） |
| Key 加随机后缀 | 打散单分片压力 | 需同步多副本，写放大 | 可预知热点（爆款 SKU） |
| 拆分大 Value | 降低单次耗时与带宽 | 无（结构改造） | 大 Hash/大 List（>10KB） |

### 8.5 一句话速记
热点先发现再打散：可预知的靠预热与本地缓存，不可预知的靠实时 TopN 加随机后缀分流；写后读一致用手写主库加会话粘性。

## 9. 库存扣减防超卖

### 9.1 核心原理

库存扣减的本质是在并发下对同一行或同一 Key 做正确的“检查并扣减”。超卖成因有三类：并发更新丢失（先查后改，两个线程都读到 1）、缓存与 DB 不一致（Redis 扣成功 DB 没扣）、扣减成功但订单失败。防超卖方案按性能递增：DB 乐观锁 → Redis + Lua 预扣减 → 分段扣减 + 异步落库 + 对账；少卖则靠超时回补与对账修正。

### 9.2 面试问答

**Q1：为什么乐观锁 UPDATE 能防超卖？**A：InnoDB 对该行更新加排他锁，`stock >= n` 由当前读保证看到最新已提交值，并发更新被串行化；判断依据是影响行数（1 成功、0 库存不足），绝不能只看是否抛异常；边界是必须走索引（主键或唯一索引）否则可能锁全表，且不能把条件与扣减拆成两条 SQL，对比见 [../02-数据库/02-MySQL事务锁与MVCC.md](../02-数据库/02-MySQL事务锁与MVCC.md)。
**Q2：为什么还需要 Redis 预扣减？** A：秒杀瞬时 QPS（示例假设 5 万）远超 MySQL 单行更新的承载能力（同热门记录大量并发更新形成锁竞争，示例假设单行千级 TPS）；Redis 单机十万级 QPS 且 Lua 原子执行，能在内存先扣减、滤掉大部分无效请求；边界是 Redis 数据可能丢失，必须配合 DB 最终扣减与对账，它只是准入闸门而非权威账本。
**Q3：Lua 脚本与分段扣减要注意什么？** A：取值要判空（`GET` 返回 false 时返回错误码而不是当作 0，避免把“未初始化”误判为“卖完”）、不足返回负值而非报错、脚本要短以免阻塞 Redis；分段扣减把库存拆 N 段分散竞争（示例假设 1 万库存拆 20 段，压力降为 1/20），边界是会产生“部分段已空、其他段有货”的碎片，需要跨段补偿与水位告警。
**Q4：扣减成功但订单失败，库存怎么回来？** A：三重兜底——事务内预扣与 MQ 入队同段逻辑，入队失败立即回补；消费端重试 N 次后进死信队列由补偿任务回补并通知用户；定时对账扫描“库存已扣但无成功订单”的记录（示例假设 5 分钟一次）按预扣流水与订单流水核对回补；边界是回补必须幂等（状态字段或唯一索引），少卖则靠预扣流水把超时 PENDING 置 ROLLBACK 并每日校验“总库存 = 初始 − 成功订单 − 取消回补”。

### 9.3 高频追问与陷阱

- 追问“乐观锁和悲观锁怎么选”：低冲突用乐观锁（无锁等待、吞吐高），高冲突用 Redis 预扣或分段；`SELECT ... FOR UPDATE` 在秒杀下会形成长事务与死锁风险，不推荐作主方案。
- 陷阱：只用 Redis 不用 DB 兜底，Redis 重启后库存错乱出现超卖；把 update 影响行数用 try/catch 兜底，扣减失败却静默当成功。

### 9.4 示例

```lua
-- 返回 >=0 为剩余库存，-1 库存不足，-2 未初始化；KEYS[1]=stock:sku:{skuId}
local stockKey, num = KEYS[1], tonumber(ARGV[1])
local current = redis.call('GET', stockKey)
if current == false then return -2 end            -- 未初始化属异常，绝不能当作 0
current = tonumber(current)
if current < num then return -1 end               -- 库存不足
local left = redis.call('DECRBY', stockKey, num)
if left < 0 then                                  -- 双保险：不允许负库存
  redis.call('INCRBY', stockKey, num)
  return -1
end
return left                                       -- >=0 视为预扣成功
```

### 9.5 一句话速记
防超卖口诀是“先判后扣必须原子、以影响行数为准、Redis 做闸门 DB 做账本、全链路幂等加对账兜底”。

## 10. 秒杀系统全链路设计

### 10.1 核心原理

秒杀是“高并发 + 强一致 + 短时脉冲”的极端组合，原则是层层过滤、逐级削峰，把绝大部分流量在到达后端前干掉：前端静态化与置灰 → CDN 承载静态资源 → 网关防刷限流 → Redis 预扣挡掉无库存请求 → MQ 异步下单 → DB 最终扣减与对账。另一条主线是可预期：活动时间已知，能提前预热、压测与备预案。

### 10.2 面试问答

**Q1：秒杀分层防护怎么设计？** A：前端（静态化、按钮置灰、答题或验证码、倒计时本地化）→ CDN（静态页缓存、动态接口回源）→ 网关（IP/设备/账号黑名单、URL 动态化、限流）→ 服务（Redis 预扣、单用户限购、幂等）→ 异步（MQ 削峰、DB 最终扣减、对账补偿）；边界是防护层越多体验越差，示例假设答题环节会损失 10%~30% 用户意愿，必须评估转化率。
**Q2：限购与库存预热口径怎么统一？** A：限购用 Redis Set 记录用户-商品关系（`SADD seckill:users:{skuId} {userId}` 返回 0 表示已买过）加 DB 唯一索引 `uk_user_sku (user_id, sku_id, activity_id)` 兜底，限购多件用 Lua 原子处理，边界是限购维度要区分活动、黑产多账号需设备指纹与 IP 风控；口径统一靠预热脚本幂等（`SET` 绝对值而不是 `INCR`）并记录初始值与时间到流水表，对账用“初始值 − 成功订单 − 回补数 = 剩余值”校验，预热与开抢之间不能有真实售卖。
**Q3：怎么做压测与预案？** A：压测三阶段——单接口压测定阈值、全链路压测（影子表加流量染色）验证端到端容量与瓶颈、演练式压测模拟登录答题下单轮询的真实行为；预案五要素是降级开关清单、限流阈值调整方案与操作人、兜底页面、容量弹性（提前扩容、镜像预拉取、连接池上调）、值班决策链；边界是所有预案必须在压测或演练中至少验证过一次。
**Q4：结果怎么通知用户，超时怎么办？** A：前端轮询（示例假设每 500ms~1s 一次，需加轮询限流与退避）、长轮询（服务端 hold 5~10 秒有结果立即返回）、推送（WebSocket/SSE/App Push，实时性好但需维护长连接）；前端必须设超时（示例假设 30s），超时后展示“结果查询中”并引导去订单列表确认而不是直接报失败；边界是超过阈值仍处理中的订单由定时任务置失败并回补库存。

### 10.3 高频追问与陷阱

- 追问“超卖和少卖哪个更严重”：两者都是事故——超卖要赔付并引发客服危机，少卖则营销目标落空、损害信任；技术上是预扣闸门防超卖、对账回补防少卖。
- 陷阱：限购只在前端做，脚本直接调接口绕过；秒杀 URL 不动态化，脚本可提前拿到地址。

### 10.4 示例

| 层级 | 目标与手段 | 削峰效果（示例假设） |
| --- | --- | --- |
| 前端 / CDN | 静态化、置灰、答题；静态页缓存 | 拦截 50%~70% 无效流量，源站带宽降 80% 以上 |
| 网关 | 黑名单、URL 动态化、接口限流 | 挡掉刷量，保留正常流量 |

### 10.5 一句话速记
秒杀就是“前端拦一半、CDN 卸静态、网关防脚本、Redis 定胜负、MQ 削峰、DB 记账、对账兜底”。

## 11. 高可用与多机房架构

### 11.1 核心原理

高可用 = 冗余 + 故障转移 + 容量余量。冗余粒度从低到高：单机多进程 → 无状态多实例 → 主从 → 集群 → 同城双活 → 异地多活 → 单元化（SET 化），每提升一级可用性上升但一致性与成本复杂度也上升。多机房核心难题是数据同步与写冲突：单元化把用户按维度（如 user_id 取模）划分到不同单元，每单元只写自己的数据，用“单元内闭环 + 跨单元异步同步”从根上避免冲突。

### 11.2 面试问答

**Q1：同城双活与异地多活的取舍？** A：同城双活（示例假设距离 30~50km）延迟低、切换快、数据一致性好，能抗单机房故障；异地多活（示例假设上千公里）延迟高，必须做单元化与异步同步，能抗城市级灾难但带来跨单元一致性与路由复杂度；边界是异地多活要求业务可拆分（用户维度无强耦合），全局唯一约束需单独设计，见 [./03-分布式锁与分布式ID.md](./03-分布式锁与分布式ID.md)。
**Q2：流量怎么调度到不同机房？** A：DNS/GSLB 按地理位置、线路质量、机房健康度解析到就近入口；接入层 VIP 加健康检查做机房级故障摘除；网关按权重做灰度与比例分流；应用内做单元路由（按 user_id 计算目标单元、本地优先跨单元兜底）；边界是切换必须防止流量全压单机房引发二次雪崩，切换前确认对端有余量（示例假设可承接 1.5 倍单机房流量）。
**Q3：数据同步与冲突怎么处理？** A：同步方式按一致性从强到弱——同步双写（延迟高易阻塞）→ 半同步复制（至少一副本确认）→ 异步复制或 binlog 订阅（延迟秒级，最常用）→ 业务级消息广播；冲突策略有最后写入获胜（LWW，依赖可信时钟）、版本号或向量时钟、业务规则优先（余额以主单元为准）、人工合并；边界是 LWW 在时钟不同步时会丢更新，金额与库存必须由单一归属单元负责写，理论见 [./01-分布式理论与CAP-BASE.md](./01-分布式理论与CAP-BASE.md)。
**Q4：混沌工程怎么做才有价值？**A：原则是先假设、后验证、从非生产到生产、从单点到组合；工具如 ChaosBlade、Chaos Monkey 可注入 CPU/内存/磁盘压力、网络延迟与丢包、进程被杀、依赖报错、Redis/DB 延迟；流程是定义稳态指标（错误率、TP99）→ 注入故障 → 观察是否触发预期降级 → 恢复 → 复盘改进；边界是必须控制爆炸半径、要有中止开关、严禁在生产核心链路无准备地随机杀节点，且每次演练都要产出改进项。

### 11.3 高频追问与陷阱

- 追问“多云的价值”：降低单云厂商故障与政策风险，代价是跨云延迟、数据同步与运维复杂度，一般只对核心链路做多云。
- 陷阱：把“多副本”等同于“高可用”，副本同步延迟或选主期间仍会失败（Redis 主从异步复制可能丢数据）。

### 11.4 示例

| 架构 | 数据一致性 | 容灾级别与复杂度 |
| --- | --- | --- |
| 单机房多实例 | 强 | 抗实例故障，低复杂度 |
| 同城主备 / 同城双活 | 强 / 较强（半同步、共享存储） | 抗机房故障，秒~分钟级切换，中高复杂度 |
| 异地多活（单元化） | 最终一致，单元内强 | 抗城市级灾难，高复杂度 |
| 多云部署 | 最终一致 | 抗云厂商故障，复杂度很高 |

### 11.5 一句话速记
高可用就是“冗余 + 自动故障转移 + 容量余量”；多机房难点是数据同步与写冲突，能用单元化让写不冲突就先别做双写。

## 12. 降级预案、开关与可观测性

### 12.1 核心原理

降级预案必须能被不假思索地执行，模板是：触发条件（什么指标到多少）→ 决策人（谁拍板）→ 动作（按哪个开关）→ 验证（看什么指标）→ 回滚（什么条件下恢复）。开关分三类：功能开关（灰度新功能）、降级开关（关闭非核心能力）、限流开关（调整阈值）。可观测性三支柱是日志（发生了什么）、指标（系统现在怎么样）、链路追踪（这一次请求经过了谁），三者必须共用同一个 traceId。

### 12.2 面试问答

**Q1：开关怎么设计才安全？** A：存配置中心（Nacos/Apollo）支持秒级推送与灰度（先按实例或机房生效）；每个开关有 owner、生效范围与安全默认值；变更必须审计留痕；不被滥用成 if-else 分支堆（临时开关要有清理机制与有效期，示例假设不超过 2 周）；刷新加随机延迟防惊群；边界是开关本身要有兜底——配置中心不可用时用本地缓存的上一次配置并告警。
**Q2：可观测性三支柱各解决什么问题？**A：日志解决细节与因果（结构化 JSON 加 traceId 串联，分级并按级别采样：ERROR 全量、INFO 抽样、DEBUG 默认关闭可动态打开）；指标解决趋势与告警（时序聚合与阈值、同环比判断，成本低可长期留存）；链路追踪解决跨服务定位（TraceId/SpanId 表达调用树，示例假设核心链路 100%、非核心 1% 采样）；边界是三者必须共用 traceId，否则是三套孤岛，落地见 [../07-工程化与DevOps/03-CICD与监控告警.md](../07-工程化与DevOps/03-CICD与监控告警.md)。
**Q3：RED 与 USE 分别是什么？** A：RED 面向服务（请求视角）——Rate 请求速率、Errors 错误率、Duration 响应时长（用分位而非均值）；USE 面向资源（资源视角）——Utilization 使用率、Saturation 饱和度（队列长度、GC 暂停）、Errors 错误数；实践是应用与中间件用 RED、CPU/内存/磁盘/网络用 USE；边界是只看 RED 会漏资源瓶颈，只看 USE 会漏体验劣化。
**Q4：SLI/SLO/SLA 与错误预算、故障分级怎么用？** A：SLI 是指标（成功率、延迟分位、吞吐），SLO 是内部目标（示例假设 99.95%），SLA 是带赔偿条款的对外承诺（通常比 SLO 宽松）；错误预算 = 100% − SLO，示例假设 SLO 99.95% 对应每月约 21.6 分钟不可用额度，预算充足时正常发布、快速消耗时冻结发布；故障分级示例假设 P0 核心不可用或资金事故 5 分钟响应全员拉群、P1 15 分钟、P2 1 小时、P3 按迭代，且必须与告警通道（电话/IM）联动。

### 12.3 高频追问与陷阱

- 追问“日志太多了怎么办”：分级 + 采样 + 异步落盘，限制单条长度与字段数，支持按 traceId 动态打开 DEBUG。
- 陷阱：复盘只写“加强监控”，没有责任人与时限，改进项无法闭环。

### 12.4 示例

| 层次 | 关键监控项 | 示例告警阈值（示例假设） |
| --- | --- | --- |
| 应用 / JVM | QPS、错误率、TP99、线程池队列；堆使用率、GC 停顿 | 错误率 > 1% 或 TP99 > 500ms；老年代 > 80% |
| DB / Redis | 活跃连接、慢查询、主从延迟；命中率、RT、大 Key | 连接池 > 80%、主从延迟 > 1s；命中率 < 90% |

```text
故障复盘模板（缓存雪崩导致 DB 打挂）：
标题：2025-03-15 商品详情页不可用 22 分钟（P1）
时间线：10:00 运营批量刷新 20 万商品缓存、统一 TTL 30 分钟 → 10:30 缓存集中过期、DB QPS 从 3000 飙至 24000
→ 10:31 DB CPU 100%、连接池打满、错误率 65% → 10:32 告警（错误率 > 1%）拉起 P1 → 10:36 止血（开详情读本地缓存开关 + 详情限流）

```

### 12.5 一句话速记
预案写成“触发—决策—动作—验证—回滚”五段式；可观测性靠日志、指标、链路三支柱用 traceId 串起来——没有度量的稳定性只是运气。

## 自测题（含答案要点）

1. 分层职责与原则？答：接入分发防护、网关入口治理、应用业务无状态、中间件解耦削峰、存储持久扩展；原则是上游挡、中间缓、下游削。
2. 峰值 QPS 与实例数公式？答：峰值 = 日活×人均÷86400×峰值系数；实例 = 峰值÷单机×冗余（1.5~2），示例假设 7000÷500×2 = 28 台。
3. 并发数与 QPS、RT 关系？答：并发 = QPS × RT（利特尔法则），RT 减半等于容量翻倍。
4. 为什么 TP99 比平均 RT 更能反映体验？答：平均值被大量快请求稀释、掩盖长尾；均值用于容量计算，分位用于体验与 SLA。
5. 全链路压测为什么必须隔离数据？答：压测会写数据污染真实库存与订单，需流量染色 + 影子库表 + 影子 Topic + 依赖 Mock，并有总开关与清理。
6. 三层缓存如何分工？答：Caffeine 挡热点（快、容量小、最难一致）、Redis 挡高频共享（亚毫秒、容量大）、CDN 挡静态（就近、TTL 弱一致）。
7. 为什么“先更新 DB 再删缓存”？答：删除幂等且避免并发写乱序，TTL 与 binlog 订阅兜底；延迟双删可缩小不一致窗口。
8. 穿透、击穿、雪崩怎么处理？答：空值缓存或布隆过滤器；互斥重建或逻辑过期；TTL 抖动 + 多级缓存 + 集群高可用与降级。
9. 线程池为什么不能用无界队列？答：maxPoolSize 失效、请求无限排队直到超时，表现为慢性劣化而非快速失败，且可能 OOM。
10. 四种限流算法如何选？答：固定窗口有临界、滑动窗口平滑但开销大、漏桶匀速但不允许突发、令牌桶兼顾平均与突发，生产首选令牌桶。
11. 三层限流分工与阈值关系？答：Nginx 做 IP/连接级挡攻击、网关做接口/租户级粗限流、Sentinel 做资源与热点级细限流；阈值满足 Nginx ≥ 网关 ≥ 单机×实例数。
12. 熔断三态与为何不再选 Hystrix？答：Closed 统计超阈值转 Open，Open 到休眠窗口结束转 Half-Open，探测达标回 Closed；Hystrix 已停止维护，改用 Sentinel 或 Resilience4j。
13. 超时预算与重试规则？答：上游超时必须小于下游超时之和并留 20% 缓冲、传递全局 deadline；重试用指数退避加抖动、只在边界层，非幂等与结果不确定时禁止重试。
14. 幂等怎么做？答：唯一键前置去重表或 setnx + DB 唯一索引兜底 + 状态机校验，因 Redis 会失效故 DB 兜底不可少。
15. 防超卖的核心与边界？答：`update ... where stock >= n` 以影响行数为准（当前读加行锁串行化），Redis 预扣只作准入闸门、DB 才是权威账本，配合流水与对账防少卖。

## 背诵卡片

- 分层优化：上游挡、中间缓、下游削，扩容只扩最紧的那一层；LB 不等于扩容。
- 峰值 QPS = 日活 × 人均请求 ÷ 86400 × 峰值系数（日常 3~5，大促 10 以上为示例假设）。
- 峰值系数必须用历史监控回归（取同类活动峰值上浮约 20%），不能拍脑袋。
- 利特尔法则：并发数 = QPS × RT，RT 减半等于容量翻倍；实例数 = 峰值 ÷ 单机 × 冗余（1.5~2）。
- 平均 RT 会骗人：容量看平均，体验看 TP99/TP999（长尾效应）。
- 四级缓存分工：Caffeine 挡热点、Redis 挡高频、CDN 挡静态、DB 是最后一道。
- 线程池隔离：按依赖分池，池满只影响该依赖；绝不用共享默认池与无界队列。
- MQ 削峰边界：积压 ≈（峰值 QPS − 消费 TPS）× 持续时间，积压时长必须小于用户容忍上限。
- 四种限流：计数器有临界、滑动窗口平滑、漏桶匀速、令牌桶兼顾平均与突发（首选）。
- 限流分工：Nginx 挡 IP 与连接攻击、网关做接口与租户粗限流、Sentinel 做资源与热点细限流。
- 熔断三态：Closed → Open → Half-Open → Closed/Open；Hystrix 已停止维护。
- 舱壁隔离：按依赖、租户、业务、机房分池，一个舱进水不影响其他舱。
- 超时预算：上游超时必须小于下游超时之和，逐层递减并留约 20% 缓冲，传递全局 deadline。
- 重试策略：指数退避加抖动、只在最外层、有最大次数与总耗时；抖动用于避免重试风暴。
- 重试必须幂等：非幂等写、已超时且结果不确定、明确业务错误、限流或熔断拒绝一律不重试。
- 异步下单：入队 → 幂等消费 → 建单扣减 → 结果通知（轮询/长轮询/推送），超时置失败并回补库存。
- 热点打散：预热、本地缓存、Key 加随机后缀、拆分大 Value、逻辑过期。
- 写后读一致三招：刚写完读主库、会话粘性延迟窗口、位点或版本校验未追平回主库。
- 乐观锁防超卖：UPDATE stock SET available = available - n WHERE sku_id = ? AND available >= n，以影响行数为准。
- Redis + Lua 预扣：脚本内 GET、判空、判断、DECRBY 原子完成；未初始化返回错误码而不是当作 0。
- 分段扣减：库存拆 N 段分散单 Key 竞争，需跨段补偿与各段水位告警防碎片。
- 秒杀分层防护顺序：前端置灰答题 → CDN 静态 → 网关防刷限流 → Redis 预扣 → MQ 异步下单 → DB 落账 → 对账回补。
- 幂等做在哪一层：入口唯一键去重（Redis setnx）+ DB 唯一索引兜底 + 状态机校验，三层缺一不可。
- 同城双活延迟低、切换快、可较强一致；异地多活抗城市级灾难但需异步同步、写冲突复杂。
- 单元化（SET 化）按 user_id 等维度划分，让每个单元只写自己的数据，从根本上避免写冲突。
- 降级开关经配置中心动态生效、支持灰度、默认值安全、有 owner 与审计、临时开关要有有效期。
- 预案五段式：触发条件 → 决策人 → 动作 → 验证 → 回滚，动作必须是一键开关。
- 可观测性三支柱：日志看细节、指标看趋势、链路看跨服务定位，靠 traceId 串联。
- RED 看服务（速率/错误/延迟），USE 看资源（使用率/饱和度/错误）。
- SRE 指标：SLI 是指标、SLO 是内部目标、SLA 是对外承诺；错误预算 = 100% − SLO。
- 故障分级：P0 5 分钟响应全员拉群、P1 15 分钟、P2 1 小时、P3 按迭代（示例假设）。
- 故障复盘五要素：时间线、影响面、根因（直接/深层/管理）、止血、改进（含责任人与时限）；混沌工程要先小流量、有中止开关。
