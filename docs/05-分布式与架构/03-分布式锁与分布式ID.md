## 1. 分布式锁的本质与六要素
### 1.1 核心原理
本地锁（`synchronized`、`ReentrantLock`、`StampedLock`）的互斥语义建立在 **JVM 进程内的对象头/AQS state** 上，作用域只有一个进程：同一 JVM 内线程互斥，不同 JVM 之间互不可见；一旦出现**多实例部署**（负载均衡轮询、K8s 多副本）、**容器漂移与扩缩容**、**同机多进程**（灰度双跑、sidecar），本地锁完全失效——两个实例各持自己的锁同时进入临界区，超卖与重复执行随之而来，因此必须把"锁状态"外置到**所有实例都能访问且能达成共识**的共享存储：Redis、ZooKeeper、etcd、数据库。

| 六要素 | 含义 | 不满足时的现象 |
| --- | --- | --- |
| 互斥 | 同一时刻只有一个客户端持锁 | 超卖、重复执行 |
| 避免死锁 | 持锁者崩溃后锁能自动或兜底释放 | 锁永久占用，业务全阻塞 |
| 可重入 | 同一线程重复加锁不阻塞自己 | 同类方法互调时自死锁 |
| 高可用 | 存储节点故障时锁服务仍可用 | 锁服务成为单点 |
| 高性能 | 加解锁延迟低、吞吐高 | 加锁成为业务瓶颈 |
| 可续期 | 业务耗时超过租期时能续期 | 锁提前失效，临界区被并发进入 |
### 1.2 面试问答
**Q1：为什么 `synchronized` 在分布式环境下失效？** A：结论——锁状态只存在于单个 JVM 堆内的对象头里，跨进程不可见；原因——monitor 进入/退出与 AQS 的 `state` 都是进程内内存语义；边界——单机也可能失效（同机两个进程、Tomcat 解压两份、灰度双跑），只有"存储介质在进程之外 + 全体参与者达成一致"才成立。
**Q2：什么情况下可以退回本地锁？** A：结论——只要"同一资源只由一个实例处理"就可以；原因——一致性哈希把订单固定路由到某实例、MQ 按 key 顺序投递到单消费者、定时任务靠选主只在一台机器执行时，并发方只在本进程内；边界——扩缩容会重新分配路由，切换瞬间仍可能两个实例处理同一 key，关键路径仍要叠加幂等。
**Q3：分布式锁本质上是什么系统问题？有锁了还要幂等吗？** A：结论——是建立在"共享存储 + 共识/超时"之上的互斥，本质是 CP 与 AP 的取舍，且锁与幂等是两个层次、都要有；原因——Redis 主从异步复制偏 AP（极端情况丢锁），ZooKeeper/etcd 靠多数派写入偏 CP（极端情况写不可用），而锁只在"加锁成功到锁失效"窗口内互斥，幂等是最终一致性兜底；边界——没有既绝对安全又极致性能的方案，工程上是"锁保证大概率互斥 + 业务幂等兜底"，幂等靠唯一索引（最可靠）、状态机流转、去重表或 `SETNX` 标记实现，见 [分布式事务](./02-分布式事务.md) 与 [分布式理论与CAP-BASE](./01-分布式理论与CAP-BASE.md)。
**Q4：分布式锁用在哪些场景？** A：结论——临界区必须串行且重复执行有代价的场景；原因——秒杀库存扣减、接口防重复提交、MQ 防重复消费、多实例定时任务只跑一次、缓存击穿时只放一个线程回源重建、对账任务同一周期只跑一次；边界——能用唯一索引、幂等表、状态机、条件写解决的不要上分布式锁，数据库的原子性手段比锁更可靠。
### 1.3 高频追问与陷阱
- 把锁当事务用（解锁早于事务提交 → 别人读到未提交数据、丢失更新；正确顺序"加锁 → 开事务 → 业务 → 提交 → 解锁"）；锁粒度切错（锁 `orderId` 却改共享库存）；无参 `tryLock()` 不等待导致请求被直接拒绝；异常路径绕过 `finally` 导致锁不释放。
### 1.4 示例（锁与事务的边界，文字描述）

```text
错误：开事务 → 加锁 → 业务 → 解锁 → 提交事务     正确：加锁 → 开事务 → 业务 → 提交事务 → 解锁
（前者解锁后别人能读到未提交数据；后者可用 TransactionSynchronization.afterCompletion 回调解锁）
```
### 1.5 一句话速记
本地锁管进程内、分布式锁管跨进程；六要素是互斥、不死锁、可重入、高可用、高性能、可续期。

## 2. Redis 分布式锁：从 SET NX 到 Redisson
### 2.1 核心原理
**（1）加锁与过期必须一条命令完成。** `SETNX key value` 成功后再 `EXPIRE key 30`，两条命令之间进程崩溃就留下**永不过期的锁**；Redis 2.6.12 起 `SET` 支持 `NX`/`PX`，一条命令原子完成"不存在才设置 + 设置过期"。**（2）value 必须是唯一标识**（通常 `UUID + ":" + threadId`）：若写死为 `"1"`，A 持锁期间 TTL 到期、B 拿到锁，A 执行完 `DEL` 会**误删 B 的锁**。**（3）释放必须是"比较 + 删除"的原子操作：** 先 `GET` 再 `DEL` 存在窗口期（GET 后锁恰好过期被 B 持有，DEL 仍删掉 B 的锁），必须用 Lua 在 Redis 单线程内原子执行。**（4）TTL 与业务耗时的矛盾：** 短了业务没跑完就丢锁，长了持锁者宕机要等很久，解法是**看门狗续期**。
**（5）看门狗（watchdog）。** Redisson 加锁成功后注册定时任务，周期性检查线程是否仍持锁，是则把过期时间重置为 `lockWatchdogTimeout`；**Redisson 默认 `lockWatchdogTimeout = 30s`，续期间隔约为其 1/3（约 10s）**，默认值与实现细节**以 Redisson 官方文档/源码为准**。只有**不显式指定 leaseTime** 的加锁方式才启用看门狗（`tryLock(3, 10, SECONDS)` 这类显式租期不续期、到期即释放）；看门狗依赖客户端进程存活，`kill -9` 或长 STW 会让续期中断。**（6）可重入实现要点（Redisson）：** 用 Hash 承载，field = `客户端ID:线程ID`、value = 重入次数；加锁时 field 不存在则 `hincrby 1 + pexpire`，存在且是自己则 `hincrby 1` 并续期；解锁时 `hincrby -1`，减到 0 才 `del` 并**向 `redisson_lock__channel:{锁名}` 频道 publish 解锁消息**；抢锁失败的线程订阅该频道阻塞等待、收到广播后重新竞争，避免无脑自旋（字段名以 Redisson 源码为准）。
### 2.2 面试问答
**Q1：为什么必须 `SET key value NX PX`，不能 `SETNX` 后 `EXPIRE`？** A：结论——两条命令之间存在"已加锁但未设过期"的窗口，此刻崩溃锁即永久残留；原因——Redis 只保证单条命令原子，`SET ... NX PX` 由服务端一次完成判断与写入；边界——Lua 或 `MULTI/EXEC` 也能实现，但 `SET NX PX` 最短、最省 RTT。
**Q2：value 为什么不能写死？** A：结论——用于区分锁的所有者，防止误删他人锁；原因——TTL 到期后锁可能已被他人持有，固定 value 的旧持有者 `DEL` 会删掉新持有者的锁；边界——value 唯一只解决"安全释放"，不解决锁过期本身引发的并发，仍需业务幂等。
**Q3：为什么解锁要用 Lua 脚本？** A：结论——把"读 value 判归属"和"删 key"合并为一次原子操作；原因——两步之间锁可能刚好过期并被他人获取，`DEL` 就会误删；边界——Lua 在 Redis 单线程串行执行，脚本必须短小（只做 GET/比较/DEL），写循环或重逻辑会阻塞其他命令。
**Q4：TTL 应该设多长？看门狗能保证锁不丢吗？** A：结论——默认不设显式租期、交给看门狗，必须固定值时按"P99 业务耗时 × 2~3 倍"估算并配幂等；看门狗并不能保证锁不丢（续期由本地定时线程执行，崩溃、分区、长 STW 都会让续期失败）；原因——TTL 是小概率故障下的自我保护，过大则故障恢复慢、过小则业务没跑完就丢锁；边界——`finally` 中解锁要判断 `isHeldByCurrentThread()`（非持锁线程 `unlock` 会抛 `IllegalMonitorStateException`）。
**Q5：多线程抢同一把锁会自旋吗？主从切换会丢锁吗？** A：结论——不会无脑自旋：失败线程订阅解锁频道，解锁时 publish 唤醒再重新竞争；主从切换会丢锁，这是 Redis 锁最著名的缺陷；原因——主从复制异步，加锁成功后 master 尚未同步 key 就宕机，slave 升主后 key 不存在，另一客户端可再次加锁成功，出现两个持锁者；边界——`WAIT`（Redis 3.0+）只能降低概率，主流做法是"接受小概率失效 + 业务幂等"，强一致场景改用 ZK/etcd，见第 3 节与 [Redis高可用与缓存治理](../02-数据库/05-Redis高可用与缓存治理.md)。
### 2.3 高频追问与陷阱
- 用了不带 timeout 的 `setIfAbsent(k, v)` 重载 → 生成无过期时间的锁；解锁硬编码 value 或直接 `delete(key)` → 误删他人锁（最高频事故）；`tryLock(0, ...)` 后不看返回值就进临界区；Lua 与 `RedisTemplate` 序列化配置不一致，脚本里 `KEYS`/`ARGV` 比较恒为 false。
### 2.4 示例（加锁、Lua 原子释放、Redisson 用法）

```lua
-- unlock.lua：value 匹配才删除（比较 + 删除是一个原子操作），避免误删他人锁
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end
```

```java
// 加锁：一条命令完成 NX + PX；value 为唯一标识
String value = UUID.randomUUID() + ":" + Thread.currentThread().getId();
Boolean ok = redisTemplate.opsForValue().setIfAbsent("lock:order:" + orderId, value, 30, TimeUnit.SECONDS);
if (!Boolean.TRUE.equals(ok)) { throw new BizException("获取锁失败，请稍后重试"); }
try { /* 临界区：扣库存 / 幂等校验 / 状态流转 */ } finally {   // 释放：Lua 原子比较删除
    redisTemplate.execute(new DefaultRedisScript<>(UNLOCK_LUA, Long.class), Collections.singletonList("lock:order:" + orderId), value);
}   // 等价 Jedis 写法：jedis.eval(UNLOCK_LUA, keys, args)
// Redisson：可重入 + 看门狗续期（不显式指定 leaseTime 才会续期）
RLock lock = redissonClient.getLock("lock:order:" + orderId);
if (lock.tryLock(3, TimeUnit.SECONDS)) { try { /* 临界区 */ } finally { if (lock.isHeldByCurrentThread()) { lock.unlock(); } } }
```
### 2.5 一句话速记
`SET key uuid:threadId NX PX` 加锁、Lua 比较再删释放、Redisson Hash 计数可重入、看门狗周期续期（默认 30s、约 1/3 周期续，以官方为准），一切失效场景最终靠业务幂等兜底。

## 3. RedLock 与主从切换丢锁
### 3.1 核心原理
**RedLock 完整流程（antirez 提出）：** ① 准备 N 个**相互独立**的 Redis master（经典 N = 5，不设主从、不做复制，避免异步复制丢锁）；② 记录开始时间 `T1`，客户端**顺序**向每个实例发送 `SET key value NX PX ttl`，每个实例设置**很短**的连接/响应超时（远小于 ttl，例如 5~50ms），失败或超时立即跳到下一个；③ **成功实例数 ≥ N/2 + 1（多数派）** 且**总耗时 `elapsed = T2 - T1` 小于锁有效期**才算加锁成功；④ 锁的实际有效期 = `ttl - elapsed - 时钟漂移补偿`（漂移一般毫秒级）；⑤ 加锁失败则**向所有实例发送释放请求**（含那些认为成功的），避免残锁；解锁同样对所有实例执行 Lua 比较删除。

| 观点 | 人物 | 核心论点 |
| --- | --- | --- |
| 质疑 | Martin Kleppmann（《How to do distributed locking》） | RedLock 依赖多个进程的**时钟**判断过期，而进程可能在任意点长时间 GC/STW、网络延迟、时钟跳变；一次 GC 就可能让业务在自己以为仍持锁时其实已过期，**且没有 fencing token**（单调递增令牌，用于让存储侧拒绝过期持有者的写入），无法阻止旧持有者继续写。结论：RedLock 不是正确性工具，只适合"效率优化"。 |
| 反驳 | antirez（《Is Redlock safe?》） | RedLock 不假设时钟完美，只要求"时钟漂移有界 + 系统近似同步"，对效率型用途已经足够；正确性要求高的场景应引入 fencing token，或在存储层做条件写。 |

**主流工程结论（存在争议）：** RedLock 生产落地很少（多实例成本高、超时敏感、性能差），**多数公司选择"单实例/主从 + `SET NX PX` + 业务幂等"**；一致性要求极高的场景改用 ZooKeeper/etcd。**主从切换丢锁成因链：** A 加锁成功 → master 内存已写入但复制异步、key 未同步到 slave → master 宕机（崩溃/掉电/分区）→ 哨兵或集群选举让 slave 升主（key 不存在）→ B 向新 master 加锁成功 → 结果 A、B 同时持有同一把锁。

```text
A SET NX PX 成功 → 复制异步未同步 key → master 宕机 → slave 升主（无 key）→ B 加锁成功 → A、B 双持锁
```

| 环节 | 是否可控 | 缓解手段 |
| --- | --- | --- |
| 异步复制 | 不可控（Redis 复制固有语义） | 无根治手段，只能缩小窗口；调小哨兵 `down-after-milliseconds` 可加快切换但会引入误判 |
| `WAIT numreplicas timeout` | 可控但有限 | 加锁后等副本确认可缩小窗口，代价是延迟升高且非强一致 |
| 业务后果 | 可控 | **幂等 + 唯一索引 + 状态机 CAS** 兜底，唯一可靠的防线 |
### 3.2 面试问答
**Q1：RedLock 为什么要多数派成功？** A：结论——多数派保证任意两个成功集合必相交，任意时刻最多一个客户端认为自己持锁；原因——与 Raft/Paxos 的 quorum 思想一致，容忍少数节点故障（5 挂 2 仍可用）；边界——该保证只在"进程不会在锁有效期内暂停超过漂移上界"时成立，这正是 Kleppmann 攻击的点。
**Q2：为什么加锁要顺序执行？Kleppmann 的核心质疑是什么？** A：结论——顺序执行才能准确计算 `elapsed`，让"有效期 = ttl - elapsed"有意义；Kleppmann 指控两点：**没有 fencing token 时正确性无法保证**、**过期判断依赖本地时钟而进程暂停不受控**（协议正确也可能写入过期数据）；原因——并发请求无法确定统一成功时刻，而即使协议正确，持锁者在暂停期间锁已过期却不知情、仍会写入存储；边界——N 个实例意味着 N 次 RTT，加锁延迟远高于单实例。
**Q3：antirez 如何反驳？为什么没有标准答案？** A：结论——antirez 认为只需"近似同步 + 时钟漂移有界"，fencing 应由存储层负责，Kleppmann 认为这是把假设强加给使用者；原因——争论本质是分布式系统模型假设边界之争，基于超时判断的锁都是"效率锁"而非"正确性锁"；边界——面试给出双方观点 + 主流工程选择即可，不要说"RedLock 是错的"；业务必须强一致时应使用锁 + fencing token（资源侧只接受"令牌大于已记录值"的写入，需存储侧支持条件更新）。
**Q4：ZooKeeper 就没有主从丢锁问题吗？** A：结论——ZK 不靠超时判断过期，而靠会话 + 临时节点，因此没有 Redis 式的异步复制丢锁；原因——创建临时节点前必须已与 quorum 建立会话，节点创建走 Leader 的 ZAB 多数派提交，Leader 宕机后新 Leader 仍保证已提交数据不丢；边界——ZK 有自己的坑，`sessionTimeout` 依赖连接质量，长时间 GC 仍可能被判会话过期而丢锁。
### 3.3 高频追问与陷阱
- 把 RedLock 当成"高可用单实例锁"（它解决的是单实例丢锁，代价是延迟与运维复杂度）；5 个实例共用一台物理机或一个交换机时故障域不独立，RedLock 形同虚设；业务耗时超过 `ttl - elapsed` 同样丢锁且没有看门狗（Redisson 3.x 已废弃 `RedissonRedLock`，推荐 `RLock` 组合，以官方文档为准）；误以为多数派能像 Raft 那样容错任意少数故障——时钟问题与 GC 停顿不属于节点故障模型。
### 3.4 示例（RedLock 加解锁伪代码）

```text
redlock_acquire(key, ttl, n=5):
  T1 = now();  for each master_i: ok_i = SET(key, uniqueValue, NX, PX=ttl)   # 顺序执行、短超时
  success = count(ok_i);  elapsed = now() - T1
  if success >= n/2 + 1 and elapsed < ttl: return { acquired: true, validity: ttl - elapsed - drift }
  else: for each master_i: eval(UNLOCK_LUA, key, uniqueValue); return { acquired: false }   # 回滚残锁
```
### 3.5 一句话速记
RedLock = N 个独立 master 顺序 `SET NX PX`，多数派成功且耗时小于 ttl 才算成功；Kleppmann 用 GC/时钟/无 fencing token 质疑，antirez 用有界漂移反驳——**存在争议，主流生产选单实例/主从 + 幂等**。

## 4. ZooKeeper 分布式锁
### 4.1 核心原理
ZK 锁的载体是**临时顺序节点（ephemeral sequential）**，锁的"过期"由**会话**而非超时时间决定。**获取流程：** ① 在锁目录（如 `/lock/order`）下创建临时顺序节点，ZK 自动追加单调递增序号 `/lock/order/order-0000000001`；② 判断自己是否序号最小——是则加锁成功，不是则**只对自己前一个节点注册 Watch**（`exists`/`getData`）并阻塞等待；③ 前驱节点被删除触发回调，回到第 ② 步重新判断。**释放流程：** 主动释放 = 删除自己的临时节点（触发后继 Watch）；异常或宕机释放 = 会话超时后 ZK 自动删除该会话创建的所有临时节点——**不需要 TTL 续期，这是 ZK 相对 Redis 的核心优势**。**惊群与顺序节点优化：** 若所有等待者都监听锁目录的"子节点变化"，锁一释放**所有等待者同时被唤醒**抢锁（羊群效应/惊群），给 ZK 集群造成瞬时压力；**只监听前驱节点**把唤醒变成**链式、逐个**的，天然实现**公平锁（FIFO）**。**性能瓶颈：** 节点创建/删除都是**写请求**，必须走 Leader 由 ZAB 多数派提交，集群越大写性能越低，吞吐通常比 Redis 低一个数量级（量级为经验值，以实测为准）；`sessionTimeout` 还受 `tickTime`/`minSessionTimeout`/`maxSessionTimeout` 约束，长 GC 可能被误判为会话失效。
### 4.2 面试问答
**Q1：ZK 锁为什么不用设置过期时间？** A：结论——临时节点随会话存在，会话结束（超时未心跳）节点自动消失；原因——ZK 用心跳维护会话，服务端在 `sessionTimeout` 内收不到心跳即判定会话失效并清理临时节点，等价于自动释放；边界——会话超时依赖连接质量，Full GC 或网络抖动可能被误判，出现"自己以为还持锁、实际已释放"，与 Redis 丢锁同类风险。
**Q2：为什么只监听前一个节点能避免惊群？** A：结论——把"一把锁唤醒 N 个等待者"变成"一个节点唤醒下一个节点"的链式传递；原因——每个等待者只关心自己的前驱，锁释放只精准唤醒直接后继，形成公平排队；边界——ZK 的 Watch 是**一次性**的，回调后必须重新注册，链式唤醒在极端情况可能因某客户端长时间不响应而拖慢整条队列。
**Q3：ZK 锁的可重入怎么实现？** A：结论——ZK 原生不支持，需要客户端在本地记录"线程 + 重入次数"，重入时不再创建新节点；原因——同线程重复创建顺序节点会排到队列后面造成自阻塞；边界——Curator 的 `InterProcessMutex` 内部用 `ConcurrentMap<Thread, LockData>` 维护线程与重入计数，生产上应直接用 Curator 而不是手写，原理见 [ZooKeeper与分布式协调](../04-中间件/06-ZooKeeper与分布式协调.md)。
**Q4：ZK 锁和 Redis 锁怎么选？** A：结论——要求"锁失效自动恢复、公平、不需要续期"选 ZK，要求"高吞吐、低延迟、能接受小概率失效"选 Redis；原因——ZK 靠 quorum 提交 + 会话保证，一致性更强但写入昂贵，Redis 单命令极快但复制异步；边界——ZK 集群 Leader 选举期间写不可用，属于牺牲可用性换一致性。
### 4.3 高频追问与陷阱
- 用**持久节点**实现锁 → 客户端崩溃后锁永不释放；监听父目录或最小节点 → 惊群；忘记 Watch 是一次性的 → 首次唤醒后不再触发、排队"卡死"；`sessionTimeout` 过大 → 崩溃后锁要等很久，过小 → 网络抖动即丢锁。
### 4.4 示例（Curator 加解锁）

```java
InterProcessMutex lock = new InterProcessMutex(client, "/lock/order");
if (lock.acquire(3, TimeUnit.SECONDS)) {     // 内部即"临时顺序节点 + 只监听前驱"
    try { /* 临界区 */ } finally { lock.release(); }
}
```
### 4.5 一句话速记
ZK 锁 = 临时顺序节点 + 只监听前驱 + 会话超时自动释放；天然公平但写走 Leader、吞吐低，生产用 Curator。

## 5. 数据库分布式锁
### 5.1 核心原理
数据库方案有三条路线，共同点是**利用数据库自身的原子性/事务**，不引入额外中间件。**（1）唯一索引插入法：** `INSERT` 成功即加锁成功，业务完成后 `DELETE` 释放；为应对持锁进程宕机导致的行残留，加 `expire_time` 字段，新请求发现记录已过期可先删再插（本质是拿数据库做 TTL），插入抛 `DuplicateKeyException` 说明锁被占用。**（2）`SELECT ... FOR UPDATE` 悲观锁：** 事务中对目标行加排他锁（X 锁），事务提交/回滚时自动释放，**必须把整个临界区包在同一个事务里**且不能提前释放；关键是**命中索引**，`WHERE` 无索引会退化为锁大量记录甚至全表，长事务还会占用连接池。**（3）乐观锁版本号：** 不显式加锁，用 `UPDATE ... WHERE version = ? AND stock >= 1` 判断受影响行数，失败则重试或直接返回，适合冲突率低的场景。
### 5.2 面试问答
**Q1：唯一索引方案里，宕机残留的锁怎么清理？** A：结论——靠 `expire_time` 字段 + 定时清理任务双保险；原因——`INSERT` 成功但进程被 `kill -9` 时 `DELETE` 永远不会执行，新请求看到记录已过期可先删除再插入（需在事务中 `SELECT ... FOR UPDATE` 防止并发抢夺）；边界——时间判断要统一取数据库时间 `NOW()`，避免多机时钟不一致造成误判。
**Q2：`FOR UPDATE` 为什么容易引发事故？** A：结论——三个坑：索引缺失导致锁范围扩大、事务过长导致连接与锁等待、锁等待超时（`innodb_lock_wait_timeout` 默认 50s，**以官方文档为准**）；原因——InnoDB 的锁加在索引记录上，缺少合适索引会扫描并锁住更多记录；边界——锁只在事务内有效，`autocommit = 1` 且未显式开事务时 `FOR UPDATE` 的锁会立即释放、等价于没加锁，机制详见 [MySQL事务锁与MVCC](../02-数据库/02-MySQL事务锁与MVCC.md)。
**Q3：数据库锁的性能与死锁风险如何？乐观锁为什么正确？** A：结论——数据库锁性能最低、最易成为瓶颈，但实现最简单、一致性最可靠；乐观锁把互斥下沉到"单条 UPDATE 的行锁 + 版本条件"上，由数据库保证原子性；原因——每次加解锁都是一次带事务开销的写入，QPS 量级远低于 Redis，多把锁按不同顺序获取时极易在 InnoDB 层死锁，而 `WHERE version = ?` 使并发的后者影响行数为 0、重试即可；边界——规避死锁要**统一加锁顺序**、缩短事务，真正的防护点是 `WHERE stock >= 1` 这类条件写，它天然不会超卖。
**Q4：数据库锁和 Redis 锁怎么选？** A：结论——低频、强一致、不愿引入中间件选数据库，高频、短临界区选 Redis；原因——数据库锁的正确性来自事务与唯一约束，不会因进程暂停或主从切换丢锁，代价是性能与连接占用；边界——锁表与业务表同库同事务时，长事务会把锁行一起裹挟，建议用独立锁表并配独立连接池。
### 5.3 高频追问与陷阱
- `FOR UPDATE` 写在事务外或 `REQUIRES_NEW` 里，锁范围与预期不符；锁表用普通索引而非唯一索引，出现重复行；忘记 `expire_time` 清理，一次宕机后业务永久阻塞；用 `SELECT ... FOR UPDATE` 锁不存在的数据会加间隙锁，阻塞并发插入。
### 5.4 示例（锁表 DDL 与三类 SQL）

```sql
-- 唯一索引法 DDL：resource 唯一，expire_time 兜底（宕机残留由定时任务清理）
CREATE TABLE `distributed_lock` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT, `resource` VARCHAR(128) NOT NULL COMMENT '资源标识，如 order:1001',
  `owner` VARCHAR(128) NOT NULL COMMENT '持有者：UUID+线程ID', `expire_time` DATETIME NOT NULL COMMENT '过期时间',
  PRIMARY KEY (`id`), UNIQUE KEY `uk_resource` (`resource`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COMMENT = '数据库分布式锁表';
-- 加锁：插入成功即持锁（DuplicateKeyException = 被占用）；释放：只有 owner 匹配才删除
INSERT INTO distributed_lock (resource, owner, expire_time) VALUES ('order:1001', 'uuid:thread-1', DATE_ADD(NOW(), INTERVAL 30 SECOND));
DELETE FROM distributed_lock WHERE resource = 'order:1001' AND owner = 'uuid:thread-1';
-- 悲观锁：必须在事务内且 WHERE 命中索引；乐观锁：条件写 + 版本号，影响行数为 0 视为失败
SELECT * FROM t_stock WHERE sku_id = 1001 FOR UPDATE;
UPDATE t_stock SET stock = stock - 1, version = version + 1 WHERE sku_id = 1001 AND version = 7 AND stock >= 1;
DELETE FROM distributed_lock WHERE expire_time < NOW();   -- 过期锁清理（定时任务）
```
### 5.5 一句话速记
数据库锁三条路：唯一索引插入（防死锁靠 `expire_time`）、`FOR UPDATE`（必须命中索引且在事务内）、乐观锁条件写（`WHERE version = ?`）；性能最差但一致性最可靠。

## 6. etcd 方案与六种方案选型
### 6.1 核心原理
etcd 基于 Raft，锁的实现要素是 **lease（租约） + revision（版本号） + 事务 CAS + Watch**：① **创建租约** `LeaseGrant(ttl)`，客户端周期性 `LeaseKeepAlive` 续约，否则租约到期后其上所有 key 自动删除（等价于带续期的自动释放）；② **事务 CAS 抢锁**，key 设计为 `/lock/order/{uuid}`，用 `Txn` 判断"按前缀查询是否已有 key"（`Compare(CreateRevision(prefix), "=", 0)`），条件成立才 `Put(key, value, WithLease(id))`，比较与写入在 Raft 提交中原子完成，故同一时刻只有一个客户端能让比较成立；③ **排队与公平**，查询失败则取前缀下**最小的 create revision**（等价于 ZK 的顺序号），只 **Watch 前一个 revision 对应的 key**，被删除后重新竞争，实现公平锁并避免惊群；④ **释放** 主动 `Revoke(leaseId)`，进程崩溃则等租约到期自动释放。

| 维度 | ZooKeeper | etcd |
| --- | --- | --- |
| 一致性协议 | ZAB（多数派） | Raft（多数派） |
| 锁载体 | 临时顺序节点 | lease 绑定的 key + revision |
| 自动释放机制 | 会话超时删除临时节点 | 租约到期删除 key |
| 排队公平性 | 顺序节点 + 监听前驱 | create revision + Watch 前驱 |
| 续期方式 | 心跳（受 sessionTimeout 约束） | `LeaseKeepAlive`，TTL 更短更灵活；生态上 ZK 偏 Java/Hadoop（Curator），etcd 偏云原生/K8s |
### 6.2 面试问答
**Q1：etcd 的锁为什么天然带"租约续期"？** A：结论——因为 key 的存活绑定在 lease 上，客户端定期 keepalive 即可续命；原因——Raft 保证租约与 key 的绑定在多数派上一致，不需要像 Redis 那样靠固定 TTL + 客户端定时重置；边界——keepalive 中断同样丢锁，泄露的 lease 由 etcd 自动回收。
**Q2：Txn 的 compare 为什么能保证互斥？** A：结论——因为"比较 + 写入"作为一条事务在 Raft 日志中提交，全体节点按同一顺序应用；原因——Raft 保证已提交日志的全局顺序一致，任意两个竞争的 Txn 必有先后、后者的 compare 必然失败；边界——etcd 的写受多数派约束，写入延迟高于 Redis，Leader 选举期间写不可用。
**Q3：为什么用 revision 而不是自己生成序号排队？** A：结论——revision 是全集群单调递增的全局版本号，天然可作为排队依据；原因——ZK 的顺序号需要父节点维护计数器，而 etcd 的 create revision 由 MVCC 版本直接提供；边界——revision 语义与 MVCC 相关，跨版本行为细节**以 etcd 官方文档为准**。
**Q4：什么场景选 etcd？** A：结论——已深度使用 K8s/云原生栈、需要"带租约的强一致协调 + Watch 事件"的场景；原因——etcd 是 K8s 默认存储，选主、服务发现、配置分发、分布式锁可复用同一套集群与运维体系；边界——纯 Java 技术栈、追求极致吞吐时优先 Redis 或 ZK，参见 [SpringCloud微服务体系](../03-框架/05-SpringCloud微服务体系.md) 与 [ZooKeeper与分布式协调](../04-中间件/06-ZooKeeper与分布式协调.md)。
### 6.3 六种分布式锁方案综合对比大表

| 方案 | 一致性 | 性能 / 吞吐量级 | 实现复杂度 | 故障表现 | 可重入 | 自动释放 |
| --- | --- | --- | --- | --- | --- | --- |
| Redis 单实例/主从（SET NX PX） | 弱（异步复制可能丢锁） | 高（万级 QPS 以上） | 低 | 主从切换丢锁 → 并发进入 | 需自研或 Redisson | 靠 TTL / 看门狗 |
| RedLock（多独立 master） | 中（有争议） | 低（N 次 RTT、超时敏感） | 高 | 故障域难独立；无 fencing token 仍有风险 | 需自研 | 靠 TTL（无看门狗） |
| ZooKeeper（临时顺序节点） | 强（quorum 提交） | 中低（写走 Leader，数千 QPS 量级） | 中（建议 Curator） | 会话超时丢锁；无 Leader 时不可用 | 需客户端维护 | 会话失效自动删除 |
| etcd（lease + Txn + revision） | 强（Raft） | 中 | 中 | 租约到期丢锁；Leader 选举期间写不可用 | 需客户端维护 | 租约到期自动删除 |
| 数据库唯一索引 | 强（单库） | 低 | 低 | 宕机残留锁需 expire_time 清理 | 不支持 | 需清理任务 |
| 数据库 FOR UPDATE / 乐观锁 | 强（单库事务） | 低 | 低 | 索引缺失锁表、长事务占连接、死锁 | 同事务天然可重入 | 事务结束即释放 |

> 性能列的量级为经验参考值，随版本、部署形态、网络与压测方式差异很大，**以实测为准**。
### 6.4 选型建议

| 业务特征 | 推荐方案 | 理由 |
| --- | --- | --- |
| 高并发秒杀、幂等控制，可接受极小概率失效 | Redis `SET NX PX` + Redisson + 幂等兜底 | 性能最高、实现最短 |
| 防重复提交、防重复消费（短临界区） | Redis `SETNX` 标记 / 唯一索引 | 临界区短，甚至不需要锁，只需标记 |
| 低频强一致（对账、日终、选主）/ 已有数据库且 QPS 低 | ZooKeeper / etcd；数据库唯一索引 / `FOR UPDATE` | 一致性优先，频率低不怕慢；数据库方案运维成本为零 |
| 临界区耗时不可预估（大批量任务） | Redis + 看门狗续期，或 ZK 会话 | 避免 TTL 到期丢锁 |
### 6.5 一句话速记
etcd 锁 = lease 续约 + Txn CAS 抢锁 + revision 排队 + Watch 前驱；选型口诀：高并发选 Redis（配幂等），强一致选 ZK/etcd，低频简单选数据库。

## 7. 锁粒度、锁分段与线上故障复盘
### 7.1 核心原理
锁粒度决定并发度：越粗（锁整表、锁全部商品）冲突越多、吞吐越低；越细（按 `orderId` 加锁）并发越高，但锁数量与运维成本上升，还要防止"锁粒度切错"——锁了 `orderId` 却改共享库存等于没锁。**锁分段（锁分桶）**把一个大资源拆成 N 个可独立加锁的子资源，把"1 把锁上的串行"变成"N 把锁上的并行"（`orderId % 16` 选锁 key、库存拆成 `stock_1`~`stock_16` 分段扣减），代价是要处理跨段扣减的原子性、剩余量汇总与哈希倾斜带来的新热点（热点段可二次拆分）。

| 粒度/手法 | 示例 | 并发度 | 风险 |
| --- | --- | --- | --- |
| 全局锁 | `lock:order` 一把锁管所有订单 | 最低 | 全站串行，极易成为瓶颈 |
| 资源级锁 | `lock:order:{orderId}` | 高 | 锁对象过多，内存与运维成本上升 |
| 分桶/分段锁 | `lock:sms:{userId % 32}`、库存分 16 段 | 高且可控 | 哈希倾斜、跨段操作复杂、需汇总剩余量 |
| 无锁化 / 队列化 | 条件写 `WHERE stock >= 1`；MQ 按 key 顺序投递单消费者 | 最高 / 中高 | 只适用于可幂等或可 CAS 的场景；吞吐受单消费者限制，见 [消息队列与RocketMQ](../04-中间件/01-消息队列与RocketMQ.md) |
### 7.2 面试问答
**Q1：秒杀为什么要做库存分段锁？** A：结论——把单点热点锁打散成 N 个桶，吞吐近似提升 N 倍；原因——单把锁的极限就是串行处理能力，而库存扣减临界区很短，锁竞争的网络 RTT 与排队开销反而成为瓶颈；边界——分段后要处理"某段扣完但总量还有"的跨段请求与汇总最终一致性，通常配合 Redis 预扣减 + 异步落库。
**Q2：锁粒度怎么定？** A：结论——以"业务不变量的最小范围"为准，被同时修改的数据才需要同一把锁；原因——锁范围必须覆盖临界区内所有共享资源，过大损失并发、过小保护不足；边界——跨多资源时统一加锁顺序（如先 `orderId` 后 `skuId`）避免死锁，不确定时先用粗粒度保证正确，再按压测细化。
**Q3：锁与事务的边界为什么会出事故？** A：结论——解锁早于事务提交时，其他线程会读到未提交的旧数据，产生丢失更新；原因——锁保护临界区互斥，事务保证可见性与原子性，锁的时间窗必须完整包住事务；边界——正确做法是提交后再解锁（`TransactionSynchronization` 的 `afterCompletion`），或干脆只用数据库锁 `FOR UPDATE`。
**Q4：定时任务、缓存击穿、对账怎么落地？** A：结论——都是"抢到锁才执行"的同一模式；原因——多实例部署下定时任务天然重复触发，锁 key 用 `lock:job:{jobName}:{周期}` 并设短 TTL；边界——缓存击穿重建锁要设很短 TTL 并做双重检查（拿锁后再查一次缓存），对账任务锁要覆盖整个对账周期，并监控"锁未释放导致任务堆积"。
### 7.3 高频追问与陷阱
- 只监控"加锁失败率"不监控"平均持锁时长"，TTL 悄悄到期无人发现；锁 key 含可变字段（如时间戳）会变成每毫秒一把新锁，形同无锁；误删他人锁、锁等待超时都应独立埋点告警，参见 [CICD与监控告警](../07-工程化与DevOps/03-CICD与监控告警.md)。
### 7.4 示例（分段锁与线上故障复盘：现象 → 根因 → 修复）

```java
int bucket = Math.floorMod(orderId.hashCode(), 16);     // 分段锁：热点打散到 16 个锁
RLock lock = redissonClient.getLock("lock:order:" + bucket);
lock.lock();                                            // 生产建议 tryLock(wait) + 业务幂等
try { /* 扣减 stock_${bucket}，汇总总剩余量 */ } finally { lock.unlock(); }
```

| 问题 | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 误删他人锁 | 并发进临界区，库存超卖 | `GET` 后 `DEL` 非原子；value 固定无法判断归属 | value 用 `UUID:threadId`，释放走 Lua 比较删除 |
| 锁提前失效导致并发 | 高峰期偶发重复执行 | 业务耗时超过 TTL，且显式设了 leaseTime 未启用看门狗 | 改用看门狗续期；压测最长持锁时长；业务加幂等 |
| 锁未释放导致业务阻塞 | 某资源后续请求全部被拒 | 异常路径未走到 `finally`；进程崩溃后锁无 TTL | 统一 try/finally 模板；所有锁必须带过期时间 |
| 时钟漂移 | 偶发"锁已过期"误判 | 依赖应用机时钟比较 `expire_time` 或算剩余租期 | 统一取服务端时间（Redis `TIME`、数据库 `NOW()`），配 NTP |
| 锁与事务边界不一致 | 数据被覆盖、丢失更新 | 先解锁后提交，或 `@Transactional` 内加锁顺序颠倒 | 事务提交后再解锁，或用 `FOR UPDATE` 承担互斥 |
| Redis 主从切换丢锁 | 切换瞬间出现两个持锁者 | 异步复制 + 主从切换 | 接受小概率失效，用唯一索引/状态机 CAS 兜底；强一致场景换 ZK/etcd |
### 7.5 一句话速记
粒度按"最小不变量"定、热点按分段打散；线上事故几乎都能归到"误删、提前失效、不释放、时钟、事务边界、主从切换"六类，修复思路统一是"原子释放 + 自动续期 + 幂等兜底"。

## 8. 分布式 ID 的需求与方案全景
### 8.1 核心原理
分布式 ID 要同时满足六个维度，所有方案都是在这些维度上做取舍：

| 需求维度 | 含义 | 不满足的后果 |
| --- | --- | --- |
| 全局唯一 | 跨库跨表不重复 | 主键冲突、数据覆盖 |
| 趋势递增 | 整体随时间变大（允许局部乱序） | B+ 树随机插入、页分裂、写放大 |
| 有序性 | 严格单调更利于排序与游标分页 | 分页/增量拉取困难，需额外时间字段 |
| 性能（TPS） | 单机可产生的 ID 数 | ID 服务成为写瓶颈 |
| 高可用 | 依赖组件故障时可降级 | ID 服务挂掉，全站不可写 |
| 长度可控 | 位数少、能用 BIGINT 承载 | 索引膨胀、存储与网络开销增加 |

**主要方案：** **UUID** 本地生成、无网络开销，但 32 位十六进制（含横线 36 字符）过长且**完全无序**，作为 InnoDB 主键会造成 B+ 树随机插入与频繁页分裂、写入性能明显下降，只适合做请求 ID/traceId/文件名。**数据库自增 + 多实例步长**：用 `auto_increment_increment`（步长）与 `auto_increment_offset`（偏移）让多实例生成互不冲突的 ID（实例 1 出 1,3,5…，实例 2 出 2,4,6…），简单可靠、天然趋势递增，但强依赖数据库、扩容要改配置、ID 有空洞。**号段模式（segment）**：库里只存"当前最大号 + 步长"，一次取一批缓存在内存发放，把 N 次数据库访问降为 1 次，配合**双 buffer** 在号段用剩一定比例时异步预取下一段，做到取号无阻塞（美团 Leaf 的 Leaf-segment 思路）。**Redis `INCR`/`INCRBY`** 原子自增、趋势递增、性能高，但可用性依赖 Redis 与持久化语义：RDB 恢复或主从切换后计数可能回退从而重复发号（AOF `everysec` 只是降低概率，**以官方持久化文档为准**），可用 `INCRBY key 1000` 批量取号降 RTT。**Snowflake** 纯本地生成、性能极高，是当前主流（见第 9 节）；**框架化号段**见第 10 节。
### 8.2 面试问答
**Q1：为什么 UUID 不适合做 MySQL 主键？** A：结论——无序且过长，破坏 B+ 树写入局部性；原因——InnoDB 主键即聚簇索引，UUID 随机分布使插入点随机跳跃，造成页分裂、页填充率下降与随机 IO，且 36 字符远比 `BIGINT` 大，二级索引还会存主键值从而放大索引体积；边界——若必须用，可转 `BINARY(16)` 或改用时间有序的 UUID v7/ULID 缓解。
**Q2：数据库自增 ID 在分库分表下怎么用？** A：结论——多实例设不同步长与偏移，或改用号段模式集中发放；原因——步长法让各实例 ID 空间互不相交且不引入新组件，但扩容要改步长并重启，易产生空洞；边界——步长法的 ID 在实例间交错，只满足"趋势递增"，且各实例 `auto_increment_increment` 必须全局一致。
**Q3：号段模式为什么性能高？双 buffer 解决什么问题？** A：结论——把"每个 ID 访问一次数据库"变成"一次取 1000 个缓存在内存发放"，TPS 从数据库写入量级提升到内存量级；原因——唯一性由数据库的原子更新（`UPDATE max_id = max_id + step`）保证；双 buffer 在号段用剩一定比例（如 10%~20%）时异步预取下一段，避免号段用完才去取造成阻塞与尖刺；边界——号段 ID 趋势递增但不连续，服务重启会浪费剩余号段。
**Q4：Redis 生成 ID 会不会重复？ID 需要严格单调递增吗？** A：结论——可能重复，且多数场景只需"趋势递增"而非严格单调；原因——Redis 重启若从旧 RDB/AOF 恢复，`INCR` 值可能回退，主从切换同样可能回退，而主键的作用只是唯一 + 写入局部性，新 ID 总体大于旧 ID 就足够；边界——不能把 Redis 当唯一 ID 来源，可搭配"重启后从数据库号段表重新加载起点"；流水号、账务凭证号等需严格有序的业务应单独设计"日期 + 序列"编号体系并由单点或数据库序列保障，与主键 ID 分离。
### 8.3 高频追问与陷阱
- 用自增 ID 做业务订单号 → 可枚举、能被推断单量，分库后还不连续；号段步长过小（如 1）等于退化成数据库自增，过大（如百万）重启浪费严重；本地缓存号段却不做提前预取，会造成周期性取号阻塞尖刺；用 `MAX(id) + 1` 生成 ID 在并发下必然重复。
### 8.4 示例（自增步长配置与 Redis 批量取号）

```sql
-- 多实例自增步长：实例1 出 1,3,5…；实例2 把 offset 改为 2，出 2,4,6…
SET GLOBAL auto_increment_increment = 2;   SET GLOBAL auto_increment_offset = 1;   -- 扩容时统一变更
```

```lua
-- 批量取号：一次 RTT 取 1000 个，本地按序发放，降低 Redis 压力
local id = redis.call('INCRBY', KEYS[1], 1000)   return { id - 999, id }
```
### 8.5 一句话速记
唯一、趋势递增、有序、性能、可用、长度可控六维取舍：UUID 只配做请求 ID，数据库自增简单但扩容难，号段靠"批量取号 + 双 buffer"换性能，Redis 快但有回退风险，雪花是本地生成的主流答案。

## 9. 雪花算法 Snowflake 与时钟回拨
### 9.1 核心原理
Snowflake 把 64 位 `long` 拆成"时间 + 机器 + 序列"三段，在**纯本地、无网络**前提下生成趋势递增的全局唯一 ID；经典位宽如下（**不同实现可调整位宽**，例如压缩机器位、把时间戳改秒级）。

| 位段 | 位数 | 含义 | 说明 |
| --- | --- | --- | --- |
| 符号位 | 1 | 恒为 0 | 保证正数，Java `long` 处理更方便 |
| 时间戳 | 41 | 当前毫秒 - 自定义起始纪元 | `2^41` ms ≈ 69.7 年，纪元上线后不可更改 |
| 数据中心 ID | 5 | datacenterId | 最多 32 个数据中心 |
| 机器 ID | 5 | workerId | 每数据中心最多 32 台机器，合计 1024 个节点 |
| 序列号 | 12 | 同一毫秒内的自增序号 | 12 位 = 4096 个/毫秒，用完则自旋等待下一毫秒 |

**单机并发量估算：** `4096/ms × 1000 = 4,096,000/s`，理论上限约 **409.6 万/秒**；实际受毫秒时钟精度、系统调用开销、序列自旋、JVM 实现限制，**明显低于理论值，以压测为准**。ID 整体趋势递增（同毫秒内按序列递增、跨毫秒递增），跨机器同毫秒内可能乱序，因此是"趋势递增"而非严格单调。**workerId 分配**必须全局唯一：配置中心下发、ZK/etcd 临时节点注册上报（Leaf-snowflake 思路）、数据库 `worker_node` 表注册，或基于 Pod 序号/IP 末位（要防扩容冲突）。

| 时钟回拨策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 拒绝/等待 | 记录上次时间戳，发现回拨就抛异常或自旋等待追平 | 实现简单，绝不产生重复 ID | 回拨量大时长时间不可用，影响写入 |
| 借用未来时间/备用位 | 用扩展位（如预留 2 位）充当额外序列，或直接用"未来时间戳"继续发号 | 回拨期间仍可用 | 需预留位宽，恢复后一段时间不可用，ID 可能跳变 |
| 历史最大时间戳比较 + 报警 | 维护进程内/持久化最大时间戳，小回拨用"上次时间戳 + 递增序列"发号并告警 | 兼顾可用性与安全 | 依赖持久化最大时间戳，回拨过大仍需拒绝 |
### 9.2 面试问答
**Q1：Snowflake 为什么能保证 ID 唯一？** A：结论——唯一性由"机器维度 + 时间维度 + 毫秒内序列"三者共同保证，只要 workerId 不重复、时间不倒退、同毫秒序列不溢出就不会重复；原因——三个维度构成互不相交的命名空间；边界——**时钟回拨是唯一性最大的敌人**，且要保证 workerId 全生命周期唯一（缩容后重建 Pod 不能复用旧 workerId）。
**Q2：为什么时间戳要从自定义纪元算起？** A：结论——41 位装不下 Unix 毫秒时间戳的合理余量，用自定义起始纪元（如服务上线时间）能最大化可用年限；原因——`(now - epoch)` 的位数需求由"要覆盖多少年"决定；边界——纪元一旦上线就不能改，否则历史 ID 与新增 ID 会撞车，多业务线共用发号服务时纪元必须统一。
**Q3：同一毫秒序列号用完了怎么办？** A：结论——自旋等待到下一毫秒再发号（`while (now <= lastTimestamp)`）；原因——序列位只有 12 位，同毫秒超过 4096 个请求必须等待，否则序列回绕会产生重复；边界——高并发下限流/背压很重要，自旋会打满 CPU，也可调位宽（机器位 4 + 序列位 14）提高单机上限，代价是节点数减少。
**Q4：怎么估算 Snowflake 容量是否够用？** A：结论——按"节点数 × 4096/ms × 1000"估算上限并留 3~5 倍余量；原因——1024 节点 × 409.6 万/秒是理论天花板，实际瓶颈通常是 workerId 是否够分配；边界——节点数不足时可把 5+5 机器位合并成 10 位自管，或用 ZK 动态分配，位宽调整必须以团队约定为准并写入文档。
### 9.3 高频追问与陷阱
- 直接复制网上代码，`epoch` 与位宽和本团队发号服务不一致导致 ID 冲突；workerId 从 IP 末位推导，K8s 重建后复用同一 workerId 会重复；只处理时钟回拨不处理序列溢出，高并发下自旋打满 CPU；把雪花 ID 直接暴露给前端（同毫秒内末位有规律）可被推断业务量。
### 9.4 示例（核心发号逻辑与时钟回拨处理，小回拨等待、大回拨拒绝并告警）

```java
public synchronized long nextId() {
    long now = System.currentTimeMillis();                       // 1) 时钟回拨：小回拨自旋等待，大回拨拒绝 + 告警
    if (now < lastTimestamp) { long offset = lastTimestamp - now;
        if (offset <= 5) { while (System.currentTimeMillis() < lastTimestamp) { } now = System.currentTimeMillis(); }
        else { throw new IllegalStateException("clock moved backwards: " + offset + "ms"); } }
    if (now == lastTimestamp) {                                  // 2) 同毫秒：12 位序列自增，溢出则等下一毫秒
        sequence = (sequence + 1) & 0xFFF;
        if (sequence == 0) { while ((now = System.currentTimeMillis()) <= lastTimestamp) { } }
    } else { sequence = 0L; }                                    // 3) 新毫秒：序列归零
    lastTimestamp = now;
    return ((now - EPOCH) << 22) | (datacenterId << 17) | (workerId << 12) | sequence;   // 41 位时间 + 5 + 5 + 12
}
```
### 9.5 一句话速记
雪花 = 1 符号 + 41 毫秒 + 5 数据中心 + 5 机器 + 12 序列（位宽可调），单机理论 4096/ms ≈ 409.6 万/秒；落地三要点：workerId 全局唯一、时钟回拨有策略、序列溢出有背压。

## 10. 号段模式与 Leaf / TinyId / UidGenerator
### 10.1 核心原理
号段模式：数据库只存"当前最大号"，实例按 `step` 批量领段并在内存发放，用条件更新保证并发安全，双 buffer 让预取异步化。**Leaf-segment** 支持按消耗速度动态调整步长，用双 buffer 消除取号尖刺；**Leaf-snowflake** 在雪花基础上用 ZK 上报 workerId 与上次时间戳，解决 workerId 分配与回拨校验；**TinyId** 是号段的工程化实现，支持多 DB 与双号段；**UidGenerator** 用"秒级时间 + workerId + 序列"生成 64 位 ID，**默认位宽为 1 位符号 + 28 位秒级时间 + 22 位 workerId + 13 位序列（workerId 由数据库分配）**，28 位秒约可用 8.7 年——**具体位宽与行为以百度官方文档为准**。

| 框架 | 流派 | 核心机制 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| 美团 Leaf-segment | 号段 | DB 号段 + 双 buffer + 动态步长 | 趋势递增、性能高、可读性好 | 依赖 DB，ID 有空洞 |
| 美团 Leaf-snowflake | 雪花 | 雪花 + ZK 上报 workerId/时间戳 | 无网络依赖、性能极高 | 依赖时钟，位宽固定 |
| 滴滴 TinyId | 号段 | 号段 + 多 DB + 双号段缓存 | 可用性高、易接入 | 需部署独立服务，ID 不连续 |
| 百度 UidGenerator | 雪花变体 | 秒级时间 + DB 分配 workerId + 缓存序列 | 单机吞吐极高、位宽紧凑 | 时间位短（约 8.7 年）、依赖 DB 分配 |
### 10.2 面试问答
**Q1：号段模式怎么保证并发安全？** A：结论——靠数据库条件更新/事务保证"同一段号只被一个实例领走"；原因——`UPDATE ... SET max_id = max_id + step WHERE biz_tag = ?` 是原子写，再 `SELECT` 取得新值；边界——用"先查后改"两步会并发重复，必须一条 `UPDATE` 或 `FOR UPDATE`。
**Q2：双 buffer 怎么设计？** A：结论——内存维护"当前号段 + 预取号段"，当前号段消耗到阈值（如 10%）时异步线程去 DB 取下一段；原因——取号是内存操作，避免等到用完才同步等 DB 造成阻塞与 RT 尖刺；边界——异步预取失败要有降级（阻塞取或快速失败）与告警，否则号段耗尽直接不可用。
**Q3：动态步长有什么用？** A：结论——按号段消耗速度自动调整步长，让"一个号段既撑得久又不浪费"；原因——固定小步长导致频繁访问 DB，固定大步长在低谷时浪费大量 ID（重启丢号严重）；边界——动态调整需持久化"上次更新时间"并做限幅（如 1000~1000000），避免抖动。
**Q4：框架怎么选？** A：结论——需要趋势递增且能接受依赖 DB 选 Leaf-segment/TinyId，追求极高性能与本地生成选 Leaf-snowflake/UidGenerator；原因——号段把复杂度放在 DB 与运维，雪花把复杂度放在时钟与 workerId 分配；边界——自研成本不低，多数公司直接用 Leaf/TinyId 或封装雪花，并与分库分表键设计保持一致（见第 11 节）。
### 10.3 高频追问与陷阱
- 号段表用 `MAX(id)` 计算新号段而非条件更新，并发下重复发号；忘记处理"当前号段耗尽 + 预取失败"的降级路径；多业务共用一张号段表却未按 `biz_tag` 隔离。
### 10.4 示例（号段表 DDL 与取号逻辑）

```sql
-- 美团 Leaf 风格的号段表：一个 biz_tag 一行，step 为每次领取的号段长度
CREATE TABLE `leaf_alloc` (
  `biz_tag`     VARCHAR(128) NOT NULL COMMENT '业务标识',
  `max_id`      BIGINT       NOT NULL DEFAULT 1 COMMENT '当前已分配到的最大 ID',
  `step`        INT          NOT NULL COMMENT '号段长度',
  `update_time` TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`biz_tag`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'order';   -- 领段（条件更新保并发安全）
SELECT max_id, step FROM leaf_alloc WHERE biz_tag = 'order';            -- 取回本段上界
```

```java
// 内存发放：当前号段 [current, max] 用完后切换缓冲号段，用剩 10% 时异步预取下一段
public synchronized long nextId() {
    if (current >= max) {
        Segment next = buffer.poll();                 // 双 buffer：优先用预取好的号段
        if (next == null) { next = fetchFromDb(); }   // 预取失败则同步取（降级路径）
        current = next.start; max = next.end; asyncPrefetch();
    }
    return current++;
}
```
### 10.5 一句话速记
号段 = "DB 只管发段、内存负责发号" + 双 buffer 异步预取 + 条件更新保安全；Leaf/TinyId 走号段，Leaf-snowflake/UidGenerator 走雪花变体（UidGenerator 默认 1+28+22+13，以官方为准）。

## 11. ID 方案对比、选型与分库分表配合
### 11.1 核心原理
**（1）分布式 ID 方案对比大表：**

| 方案 | 唯一性 | 有序性 | 性能 | 依赖 | 长度 | 可用性 |
| --- | --- | --- | --- | --- | --- | --- |
| UUID | 高 | 完全无序 | 极高（本地） | 无 | 36 字符/16 字节 | 最高 |
| 数据库自增（含步长） | 高 | 严格递增（单库） | 低 | 单库/多库 | BIGINT | 低（DB 单点） |
| 号段模式 | 高 | 趋势递增 | 高 | 数据库 | BIGINT | 中高（可多 DB/降级） |
| Redis INCR/INCRBY | 高（配置不当时可能回退） | 趋势递增 | 很高 | Redis | BIGINT | 中（受持久化/切换影响） |
| Snowflake | 高（需 workerId 唯一） | 趋势递增 | 极高（本地） | 时钟 + workerId 分配 | BIGINT | 最高 |
| UidGenerator / Leaf / TinyId | 高 | 趋势递增 | 极高 / 高 | DB 分配 workerId；号段依赖 DB | BIGINT | 高（号段 + 双 buffer） |

**选型结论：** 需要"趋势递增 + 高并发"时选 **雪花或号段**（雪花偏本地高性能、号段偏可读与可预测）；需要严格有序（凭证号、流水号）时用数据库序列或单点发号器；只要求唯一且不落库做主键可用 UUID；绝不要用 `MAX(id) + 1` 或时间戳拼接。**（2）与分库分表的配合：** 分片键决定路由，ID 生成必须与路由解耦——① 用 `orderId` 做分片键时，ID 由发号器先生成再按 `orderId % N` 路由（"ID 先行、路由后置"）；② 用 `userId` 做分片键时，先路由再在片内生成，需保证跨片唯一（雪花天然满足）；③ 避免跨片查询，查询条件必须带分片键；④ 扩容时不能依赖 `id % N` 反推分片，应把分片位编入 ID 或用映射表，细节见 [MySQL调优主从与分库分表](../02-数据库/03-MySQL调优主从与分库分表.md)。
**（3）主键设计对比：**

| 主键类型 | 索引局部性 | 页分裂 | 写入性能 | 主从切换 | 敏感信息泄露 |
| --- | --- | --- | --- | --- | --- |
| 自增 BIGINT | 最好（顺序追加） | 少 | 高 | 需处理自增冲突（双主步长） | 泄露业务量 |
| 雪花 BIGINT | 好（趋势递增） | 很少 | 高 | 无影响（本地生成） | 泄露时间与机器信息 |
| UUID（字符/BINARY(16)） | 差（随机插入） | 频繁 | 低 | 无影响 | 可预测性低，也难枚举 |
| 业务主键 | 依业务而定 | 视情况 | 视情况 | 视情况 | 易泄露（手机号、身份证） |
### 11.2 面试问答
**Q1：为什么"趋势递增 + 高并发"最终落到雪花或号段？** A：结论——两者都满足唯一、趋势递增、高性能，只是依赖不同；原因——雪花本地生成无网络开销但依赖时钟与 workerId 分配，号段依赖 DB 但 ID 连续可读、便于排查；边界——业务需要严格有序或可读性（对账、凭证）优先号段，要求极致吞吐、无外部依赖优先雪花。
**Q2：ID 生成与分片键怎么配合？** A：结论——让 ID 与分片键同源，或"ID 先于路由生成"，保证路由可确定；原因——分片路由必须只用分片键，若 ID 与分片键无关就只能全片扫描；边界——常见做法是 `userId` 做分片键、`orderId` 用雪花保证全局唯一，查询强制带 `userId`，或用"基因法"把 `userId` 末位编进 `orderId` 以便按 `orderId` 反查。
**Q3：主键用自增还是雪花？** A：结论——单库或对写入局部性要求极高用自增，分库分表或多实例写用雪花；原因——自增依赖单点数据库、主从切换需要步长/双主配置，雪花本地生成无冲突；边界——雪花要处理时钟回拨与 workerId 唯一，自增要处理数据迁移时 ID 冲突，两者都可与业务编号分离设计。
**Q4：业务编号和主键 ID 该不该是同一个？** A：结论——不建议，应分离；原因——主键追求性能与唯一（自增/雪花 BIGINT），业务编号追求可读、可校验、防枚举（如"日期 + 类型 + 随机序列 + 校验位"）；边界——分离后要用唯一索引约束业务编号以保证可查，并注意不要在日志/接口中暴露内部主键。
### 11.3 高频追问与陷阱
- 分片键与查询条件不一致 → 全片路由甚至广播查询；扩容后仍用 `id % 旧分片数` 计算分片，数据错乱；用 UUID 做主键又做分片键，索引膨胀严重；把自增 ID 当订单号暴露，竞对可估算单量。
### 11.4 示例（ID 先行、路由后置与主键/业务编号分离）

```sql
INSERT INTO order_03 (id, order_no, user_id, sku_id, amount, status)   -- 先发号再按 user_id % 4 路由
VALUES (1927364512345678912, 'SO20250601000001', 10086, 2001, 99.00, 'CREATED');
SELECT * FROM order_03 WHERE user_id = 10086 AND id = 1927364512345678912;   -- 查询必带分片键
ALTER TABLE order_03 ADD UNIQUE KEY uk_order_no (order_no);                   -- 业务编号独立且唯一
```
### 11.5 一句话速记
对比看六维（唯一、有序、性能、依赖、长度、可用），选型口诀"趋势递增 + 高并发 → 雪花或号段"；分库分表下 ID 与路由解耦、查询必带分片键，主键用 BIGINT（自增或雪花）、业务编号单独设计。

## 自测题（含答案要点）
1. **分布式锁六要素是什么？** 要点：互斥、避免死锁、可重入、高可用、高性能、可续期；本地锁失效三原因（多实例、容器漂移、同机多进程）。
2. **为什么 `SETNX` + `EXPIRE` 不安全？** 要点：两条命令之间存在"有锁无过期"窗口，崩溃即永久残留；应用一条 `SET key value NX PX`。
3. **写出释放锁的 Lua 脚本并说明为什么必须原子。** 要点：`if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end`；否则可能在锁已易主后误删他人锁。
4. **看门狗机制说清楚。** 要点：默认 `lockWatchdogTimeout` 30s、约 1/3 周期续期（以官方为准）；只有不显式设 leaseTime 才续期；进程崩溃/长 STW 仍会丢锁。
5. **Redisson 可重入怎么实现？** 要点：Hash，field = 客户端ID:线程ID、value = 重入次数；减到 0 才删并 pub/sub 广播唤醒等待者。
6. **RedLock 流程与争议。** 要点：N 个独立 master 顺序 `SET NX PX`，多数派成功且 elapsed < ttl；质疑方 Kleppmann（GC/时钟漂移/无 fencing token），反驳方 antirez（漂移有界即可）；存在争议，主流选单实例/主从 + 幂等。
7. **主从切换为什么丢锁？** 要点：异步复制 → master 宕机 → slave 升主无 key → 新客户端加锁成功 → 两个持锁者；靠幂等/唯一索引兜底。
8. **ZK 锁的获取、释放流程与惊群优化。** 要点：临时顺序节点 → 序号最小者持锁，否则只 Watch 前驱；释放 = 删节点或会话超时自动清理；只监听前驱避免惊群、天然公平。
9. **数据库三种锁方案各说一句。** 要点：唯一索引插入（`expire_time` 清残留）、`FOR UPDATE`（命中索引 + 事务内）、乐观锁条件写（`WHERE version = ? AND stock >= 1`）。
10. **六种分布式锁方案怎么选？** 要点：高并发 Redis + 幂等；强一致 ZK/etcd；低频简单数据库；正确性要求极高时加 fencing token。
11. **分布式 ID 六个需求维度。** 要点：全局唯一、趋势递增、有序性、性能、高可用、长度可控。
12. **UUID 为什么不适合做主键？** 要点：无序导致 B+ 树随机插入与页分裂，36 字符过长、索引膨胀；只适合请求 ID。

## 背诵卡片
1. 本地锁只在一个 JVM 内互斥，多实例部署即失效，必须外置共享存储。
2. 分布式锁六要素：互斥、不死锁、可重入、高可用、高性能、可续期。
3. 加锁一条命令：`SET key value NX PX 30000`，绝不能 `SETNX` 后再 `EXPIRE`。
4. 锁 value = `UUID:threadId`，用于识别持有者，防止误删他人锁。
5. 解锁必须 Lua：GET 比较 + DEL 合成一个原子操作。
6. Redisson 看门狗默认 30s，约 1/3 周期续期（以官方为准），显式 leaseTime 不续期。
7. Redisson 可重入：Hash，field = 客户端ID:线程ID，value = 重入次数。
8. Redisson 等待用 pub/sub 广播唤醒，不做无脑自旋。
9. 锁与事务顺序：加锁 → 开事务 → 业务 → 提交 → 解锁。
10. 锁 value 若写死，一次 TTL 到期就会误删他人的锁。
11. RedLock：N 个独立 master，多数派成功 + elapsed < ttl 才算加锁成功。
12. RedLock 存在争议：Kleppmann（GC/时钟/无 fencing token） vs antirez（漂移有界）。
13. 主流结论：单实例/主从 `SET NX PX` + 业务幂等；强一致用 ZK/etcd。
14. 主从切换丢锁成因链：异步复制 → 主宕机 → 从升主无 key → 双持锁。
15. ZK 锁 = 临时顺序节点，序号最小者持锁，其余只 Watch 前驱。
16. 只监听前驱 = 公平锁 + 避免惊群；Watch 是一次性的，必须重新注册。
17. ZK 会话超时自动删临时节点，不需要 TTL 续期；但长 GC 可能丢锁。
18. ZK 锁性能瓶颈：写走 Leader、多数派提交，吞吐通常比 Redis 低一个数量级。
19. 数据库唯一索引：INSERT 成功即持锁，完成后 DELETE，靠 `expire_time` 清理残留。
20. `FOR UPDATE` 必须命中索引且在事务内，否则锁表或等于没加锁。
21. 乐观锁：`UPDATE ... WHERE version = ? AND stock >= 1`，影响行数为 0 即失败。
22. etcd 锁 = lease 续约 + Txn CAS（compare create revision）+ revision 排队 + Watch 前驱。
23. 锁分段：按 ID 取模或拆分段资源，把 1 把锁变成 N 把，注意倾斜与汇总。
24. 六类线上事故：误删、提前失效、不释放、时钟漂移、事务边界、主从切换。
25. 分布式 ID 六维：唯一、趋势递增、有序、性能、高可用、长度可控。
26. UUID 无序 → B+ 树随机插入、页分裂，只适合请求 ID。
27. 数据库自增多实例：`auto_increment_increment` + `auto_increment_offset`。
28. 号段模式 = DB 领段 + 内存发号 + 双 buffer 异步预取。
29. Redis `INCRBY` 批量取号降 RTT，但持久化/切换可能回退导致重复。
30. Snowflake = 1 符号 + 41 毫秒 + 5 数据中心 + 5 机器 + 12 序列（位宽可调）。
