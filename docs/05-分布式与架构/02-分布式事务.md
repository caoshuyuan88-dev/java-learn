## 1. 分布式事务的边界判定
### 1.1 核心原理
**本地事务**的边界是"同一个数据库连接 + 同一个事务引擎"：`BEGIN` 到 `COMMIT` 之间所有写要么一起生效、要么一起回滚，由 undo/redo 与锁保证（见 [MySQL事务锁与MVCC](../02-数据库/02-MySQL事务锁与MVCC.md)）。**分布式事务**的边界是"一次业务操作跨越了两个及以上独立资源管理器（RM）"，典型形态：跨库（分库分表后两个分片）、跨服务（订单服务与库存服务各连自己的库）、跨资源（数据库 + Redis + MQ）。核心认知：**分布式事务不是"要不要一致"，而是"多长窗口内一致、不一致时谁来兜底"**；CAP 决定跨分区时强一致与可用不可兼得（见 [分布式理论与CAP-BASE](./01-分布式理论与CAP-BASE.md)），所以工程立场是"能不用就不用"。
### 1.2 面试问答
**Q1：什么情况下真的需要分布式事务？**
A：结论——只有"两个写必须原子生效、中间态不可接受、且无法事后补偿"时才需要。三类真需求：① 资金类（A 扣 B 加，中间态意味着钱消失）；② 强唯一约束类（下单扣库存 + 创建订单，超卖不可接受）；③ 跨库同一业务的分片写（同一订单的两张从表落在不同库）。边界：只要中间态能被用户容忍并最终修正，就不该用分布式事务（详见 [分布式理论与CAP-BASE](./01-分布式理论与CAP-BASE.md)）。

**Q2：什么情况下其实不需要分布式事务？**
A：判定三问：① 中间态能否被用户看到并接受（下单送积分 → 能）；② 失败能否重试到成功（发短信、写日志 → 能）；③ 不一致能否被定时任务或对账修复（少给积分 → 能补）。任一为"能"，就用「本地事务 + 可靠消息 + 幂等消费 + 定时对账」解决，成本远低于 TCC/Seata。

**Q3：同一服务内使用多个数据源，算分布式事务吗？**
A：算。判据是"是否跨 RM"，不是"是否跨进程"。同一个 JVM 里两个 `DataSource` 连两个库就是两个 RM，`@Transactional` 只管辖绑定的事务管理器那一个，另一个库的提交/回滚完全不受控，表现为"主库回滚了、另一个库写进去了"。`ChainedTransactionManager` 只解决提交顺序、不解决原子性；正确做法是同库多表、或引入 XA / Seata AT。

**Q4：能不用就不用，替代手段具体有哪些？**
A：四件套。① **幂等**：把"重复执行"变安全（唯一索引、状态机、Token），是一切的底座；② **重试 + 退避**：把"可能失败"变"最终成功"，配合最大重试次数与死信兜底；③ **最终一致**：异步化 + 可靠消息 + 显式状态机；④ **对账 + 人工兜底**：兜住前三条没兜住的情况（见第 11 节）。另一种收敛手法是把强耦合的写放进同库（服务/表合并）、或用写时冗余消除跨服务读。

**Q5：面试官说"我们项目就用了 Seata"，怎么答？**
A：先承认现状，再给治理动作。用了不等于用对：AT 的全局锁会降低并发、undo_log 增加写放大、回滚要读快照。要能补充：明确事务边界（禁止把 RPC 与慢逻辑包进全局事务）、标注哪些分支可降级为幂等 + 对账、给全局锁竞争与超时配监控。这样既回答问题又展示工程判断（参考 [场景设计与开放题](../08-面试实战/03-场景设计与开放题.md)）。
### 1.3 高频追问与陷阱
- 陷阱：把"分布式事务"等同于"强一致"。TCC/Saga/可靠消息都是最终一致，强一致的只有 XA/2PC 与 Seata AT 的部分场景，且都要付性能代价。
- 陷阱：以为 `@Transactional` 加在跨服务调用上就生效——它只对当前线程当前数据源有效，远程调用里的写不在其管辖范围。
- 追问：分布式事务与分布式锁的关系？锁解决并发互斥（见 [分布式锁与分布式ID](./03-分布式锁与分布式ID.md)），事务解决原子提交，两者常配合但不互相替代。
### 1.4 示例：判定表

| 业务动作 | 跨 RM | 中间态可接受 | 结论 | 推荐方案 |
| --- | --- | --- | --- | --- |
| 创建订单 + 扣库存 | 是 | 否（超卖） | 需要 | TCC 冻结库存 / Seata AT |
| 下单成功 + 加积分 | 是 | 是 | 不需要 | 本地消息表 + 幂等消费 |
| 支付成功 + 发短信 | 是 | 是 | 不需要 | MQ 异步 + 失败重试 |
| 转账 A 扣 B 加 | 是 | 否 | 需要 | TCC 或 XA |
| 同库两表写入 | 否 | — | 本地事务 | `@Transactional` |
| 同服务两个数据源 | 是 | 否 | 需要 | XA / Seata AT |
### 1.5 一句话速记
跨 RM 才叫分布式事务；能收敛就不引入，能最终一致就不强一致，剩下的才轮到 TCC/XA/Seata。
## 2. XA / 2PC 与 MySQL XA 实现
### 2.1 核心原理
XA 是 X/Open DTP 模型下的**两阶段提交**规范。DTP 三角色：**AP**（Application 业务应用）、**TM**（Transaction Manager 事务管理器，负责协调全局事务）、**RM**（Resource Manager 资源管理器，通常是数据库）。一阶段 prepare：TM 让所有 RM 执行并锁定资源、写好 redo/undo，但**不提交**；二阶段 commit：全票通过则 TM 通知全部 commit，任一失败则通知全部 rollback。MySQL 命令族：`XA START 'xid'`（开启，ACTIVE）→ `XA END 'xid'`（SQL 结束，IDLE）→ `XA PREPARE 'xid'`（准备提交并持锁，PREPARED）→ `XA COMMIT 'xid'`（可带 `ONE PHASE` 一跳到底）或 `XA ROLLBACK 'xid'`，崩溃恢复入口是 `XA RECOVER`（列出处于 PREPARED 的事务）。
### 2.2 面试问答
**Q1：XA 两阶段提交流程，画一下。**
A：① AP 向 TM 请求开始全局事务；② TM 给各 RM 分配 xid，RM 执行 `XA START..END..PREPARE` 并返回投票；③ 全票通过则 TM 通知所有 RM `XA COMMIT`，否则 `XA ROLLBACK`。原因：prepare 的目的是让 TM 拿到所有 RM 的"投票"，避免部分提交。边界：两阶段不是原子的——TM 在"全部 prepare 完成、尚未发出 commit"的窗口崩溃，会出现部分 RM 已提交、部分未提交，只能靠日志 + 恢复流程兜底（3PC 用 preCommit 与超时缓解，无法根治，工程上极少使用）。

**Q2：XA 为什么性能差？**
A：三个原因。① **持锁时间长**：prepare 到 commit 之间行锁不放，锁窗口从毫秒级放大到网络往返级；② **连接占用**：XA 事务必须绑定同一连接，高并发下连接池很快被打满；③ **同步开销**：prepare 需要 fsync redo，开 binlog 时还要保证两阶段日志一致性，磁盘同步次数翻倍。边界：XA 适合"低频、短事务、总量不大"的场景，如日终批量跨库对账。

**Q3：XA 的崩溃恢复怎么做？**
A：靠持久化的全局事务日志 + `XA RECOVER` 补偿。TM 必须把"全局 XID → 各分支 prepare 结果"落盘，重启后扫描日志，对 PREPARED 的事务按日志判决补发 commit/rollback。边界：`XA RECOVER` 只能列出 PREPARED 状态的事务，已 commit/rollback 的看不到；TM 日志丢失就只能靠对账修复。这段时间锁一直不放，是典型的"卡死半个库"故障。

**Q4：MySQL XA 有哪些已知限制？**
A：常见几点（细节以官方文档为准，不同版本有差异）：① 只支持 InnoDB 等事务引擎，写非事务表会**隐式提交**；② **DDL 会隐式提交**，XA 事务里执行 DDL 直接破坏原子性且不会报错，问题在回滚时才暴露；③ XA 事务与 **binlog** 的交互有特殊要求，"一致快照/崩溃恢复"行为在历史版本上有过 bug 与行为变更；④ 一个连接同一时刻只能有一个活跃 XA 事务，不能嵌套；⑤ XID 长度有上限（历史默认 128 字节，由 gtrid/bqual/formatID 组成），超长报错；⑥ PREPARED 事务会长期阻塞该行的加锁，运维必须重点监控。

**Q5：XA 是不是已经完全不用了？**
A：有争议，给主流结论 + 分歧。**主流结论**：互联网高并发业务里 XA 基本被淘汰（性能与持锁问题）。**分歧点**：在"低频、强一致、跨异构数据源（两个不同品牌数据库，或数据库 + MQ）"场景下，XA 仍是标准且成熟的选择，很多金融日终批处理还在用。稳妥答法："XA 的适用场景被大幅压缩，而不是死了"。
### 2.3 高频追问与陷阱
- 陷阱：以为"prepare 之后 rollback 也能立刻释放锁"——释放发生在 rollback 完成那一刻，而它同样要一次网络往返。
- 陷阱：在 XA 事务里执行 `ALTER TABLE`；隐式提交破坏原子性后只留一个"部分生效"的库。
- 追问：TCC 是不是 2PC 的应用层版本？可以这么理解——把 prepare 换成"资源预留（Try）"，commit/rollback 换成 Confirm/Cancel，但锁的粒度从数据库层收回到业务层，所以并发更高。
### 2.4 示例：XA 两阶段时序
```text
AP ──①begin──▶ TM ──②XA START..PREPARE──▶ RM1 ──③OK/FAIL──▶ TM（同时对 RM2 同一套流程）
TM ──④全票通过? 是: 向所有 RM 发 XA COMMIT ；否: 向所有 RM 发 XA ROLLBACK
崩溃恢复：TM 重启 ─▶ 读全局日志 ─▶ XA RECOVER 比对 ─▶ 补发 COMMIT / ROLLBACK
```
XA 命令与作用速查：`XA START/END` 划定范围，`XA PREPARE` 落盘并持锁，`XA COMMIT/ROLLBACK` 判决，`XA RECOVER` 恢复。
### 2.5 一句话速记
XA 是标准两阶段提交：prepare 持锁不放手、连接不能还池，强一致但吞吐差，今天只在高价值低频跨库场景保留。
## 3. 柔性事务分类与适用场景
### 3.1 核心原理
"柔性事务"指**满足 BASE（基本可用、软状态、最终一致）而不满足 ACID 强隔离**的方案，按"谁来承担最终一致的兜底责任"分为三类：**补偿型**（业务代码负责，TCC、Saga：允许中间态存在，通过显式反向操作撤销已生效步骤）；**异步确保型**（消息中间件负责，可靠消息：把跨服务写改造成"本地事务 + 消息"，靠至少一次投递 + 消费幂等保证）；**最大努力通知型**（定时任务与对账负责，不保证送达，只保证尽力通知 + 定时重试 + 对账兜底）。
### 3.2 面试问答
**Q1：柔性事务与"刚事务"的核心区别是什么？**
A：**隔离性**。柔性事务放弃数据库级锁与隔离，中间态对外可见，因此必须额外解决"脏读中间态、重复执行、补偿不可逆"三类问题。边界：柔性事务都要求业务具备**幂等能力**与**可补偿能力**，做不到这两点就不能选柔性方案。

**Q2：三类柔性事务怎么选？**
A：按"能接受的延迟"倒推。毫秒级强约束且可侵入 → TCC；秒级到分钟级、下游可异步 → 可靠消息；跨公司/跨信任域、对方可能不可靠 → 最大努力通知 + 对账。Saga 是 TCC 的"低成本版"，适合步骤多、时长长的长流程（占座 → 支付 → 出票 → 通知）。

**Q3：为什么说"最终一致"是主流方案而不是降级方案？**
A：因为跨网络分区时强一致不可得（CAP），而互联网业务的绝大多数场景并不真的需要强一致：用户体验上"下单成功、积分 2 秒后到账"完全可接受；系统设计上异步化把 RT 从"最长链路求和"降为"最慢一段"。边界：资金核心账务仍要求强一致或准强一致，这类系统宁可牺牲可用性。

**Q4：柔性事务下"中间态可见"会带来什么业务问题？**
A：三个。① **超卖/透支**：中间态没锁，需要预留（冻结）字段解决；② **重复扣减**：补偿与正向操作时序错乱，需要幂等键 + 状态机解决；③ **状态回退的展示问题**：用户已看到"成功"随后被补偿成"失败"，需要前端"处理中/待确认"设计（见第 11 节）。
### 3.3 高频追问与陷阱
- 陷阱：把"最终一致"说成"最终一定一致"。不一致是常态，一致靠兜底机制（重试、对账、人工）保证，没有兜底的最终一致等于没做。
- 陷阱：认为柔性事务不需要锁。TCC 的 Try 阶段仍需并发控制（如 `WHERE stock - frozen >= n`），只是锁在业务行上而非数据库长事务里。
- 追问：柔性事务与幂等的关系？幂等是柔性事务的**前置条件**，不是可选优化。
### 3.4 三类柔性事务对比表

| 维度 | 补偿型（TCC/Saga） | 异步确保型（可靠消息） | 最大努力通知型 |
| --- | --- | --- | --- |
| 一致性强度 | 最终一致（TCC 可近似强一致） | 最终一致 | 最终一致（依赖对账） |
| 一致性延迟 | 毫秒~秒 | 秒~分钟 | 分钟~T+1 |
| 业务侵入性 | 高（三阶段/补偿接口） | 低（写本地消息表） | 极低 |
| 隔离性 | 无数据库隔离，靠预留/状态机 | 无 | 无 |
| 是否依赖 MQ | 不依赖 | 强依赖 | 可选（通知渠道） |
| 兜底角色 | 业务补偿代码 | MQ + 消费端幂等 | 定时任务 + 对账 |
| 代表实现 | Seata TCC、Hmily、Saga | 本地消息表、RocketMQ 事务消息 | 支付异步通知、对账文件 |
| 适用场景 | 资金、库存等强约束 | 下游多、可异步的业务 | 跨公司、弱约束通知 |
### 3.5 一句话速记
柔性事务 = 放弃隔离性换取可用性；补偿型靠业务撤销、异步确保型靠消息、最大努力通知型靠对账，三者都必须以幂等为底座。
## 4. TCC（Try-Confirm-Cancel）
### 4.1 核心原理
TCC 把一次分布式事务拆成三个阶段并由业务自己实现三个接口：**Try** 检查并**预留**资源（把资源从"可用"搬到"冻结"，不真正扣减，如冻结库存 `frozen_stock`、冻结金额 `frozen_amount`）；**Confirm** 确认真正扣减（`冻结 → 已扣`），**幂等且必须成功**；**Cancel** 取消、把冻结释放回可用，**幂等且必须成功**。Try 成功只是"拿到资源承诺"，TM 收集全部分支 Try 结果后驱动全部 Confirm 或全部 Cancel。因为资源在 Try 阶段已锁定，TCC 天然防超卖，隔离性优于 Saga，代价是侵入性与开发量最大。
### 4.2 面试问答
**Q1：Try 阶段该做什么、不该做什么？**
A：结论——Try 只做"检查 + 预留"，不做真正的业务生效、不做耗时操作。原因：Try 要快速返回并长期持有预留；若 Try 里直接扣款，Cancel 就必须"退款"，链路复杂度与出错概率都成倍上升。边界：Try 必须幂等（网络重试会重复调用），且必须对"预留不足"快速失败。

**Q2：空回滚是怎么产生的，怎么解决？**
A：结论——**Cancel 比 Try 先到**时产生。原因：Try 调用超时或进程崩溃，TM 认为 Try 失败并下发 Cancel，而 Cancel 在一个从未执行过 Try 的分支上"释放不存在的冻结"，若实现是"无条件减冻结量"，就会误释放别人的冻结，造成超卖或金额错误。解法：Cancel 先查事务控制表，**没有 Try 记录就插入一条 `status=CANCELED` 占位记录（或直接返回成功）**，不做任何业务释放——空回滚变成无害空操作，这条记录同时用于识别悬挂。

**Q3：悬挂是怎么产生的，怎么解决？**
A：结论——**Cancel 先到、迟到的 Try 后到**。原因：Try 因网络拥塞或 GC 卡住长时间未返回，TM 超时判失败并执行 Cancel（Cancel 做空回滚并写入占位记录）；随后迟到的 Try 真正执行成功，资源被永久冻结，而全局事务早已结束，再没人来确认或取消它。解法：**Try 执行前先查控制表**，若该业务键已有记录且状态为 `CANCELED` 就直接拒绝本次 Try（不做预留）。要求业务唯一键（订单号）在控制表上建**唯一索引**，用 `INSERT ... ON DUPLICATE KEY` / `insertIgnore` 保证并发下只生效一次。

**Q4：Confirm 和 Cancel 的幂等怎么保证？**
A：控制表 + 状态机。控制表以 `(tx_id, branch_id)` 为主键记录状态，执行前先 `UPDATE ... SET status='CONFIRMED' WHERE tx_id=? AND branch_id=? AND status='TRYING'`，**影响行数为 1 才真正执行业务**，为 0 说明重复调用，直接返回成功。注意：Confirm/Cancel 必须返回成功而不是把异常抛给 TM，否则 TM 会一直重试（重试概率在失败路径上更高，所以 Cancel 的幂等比 Confirm 更关键）。

**Q5：Confirm 或 Cancel 一直失败怎么办？**
A：分层兜底。① 重试：TM/TC 侧指数退避重试；② 持久化补偿：把失败分支写入补偿表，由定时任务无限次重试并告警；③ 人工介入：超过阈值（如 24 小时）转工单；④ 对账修复：比对冻结量与预期量，发现长期悬挂/空洞则平账。原则是**把 Confirm/Cancel 定义为"业务上必然成功"的操作**（幂等 UPDATE + 唯一索引），而不是"可能失败"的外部调用。

**Q6：TCC 与 2PC 的关系，代价有哪些？**
A：TCC 是应用层的两阶段提交：Try ≈ prepare，Confirm/Cancel ≈ commit/rollback，锁粒度从数据库行锁上升到业务预留字段、不占数据库长事务，所以并发显著更好。代价清单：高侵入（一能力三接口 + 冻结字段）、高开发量（控制表、幂等、防悬挂、补偿任务、监控）、Confirm/Cancel 必须成功、防重复杂、需要监控"冻结量 vs 预期量"的差值。
### 4.3 高频追问与陷阱
- 陷阱：只做 Confirm 幂等、不做 Cancel 幂等；陷阱：控制表没建唯一索引，靠"先查后插"保证唯一，并发下必然重复插入。
- 陷阱：以为空回滚只要"判断记录存在就 return"即可——不落占位记录就挡不住后来的悬挂 Try。
- 追问：TCC 能否只实现两阶段（Try 与 Confirm 合并）？可以，但这种"不预留、Confirm 里做真正业务"的形态本质上退化成 Saga，会失去防超卖能力。
### 4.4 示例：资源预留与控制表
```sql

-- Cancel:  UPDATE stock SET frozen = frozen - #{n} WHERE sku_id=#{sku} AND frozen >= #{n};
```

## 5. 可靠消息最终一致性
### 5.1 核心原理
核心思想：**把"跨服务的两个写操作"改造成"本地事务 + 一条消息"**。本地事务保证"业务写成功 ⟺ 消息记录落库"，投递器再把消息可靠送达下游，下游消费保证幂等，于是分布式一致性被降解为两个已被解决的问题——**消息不丢**与**消费幂等**。两种落地形态：**本地消息表**（自建表 + 定时扫描补发，不依赖 MQ 事务特性）与 **RocketMQ 事务消息**（half message + 回查，由 MQ 参与两阶段）。详见 [消息队列与RocketMQ](../04-中间件/01-消息队列与RocketMQ.md)。RocketMQ 事务消息流程：① 发 **half message（半消息）**，已持久化但对消费者不可见；② Broker 返回成功后执行**本地事务**；③ 按结果发 **commit**（可见、可投递）或 **rollback**（删除）；④ 若第 ③ 步因崩溃/网络未送达，Broker 定时**回查**本地事务状态并据此判决。
### 5.2 面试问答
**Q1：本地消息表怎么保证"业务成功消息一定发出"？**
A：业务表与消息表写在**同一个本地事务**里，两者要么都成功要么都回滚，于是"业务成功"必然伴随"消息记录存在"；再由独立线程/定时任务扫描待发送记录投递 MQ，成功后更新状态。边界：投递成功但状态更新失败会造成重复发送，所以消费端必须幂等——这就是"至少一次投递"的标准形态。

**Q2：本地消息表会不会成为性能瓶颈？**
A：会，但通常不是第一瓶颈。每次业务写多一次同库同事务的 Insert；真正的风险是扫描：`SELECT ... WHERE status=0` 全表扫会拖慢库，必须建 `(status, next_retry_time)` 联合索引 + `LIMIT` 小批量拉取；消息量爆炸后要分表、按月归档、定期清理已确认记录。更高并发下改用 RocketMQ 事务消息（省掉扫描）或"业务表状态字段 + 延迟消息补偿"。

**Q3：RocketMQ 事务消息的回查机制解决什么问题？**
A：解决"生产者本地事务结果未知"（发送 commit/rollback 时宕机）。Broker 定时回查，生产者实现 `TransactionListener#checkLocalTransaction`，依据本地事务状态回答。边界：回查有次数上限（默认 15 次，以官方文档为准），超过上限默认回滚；回查逻辑必须能在"事务已不在当前线程上下文"时判断状态，所以状态要落到本地表/业务表，不能放 ThreadLocal。

**Q4：消息不丢要在哪几处保证？**
A：三处，缺一处都可能丢。① **发送端**：同步发送 + 校验 SendStatus，失败重试并落本地消息表兜底；② **存储端**：同步刷盘（SYNC_FLUSH）+ 主从同步复制（SYNC_MASTER）；③ **消费端**：业务处理成功再返回 CONSUME_SUCCESS，异常返回 RECONSUME_LATER 进重试队列，重试耗尽进死信队列并告警。

**Q5：消费端幂等怎么做？**
A：三种做法按可靠性排序：① **唯一索引**（最优）——把业务幂等键（订单号）作唯一键，插入冲突即视为已处理；② **状态机**——`UPDATE ... WHERE status='待处理'`，影响行数为 0 说明已处理；③ **Redis 去重**——`SETNX msgId`，但受 Redis 可用性与过期时间影响，只能作辅助。幂等键必须来自业务语义（订单号），不能依赖 MessageId（重发会变）。

**Q6：消息堆积、顺序性与可靠性怎么权衡？**
A：堆积分三步处理：定位（消费能力不足 → 扩消费者/提高并发/批量消费；逻辑慢 → 查慢 SQL 与外部接口超时）、应急（限流上游、非核心消费降级为先落库后处理）、根因（毒消息进死信）。顺序性：只有"处理结果依赖前一条"时才需要（订单状态流转），RocketMQ 用 MessageQueue 选择器把同一业务键路由到同一队列并单线程消费；**顺序与并发互斥**（并发上限 = 队列数），跨服务更推荐用状态机 + 序号校验做乱序防御。监控见 [CICD与监控告警](../07-工程化与DevOps/03-CICD与监控告警.md)。
### 5.3 高频追问与陷阱
- 陷阱：先发消息再写库——消息已发出但本地事务回滚，下游收到"幽灵事件"；必须用本地消息表或事务消息杜绝。
- 陷阱：认为事务消息能保证"消息一定被消费"——它只保证消息对消费者可见，消费失败仍需重试与死信兜底。
- 追问：本地消息表与事务消息的本质区别？前者是"本地事务 + 轮询补偿"（简单、有延迟、依赖扫描），后者是"MQ 参与的两阶段 + 回查"（实时性好、耦合 MQ）。
### 5.4 示例：本地消息表 DDL 与投递流程
```sql
CREATE TABLE `local_message` (
  `id` bigint unsigned NOT NULL AUTO_INCREMENT, `biz_key` varchar(64) NOT NULL COMMENT '业务幂等键，如订单号',
  `topic` varchar(64) NOT NULL, `payload` varchar(4000) NOT NULL COMMENT '消息体 JSON',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '0待发送 1已发送 2已完成 3超限失败',
  `retry_count` int NOT NULL DEFAULT 0, `next_retry_time` datetime NOT NULL COMMENT '下次重试时间，实现退避',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`), UNIQUE KEY `uk_biz_key` (`biz_key`), KEY `idx_status_retry` (`status`,`next_retry_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
```text
① 业务写与消息记录同库同事务
   BEGIN; UPDATE orders SET status='PAID' WHERE order_no=?; INSERT INTO local_message(biz_key,topic,payload,status,next_retry_time) VALUES(?,'ORDER_PAID',?,0,now()); COMMIT;
② 投递流程（状态机）：定时任务每 1s 执行 WHERE status=0 AND next_retry_time<=now() LIMIT 100
   ├─ 发送成功 ─▶ status=1（已发送，等消费端 ACK 或对账确认）
   ├─ 发送失败 ─▶ retry_count++ ; next_retry_time = now + 2^retry_count 秒（上限 5 分钟）
   └─ retry_count>15 ─▶ status=3 超限失败 + 告警 + 人工/对账兜底
③ 消费端：幂等键处理 → 成功返回 CONSUME_SUCCESS → 可选回调把 status 置 2
```
### 5.5 一句话速记
可靠消息 = 本地事务写业务与消息记录 + 至少一次投递 + 消费幂等；本地消息表靠扫描补偿，事务消息靠半消息与回查。
## 6. 最大努力通知与对账
### 6.1 核心原理
最大努力通知是**可靠性最低、成本也最低**的一类方案：服务方在业务完成后**尽力**通知接收方（HTTP 回调 / MQ / 对账文件），接收方不保证在线，通知失败就按**递增退避**重试若干次，最终仍失败则**不再保证**，一切以 **T+1 对账或准实时对账**为准。它不试图在链路内解决一致性，而是把一致性外包给"对账"这个离线兜底环节——这与可靠消息"在链路内保证至少一次送达"是根本区别，所以它**必须**配对账，否则就是没有兜底的尽力而为。
### 6.2 面试问答
**Q1：什么时候用最大努力通知而不是可靠消息？**
A：结论——**对方不可控或不需要强保证**时用。原因：跨公司（第三方支付、银行、运营商）场景下你无法要求对方实现幂等，也无法要求对方持久化你的消息，而这类通知往往只是"提醒"，真实状态以对账为准。边界：如果通知丢失会导致资金差错且没有对账机制，就不能用这个方案。

**Q2：通知重试策略怎么设计？**
A：三段式。① 次数：一般 5~8 次（覆盖常见抖动与对方短时故障），太多会拖长资源占用；② 退避：指数退避（1s、5s、30s、2m、10m、1h），避免打垮对方；③ 时限：设有效期（如 24 小时），超过则放弃通知并转对账。所有重试记录必须落库，否则进程重启即丢失。

**Q3：对账怎么做，T+1 和准实时有什么区别？**
A：**T+1 对账**：次日取双方（或含渠道）流水文件，按"业务单号 + 金额 + 状态"逐笔比对，输出四类差异——我方有对方无（长款/未入账）、对方有我方无（短款/漏记）、金额不一致、状态不一致；差异按预设规则自动修复（补状态、补记账、发起退款），无法自动修复的生成工单。**准实时对账**：分钟级拉取对方流水或依赖实时查询接口，把窗口从 24 小时压到分钟级，代价是要处理"对方流水尚未落库"的假差异（需设延迟判定窗口）。边界：对账必须**幂等可重跑**且**可追溯**。

**Q4：最大努力通知还需要幂等吗？**
A：需要，而且更关键。重试与对账修复都会重复投递同一业务结果，接收方必须"收到几次、处理一次"：做法与可靠消息一致——业务单号唯一索引或状态机判断。
### 6.3 高频追问与陷阱
- 陷阱：只做通知不做对账。对账是这类方案**唯一的正确性来源**，没有对账就等于"尽力而为之后没有兜底"。
- 陷阱：对账只看"总量一致"就宣布成功——总量一致会掩盖单边差异，必须按单号逐笔比对。
- 追问：对账系统怎么不与业务系统耦合？只读业务库或用 binlog 同步出独立流水库（见 [MySQL调优主从与分库分表](../02-数据库/03-MySQL调优主从与分库分表.md)），不写业务表，修复动作通过业务接口或补偿任务执行。
### 6.4 最大努力通知 vs 可靠消息

| 维度 | 最大努力通知 | 可靠消息（本地消息表/事务消息） |
| --- | --- | --- |
| 送达保证 | 尽力通知，无保证 | 至少一次，链路内保证 |
| 重试策略 | 有明确上限（如 8 次 / 24 小时） | 一直重试或进死信队列 |
| 兜底方式 | T+1 或准实时对账 | 死信重投 + 对账 |
| 是否依赖 MQ | 不必须（可用 HTTP 回调） | 强依赖 |
| 实现成本 | 低 | 中 |
| 一致性延迟 | 分钟 ~ T+1 | 秒 ~ 分钟 |
| 典型场景 | 支付结果通知、第三方回调 | 下单后扣库存、发券、加积分 |
### 6.5 一句话速记
最大努力通知 = 有限次退避重试 + 对账兜底；链路内不保证一致，一致性的正确性来自逐笔对账。
## 7. Saga
### 7.1 核心原理
Saga 把一个长流程拆成 N 个**本地事务** T1..Tn，每个 Ti 配一个**补偿事务** Ci：正常路径顺序执行 T1..Tn；某一步失败则**倒序**执行 C(i-1)..C1 撤销已生效步骤。它无隔离性、无资源预留，靠补偿链实现最终一致。两种组织方式：**编排式（Orchestration）**——有中心协调者（状态机/流程引擎，如 Seata Saga、Temporal、Camunda），由它决定下一步调谁、何时补偿，流程可视化、易排错，但协调者是单点且需维护状态机；**协同式（Choreography）**——无中心，各服务订阅事件触发下一步，耦合低、扩展好，但流程分散难以追踪，参与者多时形成"事件迷宫"。
### 7.2 面试问答
**Q1：Saga 与 TCC 的本质区别？**
A：结论——**是否预留资源**。TCC 的 Try 先锁定资源再确认，天然隔离、可防超卖，但业务侵入大；Saga 直接生效、失败再补偿，无锁、吞吐高、代码量小，但存在"补偿失败"与"中间态被读"的固有风险。边界：资金/库存等不可超卖、不可透支的场景优先 TCC；流程长、步骤多、单步可逆的场景优先 Saga。

**Q2：补偿的不可逆问题怎么处理？**
A：结论——**补偿必须设计成业务上总是可执行**，做不到就改成"向前修复"。三种手法：① **语义补偿**：不撤销原操作，而是发一条冲正/退款的反向业务单（账务系统常用）；② **业务延迟**：把不可逆动作放到流程最后一步（先占座、后出票），使前序步骤都可逆；③ **人工兜底**：确实无法自动处理的转工单。

**Q3：Saga 的中间态对外可见怎么办？**
A：用状态机 + 状态过滤缓解。① 业务数据加显式状态（`PENDING/SUCCESS/CANCELED`），查询接口默认过滤中间态；② 用"语义锁"把订单置为"处理中"，禁止并发修改；③ 关键字段加版本号，补偿时校验版本，避免覆盖后续修改（思路同乐观锁，见 [MySQL事务锁与MVCC](../02-数据库/02-MySQL事务锁与MVCC.md)）。

**Q4：协同式和编排式怎么选？**
A：步骤少（≤4）且团队自治程度高 → 协同式；步骤多、需要可视化追踪、需要统一的超时与补偿 → 编排式。绝大多数互联网公司选编排式，因为可观测性与可运维性比"无中心"更重要。
### 7.3 高频追问与陷阱
- 陷阱：把"补偿"实现成"删除数据"。补偿应是**业务语义的撤销**（退款、解冻、置状态），物理删除会丢失审计与对账依据。
- 陷阱：补偿接口不做幂等——补偿同样会被重试，重复补偿等于重复退款。
- 追问：Saga 与 TCC 哪个性能更好？Saga（无预留、无锁），但代价是中间态可见与补偿失败风险，性能不是唯一维度。
### 7.4 示例：Saga 与 TCC 对比表

| 维度 | TCC | Saga |
| --- | --- | --- |
| 资源锁定 | Try 阶段预留（冻结） | 不预留，直接生效 |
| 隔离性 | 较好（靠预留字段与本地事务） | 无 |
| 业务侵入性 | 高（3 接口 + 冻结字段） | 中（正向 + 补偿接口） |
| 并发能力 | 中（预留字段有行竞争） | 高 |
| 补偿难度 | 低（释放预留即可） | 高（可能不可逆） |
| 事务时长 | 短（毫秒~秒） | 可长（秒~天） |
| 适用场景 | 资金、库存等强约束短事务 | 出行/审批/履约等长流程 |
### 7.5 一句话速记
Saga = 长流程的"正向执行 + 倒序补偿"，无锁高吞吐，但要求补偿可执行、中间态可容忍。
## 8. Seata 详解：三大角色、AT 模式与全局锁
### 8.1 核心原理
**三大角色**：**TC**（Transaction Coordinator，独立部署的 `seata-server`，维护全局/分支事务状态、驱动提交回滚、管理全局锁）、**TM**（Transaction Manager，即标注 `@GlobalTransactional` 的那个服务，负责开启/提交/回滚全局事务）、**RM**（Resource Manager，每个参与业务库的服务，负责注册分支、生成 undo_log、执行本地提交与二阶段回滚）。交互流程：TM 向 TC 申请开启全局事务得到 `XID` → XID 沿调用链传播 → 各 RM 用 XID 注册分支并执行本地事务、记录 undo_log → TM 向 TC 发起全局提交/回滚 → TC 通知各 RM 做二阶段。**TC 是新增单点**，生产必须集群 + 持久化（db/file/redis 三种存储模式，生产推荐 db），可用 [ZooKeeper与分布式协调](../04-中间件/06-ZooKeeper与分布式协调.md) 或注册中心做高可用。

**AT 模式两阶段**：一阶段在同一个本地事务里执行**业务 SQL + 写 undo_log**（记录 before image 与 after image），然后**立即提交本地事务**（这是 AT 与 XA 最大的区别：不长期持锁）；二阶段提交只需**异步删除 undo_log**（极快）；二阶段回滚先**用 after image 校验当前数据是否被其他全局事务改过**，一致则用 before image 反向生成补偿 SQL 并删除 undo_log，不一致则判定冲突、告警转人工。**全局锁与隔离性**：一阶段本地提交后行锁已释放，因此需要 TC 侧的**全局锁**做**写隔离**——同一行的全局锁未释放前其他全局事务不能改这一行（串行提交），避免"脏写"导致回滚失效；**读隔离**默认是**读未提交**（可能读到其他全局事务的中间态），要读到已提交需用 `SELECT ... FOR UPDATE`（配合 `@GlobalLock`）让查询也走全局锁，代价是性能下降。
### 8.2 面试问答
**Q1：AT 模式能不能保证隔离性？**
A：有争议，给主流结论。**主流结论**：AT 只保证**写隔离**（全局锁防脏写），**不保证读隔离**，默认等价于"读未提交"；用 `@GlobalLock + select ... for update` 可把读提升到"读已提交"，但增加锁竞争。**分歧点**：有人认为全局锁下 AT 已接近"读已提交"，实际上只有显式加锁的读才如此。答法：先说写隔离有、读隔离默认没有，再说如何按需提升。

**Q2：AT 的全局锁会带来什么问题，怎么优化？**
A：会把热点行压成串行。全局锁由 TC 内存 + 数据库表共同维护，同一行只能被一个全局事务持有，所以热点行（如秒杀库存）并发骤降；且锁释放依赖 TC 通知，TC 不可用或网络分区时会长时间占用。优化：① 缩小全局事务范围，只包必须原子提交的写；② 热点行改 Redis 预扣 + 异步落库（见 [Redis数据结构与核心原理](../02-数据库/04-Redis数据结构与核心原理.md)）；③ 避免把多个热点行放进同一全局事务；④ 给全局锁设超时，超时事务自动回滚。

**Q3：`@GlobalLock` 的使用前提是什么？**
A：只适用于**读**场景或"先查后改但不想开启全局事务"的场景，且查询必须是**带锁查询**（`FOR UPDATE`）。原因：`@GlobalLock` 本身不开全局事务，作用是"访问数据前先申请全局锁"，让本地读/写与其他全局事务互斥。边界：`@GlobalLock(readOnly = true)` 表示只检查、不注册占用全局锁，适用于"确认数据是否处于中间态"的高频校验；此时必须配合真正的 `select for update` 才能得到读隔离，否则只是检查而不会阻塞别人。

**Q4：AT 回滚为什么不会覆盖别人的修改？**
A：靠 **after image 校验**（类似乐观锁）：回滚前比对当前行值与 undo_log 中 after image 是否一致——一致说明"没人改过"，可安全用 before image 反向补偿；不一致说明中间被别的全局事务改过，Seata 判为冲突并告警，避免把别人的修改回滚掉。这也解释了为什么 AT 必须配**全局锁**：没有全局锁，校验失败率极高，回滚几乎不可用。

**Q5：AT、TCC、Saga、XA 怎么选？undo_log 会不会膨胀？**
A：AT（无侵入、成本最低、适合常规跨库 Crud，代价是全局锁与 undo_log）；TCC（需强预留语义、要防超卖，侵入大但最可控）；Saga（长流程、需可视化编排）；XA（需严格强一致且能接受性能损失）。同一系统甚至同一全局事务内可混用。undo_log 正常不会膨胀（二阶段提交成功即删除），膨胀只会发生在"TC 长时间不驱动二阶段"或"回滚反复失败"时，伴随全局锁占用与业务阻塞，属于必须告警的异常；运维建议监控 undo_log 行数、全局锁表行数与 TC 连接数。
### 8.3 高频追问与陷阱
- 陷阱：把 `@GlobalTransactional` 加在包含 RPC 与长耗时逻辑的方法上。全局事务应从业务边界开始、在所有分支写完后尽快结束，否则全局锁持有时间过长。
- 陷阱：跨线程丢 XID（`@Async`/线程池）、调用非事务型外部接口（直接 HTTP 写对方库）导致分支未注册或形成"孤儿分支"。
- 追问：TC 挂了会怎样？已开启的全局事务无法推进二阶段，分支处于"待确认"，新事务无法开启；必须集群 + db 存储 + 降级预案（暂停入口流量、人工驱动或按 undo_log 补偿）。
### 8.4 示例：undo_log 与全局锁表结构
```sql
-- 每个参与 AT 的业务库都要建 undo_log（字段以官方文档为准）
CREATE TABLE `undo_log` (
  `branch_id` bigint NOT NULL, `xid` varchar(100) NOT NULL, `context` varchar(128) NOT NULL,
  `rollback_info` longblob NOT NULL COMMENT 'before/after image 序列化内容', `log_status` int NOT NULL COMMENT '0正常 1全局已完成',
  `log_created` datetime NOT NULL, `log_modified` datetime NOT NULL, UNIQUE KEY `ux_undo_log` (`xid`,`branch_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
-- TC 侧全局锁表：写隔离的核心；row_key = resourceId^tableName^pk
CREATE TABLE `lock_table` (
  `row_key` varchar(128) NOT NULL, `xid` varchar(96) DEFAULT NULL, `transaction_id` bigint DEFAULT NULL, `branch_id` bigint NOT NULL,
  `resource_id` varchar(256) DEFAULT NULL, `table_name` varchar(32) DEFAULT NULL, `pk` varchar(36) DEFAULT NULL,
  `gmt_create` datetime DEFAULT NULL, `gmt_modified` datetime DEFAULT NULL, PRIMARY KEY (`row_key`), KEY `idx_branch_id` (`branch_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
AT 两阶段流程（文字版）：一阶段 `UPDATE stock SET stock=stock-1 WHERE sku_id=1` + `INSERT undo_log{before:10, after:9}` 在同一本地事务提交并持有该行全局锁 → 二阶段提交：TC 通知各 RM 异步删除 undo_log；二阶段回滚：TC 通知各 RM 校验当前值是否等于 after(9)，相等则用 before(10) 反向 UPDATE 并删除 undo_log，不等则判冲突、告警转人工。TC 侧还有 `global_table`（记录 xid、status、application_id、transaction_service_group、transaction_name、timeout、begin_time 等）用于全局事务状态持久化与恢复（以官方文档为准）。
### 8.5 Seata 四种模式对比表

| 维度 | AT | TCC | Saga | XA |
| --- | --- | --- | --- | --- |
| 业务侵入 | 无（自动代理 SQL） | 高（3 接口） | 中（补偿接口） | 无 |
| 一阶段 | 本地事务立即提交 | 只预留（本地提交） | 直接生效 | 不提交（PREPARE 持锁） |
| 隔离性 | 写隔离有、读隔离需显式加锁 | 好（预留） | 无 | 强（数据库锁） |
| 持锁时长 | 短（仅本地事务） | 短 | 无锁 | 长（到二阶段结束） |
| 二阶段回滚 | 自动（before image） | 调用 Cancel | 倒序补偿 | 数据库 ROLLBACK |
| 性能 | 中（热点行受全局锁限制） | 较高 | 高 | 低 |
| 适用场景 | 常规跨库 Crud | 资金/库存强约束 | 长流程 | 强一致低频 |
### 8.6 一句话速记
Seata = TC 协调 + TM 开启 + RM 执行；AT 一阶段"业务 SQL + undo_log 一起提交"，二阶段提交删日志、回滚靠 before image，写隔离靠全局锁、读隔离要显式加锁。
## 9. 各方案综合对比与选型决策树
### 9.1 核心原理
选型本质是三个问题的排序：**一致性要求有多强（能否容忍最终一致）→ 业务能不能改造（能否写补偿/预留）→ 现有基础设施有什么（有没有 MQ、有没有 Seata）**。绝大多数互联网业务落在"最终一致 + 弱改造 + 已有 MQ"的区间，因此可靠消息类是事实上的默认答案。
### 9.2 面试问答
**Q1：选型决策树怎么答？**
A：按顺序问四句。① **能不能不跨库**（架构收敛）？能 → 本地事务。② **能容忍最终一致吗**？不能 → 短事务高频用 TCC，低频强一致用 XA。③ **能容忍秒级/分钟级延迟吗**？能 → 有 MQ 就用可靠消息（本地消息表 / 事务消息）。④ **流程是否长、步骤是否多**？是 → Saga；对方不可控且只做通知 → 最大努力通知 + 对账。最后补一句：任何方案都要配幂等 + 对账兜底。

**Q2：为什么互联网公司很少选 XA？**
A：性能与运维成本：持锁到二阶段、连接无法归还、PREPARED 事务需要人工恢复，而互联网业务多为高频短事务且能接受最终一致。反过来说，若业务是"每日一次、跨两个库、必须严格一致"，XA 反而比 TCC 更省事（无业务侵入）。

**Q3：能不能一个系统混用多种方案？项目中怎么答？**
A：可以且推荐：强约束分支（扣款、扣库存）用 TCC，弱约束分支（加积分、发券、发短信）用可靠消息，第三方通知用最大努力通知 + 对账，关键是**把强约束分支数量压到最少**。项目经理式回答用三层结构：主链路（TCC 或 AT）+ 旁路（本地消息表 + 幂等消费）+ 兜底（对账 + 工单），并给出量化指标（如日均差异单 < 万分之零点五），体现工程闭环（参考 [高频八股速查手册](../08-面试实战/02-高频八股速查手册.md)）。
### 9.3 各方案综合对比大表

| 方案 | 一致性强度 | 性能/吞吐 | 业务侵入性 | 可用性/单点 | 实现复杂度 | 事务时长 | 典型适用场景 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 本地事务 | 强（ACID） | 最高 | 无 | 单库单点 | 极低 | 毫秒 | 同库多表 |
| XA / 2PC | 强（准 ACID） | 低（持锁到二阶段） | 无 | TM 单点需高可用 | 中 | 毫秒~秒 | 低频跨库、异构数据源、日终批处理 |
| 本地消息表 | 最终一致 | 高 | 低 | 依赖 MQ 与扫描任务 | 低 | 秒~分钟 | 下游可异步、已有 MQ |
| RocketMQ 事务消息 | 最终一致 | 高 | 低 | 依赖 MQ 集群 | 低 | 秒~分钟 | 订单类主链路异步化 |
| TCC | 最终一致（可近似强一致） | 中高 | 高 | TC/TM 单点，需重试机制 | 高 | 毫秒~秒 | 资金、库存、额度等强约束 |
| Saga | 最终一致 | 高 | 中 | 编排器单点 | 中高 | 秒~天 | 出行、履约、审批等长流程 |
| 最大努力通知 | 最终一致（靠对账） | 高 | 极低 | 通知方单点 | 低 | 分钟~T+1 | 第三方通知、跨公司结算 |
| Seata AT | 最终一致（写隔离） | 中（热点行受全局锁限制） | 无 | TC 单点需集群 | 低 | 毫秒~秒 | 常规跨库 Crud、老系统改造 |
### 9.4 高频连环追问与决策树

| 连环追问 | 回答要点 |
| --- | --- |
| AT 能不能保证隔离性？ | 写隔离有（全局锁），读隔离默认没有，需 `@GlobalLock + for update` |
| 悬挂怎么产生的？ | Cancel 先到并落占位记录，迟到 Try 又执行了预留；Try 必须查控制表 |
| TCC 三个问题如何解决？ | 一张控制表：唯一索引防重/防悬挂，状态机判空回滚，幂等返回成功 |
| 为什么不用 XA？ | 持锁到二阶段、连接占用、PREPARED 需人工恢复；低频强一致场景仍可用 |
| 最终一致期间数据怎么展示？ | 显式状态机 + 前端"处理中"，查询过滤中间态，超时终结并补偿 |
| Confirm/Cancel 失败了怎么办？ | 无限重试 + 补偿表 + 告警 + 人工工单，业务上定义为必然成功 |
| 本地消息表会不会性能瓶颈？ | 会：索引 + limit + 分表归档；更高并发换事务消息 |
| 消息丢了怎么办？ | 三处保证（发送/存储/消费）+ 死信队列 + 对账兜底 |

决策树（文字版）：`是否跨 RM` → 否：本地事务；是 → `能否收敛到一个库` → 能：重构为同库 → 否 → `能否容忍最终一致` → 否：短事务高频用 TCC，低频强一致用 XA → 是 → `下游能否异步` → 能：有 MQ 用可靠消息（否则本地消息表）→ 否 → `流程是否长` → 是：Saga → 对方不可控且只需通知：最大努力通知 + 对账。
### 9.5 一句话速记
选型四问：能否不跨库 → 能否最终一致 → 能否异步 → 流程是否够长；对应答案依次是本地事务、TCC/XA、可靠消息、Saga/最大努力通知。
## 10. 典型场景：电商下单全链路事务设计
### 10.1 核心原理
下单链路涉及**订单、库存、优惠券、支付、积分**五个服务，但它们的约束强度完全不同，正确做法是**分层处理**：强约束环节（库存、支付）用预留或 TCC 保证不超卖、不重复支付；弱约束环节（优惠券、积分、通知）用可靠消息求最终一致；外部渠道（支付回调）用最大努力通知 + 对账收口。核心原则：**把强一致要求的范围压到最小，让长链路跑在最终一致上。**
### 10.2 面试问答
**Q1：下单扣库存用 TCC 还是消息？**
A：用 TCC（或"Redis 预扣 + 异步落库"）。原因：扣库存必须**立即判定成功/失败**，用消息异步化会出现"下单成功但库存不够"，只能事后道歉退单。边界：秒杀场景可在 Redis 层做原子预扣、DB 异步兜底，此时一致性由"Redis 预扣 + 定期对账"保证，属于工程上的特殊选择（见 [高并发高可用架构设计](./04-高并发高可用架构设计.md)）。

**Q2：支付成功后的加积分、发券为什么用消息？**
A：因为它们是可延迟、可重试、可补发的弱约束操作。订单服务在"更新订单为已支付"的**同一本地事务**里插入本地消息表记录，再由投递器发 MQ，积分服务幂等消费；即使消息丢失，也有对账任务按"已支付订单缺积分"补齐。

**Q3：支付回调重复且乱序怎么处理？**
A：三件套。① **幂等**：以支付单号 + 渠道流水号建唯一索引，重复回调插入冲突即返回成功；② **状态机**：订单状态单向流转（`待支付 → 已支付 → 已发货`），用 `UPDATE ... WHERE status='待支付'` 的受影响行数判断，乱序的旧状态回调直接被拒；③ **主动查询兜底**：定时对"待支付超过 N 分钟"的订单主动调渠道查单，避免回调丢失。

**Q4：整个链路怎么保证用户看到的状态是对的？**
A：显式建模 + 前端配合。订单状态机：`待支付 / 支付中 / 已支付 / 已取消 / 已退款`；接口返回"支付中"时前端展示"处理中，请稍候"并轮询订单状态；超过阈值（如 5 分钟）仍为处理中则由后台任务置为失败并触发补偿（释放库存、解冻券）。原则：**不让用户看到"假成功"，也不让用户卡在永不结束的"处理中"**。

**Q5：对账发现"扣了库存但订单取消了"怎么办？**
A：按差异类型定向修复：① 订单已取消但库存仍冻结 → 调库存服务的解冻接口（幂等）；② 库存已扣减但订单不存在 → 反向补偿 `stock = stock + n`（需流水支撑，避免重复补偿）；③ 无法自动判定的差异 → 人工工单。修复动作必须有**幂等键与审计日志**，且优先级低于"防止错上加错"。
### 10.3 逐环节方案与兜底

| 环节 | 约束强度 | 失败后果 | 方案 | 兜底 |
| --- | --- | --- | --- | --- |
| 创建订单（本地事务） | 强 | 无单 | 本地事务，订单号作幂等键 | 唯一索引防重复下单 |
| 扣库存 | 强 | 超卖 | TCC 冻结库存（或 AT + 全局锁） | 对账校验 `stock + frozen` 总量 |
| 锁优惠券 | 中 | 券被重复使用 | TCC 或"预占 + 超时释放" | 定时扫描过期预占 |
| 创建支付单 | 强 | 重复支付 | 支付单号全局唯一 + 状态机 | 渠道对账 |
| 支付结果通知 | 强（资金） | 漏单 | 最大努力通知 + 主动查询 | 定时查单 + 手工补单 |
| 加积分/发通知 | 弱 | 少给积分 | 本地消息表 + 消费幂等 | 对账补发 |

全链路（文字版）：用户下单 → ①订单服务本地事务创建订单(PENDING，订单号=幂等键) → ②TCC-Try 冻结库存 + 预占优惠券（任一失败则 Cancel 已成功的预留并把订单置 FAILED）→ ③订单置"待支付"并创建支付单（支付单号唯一）→ ④用户支付、渠道异步通知（最大努力通知：重试 8 次 + 定时主动查单）→ ⑤订单服务本地事务[订单置已支付 + 插入本地消息表] → ⑥投递 MQ，积分服务/通知服务幂等消费 → ⑦TCC-Confirm 真正扣减库存、核销优惠券 → ⑧T+1 对账（订单-支付-库存-积分 四方流水比对）+ 人工工单。
### 10.4 高频追问与陷阱
- 陷阱：把整个下单链路包在一个 Seata 全局事务里。跨 5 个服务的长事务会让全局锁持有数秒，热点商品直接被打爆；必须按"强约束/弱约束"拆分事务边界。
- 陷阱：支付回调接口没有幂等与状态机，渠道重试导致重复发货、重复加积分。
- 追问：库存扣减成功但订单创建失败怎么处理？先本地事务创建订单（含库存预占字段）再调库存 Try；Try 失败则订单置失败并回滚本地事务；Try 超时则依赖 TC 的 Cancel 与对账修正。
### 10.5 一句话速记
下单链路要分层：库存与支付用 TCC/预留保强约束，积分与通知用可靠消息求最终一致，外部渠道用最大努力通知 + 对账收口。
## 11. 幂等、对账与人工兜底：三层防线
### 11.1 核心原理
分布式事务的可靠性不来自某个框架，而来自**三层纵深防御**：**第一层幂等**（让重复执行无害，是所有重试与补偿的前提）、**第二层对账**（用离线逐笔比对发现链路内无法发现的差错）、**第三层人工兜底**（对自动修复不了的差异给出口）。只做第一层、或只依赖框架的方案，在真实故障面前一定有缺口。
### 11.2 三层防线表

| 防线 | 解决的问题 | 实现手段 | 失效后果 | 关键要求 |
| --- | --- | --- | --- | --- |
| 幂等 | 重复投递/重试/补偿 | 唯一索引、状态机、幂等键表 | 重复扣款、重复发货 | 幂等键必须来自业务语义 |
| 对账 | 消息丢失、补偿失败、并发覆盖 | T+1 或准实时逐笔比对 + 差异分类 | 差错长期沉淀且不可知 | 幂等、可重跑、可追溯 |
| 人工兜底 | 无法自动修复的差异 | 工单系统 + 审批流 + 审计日志 | 差错无法收敛、客诉升级 | 有 SLA、有责任人、可复盘 |
### 11.3 面试问答
**Q1：最终一致性期间数据怎么展示给用户？**
A：用显式状态机而不是"猜"。① 业务表加状态字段（`PENDING/PROCESSING/SUCCESS/FAILED/CANCELED`），中间态展示为"处理中"；② 查询接口默认过滤中间态（列表里不展示未完成订单）；③ 前端对"处理中"做轮询或长连接推送，并给出预期时长；④ 后台定时任务对超时中间态做终结（置失败 + 触发补偿），避免永久卡住。

**Q2：为什么说"幂等是前提而不是优化"？**
A：因为分布式环境下"至少一次投递"是常态：网络超时无法区分"对方没收到"和"对方处理了但响应丢了"，任何重试机制都会造成重复。没有幂等，重试就是风险；有了幂等，重试才成为可靠性手段。

**Q3：对账系统的架构要点？**
A：① **数据来源**：业务流水表或用 binlog 同步出的独立流水库，不与业务主库争资源；② **比对键**：业务单号 + 金额 + 状态，逐笔而非只看总量；③ **差异分类**：单边、金额不符、状态不符、时间差（延迟导致的假差异需设判定窗口）；④ **修复闭环**：自动修复 → 失败转工单 → 结果回写并留审计；⑤ **运行要求**：可重复执行、可按日期区间重跑、有监控告警。

**Q4：三层防线怎么与前面的方案配合？**
A：以 TCC 为例：幂等保证 Confirm/Cancel 可重入；对账校验"冻结总量 = 预期冻结总量"，发现悬挂与空洞；人工兜底处理长期无法确认的分支。以可靠消息为例：消费端幂等防重复，死信队列 + 本地消息表扫描防丢失，对账按"已支付订单是否都有积分"补齐差额。
### 11.4 高频追问与陷阱
- 陷阱：只做幂等不做对账。幂等只保证"重复无害"，无法发现"从未发生"的差错（消息永远没发出、补偿从未被触发），这类缺口只能靠对账暴露。
- 陷阱：把对账做成写业务库的脚本。修复动作必须走业务接口（带幂等键），对账系统只读流水，否则一次误修复就会污染主链路且难以回溯。
- 追问：一致性做到什么程度算合格？答法要带指标：核心链路差异率、对账差异单量、自动修复率、人工工单 SLA，并说明监控告警与复盘机制（见 [CICD与监控告警](../07-工程化与DevOps/03-CICD与监控告警.md)）。
### 11.5 一句话速记
分布式事务的可靠性 = 幂等（防重复）+ 对账（查差错）+ 人工工单（兜住剩余），框架只负责其中的编排部分。
## 自测题（含答案要点）
1. **什么情况下必须用分布式事务？** 跨 RM 且中间态不可接受、无法用补偿抹平：资金类（A 扣 B 加）、强唯一约束类（下单扣库存）、跨库同一业务的分片写。
2. **同一服务用两个数据源算分布式事务吗？** 算，判据是"跨 RM"而非"跨进程"；`@Transactional` 只管辖其绑定事务管理器的那一个数据源，`ChainedTransactionManager` 只解决提交顺序。
3. **能用哪些手段替代分布式事务？** 幂等 + 重试退避 + 最终一致（可靠消息 + 状态机）+ 对账与人工兜底；或把强耦合写收敛到同一个库。
4. **XA 的三角色、六条命令，以及它为什么慢？** AP 应用、TM 事务管理器、RM 资源管理器；命令 XA START / END / PREPARE / COMMIT / ROLLBACK / RECOVER；慢是因为 prepare 到 commit 之间持行锁不释放、XA 连接不能归还连接池、两阶段日志同步开销翻倍，且 PREPARED 事务崩溃后需人工恢复。
5. **MySQL XA 的已知限制举例？** 只支持事务引擎、DDL 会隐式提交破坏原子性、一连接一活跃 XA 事务、XID 长度上限、与 binlog 的交互有版本差异（以官方文档为准）。
6. **柔性事务分三类，分类依据是什么？** 补偿型（TCC/Saga）、异步确保型（可靠消息）、最大努力通知型（对账兜底）；依据是"谁来承担最终一致的兜底责任"。
7. **TCC 三阶段各做什么？** Try 检查并预留（冻结库存/金额）、Confirm 确认扣减、Cancel 释放预留；后两者必须幂等且必须成功。
8. **空回滚与悬挂的成因与解法？** 空回滚是 Cancel 比 Try 先到、误释放不存在的冻结，解法是 Cancel 查控制表无 Try 记录时插入 `CANCELED` 占位记录并空返回；悬挂是 Cancel 先落占位记录后迟到的 Try 又执行了预留，解法是 Try 执行前查控制表、状态为 CANCELED 则拒绝预留（biz_key 唯一索引兜底并发）。
9. **本地消息表怎么保证消息一定发出？性能瓶颈怎么解？** 业务写与消息记录同库同事务 + 定时扫描补发 + 退避重试 + 超限告警；瓶颈靠 `(status,next_retry_time)` 联合索引 + `LIMIT` 批量 + 分表归档解决，更高并发换事务消息。
10. **RocketMQ 事务消息的四个环节？消息不丢的三处保证？** 半消息 → 执行本地事务 → commit/rollback → Broker 回查；不丢靠发送端（校验 SendStatus + 重试 + 本地表）、存储端（同步刷盘 + 同步复制）、消费端（重试 + 死信 + 告警）。
11. **AT 两阶段分别做什么，隔离性什么水平？** 一阶段业务 SQL + undo_log 同本地事务提交；二阶段提交删 undo_log、回滚用 after image 校验 + before image 反向补偿；写隔离有（全局锁防脏写），读隔离默认读未提交，需 `@GlobalLock + for update` 提升。
12. **最终一致性期间怎么展示数据、Confirm/Cancel 一直失败怎么办？** 显式状态机 + 前端"处理中" + 查询过滤中间态 + 超时终结补偿；失败则持久化补偿表无限重试 + 告警 + 人工工单 + 对账平账。
## 背诵卡片
1. 分布式事务的判据是"跨 RM"，不是跨进程、不是跨 JVM。
2. 能收敛到一个库就不用分布式事务；能最终一致就不用强一致。
3. 替代四件套：幂等、重试退避、最终一致、对账兜底。
4. 中间态可接受、失败可重试、不一致可修复——三条任一成立就不需要强一致。
5. DTP 三角色：AP 应用、TM 事务管理器、RM 资源管理器。
6. XA 命令链：START → END → PREPARE → COMMIT / ROLLBACK，恢复用 RECOVER。
7. XA 从 prepare 持锁到二阶段结束，连接不能还池，所以吞吐差。
8. XA 不适配高频短事务，但低频跨库强一致仍是标准答案。
9. XA 事务里禁止 DDL——隐式提交会直接破坏原子性。
10. 2PC 窗口风险：全部 prepare 后 TM 崩溃 → 部分提交，需日志与恢复流程。
11. 柔性事务三分类：补偿型、异步确保型、最大努力通知型。
12. 柔性事务放弃隔离性，换取可用性与吞吐。
13. TCC = Try 预留 + Confirm 扣减 + Cancel 释放，后两者必须幂等且必须成功。
14. TCC 的锁在业务预留字段上，不占数据库长事务，并发优于 XA。
15. 空回滚 = Cancel 先到；解法是 Cancel 无 Try 记录时落占位记录空返回。
16. 悬挂 = Cancel 先到、迟到 Try 后到；解法是 Try 执行前查控制表状态。
17. 一张事务控制表 + 唯一索引，可同时解决空回滚、悬挂与重复调用。
18. TCC 的代价：三接口侵入、冻结字段、控制表、补偿任务、监控告警。
19. 可靠消息 = 本地事务写业务与消息 + 至少一次投递 + 消费幂等。
20. 本地消息表靠定时扫描补发，事务消息靠半消息与 Broker 回查。
21. 消息不丢三处：发送端、存储端、消费端，缺一不可；幂等键必须来自业务语义。
22. 顺序消息的并发上限等于队列数，局部有序通常就够。
23. 最大努力通知 = 有限次退避重试 + 对账兜底，正确性来自对账。
24. 对账必须逐笔比对，总量一致会掩盖单边差异。
25. Saga 无隔离性，靠状态机与语义锁缓解中间态可见。
26. Saga 补偿不可逆时改为语义补偿（冲正/退款），并把不可逆步骤放到最后。
27. Seata 三角色：TC 协调、TM 开启（@GlobalTransactional）、RM 执行。
28. AT 一阶段"业务 SQL + undo_log"同本地事务提交；二阶段提交删日志，回滚用 after image 校验 + before image 反向补偿。
29. AT 写隔离靠全局锁，读隔离默认没有，需 @GlobalLock + 加锁查询；TC 是新增单点必须集群。
30. 三层防线：幂等防重复、对账查差错、人工工单兜剩余；选型四问：能否不跨库 → 能否最终一致 → 能否异步 → 流程是否够长。
