## 1. 简历结构与排版原则

### 核心要点

**一页还是两页？**

| 工作年限 | 建议页数 | 说明 |
|---|---|---|
| 校招 / 0~1 年 | 严格 1 页 | 项目少，1 页足够；两页显得注水 |
| 1~3 年 | 1 页，最多 1.5 页 | 只留 1 个主项目 + 1 个次项目 |
| 3~5 年 | 2 页 | 项目深、亮点多；第 1 页必须是黄金信息 |
| 5 年以上 | 2 页，绝不超过 3 页 | 强调架构、Owner、带人与结果 |

**模块顺序（社招黄金顺序）**：个人信息 → 求职意向 → 专业技能 → 工作经历（含项目）→ 项目经历 → 教育背景 → 加分项（开源 / 博客 / 专利 / 证书）。

**四条排版铁律**

1. **时间倒序**：工作经历、项目经历、教育背景全部倒序，最近的在最上面，面试官只认真看前 1/3。
2. **量化优先**：凡是能加数字的句子，一律加数字——QPS、数据量、RT、可用性、成本、人数、周期、百分比。
3. **STAR 压缩成短句**：每个项目 4~8 行，每行一个独立信息点，不写"负责了相关工作"这种无信息量句子。
4. **技术名词统一大小写与官方写法**：`Spring Boot` 不是 `springboot`，`MySQL` 不是 `Mysql`，`Redis` 不是 `redis`（技术栈列表中除外，可保留原样）。

**排版细节清单**

| 项目 | 要求 |
|---|---|
| 字体 | 中文宋体/微软雅黑，英文 Times New Roman/Calibri，正文 10.5~11pt |
| 颜色 | 黑白为主，最多一处主色；禁止彩色图标堆砌 |
| 文件格式 | 一律导出 PDF（防止 Word 排版错乱），命名 `姓名-Java后端-年限-手机号.pdf` |
| 联系方式 | 手机 + 邮箱 + GitHub（有内容才放）+ 城市，禁止放生日、身份证、婚育 |
| 空行与留白 | 模块之间留 1 行，行距 1.15~1.3，页边距 2cm |
| 关键词 | 投递的 JD 里出现的技术词，必须在简历里出现同名词（HR/ATS 靠关键词初筛） |

### 常见问题与标准答法

**Q1：简历要不要写"求职意向"？**

A：要。一行写清：`求职意向：Java 后端开发工程师（社招 / 可立即到岗 / 期望城市：杭州）`。作用有三个：让 HR 一眼判断岗位匹配度、避免被投到不相关岗位、表明到岗时间（HR 最关心的一件事）。

**Q2：教育背景不好（非科班 / 大专 / 二本）怎么处理？**

A：把教育背景往下放，放在工作经历之后；技术栈与项目放最前。**不要隐瞒学历**（背调必查），但可以不在第一屏。非科班可在"专业技能"或"加分项"补一句：`自学路线：CSAPP + 深入理解 JVM + 自研 RPC 框架（GitHub 300 star）`，用行动对冲学历。

**Q3：项目经历和工作经历怎么分工？**

A：工作经历写"公司 + 时间 + 岗位 + 团队规模 + 一句话业务 + 主要战绩"（3~4 行）；项目经历只写 2~3 个重点项目，展开技术细节。**不要把公司所有项目都列一遍**——面试官只会挑 1~2 个深挖，列太多等于自己挖坑。

### 陷阱与禁忌

- 不写"精通"（除非你是该技术的作者/committer），不写"熟悉 Office""熟练使用 IDE"这类无效技能。
- 不写虚假职级/虚假团队规模，背调与交叉面一问就穿。
- 不写与岗位无关的经历（学生会、兼职、驾校）。
- 不留空白时间段（超过 3 个月的空档，主动在简历上标注原因：`2023.03-2023.06 个人技术进修 / 家庭原因`）。

### 一句话速记

> 两页之内、倒序排列、每个项目必有数字、每个技术词都与 JD 对齐。

## 2. 技术栈分级写法

### 核心要点

**四级描述词的标准语义**

| 描述词 | 含义 | 面试官期待 |
|---|---|---|
| 精通 | 读过源码、能定位框架级 Bug、能二次开发 | 敢问源码级问题（Spring 循环依赖、AQS 队列、Netty 事件循环） |
| 熟练掌握 | 用过 2 年以上、能独立排查线上问题、懂核心原理 | 会问原理 + 场景（为什么用、踩过什么坑） |
| 熟悉 | 用过 1 年左右、能独立完成日常开发 | 只问基本用法与常见陷阱 |
| 了解 | 看过文档 / 做过 demo，没有生产经验 | 基本不问，问了答"了解层面"即可 |

**正确写法（按熟练度分层，每层一行）**

```
熟练掌握：Java（集合/并发/JVM 调优）、MySQL（索引优化/事务/分库分表）、Redis（缓存治理/分布式锁）、
          Spring / Spring Boot / MyBatis、RocketMQ、Linux 常用命令与排查
熟悉：    Elasticsearch、Spring Cloud（Nacos/Sentinel/Gateway）、Docker / K8s 基础运维、
          Kafka、ShardingSphere、分布式事务（Seata）
了解：    Flink 实时计算、Hadoop/Hive 离线数仓、Go 语言基础
```

### 常见问题与标准答法

**Q1：技术栈清单要不要写版本号？**

A：写主版本即可，如 `Spring Boot 2.7 / 3.x`、`JDK 8 / 17`。写版本号能证明你真在用（面试官会顺着问 JDK 17 有什么变化，你要能答：[Java 新特性与语言演进](../01-Java基础/05-Java新特性与语言演进.md)）。

**Q2：某个技术我只是"用过"，写"熟悉"会被问死吗？**

A：会，但可控。判断标准：**能不能说出"我为什么选它、它帮我解决了什么、我在它上面踩过什么坑"**。三问都能答，就写"熟悉"；只能答第一问，写"了解"。诚实分级比吹牛的好处是：面试官问的深度会匹配你的声明，你不会被拖进不擅长的水域。

### 陷阱与禁忌

| ❌ 常见错误 | ✅ 正确写法 |
|---|---|
| `精通 Java、MySQL、Redis、Spring、Kafka、ES、K8s……`（一行全是精通） | 按 熟练/熟悉/了解 分三行，每行 4~6 项 |
| `熟悉 Java 基础知识` | `熟练掌握 Java 并发编程（AQS/CAS/线程池调优）与 JVM 内存模型` |
| `了解过 Redis` | `熟悉 Redis（缓存穿透/击穿/雪崩治理、Redlock 与 Redisson 分布式锁）` |
| `会用 Git` | `熟练掌握 Git 分支模型（Git Flow / trunk-based）与 Code Review 流程` |
| 技术栈写成一大坨不定长的段落 | 每项后面用括号补一个能力锚点（做了什么 / 解决什么问题） |

### 一句话速记

> 技术栈不是名词罗列，是"我在这项技术上能做到什么"的承诺书；写什么级别，就要接住什么级别的追问。

## 3. 项目描述模板与优秀示例

### 核心要点

**万能五段式模板**

```
【项目名】xxx 平台（时间 2022.06 - 2023.08　角色：核心开发 / 技术负责人　团队：6 人）
【背景】一句话：谁在用、规模多大、为什么做（1 行）
【职责】我负责哪 2~3 个模块 / 我推动了什么（1~2 行，避免"参与""协助"这类弱动词）
【方案】技术选型 + 关键设计（2~3 行，必须有具体组件与数据结构）
【难点】1~2 个真实难点 + 你怎么解决的（2~3 行，这是面试官最想看的）
【结果】量化收益（1 行：RT / QPS / 可用性 / 成本 / 人力）
```

**动词升级表（弱动词 → 强动词）**

| 弱动词 | 强动词 |
|---|---|
| 参与、协助、配合 | 主导、设计、落地、重构、推动 |
| 负责开发 | 独立完成 XX 模块的设计与实现 |
| 优化了性能 | 通过 XX 手段把 P99 RT 从 800ms 降到 90ms |
| 使用 Redis 做缓存 | 设计两级缓存 + 逻辑过期，扛住 3w QPS 大促流量 |

### 常见问题与标准答法

**Q1：示例一——电商订单中心（交易链路方向）**

A：

> **电商订单中心（2022.06-2024.03　核心开发　团队 8 人）**
> **背景**：面向 B 端商城的订单系统，日均订单 60w、大促峰值下单 QPS 4500，承接下单、支付回调、履约、售后全链路。
> **职责**：负责订单创建与状态机、支付回调幂等、超时关单三大核心模块，主导订单表分库分表改造。
> **方案**：订单号采用雪花算法 + 分库分表基因位（16 库 × 64 表）；订单状态用状态机 + 事件表驱动，状态变更通过本地消息表 + RocketMQ 异步通知履约；超时关单用 RocketMQ 延时消息（30 分钟）+ Redis ZSet 兜底补偿。
> **难点**：① 支付回调重复推送导致重复入账——落地"唯一索引 + 状态机前置校验 + Redis SETNX 三级幂等"，重复请求拦截率 100%；② 分库分表后历史订单查询跨 1024 张表——用 ShardingSphere 分片 + 异构 ES 宽表双写，C 端查询 RT 从 1.2s 降到 120ms。
> **结果**：下单链路 P99 从 620ms 降至 110ms；大促零故障，订单与支付流水对账差异率 0；改造后单库压力下降 92%。

**Q2：示例二——高并发营销（秒杀/发券）**

A：

> **营销促销中台（2023.02-2024.06　技术负责人　团队 6 人）**
> **背景**：支撑商城秒杀、限时折扣、优惠券发放三类活动，最高单活动瞬时流量 12w QPS，日均发券 300w 张。
> **职责**：负责活动模型设计、库存扣减方案、风控与降级，统筹压测与容量评估。
> **方案**：静态资源全部 CDN + 页面静态化；网关层 Nginx + Sentinel 做 QPS 限流与热点参数限流；库存预热到 Redis，用 Lua 脚本保证"校验 + 扣减 + 记录"原子性；下单请求入 RocketMQ 削峰，异步落库，前端轮询结果；超卖兜底用"Redis 扣减 + DB 乐观锁 update stock = stock - 1 where stock >= 1"双保险。
> **难点**：① 热点 key（单个爆款 SKU）打爆单分片——把库存 key 按分片拆成 20 份（`stock:skuId:{0..19}`），请求随机路由，单 key QPS 从 12w 降到 6000；② 大流量下 Redis 抖动导致扣减超时——加本地缓存 + Sentinel 熔断，降级为"排队领号、事后通知"，保住主站不被拖垮。
> **结果**：秒杀峰值支撑 12w QPS，超卖 0 单；营销期间主站可用性 99.99%；压测结论沉淀为容量评估模板，后续活动零扩容。

**Q3：示例三——数据同步平台（中间件/平台方向）**

A：

> **数据同步平台（2021.09-2022.08　核心开发　团队 4 人）**
> **背景**：公司 30+ 业务库需要把 MySQL 增量数据同步到 ES / Hive / 下游服务，原有定时全量同步延迟 30 分钟且经常拖垮源库。
> **职责**：负责基于 Binlog 的增量同步引擎、任务调度与数据一致性校验模块。
> **方案**：Canal 订阅 MySQL Binlog → 内部 Disruptor 队列缓冲 → 按主键哈希多线程并行投递到多目标端；任务状态存 ZooKeeper 避免重复消费；同步任务用 XXL-JOB 调度，支持断点续传；一致性校验用"抽样分片 + 逐行 CRC 比对"。
> **难点**：① 顺序性与吞吐的矛盾——同一主键必须串行、不同主键可并行，用"主键哈希到固定线程"解决，吞吐从 3k TPS 提升到 6w TPS；② DDL 变更导致解析失败——建立 Binlog 兼容层 + 变更告警，失败任务自动重试并降级到全量比对。
> **结果**：同步延迟从 30 分钟降到 3 秒内（P99），源库负载下降 40%，替代 5 条人工导数流程，每年节省约 60 人日。

### 陷阱与禁忌

- 项目背景写三段话（业务介绍比技术细节还长）——面试官不关心你公司做什么生意，只关心你的技术。
- 结果写"提升了系统性能""获得领导好评"——没有数字的结果等于没有结果。
- 项目时间与公司任职时间冲突（前后矛盾是造假信号）。
- 把团队成果全写成个人成果（面试官必问"你在里面的具体贡献是什么"，含糊就崩）。

### 一句话速记

> 项目 = 一句话背景 + 我做了 2~3 件事 + 具体技术方案 + 一个真难点 + 一串数字。

## 4. CRUD 项目如何包装出技术深度

### 核心要点

**核心认知**：面试官不排斥 CRUD，排斥的是"只会照着需求写增删改查、从不思考"。**深度 ≠ 高大上组件，深度 = 你在约束下做了取舍并拿到结果。** 三条包装路径：

1. **往"量"上做**：数据量、QPS、并发数、接口数、调用方数量——量变必然带来方案变化。
2. **往"稳"上做**：一致性、幂等、可观测、故障自愈、对账——稳定性是最容易讲出细节的方向。
3. **往"省"上做**：RT 优化、成本优化、人力提效（工具化/平台化/自动化）——成本节省是硬指标。

### 常见问题与标准答法

**Q1：改写对比一（普通管理后台接口）**

A：

| | ❌ 改写前 | ✅ 改写后 |
|---|---|---|
| 描述 | 负责商品管理模块的开发，实现商品的增删改查、上下架功能 | 负责商品域接口的设计与实现：列表接口日均 800w 次调用，原实现全表 like 模糊匹配 + N+1 查询，P99 1.4s；改为 ES 检索 + 批量查询合并 + 二级缓存（Caffeine + Redis），并做接口字段按需返回裁剪，P99 降至 90ms，DB 负载下降 70% |
| 面试官反应 | 无问题可问，直接跳过 | 追问链路：为什么用缓存不用索引？缓存一致性怎么保证？ES 与 DB 如何同步？ |

**Q2：改写对比二（定时任务/批处理）**

A：

| | ❌ 改写前 | ✅ 改写后 |
|---|---|---|
| 描述 | 使用 XXL-JOB 编写定时任务，每天凌晨同步数据 | 设计日终对账任务：原单机分页扫描 400w 流水耗时 3.5h 且失败需重跑全量；改造为按业务日期分片 + 分布式并行执行（20 个执行器分片），失败分片独立重试 + 幂等落库（对账结果表唯一索引），耗时降到 12 分钟；任务增加运行时长/差异条数告警，连续 6 个月零人工介入 |
| 面试官反应 | "就是写了个 job" | 分片怎么分？执行器挂了怎么办？如何保证任务不重复执行？ |

**Q3：改写对比三（后台管理系统的"简单"重构）**

A：

| | ❌ 改写前 | ✅ 改写后 |
|---|---|---|
| 描述 | 参与系统重构，优化代码结构 | 主导订单模块分层重构：原有 Service 层单类 3000+ 行、审批流硬编码 if-else 12 个分支，需求变更平均 3 人日；引入"状态机（Spring StateMachine）+ 策略工厂 + 领域事件"，新增审批节点从改代码变为配置化，单需求交付时间从 3 人日降到 0.5 人日；重构期间用双跑对照 + 影子流量验证，线上零回归 |
| 面试官反应 | 空泛 | 怎么保证重构不出问题？状态机选型理由？老代码怎么下线？ |

**Q4：没有任何亮点的"纯 CRUD"怎么起步？**

A：选一个接口做**深挖三件事**：① 把它的耗时拆开（DB / RPC / 序列化 / GC），找到占比最大的一项；② 针对这一项做一次可验证的优化（加索引、批量合并、改异步、加缓存）；③ 补上监控与告警，证明优化是长期生效的。做完这三步，你就有了一个可以讲 10 分钟的真实案例——**深度是从一个具体接口里挖出来的，不是凭空包装出来的。**

### 陷阱与禁忌

- 编造不存在的系统（尤其大厂面试官对同类系统的真实量级很清楚，编数字必崩）。
- 把别人的架构写成自己做的（追问"为什么这么设计"就答不上来）。
- 包装过度到无法自证：任何写进简历的技术点，都要能答出"为什么用、怎么用、出过什么问题"。

### 一句话速记

> 量的差异 → 方案的差异 → 权衡的差异，这才是深度；把"我做了什么"换成"我在什么约束下做了什么取舍、拿到了什么结果"。

## 5. 技术亮点清单（问题 → 方案 → 结果）

### 核心要点

下面 10 个亮点是面试官最认的"硬通货"。**每个亮点准备一个真实故事，并预判 3 个追问**。表达统一句式：

> **问题**（什么现象/什么痛点，带数字）→ **方案**（选了什么、为什么不用替代方案、关键实现细节）→ **结果**（量化收益 + 顺带收获）。

### 常见问题与标准答法

**Q1：缓存类亮点怎么说？**

A：`问题：首页商品接口 QPS 1.2w，DB CPU 长期 80%+，大促必宕。方案：设计 Caffeine（本地 30s）+ Redis（10min）两级缓存，热点 key 逻辑过期避免击穿，缓存空值 + 布隆过滤器防穿透，失效时间加 ±10% 随机抖动防雪崩；缓存更新采用"先更新 DB 再删除缓存 + 延时双删 + Binlog 订阅补偿"。结果：DB QPS 从 1.2w 降到 900，接口 P99 从 420ms 降到 60ms。` 追问预判：为什么不先删缓存？延时双删延多久？[Redis 高可用与缓存治理](../02-数据库/05-Redis高可用与缓存治理.md)

**Q2：分库分表怎么说？**

A：`问题：订单表 6 亿行，单表查询慢、DDL 无法执行、单库磁盘 90%。方案：按 user_id 哈希分 16 库 × 64 表，分片键选择 user_id（保证 C 端查询单分片），历史数据按时间归档到冷库；跨分片查询走 ES 宽表 + 分页归并，非分片键查询用基因法/异步双写到异构表。结果：单表数据量降到 600w，写入 QPS 从 2k 提升到 3.5w，DDL 从 8 小时缩短到分钟级。` 追问预判：为什么不用 range 分片？扩容怎么平滑迁移？分布式事务怎么办？[MySQL 调优主从与分库分表](../02-数据库/03-MySQL调优主从与分库分表.md)

**Q3：异步解耦怎么说？**

A：`问题：下单成功要同步调用 5 个下游（积分、券、履约、推送、风控），任一下游抖动都导致下单 RT 上升到 2s+，接口成功率跌到 96%。方案：核心链路只写本地订单 + 发送 RocketMQ 事务消息，下游异步消费；消费端按业务分组、独立线程池隔离，失败进重试队列（16 次退避重试）+ 死信队列人工兜底；用本地消息表保证"订单落库与消息发送"一致。结果：下单 P99 从 2.1s 降到 130ms，成功率 99.99%，下游故障不再影响主链路。` 追问预判：消息丢失怎么办？重复消费怎么保证？顺序性怎么保证？[消息队列与 RocketMQ](../04-中间件/01-消息队列与RocketMQ.md)

**Q4：幂等怎么说？**

A：`问题：支付回调重复推送、用户双击提交、MQ 重试导致重复创建订单（日均 200+ 笔重复单，客诉集中）。方案：分层幂等——① 入口用唯一业务号（请求 ID）做 Redis SETNX + 短 TTL 拦重复；② 落库用业务唯一索引兜底（order_no、out_trade_no）；③ 状态机做前置校验（只允许 待支付→已支付 单向流转）；④ MQ 消费端用去重表 + 消费位点幂等。结果：重复单降为 0，回调成功率 100%。` 追问预判：Redis 挂了怎么办（唯一索引兜底）？[分布式锁与分布式 ID](../05-分布式与架构/03-分布式锁与分布式ID.md)

**Q5：限流降级怎么说？**

A：`问题：上游流量不规律，大促瞬时流量是日常 20 倍，一次突发把订单服务打挂并引发雪崩。方案：网关层（Nginx limit_req + Sentinel 集群流控）做入口 QPS 限流；服务层对非核心接口做线程数隔离 + 熔断（慢调用比例 > 50% 熔断 10s）；设计三档降级预案（关闭推荐位 / 只读模式 / 排队领号），预案配置在 Nacos 支持秒级开关。结果：大促期间核心下单成功率 99.99%，非核心功能有序降级，零人工介入。` 追问预判：限流算法怎么选？熔断和降级区别？[Nginx 与网关限流](../04-中间件/05-Nginx与网关限流.md)

**Q6：灰度发布怎么说？**

A：`问题：发版事故多，一次全量上线导致 30 分钟不可用。方案：建立三级灰度——单机灰度（1 台观察 10 分钟）→ 小流量灰度（按 userId 尾号取模 5%）→ 全量；灰度期间对比新老版本的核心指标（错误率、RT、业务成功率），异常自动回滚（发布系统对接监控阈值）；数据库变更遵循"先兼容双写、再切读、最后清理"的三步走。结果：上线事故率从每月 2 次降到 0，回滚时间从 20 分钟降到 90 秒。` 追问预判：灰度怎么做流量染色？不可回滚的 DDL 怎么处理？

**Q7：性能优化怎么说？**

A：`问题：订单详情接口 P99 1.2s，用户投诉。方案：先用 Arthas trace 定位——DB 查询占 700ms（缺索引 + 3 次回表）、RPC 串行调用 3 次占 350ms。改造：① 加覆盖索引消除回表，慢 SQL 从 700ms 降到 30ms；② 3 次 RPC 改并行（CompletableFuture + 自定义线程池，超时 200ms 快速失败）；③ 大字段懒加载、返回字段裁剪。结果：P99 1.2s → 110ms，DB CPU 从 75% 降到 25%。` 追问预判：并行化的线程池怎么配？超时了怎么兜底？[JVM 与 GC 调优](../01-Java基础/04-JVM与GC调优.md)

**Q8：稳定性治理怎么说？**

A：`问题：故障多是"发现晚、定位慢、恢复靠人"，平均 MTTR 45 分钟。方案：建立可观测三件套（Metrics：Micrometer + Prometheus + Grafana；Tracing：SkyWalking 全链路 traceId 贯通；Logging：ELK + 结构化日志 + traceId 检索）；定义四个黄金指标（流量/错误/延迟/饱和度）并配 SLO 告警，告警分级（P0 电话、P1 群消息）；沉淀 12 篇故障预案 Runbook 并做季度演练。结果：MTTR 从 45 分钟降到 8 分钟，告警准确率从 40% 提到 92%，重复故障下降 80%。` 追问预判：告警风暴怎么治理？[CICD 与监控告警](../07-工程化与DevOps/03-CICD与监控告警.md)

**Q9：DDD 重构怎么说？**

A：`问题：单体系统 40w 行代码，一个需求改 5 个模块，回归测试 3 天；订单、库存、营销逻辑缠绕在同一个 Service 里。方案：先按业务能力划限界上下文（订单域/库存域/营销域/用户域），用"绞杀者模式"逐步剥离——新需求只在新模块开发，老逻辑通过防腐层（ACL）适配；领域内落地聚合根 + 领域事件，跨域用事件驱动最终一致（本地事件表 + MQ）。结果：新需求平均交付周期从 6 人日降到 2 人日，模块间循环依赖从 37 处降到 0，回归测试从 3 天降到 4 小时。` 追问预判：聚合根怎么划分？为什么不直接微服务化？

**Q10：技术方案推动怎么说？**

A：`问题：团队 5 个系统各自实现限流，规则不一致、故障时互相影响，且没人愿意改（担心影响自己的稳定性）。方案：① 用数据说话——统计三个月内因限流缺失导致的 4 次故障，量化损失；② 先做 POC 在一个非核心系统验证（2 周，指标提升 30%）；③ 输方案文档 + 评审会，明确迁移计划与回滚方案；④ 分三批迁移，每批由原 Owner 自己改、我提供工具与支持。结果：方案在 5 个系统落地，故障数下降，方案被推广到另外 2 个业务线，我也因此成为该中间件的 Owner。` 追问预判：遇到反对怎么处理？

### 陷阱与禁忌

- 亮点堆砌但互相矛盾（既说"全异步化"又说"强一致"）。
- 只讲组件不讲约束（不提数据量、QPS、团队规模的方案都是空谈）。
- 把开源项目文档里的方案原样搬来当自己的（追问实现细节立刻暴露）。

### 一句话速记

> 问题带数字、方案带取舍、结果带对比，每个亮点预判 3 个追问。

## 6. STAR 与 STAR-L 法则

### 核心要点

| 字母 | 含义 | 时间占比 | 说错的表现 |
|---|---|---|---|
| S (Situation) | 背景：什么业务、什么规模、什么痛点 | 15% | 讲太长，把公司业务讲了一遍 |
| T (Task) | 任务：我负责什么、目标是什么 | 10% | 用"我们"，看不出个人贡献 |
| A (Action) | 行动：我做了什么（技术细节、取舍、踩坑） | **55%** | 一句带过，全部时间给了背景 |
| R (Result) | 结果：量化收益 + 复盘收获 | 20% | 无数字、无沉淀 |

**STAR-L 多出来的 L = Learning（反思/沉淀）**：面试官（尤其三面/总监面）最看重这一项，它证明你"能把一次经历变成可复用的方法论"。

### 常见问题与标准答法

**Q1：完整 STAR-L 示例（讲一次线上故障处理）**

A：

> **S**：大促首日 20:10，订单服务错误率从 0.1% 突增到 12%，用户反馈下单失败，当时我已值班 on-call，影响面是核心交易链路（每分钟约 3000 单）。
> **T**：我作为当班负责人，目标是在 15 分钟内恢复服务，并保证不产生数据错乱。
> **A**：（1）先看大盘：错误集中在订单创建接口，DB 侧错误为"too many connections"，判断是连接池耗尽；（2）`SHOW PROCESSLIST` 发现 137 个 `Waiting for table metadata lock` 的会话，追溯到 3 分钟前有一位同事在订单表执行了加索引的 DDL；（3）我先 `kill` 掉 DDL 语句恢复可用性（2 分钟内错误率回落到 1%），再把连接池 `maxActive` 临时从 50 提到 80 撑住堆积；（4）事后改用 gh-ost 在线 DDL，并把 DDL 纳入发布流程的审批与低峰窗口；（5）补充"metadata lock 等待数"监控指标与告警。
> **R**：故障从发现到恢复 8 分钟，数据零错乱；同类故障后 8 个月零复发；MTTR 从 45 分钟降到 8 分钟。
> **L**：我总结出一条原则——**DDL 是生产环境最高危操作之一，必须有工具（gh-ost/pt-osc）+ 流程（低峰 + 审批）+ 监控（MDL 等待）三重保障**；并且我把这套做法写进团队规范，成为后续所有表结构变更的默认流程。学到的方法比这次故障本身更值钱。

**Q2：STAR 讲得多久合适？**

A：主项目 2~3 分钟，单个亮点故事 60~90 秒，单次故障 90~120 秒。**先给结论**（"这是连接池被 MDL 阻塞导致的连锁故障，8 分钟恢复"），再展开过程——面试官时间有限，结论先行能让他决定要不要追问细节。

### 陷阱与禁忌

- 全程用"我们"（面试官会认为你在蹭团队成果）——每个 Action 开头换成"我……"。
- Action 只说流程不说技术（"我拉了个群协调各方"没有任何技术含量）。
- 结果只讲业务收益，不讲技术沉淀（L 缺失是二三面失分主因）。

### 一句话速记

> S15% / T10% / A55% / R20% + 一句 Learning；结论先行，Action 用"我"开头。

## 7. 面试官在项目环节的考察点

### 核心要点

| 考察维度 | 面试官在想什么 | 危险信号 | 加分信号 |
|---|---|---|---|
| 真实性 | 这项目他真的做过吗？ | 细节含糊、数字记不清、术语用混 | 随口报出表结构、字段名、配置值 |
| 技术深度 | 他理解到自己方案的哪一层？ | 只会背组件特性 | 能讲清底层机制与失败场景 |
| Owner 意识 | 出问题是等别人解决，还是主动扛？ | "那是运维的事""后来别人改的" | "我发现后主动推动，做了XX" |
| 权衡能力 | 他知道方案的代价吗？ | "这个方案是最好的" | "代价是XX，在当时的规模下可接受" |
| 结果导向 | 他的工作产生了什么影响？ | 无指标、无对比 | 有前后对比、有长期跟踪、有推广 |
| 方法论 | 换个场景他还能做吗？ | 只会一个方案 | 能抽象出可迁移的排查/设计套路 |

### 常见问题与标准答法

**Q1：怎么体现"权衡"？**

A：每个技术选择都补一句代价与前提，句式：
> "我们选了 A 而不是 B，因为当时的约束是【数据量/QPS/团队规模/工期】。A 的代价是【复杂度/一致性延迟/运维成本】，我们通过【补偿手段】把代价控制住。如果规模涨到【X 倍】，我会重新评估改成 B。"

**Q2：怎么体现 Owner 意识？**

A：讲你在职责边界之外做的事。三句模板：
> "这个问题严格说不是我的模块，但它卡住了整个链路，所以我先做了【临时止血】，再推动【长期方案】，并把它写进了团队【规范/文档】。"

### 陷阱与禁忌

- 把"我参与"讲成"我主导"，一追问谁写的代码就崩。
- 一味说方案好，从不提缺点（面试官会主动挖：那这个方案的缺点是什么？）。
- 抱怨前公司/前同事（三面大忌）。

### 一句话速记

> 六维打分：真实、深度、Owner、权衡、结果、方法论；每个项目按这六维自查一遍再上考场。

## 8. 项目连环追问 45 问与准备方法

### 核心要点

**追问的三种走向**：① 往深处问（原理、源码）；② 往旁边问（替代方案、同类系统）；③ 往极端问（流量 ×10、机器挂一半、数据涨到百亿）。**准备方式就是提前把这三条路各走一遍。**

### 常见问题与标准答法

**Q1：项目连环追问清单（45 问，按主题分组）**

A：

| # | 追问 | 准备提示 |
|---|---|---|
| 1 | 这个需求/系统解决什么问题？ | 一句话业务价值 + 谁在用 |
| 2 | 为什么由你来做？你在团队中的角色？ | 说清职责边界 |
| 3 | 你个人具体写了哪些代码/模块？ | 报 2~3 个模块名 |
| 4 | 你的贡献占比大概多少？ | 如实说，如"我负责 60%，另两人配合" |
| 5 | 为什么这么设计？ | 约束 → 选择 → 代价 |
| 6 | 有没有考虑过别的方案？ | 至少准备 2 个被否方案及原因 |
| 7 | 为什么不用 XX 技术？ | 对比 2~3 个维度 |
| 8 | 当时的技术选型是谁定的？ | 诚实：技术负责人定，我参与评估/我主导 |
| 9 | 数据量多大？表多少行？几个库几张表？ | 记死具体数字 |
| 10 | QPS / TPS 多少？峰值多少？ | 日常 + 峰值两个数 |
| 11 | 单机配置？多少台机器？ | 4C8G / 8 台 之类 |
| 12 | RT 多少？P99 还是平均？ | 报 P99 更专业 |
| 13 | 整体可用性是多少？ | 99.9% / 99.99% |
| 14 | 上下游有哪些系统？如何交互？ | 画得出架构图 |
| 15 | 接口协议是什么？ | HTTP/JSON、Dubbo、gRPC |
| 16 | 关键表结构是什么？有哪些索引？ | 至少背 1 张核心表 |
| 17 | 缓存怎么设计的？key 怎么定？过期多久？ | 说出 key 命名与 TTL |
| 18 | 缓存和 DB 一致性怎么保证？ | 延迟双删 / Binlog 订阅 |
| 19 | 消息队列用哪个？为什么？ | 选型对比 + 幂等 + 顺序 |
| 20 | 消息丢失/重复/积压怎么处理？ | 三套预案 |
| 21 | 分布式事务怎么解决？ | 最终一致 + 补偿 |
| 22 | 幂等怎么做的？ | 唯一索引 + 状态机 + 去重表 |
| 23 | 怎么限流？阈值怎么定？ | 压测得出，非拍脑袋 |
| 24 | 怎么熔断降级？降级了用户看到什么？ | 有具体降级预案 |
| 25 | 遇到过什么线上问题？ | 至少准备 2 个故障案例 |
| 26 | 怎么排查的？用了什么工具/命令？ | 报命令与指标 |
| 27 | 定位根因花了多久？怎么恢复的？ | 时间线讲清楚 |
| 28 | 这个故障杜绝了吗？怎么防复发？ | 工具 + 流程 + 监控 |
| 29 | 数据库慢查询怎么优化的？ | 索引/改写/分页深翻页 |
| 30 | 连接池怎么配的？为什么是这个值？ | 结合 QPS 与 RT 估算 |
| 31 | 线程池参数怎么定的？拒绝策略？ | 有估算过程 |
| 32 | JVM 参数怎么配的？GC 怎么调优？ | 结合 GC 日志 |
| 33 | 有做过全链路压测吗？怎么做的？ | 流量模型 + 数据隔离 |
| 34 | 性能瓶颈在哪？怎么定位的？ | 分层定位法 |
| 35 | 上线流程是怎样的？怎么发布？ | 灰度 + 回滚 |
| 36 | 灰度怎么做流量染色的？ | 用户/机器/IP 维度 |
| 37 | 监控告警怎么配的？ | 四个黄金指标 |
| 38 | 如果流量翻十倍怎么办？ | 先说瓶颈在哪，再给方案 |
| 39 | 如果机器挂一半怎么办？ | 容量 + 降级 + 兜底 |
| 40 | 如果数据涨到百亿怎么办？ | 归档 + 分片 + 冷热分离 |
| 41 | 这个方案有什么缺点？ | 主动说代价 |
| 42 | 现在回头看，哪里做得不好？ | 有反思 ≠ 自我否定 |
| 43 | 如果重做一次你会怎么改？ | 具体到方案 |
| 44 | 项目最大的收获是什么？ | 方法论 + 能力成长 |
| 45 | 这段经历对现在的工作有什么影响？ | 迁移到当下岗位 |

**Q2：准备方法（面试前 3 天怎么做）**

A：

1. **画架构图**：给主项目手画一张"上下游 + 组件 + 数据流"图，标注瓶颈点与关键路径。面试时能在白板/纸笔上 30 秒画出来，可信度立刻上升。
2. **背数据卡**：把 10 个关键数字写在一张卡片上（数据量、QPS、RT、机器数、表数、可用性、成本、人力、周期、故障恢复时长）。
3. **准备 2 个故障案例**：一个"性能类"（慢 SQL/GC/内存泄漏），一个"稳定性类"（雪崩/连接池/MQ 积压），每个都准备完整时间线。
4. **演练极端问题**：对第 38~41 问自问自答一遍并写下要点。
5. **预估雷区**：凡是简历上写了但自己不熟的点（别人做的模块），要么删掉，要么补齐到能答"了解"。

### 陷阱与禁忌

- 数字前后不一致（第 9 问说 6 亿行，第 40 问说 6 千万）。
- 一问"为什么不换个方案"就说"当时没想过"（等于承认不思考）。
- 故障案例说成"没遇到过线上问题"（面试官直接判定没 Owner 经历）。

### 一句话速记

> 45 问里，40 问都能靠"提前准备的数据卡 + 架构图 + 2 个故障案例"接住。

## 9. 高频项目问题标准答法

### 核心要点

五个必考问题的答题骨架：**结论先行 → 分点展开 → 主动补代价 → 落到结果**。每个答法控制在 90 秒内。

### 常见问题与标准答法

**Q1："你在项目里具体负责什么？"**

A：
> "我在 XX 项目里负责三块：一是【核心模块 A】，独立完成设计与编码；二是【难点 B】，这是我主动承接的，解决了【具体问题】；三是【推动 C】，比如推动团队把 XX 流程规范化。三块的代码量占比大约 6:3:1，另两位同事分别负责【D】和【E】。如果您想深入，我可以先从 A 展开，也可以直接讲 B 那个难点。"

要点：**分模块 + 说占比 + 指路（让面试官自己选深挖方向，你提前准备好两个方向）**。

**Q2："你遇到过最有挑战的技术问题是什么？"**

A：
> "最有挑战的是订单表分库分表改造中的**数据平滑迁移**。挑战有三个：一是 6 亿行数据要不停机迁移；二是迁移期间新旧路由并存，双写一致性风险高；三是历史跨分片查询没法靠单分片索引。我的方案是四步：① 先用 ShardingSphere 做"双写 + 双读校验"，新数据双写两边、读走老库；② 用存量迁移工具按主键区间分批搬历史数据，每批迁移后做抽样 CRC 比对；③ 用影子流量回放验证新库的正确性与性能；④ 择低峰窗口切读、观察一周后下线双写。整个过程 3 周，零停机、零数据错乱，切换后单表从 6 亿降到 600w、写入 QPS 提升 17 倍。这里面最深的体会是：**迁移方案的核心不是搬数据，而是随时能回滚**。"

**Q3："你怎么做性能优化？"**

A：
> "我的方法是"先量后调，不猜"——四步：① 立基线：明确优化目标和当前值（如 P99 1.2s，目标 200ms）；② 分层定位：接口层看 trace 耗时分布，应用层看线程池/GC/锁，DB 层看慢日志和回表，网络层看 RTT；③ 按收益排序动手，一次只改一项并复测（避免互相干扰）；④ 加监控固化，防止回退。具体手段上我一般按"先低成本高收益"的顺序：索引与 SQL 改写 → 减少调用次数（批量化/并行化）→ 加缓存 → 异步化 → 最后才考虑扩容。在 XX 项目里我用这套方法把订单详情 P99 从 1.2s 降到 110ms。"

**Q4："如果让你重做，你会怎么改？"**

A：
> "两点会改。第一，**分片键的选择**：当时按 user_id 分片，导致运营侧的商户维度查询全部跨分片，我们后来用 ES 宽表补救；如果重做，我会在设计初期就把"C 端查询 + 运营查询"两类访问模式都列出来，用异构表或者基因法一次解决，而不是打补丁。第二，**幂等方案**：当时先做了 Redis 层拦截，后来才补唯一索引，中间出过一次重复单；正确顺序应该是**先做数据库层的强幂等兜底，再叠加 Redis 做性能优化**——数据库约束是不可绕过的最后防线。这两点后来都写进了我们组的设计规范。"

要点：**说具体方案而不是"我会更注意测试"，并且落到"我后来把经验固化成规范"**。

**Q5："这个项目你最大的收获是什么？"**

A：
> "最大的收获不是写了多少代码，而是建立了一套可迁移的方法：**任何稳定性改造，先做到"可观测"，再到"可回滚"，最后才是"更优"**。分库分表如此，灰度发布、限流降级也是如此。第二点收获是协作层面——我第一次作为 Owner 推动跨 3 个团队的方案落地，学会了用数据说服人、用 POC 降低别人的风险感，这套方法我后来在【另一个场景】也复用了。"

### 陷阱与禁忌

- 答"最有挑战的问题"时选了八股题（"最有挑战的是理解 AQS"）——面试官要的是工程挑战。
- 答"重做怎么改"时说"没什么可改的"（等于没有反思能力）。
- 收获停留在"技术变强了""抗压能力提升了"这种非具体表述。

### 一句话速记

> 结论先行 → 分点 → 主动说代价 → 结果带数字 → 末尾给一句方法论（L）。

## 10. 技术难点表达话术模板（5 组）

### 核心要点

遇到任何"讲一个难点"的要求，从下面 5 组句式中选一组套用，把括号里的内容替换成你项目的真实内容即可。

### 常见问题与标准答法

**Q1：模板一——性能类难点**

A：
> "难点在于【场景：如单接口 QPS 1.2w / RT 1.4s / DB CPU 85%】。我先用【工具：Arthas trace / 慢日志 / 火焰图】定位到瓶颈在【环节】，占比【X%】。改造分三步：【步骤 1】【步骤 2】【步骤 3】。最终【指标】从【旧值】降到【新值】，同时【附带收益：DB 负载下降 / 成本节省】。"

**Q2：模板二——一致性类难点**

A：
> "难点在于【两个操作必须一致，但没有分布式事务】。我们的原则是**不追求强一致，而是追求"最终一致 + 可对账 + 可补偿"**。具体做法：【本地消息表 / 事务消息】保证提交与发送一致；消费端【幂等 + 重试 + 死信】保证不重不丢；另外每天跑【对账任务】，差异自动进【补偿队列】。结果是【差异率/资金误差】降到 0。"

**Q3：模板三——稳定性/故障类难点**

A：
> "难点在于【故障的连锁反应：一个下游抖动导致整站雪崩】。我的思路是**隔离 + 快速失败 + 兜底**：隔离用【独立线程池 / 独立集群 / 按业务分组】；快速失败用【超时 + 熔断】，超时时间按 P99.9 设；兜底是【降级预案：返回缓存数据 / 排队领号 / 关闭非核心功能】。故障时【MTTR】从【旧值】降到【新值】，且【防止了二次故障】。"

**Q4：模板四——架构/重构类难点**

A：
> "难点在于【老系统改不动：一个需求要动 5 个模块，回归 3 天】。我没有选择大爆炸式重构，而是用**绞杀者模式**：新需求只在新模块做，老逻辑通过【防腐层/适配器】兼容；每迁完一块，就用【影子流量双跑 + 指标对比】验证，再灰度切流。过程中最重要的是【回滚能力：任何一步都能 5 分钟内退回】。结果是【交付周期 / 缺陷率 / 依赖数】的具体改善。"

**Q5：模板五——技术选型/推动类难点**

A：
> "难点不在于技术，而在于【说服别人一起改，且他们的系统不能被拖垮】。我的做法：① 用数据量化问题（三个月 4 次故障、损失 X）；② 先在一个非核心系统做 POC，拿出【具体指标提升】；③ 给出迁移方案 + 回滚方案 + 时间表，明确"谁改、改多久、出事怎么退"；④ 分批推进，把风险切成小块。最终【落地范围 / 影响面】，方案被【推广到其他团队】。"

### 陷阱与禁忌

- 只讲"做了什么"不讲"为什么这么做"（模板里"我的思路是"这一句不能省）。
- 讲难点却不讲结果（面试官会认为这事没做成）。

### 一句话速记

> 难点必配工具、方案必带取舍、结尾必有数字与新原则。

## 11. 不同轮次的考察差异与应对

### 核心要点

| 轮次 | 时长 | 考察重心 | 你的表达重点 | 常见失分 |
|---|---|---|---|---|
| 一面（技术基础） | 45~60min | Java/DB/中间件八股 + 基础编码 | 精准、简洁、不跑题；不会就说不会 | 在八股上纠缠太久，项目没时间讲 |
| 二面（项目与深度） | 60min | 项目真实性、技术深度、排查能力 | 架构图 + 数据卡 + 故障案例 | 项目讲不清、追问就含糊 |
| 三面（架构与视野） | 45~60min | 系统设计、技术选型、方法论、影响力 | 权衡分析、长期规划、跨团队经历 | 只讲实现不讲决策 |
| 交叉面（跨团队） | 30~45min | 协作、沟通、抗压、文化匹配 | 用具体事例讲冲突如何解决 | 抱怨同事/团队，或说"没冲突" |
| HR 面 | 30~45min | 稳定性、动机、薪资期望、真实性 | 诚实、稳定、有规划 | 薪资撒谎、离职原因踩雷 |

### 常见问题与标准答法

**Q1：三面（总监面）最想听什么？**

A：三件事：① 你有没有**判断力**（面对模糊需求怎么定方向、怎么取舍）；② 你有没有**影响力**（推动过什么、带过谁、写没写过规范）；③ 你的**上限**（学习速度、技术视野、对行业趋势的理解）。话术：
> "这个项目里我做了两个判断：一是当时团队想直接上微服务，我评估后建议先做模块化 + 边界清晰化，因为我们的团队只有 6 个人、运维能力不足以支撑 20 个微服务的治理成本；二是把稳定性指标（可用性、MTTR）纳入了迭代的验收项。事后看，第一个判断让我们的上线速度保持住了，第二个判断让故障数下降了 80%。"

### 陷阱与禁忌

- 对 HR 说"上一家老板不行"（无论什么理由，都换成客观事实：组织调整、业务方向变化、技术栈不匹配）。
- 交叉面表现得防御性强（"这个我不清楚，不归我管"）——改成"这块我了解得有限，我知道的部分是……"。

### 一句话速记

> 一面拼准确、二面拼深度、三面拼判断、交叉面拼协作、HR 面拼稳定。

## 12. 没有高级项目经验时的应对策略

### 核心要点

大多数候选人（尤其中小厂 / 传统行业背景）都没有"百万 QPS 秒杀"经历。**正确的策略不是编造，而是"把已有的东西讲深"**。四条路径：

| 策略 | 做法 | 可直接用的话术 |
|---|---|---|
| 1 把日常优化讲深 | 挑一个真实优化，讲透工具、指标、取舍 | "我们的量不算大，单表 800w、峰值 QPS 800，但优化前后的方法论和千万级是一样的：先定位瓶颈，再按收益排序改。" |
| 2 讲排查过程 | 故障/value 排查最能体现能力，与系统规模无关 | "虽然只有一台机器，但 MDL 阻塞、连接池耗尽、GC 停顿这些问题的定位过程和你们大促遇到的是同一套。" |
| 3 讲开源学习与自研 | 自研 RPC/网关/ID 生成器 + 读源码 | "我在业余时间照着 Dubbo 的设计写了一个 RPC 框架（GitHub 链接），实现了 SPI、负载均衡、Netty 通信、注册中心，这让我对服务治理有了底层理解。" |
| 4 讲迁移与复用 | 把 A 项目的方法用到 B 场景 | "我在上一家公司把压测方法论沉淀成模板，带到新项目后，首次大促前我们只花了 3 天就完成了容量评估。" |

### 常见问题与标准答法

**Q1：面试官说"你这量级太小了"怎么接？**

A：
> "确实，我们量级不大，所以我在这个项目里更关注**方案的可扩展性和正确的技术判断**。比如缓存这块，我按"未来涨 10 倍"的目标设计：key 分了逻辑分片、TTL 有抖动、热点做了本地缓存——这些在低量级下是浪费，但迁移成本几乎为零。另外我用压测把系统的真实容量摸清楚了：压到 3000 QPS 时 RT 开始劣化，瓶颈在 DB 的写锁，这也是我们后来做读写分离的决策依据。"

要点：**承认量级差距 → 转而强调方法的可迁移性 + 主动做过容量评估 → 用一次压测证明你能处理更大规模**。

**Q2：自研项目怎么讲才有说服力？**

A：四要素：**动机**（为什么造这个轮子）+ **设计**（模块划分与关键取舍）+ **难点**（比如 Netty 粘包拆包、心跳、序列化选型）+ **验证**（压测数据、GitHub star、被谁用过）。避免"跟着视频教程写了一个"，那没有加分。

### 陷阱与禁忌

- 编造量级（大厂面试官对量级极其敏感，一个数字就能问穿）。
- 贬低自己的项目（"就是很普通的 CRUD"）——同样的事，讲法决定评价。

### 一句话速记

> 项目规模无法造假，但深度、工具、方法论、可迁移性都可以自己挣。

- [ ] 24. 无"期望薪资"写在简历上（留到谈薪环节）
- [ ] 25. 无与岗位无关的爱好/兼职/学生经历（校招可保留 1 条）
- [ ] 26. 排版统一：字号、行距、项目符号全篇一致
- [ ] 27. 单页信息密度合理（不是一屏只有 5 行）
- [ ] 28. 找 2 个人交叉校对（一人看技术、一人看表达）
- [ ] 29. 用手机打开 PDF 检查排版是否错乱
- [ ] 30. 针对不同 JD 准备了 2~3 个版本的简历（偏业务 / 偏中间件 / 偏架构）

### 陷阱与禁忌

- 一个版本投所有岗位（大厂中间件岗与业务岗筛选关键词差异很大）。
- 简历里出现的每个项目都要能讲 10 分钟，否则宁可不写。

### 一句话速记

> 简历上的每一行都要经得起 3 个追问——写不出 3 个追问的内容，就删掉。

## 14. 投递策略

### 核心要点

| 维度 | 建议 |
|---|---|
| 渠道优先级 | 内推 > 官网/猎头 > BOSS/拉勾 > 海投（内推的简历到达率与反馈率最高） |
| 内推用法 | 找在职员工内推时，附一句"我的匹配点"（3 条），方便对方帮你递给合适的团队 |
| 岗位匹配度 | 技术栈重合度 < 60% 的岗位不投；JD 要求"精通 JVM 调优 + 源码级"而你没读过源码，不投 |
| 投递节奏 | 分三批：第一批 2~3 家"练手公司"（非首选），第二批 3~5 家主力目标，第三批 2 家冲刺（大厂/心仪团队） |
| 时间点 | 周二~周四上午 9~11 点投递，反馈率高于周末；大厂集中在 3~4 月与 8~10 月 |
| 单日投递量 | 3~5 家，留出应对面试与复盘的时间；一次性投 30 家会导致面试撞车、准备不足 |
| 拒后处理 | 记录拒因（技术深度/表达/薪资/岗位不匹配），同类问题出现 3 次就必须修正策略 |
| 保底策略 | 保证任何时候都有 1 家"保底 offer"在手，谈薪时心态完全不同 |

### 常见问题与标准答法

**Q1：面试撞车怎么办？**

A：按"目标优先级"排序：冲刺公司 > 主力目标 > 练手公司。练手的可以礼貌改期（HR 通常能接受一次改期），主力与冲刺公司尽量不推迟（推迟可能被理解为积极性不高）。同一天最多安排 2 场，中间留 1.5 小时缓冲。

**Q2：简历投出去没人回怎么办？**

A：按顺序排查：① 关键词匹配度（把 JD 里的技术词补进简历）；② 页数与排版（第一屏没有关键信息）；③ 项目描述（没有数字、没有深度）；④ 渠道（改内推）；⑤ 岗位级别（3 年经验投"高级/专家"岗大概率被过滤）。**同一份简历连续投 20 家无反馈，必须先改简历再继续投。**

### 陷阱与禁忌

- 裸辞后海投，时间压力会导致心态崩、接受低薪 offer。
- 同时在多家公司做"批量面试"却完全不准备，浪费机会成本。
- 拿到 offer 后不回绝其他公司，把路走窄（行业圈子很小）。

### 一句话速记

> 内推优先、三批投递、单日 3~5 家、练手先行、拒后必复盘。

## 自测题（含答案要点）

1. **简历一页还是两页？** 1~3 年 1 页；3~5 年 2 页；5 年以上最多 2 页。首屏必须是黄金信息。
2. **"精通"能不能写？** 除非能应对源码级追问，否则一律换成"熟练掌握"。
3. **技术栈清单的三层分级是什么？** 熟练掌握 / 熟悉 / 了解，每项配一个能力锚点。
4. **项目描述的五段式？** 背景一句话 + 我的职责 + 技术方案 + 难点与解决 + 量化结果。
5. **你的项目 QPS 是多少？峰值多少？** 必须能立刻报出日常与峰值两个数字。
6. **为什么用 user_id 当分片键？** 因为 C 端查询都以用户维度为主，能保证单分片路由；代价是运营侧跨分片查询，用 ES 宽表补偿。
7. **幂等方案的正确顺序？** 先 DB 唯一索引兜底，再叠加 Redis 提升性能。
8. **STAR 中 A 占多少时间？** 约 55%；R 约 20%；S+T 不超过 25%。
9. **STAR-L 的 L 指什么？** Learning，反思与方法论沉淀，是二三面的主要得分点。
10. **面试官在项目环节考察哪六点？** 真实性、技术深度、Owner 意识、权衡能力、结果导向、方法论。
11. **"这个方案有什么缺点"怎么答？** 主动说代价（复杂度/延迟/运维成本）+ 控制手段 + 什么条件下会换方案。
12. **"如果流量翻十倍"怎么答？** 先指出现有瓶颈在哪，再给扩容/分片/降级三步方案，最后补容量评估方法。
13. **没有大厂量级经验怎么办？** 承认差距 + 强调方法论可迁移 + 用压测证明容量评估能力 + 自研/开源补充底层理解。
14. **三面（总监面）最看重什么？** 判断力、影响力、天花板。
15. **投递节奏怎么安排？** 练手（2~3 家）→ 主力（3~5 家）→ 冲刺（2 家），单日 3~5 家，周二至周四上午投递。
16. **简历自查最重要的一条？** 简历上每行都能经得起 3 个追问，讲不清的直接删。
17. **"你最大的收获是什么"该怎么收尾？** 落到一句可复用的方法论或原则，而不是"能力提升了"。
18. **故障案例要准备几个、什么类型？** 至少 2 个：一个性能类（慢 SQL/GC/内存），一个稳定性类（雪崩/积压/连接池）。

## 背诵卡片

1. 3~5 年经验：简历 2 页，首屏放公司、年限、核心技术栈。
2. 一页/两页的判断标准不是篇幅，而是"每一行是否都值得被深挖"。
3. 时间倒序、量化优先、弱动词全部换成强动词。
4. 技术栈分三级：熟练掌握 / 熟悉 / 了解，写什么级别接什么追问。
5. 项目五段式：背景一句话 + 职责 + 方案 + 难点 + 量化结果。
6. 项目里"我"的贡献要给占比：我 60%，另两人各 20%。
7. 弱动词清单：参与、协助、配合、负责相关、优化了性能。
8. 强动词清单：主导、设计、落地、重构、推动、沉淀。
9. 简历命名：姓名-Java后端-年限-手机号.pdf。
10. 不要放生日、婚育、身份证；不要放期望薪资。
11. 每个项目准备：架构图 + 数据卡 + 2 个故障案例。
12. 数据卡十项：数据量、QPS、峰值、RT、机器数、表数、可用性、成本、人力、恢复时长。
13. 追问三方向：往深处问原理、往旁边问替代方案、往极端问 10 倍。
14. "为什么这么设计"必答三件套：约束 → 选择 → 代价。
15. "有没有别的方案"提前准备 2 个被否方案 + 否决理由。
16. CRUD 包装三路径：往量上做、往稳上做、往省上做。
17. 幂等正确顺序：DB 唯一索引兜底 → Redis 拦截 → 状态机校验。
18. 一致性表达原则：不追强一致，追"最终一致 + 对账 + 补偿"。
19. 稳定性表达原则：隔离 + 快速失败 + 兜底。
20. 重构表达原则：绞杀者模式 + 影子流量双跑 + 随时可回滚。
21. 性能优化四步：立基线、分层定位、按收益排序、加固监控。
22. 性能手段优先级：索引与 SQL → 批量/并行 → 缓存 → 异步 → 扩容。
23. STAR 占比：S15% T10% A55% R20%。
24. 每个故事结尾补一句 Learning，这是二三面的加分点。
25. 每个 Action 用"我"开头，绝不用"我们"通篇。
26. 结论先行：先用一句话给出答案，再展开过程。
27. 三面拼判断力、影响力、天花板；一面拼准确性。
28. 交叉面别说"没有冲突"，要说"冲突如何用数据解决"。
29. HR 面离职原因只讲客观事实，绝不抱怨前公司。
30. 重做方案的回答要具体到技术选择，不能只说"多做测试"。
31. 量级不够就讲方法论：工具、指标、取舍、可迁移性。
32. 自研项目四要素：动机、设计、难点、验证数据。
33. 简历投产前必做：2 人交叉校对 + 手机端排版检查。
34. 岗位匹配度低于 60% 不投；一版简历不投所有岗位。
35. 内推附 3 条匹配点，让内推人好递。
36. 三批投递：练手 → 主力 → 冲刺；单日 3~5 家。
37. 连续 20 家无反馈，先改简历再投。
38. 保底 offer 是最强的心态稳定器。
39. 每场面试后 30 分钟内填复盘表：问题、我的回答、更好回答、盲区、下一步。
40. 简历上写不出 3 个追问的内容，一律删掉。
