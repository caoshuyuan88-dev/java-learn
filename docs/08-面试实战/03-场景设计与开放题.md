### 0.1 场景题统一答题框架

任何一道场景题（无论排查还是设计），都按这 6 步走。**前 3 步是"想清楚"，后 3 步是"说清楚"**，缺任何一步都会被判定为"经验不足"。

| 步骤 | 要说什么 | 示例话术 |
| --- | --- | --- |
| ① 澄清需求 | 主动确认边界：QPS 量级、数据量、一致性要求、是否允许降级、时间窗口、上下游是谁 | > "我先确认几个前提：这个接口的日常 QPS 和峰值大概多少？数据是只读还是读写混合？对一致性是强一致还是最终一致就能接受？" |
| ② 定目标与指标 | 把模糊问题转成可量化目标：可用性 99.9% 还是 99.99%、RT P99 ≤ 200ms、消息不丢不重、数据误差 ≤ 0 | > "我先把目标定下来：可用性 99.99%，读接口 P99 控制在 100ms 内，写接口最终一致、允许秒级延迟。有了指标才能谈方案取舍。" |
| ③ 分层定位 | 用排查树或架构分层逐层排除，**不要一上来就猜结论** | > "我会按业务层→接入层→应用层→中间件层→系统层自上而下看，先确认是全局还是单机、是突增还是渐变。" |
| ④ 假设与验证 | 每个猜测都给出"怎么验证"，体现数据驱动 | > "如果怀疑是慢 SQL，我先看慢查询日志和 `SHOW PROCESSLIST`，再 `EXPLAIN` 看执行计划；能用一条命令验证的就不靠猜。" |
| ⑤ 方案与权衡 | 给 2~3 个方案并说明选择理由，主动说成本与代价 | > "这里有两个选择：本地缓存快但有脏读，分布式缓存一致但多一次网络开销。按我们的量级和一致性要求，我选分布式缓存 + 短 TTL。" |
| ⑥ 兜底与复盘 | 主动说降级、熔断、限流、开关、回滚，以及事后如何防复发 | > "上线前我准备了降级开关和回滚脚本；事后我会补一个监控看板 + 告警阈值，并写复盘文档沉淀到团队知识库。" |

**六个步骤的"必背关键词"**：澄清 → 量化 → 分层 → 验证 → 权衡 → 兜底。面试时如果紧张，先默念这 12 个字，再展开。

### 0.2 回答节奏与时间分配

**5 分钟版**（一面快问快答，通常只给 3~5 分钟）

| 时间段 | 内容 | 关键动作 |
| --- | --- | --- |
| 0:00-0:30 | 澄清 2~3 个关键前提 | 至少问一个量级（QPS/数据量）、一个要求（一致性/SLA） |
| 0:30-1:00 | 给结论 + 量化目标 | 先抛结论："核心瓶颈在 X，方案是 Y" |
| 1:00-3:00 | 分层定位 / 核心链路设计 | 口述 + 白板画一条主链路，不追求面面俱到 |
| 3:00-4:30 | 权衡与兜底 | 主动说 1 个取舍、1 个降级、1 个监控 |
| 4:30-5:00 | 一句话复盘 | "如果是生产环境，我还会加 X 校验" |

**15 分钟版**（二三面深挖）

| 时间段 | 内容 |
| --- | --- |
| 1 分钟 | 澄清需求（QPS、数据量、读写比、一致性、可用性、预算） |
| 1 分钟 | 定指标与总体架构，先画一张分层图 |
| 3 分钟 | 核心链路逐步展开：接入 → 服务 → 缓存 → DB → MQ |
| 6 分钟 | 深挖 2 个考点（面试官会挑他关心的，你提前准备 3 个可深挖点） |
| 3 分钟 | 边界与异常：热点、幂等、超时、重试、降级、扩容 |
| 1 分钟 | 演进路线：从当前量级到 10 倍量级怎么改 |

**三条铁律**：

1. **先给结论再展开**：不要让面试官等 3 分钟才听到你的方案。
2. **主动画图**：口头说"我画一下"然后画分层图/时序图，比纯语言描述清晰 3 倍。
3. **主动报数字**：QPS 1 万、缓存命中率 95%、P99 200ms、连接池 20、队列 1000 — 有数字才像做过。

### 0.3 排查类题的通用排查树

自上而下逐层排除，**先用一条命令确认"是不是全局问题"，再逐层缩小**。

| 层级 | 先确认什么 | 常用命令 / 工具 | 典型结论 |
| --- | --- | --- | --- |
| 业务层 | 是全体用户还是部分用户？是所有接口还是单接口？ | 业务监控看板、埋点、AB 分组、错误码分布 | 单接口异常 → 看代码/下游；全体异常 → 看基础设施 |
| 接入层 | DNS/CDN/LB/Nginx 是否正常，是否 502/504 突增 | `nginx -T` 看配置、`access.log`/`error.log`、`ss -s`、LB 健康检查状态 | 504 多 → 后端超时；502 多 → 后端不可用/端口没起来 |
| 应用层 | GC、线程池、连接池、锁竞争、依赖调用耗时 | `jstat -gcutil`、`jstack`、`arthas dashboard/thread -n 3/thread -b/trace`、`async-profiler`、APM 链路追踪 | Full GC 频繁、线程卡在 I/O、连接池 getConnection 等待 |
| 中间件层 | DB/Redis/MQ/ES 自身是否健康 | MySQL：`SHOW PROCESSLIST`、`SHOW ENGINE INNODB STATUS`、慢日志 + `pt-query-digest`；Redis：`INFO`、`--bigkeys`、`--hotkeys`、`SLOWLOG GET`；MQ：消费 Lag、Broker 磁盘/写入延迟；ES：`_cluster/health`、`_cat/thread_pool` | 慢 SQL 拖垮连接池、Redis 大 key 阻塞、MQ 消费能力不足 |
| 系统层 | CPU/内存/磁盘/网络/句柄是否到瓶颈 | `top -Hp`、`vmstat 1`、`iostat -x 1`、`sar -n DEV 1`、`free -m`、`df -h`、`df -i`、`ulimit -n`、`dmesg -T` | CPU steal 高 → 宿主机争抢；`df -i` 满 → inode 耗尽；`dmesg` 有 OOM Killer 记录 |
| 依赖层 | 第三方/下游服务是否变慢或不可用 | 超时率、重试次数、熔断器状态、`mtr`/`curl -w` 分段计时 | 下游 P99 上升导致上游线程池被占满 → 连锁雪崩 |

**排查树使用口诀**：先分层、后分机、再分接口，最后分调用；每一步都用一条命令把可能性砍掉一半，而不是凭经验直接下结论。

## 1. 线上问题排查类（20 题）

### Q1：线上 CPU 100% 怎么排查？
- **【考察点】**：Linux 排查工具链、JVM 线程模型、能否把"哪个线程在跑什么代码"定位到具体行。
- **【回答要点（分步骤）】**：
  1. 先判定范围：`top` 看 load average 与 `%sy`/`%us`/`%wa` 占比；`top -Hp <pid>` 看是单线程还是多线程打满。`%wa` 高说明不是 CPU 算力问题，而是 I/O 等待，转去看磁盘。
  2. 定位到线程：记录 `top -Hp` 里占 CPU 最高的 TID，转十六进制 `printf '%x\n' <tid>`，然后 `jstack <pid> | grep -A 30 <hex>` 找到对应线程栈。
  3. 如果是多个业务线程都在同一段代码：`arthas` 连上去执行 `dashboard` 看线程分布，`thread -n 3` 看最忙 3 个线程栈，`thread -b` 直接找阻塞其他线程的锁持有者。
  4. 需要采样分析就用 `async-profiler`：`./profiler.sh -d 30 -e cpu -f /tmp/cpu.html <pid>`，火焰图里最宽的栈就是热点。
  5. 常见根因：正则回溯/死循环（如 `String.split` 超长字符串）、序列化大对象（JSON 深拷贝）、无限重试、自旋锁、GC 线程占用（`jstat -gcutil` 看 FGC 是否在飙升）、日志同步打印过多。
  6. 止血优先：流量入口限流或摘掉异常节点，再考虑回滚版本、加 `-XX:ActiveProcessorCount` 或扩容。
- **【常见误区】**：只看 `top` 就下结论；用 `jstack` 时忘记把 TID 转十六进制；把 GC 线程占用误判成业务代码死循环；直接 `kill -9` 重启而不留现场（应先 `jstack` 存一份栈、`jmap` 存一份堆）。
- **【迁移话术】**：> "这类问题的排查路径是通用的：先分机器、再分线程、最后到代码行。我没在生产上遇到百分百的 CPU 打满，但在压测时用同样的 top -Hp → printf → jstack → profiler 的链路定位过一次序列化热点，路径是一样的。"

### Q2：内存泄漏与 OOM 怎么排查？
- **【考察点】**：JVM 内存分区、堆转储分析、能否区分"真泄漏"与"内存不够"。
- **【回答要点（分步骤）】**：
  1. 先看 OOM 报的是哪块内存：`java.lang.OutOfMemoryError: Java heap space`（堆）、`Metaspace`（类元数据/动态代理/热部署）、`GC overhead limit exceeded`（GC 空转）、`unable to create new native thread`（线程数/栈内存）、`Direct buffer memory`（堆外）。
  2. 生产环境必须提前配好：`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/dump`，加 `-XX:+ExitOnOutOfMemoryError` 让它快速失败，避免半死不活地拖垮整条链路。
  3. 现场分析：`jmap -histo:live <pid> | head -30` 看对象数量 Top（快速定位是哪个类暴涨）；`jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>` 拿堆，MAT 打开看 Dominator Tree 与 Leak Suspects 报告。
  4. 若已有多个 dump，用 MAT 做对比（Compare Basket），看哪类对象在两次之间只增不减 — 这才是泄漏的判决性证据。
  5. 高频泄漏场景：`ThreadLocal` 未 `remove`（线程池复用导致 value 永不释放）、静态集合/本地缓存无上限无过期（`HashMap` 当缓存）、监听器/回调注册后未注销、连接/流未关闭、`String.intern` 或大 `substring` 持有大数组。
  6. 堆外内存用 `-XX:NativeMemoryTracking=detail` + `jcmd <pid> VM.native_memory summary` 看，或用 `pmap -x <pid> | sort -k3 -n` 看匿名内存段。
- **【常见误区】**：重启就完事、不做 dump 分析（下次一定复发）；只看堆不看 Metaspace 和直接内存；把"对象多"当成"泄漏"（要先看是否被 GC Root 强引用）；忘记线程池场景下 ThreadLocal 一定泄漏。
- **【迁移话术】**：> "内存问题的通用套路是：先确认哪块内存、再拿 dump、再用 MAT 看支配树、最后用两次 dump 对比确认增长。即使我没遇到过线上 OOM，我在本地用这套流程定位过缓存无上限的问题。"

### Q3：Full GC 频繁怎么排查？
- **【考察点】**：GC 日志解读、分代假设、能否算出"到底是分配太快还是回收太慢"。
- **【回答要点（分步骤）】**：
  1. 开 GC 日志（这是前提）：`-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=100M`（JDK 9+），JDK 8 用 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/data/logs/gc.log`。
  2. `jstat -gcutil <pid> 1000 20` 看关键列：`O`（老年代使用率）、`FGC`（次数）、`FGCT`（总耗时）、`GCT`。**判定标准**：FGC 每分钟 > 1 次或 FGCT 单次 > 1s，就要处理。
  3. 分三种情况判断：
     - 老年代使用率持续高位不降 → 有对象长期存活或被强引用，按内存泄漏排查（见 Q2）。
     - 老年代使用率低但 FGC 频繁 → 触发了 `System.gc()`（`-XX:+DisableExplicitGC` 或 `-XX:+ExplicitGCInvokesConcurrent`）或元空间/大对象分配导致。
     - 每次 FGC 后老年代降幅很小 → 说明对象生命周期长，考虑调大新生代或改 `-XX:MaxTenuringThreshold`。
  4. 对症下药：分配速率过高（大对象/批量查询全量捞数据）先找业务代码；`Survivor` 太小导致对象过早晋升，用 `-XX:SurvivorRatio`、`-XX:TargetSurvivorRatio` 调；大对象用 `-XX:PretenureSizeThreshold`（仅 Serial/ParNew 生效，G1 无此参数）。
  5. G1 专有排查：`-XX:MaxGCPauseMillis` 设置不合理会引发频繁 Mixed GC，用 `jstat -gc` 看 `G1 Evacuation Pause` 和 `Humongous` 分配；`-XX:InitiatingHeapOccupancyPercent`（IHOP）过低会导致并发标记过于频繁。
  6. 长期方案：换 G1/ZGC（`-XX:+UseZGC`，停顿 < 10ms）、把大对象拆小、把"全量查询"改成游标/分页、把本地缓存换 Redis。
- **【常见误区】**：不看 GC 日志只凭感觉调参；把 FGC 频繁直接归因为"内存不够"而盲目加堆（反而让单次停顿更长）；忽略 `System.gc()` 被 RMI/直接内存回收触发；G1 下照抄 CMS 参数把 JVM 启动搞失败。
- **【迁移话术】**：> "我的排查顺序是：GC 日志 → jstat 看趋势 → 判断是分配快还是回收慢 → 定位到代码或参数。这套顺序和具体业务无关，任何 Java 服务都适用。"

### Q4：接口 RT 变高怎么排查？
- **【考察点】**：链路追踪意识、能否把"变高"拆成"哪个环节变高"。
- **【回答要点（分步骤）】**：
  1. 先量化：是哪条接口、P50/P99/P999 各是多少、从什么时间开始、是突变还是渐变、影响面（全量用户还是部分机房/部分版本）。**只提高 P99 而 P50 正常 → 通常是长尾问题**（GC、锁、连接池等待、个别慢节点）；P50 一起升高 → 全局瓶颈。
  2. 分层拆耗时：靠 APM（SkyWalking/Arthas trace/自研埋点）把一次请求拆成「网关 → 应用 → 缓存 → DB → 下游 RPC」，看哪一段耗时占比最大。
  3. 单机验证：`arthas trace com.xxx.Service method -n 5 --skipJDKMethod false` 看方法内部各子调用耗时；`watch` 看入参出参。
  4. 逐层排查常见根因：
     - 应用层：Full GC（`jstat`）、线程池排队（`arthas thread` 看等待线程数）、连接池获取连接耗时（HikariCP 打 `metrics` 或在 APM 里看）。
     - 缓存层：缓存命中率下降（`INFO stats` 看 `keyspace_hits/keyspace_misses`）、大 key（`--bigkeys`）、热 key、Redis 慢查询（`SLOWLOG GET 10`）。
     - DB 层：慢 SQL 数量、`Threads_running`、锁等待（`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 与锁等待段）。
     - 下游：对方 P99 上升、重试放大流量、超时时间设置过长（如 5s，把线程一直占住）。
  5. 止血：先摘掉慢节点/扩容，再开限流保护；如果确认是某次发布引入，直接回滚。
- **【常见误区】**：只看平均 RT（平均值掩盖长尾）；不看时间线（忽略了"刚好在发布之后"）；在应用层死磕，其实是 DNS 解析或 LB 转发慢；超时设置比下游 RT 大一个数量级，导致线程被长期占用。
- **【迁移话术】**：> "我处理 RT 问题的固定动作是：先定基准（哪个分位数、什么时候开始）、再拆链路、再单机复现。哪怕系统我没做过，只要它有链路追踪，这套方法就能落地。"

### Q5：数据库连接池耗尽怎么排查？
- **【考察点】**：连接池原理、慢 SQL 与连接泄漏的区分、能否给出精确的池参数。
- **【回答要点（分步骤）】**：
  1. 识别症状：日志里出现 `Connection is not available, request timed out after 30000ms`（HikariCP）或 `Could not get JDBC Connection`；APM 里 `getConnection` 耗时飙升；`SHOW STATUS LIKE 'Threads_connected'` 逼近 MySQL 的 `max_connections`。
  2. 区分三类原因：
     - **连接泄漏**：拿到的连接没还（手动 `getConnection` 未 `close`、异常路径漏归还、事务未提交/回滚）。看 HikariCP 的 `activeConnections` 是否"只增不降"。
     - **慢 SQL 占住连接**：`SHOW FULL PROCESSLIST` 看哪些会话 `Time` 很大且 `State` 是 `Sending data`/`Waiting for table metadata lock`。用 `pt-query-digest /var/log/mysql/slow.log` 聚合出 Top 慢 SQL。
     - **池太小 / 请求量突增**：`activeConnections` 长期等于 `maximumPoolSize`，但单条 SQL 很快 — 这是容量问题，不是泄漏。
  3. 定位泄漏细节：`SHOW PROCESSLIST` 里 `Sleep` 很久的连接说明归还了但空闲；若连接数等于池上限且都在 `Query`/`Sending data` 状态，则是慢 SQL 拖住；若连接都在等待锁，则看 `SHOW ENGINE INNODB STATUS` 的锁等待。
  4. 参数建议：HikariCP `maximumPoolSize` 通常按 `CPU 核数 × 2 + 磁盘数` 量级起步（不是越大越好，MySQL 侧连接数是硬上限），`connectionTimeout` 设 1~3s 而不是默认 30s（快速失败比排队好），`leakDetectionThreshold=60000` 帮你在测试环境抓泄漏，`maxLifetime` 比 MySQL `wait_timeout` 小 30s 左右避免用到已被服务端断开的连接。
  5. 兜底：入口限流 + 慢 SQL 熔断（如 Sentinel 对 DAO 层做慢调用比例控制）+ 把非核心查询走只读从库。
- **【常见误区】**：一味调大 `maximumPoolSize`（连接数打满 MySQL，`max_connections` 打爆后全站不可用）；把 `connectionTimeout` 设很大导致请求堆积；忽略"手动管理连接"的遗留代码；忘了 `@Transactional` 里包含 RPC 调用，导致事务时间被拉长、连接被长时间持有。
- **【迁移话术】**：> "连接池问题的判断口径很清晰：看活跃连接数是否只增不降。只增不降就是泄漏，波动但不超上限就是慢 SQL，长期贴着上限就是容量不够。三个方向三种解法。"

### Q6：慢 SQL 怎么排查和优化？
- **【考察点】**：EXPLAIN 解读、索引设计、能否给出"改 SQL / 改索引 / 改架构"三层方案。
- **【回答要点（分步骤）】**：
  1. 先找到它：开慢日志（`slow_query_log=ON`、`long_query_time=1`、`log_queries_not_using_indexes=ON`），用 `pt-query-digest` 按"总耗时"排序（**不只看单条最慢，要看累计耗时占比**）。线上应急可用 `SHOW FULL PROCESSLIST` 抓现场。
  2. 看执行计划：`EXPLAIN` 重点看 `type`（要至少 `range`，避免 `ALL` 全表扫）、`key`（实际用的索引）、`rows`（预估扫描行数）、`Extra`（`Using filesort`/`Using temporary`/`Using index condition`）。必要时 `EXPLAIN ANALYZE` 看真实耗时分布。
  3. 常见病灶与解法：
     - 索引失效：函数作用于索引列（`WHERE DATE(create_time)=...`）、隐式类型转换（字符串列传数字）、`LIKE '%x'` 前导通配、`OR` 连接不同列、最左前缀不满足。改写成范围查询或调整索引顺序。
     - 深分页：`LIMIT 1000000, 20` 会扫描并丢弃前 100 万行。改成延迟关联 `SELECT a.* FROM t a JOIN (SELECT id FROM t WHERE ... ORDER BY id LIMIT 1000000,20) b ON a.id=b.id`，或业务上改成游标翻页（`WHERE id > last_id ORDER BY id LIMIT 20`）。
     - 大事务/长事务：`information_schema.innodb_trx` 看 `trx_started`，超过 10s 的事务要报警并拆小。
     - 回表过多：加覆盖索引，把 `SELECT *` 改成只取必需列。
  4. 索引设计原则：区分度高的列在前、联合索引遵循最左前缀、避免在索引列上做计算、单表索引不超过 5~6 个（写入放大）、用 `ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE` 在线加索引（大表建议用 `gh-ost` 或 `pt-online-schema-change`）。
  5. 架构层：单表超过 500 万~1000 万行且持续增长时，考虑归档冷数据、读写分离、垂直拆分、按业务键分库分表。
- **【常见误区】**：只看 `EXPLAIN` 不看真实数据分布（`rows` 是估算值）；加了索引但顺序不对导致用不上；在大表上直接 `ALTER TABLE` 造成锁表；优化了单条最慢 SQL 却忽略"调用量 10 万次、单次 50ms"的累计杀手。
- **【迁移话术】**：> "慢 SQL 的优化分三层：先改 SQL 写法，再改索引，最后才动架构。顺序不能反，因为前两层成本最低、见效最快，而动分库分表是不可逆的大工程。"

### Q7：死锁怎么排查？
- **【考察点】**：能否区分数据库死锁与 Java 死锁，各自的证据入口在哪里。
- **【回答要点（分步骤）】**：
  1. **判断是哪一类**：数据库死锁表现为 SQL 抛出 `Deadlock found when trying to get lock; try restarting transaction`；Java 死锁表现为线程永久 `BLOCKED`、接口无响应但 CPU 不高。
  2. **MySQL 死锁**：`SHOW ENGINE INNODB STATUS\G` 看 `LATEST DETECTED DEADLOCK` 段 — 里面直接给出两个事务各自持有的锁、等待的锁、执行的 SQL、以及 **InnoDB 选择回滚哪个事务**。历史死锁开 `innodb_print_all_deadlocks=ON` 写进错误日志。当前锁等待用 `SELECT * FROM performance_schema.data_lock_waits` 与 `information_schema.innodb_trx` 关联，看 `trx_wait_started` 与 `trx_query`。
  3. **MySQL 死锁根因**：两个事务以相反顺序更新同一批行（如 A 先更 id=1 再更 id=2，B 先更 id=2 再更 id=1）；缺索引导致 `UPDATE ... WHERE name=?` 全表扫描并锁大量行/间隙锁；唯一索引冲突场景下 insert 的加锁顺序；`SELECT ... FOR UPDATE` 与普通 `UPDATE` 混用。
  4. **MySQL 死锁解法**：统一加锁顺序（按主键升序批量更新）；把大事务拆小、缩短持锁时间；给 `WHERE` 条件补索引减少锁范围；乐观锁（`UPDATE ... SET version=version+1 WHERE version=?`）替代悲观锁；捕获死锁异常后做有限次重试（指数退避 + 幂等保证）。
  5. **Java 死锁**：`jstack <pid>` 输出末尾会自动打印 `Found one Java-level deadlock` 并给出线程名、持有的锁、等待的锁、代码行号。`arthas thread -b` 更直接，只输出阻塞别人的那个线程。
  6. **Java 死锁根因**：两把锁顺序不一致；嵌套 `synchronized`；`ThreadPoolExecutor` 中任务提交子任务并等待结果（父任务占着线程等子任务，线程池满了子任务永远排队）；`CompletableFuture` 链条上循环依赖。
  7. **预防**：多把锁固定全局顺序；用小锁粒度代替大锁；用 `tryLock(timeout)` 替代无限等待；线程池避免任务内嵌套提交同池任务（改用不同池或 `ForkJoinPool`）。
- **【常见误区】**：只看应用日志不看 InnoDB Status（那里有完整证据）；把"锁等待超时"（`Lock wait timeout exceeded`，默认 50s）当成死锁（死锁会被 InnoDB 立即检测并回滚，不等 50s）；认为死锁只能靠重试解决，不修加锁顺序。
- **【迁移话术】**：> "死锁排查的关键是先拿到权威证据：数据库看 InnoDB Status 的 LATEST DETECTED DEADLOCK，Java 看 jstack 的死锁段落。这两个地方都直接告诉你谁持有什么、在等什么，不需要靠猜。"

### Q8：MQ 消息积压上千万怎么处理？
- **【考察点】**：MQ 消费模型、能否分层给出"止损 + 追数据 + 复盘"的完整方案。
- **【回答要点（分步骤）】**：
  1. 先定位积压的**原因**再动手：消费端挂了？消费变慢（依赖下游变慢/慢 SQL）？生产端突增（活动流量、上游重试风暴、消息重复投递）？消费者数量不足？分区/队列数少于消费者数导致扩消费者无效？
  2. **应急止损（分钟级）**：
     - 消费端：扩消费者实例（RocketMQ 扩消费者数受队列数上限；Kafka 受分区数上限 — 这是最容易踩的坑）。
     - Kafka 临时扩容：用 `kafka-reassign-partitions.sh` 或 `kafka-topics.sh --alter --partitions` 增加分区（注意：增加分区会破坏按 key 的顺序性）。
     - 提高单机消费并发：RocketMQ 调 `consumeThreadMax`（默认 20 提到 100+）；Kafka 用 `concurrency`（Spring Kafka）或手动创建多 `KafkaConsumer` 线程。
     - 批量消费：`max.poll.records` / RocketMQ 的 `consumeMessageBatchMaxSize` 调大，减少网络往返。
  3. **降级业务重要性**：非核心消息（日志、埋点、通知）先丢弃或落库异步补偿；核心消息保证处理。
  4. **临时"搬运"方案（积压太多、原消费者能力上限）**：写一个临时消费者，把消息快速转发到一个新建的、分区数更多的 topic，再让一批消费者并行消费新 topic。**这是追积压的经典手法**，代价是顺序性丢失、要保证转发本身幂等。
  5. **防重复与顺序**：扩容和 Go 改并发后，消费会乱序与重复，必须保证消费幂等（唯一键去重表 / Redis setnx / 状态机 + 版本号），否则追回数据反而造成业务脏数据。
  6. **恢复后行动**：把消费者 Lag 做成监控大盘并设告警（如 Lag > 10 万告警、> 100 万 P1）；给消费端加自动扩容（KEDA / 云上按 Lag 弹性）；排查上游是否有重试风暴（重试次数、死信队列）。
- **【常见误区】**：不看分区数直接加消费者（扩了没用，白扩容）；为了追速度关掉幂等（造成重复下单/重复扣款）；用"清空 topic / 跳过消息"的方式解决积压（丢业务数据）；忘记下游 DB 会被追数据的洪峰打死（追数据也要限速）。
- **【迁移话术】**：> "积压处理我总结成三步：止损（扩消费者/提并发）、分流（临时 topic 搬运 + 降级非核心）、追平（限速追数据 + 幂等兜底）。顺序不能乱，先扩并发再补幂等，很容易把积压变成资损。"

### Q9：缓存雪崩怎么处理？
- **【考察点】**：对"同时大面积失效"的理解，以及预防手段是否成体系。
- **【回答要点（分步骤）】**：
  1. 定义清楚：大量缓存 key 在同一时刻集中过期，或缓存服务整体不可用，导致请求全部穿透到 DB，DB 被打挂形成连环故障。
  2. **防集中过期**：基础 TTL 上叠加随机抖动，例如 `ttl = 30min + random(0, 10min)`，把过期时间打散到窗口内。
  3. **防缓存整体不可用**：Redis 做主从 + 哨兵或 Cluster 集群，避免单点；做多级缓存（本地 Caffeine + Redis），Redis 挂了本地还能顶几秒到几十秒。
  4. **请求侧保护**：
     - 限流：网关层对回源流量限流（Sentinel/Nginx `limit_req`），保证 DB 不被瞬时打满。
     - 熔断降级：DB 压力超阈值时直接返回兜底数据（默认值、静态页、上一次快照），而不是打 DB。
     - 单飞（single-flight）：同一个 key 只允许一个线程回源，其余等待结果（Redis 分布式锁 / `ConcurrentHashMap` + `CompletableFuture` 本地合并）。
  5. **预热**：发布前用脚本把热点 key 提前加载（`redis-cli --pipe` 批量写或应用启动时预热），避免服务刚启动就全量回源。
  6. **兜底数据**：对读多写少的配置类数据，在应用本地保留一份"最后可用版本"，Redis 和 DB 都挂了也能降级返回。
- **【常见误区】**：只做随机 TTL 就以为解决了雪崩（缓存服务整体挂掉时随机 TTL 无意义）；预热脚本在流量高峰执行；降级返回空数据而业务没做兼容导致前端报错。
- **【迁移话术】**：> "雪崩的本质是"失效时刻集中 + 回源能力不足"，所以两头都要治：过期时间打散是治"集中"，限流 + 熔断 + 单飞是治"回源能力"。只做一头都挡不住。"

### Q10：缓存击穿怎么处理？
- **【考察点】**：热 key 失效瞬间的并发控制，能否说出具体实现。
- **【回答要点（分步骤）】**：
  1. 定义清楚：**单个热点 key** 在过期瞬间被大量并发请求同时打到 DB。与雪崩（大量 key 同时过期）和穿透（查不存在的数据）严格区分 — 面试时先把三个概念分开说，是加分项。
  2. **方案一：互斥锁重建**。缓存失效时，只让拿到锁的线程查 DB 并回写缓存，其他线程短暂等待（如 50ms）后重试读缓存。伪代码：
     ```
     String token = UUID.randomUUID().toString();          // 锁的持有者标识
     boolean locked = redis.set(lockKey, token, "NX", "PX", 10000);  // 原子加锁 + 过期
     if (locked) {
         try {
             Object v = db.query(key);
             redis.set(key, v, "EX", 1800 + rand(0, 600));  // TTL 加随机抖动
         } finally {
             // Lua 脚本原子校验 token 再删，避免删掉别人的锁
             // if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end
             redis.eval(DEL_IF_MATCH_LUA, lockKey, token);
         }
     } else {
         Thread.sleep(50);                                 // 等重建完成后重读缓存
         Object v = redis.get(key);
     }
     ```
  3. **方案二：逻辑过期（不设物理 TTL）**。value 里存 `expireTime` 字段，物理上永不过期。读到逻辑过期的数据时，返回旧值 + 异步线程去重建。优点：**请求永不阻塞**；缺点：会有一小段脏数据窗口，需要业务能接受。
  4. **方案三：本地缓存兜底**。热点 key 在应用内用 Caffeine 缓一份（TTL 1~5s），即使 Redis 失效也能挡住绝大多数请求；配合 `refreshAfterWrite` 做异步刷新。
  5. **方案四：热点探测 + 预热**。用 `redis-cli --hotkeys`（需 `maxmemory-policy=allkeys-lfu`）或客户端统计找出热点 key，把它们设为逻辑过期/永不过期并常驻。
  6. **兜底**：即使 DB 被短暂打到，也要有 DB 层的连接池上限与限流，避免"击穿一个 key 打挂整个库"。
- **【常见误区】**：把击穿说成雪崩（概念混淆直接减分）；用 `setnx` 加锁但不设过期时间（持锁进程挂掉导致永久死锁）；`del` 锁时不校验持有者（删掉别人的锁）；等待期间不设最大重试次数导致线程堆积。
- **【迁移话术】**：> "击穿的核心是"一个热 key + 高并发"，所以答案就两条路：要么让只有一个线程去回源（互斥锁），要么让请求永远不阻塞（逻辑过期 + 异步刷新）。我会优先用逻辑过期，因为它没有等待。"

### Q11：Redis 内存告警怎么处理？
- **【考察点】**：Redis 内存构成、淘汰策略、能否定位"谁在吃内存"。
- **【回答要点（分步骤）】**：
  1. 看全景：`INFO memory` 关注 `used_memory_human`、`used_memory_rss`（RSS 明显大于 used 说明有内存碎片，看 `mem_fragmentation_ratio`，> 1.5 考虑 `activedefrag yes`）、`maxmemory`、`maxmemory_policy`、`evicted_keys`（已开始淘汰就是已经影响业务了）。
  2. 找"谁在吃"：`redis-cli --bigkeys` 按类型扫出最大的 key（**注意它会 `SCAN` 全库，线上建议在从库或低峰执行**）；对可疑 key 用 `MEMORY USAGE <key>` 精确看字节数；`INFO keyspace` 看各 DB 的 key 数量；按前缀抽样统计 `redis-cli --scan --pattern 'user:*' | head` 配合脚本分类。
  3. 常见根因：大 key（单个 Hash/List/ZSet 存放百万级元素，如把整个用户列表塞进一个 key）；无 TTL 的 key 越积越多；业务量增长导致正常数据量翻倍；内存碎片率过高；同一实例混部了多个业务的数据。
  4. **应急止血**：对可删数据执行 `UNLINK`（异步删除，避免 `DEL` 大 key 阻塞主线程）；控制写入；必要时临时调大 `maxmemory`（要预留拷贝缓冲区）；实在不行加从库承载读流量。
  5. **治本**：
     - 大 key 拆分：把 `user:all` 拆成 `user:list:{shardId}` 分片；把大 Hash 按字段哈希拆分；List 改成 Stream/分页 List。
     - 全量 key 加 TTL（除确需常驻的配置类），TTL 加随机抖动。
     - 用 Hash 分桶存大量小对象（如 `user:info:{uid/1000}` 里放 1000 个 field），利用 ziplist 编码显著省内存。
     - 设置合理淘汰策略：缓存场景用 `allkeys-lru` 或 `allkeys-lfu`（LFU 对热点更友好）；确需保证数据不丢则用 `noeviction` 但必须配监控告警，否则写入会直接报错。
     - 容量规划：单实例控制在 10~20GB 以内（RDB fork 与主从同步都会放大），超过就 Cluster 分片。
  6. 兜底：`maxmemory` 一定小于机器物理内存的 70%，预留 fork 拷贝空间；开启 `lazyfree-lazy-eviction yes` 让淘汰也异步。
- **【常见误区】**：`maxmemory` 不设（Redis 撑爆机器被 OOM Killer 杀）；`maxmemory-policy` 设成 `noeviction` 又不监控（写入静默失败或报错）；用 `KEYS *` 找大 key 把线上阻塞住；只扩容不加 TTL 与拆分，过几个月又满。
- **【迁移话术】**：> "Redis 内存问题的处理顺序是：先看 INFO 判断是碎片还是数据、再用 --bigkeys 找到大头、然后是删/拆/打散 TTL，最后才是扩容。直接扩容是最贵也最不解决问题的做法。"

### Q12：服务雪崩怎么处理？
- **【考察点】**：对"连锁失败"的机制理解，以及熔断、隔离、降级是否成体系。
- **【回答要点（分步骤）】**：
  1. 说清机制：下游变慢 → 上游调用线程被占满 → 上游线程池耗尽 → 上游也变慢 → 继续向上蔓延，最终全站不可用。**核心是"资源被慢调用占住"而不是"报错"**。
  2. **三件套**：
     - **超时**：所有跨进程调用必须设超时（连接超时 1s、读超时按下游 P99 的 1.5~2 倍设置），绝不能无限等。HTTP 客户端、RPC、DB、Redis 客户端都要显式配。
     - **熔断**：Sentinel/Resilience4j/Hystrix 配置"慢调用比例 + 异常比例 + 异常数"三选一的熔断规则，熔断后快速返回兜底，10~30s 后半开探测。
     - **隔离**：线程池隔离或信号量隔离，让不同下游互不影响；容器层面把核心服务与非核心服务分开部署（避免同一台机器上的批处理任务拖垮在线接口）。
  3. **限流**：入口限流（拒绝超过承载能力的流量，保护自己）+ 出口限流（限制对下游的调用速率，保护别人）。Sentinel 的 QPS 流控、Nginx `limit_req`、集群流控模式都要能说出来。
  4. **降级**：为每个非核心依赖准备降级分支（推荐位返回空、评价返回缓存旧值、风控超时按"放行但记日志"处理），并用开关控制（Apollo/Nacos 配置中心热更新，秒级生效）。
  5. **重试要克制**：重试次数 1~2 次且必须配指数退避 + 抖动；只在幂等且可重试的调用上重试；**大促时优先关掉重试**，否则重试本身会放大流量 2~3 倍。
  6. **兜底与演练**：核心链路做单机房/单依赖故障演练（混沌工程），提前发现单点；把"少依赖"作为架构原则（强依赖不超过 3 个）。
- **【常见误区】**：只做限流不做熔断（下游挂了限流也拦不住线程堆积）；超时设成 30s（比不做超时还危险）；重试无上限导致流量放大；降级逻辑从未演练过，真出事时代码报错。
- **【迁移话术】**：> "雪崩治理我记成"两减一守"：减少慢调用（超时 + 熔断）、减少依赖（降级 + 隔离）、守住入口（限流）。这三条不管系统多大都适用。"

### Q13：线程池打满怎么排查？
- **【考察点】**：线程池参数与拒绝策略、能否区分"任务太多"和"任务太慢"。
- **【回答要点（分步骤）】**：
  1. 看症状：日志里出现 `RejectedExecutionException`；接口大批超时；`jstack` 里大量线程处于 `WAITING`/`TIMED_WAITING` 在同一个队列的 `take`/`poll` 上，或者处于 `RUNNABLE` 卡在 socket read。
  2. 拿来数据：`arthas thread` 看线程数与状态分布；**生产环境必须给线程池起名字**（`ThreadFactoryBuilder().setNameFormat("order-pool-%d")`），否则 `jstack` 里全是 `pool-1-thread-x` 无法定位。有 Micrometer/Actuator 的话直接看 `executor.active`、`executor.queued`、`executor.completed` 指标。
  3. 判定类型：
     - `active = maxPoolSize` 且 `queue` 很长、任务本身很快 → **流量大于处理能力**，要扩容或削峰。
     - `active` 高且任务耗时暴涨 → **任务变慢**，去看任务内部的 I/O、锁、下游调用。
     - `active` 不高但队列满 → 参数配置不合理（核心线程太小）或队列容量太小。
     - 线程数远超 `maxPoolSize` → 有代码在池外直接 `new Thread`，或用了无界的 `CachedThreadPool`。
  4. 参数原则：CPU 密集型 `N+1`；I/O 密集型 `2N` 或按 `N × (1 + 等待时间/计算时间)` 估算；队列**必须有界**（`ArrayBlockingQueue` 或 `LinkedBlockingQueue(capacity)`），绝不用无界队列；`allowCoreThreadTimeOut(true)` 让空闲核心线程也能回收（适合突发流量型业务）。
  5. 拒绝策略：`CallerRunsPolicy` 起到背压作用（让调用方自己去执行，自然降速，**在线业务常用**）；`AbortPolicy` 明确失败并由上层返回"系统繁忙"；`DiscardOldest` 只适合可丢弃的日志类任务。绝不使用静默丢弃默认策略而不记录。
  6. 隔离：按业务划分独立线程池（订单池、通知池、报表池），避免一个慢业务占满公共池拖垮全站；配合 Sentinel 把线程池活跃度做成自适应限流指标。
- **【常见误区】**：用 `Executors.newFixedThreadPool`（无界队列，任务无限堆积导致 OOM）；线程池没设名字导致无法排查；拒绝策略静默丢弃且不告警；所有业务共用一个线程池。
- **【迁移话术】**：> "线程池打满的判断很直接：看 active 是否长期顶到上限、队列是否在涨、任务耗时是否变长。三个指标分别对应流量问题、能力问题、依赖问题，方向完全不一样。"

### Q14：日志暴涨怎么处理？
- **【考察点】**：日志治理意识、能否兼顾"止血"与"不丢排查证据"。
- **【回答要点（分步骤）】**：
  1. 先量化：是日志文件增长快（`df -h` / `du -sh /data/logs/*` 看哪个文件大）还是写入 QPS 高，会不会撑爆磁盘（撑爆磁盘会导致服务写日志阻塞甚至崩溃）。
  2. 找源头：
     - 错误日志暴增 → 有异常在大量抛出（如 NPE、下游超时），**先看异常本身，日志暴涨往往只是症状**。
     - 循环里的日志 → 代码在批量处理时逐条打印，把 `log.info` 打到循环内。
     - 某个参数开启导致打全量入参/出参（大对象 `toString`）。
     - 重复告警触发（同一个异常每秒刷上万行）。
  3. **应急止血**：动态调整日志级别（`arthas logger` 命令、Spring Boot Actuator 的 `/loggers` 接口、Apollo/Nacos 配置热更新），把 DEBUG 降为 WARN；对异常做"限流打日志"（同一异常 1 分钟只打一次完整栈，其余只计数）；把非核心日志异步化（Logback 的 `AsyncAppender`）。
  4. **防爆仓**：Logback 配 `RollingFileAppender` + `SizeAndTimeBasedRollingPolicy`（单文件 100MB、保留 7~15 天、`totalSizeCap` 限制总大小），或交给 Filebeat/Fluentd 采集后本地只留 1 天；日志盘与数据盘分离，并且**监控日志盘用量，80% 告警**。
  5. **治本**：日志规范落地（统一埋点格式、禁止在循环里打 info、禁止打印全量集合和大对象、敏感字段脱敏）；序列化大对象时先做长度截断（如只打前 500 字符）；采样打日志（如每 100 次打一条）。
  6. **注意顺序**：先降级止血（避免磁盘满导致全站挂），再定位异常根因。**降日志级别时千万别把错误日志一起关掉**，否则事后无法复盘。
- **【常见误区】**：上来就删日志文件（丢掉现场，且 `rm` 掉正在写的文件句柄不释放会导致磁盘不释放，应 `truncate -s 0` 或用 logrotate）；日志级别全局调成 ERROR 导致关键线索丢失；不做日志盘容量监控。
- **【迁移话术】**：> "日志暴涨我按两步走：先保命（降级、异步、轮转），再治病（找到刷日志的那段代码）。因为日志盘写满会把整个服务拖垮，止血必须在定位之前。"

### Q15：磁盘满怎么处理？
- **【考察点】**：Linux 磁盘与 inode 的区别、能否快速定位"谁把盘写满了"。
- **【回答要点（分步骤）】**：
  1. 先确认是空间满还是 inode 满：`df -h` 看容量，`df -i` 看 inode。**两者是独立的**，小文件极多时容量还有剩但 inode 先耗尽，写入照样报 `No space left on device`。
  2. 定位大目录：`du -sh /data/* | sort -rh | head -20`，逐层下钻；`lsof +L1` 找"已删除但被进程占用"的文件（常见于日志删除后句柄未释放，`df` 显示满但 `du` 找不到大头，**重启进程或 `: > file` 才能释放**）。
  3. 常见根因：日志未做轮转（见 Q14）；堆 dump 文件堆积（`HeapDumpPath` 目录常年不清理）；MQ 消息文件积压；容器镜像/临时文件；`/tmp` 被大文件占满；core dump。
  4. **应急**：先清日志（用 `truncate -s 0` 或 logrotate，不要 `rm` 正在写的文件）、删旧 dump、清理 `/tmp`；再考虑扩盘（云盘在线扩容 + `resize2fs`/`xfs_growfs`）。
  5. **治本**：所有日志配轮转并限制总大小；把数据盘与日志盘、系统盘分离；对磁盘用量做监控，**容量 80% 告警、90% P1**；对大文件写入场景（MQ、ES）提前按"每天写入量 × 保留天数"算容量并留 30% 冗余。
  6. 兜底：应用侧要能容忍磁盘写失败（日志写失败不应导致业务异常，Logback 有 `ignoreExceptions` 默认 true，但要确认没被改成抛出）。
- **【常见误区】**：只看 `df -h` 不看 `df -i`；用 `rm` 删除正在写入的日志导致空间不释放；磁盘满后只重启服务不扩容（几分钟后又满）；把日志和数据放同一个盘导致"日志写满把数据库搞挂"。
- **【迁移话术】**：> "磁盘满排查两步：先分清是容量还是 inode，再找大目录。真正容易踩的坑是删了日志但空间不释放，那说明是句柄没关，得用 lsof +L1 确认。"

### Q16：网络抖动怎么排查？
- **【考察点】**：能否区分"我的问题"和"网络的问题"，是否知道把网络指标量化。
- **【回答要点（分步骤）】**：
  1. 先量化症状：是偶发丢包还是整段时间高延迟？只影响某个机房/某台机器/某个下游？用 `mtr <目标IP>`（结合 ping 与 traceroute，看每一跳的丢包率和延迟抖动）和 `ping -c 100 -i 0.2` 看延迟分布与丢包率。
  2. 服务器侧指标：`sar -n DEV 1`（收发包速率、丢包 `%ifdrop`）、`ss -s`（TCP 连接状态统计）、`netstat -s | grep -i -E 'retrans|drop|overflow'`（重传、丢包、队列溢出）、`ip -s link`（网卡层错误与丢包计数）。
  3. 应用侧表现与对策：RPC 超时率上升、TCP 重传导致 P99 抬高。**TCP 层抖动通常表现为长尾延迟，P50 正常**；可通过适当增大 TCP 连接复用、开启 keep-alive、把读写超时与重试配好（含指数退避 + 抖动）来削峰。
  4. 区分三类问题：
     - 真网络问题：所有走该链路的服务同时抖动 → 找网络/云厂商，提供 `mtr` 报告与时间点。
     - 对端问题：只有一个下游抖动 → 看对端是否扩容/发布，用熔断保护自己。
     - 自己问题：网卡打满（`sar -n DEV` 看 `txkB/s` 是否接近带宽上限）、连接数过多导致 `TIME_WAIT` 堆积（`net.ipv4.tcp_tw_reuse=1`、`somaxconn`、`tcp_max_syn_backlog` 调优）。
  5. 兜底：多机房/多可用区部署 + 就近路由；关键调用做多副本容错（同时请求两个下游取先返回的，如"备份请求"模式，注意会放大流量）。
- **【常见误区】**：把所有超时都归为网络问题（先看对端 P99 与自己的 GC）；用单次 `ping` 判断（要长时间统计）；忽略容器网络（cgroup 限流、`tc` 丢包、多租户争抢）；调大超时来"解决"抖动（只是把问题往后推）。
- **【迁移话术】**：> "网络抖动最难的是归因，所以我的第一步永远是量化：丢包率、延迟分布、重传数。如果只有一条链路有问题，就要拿着 mtr 数据找网络团队，而不是在应用代码里找。"

### Q17：服务每隔一段时间就卡顿一下，怎么排查？
- **【考察点】**：周期性问题的敏感度，"定时任务 / GC / 缓存过期 / 内核行为"几条主线是否都想得到。
- **【回答要点（分步骤）】**：
  1. 先确定周期：从监控图上量出卡顿发生的间隔（每分钟、每 5 分钟、整点、每天凌晨）。**周期本身就是最大的线索**。
  2. 按周期长度对号入座：
     - 秒级/分钟级：`cron` 任务、定时调度（`@Scheduled`、XXL-JOB）、`ThreadPoolExecutor` 定时刷缓存、`Thread.sleep` 循环里的批量任务。
     - 5~15 分钟：日志轮转（`logrotate` 压缩大文件占 I/O）、监控采集、`jstat` 类定时巡检脚本。
     - 整点/每天凌晨：数据同步、备份（`mysqldump` 会占满 I/O 并让 `%wa` 飙升）、报表跑批、缓存集中刷新（TTL 设成整点导致集中过期，见 Q9）。
  3. 逐层验证的工具：
     - 系统层：`vmstat 1` 持续看 `r`（运行队列）、`b`（阻塞）、`si/so`（swap）、`%wa`；`iostat -x 1` 看 `%util` 与 `await`；`sar -q 1` 看负载。
     - JVM 层：`jstat -gcutil <pid> 1000` 持续看是否有周期性 Full GC；`arthas dashboard` 挂着看 `gc` 列与线程数突变。
     - 进程层：`pidstat -u -d -p <pid> 1` 看该进程自己的 CPU 与 IO；`pidstat -w` 看上下文切换。
  4. 高频答案（面试官最想听到的）：
     - **周期性的 Full GC**：定时任务一次性加载大量数据进堆，触发 FGC，造成秒级 STW。
     - **定时任务与在线流量争抢资源**：跑批任务没做资源隔离，占满 CPU 或 DB 连接。
     - **缓存集中失效**：大量 key TTL 相同且集中在整点。
     - **内核行为**：`swap` 换页、`kswapd` 回收内存、`NUMA` 不均衡、CPU 频率调节（`cpufreq`）。
  5. 解法：跑批任务与在线服务物理隔离（独立机器/独立集群）；跑批限速（分批 + `Thread.sleep` 或令牌桶）；缓存 TTL 打散；DB 备份走从库且限制带宽；对周期性任务加"错峰"机制（打散到整个时间窗口）。
- **【常见误区】**：不画时间线直接猜代码；忽略"监控采集脚本自己就是元凶"；把跑批任务和在线接口部署在同一台机器上；只看应用日志不看系统层（`vmstat` 的 `%wa` 往往会直接指向答案）。
- **【迁移话术】**：> "周期性卡顿我有固定套路：先用监控图量出周期，再用周期长度去匹配嫌疑对象 — 分钟级先看定时任务，5 分钟以上先看日志轮转和监控采集，整点先看备份和缓存集中过期。"

### Q18：时钟回拨怎么处理？
- **【考察点】**：分布式 ID、时间戳依赖、锁超时等对时钟的敏感性，以及 NTP 的认知。
- **【回答要点（分步骤）】**：
  1. 先说清危害：时钟回拨会让**雪花算法 ID 可能重复**；让**基于过期时间的分布式锁提前失效**或永久不失效；让**幂等 token / 签名校验失败**；让**顺序消息乱序**；让**基于时间窗口的限流统计错误**。
  2. 发生原因：NTP/chrony 自动校时（尤其是机器刚启动、时钟漂移较大时是大步长回拨）；虚拟机迁移/暂停恢复；人工 `date -s` 改时间；容器与宿主机时钟不同步。
  3. **雪花算法的处理（最常被追问）**：
     - 检测到回拨后**小幅度回拨（如 ≤ 5ms）就自旋等待**，等时钟追上来再生成。
     - 回拨幅度较大则**直接抛异常/快速失败**，让上游重试，避免生成重复 ID — 宁可失败不可重复。
     - **备用 workerId 方案**：每台机器预留两组 `workerId`，检测到回拨时切换到备用 ID，用"另一条时间线"继续生成。
     - 更稳的做法：**ID 里不依赖机器时钟**，改用号段模式（Leaf-segment 从 DB 批量取号，双 buffer 预取）或 Redis `INCR`，从根本上绕开时钟问题。
  4. **分布式锁的处理**：用**看门狗续期**（Redisson `RLock` 的 `lockWatchdogTimeout`，默认 30s，每 10s 续一次）而不是单一 TTL；续期失败时主动让业务失败而不是假装持锁；关键业务在锁内再加**fencing token（递增版本号）**，即使旧持有者恢复也无法写入。
  5. **工程措施**：所有机器统一 NTP 源并监控偏移量（`chronyc tracking`、`ntpq -p`），偏移超过阈值告警；禁止大步长校时（配置 `makestep`/`maxslewrate` 做缓慢校正）；容器内不要自己跑 NTP，用宿主机时钟。
  6. 兜底：对时间敏感的逻辑尽量改成**单调时钟**（Java 里用 `System.nanoTime()` 做耗时计算而非 `currentTimeMillis()`）。
- **【常见误区】**：认为 NTP 只会往前调（NTP 会双向校正）；用 `System.currentTimeMillis()` 计算耗时（应使用 `System.nanoTime()`）；分布式锁只设 TTL 不看门狗（业务没跑完锁就过期了）；认为容器里时间一定准（容器与宿主机可能不一致）。
- **【迁移话术】**：> "时钟回拨对两类东西最危险：生成 ID 和基于过期的锁。我的原则是"宁可失败不可重复" — ID 生成器检测到回拨就快速失败，锁用看门狗续期加 fencing token，从机制上不依赖单次时间判断。"

### Q19：MySQL 主从延迟怎么排查和优化？
- **【考察点】**：复制原理、并行复制的理解，以及"业务上怎么容忍延迟"的视野。
- **【回答要点（分步骤）】**：
  1. 量化延迟：从库执行 `SHOW SLAVE STATUS\G` 看 `Seconds_Behind_Master`（**注意它只反映 SQL 线程与 IO 线程的时间差，主库无写入时会失真，会显示 0**）、`Relay_Log_Pos` 与 `Exec_Master_Log_Pos` 的差值、`Slave_SQL_Running_State`。
  2. 分析根因（按频率排序）：
     - **主库写入量大、从库单线程回放跟不上**：MySQL 5.7+ 开并行复制 `slave_parallel_workers=8`、`slave_parallel_type=LOGICAL_CLOCK`（8.0 为 `replica_parallel_*`）。
     - **大事务**：一个事务几万行变更，从库只能串行回放。拆大事务（分批 500~1000 行提交）。
     - **从库上有慢查询/大查询**：`SHOW PROCESSLIST` 看从库是否在跑报表；大查询会与回放争抢资源，造成 `MDL` 等待。
     - **从库硬件弱于主库**：磁盘 IOPS 不足，`iostat` 看 `%util` 饱和。
     - **无主键/无唯一键的表**：`ROW` 格式下每一行变更都要全表扫描定位，回放极慢 — 这是经典坑。
     - **DDL**：从库回放 DDL 只能串行，大表加索引会阻塞数小时。
  3. 排查命令：主库 `SHOW MASTER STATUS` 与 `SHOW BINLOG EVENTS`；从库 `SHOW SLAVE STATUS`、`SHOW PROCESSLIST`、`pt-heartbeat`（**比 Seconds_Behind_Master 准确得多**，它写心跳表并对比时间戳）。
  4. **业务侧优化（这才是加分项）**：
     - 写后立刻读的场景改为**强制走主库**（用注解/中间件路由，如 ShardingSphere 的 `HintManager`）。
     - 对延迟不敏感的业务（报表、搜索索引）走从库，并对延迟设上限（如 > 3s 就降级走主库或不展示）。
     - 用**缓存兜底**：写成功后写缓存，从库没同步也能读到。
     - 用 `semi-sync`（半同步复制）保证至少一个从库收到 binlog 再提交，减少"主库提交了但从库还没有"的窗口 — 代价是写延迟增加。
     - 用**组复制 MGR / 云上强一致只读**应对强一致读需求。
  5. 长期方案：分库分表降低单实例写入量；按业务拆分主库；大表补主键与唯一键；把跑批 SQL 移到专用从库（多级复制：主 → 中继 → 报表从库）。
- **【常见误区】**：只信 `Seconds_Behind_Master`（可能假 0）；认为加从库能降低延迟（加从库只提升读能力，不解决回放慢）；在生产从库上直接跑大报表；忽略"无主键表导致行回放全表扫"这个经典问题。
- **【迁移话术】**：> "主从延迟我分两头治理：技术上是并行复制、拆大事务、补主键；业务上是写后读强制走主库、非关键读容忍延迟并设上限。只做技术不做业务侧兜底，线上还是会出问题。"

### Q20：分布式锁失效了怎么排查？
- **【考察点】**：分布式锁的失效模式是否清晰，能否给出"失效了也不出错"的兜底设计。
- **【回答要点（分步骤）】**：
  1. 先分类失效模式（面试时能列出 5 条以上基本就满分）：
     - **锁提前过期**：业务执行时间 > TTL，锁自动释放，另一个线程进来了。修复：看门狗自动续期（Redisson）、业务侧加执行时长监控、TTL 按 P99 的 2~3 倍设置。
     - **误删别人的锁**：A 的锁过期后 B 拿到锁，A 执行完 `del` 把 B 的锁删了。修复：value 存唯一标识（UUID + 线程 ID），删除时用 Lua 原子校验 `if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) end`。
     - **加锁与设置过期非原子**：`setnx` 成功后进程挂掉，锁永不过期，形成死锁。修复：用 `SET key value NX PX 30000` 一条命令（或 Lua）。
     - **Redis 主从切换丢锁**：主节点写入锁后还没同步到从库就宕机，从库升主后锁丢失。修复：Redisson 的 **RedLock**（多主多数派加锁，但性能下降且仍有争议）、或改用 **ZooKeeper 临时顺序节点**（依赖 ZAB 多数派，天然避免该问题）、或数据库唯一键/乐观锁。
     - **时钟回拨**导致 TTL 判断异常（见 Q18）。
     - **锁粒度过大**：一把锁锁住整个业务，变成串行瓶颈，表现为"锁没失效但系统卡死"。
     - **未加锁成功就执行**：`tryLock` 返回 false 但代码没检查返回值。
  2. 取证手段：Redis `MONITOR` 短时采样（**生产慎用，会显著降性能**）或 `SLOWLOG`；给锁加 key 前缀并在 `INFO keyspace` / `--bigkeys` 看异常存在时间特别长的锁 key；客户端侧打点"加锁等待耗时、持锁耗时、续期次数"。
  3. **终极方案：不依赖锁的正确性**。锁只是性能优化，正确性必须由幂等保证：
     - 数据库唯一索引（最可靠，冲突即重复）。
     - 状态机 + 版本号乐观锁（`UPDATE ... WHERE status='待支付' AND version=?`，影响行数为 0 就说明被抢了）。
     - 业务上做"可重入 + 可重复执行"设计（如扣减用 `UPDATE stock=stock-1 WHERE stock>0`）。
  4. 选型对照：Redis 锁性能高、有丢锁风险；ZK 临时节点可靠性高、性能低且需处理会话超时；数据库唯一索引最简单可靠但并发能力有限；云上可用 etcd/Consul。**加锁粒度越小越好**（按业务 key 加锁而不是全局锁）。
- **【常见误区】**：只答"上 Redis 锁"不说失效场景；用 `setnx` + 单独 `expire`（非原子）；持锁做长耗时操作（RPC、大批量循环）；把锁当作一致性的唯一保证，从不做幂等；用 RedLock 却不了解其争议（Martin Kleppmann 与 antirez 的辩论要知道大概）。
- **【迁移话术】**：> "分布式锁我的判断标准是：锁只用来减少并发冲突，绝不能作为正确性的最后一道防线。最后一道防线永远是幂等 — 唯一索引加状态机，这样即使锁失效业务也不会错。"

## 2. 系统设计类（14 题）

### Q21：如何设计一个幂等接口？
- **【考察点】**：幂等语义的理解、token 机制、唯一索引兜底。
- **【回答要点（分步骤）】**：
  1. 先澄清语义：幂等 = **同一请求执行多次，业务结果与执行一次相同**（返回值可以不同）。要先问清幂等键是什么（订单号、请求流水号、业务主键），以及幂等窗口有多长（几分钟还是永久）。
  2. 方案一 **Token 机制（防重复提交）**：客户端先调 `getToken` 拿唯一 token（存 Redis，TTL 5 分钟）；提交时带上 token，服务端用 Lua 脚本原子 `GETDEL`/`DEL` 校验并通过才处理，删成功才允许执行。适合"用户手抖点两次"。
  3. 方案二 **唯一索引兜底**：把幂等键建成数据库唯一索引，重复插入抛 `DuplicateKeyException`，捕获后返回"已处理"。**最可靠、零额外组件**，必须要有。
  4. 方案三 **状态机 + 乐观锁**：`UPDATE order SET status='已支付', version=version+1 WHERE id=? AND status='待支付' AND version=?`，`affectedRows=0` 说明已被处理。
  5. 方案四 **去重表/幂等表**：`INSERT INTO idempotent(key, status) VALUES(?, 'PROCESSING')`，插入成功才继续；失败则查询状态决定返回什么。适合跨服务长流程。
  6. 方案五 **Redis setnx 前置拦截**：`SET idem:{key} 1 NX EX 86400`，返回 0 直接拒绝。性能最好但有丢锁风险（主从切换），**只能作为第一道快速过滤，不能作为唯一保证**。
  7. 工程要点：幂等键从**上游传入**而不是服务端自己生成；异步场景（MQ 消费）必须幂等（消息天然会重复）；**先落库后调下游**，并在下游调用失败时记录状态以便补偿（而不是直接回滚整个流程）。
- **【常见误区】**：只用 Redis 防重（丢锁就重复）；把"加了乐观锁"当成幂等（并发 0 不等于历史重放幂等）；幂等键用业务参数拼接且拼接顺序不稳定；对"查询类接口"也大动干戈做幂等（读本来就幂等）。
- **【迁移话术】**：> "幂等设计我的口诀是"键 + 表 + 状态机"：上游给幂等键，数据库唯一索引兜底，业务用状态机保证只能前进不能重放。Redis 只能做前置快筛，不能当唯一保证。"

### Q22：如何保证 MQ 消息不丢、不重？
- **【考察点】**：能否在"生产 → Broker → 消费"三段各自说清丢失点与解决办法。
- **【回答要点（分步骤）】**：
  1. **不丢 — 生产端**：发送后必须处理返回结果（RocketMQ `sendStatus != SEND_OK` 要重试，Kafka `producer.send()` 的 `Callback` 要检查异常）；重试仍失败则落本地"消息表"由定时任务补偿（本地消息表 / 事务消息）。同步发送比异步更可靠（异步要有回调兜底）。设 `acks=all`（Kafka）或 `SYNC_FLUSH`（RocketMQ 刷盘策略），且**`min.insync.replicas ≥ 2`**。
  2. **不丢 — Broker 端**：开启持久化（RocketMQ `flushDiskType=SYNC_FLUSH`；Kafka `replication.factor ≥ 3`、`unclean.leader.election.enable=false` 防止落后副本上位）；保证消息至少有 2 个副本落盘才算成功；监控磁盘与页缓存刷盘延迟。
  3. **不丢 — 消费端**：**先业务处理成功，再提交 offset / ack**。绝不能"先 ack 后处理"；处理失败或抛异常时不要 ack（RocketMQ 会自动重投，Kafka 用 `enable.auto.commit=false` + 手动 `commitSync`）。重试超过上限进死信队列（RocketMQ `%DLQ%`）并告警，人工介入而不是悄悄丢。
  4. **不重 — 消费幂等**：MQ 只能保证 at-least-once，**去重必须业务自己做**。手段：唯一索引、去重表（`msgId` 唯一键）、Redis setnx + TTL、状态机版本号。注意"消息重复"与"业务重试"要能区分。
  5. **顺序性**：需要顺序时按业务 key 选择分区/队列（RocketMQ 用 `MessageQueueSelector` 按订单号路由；Kafka 用 key 的 hash），并让**消费端单线程处理该队列**；不要在两个分区之间指望顺序。
  6. **可观测**：监控"生产失败率、发送 RT、Broker 堆积、消费 Lag、重试次数、死信量"六个指标；给消息加 traceId 串起全链路。
- **【常见误区】**：只说"开持久化"就认为不丢（生产端、消费端都会丢）；用异步发送且不看回调；先 ack 后处理（重复反而变成丢）；认为 MQ 自带去重；为追性能把 `acks=1` 且副本数 1。
- **【迁移话术】**：> "消息不丢要分三段看：生产端确认 + 重试、Broker 端多副本 + 同步刷盘、消费端先处理后 ack。不重只能靠业务幂等，因为 MQ 的语义上限就是 at-least-once。"

### Q23：如何防止重复支付？
- **【考察点】**：支付这类资损场景的设计严谨度，能否想到"最终一致 + 对账"而不是只讲加锁。
- **【回答要点（分步骤）】**：
  1. 说清风险：重复支付的直接后果是**用户被多扣钱**（资损），所以设计目标是"宁可多拦一千次，不可少拦一次"。
  2. **入口幂等**：一笔订单只有一条支付单（`order_id` 唯一索引）；支付单状态机 `INIT → PAYING → SUCCESS/FAIL`，只有 `INIT` 可以发起支付。
  3. **调用渠道的幂等**：给渠道传唯一的商户订单号（`out_trade_no` = 支付单号），渠道侧也按此去重；**超时不要立即重试**，而是先调用渠道的"查询接口"确认状态（超时可能是渠道已成功但响应丢了）。这是最容易被忽略的一点。
  4. **回调处理**：渠道回调可能重复、乱序，必须以"查询到的渠道终态"为准而不是回调报文；回调处理用唯一索引（`channel_trade_no`）去重；处理成功后返回渠道要求的成功报文，否则渠道会一直重推。
  5. **状态流转用乐观锁 / 条件更新**：`UPDATE pay_order SET status='SUCCESS' WHERE id=? AND status IN ('INIT','PAYING')`，影响行数为 0 就放弃处理，天然防并发重复。
  6. **分布式锁粒度**：按支付单号加锁（不是全局锁），并配合看门狗续期；锁失败直接返回"处理中"，让客户端轮询查询而不是重试支付。
  7. **对账兜底（最重要）**：每日与渠道做**双向对账**（我方流水 vs 渠道流水），发现"长款/短款/单边账"自动生成差错单，人工或自动发起退款/补单。**没有对账的支付系统一定出事故**，这句话面试官很想听到。
  8. **可观测**：同一订单的多次支付发起要告警；支付成功率、超时率、回调延迟 P99 都要有看板。
- **【常见误区】**：靠前端"按钮置灰"防重复（刷新就失效）；只加锁不做唯一索引；渠道回调一来就直接改状态而不校验金额与订单号；超时无脑重试导致用户被扣两次款；不做对账。
- **【迁移话术】**：> "支付类需求我的第一原则是"任何一层都可能重复，所以每一层都要幂等"，最后再用对账兜底 — 因为只要涉及钱，就必须假设前面的防线会漏，对账是最后一道兜底。"

### Q24：如何设计订单超时自动关闭？
- **【考察点】**：能否比较多种延时方案的优劣，且知道大数据量下怎么落地。
- **【回答要点（分步骤）】**：
  1. 先澄清：超时时间多长（15 分钟 / 24 小时）、订单量级（每天几千还是几百万）、**是否要求精确到秒**（绝大多数业务允许分钟级误差，这句话能救很多设计）。
  2. **方案一 定时任务轮询**：每分钟 `SELECT ... WHERE status='待支付' AND create_time < now()-15min LIMIT 1000`，批量处理。优点：实现最简单；缺点：扫表压力大（要建 `(status, create_time)` 联合索引）、时间精度受调度间隔限制。**量小（日订单 < 10 万）用它最实在**。
  3. **方案二 延时队列（推荐）**：RocketMQ 支持固定级别延时消息（1s/5s/…/2h，**RocketMQ 5.0 支持任意时间**）；RabbitMQ 用 `TTL + 死信队列`；Kafka 无原生延时需自建。下单时发一条延时消息，到期消费到就校验并关单。优点：精度高、不扫表；缺点：消息量大时要注意堆积与重复消费（必须幂等）。
  4. **方案三 Redis 过期 + 轮询/Keyspace Notification**：`SET order:expire:{id} EX 900`，监听 `__keyevent@0__:expired` 事件触发关单。**注意 Redis 过期事件不保证及时也不保证必达**，不能作为唯一手段；用 ZSet 按 score=过期时间戳存订单号 + 定时任务每 5s `ZRANGEBYSCORE + ZREM` 扫描可以做到比较精确（`ZREM` 返回值决定谁抢到，天然分布式去重）。
  5. **方案四 时间轮（Netty `HashedWheelTimer`）**：单机高效，但**重启丢任务**，只适合短时延时且任务可从 DB 重建的场景；要配合启动时全量扫描重建。
  6. 落地关键：**关单时再校验一次状态**（用户可能在临界点刚支付成功）；关单与支付用同一把按订单号的行锁/乐观锁，避免"刚支付就被关"；关单后要回滚库存与优惠券，并且**回滚本身也要幂等**。
  7. 兜底：以 DB 状态为准，延时消息只是触发器 — 消息丢了要有"兜底扫描任务"（比如每 10 分钟扫一次超时未关且创建时间超过 30 分钟的订单）修正。
- **【常见误区】**：一上来就说"用定时任务扫全表"（不说索引和分批）；用 Redis 过期事件当唯一方案；关单不加状态校验导致已支付订单被关；忘记回滚库存/优惠券；延时消息堆积后集中触发把 DB 打爆（要有消费限速）。
- **【迁移话术】**：> "超时关单我一般给两个方案：量小就定时任务加联合索引分批扫；量大就延时消息加兜底扫描。核心是关单时再校验状态 — 因为竞态一定存在，最终以 DB 状态为准。"

### Q25：如何设计灰度发布？
- **【考察点】**：流量染色的落地方式与回滚机制，是否想过"数据兼容"。
- **【回答要点（分步骤）】**：
  1. 明确目标：新版本先只影响一小部分流量，出问题能在秒级回滚，且**新旧版本可以共存**（数据与接口兼容）。
  2. **灰度维度（从粗到细）**：机器级（先发 1 台）→ 用户级（按 uid 取模 / 白名单）→ 流量比例（1% → 5% → 20% → 100%）→ 业务维度（按地域、渠道、版本、会员等级）。
  3. **流量染色与路由**：网关（Nginx/SLB/Spring Cloud Gateway）按 uid 或 header 计算哈希，决定转发到哪个版本；Kubernetes 用两套 Deployment + Service（标签选择器分组）或 Istio VirtualService 按权重路由。**同一用户的请求必须固定路由到同一版本**（否则用户体验割裂、缓存/会话混乱）。
  4. **数据兼容是重点**：只加字段不删字段、不改变已有字段语义；数据库变更必须**向前兼容**（先加新字段双写，灰度完成后再切读，最后再删旧字段 — "扩展/迁移/收缩"三步）；消息格式加版本号，消费端兼容新旧两种。
  5. **可观测与放量门禁**：灰度期间对比新老版本的错误率、P99、业务指标（下单成功率），任一指标劣化超阈值就自动回滚（Argo Rollouts / 自研发布平台的分析能力）。
  6. **回滚**：镜像保留上一版本，回滚只切流量不重建（秒级）；数据库变更是**不可逆项**，所以必须做成兼容的；写好回滚演练脚本并定期演练。
  7. 变体：**蓝绿发布**更干净（两套环境切流量，回滚快）但要双倍资源；**滚动发布**省资源但回滚慢；**特性开关（Feature Flag）**把"发布"和"上线"解耦，代码先发、功能后开，最灵活。
- **【常见误区】**：灰度只按机器分不按用户分（用户在不同请求间来回切版本）；数据库做了破坏性变更导致无法回滚；灰度期间不设自动回滚门禁，靠人盯监控；忘记灰度期间新旧版本共用的缓存与 MQ 消息格式兼容。
- **【迁移话术】**：> "灰色的关键不是流量切分，而是**数据兼容** — 只要数据库变更做成向前兼容的扩展-迁移-收缩三步，回滚就永远只是一次流量切换，风险可控。"

### Q26：如何组织一次全链路压测？
- **【考察点】**：压测的工程化程度，尤其是"影子表 / 流量标识 / 数据隔离"这些真实细节。
- **【回答要点（分步骤）】**：
  1. 定目标：压测要回答的问题 — 容量是多少（TPS/QPS 上限）、瓶颈在哪一层、扩容比例是多少、大促需要预留多少余量（通常按预估峰值 × 1.5~2 倍）。**没有目标的压测只是跑脚本**。
  2. 建模：基于线上日志统计接口占比与参数分布（用 `pt-query-digest` 或网关 access.log 做流量模型），**不要所有请求都打同一个商品 ID**（会造出不真实的热点）。
  3. **流量标识与数据隔离（最关键）**：
     - 压测流量带特殊 header（如 `X-Load-Test: true`）或独立 UID 段，全链路透传（HTTP header → RPC attachment → MQ 消息属性 → 线程上下文）。
     - 写操作路由到**影子表**（`order_2024_shadow`），缓存写**影子 key**（前缀 `shadow:`），MQ 发到**影子 topic**，保证压测数据不污染生产。
     - 下游第三方（支付、短信）用 mock 或"压测白名单账号"，**绝不能真发短信真扣款**。
  4. 环境与工具：JMeter / wrk / 自研压测平台（如阿里 PTS）；施压机与被压服务分离（避免压测机抢 CPU）；先单接口压测找单机上限，再做混合链路压测。
  5. 观测：压测期间必须同时看**应用层（GC、线程池、连接池、RT 分位数）、中间件层（DB QPS / 慢 SQL / 锁等待、Redis QPS / 大 key、MQ Lag）、系统层（CPU / 内存 / 网络 / 磁盘 IO）**，否则只能看到一个"系统挂了"而不知道挂在哪。
  6. 输出与收尾：容量水位表（QPS → CPU/RT 曲线，找出拐点）、瓶颈清单与优化项、扩容方案与成本估算；清理影子数据（脚本化，防止长期堆积）。
- **【常见误区】**：在线上直接压真实数据（污染生产库、给真实用户发短信）；只压一个接口不做混合场景；不在业务高峰期或不做流量模型；压测完不清理影子数据；压完不给结论（"压通了"没有意义，要说"单机 800 TPS，瓶颈在 DB 连接池"）。
- **【迁移话术】**：> "全链路压测的真正难点不是施压，而是**数据隔离和流量透传** — 我做的核心工作就是让压测流量带着标识穿过网关、RPC、MQ、缓存，全部落到影子表，这样才敢在线上压。"

### Q27：如何设计对账系统？
- **【考察点】**：资金/数据一致性思维，能否说清"单边账、长款、短款"等业务细节。
- **【回答要点（分步骤）】**：
  1. 目的：以**权威方数据为基准**，核对双方记录是否一致，发现差异并驱动修正。常见场景：支付与渠道对账、交易与账务对账、业务库与数仓对账、MQ 消费与源库对账。
  2. 数据采集：双方各出**T+1 日终文件**（渠道一般提供对账文件），或按时间窗口调用接口拉取；把文件/数据落到**对账库**（与业务库物理隔离），记录文件校验（MD5/行数）防止文件不完整导致误判。
  3. 核心比对算法：按业务主键（商户订单号 + 渠道流水号）**双向比对**，输出四类结果：
     - **一致单**：双方都有且金额状态相同 — 正常。
     - **我方有、对方无（短款/单边账）**：我方认为成功但渠道没记录 → 可能是我方错误更新，需要挂账核查。
     - **对方有、我方无（长款）**：渠道已扣款但我方未记账 → **资损风险最高**，需要补单。
     - **金额/状态不一致**：逐字段比对差异明细。
  4. **大数据量下的实现**：不要把两张表直接 `JOIN`（几千万行会拖死库）。做法：把两份数据**按主键排序后做归并扫描**（流式读取，内存 O(1)），或按主键哈希分桶后逐桶比对（每桶放内存用 `HashSet`）；也可以用 Hive/Spark 做离线比对。
  5. **差错处理**：生成差错单（含差异类型、金额、时间），进入人工/自动处理流程；自动补单必须可追溯（记录操作人/任务、原始数据快照）；**所有修正操作本身要幂等**。
  6. **时效性分级**：T+1 日终对账兜底；对资损敏感的做**准实时对账**（每分钟比对最近 5 分钟流水），把发现差异的时间从一天缩短到分钟级。
  7. 工程细节：对账任务要能**重跑**（幂等、可按日期重算）；对账结果要出准确率看板（差异率、差异金额、处理时长）；差异率超过阈值告警到值班群。
- **【常见误区】**：只做单向比对（只查"我方有对方无"，漏掉"对方有我方无"这种资损场景）；用全表 `JOIN` 实现（跑不完）；对账文件不校验完整性；差错单处理没有闭环与统计；把对账做成月初跑一次（失去及时性）。
- **【迁移话术】**：> "对账的框架是固定的：取双方数据 → 按主键双向比对 → 分出四类差 → 差错单闭环。技术难点在大数据量下的流式归并去重，业务难点在"对方有我方无"这类资损场景的及时处理。"

### Q28：如何做一次不停机的数据迁移（如分库分表）？
- **【考察点】**：双写、全量 + 增量、数据校验与灰度切流是否完整。
- **【回答要点（分步骤）】**：
  1. 先定方案边界：是"改表结构"还是"拆库拆表"？迁移期间**是否允许双写**？数据总量与增量速率？回滚要求（多久内必须能回滚）？这些决定了成本。
  2. **推荐路径（四阶段，可回滚）**：
     - 阶段一：**双写**（新老库同时写，注意用事务/本地消息表保证不丢，或以老库为准 + 补偿）；
     - 阶段二：**全量迁移**（用 `SELECT` 分批按主键游标搬，不要 `LIMIT offset` 深分页；限速避免影响线上；搬完记录位点）；
     - 阶段三：**增量追平**（用 binlog（Canal/DTS）或业务双写补上迁移期间的新数据，直到延迟接近 0）；
     - 阶段四：**灰度切读、再切写、最后下线老库**（先让 1% 流量读新库，逐步放大到 100%，观察一段时间再切写）。
  3. **数据校验（必做）**：全量搬完后逐行/抽样对比（按主键哈希分桶，比对行数与关键字段的校验和，如 `SELECT COUNT(*), SUM(CRC32(...))` 按桶比对）；增量阶段持续比对差异表并与业务方确认可接受范围。发现不一致要能定位到具体主键并补数。
  4. **工程细节**：迁移任务幂等（可重跑，用位点表记录进度）；源库压力控制（从从库迁、限流、避开高峰）；主键/唯一键在新结构下是否还成立；`IN` 查询、跨分片查询、事务、聚合等"原来能跑的 SQL"要在新架构下重新验证，往往需要改代码或退回到搜索/数仓。
  5. 切换与回滚：切流用开关（配置中心秒级生效）；回滚方案是"切回老库 + 反向双写"，所以**老库在观察期内不能删**；准备好数据比对脚本与应急联系人。
- **【常见误区】**：只做全量不做增量（遗漏迁移期间的新数据）；不做数据校验就切流；用深分页 `LIMIT offset` 迁移（越迁越慢）；迁移任务不可重跑，中断后只能从头开始；切完马上删老库。
- **【迁移话术】**：> "迁移我记四步：双写、全量搬、增量追、灰度切。每一步都可回滚，并且必须配数据校验 — 没有校验的迁移等于赌运气。"

### Q29：限流方案怎么选型？
- **【考察点】**：算法、实现位置、集群限流三个维度的取舍能力。
- **【回答要点（分步骤）】**：
  1. 先问清：限流的**目的**（保护自己还是保护下游）、**对象**（接口、用户、IP、租户）、**阈值**（单机还是集群）、**被限流时的行为**（拒绝、排队、降级返回）。
  2. 算法对比：
     - **计数器**：简单，但有"临界问题"（两个窗口交界处可能放过 2 倍流量）。
     - **滑动窗口**：把窗口切成小格统计，精度与内存折中（Sentinel 默认实现）。
     - **漏桶**：恒定速率流出，适合削峰填谷（多余请求排队或丢弃）。
     - **令牌桶**：允许一定的突发（有桶容量），**绝大多数在线业务的最佳选择**；Guava `RateLimiter` 是单机版。
  3. 实现位置：
     - **网关层**（Nginx `limit_req_zone`、Spring Cloud Gateway `RequestRateLimiter`、Sentinel 网关流控）：最外层，能挡住无效流量，**必须做**。
     - **应用层**（Sentinel/Resilience4j 注解、Guava）：细粒度到方法/资源，可按业务参数限流。
     - **中间件层**：DB 连接池上限、MQ 消费限速、Redis 命令级限流，做**最后一道保护**。
  4. **集群限流**：单机限流的总量 = 单机阈值 × 机器数，扩容后阈值会漂移。集群限流有两种落地：**集中式**（Redis + Lua 计数器，如 `INCR` + `EXPIRE`，或 Sentinel 的 token-server），优点是精确，缺点是 Redis 是单点与性能瓶颈；**分布式配额式**（把集群配额预先分给各机器，定期上报与再分配），性能好但瞬时可能不准。**通常先用单机限流 + 网关集群限流组合**，够用且简单。
  5. 阈值怎么定：压测得到单机容量，按容量的 60~70% 设阈值（留余量给突发）；按接口重要性分级（核心接口阈值高、非核心低）；大促前按预估峰值调整并演练。
  6. 被限流后的体验：返回明确错误码 + 提示（不要返回 500）；前端可降级（展示缓存旧值）；对 VIP 用户/关键业务做差异化配额。
- **【常见误区】**：只用 Guava `RateLimiter` 做单机限流却在集群里横向扩容（总阈值失控）；把限流阈值设成压测极限值（没有余量，一抖动就雪崩）；限流不做监控（限了不知道自己被限了）；限流与熔断混为一谈（限流是主动控量，熔断是被动止损）。
- **【迁移话术】**：> "限流选型我按三点决定：算法上用令牌桶（允许突发）、位置上网关 + 应用 + 连接池三层都做、集群场景用 Redis 集中计数或配额分配。阈值永远留 30% 余量。"

### Q30：如何保证缓存与数据库的一致性？
- **【考察点】**：能否说清"为什么先更库再删缓存"、延迟双删、以及最终一致的边界。
- **【回答要点（分步骤）】**：
  1. 先明确：缓存与 DB 是两套存储，**不存在免费的强一致**，工程上追求的是"最终一致 + 允许极短的脏读窗口"。
  2. **推荐方案：Cache Aside，先更新 DB，再删除缓存（而不是更新缓存）**。原因：删缓存比更新缓存更幂等、避免"两个并发写导致旧值覆盖新值"、也避免"更新了缓存但业务后面回滚"。
  3. 为什么不是"先删缓存再更库"：删除后到更新完成之间有窗口，读请求会把旧值重新加载进缓存，之后 DB 更新完成 → 缓存长脏。而"先更库再删缓存"的窗口极小（只在并发读且恰好在删之前加载完成时才有问题）。
  4. **延迟双删**：更新 DB 后先删一次缓存，`sleep` 一小段时间（如 500ms，覆盖主从同步 + 并发读的窗口）再删一次。代价是延迟与线程占用，**通常只在一致性要求高的场景用**。
  5. **更稳的方案**：
     - **订阅 binlog 删缓存**（Canal 订阅 → 发 MQ → 消费端删缓存）：把删缓存与业务解耦，重试与顺序都可控，是目前大厂主流做法。
     - **给缓存加短 TTL 兜底**（如 5 分钟）：即使删失败，最坏脏 5 分钟。
     - **双删 + 版本号**：写入时带上数据版本（时间戳/自增版本），读到的缓存版本低于 DB 版本则视为失效。
  6. 读写并发下的正确姿势：读请求发现缓存 miss 时，用**分布式锁或单飞**避免大量回源；写请求尽量缩短事务时间（**不要在事务未提交时删缓存**，否则并发读又会加载旧值）。
  7. 一致性级别选择：能容忍秒级不一致就用 Cache Aside + TTL；金融类关键数据（余额）**不要走缓存**或只用缓存做展示、读时强制走 DB；强一致要求高的场景用"缓存只做降级备份"（正常读 DB，DB 挂了读缓存）。
- **【常见误区】**：先更新缓存再更新 DB（并发下必脏）；只删一次不做任何兜底；缓存不设 TTL（脏了永远脏）；在事务里删缓存；误以为延迟双删能保证强一致（它只是缩小窗口）。
- **【迁移话术】**：> "缓存一致性我的答案是"先更库、再删缓存、加 TTL 兜底，重要数据用 binlog 订阅删除"。同时我会主动说明：这里追求的是最终一致，如果业务要求强一致，那就不该用缓存。"

### Q31：接口响应从 500ms 优化到 50ms，怎么做？
- **【考察点】**：性能优化的方法论 — 先度量、再定位、最后优化，而不是直接猜。
- **【回答要点（分步骤）】**：
  1. **先度量，禁止直接猜**。用 APM（SkyWalking/Pinpoint）或 APM 埋点把 500ms 拆成：网关 5ms + 应用逻辑 30ms + Redis 3ms + DB 400ms + 序列化/网络 60ms。**不拆开就无法优化**，因为优化不同层的成本差 10 倍。
  2. **DB 层（最常见的大头）**：加合适索引、去掉 `SELECT *`、消除 N+1 查询（批量 `IN` 或 `JOIN` 一次取回）、去掉 `count(*)` 大表统计、拆分大事务、把读流量走从库。
  3. **减少调用次数**：串行 RPC 改并行（`CompletableFuture.allOf` + 自定义线程池，注意超时与异常聚合）；多次单查改批量查；合并循环内的缓存访问为 `MGET`/`pipeline`。
  4. **缓存**：热点数据加缓存（本地 Caffeine + Redis 两级）；注意缓存击穿（见 Q10）与预热；把"每次请求都查的配置类数据"改为本地缓存 + 定时刷新。
  5. **序列化与网络**：大响应体做字段裁剪与分页；用更快的序列化（Protobuf/JSON 对比）；开启 HTTP 压缩；长连接复用（HTTP/2、连接池）；**减少网络往返次数**通常比序列化优化收益更大。
  6. **应用层**：去掉不必要的同步锁与 `synchronized` 大块代码；把非关键逻辑（写日志、发通知、统计）**异步化**（业务线程只提交任务）；避免在请求路径上做全量 `Collections.sort` 或大对象 `toString`（日志里打大对象是经典杀手）。
  7. **算法与数据结构**：把 O(n²) 的嵌套循环改成 `HashMap` 索引查找；避免在循环里 `String` 拼接；大数据量用流式处理而不是全量载入内存。
  8. **验证**：压测对比优化前后的 P50/P99/TPS，并确认没有把问题转移到别处（比如把 DB 压力转成 Redis 压力）；上线后用 APM 复核真实收益。
- **【常见误区】**：不度量直接改代码（优化了 5% 却以为解决了问题）；只优化平均 RT 不看 P99；用加机器代替优化（成本高且治标）；为了性能牺牲可读性却不写注释；优化完不做回归压测。
- **【迁移话术】**：> "性能优化我的第一句话永远是"先拿到火焰图或链路耗时"。500ms 里如果 400ms 在一条慢 SQL 上，那所有代码级优化都是浪费时间 — 定位比优化重要 10 倍。"

### Q32：如何设计一个分布式任务调度系统？
- **【考察点】**：调度与执行分离、故障转移、分片、幂等这几块是否完整。
- **【回答要点（分步骤）】**：
  1. 需求澄清：任务量级（几千还是百万）、调度精度（秒级/分钟级/cron）、是否需要**分片并行**、是否需要**依赖编排**（DAG）、失败重试与告警要求。
  2. 核心架构（以 XXL-JOB / ElasticJob 为参照）：**调度中心（Scheduler）+ 执行器（Executor）+ 注册中心 + 任务存储**。调度中心负责触发，执行器负责跑任务，二者通过 RPC 通信；执行器向注册中心（ZK/Nacos）注册心跳。
  3. **如何避免重复执行**：调度中心对每个任务加分布式锁（ZK 临时节点 / DB 行锁），只有抢到锁的调度实例才触发；执行器侧再用"任务实例唯一键 + 状态机"保证同一次触发只执行一次。**调度器的单点用主备**（ZK/etcd 选主），备机接管超时未心跳的主机任务。
  4. **分片执行**：把一个任务拆成 N 片（如按用户 ID 取模），每台执行器领 1~N 片并行跑，总耗时降到 1/N。分片规则要支持动态扩容（分片总数固定，执行器数量变化时重新分配分片）。
  5. **失败处理**：任务超时（心跳丢失判定失败）→ 触发重试（固定次数 + 退避）；重试仍失败 → 告警（企微/钉钉/电话）；**重试必须保证任务幂等**，否则会重复处理数据。可选：任务阻塞策略（丢弃/覆盖/串行等待）。
  6. **可观测与运维**：任务执行日志在线可查（按日志 ID 关联）；执行耗时、成功率、失败次数、积压量看板；**支持手动触发、暂停、终止、重跑历史日期**（补数场景必备，且重跑要幂等）。
  7. 规模化的坑：任务集中触发（如全部 0 点执行）会造成惊群，要做**错峰**（打散到时间窗口）；执行器大批量同时拉取任务会打爆调度中心（要限流 + 分页）；DB 存任务状态要注意行锁竞争（用 `SELECT ... FOR UPDATE SKIP LOCKED` 或状态机乐观锁）。
- **【常见误区】**：用单机 `@Scheduled` 直接当分布式调度（多实例重复执行）；任务不幂等但配了自动重试；0 点集中触发不做错峰；任务失败只写日志不告警；不支持补数重跑（线上赔不起）。
- **【迁移话术】**：> "调度系统的核心矛盾是"谁负责触发"和"怎么保证只触发一次"。标准解法是调度与执行分离、抢锁决定触发权、任务幂等兜底重试，最后配上补数与告警能力。"

### Q33：分布式 ID 生成方案怎么选？
- **【考察点】**：各种 ID 方案的特性和取舍，尤其是时钟回拨与趋势递增问题。
- **【回答要点（分步骤）】**：
  1. 先明确需求：**是否需要趋势递增**（影响 MySQL 写入性能与分页）、是否需要**有意义**（如含时间、机房）、QPS 量级、是否允许重复（绝不允许）、ID 长度限制。
  2. **UUID**：最简单、无中心；缺点是无序（作为 MySQL 主键会导致页分裂，写入性能差）、占空间（36 字符/16 字节）、不可读。适合做 traceId、文件 key，**不适合做主键**。
  3. **数据库自增（含号段模式）**：单表自增最简单但单点、扩展难；**号段模式（Leaf-segment）**是主流 — 从 DB 一次取 1000 个号放内存发号，用完再取，DB 压力降到 1/1000；用**双 buffer**（当前号段用到 10% 时异步预取下一段）避免取号时抖动。
  4. **雪花算法（Snowflake）**：64 位 = 1 位符号 + 41 位时间戳（可用 69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（每毫秒 4096 个）→ **单机 400 万 QPS**，趋势递增、本地生成无网络开销。缺点：依赖机器时钟（回拨会重复，见 Q18）、机器 ID 需要分配与管理（容器环境下 IP 不稳定，要用 K8s StatefulSet 序号或 ZK 注册分配）。
  5. **Redis `INCR`**：`INCR id:order`，性能高（单机 10 万+ QPS）、天然递增；缺点是依赖 Redis 可用性、持久化配置不当会丢号（AOF `everysec` 可能丢一秒数据，重启后可能重复发号）。
  6. **美团 Leaf / 百度 UidGenerator**：Leaf 提供号段与雪花两种模式，UidGenerator 基于雪花但用"借用未来时间"解决回拨，可以直接借鉴其设计。
  7. 选型建议：**中小规模用号段模式（简单、可靠、趋势递增）**；超高 QPS 且能管好机器 ID 用雪花；对 ID 无要求（日志、追踪）用 UUID；金融场景考虑"业务前缀 + 日期 + 序列"的可读 ID。
- **【常见误区】**：UUID 直接做 MySQL 主键（页分裂、性能差）；雪花算法不处理时钟回拨；机器 ID 用随机数（多实例冲突）；Redis 发号不开 AOF 或不做持久化保障；忘记"分库分表后 ID 要能反解出分片"（如雪花 ID 中的时间戳可以用来定位历史分片）。
- **【迁移话术】**：> "ID 方案我按三个问题选：要不要趋势递增、QPS 多大、能不能容忍中心化依赖。一般业务用号段模式就够，超高并发用雪花但必须处理时钟回拨和机器 ID 分配。"

### Q34：如何设计一个秒杀系统？

- **【考察点】**：高并发设计的综合能力 — 分层过滤、削峰、库存扣减、防刷。
- **【回答要点（分步骤）】**：
  1. 澄清目标：**峰值 QPS**（如 10 万）、商品数（如 100 个 SKU）、库存量、**是否允许超卖**（不允许）、是否需要排队公平性、防刷要求。
  2. **分层过滤（核心思想：把无效流量尽量挡在最外层）**：
     - 客户端：按钮置灰 + 答题/验证码 + 本地限流；前端静态资源走 CDN。
     - 网关层：按 uid/deviceId 限流（同一用户 1 秒 1 次）、黑名单、验证码校验。
     - 应用层：内存标记（本地缓存存"已售罄"标志，售罄后直接拒绝，不打 Redis）。
  3. **削峰**：请求先写入 MQ（或 Redis List 做队列），后端按自身能力匀速消费，**把瞬时 10 万 QPS 转成可控的 5000 TPS**。用户侧返回"排队中"，前端轮询结果。
  4. **库存扣减**：
     - **Redis 预扣减**（Lua 脚本保证"查库存 + 扣减 + 记录用户"三步原子）：`if tonumber(redis.call('get', KEYS[1])) > 0 then ... end`，返回 1 表示预扣成功。
     - **DB 最终扣减**用条件更新 `UPDATE stock SET num=num-1 WHERE sku_id=? AND num>0`，影响行数为 0 则失败 — **这条 SQL 是防超卖的最终保障**。
     - 绝不用"先查后减"（并发下必超卖），也不用悲观锁（性能差）。
  5. **幂等与防重复下单**：一个用户一个商品只能下一单（`(user_id, sku_id)` 唯一索引 + Redis 去重），MQ 消费必须幂等。
  6. **数据一致性**：Redis 预扣成功但 DB 扣减失败（如超时）要有**补偿**（对账任务或重试队列回滚 Redis 库存）；大促后做一次对账，把 Redis 与 DB 库存对齐。
  7. **兜底**：库存服务降级（Redis 挂了直接返回"活动火爆"，不要打 DB）；限流阈值 + 排队超时（排队超过 N 秒直接失败，避免用户无限等待）；压测验证并预留 2 倍余量。
- **【常见误区】**：所有流量都打到 DB（`UPDATE ... WHERE num>0` 也扛不住 10 万 QPS）；用"先查询再扣减"（超卖）；不做幂等导致一人多单；Redis 与 DB 库存长期不一致又无补偿；只讲限流不讲排队削峰。
- **【迁移话术】**：> "秒杀的本质是"分层过滤 + 异步削峰 + 原子扣减"：能在客户端和网关挡住的绝不进应用，能进队列的绝不直接打 DB，最后的库存扣减一定是 Redis 原子操作加 DB 条件更新双保险。"

## 3. 开放与软技能类（26 题）

### Q35：怎么做技术选型？

- **【考察点】**：是否有结构化的选型方法，而不是"我觉得 XX 好"。
- **【回答框架】**：**四步法** — ①澄清约束（团队技术栈、运维能力、预算、交付时间、是否已有类似组件）；②列出候选并定评估维度（功能匹配、性能、社区活跃度、稳定性、学习与运维成本、生态与长期维护风险）；③用 POC 做最小验证（真实场景跑一遍，不只看文档基准测试）；④给出建议并说明**放弃的选项及原因**（体现权衡）。
- **【示例话术】**：> "选型我一般不追新。先看团队能不能维护，再看是否满足未来两年的量级，最后用一个两天的 POC 验证关键路径。选完我会把淘汰方案的理由也写进评审文档，避免后来人重复讨论。"
- **【常见误区】**：只讲某个组件的优点不讲代价；因为"大厂在用"就选（忽略自身规模与运维能力）；不做 POC 直接上；选型只由一个人拍板不经评审。

### Q36：技术方案评审怎么组织？

- **【考察点】**：能否把一个方案讲清楚并驱动团队达成共识。
- **【回答框架】**：评审前发**方案文档**（含背景、目标与指标、总体设计、核心流程时序图、数据模型、接口定义、容量估算、异常与降级、上线与回滚、排期与人力）给人提前看；评审会上先讲**问题与约束**再讲方案，重点过 3 处：数据一致性、容量瓶颈、失败场景；把争议点当场定责任人会后跟进；结论写成纪要（决定、待办、负责人、时间点）。
- **【示例话术】**：> "评审前我会把文档发出去让大家带着问题来，会上不念文档，只讨论分歧点。会议结束必须产出决定和待办，否则这次评审就白开了。"
- **【常见误区】**：开会现场讲文档（浪费所有人时间）；只讲正向流程不讲异常与回滚；有分歧不决策放任拖；没纪要、没责任人、没时间点。

### Q37：如何推动跨团队协作？

- **【考察点】**：协作与影响力，能否在没有汇报关系的情况下推进事情。
- **【回答框架】**：①先把"我的需求"翻译成"共同目标"（对业务/用户的价值，而不是"我这边要做完"）；②找到关键决策人并拉齐预期（用一页材料说清背景、诉求、时间、不做的后果）；③把接口与责任边界写清楚（谁提供什么、什么格式、什么时候给、超时怎么办），避免"口头约定"；④建立可见的进度同步机制（周会/群公告/共享看板）与升级路径（阻塞超 N 天就升级到双方主管）；⑤给对方留功劳与便利（帮对方减少工作量，比如我方先做好适配层）。
- **【示例话术】**：> "跨团队推动我靠三件事：把需求变成共同收益、把接口写成白纸黑字、把进度放到双方都能看到的地方。真卡住了我会及时升级，但升级前一定先当面沟通。"
- **【常见误区】**：靠 IM 催促推进；需求描述含糊，等对方猜；只提要求不提供便利；出问题就投诉对方；一直不升级导致项目延期。

### Q38：需求变更怎么处理？

- **【考察点】**：是否有变更管理意识，能否平衡灵活性与交付承诺。
- **【回答框架】**：①**先接住情绪与诉求**，不急着拒绝，问清"为什么变、不变会怎样、什么时候必须要"；②评估影响（工作量、对其他需求的影响、发布窗口、测试与上线成本）并**量化**给出选项；③给方案组合（本期做最小可用版本 + 下期补齐；或换出等量的其他需求；或加班但要说明质量风险）；④走变更流程留痕（变更单、评审、知会相关方），并由**产品/项目经理做优先级决策**（而不是开发自己扛）。
- **【示例话术】**：> "需求可以变，但排期和范围要一起变。我会给出三个选项：加人加时间、砍掉别的需求、或者这次只做最小版本。决策交给你，但风险我会写清楚。"
- **【常见误区】**：一口答应然后延期交付；直接说不做（不提供替代方案）；不评估影响就承诺时间；变更不留痕导致后期扯皮；自己默默加班消化所有变更。

### Q39：你怎么带新人？

- **【考察点】**：是否有培养意识与可复用的方法，而不是"我带过"。
- **【回答框架】**：①**首个任务设计**：给一个"可独立完成、结果可见、能在两天内交付"的小需求，帮他建立正反馈与对代码库的熟悉；②**给上下文而不是给答案**：讲清业务背景、系统边界、约定规范，遇到问题先让他给方案再讨论；③**建立反馈节奏**：每周一次 1v1 看进度与困惑，代码 Review 里指出问题并说明原因（不只说"这样写不好"）；④**逐步放权**：从改小 bug → 独立负责模块 → 参与方案设计，同时明确"什么时候必须找人确认"的红线；⑤给新人一份**上手文档**（环境搭建、常用命令、模块地图、常见坑），并让他在使用中不断补充。
- **【示例话术】**：> "我带给新人的第一课是"先想方案再动手，卡住 30 分钟就必须问"。我的目标不是帮他写完，而是让他三个月后能独立负责一个模块。"
- **【常见误区】**：把杂活全丢给新人；只讲怎么做不讲为什么；要么不管要么事无巨细盯着；Review 只说问题不说原因；不带新人了解业务背景。

### Q40：线上故障复盘怎么做？

- **【考察点】**：是否有"对事不对人"的复盘文化，以及能否产出防复发机制。
- **【回答框架】**：①**先恢复业务再复盘**，不要边救火边追责；②复盘会议必须有**时间线**（谁在几点发现、做了什么、几点恢复），用监控与日志还原而不是凭记忆；③区分**直接原因、根本原因、系统性原因**（直接原因可能是"发布了 bug"，根本原因是"没有灰度也没有回滚门禁"）；④产出可执行项：每条改进都要有责任人 + 截止时间 + 验证方式（加监控、加校验、改流程、加演练），并在下次复盘时回看完成情况；⑤结论要能沉淀成文档与告警规则，且**鼓励上报**（上报受表扬，隐瞒受处理）。
- **【示例话术】**：> "我复盘的底线是"不追责到人，只追责到机制"。一次故障至少要产出一条新的监控或自动化校验，否则同样的坑还会再踩一次。"
- **【常见误区】**：复盘会开成批斗会；只写"加强责任心"这类无法执行的改进项；只有直接原因不挖系统性原因；改进项没有责任人和时间；同一故障半年内复发。

### Q41：如何平衡业务交付与技术债？

- **【考察点】**：务实程度，是否既懂业务压力又能持续改善系统。
- **【回答框架】**：①**承认技术债是投资而非道德问题** — 有时为了抢占窗口期先上线是正确决策，关键是有记录、有偿还计划；②建立**债务台账**（记下债务内容、风险、偿还成本、触发条件），做到可见可排序；③**把偿还绑定在业务需求上**（做支付功能时顺带把支付模块的重复代码抽掉，即"顺手还债"，成本最低）；④**用数据说话**：把技术债折算成可感知的业务指标（线上故障次数、新增功能的平均开发时长、发布失败率），用这些数据去争取排期；⑤守住**红线**：安全、数据一致性、可回滚能力不能欠债，其他都可以谈。
- **【示例话术】**：> "我不会说"没时间还技术债"，我会说"这块代码上个月导致两次故障，每次影响 N 个用户，重构需要 5 人日 — 这是投入产出比"。用业务语言沟通，排期就更容易拿到。"
- **【常见误区】**：要么纯理想主义（不给业务让步）、要么永远妥协（系统持续恶化）；技术债不记录，只存在于开发脑里；把重构当 KPI 而不管业务收益；在红线上妥协（安全、一致性）。

### Q42：怎么做一次技术分享？

- **【考察点】**：表达与影响力，能否把复杂问题讲给不同水平的人听。
- **【回答框架】**：①选题**小切口深挖**（"我们如何把接口 P99 从 800ms 降到 80ms"胜过"MySQL 全解"）；②结构：**问题 → 过程 → 结论 → 可复用清单**（听众最关心"我能不能用"）；③用真实数据与代码片段，不讲空话；准备一个能现场演示的 demo 或图；④控制时长（20 分钟讲核心，留 10 分钟提问）；⑤分享后沉淀成文档进知识库，并收集反馈改进下一次。
- **【示例话术】**：> "我分享的原则是"讲我踩过的坑，而不是讲文档"。文档大家都会查，但踩坑的细节和权衡过程只有做过的人才知道。"
- **【常见误区】**：题目太大讲不完；纯念 PPT；只讲成功不讲失败与代价；不留提问时间；分享完不沉淀文档，人走了知识就没了。

### Q43：你怎么看待加班与压力？

- **【考察点】**：稳定性与职业态度，是否会走极端。
- **【回答框架】**：①先表明**能扛关键期**（大促保障、上线攻坚、线上故障），并给出真实经历（如"大促前两周我参与了容量评估和压测值班"）；②说明自己的**效率观**：优先保证关键路径、砍掉低价值事项、把重复劳动自动化（"我写过脚本把发布检查从 30 分钟降到 2 分钟"）；③对**长期无意义加班**的态度要理性表达 — 不加评判地说"我更倾向于用流程和自动化解决长期加班"，而不是抱怨公司；④提压力的**健康管理方式**（运动、拆解任务、及时沟通而不是硬扛）。
- **【示例话术】**：> "关键节点该顶我一定顶，我经历过连续两周的大促保障。但平时我更愿意花时间做工具和流程，把加班的原因消掉 — 因为靠加班解决长期问题是不可持续的。"
- **【常见误区】**：说"我从不加班"（让人觉得不吃苦）；或说"我随时可以 007"（显得没有判断力，也可能被当廉价劳动力）；抱怨前公司加班多（负面情绪传递）；拿不出具体经历只表态。

### Q44：你最有成就感的一件事？

- **【考察点】**：价值观与驱动力，以及能否讲清"我做了什么"而不是"团队做了什么"。
- **【回答框架】**：用 **STAR + 量化**：情境（业务背景与难度）→ 任务（我的具体职责）→ 行动（我做的关键决策与技术方案，突出**只有我能做**的部分）→ 结果（数字：性能提升多少、成本省多少、故障减少多少、业务增长多少）→ 收获（沉淀了什么方法/工具）。
- **【示例话术】**：> "最有成就感的是我把订单查询接口的 P99 从 1.2 秒降到 120 毫秒：先做链路拆解定位到三处慢 SQL 和一次 N+1 查询，通过加联合索引、改批量查询、加两级缓存解决，QPS 从 800 提到 3500，之后大促再没出现过超时告警。"
- **【常见误区】**：把团队成果说成自己一个人的（一追问细节就露馅）；只讲技术动作不讲业务结果；拿不出具体数字；选一件太小的事当成就；全程只说"我们"，听不出你个人的关键决策。

### Q45：讲一次失败的经历？

- **【考察点】**：诚实度、反思深度，以及是否真的从失败中学到东西。
- **【回答框架】**：①选一个**有真实后果但已被你修复**的案例（不要选"我太追求完美"这种伪失败）；②说清**我的责任**（不甩锅给他人/需求/环境）；③关键在**反思与改变**：这次之后你建立了什么机制（如"我现在所有变更都先准备回滚脚本"）；④结尾给正向结果（为了避免复发做了什么，后来效果如何）。
- **【示例话术】**：> "我上线过一个没做灰度的小改动，导致一批用户下单失败。根因是我只测了主流程没测异常分支，而且当时没有回滚预案。之后我推动了两个变化：一是所有变更必须灰度 1% 流量，二是我自己写了一个发布检查清单，把回滚脚本列入必填项 — 这个清单后来成了团队标准。"
- **【常见误区】**：说"我没失败过"；把失败归因于别人或公司；选一个后果太严重无法收场的案例；只讲失败不讲改变；假装把优点当缺点说。

### Q46：你怎么学习新技术？

- **【考察点】**：学习能力与自驱力，是否有可验证的方法而不是"我平时看看博客"。
- **【回答框架】**：①**以问题驱动**：遇到具体问题（如"为什么 G1 停顿比 CMS 短"）再深入，而不是盲目刷教程；②**官方文档优先**（一手资料胜过二手博客），辅以源码与规范；③**动手验证**：写 demo、压测、看监控/火焰图，把结论落到自己项目；④**输出倒逼输入**：写文档/做分享/回答同事问题，讲一遍才真正懂；⑤**追踪与沉淀**：关注官方 release notes 与社区动态，把学到的东西整理进团队知识库。
- **【示例话术】**：> "我学新东西的路径是"文档 → demo → 用在一个真实小场景 → 写成文档给别人讲"。比如学 Arthas 就是因为我排查一个线上问题需要，学完直接写成了团队的排查手册。"
- **【常见误区】**：只说"看视频/买课"（没有验证手段）；追新名词但说不清原理；学完不落地；认为学习必须在工作之外（可以在项目中边做边学）。

### Q47：为什么离职 / 为什么看机会？

- **【考察点】**：稳定性预期与职业成熟度，是否会成为隐患。
- **【回答框架】**：①**只讲向前看的理由**（想要更复杂的业务场景、更大的技术挑战、更规范的工程体系），不讲前公司是非；②把离职原因和你应聘这个岗位的**匹配点**连起来（"你们这里的订单量级和我在做的高并发方向一致"）；③对前公司保持**感激与客观**（承认学到了什么）；④如果涉及客观原因（业务被砍、组织调整、通勤），可以简要如实说明，不展开细节、不带情绪。
- **【示例话术】**：> "我在现在的团队成长很多，从 0 到 1 参与了整个交易链路。但目前业务趋于稳定，我想去面对更大的流量和更复杂的分布式场景，这也是我关注你们这个岗位的原因。"
- **【常见误区】**：抱怨领导/同事/加班/薪资（最容易被记上一笔）；说"钱少"是唯一理由；原因与岗位毫无关系；讲得过于情绪化或细节过多；频繁跳槽还给出牵强理由。

### Q48：你的职业规划是什么？

- **【考察点】**：职业成熟度、稳定性，以及规划是否与岗位匹配。
- **【回答框架】**：**分时间尺度讲，并且落在技术纵深上** — 1 年内：熟悉业务与技术栈、独立负责一个模块并做到稳定；2~3 年：成为某个方向（高并发、中间件、稳定性治理）的技术骨干，能主导方案设计与跨团队推动；3~5 年：具备系统架构与技术决策能力，能带小团队并对结果负责。避免说"想转管理"或"想创业"这类与岗位错位的话。
- **【示例话术】**：> "短期我想先把你们这条交易链路吃透，做到能独立负责；中期希望在稳定性与高并发方向成为团队里能拍板的人，比如主导容量规划和全链路压测。长期我更希望走技术专家路线，通过技术方案影响业务结果。"
- **【常见误区】**：说"没想过"（显得没有自驱）；规划与岗位无关（比如应聘后端却说想做大数据）；空谈"想成为架构师"却不说路径；说得太具体太死（显得不灵活）。

### Q49：和产品/业务意见不一致怎么办？

- **【考察点】**：沟通方式与立场，是否能同时理解业务与技术。
- **【回答框架】**：①**先理解诉求背后的目标**（"为什么现在要做"往往能发现真问题是运营策略而不是功能）；②**用数据与事实代替情绪**（给出性能、成本、风险的具体数字，比如"这个方案会让下单 RT 增加 200ms，转化率可能下降"）；③**给替代方案**（技术上做不到 A，但能用 B 达成 80% 目标）；④**明确决策权归属**：技术风险我说清，业务优先级产品定，我执行并注明风险；⑤事后回看（当时判断对不对，沉淀成经验）。
- **【示例话术】**：> "我的原则是"技术问题我负责讲清楚风险，业务取舍由产品决策"。我不会只说不行，一定会给一个成本更低的替代方案让他选。"
- **【常见误区】**：用技术术语压产品；直接说"做不了"；闷头做完再抱怨；越权替业务做决定；争论过程中上升到人身评价。

### Q50：你的方案被面试官/同事质疑时怎么办？

- **【考察点】**：抗压与思辨能力，是否愿意修正观点。
- **【回答框架】**：①**先接住**（"这个点提得好，我确实没考虑到"），不要条件反射式辩护；②**复述对方问题**确认理解一致（避免各说各的）；③**区分事实与偏好**：能用数据/实验回答的就给数据，属于取舍的就摆出双方代价；④**明确承认不确定的部分**（"这里我只有理论判断，实际需要压测验证"）；⑤如果对方是对的，**大方修改结论并说明新理由** — 这比硬撑更加分。
- **【示例话术】**：> "您说的这个并发场景我确实漏了。我重新捋一遍：如果按您说的加锁，吞吐会掉一半；但如果不加锁就要承担重复写入。我更倾向用唯一索引兜底而不是加锁，因为锁的代价更高 — 不过这里我的判断还需要压测数据支持。"
- **【常见误区】**：立刻反驳或沉默；为了面子死撑错误结论；被质疑就推翻自己全部方案（表现不稳定）；反复说"我们当时就是这么做的"（拿现状当理由）。

### Q51：做技术决策时如何收集证据？

- **【考察点】**：是否数据驱动，能否区分"观点"与"证据"。
- **【回答框架】**：①明确**决策问题**（要回答什么：选 A 还是 B、能不能上线、阈值定多少）；②收集**三类证据**：生产数据（监控、链路追踪、慢日志的真实分布）、基准测试（自己压测的 P99/TPS，而非文档宣传值）、小规模实验（灰度、POC、可回滚的试运行）；③**先定判定标准**再测（"P99 < 200ms 且错误率 < 0.1% 就通过"），避免事后解释数据；④记录决策与理由（ADR），留待未来复盘。
- **【示例话术】**：> "我定技术方案前会先写下"什么结果算通过"，再去压测。否则跑完一堆数据，很容易挑出有利于自己原方案的那几行 — 那就是自欺欺人。"
- **【常见误区】**：用别人博客的基准测试当证据；先有结论再找数据；只测平均值不测长尾；不记录决策理由（换个人就推翻重来）。

### Q52：如何向上汇报进度与风险？

- **【考察点】**：沟通效率与风险意识，是否让领导"省心"。
- **【回答框架】**：①**结论先行**：一句话说状态（正常/有风险/已延期），再给细节；②用**数字与时间点**（"完成 70%，剩余 3 人日，预计周三联调"）；③**主动报风险要带方案**（"如果下游周三前给不了接口，我会先用 mock 并行开发，风险是联调时间压缩到 1 天"），而不是只抛问题；④**分级**：可自己解决的在本周报里提一句，需要上级协调的立刻当面说；⑤保持节奏固定（周报/日会），不要"憋大招"式汇报。
- **【示例话术】**：> "我汇报的习惯是三段：现在到哪了、下一步什么时候、有什么需要你帮忙的。有风险我一定提前说，并且带一个我已经想好的应对方案。"
- **【常见误区】**：报喜不报忧直到延期才说；只讲困难不讲方案；用技术细节淹没重点；汇报频率不固定，领导不知道进展；把小事也升级（消耗信任）。

### Q53：线上事故你是责任人，怎么办？

- **【考察点】**：责任担当与应急处置的成熟度。
- **【回答框架】**：①**第一优先是止损**（回滚/降级/摘流量），不是解释原因；②**同步信息**：拉应急群、通知业务方与上级、明确谁在做什么（避免多头指挥）；③**保留现场**（日志、dump、配置、发布记录）再操作，避免"一重启什么都没了"；④**事后主动复盘并承担**，把直接原因、根本原因、改进项写清，主动提出机制上的改变；⑤对受影响的用户/业务，主动推动补偿方案。
- **【示例话术】**：> "出事时我只做三件事：止损、同步、留证据。原因和责任我做完了再讲。复盘完我会主动把改进项落到自己身上 — 比如这次之后我加了发布前必查的回滚清单。"
- **【常见误区】**：先解释后止损；隐瞒或淡化影响；把责任推给测试/运维/需求方；复盘时只写"加强意识"；不主动提补偿或改进。

### Q54：你怎么做代码 Review？

- **【考察点】**：工程素养与协作方式，是否只是走形式。
- **【回答框架】**：①**关注点排序**：正确性与边界（空值、并发、幂等、事务范围）→ 安全（SQL 注入、越权、敏感信息打日志）→ 性能（循环内查询、大对象）→ 可读性与命名 → 测试覆盖；②**给理由不给命令**（"这里建议用 `ConcurrentHashMap`，因为读多写少且要被多线程访问"）；③**区分阻塞与非阻塞**（必须改 vs 建议改，明确标记，不用个人偏好卡流程）；④**控制规模**（单次 PR 不超过 400 行，超了要求拆分）；⑤Review 后用自动化把共性规则固化（静态检查、Checkstyle、ArchUnit），减少重复人工评审。
- **【示例话术】**：> "我 Review 时会区分"必须改"和"可以更好"。涉及正确性、并发、安全的一律阻塞；风格问题我会说清理由，但不卡流程 — 更重要的是把重复出现的问题变成规则和工具。"
- **【常见误区】**：只挑格式与命名（漏掉并发和事务问题）；只说结论不说原因；用个人风格当标准；PR 太大无法认真看；Review 拖延导致别人阻塞。

### Q55：如何保证交付质量？

- **【考察点】**：是否有全流程质量意识，而不是"测试会测"。
- **【回答框架】**：①**测试左移**：需求评审时就确认验收标准与边界条件，把"异常场景清单"写进需求；②**分层测试**：单元测试覆盖核心算法与边界（不追求覆盖率数字），集成测试覆盖 DB/Redis/MQ 交互（用 Testcontainers 或 H2 需谨慎），关键链路做自动化回归；③**质量门禁**：CI 卡住编译失败、单测失败、静态检查不通过、覆盖率跌破阈值；④**发布管控**：灰度发布 + 可回滚 + 上线检查清单（配置、DB 变更、开关状态）；⑤**线上兜底**：监控告警、日志规范、快速回滚演练，出了问题能 5 分钟内回滚比"不出问题"更现实。
- **【示例话术】**：> "我认为质量的保证顺序是：评审时把场景想全、CI 卡住明显错误、灰度把风险控制在小范围、加上能秒级回滚。追求完全不发事故不现实，追求"出事故也影响可控"才是工程化。"
- **【常见误区】**：把质量等同于"测试同学的职责"；只追单元测试覆盖率而不测边界；没有回滚能力就上线；线上无监控，等用户投诉才发现。

### Q56：你怎么看待重复性/CRUD 工作？

- **【考察点】**：职业态度与主动性，是否会被琐事消耗掉。
- **【回答框架】**：①**先承认它是常态**（业务系统大部分工作就是 CRUD，把它做好也需要功底：一致性、幂等、边界）；②**在重复中找优化**（把重复代码抽成模板/脚手架、把重复操作写成脚本、把重复排查沉淀成文档）；③**主动争取有挑战的部分**（性能优化、稳定性治理、公共组件），用"做好份内事 + 提出改进方案"换取信任；④**给团队带来杠杆**（一个人写的工具让十个人省时间，这是比写业务更高的价值）。
- **【示例话术】**：> "业务开发确实有大量重复，我的做法是"做一遍、抽一次、再自动化"。我做过一个脚手架，把新服务的搭建从一天缩到半小时；也把线上排查步骤写成了手册。重复本身不可怕，可怕的是重复五年没有沉淀。"
- **【常见误区】**：表现出不屑（"每天都是 CRUD 没成长"）；抱怨但不改进；只做有挑战的事导致份内工作拖延；把所有时间都花在自研工具而忽略业务目标。

### Q57：技术文档与知识沉淀你怎么做？

- **【考察点】**：协作意识与长期主义。
- **【回答框架】**：①**文档分类**：架构与设计文档（讲清为什么这么设计、边界与取舍）、接口文档（放 Swagger/OpenAPI 保持自动同步而不是手工维护）、运维手册（部署、扩容、故障处理步骤）、复盘与决策记录（ADR）；②**写文档的原则**：结论与图优先、写给"三个月后的自己"、控制在能读完的长度、明确负责人与更新时间；③**沉淀机制**：把线上排查过程即时记录并归档到团队知识库，新人入职先读；④**避免文档腐化**：文档与代码同仓、变更时同步更新、过期文档标注或归档。
- **【示例话术】**：> "我判断一份文档值不值得写，标准是"会不会有人第二次问同一个问题"。线上故障排查手册我写得最认真，因为它能直接减少重复劳动和误操作。"
- **【常见误区】**：只写接口文档不写设计取舍；文档写完就不更新（比没有更危险）；存在个人笔记里不共享；写得又臭又长没人看；把文档当 KPI 凑数。

### Q58：团队技术意见不一致，怎么决策？

- **【考察点】**：能否在分歧中推进，而不是无限讨论。
- **【回答框架】**：①先**对齐目标与评价标准**（很多分歧其实是目标不同，比如一方优化开发效率一方优化性能）；②**把分歧限定在可验证的范围**（能用 POC/压测/数据解决的就做实验，而不是辩论）；③**明确决策机制**：技术细节由 owner 决定并公示理由；跨模块由架构师/主管决策；重大方案走评审投票或上报；④**定了就执行**（"不同意但不阻塞"，保留意见记录在文档里）；⑤**事后复盘**决策质量（结果不对就修正，但不追究"当时选了 A"）。
- **【示例话术】**：> "我讨厌"这条路上再讨论一下"式的拖延。分歧我会先问：这是事实分歧还是偏好分歧？事实分歧就做一次实验，偏好分歧就由 owner 拍板并写明理由，然后大家往前走。"
- **【常见误区】**：追求"所有人都同意"（不可能，也拖慢决策）；谁职级高听谁的（不解释理由）；决策不记录，日后重复争吵；表面同意执行时消极。

### Q59：你最大的优点和缺点是什么？

- **【考察点】**：自我认知是否真实清晰，缺点是否影响岗位胜任力。
- **【回答框架】**：①优点选**与岗位强相关**的 1~2 个，并用事例证明（"我比较擅长把复杂问题拆成可执行的步骤 — 比如上次系统降级方案，我把它拆成了 6 个开关"）；②缺点选**真实的、非致命的、且正在改进**的（"我在跨团队沟通上偏保守，容易自己扛着，后来我给团队定了"阻塞超过 8 小时必须同步"的规则"）；③**避免伪缺点**（"我太追求完美""我太拼了"这类会被识破）；④缺点必须带改进动作，否则等于没答。
- **【示例话术】**：> "优点是遇到线上问题我能稳住，先分层定位再动手；缺点是早期我太习惯自己扛，不爱麻烦别人，导致有次联调卡了两天才找对方。后来我给自己定了规则：同一个问题卡过半天就必须找人同步，现在基本不会再出现这种情况。"
- **【常见误区】**：把优点说成"我很努力/我很负责"（无信息量）；缺点说成"我太追求完美"；缺点直接踩岗位红线（如应聘后端说自己"不喜欢看代码"）；只说不改。

### Q60：如果让你从 0 到 1 带一个项目，你会怎么开始？

- **【考察点】**：全局视野与落地能力，能否把模糊需求变成可交付系统。
- **【回答框架】**：①**对齐目标**：业务要解决什么问题、成功指标是什么（转化率/耗时/成本）、上线时间和资源；②**明确边界**：本期做什么、明确不做什么（防止范围蔓延）；③**技术方案**：领域模型与表设计、接口定义、依赖梳理（下单要不要支付/风控）、容量估算、部署形态；④**风险优先**：先打通最不确定的一环（第三方对接、性能瓶颈），用最小可运行原型验证；⑤**工程节奏**：搭好脚手架与 CI/CD、定规范与分支策略、拆任务排期、每日同步；⑥**上线与运营**：灰度 → 监控告警 → 文档移交 → 复盘与迭代计划。
- **【示例话术】**：> "带新项目我先做三件事：跟业务把成功指标问清楚、把所有外部依赖的风险排到最前面（尤其是第三方和性能）、然后用一周做一个能跑通主链路的最小版本。先证明路能走通，再谈做得漂亮。"
- **【常见误区】**：上来就画大架构图（过度设计）；不定义成功指标；把不确定的依赖留到最后（最后必炸）；只关注技术不考虑上线后的运营与监控；一开始就追求完美代码导致交付延期。

## 4. 万能兜底与体面应对

### 4.1 场景题万能兜底话术（可直接背诵的句式）

1. **范围澄清式**：> "在给方案之前，我先确认几个前提：量级是多少、一致性要求是强一致还是最终一致、能不能接受降级、有没有现成的中间件可以复用？"
2. **框架先行式**：> "这类问题我一般按四步走：先量化和分层定位、再找根因并验证、然后给方案和权衡、最后说兜底和监控。我先从第一步开始说。"
3. **经验迁移式**：> "我没有直接做过这个系统，但它的核心矛盾我处理过 — 都是"高并发下的资源争抢 + 数据一致性"。我当时用的是限流加异步削峰加幂等兜底，思路可以直接搬过来。"
4. **指标驱动式**：> "我会先把这个目标翻译成指标：可用性 99.99%、读接口 P99 200ms 内、写接口最终一致允许秒级延迟。有了指标，方案取舍就有依据了。"
5. **权衡显式式**：> "这里有两个选择：A 快但有脏读，B 一致但多一次网络开销。按你们说的量级和一致性要求，我倾向 B；如果追求极致性能，A 也能接受，但要加 TTL 兜底。"
6. **分层兜底式**：> "除了主流程，我会准备三层兜底：应用内限流与降级开关、缓存和本地快照兜底、最后是快速回滚加人工预案。"
7. **数据验证式**：> "这只是我的假设，我会用一个可验证的动作确认它 — 比如打一次火焰图、看一次慢查询日志，或者直接在预发环境做一次 POC，而不是靠猜。"
8. **主动补漏式**：> "我刚才只讲了正常链路，补充两个容易漏的点：一是并发下的幂等，二是下游超时后的重试放大 — 这两点才是线上事故的高发区。"
9. **收尾复盘式**：> "上线之后我会补三样东西：监控看板、告警阈值和复盘文档，确保同类问题下次能在 5 分钟内定位。"

### 4.2 答不出来时如何体面应对

1. **先接住问题，再拆解**：> "这个场景我确实没有实战过，但我想先把它的关键难点拆一下，您看我拆的方向对不对。"（把"不会"变成"能思考"）
2. **退回到你会的相邻知识**：> "具体的参数我没把握，但我了解它依赖的机制是拉取模式下自行提交位点，常见的坑是重复消费和提交顺序，我会顺着这个方向排查。"（展示知识网络而不是单点记忆）
3. **明确边界而不是硬编**：> "这块我只有理论层面的了解，不敢给您一个确定的数字。但我更确定的是它属于离线批处理场景，和我们调度系统面对的挑战类似。"（面试官反感的是编造，不是不会）
4. **主动索要提示并顺势回答**：> "您能给我一个提示吗，比如是想听容量规划还是故障处理？"（很多面试官愿意给方向，顺着答能挽回局面）
5. **用方法论代替答案**：> "我暂时给不出结论，但我知道怎么找到结论：先看监控确定影响面，再用链路追踪定位到具体环节，最后用二分法缩小范围。"
6. **转化为可执行的下一步**：> "我会在会后补一份分析和 POC 结论发给您，包含压测数据和选型对比 — 我习惯把不确定的问题用实验解决。"
7. **诚实收口，不纠缠**：> "这个知识点我确实掌握得不牢，回去我会重点补。其他方面如果还有想了解的，我很愿意继续聊。"（干净利落地结束，不要反复道歉消耗时间）

### 4.3 把"没做过"变成"我能做"的三段式

- **第一段 承认边界（1 句）**：> "这个系统我确实没有直接负责过，我不想编一个没做过的经历。"
- **第二段 迁移能力（2~3 句）**：> "但我处理过它的同类问题：核心矛盾同样是高并发下的资源争抢和数据一致性。我之前做订单服务时用限流挡住无效流量、用异步削峰保护数据库、用唯一索引保证幂等，这套方法论在这里同样成立。"
- **第三段 可执行的落地路径（2~3 句）**：> "如果交给我，我会先花一周摸清流量模型和依赖边界，做一次容量评估和压测找瓶颈，再按"先加监控、再限流降级、最后才动架构"的顺序推进 — 因为前三步成本最低、风险最小。"

## 自测题（含答案要点）

1. **CPU 100% 的定位链路是什么？** `top` 定范围 → `top -Hp <pid>` 找线程 → `printf '%x'` 转十六进制 → `jstack` 找栈 → `arthas thread -n 3` / `async-profiler` 采样；注意区分 GC 线程与业务线程，止血前先留现场。
2. **怎么区分缓存雪崩、击穿、穿透？** 雪崩 = 大量 key 同时过期或缓存整体宕机；击穿 = 单个热 key 过期瞬间被并发打爆；穿透 = 查询根本不存在的数据，永远不命中。对策分别是随机 TTL + 多级缓存、互斥锁或逻辑过期、布隆过滤器 + 空值缓存。
3. **连接池耗尽怎么快速判断方向？** 看活跃连接是否只增不降：不降是泄漏，波动但贴上限是慢 SQL，长期贴上限是容量不足。三个方向三种解法。
4. **消息不丢要覆盖哪三段？** 生产端确认 + 重试（或本地消息表）、Broker 多副本 + 同步刷盘、消费端先处理后 ack；不重只能靠业务幂等，因为 MQ 语义上限是 at-least-once。
5. **为什么推荐"先更新 DB 再删缓存"而不是"先删缓存再更库"？** 先删缓存会让并发读把旧值重新加载进缓存形成长期脏数据；先更库再删缓存的窗口极小，且可用延迟双删 + TTL + binlog 订阅进一步收敛。
6. **分布式锁失效有哪些模式？** 锁提前过期、误删他人锁、加锁与设过期非原子、主从切换丢锁、时钟回拨、锁粒度过大、未检查 tryLock 返回值。结论：锁只做优化，正确性靠幂等。
7. **MQ 积压千万的三步处理？** 止损（扩消费者/提并发/加分区，注意分区数上限）→ 分流（临时 topic 搬运 + 非核心消息降级丢弃）→ 追平（限速追数据 + 消费幂等 + 下游保护）。
8. **Full GC 频繁怎么判断方向？** 老年代居高不下 → 按内存泄漏查；老年代低但 FGC 频繁 → 可能是 `System.gc()` 或元空间；每次回收降幅小 → 对象生命周期长，调新生代与晋升阈值。
9. **线程池打满的三种典型成因？** 流量超过处理能力（队列长但任务快）、任务本身变慢（下游或锁）、参数不合理（核心线程小、队列无界）；拒绝策略优先 `CallerRunsPolicy` 做背压。
10. **主从延迟的关键排查点？** 大事务、无主键表回放全表扫、从库跑大查询、并行复制未开启、硬件弱于主库；`Seconds_Behind_Master` 可能假 0，用 `pt-heartbeat` 更准。
11. **接口从 500ms 优化到 50ms 的第一步？** 先拆链路拿到耗时分布（APM / `arthas trace`），确认大头在 DB、缓存、RPC 还是序列化，绝不先改代码。
12. **超时关单的推荐方案？** 延时消息（RocketMQ 延时消息 / RabbitMQ TTL + 死信）+ DB 兜底扫描；关单时必须再校验状态，并与支付用同一把行锁或乐观锁。
13. **秒杀如何防超卖？** Redis Lua 原子预扣减 + DB 条件更新 `UPDATE stock SET num=num-1 WHERE num>0` 双保险；一人一单靠 `(user_id, sku_id)` 唯一索引；入口限流 + MQ 削峰。
14. **对账要输出哪几类差异？** 一致单、我方有对方无（单边账）、对方有我方无（长款，资损风险最高）、金额或状态不一致；大数据量用排序归并或分桶比对，不能用全表 JOIN。
15. **灰度发布最关键的前提是什么？** 数据兼容 — DB 变更走"扩展、迁移、收缩"三步，保证回滚只是切流量，而不是回滚数据。
16. **时钟回拨影响什么？** 雪花算法可能产生重复 ID、基于 TTL 的分布式锁提前失效、幂等 token 与限流窗口错乱；处理原则是"宁可失败不可重复"，并改用号段模式或看门狗 + fencing token。
17. **磁盘满排查第一步是什么？** 先分 `df -h`（容量）还是 `df -i`（inode）；再用 `du -sh` 逐层定位，用 `lsof +L1` 找已删除但句柄未释放的文件。
18. **周期性卡顿按什么线索排查？** 先量周期：分钟级看定时任务与缓存集中失效，5 分钟以上看日志轮转与监控采集，整点看备份与报表，秒级看 GC。
19. **被问到完全不会的领域怎么答？** 承认边界 → 拆解关键难点 → 迁移同类经验 → 给出可执行的落地路径；绝不编造经历，也绝不用一句"不会"结束回答。

## 背诵卡片

1. 场景题骨架：澄清需求 → 定目标指标 → 分层定位 → 假设验证 → 方案权衡 → 兜底复盘。
2. 五个必问前提：QPS 量级、数据量、一致性要求、可用性 SLA、能否降级。
3. 三条铁律：先给结论、主动画图、主动报数字。
4. 没做过的话术：核心矛盾相同，方法论可迁移，落地路径清晰。
5. CPU 排查链路：`top` → `top -Hp` → `printf '%x'` → `jstack` → `arthas thread -n 3`。
6. `thread -b` 直接找阻塞别人的锁持有者。
7. `jstat -gcutil <pid> 1000 20` 看 `O`、`FGC`、`FGCT`；FGC 每分钟超 1 次就要处理。
8. OOM 先分清堆、Metaspace、直接内存、native thread，生产必须开 `HeapDumpOnOutOfMemoryError`。
9. `jmap -histo:live` 快速看对象 Top；`jmap -dump` + MAT 看支配树与 Leak Suspects。
10. 两次 dump 对比只增不减的类，才是内存泄漏的判决性证据。
11. `ThreadLocal` 必须 `remove`，线程池场景下不 remove 一定泄漏。
12. 连接池耗尽判断：只增不降是泄漏，贴上限是容量不足，波动是慢 SQL。
13. HikariCP：`connectionTimeout` 设 1~3s 快速失败，`leakDetectionThreshold` 抓泄漏。
14. `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 是死锁的权威证据。
15. `performance_schema.data_lock_waits` 查当前锁等待。
16. 死锁根因：加锁顺序不一致、缺索引导致锁范围过大；解法是统一顺序 + 小事务 + 乐观锁。
17. 慢 SQL 看累计耗时占比，不只看单条最慢；深分页用延迟关联或游标翻页。
18. `EXPLAIN` 看 `type`、`key`、`rows`、`Extra`（`Using filesort`/`Using temporary`）。
19. 大表加索引用 `ALGORITHM=INPLACE, LOCK=NONE`，生产用 `gh-ost`。
20. 消息不丢三段：生产端确认、Broker 多副本同步刷盘、消费端先处理后 ack。
21. 消息不重只能靠业务幂等：唯一索引、去重表、状态机版本号。
22. MQ 积压三步：止损扩消费者、分流搬临时 topic、限速追平加幂等。
23. 缓存三兄弟：雪崩是大量 key 同时失效，击穿是单个热 key，穿透是查不存在的数据。
24. 随机 TTL 治雪崩，互斥锁或逻辑过期治击穿，布隆过滤器治穿透。
25. Redis 找大 key：`--bigkeys`、`MEMORY USAGE`；大 key 用 `UNLINK` 异步删。
26. Redis 缓存场景用 `allkeys-lru` 或 `allkeys-lfu`，`maxmemory` 别超过物理内存 70%。
27. 雪崩治理"两减一守"：减少慢调用（超时加熔断）、减少依赖（降级加隔离）、守住入口（限流）。
28. 超时必须显式设置，且不能比下游 P99 大一个数量级。
29. 线程池取好名字，否则 `jstack` 里定位不到业务。
30. 线程池队列必须有界，绝不用 `Executors` 的无界队列工厂方法。
31. 日志轮转 `SizeAndTimeBasedRollingPolicy` + `totalSizeCap`，日志盘 80% 告警。
32. 磁盘满先分 `df -h` 与 `df -i`，`lsof +L1` 找句柄未释放的文件，用 `truncate` 而不是 `rm`。
33. 周期性卡顿先量周期，再用周期匹配定时任务、日志轮转、备份、缓存集中失效。
34. 分布式锁四要素：`SET NX PX` 原子、value 唯一、Lua 校验后删、看门狗续期。
35. 锁只做优化，正确性靠唯一索引 + 状态机幂等。
36. 幂等三件套：上游给幂等键、DB 唯一索引兜底、状态机保证不可重放。
37. 支付防重的最后防线是对账；没对账的支付系统一定出事故。
38. 灰度发布的关键是数据兼容，回滚永远只是切流量。
