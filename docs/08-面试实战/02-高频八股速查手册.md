| 1.2 | Java 是值传递还是引用传递 | 只有值传递；对象传的是引用副本，副本改指向不影响原变量，改对象内容会生效 |

| 1.9 | 面向对象三大特性 | 封装（隐藏实现）、继承（代码复用，单继承）、多态（父类引用指向子类对象，运行时动态绑定） |
| 1.10 | 重载与重写的区别 | 重载编译期静态分派、同方法名不同参数；重写运行期动态分派、方法签名相同、不能收窄访问权限 |
| 1.11 | 抽象类与接口的区别 | 抽象类单继承、可有构造器与状态；接口多实现、成员默认 public static final、JDK8 起有 default/static 方法 |
| 1.12 | final、finally、finalize | final 修饰类/方法/变量不可变；finally 必执行（除 System.exit）；finalize 已废弃（JDK9 deprecated，JDK18 起可移除） |
| 1.13 | 异常体系 | Throwable → Error / Exception；Exception 分受检（编译期强制）与非受检（RuntimeException）；finally 中 return 会吞异常 |

| 1.16 | PECS 原则 | Producer Extends Consumer Super；`List<? extends T>` 只能读，`List<? super T>` 只能写 |

| 1.19 | 深拷贝与浅拷贝 | 浅拷贝只复制引用（Object.clone 默认）；深拷贝递归复制或序列化；实现 Cloneable 并重写 clone |
| 1.20 | Object 的常用方法 | equals、hashCode、toString、clone、getClass、wait/notify/notifyAll、finalize（共 11 个，含 native） |
| 1.21 | Java 8 有哪些新特性 | Lambda、函数式接口、Stream、Optional、新日期 API、接口 default 方法、方法引用 |
| 1.22 | 接口 default 方法冲突 | 多接口同签名 default 必须显式重写；类方法优先于接口 default；接口 default 优先于父接口 |
### 陷阱与禁忌
- 说"Java 有引用传递"→ 直接减分，标准答案永远是"值传递，传的是引用副本"。
- 比较两个 Integer 的 128 用 `==` 返回 false，面试官爱用 `Integer a = 128` 卡人。
- 重写 equals 不重写 hashCode，导致 HashSet 中出现两个"相等"元素，必须同改。
- finally 里写 `return` 或抛异常会覆盖 try 中的返回值与异常，真实项目禁写。
- 泛型 `List<String>` 与 `List<Integer>` 在运行期是同一个 Class，口述擦除时要点明"仅编译期约束"。
- 说 String 不可变就"为了安全"太笼统，要给出"常量池复用、hash 缓存、并发无需拷贝、可作为 Map key"四点。
### 一句话速记
> Java 全部是值传递，传对象传的是引用副本——副本换指向管不到外面，改内容才能生效。
> equals 是内容，hashCode 是桶号；改了一个就要改另一个。
> 反射能拿到一切但会慢，面试答"用反射 + 缓存 Method 或走 MethodHandle，避免热路径反复 getDeclaredMethod"。

### 陷阱与禁忌
- 说 HashMap 是"线程安全的"→ 致命错误，必须补"并发用 ConcurrentHashMap"。
- 说链表转红黑树阈值"8"但漏掉"数组长度 ≥64，否则先扩容"，被追问就露馅。
- `Arrays.asList` 返回固定长度列表，add/remove 抛 UnsupportedOperationException，基本类型数组会被当成一个元素。
- `subList` 是视图不是拷贝，原列表改结构后操作子列表抛 ConcurrentModificationException。
- 遍历中删除元素用 `for (int i...)` 会漏元素，正确用 `Iterator.remove()` 或 `removeIf`。
- 声明 `List<Integer>` 却用 `new ArrayList()` 原始类型，失去泛型检查，代码审查会被点名。
### 一句话速记
> HashMap = 数组 + 链表 + 红黑树，2 的幂容量配扰动函数，0.75 负载因子，8 转树 6 退化。
> 需要并发就用 ConcurrentHashMap，JDK8 是 CAS 加锁桶头的细粒度锁，不是分段锁。
> fail-fast 靠 modCount 校验，fail-safe 靠写时复制或弱一致迭代器。

### 陷阱与禁忌
- 说 volatile 能保证原子性 → 立即被判基础不牢，必须强调"只保证可见性与有序性"。
- 线程池用 `Executors.newFixedThreadPool` → 说得出"无界队列 OOM、`newCachedThreadPool` 最大线程 Integer.MAX_VALUE"，所以阿里规范禁止，手写 ThreadPoolExecutor。
- 说 AQS 是"乐观锁"或"阻塞队列实现"→ 不准确，要说"state + CLH 变体双向队列 + park/unpark + 模板方法"。
- ThreadLocal 用完不 remove，在线程池场景下会串数据 + 内存泄漏，这是高频追问点。
- 说 synchronized 一定比 ReentrantLock 慢 → 太绝对，JDK6 后偏向锁/轻量级锁已优化，非竞争场景性能相当。
- 死锁四条件（互斥、请求保持、不可剥夺、循环等待）答不全，破坏方式要对应说"统一加锁顺序、超时 tryLock"。
### 一句话速记
> volatile 管可见性和有序，原子性交给原子类或锁；别让它背锅。
> AQS = volatile state + CLH 队列 + park/unpark，独占共享两套模板，ReentrantLock、Semaphore、CountDownLatch 都建在它上面。
> 线程池顺序：核心 → 队列 → 最大 → 拒绝；队列选错会让 maximumPoolSize 形同虚设。

- 说"Redis 是单线程所以不会有并发问题"→ 单命令原子，但多命令组合仍非原子，需 Lua 或事务。

> 一致性首选 Cache Aside：更新 DB、删除缓存，延迟双删与 binlog 补偿只是降低不一致窗口。
> 分布式锁三要素：原子加锁（SET NX PX）、唯一 value、Lua 校验释放，加看门狗解决续期。

| 7.13 | AOP 失效场景 | 同类内部方法自调用、private/final/static 方法、非 Spring 管理的对象、this 调用；解法：AopContext.currentProxy 或拆类 |

| 7.15 | @Transactional 失效场景 | 方法非 public、自调用、异常被 catch、抛受检异常未配 rollbackFor、类未被代理、多线程调用 |
| 7.16 | 事务隔离与只读 | `@Transactional(isolation=...)` 透传数据库隔离级别；`readOnly=true` 可优化并防误写；超时用 `timeout` |

| 7.19 | 常用扩展点 | BeanPostProcessor、BeanFactoryPostProcessor、ImportSelector、ImportBeanDefinitionRegistrar、ApplicationListener、InitializingBean |
| 7.20 | Spring 事件机制 | ApplicationEventPublisher 发布、@EventListener 监听；默认同步，加 @Async 异步；@TransactionalEventListener 绑定事务阶段 |
### 陷阱与禁忌
- 说"三级缓存是为了性能"→ 主因是解决 AOP 代理与循环依赖的语义问题，性能只是附带。
- 说"@Transactional 加在方法上就一定生效"→ 自调用、非 public、异常被吞都是经典失效场景，必须能举出具体代码。
- 说"AOP 用的是反射"→ 不严谨，是动态代理（JDK Proxy 用反射调用，CGLIB 用字节码生成子类）。
- 循环依赖回答只说"三级缓存名字"却说不清每级存什么、为什么是工厂，是最容易被连环追问的地方。
- 说"Spring 单例 Bean 是线程安全的"→ 容器只保证单例，Bean 自身有无状态决定是否线程安全。
- 把 BeanFactoryPostProcessor 与 BeanPostProcessor 混为一谈：前者改 BeanDefinition，后者改 Bean 实例。
### 一句话速记
> 三级缓存：一级成品、二级半成品、三级工厂；工厂存在的唯一理由是 AOP 代理要延迟生成。
> @Transactional 失效四件套：非 public、自调用、异常被吃、rollbackFor 没配。
> AOP 有接口走 JDK Proxy，没接口走 CGLIB，同类自调用绕过代理所以失效。

- 说"MQ 保证消息不丢也不重"→ 只能做到不丢（持久化 + ack + 重试）与业务幂等，重复投递是常态。

- 顺序消费开多个消费者组或并发线程 → 顺序直接失效；RocketMQ 顺序消费是队列级锁。
- Kafka 分区数越多越好 → 分区多带来文件句柄、重平衡耗时、端到端延迟上升，需权衡。
- 事务消息用来做"强一致"→ 它给的是最终一致性，且要求本地事务与消息发送可被回查校验。
- 消费者扩容超过分区数 → 多出的实例空闲，要先把分区数与消费能力挂钩。
### 一句话速记
> 消息不丢三段论：生产端确认重试、Broker 刷盘多副本、消费端处理成功再 ack。
> 消息不重靠业务幂等：唯一键去重表 + 状态机流转 + Redis 幂等 token。
> RocketMQ 事务消息 = 半消息 + 本地事务 + 回查，Kafka 事务只覆盖流处理写读，别混着答。

| 12.7 | CLOSE_WAIT 过多 | 表示本端收到了 FIN 未 close，通常是应用没关连接（连接泄漏、未释放资源），属代码问题 |
| 12.8 | TCP 可靠传输机制 | 序号确认、超时重传（RTO）、快速重传（3 个重复 ACK）、滑动窗口流量控制、拥塞控制 |
| 12.9 | 流量控制与拥塞控制 | 流量控制用接收窗口 rwnd 防压垮对方；拥塞控制有慢启动、拥塞避免、快重传、快恢复，靠 cwnd 感知网络 |
| 12.10 | TCP 与 UDP | TCP 面向连接、可靠、有序、字节流、开销大；UDP 无连接、不保证可靠与顺序、报文边界保留、开销小（DNS、音视频、QUIC 底层） |
| 12.11 | HTTP 与 HTTPS 区别 | HTTPS = HTTP + TLS，默认 443；对称加密传数据、非对称加密协商密钥、证书验身份，防窃听篡改冒充 |
| 12.12 | TLS 握手流程 | ClientHello（随机数 + 套件）→ ServerHello + 证书 → 校验证书 → 密钥交换 → 双方生成会话密钥 → Finished；TLS1.3 精简为 1-RTT（可 0-RTT） |
| 12.13 | HTTP 方法幂等性 | GET/HEAD/PUT/DELETE 幂等；POST 非幂等；PATCH 通常不幂等；幂等是重试与网关重发的设计依据 |
| 12.14 | HTTP 状态码 | 200/201/204、301 永久重定向/302 临时/304 协商缓存命中、400/401/403/404/405、500/502 网关错误/503 不可用/504 超时 |
| 12.15 | HTTP 1.0/1.1/2/3 | 1.0 短连接；1.1 长连接 + 管道化（队头阻塞）；2.0 二进制分帧 + 多路复用 + HPACK 头压缩 + 服务端推送；3.0 基于 QUIC（UDP） |
| 12.16 | 队头阻塞 | HTTP1.1 应用层队头阻塞（同连接串行）；HTTP2 解决应用层但 TCP 层仍队头阻塞；HTTP3 用 QUIC 独立流解决 |
| 12.17 | 强缓存与协商缓存 | 强缓存：Expires/Cache-Control（max-age，优先级更高）；协商缓存：Last-Modified/If-Modified-Since、ETag/If-None-Match；命中返回 304 |
| 12.18 | 从输入 URL 到页面展示 | DNS 解析（本地缓存 → hosts → 递归查询）→ TCP 三次握手 → TLS 握手 → 发 HTTP 请求 → 服务端处理响应 → 浏览器渲染 → 四次挥手/连接复用 |
### 陷阱与禁忌
- 说"三次握手是为了可靠性，四次挥手是双向关闭"→ 前半句不准确，握手核心是同步双方初始序列号并确认收发能力。
- 说 TIME_WAIT 是"服务器的问题"→ 它是主动关闭方的正常状态，大量出现在压测客户端或短连接服务端。
- 把 502 和 504 混答：502 是上游返回无效响应（后端崩了/协议错误），504 是网关等后端超时。
- 说 HTTP/2 彻底解决队头阻塞 → 只在应用层解决，TCP 丢包仍阻塞所有流。
- 说 HTTPS 全程非对称加密 → 非对称只用于握手协商，数据用对称加密。
- 说"ETag 一定比 Last-Modified 精确"→ 语义不同，ETag 更精确但分布式环境需注意一致生成。
### 一句话速记
> 三次握手同步序号验双向，四次挥手各自关闭，TIME_WAIT 是主动关闭方等 2MSL。
> HTTPS = HTTP + TLS：非对称协商密钥，对称加密传数据，证书防冒充。
> HTTP1.1 应用层队头阻塞，HTTP2 靠多路复用解决但 TCP 层仍阻塞，HTTP3 用 QUIC 才彻底。

### 陷阱与禁忌
- 说"线程越多并发越高"→ 上下文切换与内存栈开销会让吞吐下降，Java 中用虚拟线程也要注意 pinning 与 DB 连接池限制。
- 说"共享内存不需要同步"→ 正是因为没有内核介入，才必须自己加信号量/锁。
- 说"多路复用是异步 IO"→ 它是同步非阻塞的复用，只是把等待交给内核并一次处理多连接。
- 说 epoll 一定比 select 快 → 连接数很少时优势不明显甚至更重（需 epoll_ctl 维护），要点明是高并发大量连接场景。
- 把"死锁预防"和"死锁避免"混答：前者破坏四条件（静态策略），后者运行时判断安全状态。
- 说虚拟内存"就是磁盘当内存"→ 核心是地址空间抽象与按需分页。
### 一句话速记
> 进程管资源、线程管调度、协程由用户态调度；虚拟线程把阻塞变便宜但挡不住资源池上限。
> epoll = 红黑树登记 + 就绪链表通知，只返回就绪 fd，故高并发下 O(1) 优于 select 的 O(n) 遍历。
> 死锁四条件：互斥、请求保持、不可剥夺、循环等待；破坏任一条即可预防。

### 陷阱与禁忌
- 说"CAP 三者不可兼得所以都能选"→ 分布式系统 P 不可放弃，实际是在 C 和 A 之间取舍（如 ZK 偏 CP、Eureka 偏 AP）。
- 说"TCC 就是加了个补偿"→ 必须点出空回滚、悬挂、幂等三个必须解决的问题。
- 重试不配幂等 → 是线上重复扣款/重复下单的经典事故，任何重试都要先有幂等。
- 说"分布式锁用 Redis 就够"→ 主从切换、锁过期、GC 停顿都可能破坏互斥，强一致场景考虑 ZK/etcd 或 fencing token。
- 熔断降级答"就是 try-catch 返回默认值"→ 要讲三态机、统计窗口、阈值与半开探测。
- 微服务拆分只按技术分层拆 → 会带来大量跨服务调用，应按业务能力拆。
### 一句话速记
> 分布式必然有 P，选 C 还是 A 取决于业务；BASE 是 AP 的实践落点。
> 一致性方案选择：强一致用 2PC/TCC，最终一致用本地消息表、事务消息、Saga。
> 任何重试之前先保证幂等，这是一条不可谈判的前提。

| 16.10 | 策略模式 | 把算法族封装并可互换，消除大量 if-else；生产用 Map<String, Strategy> 或 Spring 注入替代工厂分支 |
| 16.11 | 模板方法 | 父类定骨架、子类实现可变步骤（钩子方法）；AQS、JdbcTemplate、HttpServlet 都是应用 |
| 16.12 | 责任链模式 | 请求沿链传递直到被处理；Servlet Filter、Spring 拦截器、Sentinel 链路、审批流 |
| 16.13 | 外观与中介者 | 外观为子系统提供统一入口简化调用；中介者让对象间不直接通信（如消息总线） |
| 16.14 | 享元模式 | 共享细粒度对象减少内存，区分内部状态（可共享）与外部状态（外部传入）；Integer 缓存池、连接池 |
| 16.15 | 组合模式 | 树形结构统一处理叶子与容器，如菜单树、组织架构、文件系统 |
| 16.16 | 设计原则 SOLID | 单一职责、开闭、里氏替换、接口隔离、依赖倒置；另有迪米特法则与合成复用原则 |
### 陷阱与禁忌
- 单例只写"双重检查锁"却漏 volatile → 指令重排序会导致半初始化对象被发布。
- 说"设计模式用得越多越好"→ 过度设计是反模式，先满足需求与可读性，再谈扩展。
- 策略模式仍用 if-else 选择实现 → 没消除分支，应结合 Map 注册或注解自动装配。
- 把代理和装饰混答：代理控制访问（常为一个目标）、装饰增强功能（可层层叠加）。
- 责任链中节点抛异常导致整链中断 → 需明确异常传播策略与链路顺序依赖。
- 说"枚举单例不能序列化"→ 恰恰相反，枚举天然防反射与序列化破坏，是《Effective Java》推荐写法。
### 一句话速记
> 单例首选枚举；要懒加载加线程安全就静态内部类或双检锁加 volatile。
> 策略 + Map 消灭 if-else，模板方法定骨架留钩子，责任链管顺序与拦截。
> SOLID 是原则不是教条，可读性与可维护性优先于模式本身。

### 陷阱与禁忌
- 说 provided 依赖会被打进包 → 恰恰相反，编译需要但打包排除（Spring Boot 需显式配置排除或换 scope）。
- 在公共分支 rebase → 会让协作者的提交历史错乱，团队规范里通常明令禁止。
- `git reset --hard` 当成"撤销"随手用 → 会永久丢失工作区改动，误删后只能用 reflog 抢救。
- Dockerfile 里 `COPY . .` 放在依赖安装之前 → 每次改代码都失效缓存，构建变慢。
- 容器里跑多个进程或用 shell 包一层不转发信号 → 优雅停机失效，SIGTERM 到不了 Java 进程。
- K8s 只配 liveness 不配 readiness → 启动阶段被判死循环重启，同时流量会在未就绪时进来。
### 一句话速记
> Maven 冲突靠最短路径优先，先 dependency:tree 再 exclusions，版本统一用 dependencyManagement。
> rebase 改历史、只用于本地；公共分支用 merge，已推送的错误用 revert。
> K8s：Pod 是调度单元，Deployment 管副本与滚动更新，Service 给稳定入口，Ingress 做七层路由。

### 陷阱与禁忌
- 上来直接写代码不沟通 → 面试官更看思路：先复述需求、给暴力解与复杂度、再优化。
- 反转链表递归版说不清栈空间 O(n) → 迭代是 O(1) 空间，需能说明取舍。
- 快排忘随机化或三数取中 → 有序输入退化 O(n²)，这是常见追问。
- 二分写 `while (lo <= hi)` 却混用 `hi = mid` → 死循环，边界要一贯制。
- DP 只背题不解释状态定义 → 追问"为什么这样定义状态"就答不上，面试重点在推导。
- 手写 LRU 用 LinkedHashMap 一行搞定 → 可以先说"生产可用 LinkedHashMap(accessOrder=true)"，但要按面试官要求手写双向链表。
### 一句话速记
> 先暴力解交代复杂度，再优化；面试官买的是思路不是代码。
> 第 K 大用小顶堆，中位数用双堆，LRU 用哈希 + 双向链表，都是 O(1) 或 O(log n) 的固定套路。
> DP 四步：定状态、写转移、初始化、定顺序；说不清状态定义等于没做出来。

## 自测题（含答案要点）

1. **说清 Java 为什么只有值传递。** 实参是栈上的值；对象参数复制的是引用值，副本重新赋值不影响调用方，修改对象内部状态才可见。

2. **HashMap 什么时候转红黑树？为什么是 8？** 链表长度 ≥8 且数组容量 ≥64，否则优先扩容；8 基于泊松分布，链表达 8 的概率极低，属小概率兜底。

3. **JDK8 的 ConcurrentHashMap 如何做到高并发？** 数组 + 链表 + 红黑树，空桶 CAS 插入，非空桶 synchronized 锁头节点；扩容支持多线程协助迁移，计数用 baseCount + CounterCell。

4. **volatile 为什么不能保证 i++ 原子性？** i++ 是读、加、写三步，volatile 只保证每步可见和有序，不阻止中间被其他线程插入。

5. **AQS 的独占与共享模式区别？** 独占用 state=1 表示占用并记录持有线程；共享用 state 表示可用许可数（如 Semaphore、CountDownLatch 的计数）。

6. **线程池队列该怎么选？** 有界队列（ArrayBlockingQueue）能触发拒绝策略并形成背压；无界队列（LinkedBlockingQueue）会让 maximumPoolSize 失效、堆积 OOM；同步移交用 SynchronousQueue。

7. **ThreadLocalMap 的 key 为什么是弱引用？** 让 ThreadLocal 对象本身可被 GC 回收，避免长期强引用泄漏；但 value 仍强引用，线程池不 remove 仍会残留。

8. **对象什么情况下会直接进老年代？** 大对象超过 `-XX:PretenureSizeThreshold`、Survivor 中同年龄对象总和超过一半（动态年龄判定）、年龄达 15。

9. **G1 如何做到可预测停顿？** 维护每个 Region 的回收成本模型，按 `MaxGCPauseMillis` 挑选收益最高的 Region 组成回收集（Collection Set），停顿可控且与整堆大小弱相关。

10. **为什么选用 B+ 树而不是哈希或 B 树？** 哈希不支持范围查询与排序；B+ 树非叶只存键、扇出大、树矮 IO 少，叶子链表支持范围扫描与顺序读。

11. **MVCC 在 RC 与 RR 下的差异是什么？** RC 每次 SELECT 都新建 ReadView，能看到最新提交；RR 首次 SELECT 建立并复用 ReadView，因此整个事务看到一致快照。

12. **间隙锁解决了什么问题，又带来什么代价？** 阻止区间插入以在当前读下防幻读；代价是加锁范围变大、并发插入冲突增加，且仅在 RR 下生效。

13. **为什么先更新数据库再删除缓存？** 更新缓存存在并发覆盖与无效写放大；删除后下次读回源，出错概率更低，配合延迟双删降低不一致窗口。

14. **Redis 内存淘汰和过期策略有什么区别？** 过期策略处理"已过期 key"（惰性 + 定期删除）；淘汰策略在内存达到 maxmemory 时按 LRU/LFU/random/TTL 规则驱逐 key。

15. **Spring 三级缓存为什么第三级是 ObjectFactory？** 只有真正需要时才决定返回原始对象还是 AOP 代理，保证其他 Bean 注入的引用与最终单例一致。

16. **@Transactional 自调用为什么失效？** 事务能力来自代理增强，同类内部 this 调用不经过代理，事务拦截器不执行；可用 AopContext.currentProxy 或拆到另一个 Bean。

17. **Spring Boot 自动装配被覆盖的顺序是什么？** 用户自定义 Bean 先注册，自动配置类多用 @ConditionalOnMissingBean 兜底；可用 `@AutoConfigureBefore/After` 与 `spring.autoconfigure.exclude` 控制。

18. **RocketMQ 事务消息如何保证最终一致？** 先发半消息 → 执行本地事务 → commit/rollback；Broker 定时回查未决消息，消费端幂等处理；补偿逻辑要与本地事务可被查询校验。

19. **TIME_WAIT 与 CLOSE_WAIT 各自说明什么？** TIME_WAIT 是主动关闭方等 2MSL，正常但连接数过高需优化；CLOSE_WAIT 是本端收到 FIN 未关闭，说明代码没释放连接。

20. **分布式事务在什么情况下用 TCC 而不是消息表？** 需要较强的中间态控制、资源可预留、要求较低延迟时用 TCC；流程长且能接受最终一致时优先本地消息表或事务消息。
## 背诵卡片

1. Java 只有值传递，对象传的是引用副本。
2. equals 比内容、hashCode 定桶号，重写一个必须重写另一个。
3. HashMap：数组 + 链表 + 红黑树，2 的幂容量，0.75 负载因子，8 转树 6 退化且需数组 ≥64。
4. 并发 Map 用 ConcurrentHashMap，JDK8 是 CAS + 锁桶头的细粒度锁。
5. fail-fast 看 modCount，fail-safe 靠写时复制或弱一致迭代器。
6. volatile 管可见性与有序性，不管原子性。
7. AQS = volatile state + CLH 双向队列 + park/unpark + 模板方法。
8. 线程池顺序：核心线程 → 队列 → 最大线程 → 拒绝策略。
9. 线程池参数：CPU 密集 N+1，IO 密集按 N × (1 + 等待/计算) 估。
10. 四种拒绝策略：Abort、CallerRuns、Discard、DiscardOldest。
11. ThreadLocal 一定要 try/finally remove，尤其在线程池中。
12. synchronized 锁升级：无锁 → 偏向锁 → 轻量级锁 → 重量级锁。
13. ReentrantLock 支持可中断、可超时、可公平与多条件。
14. JVM：堆 + 元空间（本地内存）+ 程序计数器/虚拟机栈/本地方法栈。
15. 对象判活用可达性分析，GC Roots 含栈引用、静态变量、常量、JNI。
16. 三色标记漏标：CMS 用增量更新，G1 用原始快照 SATB。
17. G1 按 Region 分块、可预测停顿，JDK9 起成为默认收集器。
18. ZGC 着色指针 + 读屏障，停顿与堆大小基本无关。
19. 双亲委派：先委派父加载器，避免核心类被篡改。
20. B+ 树矮胖少 IO，叶子链表支持范围查询。
21. 二级索引叶子存主键，取不到所需列就要回表，全覆盖则 Using index。
22. 最左前缀：联合索引 (a,b,c) 只支持 a、a+b、a+b+c 这些前缀。
23. 索引失效：函数运算、隐式转换、前导 %、OR 非索引列。
24. RR 下快照读靠 MVCC，当前读靠 Next-Key Lock。
25. redo 保崩溃恢复，undo 保回滚与 MVCC，binlog 保主从与恢复。
26. 两阶段提交让 redo 与 binlog 保持一致。
27. 主从延迟来自大事务与单线程回放，用并行复制与半同步缓解。
28. 缓存穿透用布隆过滤器与空值缓存，击穿用互斥锁或逻辑过期。
29. 雪崩靠 TTL 随机化、多级缓存、熔断降级与高可用部署。
30. 缓存一致性首选先更新库再删缓存，延迟双删与 binlog 补偿兜底。
31. Redis 分布式锁：SET NX PX + 唯一 value + Lua 校验释放。
32. Spring 三级缓存：一级成品、二级半成品、三级工厂，为 AOP 代理而生。
33. @Transactional 失效四因：非 public、自调用、异常被吃、rollbackFor 未配。
34. 自动装配 = @Import + SPI 注册文件 + 条件注解。
35. MQ 三段防丢：生产确认重试、Broker 刷盘多副本、消费成功再 ack。
36. 消息幂等靠唯一键去重表、状态机与幂等 token。
37. RocketMQ 事务消息 = 半消息 + 本地事务 + 回查。
38. TCP 三次握手同步序号，四次挥手各自关闭，TIME_WAIT 等 2MSL。
39. HTTPS 非对称协商密钥、对称加密传数据、证书验身份。
40. 分布式必然有 P，在 C 与 A 间取舍；BASE 是 AP 的落地实践。
