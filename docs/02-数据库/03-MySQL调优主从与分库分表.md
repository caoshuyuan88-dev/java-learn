## 1. 核心参数调优

### 1.1 核心原理

| 参数 | 默认值 | 生产建议与理由 |
| --- | --- | --- |
| `innodb_buffer_pool_size` / `instances` | 128MB / 8 | **物理内存 50%~75%**，命中率目标 > 99%；实例仅 pool ≥ 1GB 生效，4~8 个足够 |
| `innodb_flush_log_at_trx_commit` / `sync_binlog` | 1 / **8.0 为 1、5.7 为 0** | 5.7 必须手动把 `sync_binlog` 改成 1；组合取舍见下表 |
| redo 日志大小 | 5.7 `innodb_log_file_size` 48MB×2；8.0.30+ `innodb_redo_log_capacity` 100MB | **能容纳 1~2 小时写入量**（`每秒写入量 × 3600~7200`），太小会频繁 checkpoint 刷脏造成抖动 |
| `innodb_thread_concurrency` | 0（不限制） | 一般保持 0；极端高并发下设为 `CPU 核数 × 2` 左右做准入控制 |
| `max_connections` / `thread_cache_size` | 151 / 9 | 按业务估算并与应用连接池上限对齐，避免 DB 被打爆 |
| `tmp_table_size` / `max_heap_table_size` | 各 16MB | 内存临时表受**两者较小值**限制；先优化 SQL 再考虑调大 |
| `long_query_time` / `slow_query_log` | 10 秒 / OFF | **生产建议 0.1~1 秒并开启**，`log_queries_not_using_indexes` 慎开 |
| `table_open_cache` | 8.0 默认 4000 | 不足会频繁开关表，`Opened_tables` 快速增长是信号 |

刷盘组合的取舍（安全 ↔ 性能）：

| 组合 | 不丢事务 | 掉电丢 | 适用 |
| --- | --- | --- | --- |
| `flush_log=1 + sync_binlog=1` | ✓ | 无 | 金融、交易（8.0 默认） |
| `flush_log=2 + sync_binlog=1` | 主机崩溃不丢，掉电丢最近约 1s | 约 1s | 多数互联网业务 |
| `flush_log=1 + sync_binlog=0` | redo 安全但 binlog 可能丢 | binlog 增量 | 不推荐（主从可能不一致） |
| `flush_log=0 + sync_binlog=0` | ✗ | 约 1s | 日志、埋点等可丢数据 |

### 1.2 面试问答

- **Q1：调优的优先级顺序是什么？** 先 SQL 与索引（收益最大、成本最低）→ 再表结构与数据类型（小字段、避免大字段、`NOT NULL`）→ 再参数（buffer pool、刷盘策略）→ 最后才是架构升级（读写分离、分库分表）。参数永远救不了烂 SQL。
- **Q2：`innodb_buffer_pool_size` 怎么定？** 取物理内存 50%~75%，同时给操作系统页缓存和连接内存留余量；上线后看 `Innodb_buffer_pool_reads/read_requests` 的命中率是否 > 99%，以及 `Innodb_buffer_pool_wait_free` 是否为 0。
- **Q3：redo 日志设多大合适？** 目标是"能容纳 1~2 小时的写入量"，避免写入 LSN 追近 checkpoint 频繁触发强制刷脏。改大小在 5.7 需要重启（`innodb_log_file_size` 是只读参数），8.0.30+ 的 `innodb_redo_log_capacity` 支持在线调整。
- **Q4：`innodb_thread_concurrency=0` 是什么意思？临时表参数怎么调？** 表示不做并发线程准入控制，所有请求都进 InnoDB；极端高并发下会导致大量线程争抢与上下文切换，此时可设为 CPU 核数的 2 倍左右做削峰。临时表：先确认 SQL 是否真的需要临时表（`Using temporary` 常见于 `group by`/`distinct`/`union`），能靠索引消除就消除；确实需要再调大 `tmp_table_size` 与 `max_heap_table_size`（两者取较小值生效），它们也是**每连接**上限，盲目调大会吃内存。

### 1.3 高频追问与陷阱

- 陷阱：把 `innodb_buffer_pool_size` 一调到 80% 以上就不管了——机器上还有备份工具、监控 agent 等进程时会 OOM；另外别只看 `Innodb_buffer_pool_reads` 就断言缓存不够，要算命中率，且注意 `Innodb_buffer_pool_read_ahead` 的预读统计干扰。

### 1.4 代码/配置/命令示例

```sql
SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';
SHOW VARIABLES LIKE 'sync_binlog';
SHOW STATUS LIKE 'Innodb_buffer_pool_read%';
SHOW STATUS LIKE 'Opened_tables';
SELECT COUNT FROM information_schema.INNODB_METRICS WHERE NAME='trx_rseg_history_len';
```

### 1.5 一句话速记

**调优优先级：SQL/索引 > 表结构 > 参数 > 架构；buffer pool 取内存 50%~75%，redo 容纳 1~2 小时写入量，刷盘组合按业务能丢多少数据来选。**

## 2. SQL 改写技巧大全

### 2.1 核心原理

**深分页三种方案**（`select * from t order by id limit 1000000, 20`）：

| 方案 | 写法 | 适用与代价 |
| --- | --- | --- |
| ① 游标/上次最大值 | `WHERE id > #{lastId} ORDER BY id LIMIT 20` | **最优**，但只支持顺序翻页、不能跳页 |
| ② 延迟关联 | `SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000,20) x USING(id)` | 支持跳页；子查询走覆盖索引，回表只有 20 次 |
| ③ 覆盖索引 + 二次查询 | 先用覆盖索引取主键集合，再用 `IN` 回表 | 主键数量不宜过多（几百以内） |

其他常用改写：

| 问题 | 改写 |
| --- | --- |
| `OR` 无法走索引 | 改 `UNION ALL` 并补去重条件（见 [./01-MySQL体系结构与索引.md](./01-MySQL体系结构与索引.md)） |
| `IN` vs `EXISTS` | **子查询结果集小用 `IN`，外层结果集小用 `EXISTS`**；8.0 优化器会做半连接（semi-join）改写，差异变小，以 `EXPLAIN` 为准 |
| `count(*)` 慢 | InnoDB 不维护行数，`count(*)`/`count(1)` 会选**最小的二级索引**扫描；近似统计用 `EXPLAIN` 的 `rows` 或 `information_schema.TABLES.TABLE_ROWS`；精确计数考虑计数表/Redis |
| 批量插入 | 一条 `INSERT` 带多组 `VALUES`（建议 500~1000 组/批），JDBC 加 `rewriteBatchedStatements=true` 才能合并成一条；大事务要分批提交 |
| join 驱动表 / 子查询 | 保证**小表驱动大表**、被驱动表 join 列有索引（`STRAIGHT_JOIN` 可强制但慎用）；5.7 起 `IN` 子查询可物化为临时表（`MATERIALIZED`），相关子查询尽量改 join，注意 `NOT IN` 遇 NULL 返回空集 |
| `SELECT *` | 破坏覆盖索引、放大网络与内存、影响排序优化，一律禁止 |

### 2.2 面试问答

- **Q1：深分页为什么会慢？** `LIMIT 1000000, 20` 需要先扫描并丢弃前 100 万行（即使有索引也要沿索引走 100 万次并回表），代价随 offset 线性增长。改成"从上次最大值继续"就只需一次索引定位。
- **Q2：延迟关联为什么快？** 子查询只取主键列，走覆盖索引（不回表），排序也在索引上完成；外层再用 20 个主键回表，把回表次数从 100 万降到 20。
- **Q3：`count(*)` 和 `count(1)`、`count(列)` 的区别？** `count(*)` 与 `count(1)` 语义与性能基本一致（都不看 NULL），优化器会选最小的索引扫描；`count(列)` 只统计该列非 NULL 的行数，且不能省略 NULL 判断。MyISAM 维护了总行数所以 `count(*)` 很快，InnoDB 必须扫描。
- **Q4：`IN` 和 `EXISTS` 到底怎么选？批量插入怎么又快又安全？** 记忆口诀"**小表驱动大表**"：`IN` 相当于用子查询结果驱动外层（子查询小则优），`EXISTS` 相当于用外层结果驱动子查询（外层小则优）；8.0 会做 semi-join 改写，先用 `EXPLAIN` 验证再改。批量插入：① 一条语句多组 `VALUES`；② JDBC 开启 `rewriteBatchedStatements=true`；③ 每批 500~1000 行、分批提交，避免超大事务（撑大 binlog、加重主从延迟与锁持有）；④ 用 `INSERT ... ON DUPLICATE KEY UPDATE` 或 `REPLACE` 处理冲突（注意自增 ID 消耗）。

### 2.3 高频追问与陷阱

- 陷阱：`LIMIT` 不带 `ORDER BY` 结果不确定，翻页会重复或漏数据；另外 `rewriteBatchedStatements=true` 只对 `addBatch` 形式的批处理生效，`useServerPrepStmts` 等参数会影响是否走真正的服务端预处理。

### 2.4 代码/配置/命令示例

```sql
-- 深分页三方案：①游标（最优，但不支持跳页）
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 20;
-- ②延迟关联（支持跳页，子查询走覆盖索引，回表只有 20 次）
SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000,20) x USING(id);
-- ③覆盖索引 + 二次查询（主键数量不宜过多）
SELECT * FROM t WHERE id IN (SELECT id FROM t ORDER BY id LIMIT 1000000,20);
```

### 2.5 一句话速记

**深分页首选游标、次选延迟关联；SQL 改写的核心是"减少扫描行数 + 减少回表 + 让排序走索引"。**

## 3 大表 DDL：Online DDL 与 gh-ost/pt-osc

### 3.1 核心原理

| 方案 | 原理 | 是否需要触发器 | 主库压力 | 可暂停/限流 | 说明 |
| --- | --- | --- | --- | --- | --- |
| **Online DDL（原生，5.6+）** | `ALGORITHM=INPLACE, LOCK=NONE` 原地变更，部分操作只改元数据 | 否 | 重建类操作仍需拷表 | 否 | 加/删索引、改列默认值可以 INPLACE；改列类型、加主键需要 COPY |
| **pt-online-schema-change** | 建**影子表** → 建**触发器**同步增量 → 分批拷数据 → `RENAME` 切换 | **是（3 个触发器）** | 触发器带来额外写入开销，与原表 DML 争锁 | 是（`--max-load`、`--critical-load`） | 依赖触发器，不适合触发器已很多或有外键的表 |
| **gh-ost** | 建影子表 → **解析 binlog** 同步增量 → 分批拷数据 → 原子改名 | **否** | 无触发器开销，可通过 `--max-load` 动态限速 | 是（可交互暂停） | 需要 `binlog_format=ROW`；对主从延迟更友好 |

**Online DDL 关键语法与限制**：`ALTER TABLE t ADD INDEX idx(a), ALGORITHM=INPLACE, LOCK=NONE;`。若优化器拒绝 INPLACE 会报错（而不是静默降级，指定 ALGORITHM/LOCK 时）；此时需评估是否接受 COPY 模式（全程持写锁，大表不可接受）。

### 3.2 面试问答

- **Q1：怎么给一亿行的表加索引？** 首选原生 Online DDL（`ALGORITHM=INPLACE, LOCK=NONE`），加索引属于 INPLACE 且不阻塞 DML；但要评估磁盘空间、`innodb_io_capacity` 与主从延迟，低峰执行并监控。若版本/操作不支持 INPLACE，则用 gh-ost（无触发器、可限速）。
- **Q2：pt-osc 与 gh-ost 怎么选？** 优先 gh-ost：无触发器、对原表写入影响小、可暂停可限速、对主从延迟更友好；pt-osc 的优势是兼容性好（不依赖 ROW 格式 binlog）、生态成熟。有外键或原表触发器多时都不好用，需先评估。
- **Q3：为什么 Online DDL 也叫"Online"却还锁表？** 因为"Online"只保证**不阻塞 DML**，但在某些阶段（如 prepare、commit）仍会短暂持有 MDL 写锁；另外 COPY 模式下是全程锁写。所以 DDL 前必须确认没有长事务，避免 MDL 排队卡库。
- **Q4：DDL 期间要注意什么？** ① 确认没有长事务与未提交会话；② 显式设 `lock_wait_timeout`；③ 监控主从延迟（DDL 会在从库重放）；④ 关注磁盘空间（影子表 + 原表并存）；⑤ 避开业务高峰；⑥ 大表先用 gh-ost 的 `--dry-run` 验证。

### 3.3 高频追问与陷阱

- 陷阱：以为 `ALGORITHM=INPLACE` 就等于不拷贝数据。加索引确实可以 INPLACE，但改列类型/字符集等需要重建整表（`ALGORITHM=COPY`），代价极高。
- 陷阱：gh-ost 依赖 `binlog_format=ROW`；若为 STATEMENT 则无法工作。

### 3.4 代码/配置/命令示例

```sql
-- 原生 Online DDL：加索引可 INPLACE + LOCK=NONE；执行前设会话级锁等待上限
ALTER TABLE t ADD INDEX idx_ct (create_time), ALGORITHM=INPLACE, LOCK=NONE;
SET SESSION lock_wait_timeout = 30;
-- gh-ost 等价操作（bash）：gh-ost --database=mydb --table=t \
--   --alter="ADD INDEX idx_ct(create_time)" --allow-on-master \
--   --max-load='Threads_running=30' --critical-load='Threads_running=60' --execute
```

### 3.5 一句话速记

**优先原生 Online DDL（INPLACE + LOCK=NONE），不支持时用 gh-ost（无触发器、可限速），pt-osc 靠影子表 + 触发器；DDL 前必清长事务。**

## 4. 架构演进与高可用方案对比

### 4.1 核心原理

**架构演进路线**：单机（一主一备冷备）→ 主从复制（读扩展）→ 读写分离（中间件或客户端路由）→ 分库分表（写扩展）→ NewSQL/分布式数据库（自动分片 + 弹性扩容）。

每一次演进的驱动力与代价：主从解决**读瓶颈**但引入延迟；读写分离提升吞吐但带来一致性路由复杂度；分库分表解决**写与容量瓶颈**但引入跨库查询、分布式事务、扩容迁移三座大山；NewSQL 试图用"自动分片 + 分布式事务"把复杂度收回中间件，代价是学习成本、生态与运维成熟度。

| 高可用方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **MHA** | Manager 监控 + Node 节点，主库故障后选新主并补差异 binlog，虚拟 IP 切换 | 老牌成熟、切换快（秒级~数十秒） | 社区版已基本停止维护；需 SSH 免密；有脑裂风险 |
| **MGR**（5.7.17+） | 基于 Paxos（XCom）的组复制，多数派确认，单主/多主模式 | 自动选主、数据强一致、无中心节点 | 需 GTID + ROW + 表必须有主键；网络抖动敏感、吞吐低于异步复制；多主模式冲突处理复杂 |
| **Orchestrator** | 独立服务持续探测拓扑，故障时按规则选主并改写从库指向 | 拓扑可视化、支持复杂拓扑与自动化恢复 | 自身需高可用部署；切换逻辑需调参 |
| **云 RDS（主备）** | 托管主备 + 自动切换 + 备份恢复 | 免运维、切换快、有 SLA | 版本/参数受限、`SUPER` 权限受限、成本高、跨云迁移困难 |

### 4.2 面试问答

- **Q1：主从切换怎么保证不丢数据？** 半同步 `AFTER_SYNC`（保证已提交事务至少落在一个从库）+ GTID 自动补齐差异 + 切换前确认 `Executed_Gtid_Set` 追平；MHA/Orchestrator/MGR 各自实现这套流程。见 [./02-MySQL事务锁与MVCC.md](./02-MySQL事务锁与MVCC.md)。
- **Q2：MGR 与主从复制有什么本质区别？** 主从是**异步（或半同步）单向复制**，从库是"跟随者"；MGR 是**基于共识协议**的组复制，事务需要多数派认证通过才算提交，因此天然具备自动选主与一致性保证，但也因此对网络延迟敏感、吞吐更低。
- **Q3：什么是脑裂？怎么避免？** 网络分区导致新旧主库同时可写。避免手段：① 半同步 + 多数派确认；② 用 MGR/哨兵类的共识组件选主；③ 被降级的旧主设为 `read_only`；④ 应用侧对写请求做路由仲裁（避免同时双写）。
- **Q4：什么时候该上分库分表？读写分离用什么实现？** 单表 > 2000 万行**且**写入/存储已成瓶颈，且已用尽"加索引、读写分离、归档历史数据、冷热分离、升级硬件"等手段之后——判断标准是**瓶颈类型**而非"表很大"。读写分离：客户端方案（ShardingSphere-JDBC、`AbstractRoutingDataSource`）不引入跳数但侵入代码；代理方案（Proxy、MyCat）透明但多一跳且代理自身要保高可用；生产常见做法是核心写走主库、报表读走从库、关键路径强制走主。

### 4.3 高频追问与陷阱

- 陷阱：以为上了 MGR 就万事大吉——它对网络延迟极敏感，跨机房部署容易频繁触发成员驱逐，且要求每个表都有主键；另外别把"高可用"等同于"有从库"，故障切换、选主、位点补齐、VIP/域名漂移、应用重连才是完整的高可用。

### 4.4 代码/配置/命令示例

```sql
-- MGR 前置条件核查
SHOW VARIABLES LIKE 'gtid_mode';          -- 必须 ON
SHOW VARIABLES LIKE 'binlog_format';      -- 必须 ROW
SHOW VARIABLES LIKE 'enforce_gtid_consistency';  -- 必须 ON
SELECT * FROM performance_schema.replication_group_members;
```

### 4.5 一句话速记

**演进路线=单机→主从→读写分离→分库分表→NewSQL，每次演进都换来新复杂度；高可用选型看一致性要求：MHA（老牌）、MGR（强一致但有约束）、Orchestrator（拓扑自动化）、云 RDS（免运维）。**

## 5. 分库分表：拆分方式与分片键设计

### 5.1 核心原理

| 拆分方式 | 内容 | 典型场景 |
| --- | --- | --- |
| **垂直分库** | 按业务域拆到不同库（用户库/订单库/商品库） | 业务耦合、表多到单实例放不下 |
| **垂直分表** | 把大字段/低频列拆到扩展表 | 主表行宽过大、`TEXT` 拖慢查询 |
| **水平分表** | 同一张表按分片键拆成 t_0…t_N | 单表数据量过大 |
| **水平分库** | 拆到多个实例，每个实例再分表 | 单实例写入/连接数/存储成为瓶颈 |

**分片键选择四原则**：① **分布均匀**（避免热点，`user_id` 优于 `create_time` 这种单调递增键）；② **覆盖高频查询**（能落到单个分片，避免全库扫描）；③ **不可变**（变更分片键意味着数据搬迁）；④ **与业务主键解耦**（避免用自增 ID 分片导致新数据全落一个分片）。

**路由算法**：`RANGE`（时间范围，易扩容但可能热点）、`HASH/取模`（均匀但扩容需搬迁）、`一致性哈希`（扩容只动相邻节点，但负载可能不均）、**基因法**（把分片键的基因编码进订单号等 ID 中，使"按订单号查询"与"按用户查询"都能定位到同一分片，是分布式 ID 与分片的经典配合）。

### 5.2 面试问答

- **Q1：分片键怎么选？** 优先选择"写入与查询都高频、基数高、几乎不变"的字段。订单场景通常选 `user_id`（买家维度查询最多），代价是"按商家维度查询"需要额外用异构索引表或 ES 支持。
- **Q2：为什么不用 `create_time` 分片？** 单调递增会导致所有新写入都落到最后一个分片（写热点），而老分片闲置；且范围查询跨多个分片。若必须按时间分，配合"时间 + 哈希"二级拆分。
- **Q3：取模分片扩容为什么要搬迁？** `hash(key) % 4` 改成 `% 8` 会把大部分数据的归属打乱，需要整体重分布。若用"先按 N 个逻辑分片取模、再把逻辑分片映射到物理库"（提前规划 2 的幂次倍逻辑分片），扩容只需搬迁整个逻辑分片，成本可控。
- **Q4：分表后自增主键还能用吗？垂直拆分与水平拆分怎么配合？** 自增主键不能直接用（会冲突且分片键可能不是主键），改用带分片基因的全局唯一 ID（雪花/号段）。通常**先垂直**（按业务域解耦，顺便解决"单表列太多"），**再水平**（单表数据量仍大时按分片键拆）；垂直拆分的边界要按**领域模型**而非表数量，否则跨库 join 会泛滥。

### 5.3 高频追问与陷阱

- 陷阱：分片键选成"低频查询 + 高变更"的字段，结果既有写热点又天天跨片查；另外忽略"分布式主键要带分片基因"，导致按订单号查订单时必须扫全部分片。

### 5.4 代码/配置/命令示例

```sql
-- 水平分表示意：order_0 ~ order_3，按 user_id % 4
CREATE TABLE order_0 (id BIGINT PRIMARY KEY, user_id BIGINT NOT NULL, ...) ;
CREATE TABLE order_1 (id BIGINT PRIMARY KEY, user_id BIGINT NOT NULL, ...) ;
-- 按 user_id 定位单分片（好）
SELECT * FROM order_0 WHERE user_id = 1001;
-- 按 order_no 定位（若 ID 含基因则同样可定位，否则需扫全部分片）
```

### 5.5 一句话速记

**先垂直按业务域拆、再水平按分片键拆；分片键要"均匀、覆盖高频查询、不变"，路由优先基因法 + 预留逻辑分片。**

## 6. 分库分表的三大难题：join/分页/聚合

### 6.1 核心原理

| 难题 | 解决思路 |
| --- | --- |
| **跨库 join** | ① **冗余字段**（订单表冗余商品名，避免 join）；② **广播表/小表**（字典表在每个库都存一份）；③ **绑定表**（同一分片键的表放同一分片，join 可下推）；④ **ER 分片**（把有 ER 关系的表按同一键分片）；⑤ **内存组装**（应用先查 A 得到 id 列表，再查 B，最后内存拼接，注意避免 N+1）；⑥ 异构索引（ES/宽表） |
| **跨库分页** | ① **内存归并**：每个分片取 `offset + limit` 条，汇总后排序取 `limit` 条（分片数多、深分页时代价高）；② **二次查询法**：第一轮取各分片 `min(offset/分片数 + limit)` 条，算出全局阈值，第二轮按阈值精确取数；③ **限制深度**（产品上禁止跳到第 10000 页） |
| **跨库排序/聚合** | 排序尽量下推到各分片后归并（`ORDER BY` 字段就是分片键时可直接下推）；聚合 `count/sum` 各分片先算再汇总；`distinct`、`group by` 需要内存去重，考虑预聚合表或 OLAP（ClickHouse/TiDB/ES）承接 |
| **跨库事务** | 避免强一致：把强一致需求收敛到同一分片；无法避免时用 TCC/Saga/本地消息表/事务消息，详见 [../05-分布式与架构/02-分布式事务.md](../05-分布式与架构/02-分布式事务.md) |

### 6.2 面试问答

- **Q1：分库分表后怎么做分页？** 浅分页用内存归并；深分页必须用二次查询法或禁止跳页（只允许游标翻页）。同时要明确：分页的 `total` 统计在分库分表下成本极高，产品上常改为"不显示总数"或用离线统计。
- **Q2：为什么"绑定表"能解决 join？** 若两张表用同一个分片键分片（如 `order` 与 `order_item` 都用 `user_id`），那么同一用户的订单与明细一定在同一分片，join 可以下推到单个分片执行，中间件无需跨库拼装。
- **Q3：跨库 join 为什么危险？** 中间件要实现跨库 join，只能把数据拉到内存做笛卡尔积或哈希连接，数据量稍大就内存爆炸、性能雪崩。所以设计上要**用冗余与绑定表把 join 消灭在建模阶段**。
- **Q4：分片内的 `count(*)` 怎么优化？聚合结果要求实时怎么办？** 分片内仍走索引；全局计数用"各分片求和"，更优是维护计数表（每次写入增减）或用离线数仓统计，避免大表实时全扫描。实时聚合交给预聚合（定时任务落统计表）或 OLAP 引擎（TiDB/ClickHouse/Doris）；MySQL 分片集群只承担点查与短范围查询，别让它做分析型聚合。

### 6.3 高频追问与陷阱

- 陷阱：以为 ShardingSphere 之类的中间件能"透明解决"跨库 join——它能做，但代价是内存与延迟，属于兜底而非常态；另外分片后仍写 `ORDER BY create_time DESC LIMIT 20` 这类深分页查询，各分片各取 20 条汇总会漏数据（应取 `offset + limit` 条）。

### 6.4 代码/配置/命令示例

```sql
-- 内存归并：每个分片都要取 offset+limit 条（否则漏数据），应用层汇总排序后取前 20 条
SELECT * FROM order_0 ORDER BY create_time DESC LIMIT 10020;
SELECT * FROM order_1 ORDER BY create_time DESC LIMIT 10020;
```

```yaml
# ShardingSphere 绑定表配置（order 与 order_item 同分片键，join 可下推）
rules: [- !SHARDING {bindingTables: [order, order_item]}]
```

### 6.5 一句话速记

**跨库 join 靠冗余/广播表/绑定表消灭、跨库分页靠内存归并（取 offset+limit）或二次查询、聚合交给预聚合或 OLAP；中间件的"透明"都是以内存为代价的兜底。**

## 7. 全局唯一 ID 与分布式事务

### 7.1 核心原理

| 方案 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| UUID | 随机 128 位 | 本地生成、无网络 | 无序 → 页分裂与填充率下降；占空间（存 `binary(16)` 才可接受） |
| 数据库自增/号段 | 单库自增或**号段模式**（一次取 1000 个号缓存在内存） | 有序、简单 | 单点依赖；号段模式重启浪费号段 |
| **雪花算法 Snowflake** | `1 位符号 + 41 位毫秒时间 + 10 位机器 ID + 12 位序列` | 趋势递增、本地生成、高性能 | 依赖时钟（回拨要处理）；机器 ID 需分配管理 |
| Redis `INCR` | 原子自增 | 简单、高性能 | 引入 Redis 依赖与持久化风险 |
| 美团 Leaf / 百度 UidGenerator | 号段 + 雪花双模式 | 生产验证过 | 需部署服务 |

**分库分表下的分布式事务**：能避免就避免（让强一致需求落同一分片）；必须跨库时按一致性强度选：XA/2PC（强一致但阻塞、性能差）< TCC（业务补偿，侵入大）< Saga/本地消息表/事务消息（最终一致，主流选择）。选型细节见 [../05-分布式与架构/02-分布式事务.md](../05-分布式与架构/02-分布式事务.md)。

### 7.2 面试问答

- **Q1：雪花算法的时间回拨怎么处理？** ① 小回拨（毫秒级）：等待追平后再生成；② 大回拨：直接拒绝服务并告警；③ 用"逻辑时钟"记录上次时间戳，`max(当前时间, 上次时间)` 保证单调；④ 运维侧用 NTP 且禁用步进式校时（用 slew 平滑）。
- **Q2：为什么 UUID 做主键不好？** 无序插入导致 B+ 树随机页分裂、填充率降到约 50%~70%、随机 IO；且 16 字节主键会复制进每个二级索引，树更高。见 [./01-MySQL体系结构与索引.md](./01-MySQL体系结构与索引.md)。
- **Q3：雪花 ID 怎么做分片基因？** 把 10 位机器 ID 中留出几位表示分片号，或直接在低位/高位嵌入分片键哈希（如取 `user_id % 1024`），这样从订单号就能推算出数据落在哪个分片，避免按订单号查询时扫全库。
- **Q4：号段模式与雪花的取舍？分库分表后一定要上分布式事务吗？** 号段模式依赖 DB/服务且号段连续（对分片不利，需要额外加基因），但实现简单、有序性好；雪花性能最高、无中心依赖，但要处理时钟与机器 ID 分配，生产常用 Leaf 的"号段 + 雪花"双兜底。分布式事务不一定需要：大多数场景可以**同一分片内保证强一致 + 跨分片用最终一致（本地消息表/MQ 重试/对账补偿）**来规避；真需要跨库强一致通常意味着分片键选错了。

### 7.3 高频追问与陷阱

- 陷阱：以为雪花 ID 天然有序就能当分片键——它趋势递增，用作分片键仍形成写热点，分片键还是该选业务维度（如 `user_id`）；另外别用单机锁（`synchronized`）保证 ID 唯一，多实例部署下立即失效。

### 7.4 代码/配置/命令示例

```java
// 雪花算法核心：时间回拨保护（机器 ID 由配置中心分配）——小回拨等待、大回拨拒绝
long now = System.currentTimeMillis();
if (now < lastTimestamp) {
    long offset = lastTimestamp - now;
    if (offset <= 5) { now = waitUntil(lastTimestamp); }
    else { throw new IllegalStateException("时钟回拨 " + offset + "ms"); }
}
```

```sql
-- 号段模式：一次取一批
UPDATE id_segment SET max_id = max_id + 1000 WHERE biz_tag = 'order';
SELECT max_id FROM id_segment WHERE biz_tag = 'order';
```

### 7.5 一句话速记

**分布式 ID 首选雪花/号段（趋势递增 + 本地生成 + 携带分片基因），禁用 UUID 做主键；分布式事务优先"消除"而非"解决"，跨库最终一致用消息表/MQ 补偿。**

## 8. 扩容迁移与灰度切流

### 8.1 核心原理

| 方案 | 做法 | 停机 | 风险 |
| --- | --- | --- | --- |
| **停机迁移** | 停写 → dump/导入 → 切流量 | 有（分钟到小时） | 风险最低但不可用于核心业务长停机 |
| **双写迁移** | 应用同时写新旧库（新库为主）→ 全量 + 增量同步历史数据 → 数据校验 → 灰度切读 → 停旧写 | 无 | 双写一致性、写入放大、回滚复杂 |
| **影子表 / 数据同步（DTS/canal）** | 原表不动，用 binlog 订阅工具持续同步到新分片表 → 校验 → 切换读写 | 无 | 依赖 binlog（必须 ROW）、同步延迟、切换瞬间的位点对齐 |

**标准迁移七步**：① 新建目标分片集群并建表；② 开启**增量同步**（DTS/canal/自研，从当前 binlog 位点开始）；③ 全量导出导入历史数据（按分片键并行）；④ 增量追平后做**数据校验**（行数 + checksum 抽样比对）；⑤ 应用**双写**或短暂停写对齐；⑥ **灰度切读**（1% → 10% → 50% → 100%，按用户白名单或 ID 取模）；⑦ 观察无异常后**停写旧库**并保留只读一段时间用于回滚。

**数据校验**：行数对比（`count(*)`）→ 聚合校验（`sum`/`md5(group_concat)` 分片对比）→ 抽样逐行比对（差异行定位修复）。校验工具：`pt-table-checksum`（主从）、`pt-table-sync`（修复）。

### 8.2 面试问答

- **Q1：双写怎么做才安全？** ① 写入顺序"先写旧库再写新库"或反之要有明确决策，通常以新库为准、旧库失败不阻塞主流程并落补偿；② 双写期间读取仍走旧库，保证可回滚；③ 用 MQ/事务消息保证双写的最终一致；④ 灰度切读前必须完成数据校验；⑤ 保留一键回滚开关。
- **Q2：迁移过程中怎么保证不丢数据？** 增量同步必须从"全量开始前的 binlog 位点"起（先记录位点再全量导出），否则全量期间的新写入会丢失；全量导入完成后校验位点是否追平，再切读。
- **Q3：灰度切流怎么做？** 按用户或租户维度做白名单（如 `user_id % 100 < 1`），从 1% 逐步放大；每档观察核心指标（错误率、P99、DB 负载、数据差异告警）；异常时立即把流量切回旧库。
- **Q4：扩容（增加分片数）怎么做？迁移后旧库怎么处理？** 若预留了 2 的幂次倍逻辑分片，只需搬迁整个逻辑分片到新实例：新实例建表 → binlog 同步存量 + 增量 → 校验 → 修改路由（配置中心推送）→ 观察后删旧数据；若无预留则必须全量重分布，等同一次完整迁移。旧库**不要立即下线**：保持只读并保留至少一个业务周期（1~2 周）作为回滚兜底，确认无回滚需求后归档到冷存储再释放。

### 8.3 高频追问与陷阱

- 陷阱：先全量导出再记录位点 → 全量期间的新增/更新数据永久丢失，必须"**先记位点、后全量、再增量**"；另外别跳过数据校验直接切流，分片迁移的差异往往藏在边缘数据（NULL、边界时间、特殊字符）里。

### 8.4 代码/配置/命令示例

```bash
# 1) 记录当前位点/GTID，2) 全量导出，3) 增量同步追平，4) 校验
mysql -e "SHOW MASTER STATUS" > /tmp/pos_before.txt
mysqldump --single-transaction --source-data=2 mydb t > /tmp/t.sql
# canal/DTS 从 /tmp/pos_before.txt 的位点开始订阅 binlog
pt-table-checksum --databases=mydb --tables=t --replicate=percona.checksums
```

### 8.5 一句话速记

**迁移七步：建表 → 增量订阅 → 全量导入 → 校验 → 双写对齐 → 灰度切读 → 停旧库；核心是"先记位点再全量"与"切流前必校验"。**

## 9. ShardingSphere 与 NewSQL（TiDB）对比

### 9.1 核心原理

**ShardingSphere** 是 Apache 顶级项目，三个形态：**ShardingSphere-JDBC**（客户端，jar 包，无额外网络跳数）、**ShardingSphere-Proxy**（服务端代理，对应用透明，多一跳）、**ShardingSphere-Sidecar**（云原生，尚在发展）。核心能力：数据分片（分库分表、读写分离）、分布式事务（XA / Seata 集成）、数据加密（字段级加解密）、影子库（全链路压测）、SQL 审计与链路追踪。使用概要：定义 `actualDataNodes`、`shardingColumn`、`algorithm`（`INLINE`/`MOD`/`HASH_MOD`/`RANGE` 等），配置 `bindingTables`/`broadcastTables`。

**TiDB** 是 NewSQL 代表：计算存储分离，**TiDB Server**（SQL 层，无状态可扩）、**TiKV**（分布式 KV 存储，Raft 多副本）、**PD**（Placement Driver，调度与全局 TSO）。兼容 MySQL 协议，分布式事务基于 Percolator（乐观 + 全局时间戳），5.0+ 通过 TiFlash 提供 HTAP 能力。

| 对比项 | 分库分表（ShardingSphere） | TiDB |
| --- | --- | --- |
| 扩容 | 需搬迁数据，运维成本高 | 在线加节点，自动 rebalance |
| 跨分片查询 | 靠中间件内存归并，能力受限 | SQL 层统一规划，透明支持 |
| 事务 | 局部事务 + 分布式事务（成本高） | 原生分布式事务 |
| 生态/运维 | 复用 MySQL 生态，运维熟悉 | 新体系，需学习与调优（热点、Region 调度） |
| 适用 | 点查为主、已有 MySQL 体系、成本敏感 | 海量数据 + 强一致 + 分析型混合负载 |

### 9.2 面试问答

- **Q1：什么时候选 TiDB 而不是分库分表？** 当业务需要"透明扩容 + 原生分布式事务 + 实时分析"且团队能承担新体系运维成本时；反之若只是单表数据量大的点查业务，分库分表或"归档 + 大宽表 + ES"更划算。
- **Q2：ShardingSphere-JDBC 与 Proxy 怎么选？** JDBC 无额外网络跳数、性能更好，但侵入应用（每个服务都要引依赖升级）、多语言支持差；Proxy 对应用完全透明、支持异构语言，但多一跳且代理本身要集群化保证高可用。
- **Q3：ShardingSphere 的分布式事务怎么用？** 支持 XA（强一致、性能差）、Seata-AT（基于 undo 日志的自动补偿，主流）、以及"本地事务 + 柔性事务"组合。原则仍是：能靠分片键把强一致收敛到单库就不要跨库事务。
- **Q4：分库分表真的值得吗？** 代价清单：跨库查询受限、分布式事务复杂、扩容迁移风险高、运维与排查难度上升、SQL 兼容性受限（`JOIN`/子查询/函数限制）。所以先用尽"索引优化、读写分离、归档、冷热分离、垂直拆分"等手段。
- **Q5：TiDB 的写入热点怎么解决？** 自增主键会造成写热点（新数据集中在一个 Region），解法是用 `AUTO_RANDOM` 或 `SHARD_ROW_ID_BITS` 打散；同时 PD 会调度 Region 均衡，但调度有延迟。

### 9.3 高频追问与陷阱

- 陷阱：把 ShardingSphere 当成"无痛的分布式数据库"，实际它不改变分片键选错带来的根本问题，只是把复杂度转移到中间件配置与 SQL 限制上。
- 陷阱：TiDB 不是万能的——小规模场景下其资源占用与延迟可能不如单机 MySQL；它解决的是规模化与弹性问题。

### 9.4 代码/配置/命令示例

```yaml
# ShardingSphere-JDBC 分片规则概要
dataSources: {ds0: {url: jdbc:mysql://db0:3306/mydb}, ds1: {url: jdbc:mysql://db1:3306/mydb}}
rules:
  - !SHARDING
    tables: {t_order: {actualDataNodes: ds$->{0..1}.t_order_$->{0..1},
      databaseStrategy: {standard: {shardingColumn: user_id, shardingAlgorithmName: db_inline}}}}
    shardingAlgorithms: {db_inline: {type: INLINE, props: {algorithm-expression: ds$->{user_id % 2}}}}
```

### 9.5 一句话速记

**ShardingSphere 管"分片 + 读写分离 + 加密 + 影子库"，TiDB 管"自动分片 + 分布式事务 + HTAP"；前者复用 MySQL 生态、扩容要搬迁，后者弹性但换体系。**

## 10 冷热分离、归档与"能不分就不分"

### 10.1 核心原理

**冷热分离**：按访问频率把数据分层。热数据（近 3 个月）留在 MySQL 主表并配足缓存；温数据（3~12 个月）放同库历史表或只读库；冷数据（1 年以上）归档到对象存储/数仓/ES，仅提供低频或离线查询。实现方式：① **按时间分表**（`order_202401`），查询按时间路由；② **同表加时间条件 + 分区表**（MySQL 分区表在分库分表下兼容性一般，谨慎）；③ 定时任务 + 双写把老数据搬走。

**归档要点**：① 归档任务必须**分批 + 限速**（按主键或时间 `LIMIT` 循环），避免锁表与主从延迟；② 先验证再删除（"先复制、后校验、再删"，保留回滚窗口）；③ 归档期间禁止长事务；④ 归档表结构与查询入口要规划好，否则归档等于"数据丢失"。

**"能不分就不分"的判断标准清单**：① 单表数据量是否真的超过约 2000 万行且已影响性能？② 是否已做索引优化、SQL 改写、读写分离？③ 是否已做冷热分离与历史归档（很多"大表"其实 80% 数据是冷数据）？④ 瓶颈是**读**还是**写**（读瓶颈优先读写分离 + 缓存，写瓶颈才考虑分片）？⑤ 业务是否真的需要跨分片的事务与查询？

### 10.2 面试问答

- **Q1：为什么不建议一上来就分库分表？** 因为它的代价是**不可逆的架构复杂度**：跨库 join/分页/聚合受限、分布式事务、扩容搬迁、SQL 兼容性下降、运维排查更难。而这些代价可以用"索引 + 缓存 + 读写分离 + 归档 + 垂直拆分"以低得多的成本换取。
- **Q2：冷热分离能解决多大问题？** 典型业务中 80% 的查询只访问最近 20% 的数据。把冷数据归档后，主表体积可能缩小数倍，B+ 树变浅、Buffer Pool 命中率提升、备份恢复时间大幅缩短——往往比直接分库分表更划算。
- **Q3：归档任务怎么写？** 按主键游标循环：`DELETE FROM t WHERE id <= ? AND create_time < ? LIMIT 1000`（先 `SELECT ... INTO OUTFILE`/写入归档表再删）；每批之间 `sleep` 限速；监控主从延迟并自动降速；失败可重入。
- **Q4：归档后的历史数据怎么查？面试时怎么回答"你们为什么分库分表"？** 三类查询入口：归档表（同库/只读库）+ 按时间路由；对象存储 + 离线/近线查询（Presto/Hive/Spark）；同步到 ES 提供检索——产品上把"查历史"做成低频独立入口，避免拖慢主链路。回答分库分表要用**结论 + 数据 + 取舍**：单表 X 亿行、单实例 QPS/写入 TPS 达到 Y、Buffer Pool 命中率降到 Z、备份恢复时间不可接受；已做过的优化（索引/缓存/读写分离/归档）与效果；分片键选择理由与跨分片问题如何解决。

### 10.3 高频追问与陷阱

- 陷阱：把归档做成"全量 DELETE + INSERT"，一个巨大事务直接把主从延迟打爆甚至撑爆 undo；另外归档表与主表共用连接池与磁盘会拖慢主链路，归档应走独立实例或低峰限速执行。

### 10.4 代码/配置/命令示例

```sql
-- 分批归档（可重入、限速）
INSERT INTO order_archive SELECT * FROM orders WHERE create_time < '2023-01-01' ORDER BY id LIMIT 1000;
DELETE FROM orders WHERE create_time < '2023-01-01' ORDER BY id LIMIT 1000;
-- 重复执行直到影响行数为 0，每批之间 sleep，并监控 Seconds_Behind_Master
```

### 10.5 一句话速记

**先冷热分离与归档（80% 查询只碰 20% 热数据），再考虑垂直/水平拆分；归档必须分批限速、先验证后删除；分库分表是最后手段而非首选。**

## 自测题（含答案要点）

1. **调优的优先级顺序？`innodb_buffer_pool_size` 怎么定？** —— SQL/索引 > 表结构 > 参数 > 架构；buffer pool 取物理内存 50%~75%，命中率目标 > 99%。
2. **redo 日志设多大？刷盘组合怎么选？** —— 容纳 1~2 小时写入量；按"业务能丢多少数据"选 `flush_log`/`sync_binlog` 组合。
3. **深分页的三种方案？** —— 游标（上次最大 ID）、延迟关联、覆盖索引 + 二次查询。
4. **`count(*)` 与 `count(列)` 的区别？** —— 前者不看 NULL 且会选最小二级索引；后者只统计非 NULL 行，MyISAM 有行数缓存而 InnoDB 必须扫描。
5. **`IN` 与 `EXISTS` 怎么选？批量插入的优化要点？** —— 子查询小用 `IN`、外层小用 `EXISTS`；批量插入多组 VALUES（500~1000/批）+ JDBC `rewriteBatchedStatements=true` + 分批提交。
6. **Online DDL、pt-osc、gh-ost 的差异？** —— 原生 INPLACE 不拷表（部分操作）；pt-osc 靠影子表 + 触发器；gh-ost 靠解析 binlog 同步，无触发器、可暂停限速。
7. **MHA/MGR/Orchestrator/云 RDS 各自特点？架构演进的驱动力？** —— MHA 老牌已停维护；MGR 基于 Paxos 强一致但依赖 GTID+ROW+主键；Orchestrator 拓扑自动化；云 RDS 免运维但受限。演进驱动力：读瓶颈 → 主从/读写分离；写与容量瓶颈 → 分库分表；弹性透明 → NewSQL。
8. **分片键的选择原则？为什么不用 `create_time`？** —— 分布均匀、覆盖高频查询、不可变、与业务主键解耦；`create_time` 单调递增会造成写热点与跨分片范围查询。
9. **跨库 join 的解决思路？** —— 冗余字段、广播表、绑定表、ER 分片、内存组装、异构索引（ES）。
10. **跨库深分页为什么每个分片要取 `offset + limit` 条？** —— 否则汇总后数据不全，会漏掉全局靠前的记录。
11. **雪花算法的时间回拨怎么处理？** —— 小回拨等待、大回拨拒绝并告警，或用逻辑时钟取 `max(now, last)`。
12. **迁移为什么必须"先记位点再全量"？** —— 否则全量导出期间的新写入不在增量同步范围内，会永久丢失；切流前必须完成行数/checksum/抽样三层校验。
13. **"能不分就不分"的判断标准？冷热分离的收益？** —— 单表规模、是否已做索引/缓存/读写分离/归档、瓶颈是读还是写、是否真需要跨分片事务；冷热分离让主表变小、B+ 树变浅、缓存命中率提升、备份恢复变快，往往优于直接分片。
14. **TiDB 与分库分表的核心差异？** —— TiDB 自动分片、原生分布式事务、透明扩容；分库分表需手工迁移且 SQL 能力受限。
15. **归档的三条原则？** —— 分批限速、先验证后删除、保留回滚窗口。

## 背诵卡片

1. 调优优先级：SQL/索引 > 表结构 > 参数 > 架构。
2. Buffer Pool 取物理内存 50%~75%，命中率目标 > 99%。
3. `innodb_buffer_pool_instances` 默认 8，仅 pool ≥ 1GB 生效。
4. 最安全刷盘：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`（8.0 默认）。
5. 5.7 的 `sync_binlog` 默认为 0，生产必须手动改 1。
6. redo 大小目标：容纳 1~2 小时写入量；8.0.30+ 用 `innodb_redo_log_capacity`（默认 100MB）。
7. `long_query_time` 生产建议 0.1~1 秒。
8. 内存临时表上限取 `tmp_table_size` 与 `max_heap_table_size` 的较小值（默认各 16MB）。
9. 深分页首选游标（`WHERE id > lastId`），次选延迟关联。
10. `count(*)`/`count(1)` 会选最小的二级索引，InnoDB 不维护行数。
11. 近似行数：`EXPLAIN` 的 `rows` 或 `information_schema.TABLES.TABLE_ROWS`。
12. 批量插入：多组 VALUES 500~1000/批 + `rewriteBatchedStatements=true`。
13. join 原则：小表驱动大表，被驱动表 join 列建索引。
14. `IN` 与 `EXISTS`：子查询小用 IN，外层小用 EXISTS。
15. 禁止 `SELECT *`：破坏覆盖索引、放大传输、影响排序优化。
16. Online DDL 加索引可 INPLACE + LOCK=NONE；改列类型需 COPY 重建。
17. pt-osc = 影子表 + 触发器；gh-ost = 影子表 + binlog 解析（需 ROW 格式）。
18. gh-ost 可暂停、可限速、无触发器开销，优先选择。
19. DDL 前必须清理长事务并显式调小 `lock_wait_timeout`。
20. MHA 已基本停止维护；MGR 需 GTID + ROW + 每表主键，基于 Paxos 多数派确认，跨机房网络抖动敏感。
21. 脑裂防护：半同步 + 多数派选主 + 旧主 `read_only`。
22. 演进路线：单机 → 主从 → 读写分离 → 分库分表 → NewSQL。
23. 垂直拆分按业务域，水平拆分按分片键；分片键四原则：均匀、覆盖高频查询、不可变、与业务主键解耦。
24. 预留 2 的幂次倍逻辑分片，扩容只需搬迁逻辑分片。
25. 基因法：把分片键基因编码进分布式 ID，使按 ID 也能定位分片。
26. 跨库 join 解法：冗余字段、广播表、绑定表、ER 分片、内存组装。
27. 跨库分页每个分片必须取 `offset + limit` 条再做内存归并。
28. 雪花 ID = 41 位时间 + 10 位机器 + 12 位序列，趋势递增；号段模式一次取一批缓存在内存。
29. 分布式事务优先级：消除 > TCC/Saga > 本地消息表/事务消息 > XA。
30. 迁移顺序：先记位点 → 增量订阅 → 全量导入 → 校验 → 双写 → 灰度切读 → 停旧库；旧库保留只读 1~2 周做回滚兜底。
31. ShardingSphere 三形态：JDBC（客户端）、Proxy（代理）、Sidecar（云原生）。
32. ShardingSphere 能力：分片、读写分离、数据加密、影子库、分布式事务。
33. TiDB = TiDB Server + TiKV + PD，兼容 MySQL 协议，5.0+ 有 TiFlash。
34. TiDB 写热点用 `AUTO_RANDOM` 或 `SHARD_ROW_ID_BITS` 打散。
35. 冷热分离：80% 查询只碰 20% 数据，归档往往优于分片；归档三原则=分批限速、先验证后删除、保留回滚窗口。
