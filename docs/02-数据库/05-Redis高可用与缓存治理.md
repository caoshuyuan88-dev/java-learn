## 1. 缓存穿透、击穿、雪崩

### 1.1 核心原理

三者区别（面试必答）：**穿透**是"**数据不存在**"（输入本身无效），**击穿**是"**单个热点 key 失效**"（规模是点），**雪崩**是"**大批 key 同时失效或缓存整体不可用**"（规模是面）。

| 问题 | 现象与根因 | 方案对比 |
| --- | --- | --- |
| **穿透** | 查不存在的数据，缓存永不命中，每次都打 DB；常见于恶意随机 id | ① **缓存空值**（短 TTL 30~60 秒）；② **布隆过滤器**前置拦截；③ 参数合法性校验（id ≤ 0 直接拒）；④ 接口限流/黑名单 |
| **击穿** | **单个热点 key** 过期瞬间，大量并发同时回源 | ① **互斥锁**（只有一个线程回源，其余等待重试）；② **逻辑过期**（不设 TTL，value 带过期时间，异步刷新）；③ 热点 key 永不过期 + 后台定时刷新 |
| **雪崩** | 大批 key 同时过期，或 Redis 宕机/集群故障，DB 被打满 | ① **过期时间加随机值**（基础 TTL + 随机 0~300 秒）；② **多级缓存**；③ 熔断降级；④ Redis 高可用（主从 + 哨兵/Cluster）；⑤ 提前预热 |

**互斥锁方案的三个坑**：① 回源失败必须释放锁并让等待者重试，否则永久阻塞；② 锁必须有过期时间（`SET NX EX`），防止持锁线程崩溃死锁；③ 等待者要"短暂 sleep 后重试"或"返回降级值"，避免线程堆积在锁上。

**逻辑过期方案的两个坑**：① 需异步线程池刷新且**同一 key 只能有一个刷新任务**；② 返回的是旧数据，业务必须能接受短暂不一致，并配空值兜底。

### 1.2 面试问答

- **Q1：缓存穿透怎么治？** 优先"缓存空值 + 参数校验"（成本最低），恶意攻击场景再加布隆过滤器与限流。空值必须设短 TTL，并在真实数据写入时**主动删除该空值 key**，否则会长期读到脏空值。
- **Q2：击穿为什么比穿透更危险？** 它打的是同一个热点 key，瞬间并发全部涌向 DB 的同一行/同一查询，容易锁住该行或打满 DB；穿透的危险程度取决于攻击强度。
- **Q3：互斥锁和逻辑过期怎么选？** 要求**强一致**（不能返回旧数据）用互斥锁，代价是等待；能接受**短暂不一致**、追求低延迟用逻辑过期。秒杀商品详情页常用逻辑过期，订单状态查询常用互斥锁。
- **Q4：雪崩的根因只有"同时过期"吗？怎么降级？** 不止——更严重的是 **Redis 整体故障**（宕机、分区、主从切换期间不可写），所以除了 TTL 打散还要靠高可用 + 熔断 + 多级缓存。降级顺序：读本地缓存 → 返回兜底默认值 → 查 DB 但**必须限流 + 熔断** → 关闭非核心功能。

### 1.3 高频追问与陷阱

- 陷阱：布隆过滤器"说不存在"才可信、"说存在"可能误判，必须配合 DB 查询兜底；另外别给穿透的空值 key 设很长 TTL，否则真实数据写入后长期读不到。

### 1.4 代码/配置/命令示例

```java
// 互斥锁回源（伪代码）：只有一个线程回源，其余等待后重试
String value = redis.get(key);
if (value == null && redis.set(lockKey, uuid, "NX", "EX", 10) != null) {
    try { redis.set(key, loadFromDB(key), "EX", 300 + rand(300)); }  // TTL 打散
    finally { redis.del(lockKey); }                                   // 生产用 Lua 校验 value 后删
} else if (value == null) {
    Thread.sleep(50); value = redis.get(key);                         // 或直接返回降级值
}
```

### 1.5 一句话速记

**穿透=数据不存在（空值/布隆/校验），击穿=单热点失效（互斥锁/逻辑过期），雪崩=批量失效或整体故障（随机 TTL + 多级缓存 + 熔断 + 高可用）。**

## 2. 布隆过滤器

### 2.1 核心原理

**原理**：一个长度为 `m` 的位数组加 `k` 个独立哈希函数。插入元素时用 `k` 个哈希算出 `k` 个位置并置 1；查询时若**任一位置为 0 则元素一定不存在**，若全为 1 则"可能存在"。因此它**只有假阳性（误判存在），没有假阴性（不会漏判不存在）**。

**误判率与参数**：误判率近似 `p ≈ (1 - e^(-kn/m))^k`（`n` 为元素个数）。给定 `n` 与目标 `p`，最优哈希个数 `k ≈ (m/n) · ln2`，所需空间 `m ≈ -n·ln p / (ln2)²`。例如 `n = 1 亿、p = 1%` 时约需 **9.6 bit/元素 ≈ 114MB**；同样的数据用 Set 存字符串将占用 GB 级内存。

**不支持删除**：把某个位置清零会影响其他共享该位置的元素（导致假阴性），所以 RedisBloom 的**基础布隆过滤器不支持删除**。需要删除时用：① **Counting Bloom Filter**（每位用计数器代替单比特，支持删除但内存翻倍/多倍）；② **Cuckoo Filter**；③ 用 TTL + 定期重建。

**RedisBloom**：Redis 官方模块（`redis-stack` 自带，或单独加载 `redisbloom.so`），命令：`BF.RESERVE key error_rate capacity`（建过滤器并指定误判率与容量）、`BF.ADD`/`BF.MADD`、`BF.EXISTS`/`BF.MEXISTS`、`BF.INFO`。原理上是可扩展布隆过滤器（容量用尽时自动追加一个子过滤器）。不装模块时也可以用 `SETBIT`/`GETBIT`/`BITCOUNT` 手写，但需自己管理哈希与参数。

### 2.2 面试问答

- **Q1：布隆过滤器为什么会误判？** 不同元素的哈希结果可能落在相同位置，位数组被多个元素共同置位；查询一个**未插入**的元素时，其对应位置恰好都被其他元素置 1，就会误判为存在。
- **Q2：为什么不能删除元素？** 每个位可能被多个元素共享，把它清零会同时"删掉"其他元素的存在性标记，从而产生**假阴性**（漏判存在的数据），破坏"说不存在就一定不存在"的核心保证。
- **Q3：误判率怎么控制？** 通过位数组长度 `m`、哈希个数 `k` 与元素数 `n` 三者的关系控制：`m` 越大、`k` 取最优值（约 `m/n·ln2`）时误判率越低。注意容量用尽后误判率会上升，RedisBloom 会自动追加子过滤器来缓解。
- **Q4：缓存穿透场景下布隆过滤器放在哪？** 放在**缓存之前**：请求先过布隆过滤器，说不存在就直接拒绝（不查 Redis 也不查 DB），说可能存在再走"查缓存 → 查 DB"的正常路径。数据新增时要同步 `BF.ADD`，删除时无法同步（需要定期重建或改用 Counting/Cuckoo）。
- **Q5：布隆过滤器与 Redis Set 去重的取舍？** Set 精确且支持删除，但内存占用大（元素本身要存储）；布隆过滤器内存效率高两个数量级左右，但存在误判且不支持删除。海量去重/判存用布隆，精确去重用 Set/`HyperLogLog`（后者只做基数估算也不支持判存）。

### 2.3 高频追问与陷阱

- 陷阱：把布隆过滤器的"存在"当真实存在使用（例如直接放行请求而不查 DB），会因误判把不存在的请求放到下游。
- 陷阱：容量估算不足（`BF.RESERVE capacity` 设小了）会让误判率快速上升，必须按增长预期预留容量。

### 2.4 代码/配置/命令示例

```bash
# 期望误判率 0.1%，容量 100 万
redis-cli BF.RESERVE goods:bf 0.001 1000000
redis-cli BF.MADD goods:bf 1001 1002 1003
redis-cli BF.EXISTS goods:bf 1001        # 1 = 可能存在，0 = 一定不存在
redis-cli BF.INFO goods:bf
```

### 2.5 一句话速记

**布隆过滤器 = 位数组 + k 个哈希，"不存在"必真、"存在"可能误判；`m ≈ -n·ln p/(ln2)²`，基础版不支持删除，Redis 用 RedisBloom 模块。**

## 3. 热点 key 与多级缓存

### 3.1 核心原理

**热点 key 的危害**：单 key 的 QPS 极高时，即使 Redis 集群有几十个节点，这个 key 也只落在一个节点上，会把该节点的 CPU/网卡打满，并拖慢该节点上所有其他请求。

**发现手段**：`redis-cli --hotkeys`（**需要 `maxmemory-policy` 为 `allkeys-lfu` 或 `volatile-lfu`**）、客户端埋点统计（在统一缓存客户端里按 key 维度计数上报）、代理层统计（自研代理/Codis 可以在转发层统计）、`MONITOR`（**会把所有命令推送给 monitor 客户端，高 QPS 下极其危险，生产禁用**）。经验上"热点"往往是可预测的（首页商品、秒杀、明星微博、配置），可以靠业务侧主动上报。

**多级缓存（本地 Caffeine + Redis）**：请求先查进程内本地缓存（纳秒级、无网络），未命中再查 Redis，再未命中查 DB。收益是抗住极高 QPS、避免网络与 Redis 单点压力。

| 关注点 | 做法 |
| --- | --- |
| 一致性 | 本地缓存必须设**短 TTL**（如 1~5 秒）兜底；配合 **Redis Pub/Sub 或 MQ 广播失效**消息，各实例收到后清理本地缓存 |
| 容量控制 | Caffeine 设 `maximumSize` + `expireAfterWrite`，避免本地缓存吃光堆内存导致 Full GC |
| 热点判定 | 结合 `--hotkeys` 与业务埋点，只把"真热点"放进本地缓存，避免本地缓存命中率低却占用大量内存 |
| 升级路径 | 本地 + Redis 仍不够时，用**热点 key 多副本**：给同一份数据写多个 key（如 `hot:1:{0..9}`），客户端随机选一个副本读，把流量分散到多个节点 |

**读写分离与多副本**：Redis Cluster 的从节点默认只做故障转移、**不承担读流量**（可以通过 `READONLY` 命令让客户端从从节点读，但需自行接受复制延迟与一致性风险）。若读压力极大，可用"一主多从 + 客户端读从"或"热点 key 多副本 + 随机路由"来分摊。

### 3.2 面试问答

- **Q1：本地缓存与 Redis 的一致性怎么保证？** 三层防护：① 本地缓存设**极短 TTL**（秒级），即使失效消息丢了也会很快过期；② 数据变更时通过 Redis Pub/Sub 或 MQ **广播失效消息**，各实例清理对应 key；③ 对强一致要求高的数据（如库存）**不放进本地缓存**。
- **Q2：热点 key 怎么分散？** ① 本地缓存挡掉绝大部分请求；② 多副本：`key` 拆成 `key:0`~`key:9` 写多份，读时随机选一个，把单节点压力降为 1/10；③ 读多写少的静态数据直接放本地缓存 + 对象存储/CDN。
- **Q3：为什么不能用 `MONITOR` 找热 key？** 它会把每条命令实时推送给所有 monitor 客户端，高 QPS 下监控端成为瓶颈、网络被打满、Redis 输出缓冲暴涨甚至触发 `client-output-buffer-limit` 断连——排查手段本身成了故障源。
- **Q4：`--hotkeys` 有什么前提？** 必须把 `maxmemory-policy` 设为 LFU 系列（`allkeys-lfu`/`volatile-lfu`），因为热 key 统计依赖 LFU 的访问计数；否则命令会直接报错。同时建议在从库或低峰执行，降低线上影响。
- **Q5：多级缓存的典型故障是什么？** ① 本地缓存与 Redis 不一致导致"同一用户刷出不同数据"；② 本地缓存无上限导致 Full GC / OOM；③ 缓存穿透到 DB 时**所有实例同时回源**（需要互斥锁 + 限流）。上线前必须做容量与一致性压测。

### 3.3 高频追问与陷阱

- 陷阱：把"热点 key 分片"当成万能解——它只解决**读热点**，对写热点（同一 key 高频写）需要改成"分片累加 + 定期合并"（如计数器分片 `counter:{0..9}` 各自 `INCR`，读取时求和）。
- 陷阱：本地缓存不做失效广播、只靠长 TTL，会导致数据长时间不一致。

### 3.4 代码/配置/命令示例

```java
// Caffeine 本地缓存：短 TTL 兜底 + 容量上限；变更时广播失效
Cache<String, String> local = Caffeine.newBuilder().maximumSize(10_000)
        .expireAfterWrite(Duration.ofSeconds(3)).build();
redis.publish("cache:evict", key);   // 各实例订阅后 local.invalidate(key)
// 热 key 发现：redis-cli CONFIG SET maxmemory-policy allkeys-lfu && redis-cli --hotkeys
```

### 3.5 一句话速记

**热 key 用 `--hotkeys`（需 LFU）发现，靠"本地 Caffeine + 短 TTL + 失效广播"抗读峰值，再用多副本随机路由分散；`MONITOR` 生产禁用。**

## 4. 缓存预热、降级与空值兜底

### 4.1 核心原理

**缓存预热**：在上线/大促/活动开始前，把热点数据主动加载进缓存，避免冷启动瞬间大量请求穿透到 DB。实现：① 应用启动时用定时任务/`ApplicationRunner` 批量加载；② 大促前用脚本按"历史 top N 访问"逐批预热；③ 预热要**限速 + 分批**，避免预热本身打满 DB 或 Redis。

**缓存降级**：当缓存层不可用（超时、连接失败、错误率超阈值）时按预案降级，优先级从高到低：① 读本地缓存；② 返回兜底默认值/静态内容；③ 直接查 DB，但**必须限流 + 熔断**，并接受部分请求失败；④ 关闭非核心功能。实现上通用做法是用 Sentinel/Hystrix 对 Redis 调用做熔断，熔断打开后直接走降级逻辑。

**空值兜底的两层含义**：① **穿透防护**：查询结果为空的 key 也写缓存（值为特殊标记，如空字符串），设短 TTL；② **降级兜底**：缓存与降级都失败时返回"暂无数据"而非抛异常，保证页面可用。

**缓存 key 设计要点**：统一前缀 + 业务维度（`biz:type:id:version`）；缓存值用**带版本的包装对象**（便于灰度与排查）；TTL 必须设置（除极少数"永不过期 + 后台刷新"的热点 key）；序列化优先用紧凑格式（如字符串、JSON、MessagePack），避免 Java 原生序列化（体积大、跨语言差、有安全风险）。

### 4.2 面试问答

- **Q1：预热为什么必须限速？** 一次性把几百万 key 写进缓存会瞬间打满 Redis 的 CPU/网络与 DB 的连接数，反而制造雪崩。做法是通过脚本分批写入、按 QPS 水位控制速率、从库读数据避免影响主库。
- **Q2：缓存降级的原则是什么？** "保核心、舍边缘"：核心链路（下单、支付）优先保障，非核心（推荐、评论、统计）可降级返回默认值或直接不展示；同时必须**限制降级后打到 DB 的流量**，否则降级等于把故障转移给 DB。
- **Q3：空值缓存的 TTL 设多长？** 短（30~60 秒）。太长会掩盖后来写入的真实数据；太短则穿透防护效果有限。更稳妥的做法是在真实数据写入时**主动删除该空值 key**。
- **Q4：为什么不用 Java 原生序列化？** ① 序列化后体积大（含类元信息），网络与内存开销高；② 反序列化存在安全风险（反序列化漏洞）；③ 与 Java 强耦合，无法跨语言。推荐 JSON（可读、通用）或 MessagePack/Protobuf（紧凑）。
- **Q5：缓存 key 为什么要带版本号？** 数据结构变更（新增字段、改变语义）时，可以通过**切换版本号**让新旧缓存自然隔离（新 key 前缀），避免"读到旧结构导致反序列化失败"的批量故障。

### 4.3 高频追问与陷阱

- 陷阱：降级逻辑里直接"无限制查 DB"，把缓存故障升级成数据库故障——降级必须与限流绑定。
- 陷阱：预热不加限速，预热任务本身就是一次小型雪崩。
- 追问：缓存 key 一定要设 TTL 吗？除了极少数"热点 + 后台刷新"的 key，都应当设 TTL，作为一切一致性问题的最终兜底。

### 4.4 代码/配置/命令示例


## 5. 分布式锁的完整实现

### 5.1 核心原理

**最小可用实现（SET NX EX + 唯一 value + Lua 释放）**：`SET lockKey uuid NX PX 30000`，释放时用 Lua 校验 value 相等再删除。**四个必须做到的点**：① 用 `SET key value NX PX ms` **一条命令**加锁（拆成 `SETNX` + `EXPIRE` 时中途崩溃会死锁）；② value 必须是**每线程唯一**标识（UUID + 实例标识），否则会误删别人的锁；③ 释放必须用 **Lua 保证原子**（`GET` 比较与 `DEL` 之间锁可能已过期并被别人持有）；④ 必须有超时时间。

**可重入**：用 Hash 存 `{requestId: 重入次数}`，加锁时 `HINCRBY`、解锁时递减到 0 才删除（Redisson `RLock` 用 Lua 实现）。

**看门狗（watchdog）续期**：业务耗时不可控，锁 TTL 到点自动释放会导致"锁提前失效 + 并发进入"。Redisson 默认 `lockWatchdogTimeout = 30 秒`，加锁成功后启动后台任务每 `TTL/3`（10 秒）检查并续期，直到显式 `unlock` 或客户端宕机（宕机后不再续期，锁最终自动释放）。

**RedLock 及其争议**：要求部署 **N 个独立的 Redis 主节点**（无主从关系），客户端向所有节点加锁，**多数派成功且总耗时小于锁有效期**才算成功。**Martin Kleppmann** 指出它依赖各节点时钟不发生大幅漂移，且无法避免"GC 停顿/网络延迟导致业务在锁失效后才继续执行"；**Antirez** 认为在"锁只用于提高效率、失败时有其他兜底"的前提下可靠。**主流结论：RedLock 有争议，强正确性场景应靠 DB 唯一约束/乐观锁/事务，分布式锁用于提高效率而非保证绝对安全。**

**锁超时与业务耗时的矛盾**（最本质的问题）：业务耗时 > 锁 TTL 时锁自动释放、第二个线程进入、两者并发执行导致数据错乱。三种应对：① **看门狗续期**（前提是进程没卡死）；② **业务限时**，超时快速失败；③ **数据层兜底**——用唯一约束或乐观锁（`version`/条件更新）做最终校验，**任何分布式锁都不应作为唯一的安全防线**。

### 5.2 面试问答

- **Q1：为什么不推荐 `SETNX` + `EXPIRE` 两步？** 两步之间客户端崩溃/网络中断，锁就永远不过期（死锁），必须用 `SET ... NX PX` 原子完成；同理，释放锁不用 Lua 的话，`GET` 与 `DEL` 之间锁可能已易主，会误删别人的锁。
- **Q2：锁的过期时间怎么定？** 以"业务 P99 耗时 × 2~3 倍"为起点，再配合看门狗续期；手工实现时宁可偏长（但要短于故障恢复容忍度），同时业务侧必须有超时控制。
- **Q3：Redisson 的 `RLock` 还做了什么？** `tryLock(waitTime, leaseTime, unit)` 支持等待与租期；内部用 **Hash 结构存重入计数**、Lua 保证原子、看门狗自动续期、基于 **Redis Pub/Sub 的释放通知**实现等待队列（避免自旋）；`RedissonMultiLock` 可表达 RedLock 语义。
- **Q4：持有锁的线程宕机怎么办？能用 Redis 锁做资金安全吗？** 靠 TTL 自动释放（这就是锁必须有过期时间的原因）：客户端存活时看门狗续期，挂掉后停止续期，锁在 TTL 后释放，其他线程可重新获取，代价是这段时间业务不可用。**资金安全不建议只靠 Redis 锁**——存在"锁失效后业务仍继续执行"的窗口（GC 停顿、网络延迟），应在 DB 层用唯一约束、行锁或乐观锁做最终校验。

### 5.3 高频追问与陷阱

- 陷阱：用 `Thread.currentThread().getId()` 当 value——多实例部署时不同 JVM 的线程 ID 可能相同，会互相误删锁，必须用 UUID + 实例标识；另外别在 `finally` 里无脑 `DEL`，也不要把加锁放在事务内层导致锁范围与事务边界不一致（集群模式下主从切换可能丢锁，更要把正确性交给数据层）。

### 5.4 代码/配置/命令示例

```java

String ok = jedis.set(lockKey, id, SetParams.setParams().nx().px(30000));
if (!"OK".equals(ok)) return false;
String lua = "if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end";

// 推荐做法：Redisson 自带可重入、看门狗（租期 30s 触发）与 Pub/Sub 等待
RLock lock = redissonClient.getLock("order:lock:" + orderId);
if (!lock.tryLock(3, 30, TimeUnit.SECONDS)) throw new BizException("系统繁忙，请重试");

```

### 5.5 一句话速记

**`SET key uuid NX PX` 一条命令加锁 + 唯一 value + Lua 原子释放是底线；可重入用 Hash 计数、续期靠看门狗；RedLock 有争议；锁超时与业务耗时的矛盾的终极解法是数据层兜底。**

## 6. Redis 限流实现

### 6.1 核心原理

| 算法 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **固定窗口计数器** | `INCR key` + `EXPIRE`，每窗口一个计数 | 实现最简单 | **临界问题**：窗口边界两侧可各放行一个窗口的量（约 2 倍） |
| **滑动窗口** | ZSet 存请求时间戳，`ZREMRANGEBYSCORE` 清理过期 + `ZCARD` 计数 + `ZADD` 记录 | 平滑、精确 | 每个请求都要存一条记录，内存开销大（大流量下昂贵） |
| **令牌桶** | 按速率往桶里放令牌，请求取令牌 | 允许**突发流量**，最常用 | 实现稍复杂（需 Lua 保证原子） |
| **漏桶** | 请求进桶，按固定速率流出 | 输出速率恒定、削峰 | 不允许突发，排队会引入延迟 |

**Redis + Lua 实现要点**：所有"读计数 → 判断 → 写计数 → 设置过期"的步骤必须放进 **一段 Lua 脚本**，否则并发下会超发。令牌桶的 Lua 核心逻辑是：计算"距上次补充的令牌数 = (now - lastRefillTime) × rate"，`min(capacity, tokens + 补充量)`，若 `tokens >= 1` 则扣减并放行。

**与网关限流的分工**：① **网关层（Nginx `limit_req`/`limit_conn`、Spring Cloud Gateway + Redis RateLimiter、Sentinel 网关流控）**做**全局、粗粒度、面向 IP/接口**的限流，拦掉绝大部分无效与恶意流量，成本最低；② **应用层**做**业务细粒度**限流（按用户、按商户、按资源维度），因为网关看不到业务身份；③ 两者叠加，网关是"防洪堤"，应用层是"精确阀门"。分布式限流用 Redis（或 Sentinel 集群流控），单机限流用 Guava `RateLimiter`/Sentinel 本地规则即可（性能更好、无网络依赖）。

### 6.2 面试问答

- **Q1：为什么固定窗口有临界问题？** 假设限制"每分钟 100 次"，在第 59 秒发 100 次、第 61 秒又发 100 次，虽然跨越窗口边界，但实际在 2 秒内放行了 200 次。滑动窗口或令牌桶可以消除这个问题。
- **Q2：滑动窗口为什么用 ZSet？** 因为需要按时间戳做范围删除与计数：`ZREMRANGEBYSCORE key 0 (now-window)` 清掉过期请求，`ZCARD` 得到窗口内请求数，`ZADD` 记录本次请求。缺点是每个请求一条记录，内存开销与 QPS×窗口 成正比。
- **Q3：令牌桶怎么支持突发？** 桶有容量上限，空闲时令牌累积到满桶，突发流量可一次性取走全部令牌（受容量限制），因此短时突发被允许，而长期平均速率仍受令牌补充速率约束。
- **Q4：限流阈值怎么定？** 基于压测与容量估算：`阈值 = 单实例安全 QPS × 实例数 × 安全系数(0.7~0.8)`。同时区分"入口限流"（保护整体）与"依赖限流"（保护下游 DB/第三方接口），并配合排队、熔断与降级。
- **Q5：限流和熔断的区别？** 限流是**主动控制入口流量**（不超过处理能力）；熔断是**被动切断对故障依赖的调用**（连续失败率达阈值后快速失败，避免雪崩）。限流通常量级更细（QPS/并发数），熔断针对错误率与响应时间。

### 6.3 高频追问与陷阱

- 陷阱：把"读计数 + 判断 + 写计数"拆成多条命令发送，并发下必然超发——必须用 Lua 或 `INCR` 后判断的原子语义。
- 陷阱：限流 key 不设过期时间，导致计数永远累积；每个窗口/桶都要有合理的 TTL。
- 追问：Redis 限流本身可能成为瓶颈（所有请求都打同一个 key），热点接口可用"本地限流 + Redis 限流"两级，或对限流 key 做分片。

### 6.4 代码/配置/命令示例

```lua
-- 滑动窗口限流（KEYS[1]=限流key, ARGV[1]=now_ms, ARGV[2]=窗口ms, ARGV[3]=阈值）
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
    redis.call('ZADD', KEYS[1], ARGV[1], ARGV[1] .. '-' .. math.random(100000))
    redis.call('PEXPIRE', KEYS[1], ARGV[2])
    return 1
end
return 0
```

```bash
redis-cli EVAL "$(cat limit.lua)" 1 rate:user:1001 $(date +%s%3N) 60000 100
```

### 6.5 一句话速记

**固定窗口简单但有临界问题，滑动窗口（ZSet）精确但费内存，令牌桶允许突发最常用；限流的"读判写"必须用 Lua 原子完成；网关做全局粗粒度、应用做业务细粒度。**

## 7. 计数器、点赞与幂等

### 7.1 核心原理

**计数器**：`INCR`/`INCRBY`/`HINCRBY` 都是原子操作，天然适合计数。要点：① 计数 key 必须有 TTL 或定期归档，否则无限增长；② **写热点**（同一 key 高频 `INCR`）会造成单节点压力，解法是**分片计数**——写 `counter:{0..9}` 随机一片，读时求和（`MGET` + 累加），再定时合并到主 key。

**点赞的几种实现**：

| 方案 | 结构 | 特点 |
| --- | --- | --- |
| Set | `SADD like:post:1 userId` | 天然去重、可查"谁点了赞"；百万级点赞内存开销大 |
| Hash | `HSET like:post:1 userId 1` | 同上，可扩展记录时间等元信息 |
| **Bitmap** | `SETBIT like:post:1 userId 1` | **最省内存**（1 亿用户约 12.5MB），但要求 userId 是连续小整数；统计用 `BITCOUNT`，判存用 `GETBIT` |
| 计数器 | `INCR like:count:1` | 只存总数，不存明细，最省内存 |

实践中常见组合：**Bitmap/HyperLogLog 做去重与计数，明细落 DB/数仓**；点赞状态用 Bitmap 判存（`GETBIT`），总赞数用单独计数器。

**幂等**：同一请求重复执行与执行一次的效果相同。Redis 侧手段：① `SET key value NX EX` 做**幂等令牌**（一次有效，请求处理成功后可选保留一段时间防重放）；② 用业务唯一键（订单号 + 操作类型）作为 key 做"已处理"标记；③ 拦截重复请求要与**业务状态机**配合（如"订单已支付"状态判断）。注意：Redis 的幂等标记只解决"短时间重复提交"，**真正的幂等底线是数据库唯一索引 + 状态机**。

### 7.2 面试问答

- **Q1：点赞用 Set 还是 Bitmap？** 用户 ID 是连续小整数且量级大 → Bitmap（内存效率最高）；需要记录点赞时间/用户属性 → Hash；用户 ID 是稀疏大整数或非数值 → Set。核心权衡是内存与信息量。
- **Q2：怎么处理"点赞计数"与"点赞明细"不一致？** 计数与明细分开存储必然会漂移（并发、超时、失败），因此要以**明细为准**定期重算计数，或把"用户是否点赞"作为权威数据、总赞数作为派生数据。出现不一致时以 DB 明细为准做对账修复。
- **Q3：`INCR` 高并发写同一个 key 有问题吗？** 有。单节点 CPU 会被这一个 key 打满（虽然 `INCR` 很快，但仍是单点串行）。解法是分片计数（写随机分片、读求和），或先本地聚合批量提交（把 100 次 `INCR` 合并成 1 次 `INCRBY 100`）。
- **Q4：幂等为什么要配状态机？** 仅靠 Redis 标记只能防"短时间内的重复请求"；如果标记 key 过期或 Redis 数据丢失，重复请求仍会进来。真正可靠的是在 DB 层用**唯一约束**（如 `(order_no, action)` 唯一索引）+ **状态机校验**（只允许从"待支付"变为"已支付"）。
- **Q5：点赞数据怎么落地？** 高并发点赞先写 Redis（`INCR` + Bitmap/Set 判存），再通过 MQ/定时任务**异步落库**；落库时用"幂等 + 累加"语句（`INSERT ... ON DUPLICATE KEY UPDATE cnt = cnt + 1`）避免覆盖写。要注意异步落库的延迟与对账。

### 7.3 高频追问与陷阱

- 陷阱：用 Bitmap 时 userId 不连续（雪花 ID）会导致位数组稀疏巨大——此时应改用 Set/Hash，或先做 ID 映射。
- 陷阱：幂等 key 不设过期时间，长期占用内存；设得太短则起不到防重放作用。

### 7.4 代码/配置/命令示例

```bash
# Bitmap 点赞：判存 + 计数
redis-cli SETBIT like:post:1001 88001 1
redis-cli GETBIT like:post:1001 88001
redis-cli BITCOUNT like:post:1001
# 分片计数：写随机分片，读求和
redis-cli INCR counter:post:1001:3
redis-cli MGET counter:post:1001:0 counter:post:1001:1 counter:post:1001:2
# 幂等令牌
redis-cli SET idem:order:20240101:1001 1 NX EX 60
```

### 7.5 一句话速记

**计数用 INCR（热点要分片），点赞用 Bitmap/Hash 判存 + 独立计数器，幂等用 `SET NX EX` 做临时防重 + DB 唯一索引与状态机做最终保证。**

## 8. 大 key 治理与集群运维

### 8.1 核心原理

**大 key 拆分**：目标是让单个 key 的 value 规模可控（经验阈值：String < 10KB，集合类元素数 < 5000）。

| 结构 | 拆分方式 |
| --- | --- |
| 大 Hash | 按字段哈希拆成多个 key（`h:1001:0`~`h:1001:9`），查询时先算分片；或用 `HSCAN` 分批读 |
| 大 List | 按序号分片（`list:0`、`list:1`），或改造成 Stream 按段消费 |
| 大 Set / ZSet | 按元素的哈希分片，或用 `SSCAN`/`ZSCAN` 分页读 |
| 大 String | 拆成多个段落 key，或改为对象存储 + 缓存索引 |

**删除与异步释放**：`DEL` 大 key 会阻塞主线程（释放大量内存 + 可能的 dict 缩容），必须用 **`UNLINK`**（4.0+，把对象放到后台线程释放）。同时开启 `lazyfree-lazy-expire yes`、`lazyfree-lazy-eviction yes`、`lazyfree-lazy-server-del yes`，让过期、淘汰、`FLUSHDB` 等也走异步路径。

**集群运维要点**：① **扩容**：新节点加入后 `CLUSTER ADDSLOTS`/`--cluster reshard` 迁移槽，单次迁移量要小、低峰执行，避免 `MIGRATE` 大 key 阻塞源节点；② **槽均衡**：`redis-cli --cluster rebalance`，先看 `--cluster check` 的槽分布；③ **内存告警**：`used_memory / maxmemory` 超过 **80%** 告警，超过 **90%** 严重告警；同时监控 `evicted_keys`（淘汰速率）、`mem_fragmentation_ratio`、`rejected_connections`、`blocked_clients`；④ **`maxmemory-policy` 选择**：纯缓存用 `allkeys-lru`（或 `allkeys-lfu`），混存持久数据用 `volatile-*` 并确保有 TTL 的 key 足够多；⑤ 客户端输出缓冲与复制缓冲也要监控（`CLIENT LIST` 的 `omem`），否则会莫名断连。

### 8.2 面试问答

- **Q1：为什么 `DEL` 大 key 会阻塞？** 删除要遍历并释放该 key 的所有元素（大 Hash 可能有几百万元素），同时可能触发字典缩容，整个过程在主线程完成。用 `UNLINK` 把内存释放交给后台线程即可。
- **Q2：大 key 怎么发现？** `redis-cli --bigkeys`（基于 `SCAN`，低峰/从库执行）、`MEMORY USAGE key`（精确字节数）、`--memkeys`（按内存采样）、对已知业务 key 做定时统计。`DEBUG OBJECT` 生产禁用。
- **Q3：槽迁移为什么也可能阻塞？** `MIGRATE` 是同步命令，若迁移的 key 很大，源节点在迁移期间会阻塞（同时网络传输占用带宽）。做法是先把大 key 拆小、或按 key 逐个迁移并限速（`--cluster-pipeline` 控制）。
- **Q4：内存告警线怎么定？** 常规 80% 预警、90% 严重；同时要看**增长趋势**与**淘汰速率**：`evicted_keys` 快速增长说明已经影响业务（有数据被淘汰），即使内存还没到 90% 也要立即扩容。另外预留 20%~30% 给复制缓冲与 COW。
- **Q5：`maxmemory-policy` 怎么选？** 纯缓存实例 → `allkeys-lru`（或热点明显的场景用 `allkeys-lfu`）；同一实例混有不可丢数据 → `volatile-lru`/`volatile-lfu` 并**保证有 TTL 的 key 占多数**；绝不能在生产长期使用 `noeviction`（写满即报错）。

### 8.3 高频追问与陷阱

- 陷阱：用 `FLUSHDB`/`FLUSHALL` 清理数据——会阻塞且不可恢复，生产应通过 `SCAN` 分批 `UNLINK`。
- 陷阱：扩容只加节点不迁移槽，新节点空闲而老节点仍然满；扩容必须完成槽再平衡。

### 8.4 代码/配置/命令示例

```bash
redis-cli --bigkeys -i 0.1                     # 低峰或从库执行
redis-cli MEMORY USAGE big:hash
redis-cli UNLINK big:hash                      # 异步删除，避免阻塞
redis-cli --cluster check 127.0.0.1:7000
redis-cli --cluster rebalance 127.0.0.1:7000 --cluster-use-empty-masters
redis-cli INFO memory stats | grep -E "used_memory_human|evicted_keys|rejected_connections"
```

```conf
lazyfree-lazy-eviction yes
lazyfree-lazy-expire yes
lazyfree-lazy-server-del yes
maxmemory-policy allkeys-lru
```

### 8.5 一句话速记

**大 key 按字段/序号分片，删除一律用 `UNLINK` 并开 `lazyfree-*`；集群运维看"内存 80% 预警 + 淘汰速率 + 槽均衡"，扩容必须把槽迁完。**

## 9. 压测与容量估算

### 9.1 核心原理

**QPS 估算**：单实例 Redis（简单命令、无 pipeline、千兆网卡）在常规服务器上大致可支撑 **8 万~10 万 QPS**；使用 pipeline 可显著提升（受网络与命令大小限制）；复杂命令（`ZADD` 大 ZSet、`HGETALL` 大 Hash）会大幅下降。**这些是量级参考，必须用 `redis-benchmark` 在真实环境实测**：

```bash
redis-benchmark -h 127.0.0.1 -p 6379 -c 50 -n 100000 -t set,get -P 1
redis-benchmark -h 127.0.0.1 -p 6379 -c 50 -n 100000 -t set,get -P 16   # 带 pipeline
redis-benchmark -h 127.0.0.1 -p 6379 -n 100000 -q -r 100000 -d 128      # 随机 key、128 字节值
```

**内存估算**：`总内存 ≈ 数据量 × (1.5~2)`，多出的部分来自 `redisObject` 头、`dictEntry`（哈希表节点）、jemalloc 的对齐与碎片、以及复制缓冲/AOF 缓冲。粗算法：`key 数 × (key 长度 + value 长度 + 约 50~100 字节开销)`。例：1000 万 key、key 32 字节、value 100 字节 → 数据约 1.32GB，实际占用按 1.5~2 倍估算约 **2~2.6GB**。**不要用理论值直接规划容量，必须实测 + 留 30% 余量。**

**连接数**：`maxclients` 默认 **10000**；每个连接除基础结构外还要算**输出缓冲区**（`client-output-buffer-limit normal 0 0 0` 默认不限，但 pub/sub 与 replication 有限制）。连接数过多会显著增加内存与上下文切换开销，因此**客户端应使用连接池**并限制大小（Redis 是单线程，几千连接已足够）。

**压测要点**：① 用**真实数据分布**（key 大小、命令类型、读写比例），不要只用 `SET/GET`；② 同时观测 `redis-cli --latency`、`INFO stats`（`instantaneous_ops_per_sec`、`rejected_connections`）、`INFO memory`、`INFO cpu`；③ 压测 **P99/P999 延迟**而不是平均值；④ 一定要测**故障场景**（主从切换、大 key、AOF 重写期间的延迟）。

### 9.2 面试问答

- **Q1：怎么估算需要的 Redis 实例数？** 三步：① 峰值 QPS ÷ 单实例实测 QPS（留 30% 余量）= 所需节点数；② 数据总量 × 1.5~2 ÷ 单实例可用内存 = 所需节点数；③ 连接数、网络带宽各算一遍，最后**取最大值并向上取整**，再考虑高可用副本。
- **Q2：为什么实际内存比数据量大 1.5~2 倍？** `redisObject` 头、`dictEntry` 结构、哈希表负载因子导致的空桶、jemalloc 的 size class 对齐与碎片、以及复制/AOF 缓冲都要算进去；小对象的**开销占比尤其高**（几十字节的数据可能配上百字节开销）。
- **Q3：为什么要注意 P99 而不是平均值？** Redis 是单线程，一个慢命令/一次 fork 会造成明显长尾，平均值被大量快请求稀释后看不出问题，而用户感受到的是 P99/P999。
- **Q4：压测要覆盖哪些故障场景？** 主从切换（`DEBUG SLEEP` 或手工 failover）、`BGSAVE`/`AOF 重写`期间的延迟抖动、大 key 操作、网络抖动、以及从库全量同步对主库的影响——这些才是线上真正的抖动来源。
- **Q5：连接数怎么规划？** 按"客户端实例数 × 每实例连接池大小"估算，并**保证总连接数 < `maxclients`**（留 20% 余量给管理连接）；同时确认 `ulimit -n` 与内核 `somaxconn`、`tcp_max_syn_backlog` 足够，否则会出现 accept 队列溢出。

### 9.3 高频追问与陷阱

- 陷阱：用默认 `redis-benchmark`（`-t set,get`、固定 key）压出的数字直接当作生产能力——真实业务是混合命令 + 大 value + 热点 key，性能会明显下降。
- 陷阱：容量按理论值规划，不留容量给 COW（fork 时可能接近翻倍）与复制缓冲，导致 RDB 期间 OOM。

### 9.4 代码/配置/命令示例

```bash
redis-benchmark -h 127.0.0.1 -p 6379 -c 50 -n 100000 -t set,get -P 16 -q
redis-cli --latency -h 127.0.0.1
redis-cli --latency-history -i 5
redis-cli INFO stats | grep -E "instantaneous_ops_per_sec|rejected_connections|evicted_keys"
redis-cli INFO clients | grep -E "connected_clients|blocked_clients|maxclients"
```

### 9.5 一句话速记

**单实例约 8~10 万 QPS（必须实测）；内存按数据量 ×1.5~2 并留 30% 余量；连接数受 `maxclients` 约束、客户端必须用池；压测要看 P99 与故障场景。**

## 10. 线上事故案例复盘

### 10.1 核心原理

**案例一：阻塞命令导致全站超时**。某次运营直接在生产执行 `KEYS user:*`（或应用代码里用了 `HGETALL` 大 Hash），单线程被阻塞数秒，所有请求排队，全站 P99 飙升、上游连接池打满。**根因**：单线程 + O(N) 命令。**修复**：`rename-command KEYS ""` 禁用命令、代码改用 `SCAN`/`HSCAN`、大 key 拆分、加慢查询告警（slowlog 阈值调低到 5ms 并接入监控）。

**案例二：fork 抖动导致延迟毛刺**。主库 64GB 内存、`maxmemory` 设得过高，`BGSAVE` 时 `fork` 阻塞主线程数百毫秒，同时 COW 让内存接近翻倍触发 swap，周期性出现 P99 毛刺。**根因**：大内存实例 fork + COW。**修复**：调大 `repl-backlog` 与 `save` 间隔、把 RDB 放到从库执行（`save ""` 关主库 RDB）、降低单实例内存上限（分片）、`vm.overcommit_memory=1`。

**案例三：主从全量同步引发雪崩**。`repl-backlog-size` 保持默认 1MB，网络抖动几秒后从库偏移量已不在 backlog 内 → 触发**全量同步** → 主库 `BGSAVE` + 传输 RDB 打满带宽 → 主库延迟飙升 → 上游超时重试 → 雪崩。**根因**：backlog 太小 + 重试放大。**修复**：`repl-backlog-size` 调到 64~256MB、`repl-diskless-sync yes`、客户端加超时与退避重试、限流熔断。

**案例四：缓存与 DB 不一致引发资损**。秒杀扣库存时"先更 DB 后删缓存"的删除失败（或用了"先删缓存后更库"），并发读请求把旧库存回填进缓存，后续请求基于旧库存继续下单，超卖造成资损。**根因**：缓存当成了库存权威数据。**修复**：① 库存**不走缓存判断**（`UPDATE stock SET n = n - 1 WHERE n >= 1` 在 DB 层保证）；② 缓存只做展示与削峰；③ 引入对账与超卖告警；④ 删除缓存失败必须进 MQ 重试 + TTL 兜底。

### 10.2 面试问答

- **Q1：怎么系统性预防"阻塞命令"类事故？** ① 用 `rename-command` 禁用 `KEYS`/`FLUSHALL`/`DEBUG` 等高危命令；② 代码评审禁止 `KEYS`/`HGETALL` 大对象/大 `SORT`；③ slowlog 阈值调到 5~10ms 并接入监控告警；④ 大 key 巡检（`--bigkeys`）常态化；⑤ 生产使用具备命令审计能力的代理层。
- **Q2：怎么避免 fork 抖动？** ① 控制单实例内存（分片，把大实例拆成多个小实例，fork 耗时与页表规模正相关）；② 主库关闭或减少 RDB（`save ""`），把持久化放到从库；③ 避免 RDB 与 AOF 重写同时发生；④ `repl-diskless-sync` 免落盘；⑤ 预留内存防 COW 期间 OOM/swap。
- **Q3：怎么避免"从库全量同步"雪崩？** ① `repl-backlog-size` 按"写入速率 × 最大断连时长"设置；② 客户端对 Redis 操作加**超时 + 退避重试 + 熔断**（重试必须带抖动，否则会形成重试风暴）；③ 监控 `sync_full`/`sync_partial_ok` 指标，出现全量同步立即告警；④ 降低主库内存与写入峰值。
- **Q4：缓存不一致导致资损怎么根治？** 关键结论是**不要把缓存当作权威数据源**：涉及金额、库存、优惠券的强一致判断必须落到 DB（行锁/乐观锁/唯一约束），缓存只做展示与流量削峰；同时必须有对账任务与不一致告警。
- **Q5：复盘一个 Redis 事故应该讲哪些要素？** 结构化为"**现象 → 影响面 → 时间线 → 根因（直接原因 + 根本原因）→ 止血措施 → 长期改进 → 监控与预案**"。面试中重点讲**根因与系统性改进**（监控、告警、预案、演练），而不是把责任推给"某个同事执行了危险命令"。

### 10.3 高频追问与陷阱

- 陷阱：事故复盘只讲"我们加了个监控"，不讲为什么监控当时没报警、阈值是否合理、预案是否演练过。
- 陷阱：把"重试"当万能药——不加退避与熔断的重试是雪崩的放大器。

### 10.4 代码/配置/命令示例

```conf

rename-command KEYS ""
rename-command FLUSHALL ""
rename-command DEBUG ""
save ""                          # 主库关闭 RDB，交给从库
repl-backlog-size 128mb
repl-diskless-sync yes
slowlog-log-slower-than 5000     # 5ms
maxmemory-policy allkeys-lru
```

```bash

redis-cli CLIENT LIST | sort -k6 -nr | head

```

### 10.5 一句话速记

**四类高频事故：阻塞命令（禁危险命令 + slowlog 告警）、fork 抖动（控制单实例内存 + 主库关 RDB）、全量同步雪崩（调大 backlog + 超时退避熔断）、缓存不一致资损（缓存不做权威数据源）。**

## 自测题（含答案要点）

1. **穿透、击穿、雪崩的区别与各自方案？** —— 数据不存在 / 单热点失效 / 批量失效或整体不可用；分别用"参数校验+空值+布隆"、"互斥锁或逻辑过期"、"随机 TTL+多级缓存+熔断+高可用"。
2. **雪崩为什么要给 TTL 加随机值？** —— 避免大批 key 在同一时刻过期造成集中回源。
3. **布隆过滤器为什么误判、能否删除？空间估算？** —— 不同元素哈希到相同位置；基础版不能删（会破坏"不存在必真"）；`m ≈ -n·ln p/(ln2)²`，1 亿元素、1% 误判约 114MB。
4. **热 key 怎么发现？`--hotkeys` 的前提？为什么禁用 `MONITOR`？** —— `--hotkeys`（需 LFU）、客户端埋点、代理统计；`MONITOR` 推送所有命令，高 QPS 下打满网络与输出缓冲。
5. **多级缓存怎么保证一致性？** —— 本地缓存短 TTL 兜底 + Pub/Sub/MQ 广播失效 + 强一致数据不进本地缓存。
6. **预热与降级的红线？** —— 预热必须限速分批（否则自己制造雪崩）；降级必须绑限流（否则把故障转给 DB）。
7. **分布式锁为什么要 `SET NX PX` 一条命令 + Lua 释放？** —— 拆两条命令中途崩溃会死锁；`GET` 比较与 `DEL` 之间锁可能已易主，会误删别人的锁。
8. **可重入与看门狗怎么实现？** —— Hash 存 `{requestId: 重入次数}`；Redisson 默认 `lockWatchdogTimeout=30s`，每 TTL/3 续期。
9. **RedLock 的争议结论？锁超时与业务耗时的矛盾怎么解？** —— 依赖时钟与 GC 停顿，不适合强正确性场景；终极解法是数据层唯一约束/乐观锁兜底。
10. **限流四种算法的取舍？为什么必须用 Lua？** —— 固定窗口有临界问题、滑动窗口精确但费内存、令牌桶允许突发、漏桶恒定速率；"读判写"非原子会超发。
11. **点赞用 Bitmap 的前提？幂等的最终保证在哪一层？** —— userId 需为连续小整数；DB 唯一索引 + 状态机，Redis `SET NX EX` 只做临时防重。
12. **大 key 怎么治理？内存告警线怎么定？** —— 按字段/序号分片、删除用 `UNLINK`、开 `lazyfree-*`；80% 预警、90% 严重，并盯 `evicted_keys`。
13. **容量估算的两个维度与余量？** —— QPS 实测（单实例约 8~10 万）与内存（数据量 ×1.5~2），预留 30%，并考虑 COW 与复制缓冲。
14. **四类高频事故的根因与预防？** —— 阻塞命令（禁 `KEYS`/`FLUSHALL`+slowlog 告警）、fork 抖动（控制单实例内存+主库关 RDB）、全量同步雪崩（调大 backlog+超时退避熔断）、缓存不一致资损（缓存不做权威数据源）。

## 背诵卡片

1. 穿透=数据不存在，击穿=单热点失效，雪崩=批量失效或整体故障。
2. 穿透三件套：参数校验、缓存空值（短 TTL）、布隆过滤器。
3. 击穿两方案：互斥锁（强一致）、逻辑过期（低延迟）。
4. 雪崩四道闸：随机 TTL、多级缓存、熔断降级、高可用架构。
5. 布隆过滤器"不存在"必真、"存在"可能误判，基础版不支持删除。
6. 布隆空间估算：`m ≈ -n·ln p/(ln2)²`，最优哈希数 `k ≈ (m/n)·ln2`。
7. RedisBloom 命令：`BF.RESERVE`/`BF.ADD`/`BF.EXISTS`/`BF.INFO`。
8. 热 key 发现：`--hotkeys`（需 LFU）、客户端埋点、代理统计；`MONITOR` 生产禁用。
9. 本地缓存必须短 TTL（秒级）+ 失效广播，强一致数据不落地。
10. 热点读分散：本地缓存 + 多副本随机路由 + 静态数据下沉 CDN。
11. 预热必须限速分批、从库取数、低峰执行。
12. 降级原则：保核心舍边缘、必须绑限流。
13. 缓存 key 带版本号便于平滑切换；优先 JSON/MessagePack 而非 Java 原生序列化。
14. 分布式锁：`SET key uuid NX PX` + 唯一 value + Lua 释放，value 用 UUID 不能用线程 ID。
15. 可重入用 Hash 存重入计数；看门狗默认 30s、每 TTL/3 续期。
16. RedLock 有争议，不适合强正确性场景；锁不是唯一安全防线。
17. 锁超时与业务耗时矛盾的终极解法是数据层唯一约束/乐观锁兜底。
18. 限流算法：固定窗口（临界问题）、滑动窗口（ZSet）、令牌桶（允许突发）、漏桶（恒定速率）。
19. 限流的"读判写"必须用 Lua 原子完成。
20. 限流分工：网关全局粗粒度、应用业务细粒度；阈值 ≈ 单实例 QPS × 实例数 × 0.7~0.8。
21. 计数热点要分片（写随机分片、读求和）或本地聚合成 `INCRBY`。
22. 点赞：Bitmap 最省内存（需连续小整数 ID）、Set/Hash 存明细、计数器只存总数。
23. 幂等底线 = DB 唯一索引 + 状态机。
24. 大 key 阈值经验：String < 10KB，集合类元素 < 5000；删除用 `UNLINK` + `lazyfree-*`。
25. 内存告警 80% 预警、90% 严重，并盯 `evicted_keys` 增长。
26. 容量估算取 QPS 与内存的较大值并预留 30%；压测要看 P99 与故障场景。
27. `maxclients` 默认 10000，客户端必须用连接池并留 20% 余量。
28. fork 抖动缓解：控制单实例内存、主库关 RDB、错开持久化、`repl-diskless-sync`。
29. `repl-backlog-size` 默认 1MB 是"全量同步雪崩"的常见根因。
30. 重试必须带退避与熔断，否则形成重试风暴放大故障；事故复盘讲根因与系统性改进。
