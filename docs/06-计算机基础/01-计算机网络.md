## 1. 分层模型与协议设备清单
### 1.1 核心原理
OSI 是教学模型，TCP/IP 是工程实现；面试按"每层做什么、有哪些协议、有哪些设备、数据单元叫什么"准备。

| OSI 七层 | TCP/IP 四层 | 典型协议 | 设备 | 数据单元 |
| --- | --- | --- | --- | --- |
| 应用/表示/会话层 | 应用层 | HTTP、HTTPS、DNS、SSH、FTP、SMTP | 网关、L7 负载均衡 | 报文 |
| 传输层 | 传输层 | TCP、UDP、QUIC | 四层 LB、防火墙 | 段 / 数据报 |
| 网络层 | 网络层 | IP、ICMP、ARP*、OSPF、BGP | 路由器、三层交换机 | 包 |
| 数据链路层 | 网络接口层 | Ethernet、VLAN、ARP、PPP | 交换机、网卡 | 帧 |
| 物理层 | 网络接口层 | 双绞线、光纤、Wi-Fi 物理层 | 中继器、集线器 | 比特 |

> 分歧提示：ARP 承载于以太网帧，TCP/IP 中常划网络层、OSI 讨论中常划链路层；回答"位于 IP 与 MAC 之间做地址解析"即可。
### 1.2 面试问答
**Q1：为什么要分层？**
A：结论是解耦与复用——每层只依赖下层接口，HTTP 可跑 TCP 也可跑 QUIC、IP 换代上层无感；代价是逐层封装开销，因此出现 QUIC 这类跨层优化。
**Q2：一条 TCP 连接由什么唯一标识？**
A：四元组（源 IP、源端口、目的 IP、目的端口）；因此单机并发连接受"本地端口范围 × 对端数量"限制，TIME_WAIT 占用的也是四元组。
### 1.3 高频追问与陷阱
- 集线器在物理层（共享冲突域），交换机在链路层（隔离冲突域，不隔离广播域），路由器在网络层（隔离广播域；隔离广播域也可用 VLAN）。
- "TCP/IP 五层模型"是折中说法：上三层合成应用层、下两层合成网络接口层，再加传输层与网络层。
### 1.4 示例
```bash
ip route     # 路由表与默认网关（判断走同网段还是网关）
ip neigh     # ARP 表：IP → MAC 映射
```
### 1.5 一句话速记
`应用层管语义、传输层管端到端、网络层管路由、链路层管下一跳。`
## 2. TCP 三次握手与 SYN/accept 队列
### 2.1 核心原理
| 报文 | 关键字段 | 说明 |
| --- | --- | --- |
| 1 | SYN=1，seq=x | 客户端选随机初始序号 ISN |
| 2 | SYN=1，ACK=1，seq=y，ack=x+1 | 服务端确认并同步自身 ISN |
| 3 | ACK=1，seq=x+1，ack=y+1 | 客户端确认，连接建立，可携带数据 |

服务端收 SYN 后连接进 **SYN 半连接队列**（`net.ipv4.tcp_max_syn_backlog`），收到第三次 ACK 后进 **accept 全连接队列**（受 `min(backlog, net.core.somaxconn)` 约束），等应用 `accept()` 取走。
### 2.2 面试问答
**Q1：为什么必须三次，两次不行吗？**
A：结论——三次是"双方都确认彼此收发能力正常"的最小次数；两次只能让服务端确认"客户端能发、我能收"，无法确认客户端能收，且服务端会为早已失效的历史 SYN 建连浪费资源。边界：三次握手不能阻止握手后的攻击（如 Slowloris 占连接），也不能验证客户端真实存在（源 IP 可伪造）。
**Q2：ISN 为什么随机？**
A：防止历史连接的旧报文被当作新连接数据，并降低序列号被预测注入的风险；Linux 用基于四元组哈希 + 时钟的方案，并非纯随机。
**Q3：SYN Flood 怎么防？**
A：1）`net.ipv4.tcp_syncookies=1`：半连接队列满时不建状态，把状态编码进 SYN+ACK 的 seq，第三次 ACK 带回校验后直接建连；2）调大 `tcp_max_syn_backlog`、`somaxconn`；3）缩短 `tcp_synack_retries`；4）在四层 LB/防火墙做 SYN 代理与限速。边界：syncookies 开启会丧失部分 TCP 扩展（窗口缩放、SACK 协商受限），是兜底而非常态。
**Q4：accept 队列满了会怎样？**
A：默认丢弃第三次 ACK——客户端认为已连接、服务端无连接，表现为"偶发请求超时"；`net.ipv4.tcp_abort_on_overflow=1` 则直接回 RST（客户端快速失败）。排查看 `ss -lnt` 的 Send-Q 与 `nstat -az TcpExtListenOverflows TcpExtListenDrops`。
### 2.3 高频追问与陷阱
- `listen(backlog)` 不是最大连接数而是队列长度，Java 侧对应 `ServerSocket(port, backlog)` 与 Tomcat `acceptCount`。
- 半连接队列溢出：客户端收不到 SYN+ACK 会重传；全连接队列溢出：握手完成但应用看不到新连接。
- `tcp_tw_recycle` 已在 Linux 4.12 移除，NAT 环境会丢包，禁用。
### 2.4 示例
```bash
nstat -az | grep -Ei 'ListenOverflows|ListenDrops|Syncookies'
ss -lnt                                   # Recv-Q=当前半连接数，Send-Q=backlog 上限
tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
```
### 2.5 一句话速记
`三次握手同步双向 ISN；SYN 进半连接队列，第三次 ACK 进全连接队列等 accept。`
## 3. 四次挥手与 TIME_WAIT/CLOSE_WAIT
### 3.1 核心原理
| 报文 | 方向 | 状态迁移 |
| --- | --- | --- |
| FIN | A→B | A: FIN_WAIT_1 |
| ACK | B→A | B: CLOSE_WAIT |
| FIN | B→A | B: LAST_ACK；A: FIN_WAIT_2 |
| ACK | A→B | A: TIME_WAIT（2MSL）→ CLOSED；B: CLOSED |

TIME_WAIT 在 Linux 上固定 **60 秒**（`TCP_TIMEWAIT_LEN`），无法通过参数缩短，只能减少主动关闭或复用端口。
### 3.2 面试问答
**Q1：为什么挥手是四次而握手是三次？**
A：TCP 全双工，被动方收到 FIN 只说明"对方发完了"，自己可能还有数据要发，所以 ACK 与自己的 FIN 不能合并。边界：被动方正好也无数据可发时，抓包可能看到 ACK 与 FIN 合并成"三次挥手"。
**Q2：TIME_WAIT 有什么用？**
A：两个作用：1）可靠终止——最后一个 ACK 丢失时对端会重传 FIN，主动方需保留状态以便重发 ACK，2MSL 覆盖"一次报文最大存活 + 一次重传"；2）避免旧报文污染同四元组的新连接。边界：TIME_WAIT 只出现在主动关闭方，本机几万个通常无害。
**Q3：TIME_WAIT 过多怎么办？**
A：按优先级：1）改长连接/连接池，从根上减少主动关闭；2）客户端侧设 `SO_REUSEADDR` 并开 `net.ipv4.tcp_tw_reuse=1`（仅对 connect 生效，需时间戳开启，1 秒后可复用）；3）扩大 `net.ipv4.ip_local_port_range`；4）多 IP/LB 分摊。严禁 `tcp_tw_recycle`。
**Q4：CLOSE_WAIT 过多说明什么？**
A：**一定是应用代码问题**：被动关闭方没调用 `close()`。常见根因是连接/流/HttpClient 未释放、线程池被打满导致关闭逻辑未执行、下游慢导致线程长期阻塞在读写上；与内核参数无关，调参无效。
**Q5：SO_REUSEADDR 与 SO_REUSEPORT 区别？**
A：`SO_REUSEADDR` 允许绑定处于 TIME_WAIT 的地址（避免重启报 `Address already in use`）；`SO_REUSEPORT` 允许多个 socket 绑同一端口并由内核做负载均衡（多进程 accept 的更优替代）。
### 3.3 高频追问与陷阱
- 主动关闭方出 TIME_WAIT，被动关闭方出 CLOSE_WAIT，先用 `ss -tanp` 确认角色再下结论。
- 大量 TIME_WAIT 导致端口耗尽的表现是 `Cannot assign requested address`（不是超时）。
- `FIN_WAIT_2` 长期堆积是被动方没发 FIN，受 `net.ipv4.tcp_fin_timeout` 影响，同样是应用未关闭。
### 3.4 示例
```bash
ss -tan | awk 'NR>1{print $1}' | sort | uniq -c | sort -rn   # 各状态连接数
ss -tanp state close-wait | head -20                          # 谁在泄漏连接
sysctl net.ipv4.tcp_tw_reuse net.ipv4.ip_local_port_range net.ipv4.tcp_max_tw_buckets
```
### 3.5 一句话速记
`TIME_WAIT=主动方等 2MSL，可复用不可缩短；CLOSE_WAIT=应用忘了 close，只能改代码。`
## 4. 可靠传输、滑动窗口与流量控制
### 4.1 核心原理
可靠性四件套：**序号与确认、超时重传、快速重传、校验和**；效率靠**滑动窗口 + 累积确认**。
- RTO（RFC 6298）：`SRTT=(1-α)SRTT+α·RTT`（α=1/8）、`RTTVAR=(1-β)RTTVAR+β·|SRTT-RTT|`（β=1/4）、`RTO=SRTT+4·RTTVAR`；Linux 初始 RTO 1s、最小 200ms，失败指数退避。
- 快速重传：收到 3 个重复 ACK 立即重传丢失段，不等超时；SACK（`net.ipv4.tcp_sack`）让接收方通告已收区间，避免重传整个窗口。
- 滑动窗口：发送窗口 `= min(cwnd, rwnd)`；接收方在 ACK 中通告 `rwnd`，`rwnd=0` 时发送方启动**零窗口探测**（persist timer），防止窗口更新报文丢失造成永久死锁。
### 4.2 面试问答
**Q1：TCP 如何保证不丢、不重、不乱序？**
A：每个字节有序号，接收方累积确认并重排：乱序暂存、缺失重传、重复丢弃。**TCP 只保证字节流有序可靠，不保证消息边界**，这是粘包的根源；收到半条业务消息是正常现象。
**Q2：超时重传与快速重传的适用差异？**
A：快速重传依赖后续报文触发重复 ACK，适用于"偶发丢包但后续数据继续到达"；超时重传是兜底，适用于尾部丢包或大面积丢包（无后续报文可触发 dup ACK）。
**Q3：流量控制与拥塞控制的区别？**
A：流量控制（rwnd）是接收方告诉发送方"我还能收多少"，防压垮接收端；拥塞控制（cwnd）是发送方推断网络能承受多少，防压垮网络；实际窗口取两者较小值。边界：BDP 大时窗口成为瓶颈，需开启窗口缩放并调大 `tcp_rmem/tcp_wmem`。
### 4.3 高频追问与陷阱
- 重复 ACK 不一定丢包，也可能是乱序；判断丢包看 `ss -ti` 的 `retrans`/`lost` 与抓包的 `[TCP Retransmission]`；`ss -s` 的 retrans 是全系统统计。
- 校验和只能发现错误不能纠正，错误报文被丢弃后靠重传恢复。
### 4.4 示例
```bash
ss -tin state established '( dport = :8080 or sport = :8080 )'   # RTT/重传/cwnd
nstat -az TcpRetransSegs TcpOutSegs                              # 算重传率
```
### 4.5 一句话速记
`可靠性靠重传、效率靠窗口；发送窗口 = min(cwnd, rwnd)，零窗口靠 persist 探测。`
## 5. 拥塞控制与 BBR
### 5.1 核心原理
| 阶段 | 触发条件 | cwnd 行为 |
| --- | --- | --- |
| 慢启动 | 连接开始 / 超时重传后 | 每 RTT 翻倍，指数增长到 ssthresh |
| 拥塞避免 | cwnd ≥ ssthresh | 每 RTT 线性 +1 MSS（AIMD 加法增） |
| 快重传 | 3 个重复 ACK | 立即重传丢失段，不走超时分支 |
| 快恢复 | 快重传后 | ssthresh=cwnd/2，cwnd=ssthresh（Reno）后进拥塞避免 |

演进：Tahoe（无快恢复）→ Reno → NewReno → **CUBIC**（Linux 3.19+ 默认，适合长肥网络）→ **BBR**（Google，基于模型）。
### 5.2 面试问答
**Q1：慢启动"慢"在哪？**
A："慢"指起点保守（Linux 初始 cwnd 约 10 MSS），实际增长是指数级——每 RTT 翻倍。边界：盲目调大 `initcwnd` 会在丢包链路上加剧拥塞。
**Q2：BBR 与 CUBIC 的本质差别？**
A：CUBIC 把**丢包当拥塞信号**，在有随机丢包的链路（无线、长肥网络）上会误判降速；BBR 用 `BtlBw`（最大带宽估计）与 `RTprop`（最小 RTT）建模，主动把发送速率维持在最大带宽、排队时延维持最小，不依赖丢包。边界：BBRv1 与 CUBIC 共存时存在公平性问题（会压制 CUBIC），BBRv2/3 做了改进。
**Q3：高 BDP 链路为什么跑不快？**
A：窗口不足——BDP = 带宽 × RTT 大于发送窗口时吞吐被"窗口/RTT"卡死；需开启 `tcp_window_scaling` 并调大收发缓冲，或改用 CUBIC/BBR。
### 5.3 高频追问与陷阱
- "超时重传必回慢启动"是 Tahoe/Reno 的旧行为，现代实现（PRR/Loss Recovery）更复杂；cwnd 是发送方本地变量，抓包看不到，只能从 `ss -ti` 的 `cwnd` 与发送速率推断。
- `tcp_slow_start_after_idle=0` 可避免空闲后回到慢启动，短连接/突发流量常用。
### 5.4 示例
```bash
sysctl net.ipv4.tcp_congestion_control net.ipv4.tcp_available_congestion_control
sysctl -w net.ipv4.tcp_congestion_control=bbr
```
### 5.5 一句话速记
`慢启动指数涨、拥塞避免线性涨、三重复 ACK 快重传、砍半进快恢复；BBR 不看丢包看带宽与 RTT。`
## 6. Nagle、延迟确认与粘包拆包
### 6.1 核心原理
- **Nagle**：有未确认数据时把后续小包攒起来，够一个 MSS 或收到 ACK 才发，目的是减少小包。
- **延迟确认（Delayed ACK）**：接收方最多等 40ms（Linux 默认）再回 ACK，以期待捎带数据。
- **冲突后果**：write-write-read 模式下第一次写被 Nagle 攒住、接收方又延迟 40ms 才确认，形成 **~40ms 周期性延迟**（典型于不设 `TCP_NODELAY` 的客户端连续两次小写）。
- **粘包/拆包**：TCP 是字节流无消息边界，一次 read 可能读到半条或两条半消息——这是应用层要解决的问题。
### 6.2 面试问答
**Q1：如何消除 40ms 延迟？**
A：1）`socket.setTcpNoDelay(true)` 关闭 Nagle（最常用）；2）合并写（writev 或一次 write 完整请求）；3）调整延迟确认（Linux `TCP_QUICKACK`）。边界：关掉 Nagle 会增加小包数量，需配合批处理与连接复用，否则从延迟问题变成吞吐问题。
**Q2：粘包的成因？**
A：应用写入与 TCP 收发缓冲不对齐：Nagle/滑动窗口把多次写合并进同一段；接收方读取不及时或缓冲区大于一个报文；MSS 分片把一条消息拆成多段。UDP 保留报文边界，不粘包但会丢包乱序。
**Q3：三种拆包方案怎么选？**
A：长度字段法最通用（二进制友好、可处理半包），分隔符法适合文本协议但需转义并设上限，定长法解析最快但浪费带宽。Netty 对应 `LengthFieldBasedFrameDecoder`、`LineBasedFrameDecoder`/`DelimiterBasedFrameDecoder`、`FixedLengthFrameDecoder`。
**Q4：Netty 解码器怎么配？**
A：服务端流水线一般 `LengthFieldBasedFrameDecoder(maxFrameLength, 0, 4, 0, 4)` → `LengthFieldPrepender(4)` → 业务 Codec；**必须设置 maxFrameLength**，否则恶意超长长度字段会导致 OOM。
### 6.3 高频追问与陷阱
- 关闭 Nagle 后仍可能粘包，两个问题相互独立。
- Netty 的 `ByteToMessageDecoder` 自动累积半包，自定义解码器不必自己拼缓冲。
- "TCP 粘包"是习惯叫法，准确说法是"应用层消息边界问题"。
### 6.4 示例
```java
socket.setTcpNoDelay(true);                                   // 关 Nagle
pipeline.addLast(new LengthFieldBasedFrameDecoder(1 << 20, 0, 4, 0, 4));
pipeline.addLast(new LengthFieldPrepender(4));
```
### 6.5 一句话速记
`Nagle 攒小包、延迟确认等 40ms，叠加出 40ms 延迟；拆包首选长度字段法。`
## 7. TCP vs UDP、QUIC 与 HTTP/3
### 7.1 核心原理
| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接（三次握手/四次挥手） | 无连接 |
| 可靠性 | 有序、可靠、不重复、有重传 | 不保证，可能丢/乱/重 |
| 边界 | 字节流（无边界） | 数据报（保留边界） |
| 头部/控制 | 20 字节起，有流量与拥塞控制 | 8 字节，无 |
| 广播组播 | 不支持 | 支持 |
| 典型场景 | HTTP、数据库、RPC、文件传输 | DNS、音视频、游戏、监控埋点、QUIC |

**QUIC**：基于 UDP、用户态实现，内建 TLS1.3，首次 1-RTT、恢复 0-RTT；用 Stream 隔离消除传输层队头阻塞；用 Connection ID 标识连接实现连接迁移；默认加密 + QPACK 头部压缩。
### 7.2 面试问答
**Q1：QUIC 为什么基于 UDP？**
A：中间设备（NAT、防火墙、老内核）对 TCP 改动极不友好，而 UDP 报文可自由封装；把可靠性、拥塞控制、TLS 全部搬到用户态后可快速迭代且可按连接定制策略。边界：部分企业防火墙限速甚至阻断 UDP，需支持回退到 HTTP/2。
**Q2：QUIC 解决了 TCP 的哪些痛点？**
A：1）消除传输层队头阻塞（TCP 上一个包丢失会阻塞所有流）；2）握手更快（TLS1.3 内建，0-RTT 恢复）；3）连接迁移（切 Wi-Fi/4G 不断连）；4）默认加密与头部压缩。
**Q3：什么场景坚决用 TCP？**
A：需要可靠有序且不愿自研重传与拥塞控制的场景：数据库协议、文件传输、大部分业务 RPC。公网自研 UDP 可靠性很难达到 TCP 的成熟度（KCP 属特定权衡，用带宽换延迟）。
### 7.3 高频追问与陷阱
- UDP 的 `connect()` 只是设默认对端并让内核过滤来源，仍无握手。
- DNS 默认 UDP 53，响应超 512 字节（或 EDNS0 协商更大）与区域传送用 TCP。
- HTTP/3 的 0-RTT 有重放风险，只应对幂等请求启用。
### 7.4 示例
```bash
curl -sI https://www.cloudflare.com | grep -i alt-svc    # 是否宣告 h3
nc -u -v -z 8.8.8.8 53                                   # UDP 连通性
```
### 7.5 一句话速记
`TCP 可靠但队头阻塞，UDP 快但不可靠；QUIC = UDP + TLS1.3 + 多路复用 + 连接迁移。`
## 8. HTTP 1.0/1.1/2/3 演进
### 8.1 核心原理
| 维度 | HTTP/1.0 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- | --- |
| 连接 | 默认短连接 | 默认 keep-alive | 单 TCP 连接多路复用 | QUIC（UDP）多路复用 |
| 并发 | 每域 6 条连接 | 管道化（实际废弃） | Stream 并行交错 | Stream 独立，无队头阻塞 |
| 格式 | 文本 | 文本 | 二进制分帧 | 二进制分帧 |
| 头部 | 不压缩 | 不压缩 | HPACK | QPACK |
| 队头阻塞 | 连接级 | 连接级 | TCP 层仍存在 | 无 |
| 握手 | TCP | TCP | TCP + TLS | 1-RTT / 0-RTT |

**HPACK 三招**：静态表（61 个常见头）、动态表（连接内用过的头用索引引用）、霍夫曼编码压缩字面值。
### 8.2 面试问答
**Q1：1.1 相对 1.0 的关键增量？**
A：默认长连接、强制 `Host`（虚拟主机）、`Transfer-Encoding: chunked`、`Range` 断点续传、`100-continue`、完善的缓存字段（`Cache-Control`、`ETag`）。
**Q2：1.1 管道化为什么被废弃？**
A：响应必须按请求顺序返回，前一个慢请求阻塞后面所有响应（应用层队头阻塞）；中间代理支持不一致、非幂等请求无法安全重试，收益为负。现代做法是每域多条连接或直接 HTTP/2。
**Q3：HTTP/2 解决了什么、遗留什么？**
A：解决应用层队头阻塞：多个 Stream 在同一 TCP 连接上并行交错，用 Stream ID 区分、帧头压缩。遗留 **TCP 层队头阻塞**——任何丢包阻塞该连接所有 Stream（内核按序交付），弱网下单连接 HTTP/2 甚至不如多连接 HTTP/1.1，这正是 HTTP/3 的动机。
**Q4：0-RTT 的代价？**
A：0-RTT 数据用上次会话密钥加密，服务端无法保证唯一性，**存在重放风险**，只应用于幂等请求并做防重放（时限 + ticket 单次使用）。
### 8.3 高频追问与陷阱
- HTTP/2 的服务器推送已被主流浏览器移除支持，由 103 Early Hints 取代，回答时要说明现状。
- 升级方式：HTTP/2 走 TLS + ALPN 协商 `h2`；HTTP/3 由 `Alt-Svc` 头宣告，首次仍走 HTTP/2。
- `SETTINGS_MAX_CONCURRENT_STREAMS` 决定并发流上限，溢出的请求在客户端排队。
### 8.4 示例
```bash
curl -sI -o /dev/null -w '%{http_version}\n' https://example.com
curl --http1.1 -sI https://example.com | head -1
```
### 8.5 一句话速记
`1.1 长连接、2 二进制多路复用（TCP 队头阻塞仍在）、3 上 QUIC 彻底无队头阻塞。`
## 9. HTTP 方法与状态码排查
### 9.1 核心原理
| 码 | 含义 | 排查方向 |
| --- | --- | --- |
| 301 | 永久重定向 | 被浏览器/CDN 缓存，改动需清缓存；POST 可能变 GET |
| 302/307 | 临时重定向 | 307 保持方法；登录跳转常用 |
| 304 | 协商缓存命中 | 正常无响应体；确认 ETag/Last-Modified 是否抖动 |
| 400 | 请求语法/参数错误 | 参数格式、Header 超长、非法字符、Content-Length 不符 |
| 401 | 未认证 | 缺 token 或 token 过期 |
| 403 | 已认证但无权限 | ACL、Nginx 文件权限、WAF 拦截 |
| 404 | 资源不存在 | 路由、网关前缀、反向代理 root 配置 |
| 499 | 客户端主动断开 | **Nginx 特有**：上游处理时间超过客户端超时 |
| 500 | 服务端内部异常 | 看应用日志，多为未捕获异常 |
| 502 | 网关拿到非法响应 | 后端进程挂了/端口未监听、keepalive 不一致、后端主动断连 |
| 503 | 服务不可用 | 过载限流、线程池满、健康检查失败被摘除 |
| 504 | 网关等待上游超时 | 后端慢（GC/慢 SQL/锁）或网关超时阈值过小 |

方法与语义：GET 幂等可缓存、POST 非幂等、PUT 全量替换幂等、PATCH 局部更新、DELETE 幂等、HEAD 只取头、OPTIONS 用于 CORS 预检。
### 9.2 面试问答
**Q1：GET 与 POST 的本质区别？**
A：语义区别——GET 取数据且幂等可缓存，POST 提交数据且非幂等；工程含义是 GET 可重试可缓存、参数在 URL（日志泄漏风险），POST 需 `Content-Length`/chunked、需幂等键防重放。边界："POST 比 GET 安全"是错的，明文下都不安全，URL 反而更易进日志；"POST 只能传 4KB"是实现限制而非协议规定。
**Q2：502 与 504 如何快速定位？**
A：先分层：502 优先确认后端进程与端口（`ps`、`ss -lntp | grep 端口`、从网关机器直连后端 curl），若后端存活则查 keepalive 超时不一致与请求体过大被拒；504 看后端处理时长与网关 `proxy_read_timeout`，若后端耗时超阈值应先优化后端而不是盲目调大超时。
**Q3：499 为什么会发生？**
A：Nginx 记录 499 表示客户端在响应返回前断开，根因通常是整条链路超时阈值倒挂（客户端超时 < Nginx 超时），用户重试或跳转取消旧请求；修法是让超时自内向外递减并排查后端长尾请求。
### 9.3 高频追问与陷阱
- 502 是"连不上或响应非法"，504 是"连上了但等超时"，两者根因不同。
- 业务把状态码塞进 body（HTTP 200 + `{"code":500}`）是反模式，排查先看应用层 code。
- 网关返回的 500 可能是把后端非 HTTP 响应包装后的结果，必须看后端日志确认原始错误。
### 9.4 示例
```bash
curl -o /dev/null -s -w 'code=%{http_code} dns=%{time_namelookup} conn=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://api.example.com/health
```
### 9.5 一句话速记
`4xx 怪客户端、5xx 怪服务端；502 后端不可用、504 后端太慢、499 客户端先跑。`
## 10. HTTP 缓存机制
### 10.1 核心原理
| 类型 | 字段 | 行为 | 是否发请求 |
| --- | --- | --- | --- |
| 强缓存 | `Cache-Control: max-age`、`Expires` | 未过期直接用本地副本 | 否 |
| 协商缓存 | `ETag`/`If-None-Match`、`Last-Modified`/`If-Modified-Since` | 带校验头发请求，未变返回 304 | 是 |

优先级：`Cache-Control` > `Expires`；`ETag` > `Last-Modified`。`no-cache` 不是不缓存而是**每次都要校验**；`no-store` 才是完全不落盘；`s-maxage` 只对共享缓存（CDN）生效并覆盖 `max-age`；`private` 禁止 CDN 缓存。
### 10.2 面试问答
**Q1：为什么 ETag 优先于 Last-Modified？**
A：Last-Modified 精度只到秒，内容不变但时间变化（重新部署拷文件）会误判为已更新；ETag 是内容指纹更精确。边界：Nginx 默认 ETag 由 `mtime+size` 生成，多机部署可能各不相同导致缓存频繁失效，可用内容哈希统一。
**Q2：缓存命中顺序？**
A：Service Worker → Memory Cache → Disk Cache（强缓存命中直接返回）→ 协商缓存 → 回源。强缓存先于协商缓存是一致结论，具体浏览器实现细节略有差异。
**Q3：发版后如何让前端立即生效？**
A：HTML 入口用 `no-cache`（每次校验）或极短 max-age；JS/CSS/图片用 `max-age=31536000, immutable` + **文件名内容哈希**（内容变则 URL 变）。边界：`immutable` 阻止刷新时校验，但要求文件名随内容变化。
**Q4：304 省了什么？**
A：省 body 流量（仅返回响应头），仍有一次 RTT；304 过多会成为性能问题，因此强缓存优先。
### 10.3 高频追问与陷阱
- POST 响应默认不可缓存，不要依赖。
- Nginx `proxy_cache` 与浏览器缓存是两套体系，"数据不更新"要同时看两者。
- CDN 缓存未刷新常表现为"部分用户看到旧页面"，需按 URL/目录做刷新与预热。
### 10.4 示例
```bash
curl -sI https://example.com/index.html | grep -Ei 'etag|last-modified|cache-control'
curl -s -o /dev/null -w '%{http_code}\n' -H 'If-None-Match: "abc"' https://example.com/index.html
```
### 10.5 一句话速记
`强缓存不发请求、协商缓存发请求收 304；no-cache 要校验、no-store 才是不落盘。`
## 11. Cookie/Session 与 HTTPS/TLS
### 11.1 核心原理
- **Cookie**：服务端 `Set-Cookie` 下发，浏览器按 Domain/Path 存储并在 `Cookie` 头回传；安全属性 `HttpOnly`（防 XSS 读取）、`Secure`（仅 HTTPS）、`SameSite=Lax/Strict/None`（防 CSRF，`None` 必须配 `Secure`）。
- **Session**：服务端存状态、客户端只拿 `JSESSIONID`。集群共享四法：粘性会话、Session 复制、集中存储（Spring Session + Redis，主流）、无状态 Token（JWT，扩缩容友好但撤销困难）。
- **TLS 1.2 握手（ECDHE）**：ClientHello（`random_C`、套件、SNI）→ ServerHello（`random_S`）+ Certificate（证书链）+ ServerKeyExchange（ECDHE 公钥 + 私钥签名）+ ServerHelloDone → 客户端验证书链 → ClientKeyExchange → 双方算 pre-master，用 PRF 派生主密钥与会话密钥 → ChangeCipherSpec + Finished → 加密应用数据。
- **TLS 1.3 改进**：默认 1-RTT（ClientHello 直接带 `key_share` 猜测曲线），会话恢复可 0-RTT；移除 RSA 密钥交换、CBC、RC4 与压缩，只保留 AEAD（AES-GCM、ChaCha20-Poly1305）；除 ClientHello 外握手全程加密。
### 11.2 面试问答
**Q1：对称与非对称加密在 HTTPS 中各自的角色？**
A：非对称只用于握手的身份认证与密钥协商（慢但能安全交换秘密），对称用于后续全部数据加密（快）。只有已废弃的 RSA 密钥交换才用证书公钥直接加密 pre-master。
**Q2：前向安全（PFS）是什么？**
A：服务器私钥日后泄漏也无法解密历史会话；实现方式是每次握手用临时密钥对做 ECDHE，用完即弃。TLS1.3 强制 PFS，所以"1.3 更安全"不只是算法更强。
**Q3：浏览器如何验证证书？**
A：1）签名链校验：叶子 → 中间 CA → 根 CA（根证书预置信任库）；2）有效期与域名匹配（SAN 优先于 CN）；3）吊销状态（CRL/OCSP/OCSP Stapling）；4）算法与密钥强度合规。边界：**证书链不完整（少中间证书）是"部分客户端报错"的最常见原因**。
**Q4：什么情况下能解密 TLS 流量？**
A：三种：拥有服务端私钥**且**使用 RSA 密钥交换（老配置）；客户端导出 `SSLKEYLOGFILE` 会话密钥；链路中间用受信任代理证书做 MITM。边界：ECDHE/TLS1.3 下仅凭私钥**无法**解密，这是面试常考的纠正点。
**Q5：Session 共享方案怎么选？**
A：小规模可用粘性会话（扩容与故障转移不友好）；跨机房多实例用 Redis 集中存储；对无状态要求高（网关/多端登录）用 JWT，但必须解决注销与续期问题。
### 11.3 高频追问与陷阱
- Session 与 Cookie 不是一回事：Session 是服务端存储方案，Cookie 只是默认 ID 载体。
- `SameSite=None` 不配 `Secure` 会被浏览器直接拒绝，跨域 iframe/支付回调常踩。
- 抓包能看到 TLS1.2 的证书明文，TLS1.3 除 ClientHello 外都加密。
- 会话 ID 出现在 URL（`;jsessionid=xxx`）有泄漏风险，可关闭 URL 重写。
### 11.4 示例
```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>&1 | head -30
javax.net.ssl.SSLHandshakeException    # 常见于证书链不全/信任库缺根证书
```
### 11.5 一句话速记
`非对称换密钥、对称传数据；TLS1.3 = 1-RTT + 强制 PFS + 握手加密；解密需 SSLKEYLOGFILE 或 MITM。`
## 12. DNS、ARP、NAT 与代理
### 12.1 核心原理
- **DNS 查询**：客户端 → 本地 DNS 是**递归**（本地 DNS 负责到底）；本地 DNS → 根/顶级/权威是**迭代**（逐级追问）。缓存层级：浏览器 → OS/hosts → 本地 DNS → 各级权威，时长由 TTL 决定。
- **CDN 调度**：域名 CNAME 到 CDN 的 GSLB，按客户端出口 IP 归属、运营商、探测时延、节点负载返回最优边缘 IP；`EDNS Client Subnet` 可透传真实客户端网段提高精度。
- **DNS 污染/劫持**：链路中间设备伪造响应；应对是 `HTTPDNS`（客户端直接 HTTP 查询，绕过 LocalDNS 与 UDP 53 干扰）与 DoH/DoT。
- **ARP**：同网段用 ARP 广播把 IP 解析为 MAC，跨网段则发给网关 MAC 逐跳转发。
- **NAT**：SNAT 改源地址（内网出公网）、DNAT 改目的地址（公网进内网）、NAPT 用端口复用让多主机共享一个公网 IP；内网穿透靠端口映射、`ssh -R` 反向隧道、frp。
- **代理**：正向代理代表客户端（隐藏客户端），反向代理代表服务端（隐藏服务端，可做 LB、缓存、TLS 卸载）。
### 12.2 面试问答
**Q1：递归与迭代查询的区别？**
A：递归是"你帮我查到底给我结果"（客户端→本地 DNS）；迭代是"你告诉我下一步问谁"（本地 DNS→根/顶级/权威）。边界：本地 DNS 做转发时对客户端仍是递归语义。
**Q2：改了 DNS 解析不生效为什么？**
A：多级缓存未过期：浏览器、OS、LocalDNS，以及**Java 客户端默认会永久缓存 DNS 结果**（`networkaddress.cache.ttl`，开启 SecurityManager 时为 -1）——这是长连接服务的经典坑，需显式设置 TTL。排查用 `dig @8.8.8.8` 与本地解析结果对比。
**Q3：HTTPDNS 解决什么问题？**
A：绕过 LocalDNS 的缓存不遵守 TTL、调度不准（递归出口 IP ≠ 用户 IP）与被劫持污染；代价是需自建服务、SDK 集成、IP 直连时的 SNI/Host 处理。
**Q4：正向代理与反向代理一句话区分？**
A：正向代理"客户端知道自己在用代理、服务端不知道真实客户端"；反向代理"客户端以为在直连服务器、实际由代理转发"。边界：Nginx 通过 `X-Forwarded-For`/`X-Real-IP` 传真实 IP，只应信任可信代理链注入的值。
### 12.3 高频追问与陷阱
- 容器环境 `ndots:5` 会导致大量无效 DNS 查询，表现为偶发解析超时；反向代理后 `request.getRemoteAddr()` 拿到的是代理 IP，需配置 `forward-headers-strategy`。
- NAT 会话表有超时（TCP 常见 300s、UDP 30~120s），空闲长连接被断开且双方不知情 → 表现为"偶发 connection reset"，需应用心跳或 TCP keepalive。
### 12.4 示例
```bash
dig +trace example.com                 # 观察迭代解析路径
dig @8.8.8.8 example.com +short
arp -a; ip neigh                       # ARP 表
ssh -R 8080:localhost:8080 user@public-host   # 反向隧道内网穿透
```
### 12.5 一句话速记
`本地 DNS 递归、根与权威迭代；HTTPDNS 绕污染；NAPT 靠端口复用公网 IP。`
## 13. 排查工具链
### 13.1 核心原理
排查遵循"由外到内、由粗到细"：**连通性 → 延迟丢包 → 端口连接状态 → 抓包看协议行为 → 应用日志**。

| 工具 | 作用 | 关键用法 |
| --- | --- | --- |
| ping | 三层连通与 RTT | `ping -c 10 host`；不通不代表服务不可用（常禁 ICMP） |
| mtr/traceroute | 逐跳丢包 | `mtr -rwzbc 100 host` |
| nc/telnet | 四层端口探测 | `nc -vz -w2 host 8080`；超时=被墙/未监听，拒绝=端口关闭 |
| curl | 应用层探活与耗时分解 | `-v` 看完整请求响应与 TLS 握手、`-w` 拆 dns/connect/tls/ttfb/total |
| ss | 连接状态与队列 | `ss -s`、`ss -lntp`、`ss -tanp state time-wait` |
| netstat | 协议栈统计 | `netstat -s` 看重传与溢出 |
| tcpdump | 抓包定位协议行为 | `tcpdump -i any -nn -s0 -w a.pcap port 8080` |
| lsof | 端口被谁占用 | `lsof -i:8080` |
### 13.2 面试问答
**Q1：接口偶发超时怎么排查？**
A：分四层：1）网络层用 `mtr` 看丢包、`nstat` 看重传率、`tcpdump` 看重传/RST/零窗口；2）连接层看是否有大量 TIME_WAIT/SYN-SENT/CLOSE_WAIT，连接池是否被打满、`maxIdle` 与 LB 空闲超时是否匹配；3）应用层看 GC 停顿、线程池队列、慢 SQL、锁竞争、下游 RT；4）客户端层看超时阈值与重试（超时短于后端 P99 必然"偶发"）。边界：偶发问题优先看 P99/P999 与时间分布，别只看均值。
**Q2：tcpdump 抓包后看什么？**
A：六类信号——重传（判丢包）、重复 ACK（判乱序或丢包）、零窗口（判消费端慢）、RST（判连接被重置）、只有 SYN 无 SYN+ACK（对端未监听或被拒）、TLS Alert（判证书或协议不匹配）。技巧：`-s0` 抓全包、`-nn` 不解析名称、按端口过滤、`-c` 限包数防写满磁盘。
**Q3：连接被重置（RST）可能的原因？**
A：1）服务端端口未监听或进程重启；2）客户端从连接池取出已被服务端关闭的连接（LB/NAT 空闲超时 < 连接池 keepalive）；3）backlog 溢出且 `tcp_abort_on_overflow=1`；4）服务端 close 后收到数据；5）防火墙/安全组阻断；6）`SO_LINGER=0` 主动 RST。
**Q4：如何证明是网络问题还是应用问题？**
A：做对照实验：服务端本机 `curl 127.0.0.1:port`（排除应用无法响应）→ 调用方直连后端实例 IP（排除 LB/网络策略）→ 对比多个实例（单体问题还是全局问题）。
### 13.3 高频追问与陷阱
- `ping` 不通 ≠ 服务不可用，必须用 `nc`/`curl` 验证。
- 抓包位置很关键：客户端、服务端、LB 两侧三份对比才能确定丢在哪一段；tcpdump 在高流量机器会丢包，用 `-B` 调大缓冲并加 filter。
### 13.4 示例
```bash
mtr -rwzbc 50 api.example.com
ss -lntp | grep 8080; ss -s
tcpdump -i any -nn -s0 -w /tmp/api.pcap 'host 10.0.0.8 and port 8080'
curl -o /dev/null -s -w 'dns=%{time_namelookup} conn=%{time_connect} ttfb=%{time_starttransfer} total=%{time_total}\n' http://10.0.0.8:8080/actuator/health
```
### 13.5 一句话速记
`外到内：ping/mtr → nc → ss → tcpdump → 应用日志，每步都要有对照实验。`
## 14. 综合场景题
### 14.1 核心原理
把知识串成一条链路：**DNS → ARP/网关 → TCP 握手 → TLS → HTTP 请求 → 服务端处理 → 响应 → 渲染与连接复用**；排查就是反向分段测量。
### 14.2 面试问答
**Q1：浏览器输入 URL 后发生了什么？**
A：1）URL 解析并判断是否命中强缓存；2）DNS 解析（浏览器 → hosts → 本地 DNS 递归 → 根/顶级/权威迭代，可能返回 CDN 边缘 IP）；3）建立连接：ARP 找网关 MAC → TCP 三次握手 → HTTPS 走 TLS 握手（ALPN 协商 h2/h3）；4）发送 HTTP 请求，经 LB → 网关 → 应用（Nginx → Tomcat/Netty → Spring → 业务 → 缓存/DB/RPC）；5）返回响应并可能带缓存头、经 CDN 缓存；6）浏览器解析渲染、请求子资源（可复用连接或走 HTTP/2 多路复用）；7）keep-alive 复用或空闲超时后四次挥手。
**Q2：偶发超时的完整作答思路？**
A：1）定性：收集时间分布、影响面、P99 与均值差异；2）分层定位：`curl -w` 拆耗时、`mtr` 看丢包、`ss -s` 看重传与状态、服务端看 GC 与线程池、DB 看慢查询与锁、下游看 RT；3）常见根因清单：连接池过小或泄漏、LB 与客户端 keepalive 超时倒挂、Full GC、慢 SQL、下游抖动、NAT 会话超时、跨可用区带宽打满；4）修复与验证：加压复现验证 P99 下降。边界：不要先调大超时，那只是把问题转成资源堆积。
**Q3："连接重置"与"连接超时"如何区分处置？**
A：RST 是**对端主动拒绝/断开**（端口未监听、连接已关闭、防火墙拒绝），查服务端进程、LB 空闲超时、连接池陈旧连接；超时是**没有响应**（丢包、SYN 无应答、后端卡住），查网络丢包、ACL、后端阻塞。两者也可能同现（先超时后客户端关闭触发 RST）。
**Q4：容器/K8s 环境排查有什么不同？**
A：多一层：Pod IP 与 Service ClusterIP、overlay 封装、CoreDNS 的 `ndots` 放大、NetworkPolicy、Sidecar（mTLS 与端口重定向）。排查顺序是先 `curl PodIP:port` 绕过 Service，再试 ClusterIP，最后试域名。
### 14.3 高频追问与陷阱
- 回答"输入 URL 后发生什么"要附上**可观测的排查手段**，这是区分背诵与理解的关键。
- 提连接复用必须说明边界：Nginx `keepalive_timeout`、LB 空闲超时、客户端连接池 keepalive 三者要对齐。
- 场景题作答给优先级与验证手段，不要罗列所有可能性。
### 14.4 示例
```bash
{ date; hostname; ss -s; ss -lnt; ss -tan | awk 'NR>1{print $1}' | sort | uniq -c; } \
  | tee /tmp/net-diag-$(date +%F-%H%M).txt
```
### 14.5 一句话速记
`DNS→握手→TLS→请求→处理→响应→渲染；排查反向分段测量，先定性再分层。`
## 自测题（含答案要点）
1. 三次握手为什么不能两次？两次无法确认客户端接收能力，且服务端会为失效 SYN 建连浪费资源。
2. SYN 半连接队列与 accept 队列何时使用？收到 SYN 入半连接队列，收到第三次 ACK 入 accept 队列等 `accept()`。
3. syncookies 的代价？无状态建连但丧失部分 TCP 扩展（窗口缩放、SACK 协商受限），属兜底手段。
4. TIME_WAIT 为什么是 2MSL、能否缩短？覆盖最后 ACK 丢失与旧报文消散；Linux 固定 60 秒，不可缩短。
5. CLOSE_WAIT 过多的唯一根因类别？应用未调用 close（资源泄漏、线程阻塞），调内核参数无效。
6. RTO 公式、快速重传与 SACK？`RTO=SRTT+4·RTTVAR`（最小 200ms）；3 个重复 ACK 立即重传，SACK 精确重传缺失区间。
7. 零窗口探测解决什么问题？接收方窗口更新报文丢失导致双方永久等待。
8. BBR 与 CUBIC 的核心差别？CUBIC 以丢包为拥塞信号，BBR 用带宽与最小 RTT 建模。
9. 40ms 延迟的成因与解法？Nagle 攒包 + 延迟确认 40ms；用 `TCP_NODELAY` 或合并写。
10. 粘包的本质与首选方案？TCP 字节流无消息边界；用长度字段（`LengthFieldBasedFrameDecoder`）。
11. HTTP/1.1 管道化为什么废弃？响应按序返回形成应用层队头阻塞，中间件支持差。
12. HTTP/2 遗留的最大问题与 HPACK 机制？TCP 层队头阻塞；HPACK = 静态表 + 动态表 + 霍夫曼编码。
13. 502 与 504 的区别？502 是上游返回非法响应/连不上，504 是等待上游超时。
14. 强缓存与协商缓存的字段与优先级？强缓存 `Cache-Control` > `Expires`，协商 `ETag` > `Last-Modified`。
15. 为什么 TLS1.3 仅凭服务器私钥无法解密？使用 (EC)DHE 临时密钥具备前向安全，需 `SSLKEYLOGFILE` 或 MITM。
16. Java 应用 DNS 缓存的坑？默认长期缓存解析结果，需设置 `networkaddress.cache.ttl`。
17. 连接被重置的常见原因？端口未监听、复用陈旧连接、backlog 溢出、防火墙阻断、`SO_LINGER=0`。
## 背诵卡片
1. OSI 七层 = 物数网传会表应；TCP/IP 四层 = 网络接口/网络/传输/应用。
2. 传输层单位叫段，网络层叫包，链路层叫帧。
3. 三次握手：SYN(x) → SYN+ACK(y, x+1) → ACK(x+1, y+1)。
4. 三次的理由：双向确认收发能力 + 防止历史连接误建。
5. ISN 随机：防旧报文混淆与序列号预测。
6. SYN 队列 = 半连接，accept 队列 = 全连接。
7. SYN Flood：syncookies + 调大队列 + 缩短重传 + LB 代答。
8. accept 队列满默认丢弃第三次 ACK，客户端假连接成功。
9. 四次挥手：FIN → ACK → FIN → ACK，因为 TCP 全双工。
10. TIME_WAIT 两个作用：保证最后 ACK 送达、旧报文消散。
11. Linux TIME_WAIT 固定 60 秒；主动方出 TIME_WAIT、被动方出 CLOSE_WAIT。
12. CLOSE_WAIT 多 = 代码没 close；端口耗尽报 `Cannot assign requested address`。
13. 发送窗口 = min(cwnd, rwnd)；零窗口靠 persist 探测。
14. 拥塞控制四阶段：慢启动、拥塞避免、快重传、快恢复。
15. CUBIC 看丢包，BBR 看带宽与 RTT。
16. Nagle + 延迟 ACK = 40ms 周期延迟，用 TCP_NODELAY。
17. 拆包三方案：定长、分隔符、长度字段（首选）。
18. TCP 无消息边界，粘包是应用层问题。
19. QUIC = UDP + TLS1.3 + 多路复用 + 连接迁移。
20. HTTP/1.1 长连接、HTTP/2 二进制分帧 + HPACK、HTTP/3 无队头阻塞。
21. 0-RTT 有重放风险，只用于幂等请求。
22. 301 永久 / 302 临时 / 304 协商命中 / 499 客户端断开。
23. 502 后端异常、503 过载、504 网关超时。
24. 强缓存不发请求，协商缓存发请求收 304。
25. no-cache 要校验，no-store 才是不落盘。
26. Cookie 三属性：HttpOnly 防 XSS、Secure、SameSite 防 CSRF。
27. Session 共享：粘性、复制、Redis、无状态 Token。
28. ECDHE 提供前向安全；TLS1.3 强制 PFS 且握手加密。
29. 本地 DNS 递归、根与权威迭代；HTTPDNS 绕污染。
30. 排查顺序：ping/mtr → nc → ss → tcpdump → 应用日志。
