## 1. 进程与线程
### 1.1 核心原理
| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 定义 | 资源分配的基本单位 | CPU 调度的基本单位 |
| 地址空间 | 独立，隔离性好 | 共享堆/方法区/fd，独享栈与寄存器 |
| 创建开销 | 大（页表、地址空间、fd 表） | 小（约进程的 1/10） |
| 通信 | 需要 IPC 机制 | 直接读写共享内存（需同步） |
| 崩溃影响 | 只影响自身 | 整个进程一起挂 |

- **上下文切换构成**：保存/恢复 CPU 寄存器与程序计数器、切换内核栈、更新调度信息；**进程切换额外切换页表基址寄存器（CR3）并导致 TLB 失效**。
- **切换时机**：时间片耗尽、阻塞（IO/锁/睡眠）、被高优先级抢占、主动 yield、中断返回时重新调度。
- **协程/用户态线程**：用户态调度，只保存少量寄存器、不陷入内核；阻塞时由运行时挂起任务，切换代价约为线程的 1/100~1/10。
### 1.2 面试问答
**Q1：线程切换贵在哪？**
A：直接开销是寄存器保存恢复（纳秒到微秒级），真正的损失是**间接开销**——缓存与 TLB 冷启动破坏局部性。所以"减少线程数"比"减少切换次数"更有效。边界：同进程线程切换不切页表，跨进程才刷 TLB。
**Q2：线程数越多越好吗？**
A：不是。受 CPU 核数、内存（每线程栈默认约 1MB）、上下文切换与锁竞争限制。经验值：CPU 密集 `N+1`、IO 密集 `2N~4N`（N 为核数），更准确的是按"目标 QPS × 平均耗时"估算并发度。边界：大量阻塞等待的 IO 场景应用 NIO + 少量事件循环线程或虚拟线程。
**Q3：Java 线程与操作系统线程的关系？**
A：Linux 上 1:1 映射到内核轻量级进程（`clone()` 创建），可被 `top -Hp` 看到；JDK 21 虚拟线程是 M:N（大量虚拟线程映射到少量载体平台线程）。
### 1.3 高频追问与陷阱
- 线程共享堆与方法区，栈不共享；`ThreadLocal` 数据挂在 Thread 对象上，线程池复用线程会串数据，务必 remove；`vmstat` 的 `cs` 与 `pidstat -w` 可观察切换。
### 1.4 示例
```bash
vmstat 1 5                    # cs = 每秒上下文切换次数
pidstat -w -p <pid> 1         # cswch/s 自愿、nvcswch/s 非自愿
ls /proc/<pid>/task | wc -l   # 进程的线程数
```
### 1.5 一句话速记
`进程是资源分配单位、线程是调度单位；切换大头是缓存与 TLB 失效，不是寄存器。`
## 2. 进程状态与 CPU 调度算法
### 2.1 核心原理
三态：**就绪 → 运行 → 阻塞**。迁移规则：运行 --时间片耗尽--> 就绪；运行 --等待事件--> 阻塞；阻塞 --事件完成--> 就绪（**不能直接到运行**）。Linux 内部状态：`R` 运行/就绪、`S` 可中断睡眠、`D` 不可中断睡眠、`T` 停止、`Z` 僵尸、`I` 空闲内核线程。

| 算法 | 策略 | 优点 | 缺点 |
| --- | --- | --- | --- |
| FCFS | 非抢占队列 | 公平简单 | 护航效应，长任务拖累短任务 |
| SJF | 选最短作业 | 平均等待时间最优 | 需预知时长，长任务饥饿 |
| 时间片轮转 | 固定时间片抢占 | 响应时间可预期 | 片太小则切换开销大 |
| 优先级调度 | 高优先级先跑 | 支持关键任务 | 低优先级饥饿，需老化 |
| 多级反馈队列 | 多队列 + 时间片递增 + 反馈降级 | 兼顾响应与吞吐 | 参数敏感、实现复杂 |
### 2.2 面试问答
**Q1：Linux 默认调度器是什么？**
A：普通进程用 **CFS（完全公平调度）**：不给固定时间片，而是按权重分配 CPU 时间，用 `vruntime`（虚拟运行时间，按权重缩放）挑选最小值运行；实时任务用 SCHED_FIFO/SCHED_RR。边界：6.6+ 内核挑选逻辑改为 EEVDF，但"公平分配"的思想不变。
**Q2：nice 值的作用？**
A：范围 -20（最高）~ 19（最低），普通用户只能调高 nice；每级约 1.25 倍 CPU 份额差异，只影响 CPU 争抢，不影响 IO 优先级（IO 用 `ionice`）。
**Q3：D 状态进程多说明什么？**
A：大量不可中断睡眠，通常是**磁盘或网络文件系统 IO 阻塞**（磁盘故障、NFS 卡死、内核驱动问题）；这类进程 `kill -9` 无效，只能等 IO 返回或重启。排查用 `ps -eo pid,stat,wchan,cmd` 看 `wchan` 卡在哪个内核函数。
### 2.3 高频追问与陷阱
- 僵尸进程（Z）是子进程已退出但父进程未 `wait()`，容器里 PID 1 不回收子进程会累积僵尸；Java `Thread.setPriority` 映射不到内核优先级，在 Linux 上几乎无效。
### 2.4 示例
```bash
ps -eo pid,ppid,stat,pcpu,pmem,wchan:20,cmd --sort=-pcpu | head -15
ps -eo stat,cmd | awk '$1 ~ /^[RD]/' | wc -l     # R/D 状态进程数
```
### 2.5 一句话速记
`就绪/运行/阻塞三态，阻塞必须先回就绪；CFS 按 vruntime 挑最小。`
## 3. 进程间通信（IPC）
### 3.1 核心原理
| 方式 | 数据方向 | 内核拷贝 | 适用场景 | 优缺点 |
| --- | --- | --- | --- | --- |
| 匿名管道 pipe | 单向 | 两次 | 父子进程、shell 管道 | 简单；容量默认 64KB、无消息边界 |
| 命名管道 FIFO | 单向 | 两次 | 无亲缘关系进程 | 有路径名可通信；仍单机 |
| 消息队列 | 双向 | 两次 | 解耦、按类型读取 | 有消息边界；单机、容量受限 |
| 共享内存 shm | 双向 | **零次** | 高频大数据量 | **最快**；必须自行同步 |
| 信号量 | 无数据 | — | 同步与互斥 | 只做计数/同步 |
| 信号 signal | 单向通知 | — | 事件通知（reload/terminate） | 不排队、易合并丢失 |
| Socket | 双向 | 两次 | 跨主机/跨进程 | 最通用；本机可用 unix domain 优化 |
### 3.2 面试问答
**Q1：哪种 IPC 最快，为什么？**
A：共享内存——数据不经过内核缓冲区拷贝，多进程映射同一块物理页，本质是零拷贝；代价是必须自己做同步。边界：跨机只能靠 Socket；本机通信可用 unix domain socket（Redis、Kafka 本机场景）。
**Q2：管道为什么是半双工？**
A：管道是一段内核缓冲区，默认一端写一端读；shell 的 `cmd1 | cmd2` 由两个 fork 出的进程分别把 stdout/stdin 重定向到写端/读端。边界：缓冲区满时 write 阻塞；读端关闭后写端收到 SIGPIPE（Java 中表现为 IOException: Broken pipe）。
**Q3：信号能传数据吗？**
A：不能，只传事件编号，且同类信号会合并丢失；`SIGKILL`/`SIGSTOP` 不可捕获不可忽略。实时信号支持排队但次数有限，不适合当消息通道。
### 3.3 高频追问与陷阱
- 共享内存必须配信号量或 `flock`，"无锁共享内存"是错误说法（Java 无直接共享内存，可用 `MappedByteBuffer` 近似）；管道与命名管道都不保证消息边界，读到半条要自己拼。
### 3.4 示例
`mkfifo /tmp/pipe && cat /tmp/pipe &`（命名管道）；`ipcs -m; ipcs -s`（查看共享内存段与信号量）。
### 3.5 一句话速记
`共享内存最快但需同步，Socket 最通用，管道最轻量，信号只传事件不传数据。`
## 4. 线程同步与经典问题
### 4.1 核心原理
| 原语 | 语义 | Java 对应 |
| --- | --- | --- |
| 互斥量 Mutex | 二值锁，同时只有一个持有者 | `synchronized`、`ReentrantLock` |
| 信号量 Semaphore | 计数许可，控制并发度 | `Semaphore` |
| 条件变量 | 在条件上等待/唤醒（必须配互斥量） | `Condition`、`Object.wait/notify` |
| 读写锁 | 读读共享、读写互斥、写写互斥 | `ReentrantReadWriteLock`、`StampedLock` |
| 自旋锁 | 忙等待，适合极短临界区 | CAS 循环、`AtomicInteger` |

经典问题：**生产者-消费者**（缓冲满/空时等待，必须 `while` 判条件）；**读者-写者**（读者优先会让写者饥饿，写者优先会让读者饥饿，工程上用读写锁 + 公平模式）。
### 4.2 面试问答
**Q1：为什么 wait/await 必须放在 while 里？**
A：两个原因——虚假唤醒（无 notify 也可能返回）、被唤醒到重新拿到锁之间条件可能又被破坏。必须重新检查条件。边界：`notify` 只唤醒任一线程，条件不匹配时它会再次等待；生产消费各用一个条件队列更稳。
**Q2：乐观锁与悲观锁在操作系统层面的对应？**
A：悲观锁 = 互斥量（先加锁再操作）；乐观锁 = CAS 循环（假设无冲突、失败重试）。边界：CAS 竞争激烈时空转烧 CPU，且有 ABA 问题（Java 用 `AtomicStampedReference`）；futex 的"用户态自旋 + 内核态阻塞"与 Java 锁升级是同一思想。
**Q3：`synchronized` 与操作系统互斥量的关系？**
A：慢路径最终通过 `futex` 实现：无竞争时用户态 CAS 改标记位即完成加锁（不进内核），有竞争时才 `futex(FUTEX_WAIT)` 挂起线程；`ReentrantLock` 同理走 AQS + `LockSupport.park`。详见 [../01-Java基础/03-并发编程.md](../01-Java基础/03-并发编程.md)。
### 4.3 高频追问与陷阱
- "自旋锁一定比互斥量快"是错的：临界区长时自旋白烧 CPU 并拖慢同核线程；条件变量必须与互斥量绑定，否则存在丢失唤醒的竞态窗口。
### 4.4 示例
```java
synchronized (queue) {
    while (queue.size() == capacity) queue.wait();   // 必须 while
    queue.add(item); queue.notifyAll();              // 优先 notifyAll
}
```
### 4.5 一句话速记
`锁管互斥、信号量管并发度、条件变量管等待唤醒；等待必须 while 判条件。`
## 5. 死锁
### 5.1 核心原理
**四个必要条件**：互斥、请求并保持、不可剥夺、循环等待（同时满足才可能死锁）。
- **预防**：破坏任一条件——资源一次性申请、可抢占（代价大）、**按序申请资源**（破坏循环等待，最实用）。
- **避免**：银行家算法（分配前判断是否处于安全状态），需预知最大资源需求，工程中基本不用。
- **检测与解除**：资源分配图找环 / 超时检测；解除靠剥夺资源、回滚事务、杀进程。
- **工程实践**：锁超时（`tryLock(timeout)`）、统一加锁顺序、单线程化、缩小锁粒度、无锁结构。
### 5.2 面试问答
**Q1：如何定位 Java 死锁？**
A：`jstack <pid>` 会直接输出 `Found one Java-level deadlock` 并给出线程与等待链；也可用 `jconsole` 或 Arthas 的 `thread -b`。边界：数据库死锁看 `SHOW ENGINE INNODB STATUS`，分布式锁死锁要查锁的过期与续期。
**Q2：活锁与饥饿的区别？**
A：活锁是线程都在运行但无法推进（互相礼让重试），解法是加随机退避；饥饿是某线程长期拿不到资源（优先级低或锁不公平），解法是公平锁或老化机制。
**Q3：为什么生产不用银行家算法？**
A：它要求预知每个进程的最大资源需求且资源数固定，现实需求动态变化；工程上用预防（加锁顺序 + 超时）而非避免。
### 5.3 高频追问与陷阱
- 单线程也可能死锁：同一不可重入锁重复获取、嵌套锁顺序不一致；数据库死锁很常见且通常正常（InnoDB 自动检测并回滚代价小的事务）。
- `kill -9` 持锁进程可能让共享资源处于不一致状态，需人工恢复。
### 5.4 示例
`jstack -l <pid> | grep -A 30 'deadlock'` 直接定位死锁链；Arthas 用 `thread -b` 找出阻塞其他线程的线程。
### 5.5 一句话速记
`死锁四条件：互斥、请求并保持、不可剥夺、循环等待；工程解 = 统一加锁顺序 + 锁超时。`
## 6. 虚拟内存、分页与页面置换
### 6.1 核心原理
**虚拟内存的意义**：1）进程隔离与安全；2）可用空间超过物理内存（换页 + Swap）；3）连续逻辑地址映射到离散物理页，解决碎片；4）共享库只加载一份（COW）。

**地址翻译**：虚拟地址 → 页号 + 偏移 → 查多级页表 → 物理页框 → 物理地址；**TLB** 缓存近期页表项，命中则无需访存页表。Linux 用 4/5 级页表，只为实际使用的地址范围分配页表页。

| 概念 | 单位 | 特点 |
| --- | --- | --- |
| 分页 | 固定大小（4KB，大页 2MB/1GB） | 无外部碎片、有内部碎片、对用户透明 |
| 分段 | 逻辑段（代码/数据/栈） | 符合程序逻辑便于共享保护、有外部碎片 |

**缺页中断处理流程**：访存 → 页表项无效 → 触发缺页异常 → 内核校验地址合法性（非法则 SIGSEGV）→ 分配物理页 → 内存不足则按置换算法换出（脏页先回写）→ 从磁盘读入 → 更新页表与 TLB → 重新执行指令。

| 置换算法 | 思想 | 特点 |
| --- | --- | --- |
| FIFO | 淘汰最早进入 | 简单，存在 Belady 异常 |
| LRU | 淘汰最久未使用 | 命中率好，精确实现代价高 |
| Clock | 环形扫描 + 访问位 | Linux 近似 LRU 的基础 |
| LFU | 淘汰访问次数最少 | 抗热点好，老数据难淘汰 |

**抖动（Thrashing）**：分到的页框少于工作集，缺页率暴涨，CPU 都耗在缺页上；缓解靠减少并发进程、加内存、按工作集动态调页框。
### 6.2 面试问答
**Q1：为什么需要虚拟内存？**
A：隔离（进程不能随意读写他人内存）、抽象（每进程以为自己独占连续空间，简化链接与内存管理）、超额分配（不够时用磁盘换页）。边界：代价是地址翻译开销（靠 TLB 缓解）与缺页开销，大页可减少 TLB miss。
**Q2：malloc 什么时候用 brk、什么时候用 mmap？**
A：glibc 中小于 `MMAP_THRESHOLD`（默认 128KB）从堆分配、通过 `brk` 移动堆顶；大于阈值用 `mmap` 匿名映射独立区域。`brk` 归还难、碎片多，`mmap` 的 free 直接 `munmap` 归还。Java 的 DirectByteBuffer 走 mmap/malloc，受 `-XX:MaxDirectMemorySize` 限制。
**Q3：Swap 的利弊？**
A：让内存超卖成为可能，但磁盘比内存慢 4~5 个数量级，一旦频繁换页（`si/so` 高）系统响应急剧恶化；生产常把 `vm.swappiness` 调到 1~10，K8s 默认禁用 Swap 以保证 QoS。边界：完全无 Swap 时突发峰值只能靠 OOM Killer。
**Q4：Copy-On-Write 用在哪？**
A：`fork()` 后父子共享物理页并标只读，任一方写入才复制该页，所以"fork 后立即 exec"开销很小；Redis 的 BGSAVE 也依赖 fork+COW。边界：写量大时 COW 会复制大量页导致内存翻倍（bgsave 时内存告警的根因）。
### 6.3 高频追问与陷阱
- 页表项无效不一定是缺页，也可能是非法访问（越界/野指针）→ SIGSEGV；`free` 小但 `available` 多属正常。
- minor fault（页在内存未映射）与 major fault（需读盘）差别很大；HugePage 需预分配，`HugePages_Total` 为 0 时 JVM `-XX:+UseLargePages` 会启动失败。
### 6.4 示例
```bash
vmstat 1 5                                                   # si/so 非 0 说明换页
grep -E 'MemTotal|MemAvailable|SwapTotal|Huge' /proc/meminfo
/usr/bin/time -v ./app                                       # 查看 minor/major page fault
```
### 6.5 一句话速记
`虚拟内存 = 隔离 + 抽象 + 超额分配；小分配走 brk、大分配走 mmap；Swap 一换就慢。`
## 7. 零拷贝
### 7.1 核心原理
传统 `read + write` 有 **4 次拷贝 + 4 次上下文切换**：磁盘 --DMA--> 页缓存 --CPU--> 用户缓冲 --CPU--> socket 缓冲 --DMA--> 网卡。

| 方案 | 拷贝次数 | 上下文切换 | 说明 |
| --- | --- | --- | --- |
| read + write | 4 | 4 | 基线 |
| mmap + write | 3 | 4 | 消除"内核→用户"拷贝，适合需要改数据的场景 |
| sendfile | 3（网卡支持 SG-DMA 时 2） | 2 | 应用全程不碰数据，最常用 |
| splice | 2~3 | 2 | 通过管道，不依赖硬件支持 |

应用：Kafka 用 `FileChannel.transferTo`（sendfile）发日志段；Nginx `sendfile on` 发静态文件；RocketMQ 用 mmap 写 CommitLog 并顺序写；Netty 用 `FileRegion`。
### 7.2 面试问答
**Q1：零拷贝真的是零次拷贝吗？**
A：不是——指**没有 CPU 参与的拷贝**（用户态视角零次），DMA 拷贝仍存在但不占 CPU。边界：数据要加工（加密、压缩）就无法直接 sendfile，需退回 mmap 或用户态缓冲。
**Q2：用了 sendfile 为什么还可能不理想？**
A：1）网卡/驱动不支持 scatter-gather DMA 时退化为完整拷贝；2）数据小于 MSS 或需要 TLS 加密（需用户态处理，现代可用 kTLS）；3）页缓存命中率低，磁盘成为瓶颈——零拷贝只省 CPU 与内存带宽，不解决 IO 吞吐。
**Q3：mmap 与 sendfile 怎么选？**
A：不改数据、只转发用 sendfile（最省）；需要读取或修改内容用 mmap（可随机访问，但要注意脏页回写与"文件被外部修改后行为未定义"）。边界：大文件顺序写场景 mmap 有 `fsync`/`unmap` 停顿，Kafka 因此在大文件上改用顺序写 + 页缓存。
### 7.3 高频追问与陷阱
- 零拷贝不解决持久化问题，Kafka 依然依赖页缓存与刷盘策略；Java `transferTo` 单次上限约 2GB（`int` 限制），大文件要循环并累计返回值。
- mmap 在 32 位系统受地址空间限制；64 位下虚拟地址占用会体现在 `VIRT` 中。
### 7.4 示例
```java
try (FileChannel in = FileChannel.open(Paths.get("big.log"));
     FileChannel out = FileChannel.open(Paths.get("copy.log"), CREATE, WRITE)) {
    long pos = 0, size = in.size();
    while (pos < size) pos += in.transferTo(pos, size - pos, out);   // 注意循环
}
```
### 7.5 一句话速记
`read+write 是 4 拷贝 4 切换；sendfile 降到 2 次切换，mmap+write 降到 3 次拷贝；零拷贝 = 零 CPU 拷贝。`
## 8. 用户态/内核态、系统调用与中断
### 8.1 核心原理
- **为什么分态**：内核代码可操作硬件与全部内存，用户程序不能；x86 用 ring 0/3 隔离，靠陷阱指令（`syscall`）切换。
- **进入内核态三途径**：系统调用（主动）、异常（缺页、除零）、外部中断（时钟、网卡、磁盘）。
- **系统调用流程**：用户态准备参数 → 执行 `syscall`（保存用户上下文、按调用号分发）→ 内核处理 → 返回用户态恢复上下文；开销几百纳秒到几微秒。
- **中断**：硬中断由设备触发、要求极快返回，故分**上半部**（直接处理关键动作）与**下半部**（softirq/tasklet/workqueue 延后处理耗时逻辑）；网络收包即"网卡硬中断 → NET_RX_SOFTIRQ → 协议栈 → socket 缓冲"。
### 8.2 面试问答
**Q1：系统调用开销为什么大？**
A：不止切特权级：要保存恢复上下文、切内核栈、可能污染分支预测与缓存，还要参数校验与安全拷贝（`copy_from_user`）。因此高性能程序会**减少/批量**系统调用：buffered IO、`writev` 合并写、`epoll_wait` 一次取多个事件、mmap 代替反复读写。
**Q2：vDSO 是什么？**
A：内核把 `clock_gettime`/`gettimeofday` 等只读系统调用的实现映射到用户态，调用完全不进内核（约 20~30ns），所以"`currentTimeMillis` 慢"的老结论在现代内核上不成立。
**Q3：软中断与硬中断的区别？**
A：硬中断由硬件触发、有关中断语境与时序要求；软中断由内核在 `ksoftirqd` 上下文延后执行、可被硬中断打断。`si` 时间高通常意味网络或磁盘流量大，`/proc/softirqs` 可看分类计数。
### 8.3 高频追问与陷阱
- strace 通过 ptrace 停止进程会极大放大系统调用开销，生产不要长时间挂；`perf top` 中 `do_syscall_64` 占比高说明系统调用密集，而不是内核有 Bug。
### 8.4 示例
`strace -c -f -p <pid>` 统计系统调用次数与耗时（短时间用）；`cat /proc/softirqs` 看各类软中断计数；`perf top -p <pid>` 看内核态热点。
### 8.5 一句话速记
`进内核三途径：系统调用、异常、中断；硬中断分上下半部，软中断在 ksoftirqd 里跑。`
## 9. Linux 五种 IO 模型与 epoll
### 9.1 核心原理
IO 分两阶段：**数据准备**（等到数据进内核缓冲）与**数据拷贝**（内核缓冲 → 用户缓冲）。

| 模型 | 数据准备 | 数据拷贝 | 特点 |
| --- | --- | --- | --- |
| 阻塞 IO | 阻塞 | 阻塞 | 最简单，一连接一线程 |
| 非阻塞 IO | 轮询不阻塞 | 阻塞 | 忙轮询烧 CPU |
| IO 多路复用 | 阻塞在事件上 | 阻塞 | 一线程管多连接，主流 |
| 信号驱动 IO | 不阻塞（SIGIO） | 阻塞 | 少见，信号处理复杂 |
| 异步 IO | 不阻塞 | **不阻塞** | 真异步，io_uring 为代表 |

| 维度 | select | poll | epoll |
| --- | --- | --- | --- |
| 数据结构 | 位图 fd_set | 数组 pollfd | 红黑树 + 就绪链表 |
| fd 上限 | 1024 | 无硬上限 | 无硬上限 |
| 每次调用 | O(n) 拷贝 + 遍历 | O(n) 拷贝 + 遍历 | 注册一次，回调入就绪链表 |
| 定位就绪 fd | O(n) | O(n) | O(k) |
| 触发模式 | LT | LT | LT / ET |
| 平台 | 跨平台 | 跨平台 | 仅 Linux |

**LT 与 ET**：LT 只要缓冲区有数据就持续通知（简单、默认）；ET 只在状态变化时通知一次，必须**循环读到 EAGAIN** 且 fd 必须非阻塞，否则丢事件或阻塞。Java NIO 的 `Selector` 在 Linux 上默认是 **epoll LT**。
### 9.2 面试问答
**Q1：epoll 为什么高效？**
A：1）红黑树存所有被监听的 fd，增删改 O(log n)，一次注册长期有效；2）回调机制——数据到达时内核把 fd 加入就绪链表，`epoll_wait` 直接返回就绪列表，无需遍历全部 fd；3）`mmap` 共享内存减少拷贝。边界：连接少且都活跃时 epoll 不一定比 select 快（要维护红黑树），其优势在**大量连接、少量活跃**。
**Q2：ET 模式必须注意什么？**
A：fd 设非阻塞并**循环读取直到返回 EAGAIN**，写事件也要处理"只写一部分"；否则残留数据不会再有新事件，永远读不到。
**Q3：多路复用与异步 IO 的本质差别？**
A：多路复用是"通知你可读了，你自己去读（拷贝仍阻塞）"，属**同步 IO**；异步 IO 是"我帮你读完再通知你"。Linux 原生 AIO 只对直接 IO 友好，通用性差，因此有了 `io_uring`（共享环形提交/完成队列，可批量提交）。边界：Java 的 `AsynchronousFileChannel` 在 Linux 上是线程池模拟，不是内核 AIO。
### 9.3 高频追问与陷阱
- 惊群：多线程/进程等同一事件，可用 `EPOLLEXCLUSIVE` 与 `SO_REUSEPORT` 缓解；大量短连接下 epoll 的注册/注销开销不可忽略，故 Nginx 用连接池、Netty 用对象池。
### 9.4 示例
`strace -e trace=epoll_wait,accept4,read,write -f -p <pid>` 观察 IO 事件；`ls -l /proc/<pid>/fd | wc -l` 与 `ulimit -n` 对比判断句柄是否告急。
### 9.5 一句话速记
`五种模型只差"两阶段谁阻塞"；epoll 高效在红黑树 + 就绪链表 + 回调；ET 必须读到 EAGAIN。`
## 10. Reactor/Proactor 与 Java NIO、Netty
### 10.1 核心原理
| 模式 | 谁完成读写 | 典型实现 |
| --- | --- | --- |
| Reactor | 事件就绪后应用自己读写（同步非阻塞） | Netty、Redis、Nginx |
| Proactor | 内核完成读写后通知应用（真异步） | Windows IOCP、io_uring 风格 |

Reactor 演化：单 Reactor 单线程（Redis 命令执行为此模型）→ 单 Reactor 多线程（业务交线程池）→ **主从 Reactor 多线程**（MainReactor 只 accept、SubReactor 各管一批连接读写、业务线程池处理逻辑），**Netty 默认即此模型**。

| Java NIO | Netty 封装 | 说明 |
| --- | --- | --- |
| `Selector` | `EventLoop` | 一个 EventLoop 绑定一个线程 |
| `Channel` | `NioSocketChannel`/`EpollSocketChannel` | 提供 epoll 原生封装 |
| `ByteBuffer` | `ByteBuf` | 读写指针分离、可池化、引用计数 |
| 无 | `ChannelPipeline` + `Handler` | 责任链处理编解码与业务 |
| 无 | `LengthFieldBasedFrameDecoder` | 解决粘包拆包（见 [./01-计算机网络.md](./01-计算机网络.md)） |
### 10.2 面试问答
**Q1：Netty 为什么不用 JDK 原生 NIO？**
A：1）API 复杂、`ByteBuffer` 单指针易错；2）**epoll 空轮询 bug**（selector 返回 0 却无事件导致 CPU 100%），Netty 用 `selectCnt` 计数并重建 Selector 规避；3）缺少半包处理、编解码、空闲检测；4）无内存池与零拷贝能力。
**Q2：Netty 线程模型参数怎么设？**
A：`bossGroup` 一般 1 个线程（只 accept）；`workerGroup` 默认 `2 × CPU`，纯 IO 场景 1× 核数即可；业务逻辑重时应放到独立业务线程池。**绝不能在 ChannelHandler 里做阻塞操作**（同步 DB/RPC、大文件读），会僵死整条 EventLoop 上的所有连接。
**Q3：ByteBuf 为什么优于 ByteBuffer？**
A：读写指针分离免去 flip；支持池化减少 GC；支持堆外内存与 `CompositeByteBuf` 零拷贝组合；引用计数显式管理生命周期。边界：引用计数用错即内存泄漏，可用 `-Dio.netty.leakDetection.level=paranoid` 排查。
### 10.3 高频追问与陷阱
- "Redis 是单线程"要精确：命令执行单线程，网络 IO 在 6.0 后可多线程，持久化与异步删除另起线程。
- EventLoop 绑定线程后不切换，同一连接的事件都在同一线程处理，天然无并发；Linux 上长期缺成熟 Proactor（AIO 不成熟），因此高性能服务实际都是 Reactor。
### 10.4 示例
```java
EventLoopGroup boss = new NioEventLoopGroup(1);
EventLoopGroup worker = new NioEventLoopGroup();
new ServerBootstrap().group(boss, worker).channel(NioServerSocketChannel.class)
    .childOption(ChannelOption.TCP_NODELAY, true)
    .childOption(ChannelOption.SO_KEEPALIVE, true)
    .childHandler(new ChannelInitializer<SocketChannel>() {
        protected void initChannel(SocketChannel ch) {
            ch.pipeline().addLast(new LengthFieldBasedFrameDecoder(1 << 20, 0, 4, 0, 4));
        }
    });
```
### 10.5 一句话速记
`Reactor = 就绪后自己读；主从 Reactor 就是 boss 收连接、worker 管读写，业务另起线程池。`
## 11. 文件系统与 Page Cache
### 11.1 核心原理
- **inode** 保存文件元数据（权限、大小、时间、数据块指针）但不含文件名；**目录项 dentry** 把"目录 + 文件名"映射到 inode，所以同一 inode 可有多个名字（**硬链接**），软链接则是独立文件、内容是目标路径。
- **读写流程**：`open` 得到 fd → `read/write` 先经 **Page Cache** → 缺页回源磁盘 → 脏页由内核回写线程按 `dirty_ratio`、`dirty_expire_centisecs` 刷盘。
- **顺序写 vs 随机写**：顺序写命中预读与连续块分配，吞吐远高于随机写（机械盘差两个数量级，SSD 仍有 2~5 倍），这是 Kafka 顺序追加与 LSM-Tree 优于 B+ 树随机写的原因。
- **direct IO**（`O_DIRECT`）绕过 Page Cache，适合自建缓存的数据库，代价是失去预读与合并写并需对齐；**fsync/fdatasync** 强制落盘（`fdatasync` 不写非必要元数据，更快；`O_SYNC` 每次写都等落盘）。
- **`write` 成功的含义**：数据只到 Page Cache，进程崩溃不丢，机器掉电会丢。
### 11.2 面试问答
**Q1：Page Cache 是好事还是坏事？**
A：总体是好事——把随机 IO 变顺序、重复读变内存命中、支持预读与合并写，Kafka 直接依赖它而不用 JVM 堆缓存（减少 GC 且避免双份内存）。坏处：脏页积累过多时一次性回写造成 IO 尖峰；内存被缓存占满挤压应用（看 `available`）。边界：容器内 `/proc/meminfo` 是宿主机口径。
**Q2：fsync/fdatasync/O_SYNC 的区别？**
A：`fsync` 落数据与元数据；`fdatasync` 只落数据（文件大小变化仍需元数据），更快；`O_SYNC` 每次 write 都等待落盘，最慢最安全。MySQL 的 `innodb_flush_log_at_trx_commit=1` 即每次提交 fsync redo log。
**Q3：机械盘随机写为什么慢？**
A：需要寻道 + 旋转延迟（各约几毫秒），随机 IOPS 只有 100~200，而顺序吞吐可达 100+ MB/s；SSD 无机械动作但受写放大、GC 与 FTL 映射影响，随机写仍慢于顺序写。
### 11.3 高频追问与陷阱
- inode 耗尽（`df -i` 100%）时创建文件报 `No space left on device`，而 `df -h` 空间充足——线上经典故障。
- 删除了仍被进程打开的文件空间不释放，需 `lsof +L1` 找到进程后重启或截断 `/proc/<pid>/fd/<n>`；硬链接不能跨文件系统也不能指向目录，软链接可以但目标删除后成为死链接。
### 11.4 示例
```bash
df -h; df -i                  # 空间与 inode 双查
lsof +L1                      # 已删除但仍被占用的文件
iostat -xdm 1 5 | grep -E 'Device|sd|nvme'
```
### 11.5 一句话速记
`inode 存元数据、dentry 存名字；write 只到 Page Cache，fsync 才落盘；顺序写永远优于随机写。`
## 12. CPU 缓存、伪共享与内存屏障
### 12.1 核心原理
- **缓存层级**：L1（32~64KB，约 4 周期）→ L2（256KB~1MB，约 12 周期）→ L3（数十 MB，约 40 周期）→ 内存（200+ 周期）；缓存以 **cache line（通常 64 字节）** 为单位加载。
- **MESI 一致性协议**：Modified/Exclusive/Shared/Invalid，写操作需使其他核副本失效（RFO），这是跨核通信的硬件基础。
- **伪共享（False Sharing）**：两个无关变量落在同一 cache line 且被不同核频繁写，导致该行在两核间反复失效（乒乓），性能可能下降数倍。
- **内存屏障**：编译器和 CPU 都可能重排序；硬件提供 `lfence/sfence/mfence`，JVM 提供 LoadLoad/StoreStore/LoadStore/StoreLoad 屏障。**volatile 的硬件基础** = 写后 StoreLoad 屏障 + 读前 LoadLoad 屏障（x86 上用 `lock` 前缀指令兼作全屏障）。
### 12.2 面试问答
**Q1：伪共享如何产生、如何解决？**
A：典型如 Disruptor 的 RingBuffer 游标、`LongAdder` 的 Cell 数组。解决：手动填充（前后各补到 64 字节边界）、`@sun.misc.Contended` 配合 `-XX:-RestrictContended`、把变量拆到不同对象。边界：只有**至少一方写**才会乒乓，纯读共享不受影响。
**Q2：volatile 为什么保证可见性但不保证原子性？**
A：可见性靠写回主存 + 使其他核缓存失效（MESI + 屏障），后续读必看到新值；但 `i++` 是读-改-写复合操作，多线程交错仍丢失更新，原子性要靠 CAS 或加锁。边界：volatile 还能阻止重排（DCL 单例必须用它），这是 JMM 的规范要求。
**Q3：为什么 LongAdder 比 AtomicLong 快？**
A：`AtomicLong` 所有线程 CAS 同一地址，竞争激烈时反复失败空转并让 cache line 乒乓；`LongAdder` 用分段 Cell 数组（带 `@Contended` 填充）让各线程更新自己的 Cell，最后 `sum()` 汇总，把竞争从 1 个点散开。边界：`sum()` 不保证强一致，不适合余额类精确读取。
### 12.3 高频追问与陷阱
- `@Contended` 在 JDK 9+ 对用户类需 `-XX:-RestrictContended` 才生效且额外占内存；缓存行 64 字节是 x86 主流值（部分架构 128 字节，用 `getconf LEVEL1_DCACHE_LINESIZE` 查）。
- x86 的 TSO 模型只允许 Store-Load 重排，很多屏障是空操作；CAS 的 ABA 问题与伪共享是两个独立话题，不要混答。
### 12.4 示例
```java
final class PaddedLong {                 // 手工填充规避伪共享
    long p1, p2, p3, p4, p5, p6, p7;
    volatile long value;
    long q1, q2, q3, q4, q5, q6, q7;
}
```
### 12.5 一句话速记
`缓存按 64 字节行加载、MESI 保一致；伪共享靠填充/@Contended，volatile = 屏障 + 可见性。`
## 13. 磁盘与 RAID
### 13.1 核心原理
| RAID | 方式 | 可用容量 | 冗余 | 适用 |
| --- | --- | --- | --- | --- |
| 0 | 条带化 | 100% | 无 | 追求吞吐、可容忍丢失 |
| 1 | 镜像 | 50% | 高 | 系统盘、小容量高可靠 |
| 5 | 条带 + 单校验 | (N-1)/N | 中（坏 1 块） | 读多写少；有写惩罚 |
| 6 | 双校验 | (N-2)/N | 高（坏 2 块） | 大容量盘阵，重建期安全 |
| 10 | 条带 + 镜像 | 50% | 高，性能最好 | **数据库首选** |

关键指标：IOPS（随机小 IO）、吞吐（顺序大 IO）、`%util`（饱和参考）、`await`（平均等待含排队）、`aqu-sz`（平均队列长度）。
### 13.2 面试问答
**Q1：数据库为什么推荐 RAID 10 而不是 RAID 5？**
A：RAID 5 有**写惩罚**（一次随机写要读旧数据 + 读旧校验 + 写新数据 + 写新校验，4 次 IO），随机写差；大容量盘重建要数小时到数天，重建期再坏一块就全丢。RAID 10 无校验计算、重建快、随机写最好。边界：RAID 不是备份，误删与勒索病毒无法靠它恢复。
**Q2：SSD 需要注意什么？**
A：写放大（小随机写引发整块擦除，需预留空间与 TRIM）、寿命（DWPD/TBW，写密集选企业级）、GC 与磨损均衡造成的 P99 抖动、分区与 `O_DIRECT` 对齐。边界：SSD 随机读远强于 HDD，但顺序与随机仍差 2~5 倍。
### 13.3 高频追问与陷阱
- `%util` 接近 100% 只说明有 IO 排队，多队列 SSD 可能仍有富余，`svctm` 在新版 iostat 已废弃；云盘有独立 IOPS/吞吐上限与突发积分（burst balance），云上"磁盘慢"要查云监控。
### 13.4 示例
`iostat -xdm 1 5` 看 %util/await/aqu-sz；`iotop -o -P` 定位高 IO 进程；压测用 `fio --name=rr --ioengine=libaio --bs=4k --rw=randread --size=1G --runtime=30`。
### 13.5 一句话速记
`RAID 10 性能最好、RAID 5 有写惩罚；SSD 关注写放大与寿命，iostat 看 %util + await + aqu-sz。`
## 14. 操作系统与 Java 的关联点清单
### 14.1 核心原理
| 操作系统机制 | Java 对应 | 实践影响 |
| --- | --- | --- |
| CFS 调度 | `Thread`、`ForkJoinPool`、虚拟线程 | 线程优先级无效，靠池大小与队列控制 |
| futex | `synchronized`、AQS、`LockSupport.park` | 锁竞争激烈时反复挂起/唤醒 |
| 虚拟内存 / mmap | DirectByteBuffer、`MappedByteBuffer` | 堆外内存不算堆但算 RSS，易被 OOM-Kill |
| Page Cache | 文件读写 | 小文件读取受缓存影响极大 |
| IO 模型 | NIO Selector、Netty、`AsynchronousFileChannel` | 高并发用 epoll，别用阻塞 IO 撑并发 |
| 零拷贝 | `FileChannel.transferTo`、`FileRegion` | 大文件与消息转发省 CPU |
| COW | `ProcessBuilder` fork、Redis BGSAVE | fork 大堆会短暂抖动 |
| 缓存与屏障 | `volatile`、`Atomic*`、`@Contended` | 高并发计数用 LongAdder |
| 信号 | SIGTERM 优雅停机、SIGSEGV 崩溃日志 | 容器 stop 默认 TERM，需注册 shutdown hook |
| 文件描述符 | Socket/File 通道 | `ulimit -n` 决定最大连接数 |
### 14.2 面试问答
**Q1：为什么 Java 直接内存会 OOM？**
A：直接内存不在堆里，受 `-XX:MaxDirectMemorySize` 限制（默认等于 `-Xmx`），超出抛 `OutOfMemoryError: Direct buffer memory`；同时计入进程 RSS，容器中触发 OOM Killer（进程被 `kill -9`、JVM 无日志）。排查用 `-XX:NativeMemoryTracking=summary` + `jcmd VM.native_memory`、`pmap`。边界：回收依赖 `Cleaner`/虚引用，不及时。
**Q2：JVM 如何正确识别容器资源限制？**
A：JDK 8u191+ 默认开启 `UseContainerSupport`，按 cgroup 限额计算堆与 `ActiveProcessorCount`；老版本会把宿主机资源当限额，导致 GC 线程过多、堆过大而被 OOM-Kill。边界：K8s 的 CPU limit 是配额而非核数，建议显式 `-XX:ActiveProcessorCount`。
**Q3：Java 线程卡住如何与操作系统现象对应？**
A：`top -Hp <pid>` 找高 CPU 的 LWP（即线程 tid）→ `printf '%x'` 转十六进制 → 在 `jstack` 里搜 `nid=0x...` 定位线程栈；阻塞类问题看 `pidstat -w` 的自愿切换次数，并用 `jstack -l` 看 `BLOCKED`/`WAITING` 与锁持有者。详见 [./04-Linux与常用命令.md](./04-Linux与常用命令.md)。
### 14.3 高频追问与陷阱
- 进程 RSS = 堆 + 元空间 + 直接内存 + 线程栈 + JVM 自身 + 代码缓存，"堆内存 = 进程内存"是错的。
- `ulimit -n` 与最大连接数直接相关（Tomcat `maxConnections` 默认 8192 而 Linux 默认 fd 上限 1024，必须同步改）；容器中 `/proc/cpuinfo` 仍是宿主机信息，判断核数用 `Runtime.availableProcessors()`。
### 14.4 示例
```bash
top -Hp <pid> -b -n 1 | head -20
printf '0x%x\n' <tid>
jstack <pid> | grep -A 20 'nid=0x<hex>'
cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max
```
### 14.5 一句话速记
`Java 的每次 park、write、mmap 都落在操作系统上：懂内核才知道瓶颈在哪一层。`
## 自测题（含答案要点）
1. 进程与线程的本质区别？进程是资源分配单位且有独立地址空间，线程是调度单位且共享进程资源。
2. 进程切换比线程切换慢在哪？额外切换页表并刷新 TLB，地址空间相关缓存失效；协程则在用户态调度、不陷入内核。
3. Java 线程与内核线程关系？Linux 上 1:1 映射 LWP（`clone()` 创建），JDK 21 虚拟线程为 M:N。
4. CFS 如何保证公平？按权重分配时间，调度 `vruntime` 最小的线程。
5. D 状态进程意味着什么？不可中断睡眠，通常卡在磁盘/NFS IO，`kill -9` 无效。
6. 最快的 IPC 方式及代价？共享内存（零拷贝），代价是必须自行同步。
7. 等待条件为什么必须用 while？防虚假唤醒与被唤醒后条件再次被破坏。
8. 死锁四个必要条件与最实用的破坏方式？互斥、请求并保持、不可剥夺、循环等待；统一加锁顺序 + 锁超时。
9. 虚拟内存的三大作用？隔离安全、连续地址抽象、超额分配（换页）。
10. 缺页中断处理步骤？校验地址 → 分配页 → 必要时置换并回写脏页 → 读入 → 更新页表/TLB → 重执行。
11. malloc 何时用 mmap？大块分配（默认 ≥128KB）或超过阈值时，匿名映射独立区域。
12. 零拷贝省了什么？省 CPU 参与的拷贝次数与上下文切换（DMA 拷贝仍在）。
13. sendfile 与 mmap 的适用差异？不需改数据用 sendfile；需要读写内容用 mmap。
14. 进入内核态的三种途径？系统调用、异常（缺页/除零）、外部中断。
15. epoll 相比 select 的三个优势？无 fd 上限、就绪链表 O(1) 通知、免遍历与免重复拷贝；ET 模式还需非阻塞 + 循环读到 EAGAIN。
16. Page Cache 的双刃剑？提升吞吐（顺序化、预读、合并写），但脏页回写造 IO 尖峰并占用内存。
17. 伪共享的成因与解法？无关变量共享 cache line 被多核写；填充或 `@Contended`。
18. 为什么用 LongAdder？分段 Cell 消除热点 CAS 竞争与缓存行乒乓，`sum()` 弱一致。
## 背诵卡片
1. 进程 = 资源分配单位，线程 = CPU 调度单位。
2. 线程切换真正贵在缓存/TLB 冷启动，不在寄存器保存。
3. Linux 上 Java 线程 1:1 映射 LWP；虚拟线程是 M:N。
4. 三态：就绪、运行、阻塞；阻塞必须先回就绪。
5. Linux 默认 CFS，挑 `vruntime` 最小的跑。
6. nice 范围 -20~19，只影响 CPU 争抢。
7. D 状态 = 不可中断睡眠，通常等 IO，`kill -9` 无效。
8. Z 状态 = 僵尸，父进程没 `wait()`。
9. IPC 最快是共享内存，最通用是 Socket。
10. 管道半双工、64KB 内核缓冲、无消息边界。
11. 信号只传事件编号且会合并丢失；SIGKILL/SIGSTOP 不可捕获。
12. 生产者消费者：等待必须 `while`，唤醒优先 `notifyAll`。
13. 死锁四条件：互斥、请求并保持、不可剥夺、循环等待。
14. 实用防死锁：统一加锁顺序 + `tryLock` 超时。
15. 虚拟内存三作用：隔离、抽象、超额分配。
16. 页表分级 + TLB；大页减少 TLB miss。
17. 缺页分 minor（无磁盘 IO）与 major（需读盘）。
18. 置换算法：FIFO 有 Belady 异常，Linux 用近似 LRU 的 Clock。
19. 抖动 = 页框少于工作集，缺页率暴涨。
20. 小分配走 brk，大分配（≥128KB）走 mmap。
21. Swap 一换就慢，生产常把 `vm.swappiness` 调到 1~10。
22. COW：fork 后共享物理页，写时才复制（Redis BGSAVE 靠它）。
23. read+write 是 4 次拷贝 4 次切换；sendfile 降到 2 次切换。
24. 零拷贝 = 零 CPU 拷贝，DMA 拷贝仍在。
25. Kafka 用 sendfile 发消息、RocketMQ 用 mmap 写 CommitLog。
26. 进内核三途径：系统调用、异常、中断。
27. 硬中断上半部快、下半部（softirq）慢；`si` 高说明网络/磁盘忙。
28. 五种 IO 模型差别在"两阶段谁阻塞"；epoll 是同步多路复用。
29. LT 简单、ET 高效但必须非阻塞 + 读到 EAGAIN。
30. Netty 主从 Reactor：boss 收连接、worker 管 IO、业务别阻塞 IO 线程。
