## 1. ZK 定位、数据模型与节点类型
### 1.1 核心原理
ZooKeeper 是**分布式协调服务**，提供"高可用的小数据强一致存储 + 通知机制"，用于解决分布式系统中的协调问题（选主、锁、配置、注册）。数据模型是一棵 **ZNode 树**（类似文件系统，路径如 `/app/config/db`），每个 ZNode 可存少量数据（**默认上限 1MB**，`jute.maxbuffer` 可调但绝不该用来存大对象）。**节点类型**：持久（PERSISTENT）、临时（EPHEMERAL，随会话消失）、顺序（SEQUENTIAL，创建时自动追加 10 位单调递增后缀）、持久顺序/临时顺序；3.5+ 增加**容器节点**（CONTAINER，最后一个子节点被删除后由服务端延迟清理）与 **TTL 节点**（需显式开启扩展类型）。每个 ZNode 有 **Stat 结构**（`czxid`/`mzxid`/`ctime`/`mtime`/`version`/`cversion`/`aversion`/`ephemeralOwner`/`numChildren`/`pzxid`），其中 `version` 用于 **CAS 乐观锁**（`setData(path, data, version)` 与 `delete(path, version)`，传 `-1` 表示忽略版本）。
### 1.2 面试问答
**Q1：ZK 适合做什么、不适合做什么？**
A：适合——元数据量小、读远多于写、需要强一致与通知的协调场景（配置、注册、选主、锁）。不适合——大容量存储（单节点 1MB 上限）、高写吞吐（所有写都要经 Leader + 多数派 ack + fsync，量级在万级 TPS 以内）、高频变更（每次变更都产生 Watcher 事件与事务日志）。结论：**ZK 是协调组件，不是数据库**。
**Q2：临时节点为什么是分布式协调的基石？**
A：临时节点的生命周期绑定**会话**：客户端与 ZK 断开且会话超时后，服务端自动删除该节点。由此可自然表达"进程存活"——注册中心用它表示服务在线，分布式锁用它表示持有者仍存活，选主用它表示 Candidate 存在。注意：临时节点**不能有子节点**，且会话过期与网络抖动要区分（抖动手动重连不会丢节点）。
**Q3：顺序节点的后缀有什么用？**
A：后缀由父节点维护的计数器单调递增，可在**无锁**前提下实现"排队"：所有竞争者创建临时顺序节点，序号最小者获得锁/成为 Leader，其余只需监听前一个节点，从而避免惊群。这是 ZK 实现公平锁、分布式队列、屏障的核心技巧。
**Q4：版本号怎么用？**
A：`version` 每次写自增，可用于 CAS：`setData`/`delete` 带上期望版本，版本不符抛 `BadVersionException`。用途是"读-改-写"场景防止并发覆盖；若不想校验传 `-1`。注意 `cversion` 管子节点变更、`aversion` 管 ACL 变更，三者互不相同。
**Q5：ZK 的数据是存在内存还是磁盘？**
A：**全量数据常驻内存**（这也是它能支撑高读吞吐的原因，数据量必须小），同时通过**事务日志（WAL，先写日志再改内存）**与**快照**持久化。恢复时先加载快照再重放事务日志，因此既快又可靠。
### 1.3 高频追问与陷阱
- 陷阱：把配置内容（几 MB 的 JSON）放进 ZNode——超过 1MB 直接报错，且每次读都要全量传输。
- 陷阱：用临时节点表达"业务数据"，误以为进程重启还能保留——会话过期即消失。
- 追问：容器节点（3.5+）解决什么问题？用于 Leader 选举等"一次性的父节点"场景，避免人为清理空的持久父节点。
### 1.4 配置/命令示例
```bash
create -e /lock/lock- /worker1      # 创建临时节点
create -s /lock/lock- /worker1      # 创建临时顺序节点（返回 /lock/lock-0000000001）
set /lock/lock-0000000001 v2 1      # CAS 写：期望 version=1
get -s /app/config                  # 查看数据与 Stat（含 version/cversion）
delete /lock/lock-0000000001 1      # CAS 删：期望 version=1
```
### 1.5 一句话速记
ZNode 树 + 少量内存数据 + Stat/版本号；临时节点表存活、顺序节点做排队、版本号做 CAS，单节点数据上限 1MB。

## 2. 会话机制与 Watcher 机制
### 2.1 核心原理
**会话**：客户端与集群建立 TCP 连接后协商 `sessionTimeout`（服务端会在 `2×tickTime` 与 `20×tickTime` 之间取值，`tickTime` 默认 2000ms），客户端以 `sessionTimeout/3` 的间隔发心跳（ping），服务端在超时时间内未收到心跳则认为会话失效，由 Leader 清理该会话的临时节点与 Watcher。会话状态：CONNECTING / CONNECTED / RECONNECTING / EXPIRED，一旦 EXPIRED 会话不可恢复（需重建整个协调状态）。**Watcher**：客户端在 `exists`/`getData`/`getChildren` 上注册的一次性回调，事件类型包括 `NodeCreated`、`NodeDeleted`、`NodeDataChanged`、`NodeChildrenChanged` 与连接状态的 `None` 事件；事件由服务端**异步推送**给客户端，客户端本地串行回调。
### 2.2 面试问答
**Q1：Watcher 为什么设计成一次性的？**
A：结论——为了简化语义、避免事件堆积与内存泄漏，并让客户端能"按需重新注册"。原因：若 Watcher 永久有效，服务端需要长期维护海量监听关系，且事件在客户端堆积可能造成重复处理与内存膨胀；一次性设计把控制权交回客户端——处理完事件后重新注册即可获得下一次通知。代价是**必须"先注册再读数据"**，否则两次操作之间可能丢事件。
**Q2：怎么避免"丢事件"？**
A：① 严格遵循"注册 watch → 读数据 → 判断是否需要再次注册"的顺序；② 判断条件要用**服务端状态判断**（如节点是否存在、version 是否变化），不能依赖事件本身携带的数据；③ 使用 Curator 的 `TreeCache`/`PathChildrenCache`（内部自动重新注册，还带本地缓存），避免手写 watch 的重复注册逻辑。
**Q3：连接断开或会话过期时 Watcher 会怎样？**
A：结论——**本地 Watcher 不会自动恢复**：断连期间服务端无法推送；会话过期后服务端直接清除该会话的所有 Watcher。客户端会先收到一个 `KeeperState.Expired`/`None` 事件（Curator 提供 `ConnectionState` 监听），业务必须在此基础上**重建 ZNode 与 Watcher**（这也是"网络抖动后配置不再更新"的根因）。另外会话未过期时的重连，ZK 客户端会**自动重注册**未触发的 Watcher（服务端会对比客户端发来的 watch 列表）。
**Q4：什么是羊群效应（Herd Effect），怎么优化？**
A：当大量客户端都对同一节点（如 `/lock` 或某个配置节点的全部子节点）注册 watch 时，任意一次变更会让**所有客户端同时被唤醒**，造成瞬时惊群与集中式重建（大量请求同时打到服务端）。优化：用**临时顺序节点 + 只监听前一个节点**（`getChildren` 只取一次并监听自己的前驱），使每次变更只唤醒一个客户端；或在业务层加随机抖动、退避重试。
**Q5：Watcher 事件会丢吗、会重复吗？**
A：不会丢（对已注册的 Watcher，服务端保证通知），但**可能重复/延迟**：客户端在收到事件前可能已经通过其他途径感知变化；且在断连重连场景下可能收到重复事件。因此业务处理必须**幂等**，并以"最终状态"为准而非事件次数。
**Q6：Session 超时应该设多少？**
A：结论——10~30 秒范围较常见（默认 `tickTime=2000ms`，常见配置 `sessionTimeout=30000`）。太小会因 GC 或网络抖动导致频繁会话过期（临时节点丢失、锁误释放）；太大则故障感知慢（挂掉的进程要等更久才被清理）。大规模集群中可统一约定，并在客户端加大于服务端最小值的超时。
### 2.3 高频追问与陷阱
- 陷阱：在 Watcher 回调里做耗时操作——回调在客户端单线程事件线程上执行，会阻塞后续事件处理。
- 陷阱：相信事件携带的数据——Watcher 只告诉你"发生了变化"，必须重新读取最新值。
- 追问：会话过期与连接断开有何区别？断开可重连且状态保留（会话未过期），过期则状态（临时节点、Watcher）全部失效，必须重建。
### 2.4 配置/命令示例
```java
// 一次性 watch：先注册再读，且必须再次注册
byte[] data = zk.getData(path, event -> { if (event.getType() != Event.EventType.None) { reRegister(path); } }, stat);
// Curator 持久化缓存（自动重注册）
TreeCache cache = TreeCache.newBuilder(client, "/app/config").build();
cache.getListenable().addListener((c, e) -> refreshConfig(c.getCurrentData(e.getPath()).getData()));
cache.start();
```
### 2.5 一句话速记
会话靠心跳（超时 10~30s，过期即清理临时节点与 Watcher）；Watcher 一次性、异步、不带数据，必须"先注册再读"并处理 Expired 后的重建；避免惊群就只监听前驱。

## 3. ZAB 协议与 Leader 选举
### 3.1 核心原理
ZAB（ZooKeeper Atomic Broadcast）是 ZK 的原子广播协议，分三个阶段：**发现（Discovery）**——选举出新的 Leader（也为各节点确定最新数据）；**同步（Synchronization）**——Leader 把自己的事务历史同步给 Follower，使多数派状态一致；**广播（Broadcast）**——进入正常工作状态，类似二阶段提交：Leader 为写请求分配 **zxid** 并发出 PROPOSAL，Follower 写入本地事务日志后返回 ACK，Leader 收到**多数派 ACK** 后发出 COMMIT，客户端才能看到结果。**zxid** 是 64 位：高 32 位为 **epoch**（Leader 任期，每选一次加一），低 32 位为**事务自增计数**，因此 zxid 全局单调递增，可用来判断数据新旧。**FastLeaderElection**：每台服务器投票给自己，投票内容为 `(myid, zxid)`；收到他人投票后按规则比较——**先比 zxid（大者胜），zxid 相同再比 myid（大者胜）**；某台服务器获得**多数票**即成为 Leader。崩溃恢复时，Leader 必须是多数派中数据最新的节点，从而保证已提交的事务不丢。
### 3.2 面试问答
**Q1：ZAB 和 Paxos/Raft 有什么区别？**
A：结论——ZAB 是专为**主备模式（单一 Leader 处理写）**设计的原子广播协议，与 Raft 思路相近（选举 + 日志复制 + 多数派提交），但 ZAB 强调"主备 + 顺序广播"并保证**崩溃恢复阶段能选出数据最新的 Leader**（通过 zxid 比较）。面试时说明"ZAB ≈ 类 Paxos/Raft 的多数派复制协议，关键差异在选举规则与恢复流程"即可。
**Q2：选举时的投票规则为什么是"先比 zxid 再比 myid"？**
A：为了让**数据最新的节点优先当选**，避免刚提交的事务因新 Leader 数据落后而丢失（若选错，必须回滚已提交事务，违背 ZAB 的可靠性保证）。`myid` 只在 zxid 相同时用于打破平局（保证选举一定收敛）。
**Q3：选举期间服务可用吗？**
A：**不可用**。集群进入 LOOKING 状态，客户端请求会被拒绝/挂起，直到选出 Leader 并完成同步。选举耗时通常在几百毫秒到数秒（取决于集群规模与网络），因此生产上要避免频繁 Leader 切换（GC 停顿、网络抖动都可能触发）。
**Q4：ZAB 保证哪些一致性？**
A：① 顺序一致性（客户端发起的更新按序应用）；② 原子性（要么全部成功要么全部失败）；③ 单一视图（任何客户端看到的是同一份数据视图）；④ 可靠性（一旦提交，结果被持久保留）；⑤ 实时性（客户端在读到新数据的一段时间内，后续读不会看到更旧的数据）。注意：**不保证跨客户端的强实时线性一致读**——默认读可能读到 Follower 的旧数据，需要 `sync()` 或读 Leader 才能强一致。
**Q5：写请求是二阶段提交吗？**
A：形式上接近：Leader 发 PROPOSAL → Follower 写日志并 ACK → 多数派 ACK 后 Leader 发 COMMIT 并应用。关键差别是"**只有 Leader 会发起提案**"（Follower 接到写请求会转发给 Leader），且只需要多数派 ACK 即可提交，无需全票。
### 3.3 高频追问与陷阱
- 陷阱：以为"读到的一定是最新数据"——默认读走本地内存，Follower 可能落后；需要强一致时应 `sync()` 后再读。
- 陷阱：把 zxid 当普通自增 ID——它是 epoch + counter，用于选举与数据新旧比较。
- 追问：为什么 Leader 切换会让 watch 全部失效？客户端会收到 `None`/断开事件，需要重新注册（Curator 会自动处理）。
### 3.4 配置/命令示例
```bash
# zoo.cfg 关键项
tickTime=2000
initLimit=10
syncLimit=5
server.1=10.0.0.1:2888:3888
server.2=10.0.0.2:2888:3888
server.3=10.0.0.3:2888:3888
# 2888 为 Follower 与 Leader 的数据同步端口，3888 为选举端口
```
### 3.5 一句话速记
ZAB = 发现（选举）→ 同步 → 广播（多数派 ACK 才提交）；zxid = epoch + 计数，选举"先比 zxid 后比 myid"，选举期间不可用。

## 4. 写请求处理流程与节点角色
### 4.1 核心原理
角色分四种状态：**Leader**（唯一处理写提案、负责广播与提交）、**Follower**（参与投票与写，处理读，转发写给 Leader）、**Observer**（与 Follower 类似但**不参与投票**，用于无损扩展读能力）、LOOKING（选举中）。**写流程**：客户端可连任意节点 → 若是 Follower，写请求被转发到 Leader → Leader 生成 zxid 并广播 PROPOSAL → 各 Follower 落事务日志并 ACK → Leader 收到多数派 ACK 后提交并通知 Follower COMMIT → 客户端收到响应。**读流程**：任何节点直接用本地内存数据返回（默认不经过 Leader）。因此 ZK 的**读吞吐可随节点数线性扩展，写吞吐受 Leader 与多数派 fsync 限制**。
### 4.2 面试问答
**Q1：为什么写请求必须经过 Leader？**
A：为了保证**全局顺序**：所有写都被 Leader 赋予单调递增的 zxid 并按序广播，从而让所有副本以相同顺序应用，实现顺序一致性与单一视图。如果允许任意节点直接写，就必须引入更复杂的并发冲突解决机制。
**Q2：Observer 有什么用？**
A：① 扩展**读**能力（注册中心客户端大多在读）；② 增加跨机房部署的读节点而不影响写延迟（Observer 不参与投票，跨机房的多数派写不会被拖慢）；③ 不影响集群可用性判定（投票成员数不变）。注意：Observer 不参与选举，挂了也不影响 quorum。
**Q3：为什么读可能读到旧数据？**
A：Follower 是异步接收 Leader 的 COMMIT 通知的，若客户端连接的 Follower 尚未应用最新事务，读到的就是旧值。需要强一致读时：① 调用 `sync()`（把该 Follower 与 Leader 同步）后再读；② 直接读 Leader（增加 Leader 压力）；③ 业务上容忍短暂不一致（绝大多数场景）。
**Q4：ZK 的写性能瓶颈在哪？**
A：① 所有写都必须经过 Leader（单点串行）；② 每个事务都要 fsync 事务日志（`zookeeper.forceSync` 可关闭但会牺牲持久性）；③ 多数派确认的 RTT（跨机房尤其明显）。所以 ZK 的写能力通常在万级 TPS 以下，**只用于协调数据，不能当消息队列或数据库用**。
**Q5：客户端连接地址该怎么配？**
A：配置**全部**节点地址（逗号分隔），客户端会自行挑选并故障切换；配合 Curator 的 `connectionStateErrorPolicy` 与重试策略。不要只配一个节点地址，那会形成单点。
### 4.3 高频追问与陷阱
- 陷阱：把高吞吐的元数据（如每次请求都写）放进 ZK，导致事务日志暴涨、集群抖动。
- 陷阱：以为加节点能提升写吞吐——写吞吐由 Leader 与 quorum 决定，加 Follower 反而增加 Leader 的广播开销。
- 追问：为什么 ZK 建议把事务日志与快照放在**不同磁盘**？避免顺序写（日志）与随机写（快照）互相干扰 IO。
### 4.4 配置/命令示例
```properties
dataDir=/data/zk/snapshot
dataLogDir=/data/zk/txnlog        # 与快照分离，最好独立磁盘
autopurge.snapRetainCount=5
autopurge.purgeInterval=24        # 每 24 小时清理一次，保留 5 份
maxClientCnxns=200
server.1=10.0.0.1:2888:3888
server.4=10.0.0.4:2888:3888:observer   # 观察者节点
```
### 4.5 一句话速记
写必须经 Leader 并多数派 ACK，读走本地内存所以可能读到旧值；Observer 不投票只扩读；ZK 写吞吐有限，只放协调数据。

## 5. 分布式锁与协调原语
### 5.1 核心原理
**排他锁实现要点**：① 在锁目录下创建**临时顺序节点** `<lock>/-lock-000000000N`；② `getChildren` 取全部子节点并排序，若自己的序号最小则获取锁；③ 否则**只监听自己前一个节点**的删除事件，被唤醒后再判断（避免羊群效应）；④ 释放即删除节点（或会话过期自动删除）。**共享锁（读写锁）**：把节点分为读、写两种前缀，写锁要等所有读写节点都释放，读锁只等更小的写节点。**优势**：临时节点天然解决"客户端崩溃后锁无法释放"；**代价**：性能与可靠性受 ZK 写路径限制（每次加解锁都产生写事务），且必须处理会话过期导致的"锁被误释放"。生产优先用 Curator 的 `InterProcessMutex` / `InterProcessReadWriteLock`，而非手写。
### 5.2 面试问答
**Q1：为什么用临时顺序节点而不是"创建临时节点失败即未获得锁"？**
A：后者会导致**惊群**（所有竞争者都监听同一节点，一次释放全部唤醒）且不公平（随机抢占）。顺序节点让每个竞争者只关心前驱，实现**公平排队**且每次只唤醒一个客户端。
**Q2：ZK 锁和 Redis 锁怎么选？**
A：结论——**强一致与可接受较低吞吐选 ZK**（CP，靠临时节点 + 会话保证不误释放），**极致性能且能容忍极小概率误判选 Redis**（AP + 过期时间，需 Redlock/看门狗与 fencing token 兜底）。注意两者都解决不了"锁持有者实际已长时间停止/网络分区导致两个客户端同时认为自己持锁"的极端情况，因此关键资源仍要加 **fencing token（递增序号校验）** 或幂等保护。参见 [03-分布式锁与分布式ID](../05-分布式与架构/03-分布式锁与分布式ID.md)。
**Q3：会话过期导致锁被释放怎么办？**
A：会话过期是不可恢复的"疑似长时间失联"，任何基于 ZK 的方案都会删除临时节点。防御：① 使用**同一客户端复用 + Curator 的自动重建**（重新加锁前先确认业务状态）；② 用 `InterProcessMutex` 的 `acquire` 返回结果而非假设一定成功；③ 对资源操作加**幂等 + 版本校验**（fencing token）；④ 调大 `sessionTimeout` 降低抖动误判概率。
**Q4：ZK 还能实现哪些协调原语？**
A：分布式锁、**Leader 选举**（LeaderLatch/LeaderSelector）、**分布式队列**（顺序节点排队）、**分布式屏障（Barrier）**（所有参与者到齐才继续）、**成员管理/集群管理**（临时节点表达存活）、**配置管理**（数据节点 + Watch）、**命名服务**（路径即名字）、**分布式计数器/信号量**（Curator 的 DistributedAtomicLong、InterProcessSemaphore）。
**Q5：分布式队列用 ZK 还是 MQ？**
A：ZK 的顺序节点可以实现简单队列，但**每次出队/入队都是写事务**，吞吐远低于专业 MQ，且没有消费位点、重试、死信等机制。结论——协调类队列（小规模任务分发、屏障）用 ZK，业务消息队列用 Kafka/RocketMQ/RabbitMQ。
### 5.3 高频追问与陷阱
- 陷阱：手写 Watcher 时忘记"监听到事件后要重新判断并可能重新监听"，导致持锁逻辑失效。
- 陷阱：把"获取到锁"当作绝对安全——ZK 只能保证**在会话有效期内**没有别人持锁。
- 追问：为什么不建议用 ZK 做"秒杀扣库存"？写吞吐不够且每次都要多数派确认，应使用 Redis/DB 原子操作。
### 5.4 配置/命令示例
```java
InterProcessMutex lock = new InterProcessMutex(client, "/lock/order");
if (lock.acquire(3, TimeUnit.SECONDS)) {
    try { doWithFencingToken(); }          // 业务仍应幂等 + 校验 fencing token
    finally { lock.release(); }
}
// Leader 选举：LeaderLatch（选出后不再参选）与 LeaderSelector（自动重新参选）
```
### 5.5 一句话速记
ZK 锁 = 临时顺序节点 + 只监听前驱（防惊群）+ 会话超时自动释放；强一致选 ZK、极致性能选 Redis，关键资源都要幂等与 fencing token。

## 6. 典型应用场景
### 6.1 核心原理
六大场景：**配置管理**（配置写入 ZNode，客户端 Watch 变更，实现推拉结合的动态刷新）、**服务注册与发现**（临时节点表示服务实例存活，路径如 `/dubbo/com.foo.UserService/providers/...`，消费者 Watch 子节点获取实例列表并本地负载均衡）、**Master/Leader 选举**（临时顺序节点最小者当选）、**命名服务**（路径即全局唯一名字）、**集群管理与成员感知**（临时节点集合即存活成员，配合 Watch 感知上下线）、**分布式锁与协调原语**（见第 5 节）。Dubbo（ZK 注册中心）、Kafka（2.x 的元数据与 Controller 选举）、HBase（RegionServer 与 Master 选举）、Hadoop HA 都依赖 ZK，这是"为什么 JD 要求会 ZK"的原因。
### 6.2 面试问答
**Q1：用 ZK 做注册中心有什么问题？**
A：① ZK 是 **CP**，Leader 选举或失去多数派期间注册中心不可用，会导致服务发现的读写失败（虽然客户端可缓存实例列表，但实例变更会丢失）；② 大规模服务下**写压力大**（每个实例上下线都是写事务，还伴随大量 Watch 通知）；③ 网络分区时少数派节点上的服务会被误判下线（临时节点被删）。因此 Dubbo 后来也支持 Nacos（AP 模式）作为注册中心。
**Q2：ZK 做配置管理，配置变更怎么保证实时且不丢？**
A：① 客户端启动时拉全量并注册 Watch；② 变更时 Watch 触发，**重新拉取最新数据**（事件不带数据）；③ 处理 `Expired`/重连后重新拉取全量并重建 Watch（Curator TreeCache 已封装）；④ 本地缓存配置作为服务端不可用时的兜底；⑤ 变更加版本号，避免乱序覆盖。
**Q3：Leader 选举为什么不用"抢占式"实现？**
A：抢占式（谁先创建谁当 Leader，挂了再抢）会导致频繁切换与短暂的多 Leader 观感；用临时顺序节点可让"先来的先当"，并让后加入者只监听前驱，实现**有序、无惊群**的接替。
**Q4：ZK 上放多少数据、多少节点算合理？**
A：经验上**全量数据控制在几十 MB 到百 MB 级**、单 ZNode 数据小于 1KB（上限 1MB）、总 ZNode 数量数万到数十万级；写入 TPS 控制在千级以内（要留余量应对突发与选举）。超过这些量级应考虑改用 etcd/Nacos/数据库。
**Q5：Kafka 为什么去掉了 ZK？**
A：ZK 成为元数据与分区规模瓶颈（分区越多，元数据与 Watch 压力越大）、Controller 故障切换耗时长（分钟级）、两套系统运维成本高。Kafka 用 **KRaft（Raft 元数据 quorum）** 自管理元数据后，切换降到秒级且能支撑百万分区（3.3 生产可用、4.0 移除 ZK）。这题能体现"知道 ZK 的能力边界"。
### 6.3 高频追问与陷阱
- 陷阱：把服务注册的实例列表直接存成一个 ZNode 的大 JSON（万级实例会导致写放大与通知风暴），应按实例各占一个子节点。
- 陷阱：注册中心场景不缓存实例列表，ZK 一抖动业务立即全挂。
- 追问：为什么注册中心通常"临时节点 + 客户端 Watch + 本地缓存 + 定时全量刷新"四件套？因为任何单一机制都无法同时覆盖实时性、一致性与可用性。
### 6.4 配置/命令示例
```bash
# Dubbo 风格的服务注册结构
/dubbo/com.foo.UserService/providers/dubbo://10.0.0.11:20880/...   # 临时节点
/dubbo/com.foo.UserService/consumers/...
/dubbo/com.foo.UserService/configurators/...
ls /dubbo/com.foo.UserService/providers     # 客户端以此获取实例列表
```
### 6.5 一句话速记
配置、注册、选主、命名、集群管理、锁——六个场景的共同点是"数据小、读多写少、需要强一致与通知"，这正是 ZK 的定位。

## 7. ZK 与 Eureka/Nacos/etcd 对比
### 7.1 核心原理
注册中心的核心取舍是 **CP 还是 AP**。**ZK**：CP，多数派不可用时拒绝服务，数据强一致但牺牲可用性；**Eureka**：AP，节点对等、客户端本地缓存 + 定时拉取，通过**自我保护机制**（心跳续约比例骤降时停止剔除实例）保证分区期间仍可读写（读到旧数据）；**Nacos**：同时支持 **AP（Distro 协议，临时实例/服务发现）** 与 **CP（Raft，持久实例/配置）** 两种模式，可按场景选择；**etcd**：CP，基于 Raft，提供 gRPC、Watch 流、租约（Lease），是 Kubernetes 的元数据存储。

| 维度 | ZooKeeper | Eureka | Nacos | etcd |
| --- | --- | --- | --- | --- |
| 一致性 | CP（ZAB） | AP | AP + CP 双模式 | CP（Raft） |
| 健康检查 | 会话心跳（临时节点） | 客户端心跳 + 自我保护 | 心跳/主动探测（临时与持久实例） | Lease 租约 |
| 变更通知 | 一次性 Watcher | 客户端定时拉取（30s） | 长轮询（UDP 推送可选） | Watch 流（gRPC，长连接） |
| 数据规模/写能力 | 小数据、写能力有限 | 内存注册表，写能力好 | 较好 | 中等偏上，支持较大规模 |
| 典型用户 | Dubbo、Kafka 2.x、HBase | Spring Cloud Netflix 早期默认 | Spring Cloud Alibaba、Dubbo 3 | Kubernetes、CoreOS |
| 主要短板 | 分区/选举期不可用；写放大 | 一致性弱、已停止新特性演进 | 组件较重、生态偏阿里系 | 需自己实现服务发现的业务语义 |
### 7.2 面试问答
**Q1：注册中心该选 CP 还是 AP？**
A：结论——**注册中心更倾向 AP**：服务发现最怕"注册中心不可用导致全部服务无法通信"，宁可短时间拿到稍旧的实例列表（客户端还有本地缓存与重试），也不愿完全不可用。因此 Eureka/Nacos(AP) 在微服务里更常见；而配置管理、选主等场景更看重一致性，ZK/etcd 更合适。这也是"CAP 不同场景不同取舍"的标准答法。
**Q2：Eureka 的自我保护机制是什么？**
A：当最近一分钟内续约成功的实例比例低于阈值（默认 85%）时，Eureka 认为"可能是自己网络问题"而非实例真的挂了，于是**停止剔除过期实例**（保护注册表不被误删）。代价是可能返回已下线的实例（客户端需容忍失败并重试其他实例）。
**Q3：Nacos 的 AP 与 CP 怎么选？**
A：服务发现用 **AP（Distro）**（临时实例，客户端心跳，保证可用性）；需要强一致的元数据/配置用 **CP（Raft）**（持久实例）。Nacos 允许同一集群同时提供两种能力，切换方式是把实例注册为临时或持久类型。
**Q4：ZK 与 etcd 怎么选？**
A：① 已在用 Dubbo/Kafka/HBase 等 ZK 生态 → 继续用 ZK；② Kubernetes/云原生栈、需要 Watch 流与 gRPC、需要更好的可观测与 TLS → etcd；③ 两者都是 CP，都适合小数据协调，选型更多取决于生态与团队熟悉度。
**Q5：能不能不用注册中心？**
A：可以——K8s 场景下用 Service/DNS + Ingress 做服务发现，或客户端直连配置的实例列表（静态配置）。但一旦实例数量与变更频繁，仍需要注册中心或服务网格（如 Istio 用控制面下发 Envoy 配置，本质上也是"注册 + 下发"）。
### 7.3 高频追问与陷阱
- 陷阱：把"ZK 是 CP"简单理解成"ZK 一定更可靠"——分区期间它会拒绝服务，注册中心场景可能全站不可用。
- 陷阱：忽略客户端缓存与重试，导致注册中心抖动等于业务全挂。
- 追问：为什么新项目很少再选 Eureka？Netflix 已停止其新特性演进（2.x 未开源），Spring Cloud 生态转向 Nacos/Consul/K8s。
### 7.4 配置/命令示例
```yaml
# 选型速查（Spring Cloud）
spring:
  cloud:
    zookeeper: { connect-string: 10.0.0.1:2181,10.0.0.2:2181 }   # CP，需强一致时
    nacos:     { discovery: { server-addr: 10.0.0.5:8848 } }      # AP 为主，配置管理也支持
```
### 7.5 一句话速记
注册中心偏 AP（可用性优先，配合本地缓存与重试），协调与选主偏 CP；ZK 在 Dubbo/Kafka 生态，Nacos 走 AP+CP 双模，etcd 是 K8s 标准件。

## 8. 脑裂与 quorum、集群规模
### 8.1 核心原理
ZK 通过 **quorum（多数派）** 机制规避脑裂：只有能联系到多数派节点的分区才能选出/保留 Leader 并对外服务，少数派分区无法获得多数票，会一直处于 LOOKING 状态并**拒绝服务**（客户端切到其他节点或不可用）。因此 ZK 不会出现"两个 Leader 同时接受写"的经典脑裂；它的代价是**可用性下降**（这正是 CP 的体现）。集群规模必须是**奇数**：quorum = ⌊n/2⌋+1，3 节点容忍 1 台故障、5 节点容忍 2 台、7 节点容忍 3 台；偶数节点（如 4、6）不增加容错能力（4 节点同样只容忍 1 台，quorum 为 3），却增加广播与运维成本，且得票相同时更易反复选举。

| 集群规模 | quorum（多数派） | 可容忍故障 | 写入延迟 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 最低 | 无容错，禁止生产使用 |
| 3 | 2 | 1 | 低 | 生产最小规模，最常用 |
| 5 | 3 | 2 | 中 | 大流量/关键业务常用 |
| 7 | 4 | 3 | 较高 | 收益递减，一般不超过 7 |
### 8.2 面试问答
**Q1：ZK 会出现脑裂吗？**
A：结论——**不会出现"两个 Leader 同时提交写"**，因为新 Leader 必须获得**严格多数票**，而多数派之间必然相交，旧 Leader 无法在没有多数派的情况下提交事务。但"客户端读到旧数据"与"少数派分区不可用"是正常现象，运维上要监控多数派是否完整。
**Q2：为什么推荐奇数节点？**
A：① 容错能力相同的前提下更省资源（3 与 4 都是容忍 1 台，4 台还多一份开销）；② 避免票数完全相同时反复选举（偶数节点更容易出现平票）；③ quorum 计算更直观。
**Q3：ZK 集群挂了一半会怎样？**
A：分情况：① 3 节点挂 1 台（剩 2 = 多数派）→ 正常服务，可能触发 Leader 切换并短暂不可用；② 3 节点挂 2 台（失去多数派）→ 集群**整体不可写、不可用**，剩余节点处于 LOOKING，客户端请求失败；③ 若是 5 节点挂 2 台 → 仍可服务，挂 3 台则不可用。**关键结论**：ZK 的可用性取决于"多数派是否存活"，因此 3 节点集群必须把 3 台部署在不同机架/可用区（避免同一故障域同时挂两台）。
**Q4：跨机房部署 ZK 要注意什么？**
A：多数派写延迟受机房 RTT 影响（跨城 RTT 几毫秒到几十毫秒会直接抬高写延迟）；常见做法是"**两个机房放投票节点 + 第三个机房放 Observer**"或"5 节点 3+2 分布，保证可用区故障时仍有 3 台存活"。切忌把多数派放在同一机房之外的少数派里。
**Q5：扩容缩容怎么做？**
A：3.5+ 支持**动态重配置**（`reconfig` 命令或 API，需 `dynamicConfigFile` 配置），可以运行中增删节点；更保守的做法是**滚动重启 + 逐台修改 zoo.cfg 与 myid**（一次只动一台，保证多数派在线）。缩容时切勿一次下线多台以免失去多数派；新增节点会自动从 Leader 同步快照与事务日志。
### 8.3 高频追问与陷阱
- 陷阱：3 节点集群与主库部署在同一台物理机或同一机架，一次故障挂掉 2 台直接全站不可用。
- 陷阱：为扩容读能力而盲目增加 Follower——投票成员越多写延迟越高，读扩容应优先用 Observer。
- 追问：客户端在分区的少数派侧会怎样？连接失败或收到会话过期事件，随后切换到多数派节点（需配置全部节点地址）。
### 8.4 配置/命令示例
```bash
echo srvr | nc 10.0.0.1 2181            # 查看角色（Mode: leader/follower）
echo mntr | nc 10.0.0.1 2181            # 关键指标（znode 数、延迟、连接数）
# 动态重配置（3.5+，需开启 dynamicConfigFile）
reconfig -add server.4=10.0.0.4:2888:3888:participant
reconfig -remove 4
```
### 8.5 一句话速记
quorum 决定可用性：3 挂 1 可用、挂 2 全停；集群必须奇数、跨故障域部署；读扩容用 Observer，写能力加节点无用。

## 9. 运维实践与 Curator
### 9.1 核心原理
**四字命令**（`echo <cmd> | nc host 2181`）：`ruok`（存活）、`stat`/`srvr`（状态与角色）、`mntr`（指标：znode 数、watch 数、延迟、连接数、快照与日志文件数）、`conf`（配置）、`cons`（连接详情）、`dump`（会话与临时节点）、`envi`（环境）、`wchs`/`wchc`/`wchp`（watch 统计与明细）、`dirs`（3.5.1+ 数据目录大小）、`isro`（是否只读）。**默认只放行 `srvr`**（`4lw.commands.whitelist`），其他需显式配置白名单。**数据文件**：事务日志（`dataLogDir`，`log.*`）必须与快照（`dataDir`，`snapshot.*`）分离磁盘；清理靠 `autopurge.snapRetainCount`（保留份数）与 `autopurge.purgeInterval`（清理周期），未配置时需要人工清理。**Curator** 是 Netflix 开源的 ZK 客户端封装：内置重试策略（`ExponentialBackoffRetry`、`RetryNTimes`）、连接状态监听、以及 Recipes（锁、选举、缓存、计数器、信号量、屏障），大幅降低手写 Watcher 的出错概率。
### 9.2 面试问答
**Q1：ZK 常见性能问题有哪些？**
A：① **watch 数量过多**（用 `wchs`/`wchc` 定位）——常见于大量客户端监听同一大节点；② **事务日志与快照同盘**导致 IO 争抢；③ **会话过多/超时过小**导致频繁重连与临时节点抖动；④ **ZNode 数量过大**（几十万以上）导致快照与恢复变慢；⑤ **GC 停顿**引发会话超时与 Leader 切换（堆不宜过大，4~8G 常见）；⑥ **fsync 开销**（`forceSync` 与磁盘性能）。治理手段：只监听前驱、Observer 扩读、分离磁盘、用 SSD、合理设置会话超时与堆。
**Q2：数据目录能直接删吗？**
A：不能直接删正在使用的文件（会导致节点数据缺失甚至无法恢复）。正确做法：① 配置 `autopurge.snapRetainCount` + `autopurge.purgeInterval` 自动清理（保留最近若干份快照与对应日志）；② 手工清理时只删除**已确认落后于最新有效快照的旧文件**；③ 清理前先备份并在一台节点上验证。3.5+ 可用 `zkTxnLogToolkit`/`SnapshotFormatter` 分析文件。
**Q3：怎么判断集群健康？**
A：核心指标：`Mode`（是否有唯一 Leader）、**可用节点数是否 ≥ quorum**、`AvgLatency`/`MaxLatency`、`OutstandingRequests`（积压请求）、连接数与 watch 数、事务日志与快照文件数量与磁盘水位、`ruok`/`isro` 返回是否正常。业务侧还要监控"客户端会话过期率、临时节点抖动、注册实例数突变"。
**Q4：Curator 的重试策略怎么选？**
A：结论——用 `ExponentialBackoffRetry(baseSleepTime, maxRetries)`（如 `new ExponentialBackoffRetry(1000, 3)`）；避免 `RetryForever`（在长时间故障时会造成请求堆积）。同时注册 `ConnectionStateListener`，在 `SUSPENDED`/`LOST` 时暂停业务写入，在 `RECONNECTED` 时重建缓存与锁；会话 `Expired` 时必须重建所有临时状态。
**Q5：LeaderLatch 和 LeaderSelector 的区别？**
A：`LeaderLatch`：一旦获得领导权就持有，直到 `close()` 或会话丢失，**不能自动再次参与竞选**（适合"长期唯一的调度者"）；`LeaderSelector`：通过回调在获得领导权后执行任务，任务结束自动释放并**重新参与竞选**（适合"轮流执行任务"场景，如定时任务分片）。
**Q6：升级/迁移 ZK 集群要注意什么？**
A：① 版本升级通常支持滚动升级（先升 Follower 再升 Leader），但要查版本兼容说明（如 3.4 → 3.5 的 `4lw` 白名单变化、`dynamicConfigFile` 引入）；② 客户端版本要与服务端兼容（3.4 客户端连 3.5 服务端通常可行，反向不一定）；③ 迁移时先搭新集群、双写/切流验证、再下线旧集群，并把客户端地址改为全部节点。
### 9.3 高频追问与陷阱
- 陷阱：`autopurge.purgeInterval` 默认 0（不自动清理），长期运行导致磁盘被快照与日志打满。
- 陷阱：用 `RetryForever` + 业务无超时控制，ZK 故障时把应用线程池拖死（要配合熔断与超时）。
- 追问：为什么 ZK 部署建议 JVM 堆不要太大且禁用 swap？堆过大会拉长 GC 停顿，会话超时被误判；swap 会让延迟不可控。

## 10. 高频问答收口
### 10.1 核心原理
ZK 类问题最终都收敛到"它是什么、为什么这样设计、能撑多大、坏了怎么办"四个方向，答题时先给结论，再给机制与边界。
### 10.2 面试问答
**Q1：一句话说 ZK 能做什么？**
A：它是一个**高可用的小数据强一致存储 + 通知机制**，用于分布式协调：配置管理、服务注册发现、Leader 选举、分布式锁、命名服务、集群成员管理。
**Q2：为什么说 ZK 是 CP 的？**
A：写必须由 Leader 按 zxid 顺序广播并获得**多数派 ACK** 才提交，少数派分区无法选出 Leader 并**拒绝服务**，因此优先保证一致性（数据不分裂、不丢已提交事务），代价是选举或失去多数派期间不可用。
**Q3：Watcher 为什么是一次性的？**
A：简化服务端监听管理、避免事件堆积与内存泄漏，并把"是否继续监听"的控制权交给客户端；代价是必须"先注册再读"、处理完事件再重新注册，且会话过期后必须重建（Curator 缓存组件已封装）。
**Q4：如何避免惊群？**
A：不要监听父节点的全部子节点或同一节点，而是用**临时顺序节点 + 只监听前驱**；或在客户端加随机退避与合并刷新（把多次变更合并成一次全量拉取）。
**Q5：ZK 集群挂了一半会怎样？**
A：看是否还保有多数派：3 节点挂 1 台仍可用（可能有一次 Leader 切换的短暂不可用），挂 2 台则整体不可用（不可写、不可读最新数据），客户端需切换到存活节点或降级到本地缓存。因此 3 节点必须跨故障域部署。
**Q6：ZK 和 Redis 的分布式锁怎么选？**
A：ZK 锁靠临时节点与会话保证强一致、不会超时误释放，但每次加解锁都是写事务（吞吐低）；Redis 锁性能高但依赖过期时间，存在误释放与时钟偏差风险。结论——对一致性要求高、并发不高选 ZK；高并发且可接受极小概率风险选 Redis，并统一加幂等与 fencing token。
**Q7：上线一个新服务，注册中心该选哪个？**
A：若在 Spring Cloud Alibaba 体系选 Nacos（AP + 配置管理 + 控制台），在 Dubbo 体系选 ZK（生态成熟、CP 强一致），K8s 原生环境直接用 Service/DNS 或 etcd/Consul；无论选哪个，客户端都必须有**本地缓存 + 重试 + 超时**。
### 10.3 高频追问与陷阱
- 陷阱：回答"ZK 能保证强一致"却不区分默认读可能读到旧值（需 `sync()`）。
- 陷阱：把 ZK 当通用存储/队列用，忽略写吞吐与 1MB 上限的硬约束。
- 追问：为什么大厂面试喜欢问 ZK？因为它同时考察 CAP 取舍、多数派协议、Watcher 异步语义与分布式锁的正确实现。
### 10.4 配置/命令示例
```bash
# 排查顺序：是否有多数派与 Leader → 延迟与积压 → watch 与连接数 → 磁盘与日志
echo ruok | nc 10.0.0.1 2181        # 存活
echo srvr | nc 10.0.0.1 2181        # Mode 与统计
echo mntr | nc 10.0.0.1 2181 | head -20
```
### 10.5 一句话速记
ZK 是协调组件而非存储：小数据、强一致、读多写少；Watcher 一次性要重注册，锁要防惊群，集群靠 quorum 保命，只放协调数据不放业务数据。

## 自测题（含答案要点）
1. **ZNode 有哪几类节点？** 持久、临时、顺序、持久顺序、临时顺序，3.5+ 增加容器节点与 TTL 节点。
2. **临时节点的生命周期？** 绑定会话，会话超时或客户端断开超时后被服务端删除；不能有子节点。
5. **会话超时怎么协商？** 客户端请求，服务端在 2×tickTime 与 20×tickTime 之间取值；心跳间隔约为超时的 1/3。
6. **会话过期的后果？** 临时节点删除、Watcher 清空、状态不可恢复，客户端必须重建逻辑。
8. **Watcher 为什么一次性？** 降低服务端监听维护成本、避免事件堆积与内存泄漏，控制权交给客户端重新注册。
9. **羊群效应怎么解决？** 临时顺序节点 + 只监听前驱，让每次变更只唤醒一个客户端。
10. **ZAB 的三个阶段？** 发现（选举）、同步（对齐历史）、广播（多数派 ACK 后提交）。
11. **zxid 的结构？** 高 32 位 epoch（Leader 任期）+ 低 32 位事务计数，全局单调递增。
12. **选举投票规则？** 先比 zxid（大者优先），相同再比 myid（大者胜），需多数票。
13. **选举期间可用吗？** 不可用，集群处于 LOOKING 状态直到选出 Leader 并完成同步。
14. **写请求流程？** 客户端 →（Follower 转发）Leader 生成 zxid 广播 PROPOSAL → 多数派 ACK → COMMIT → 返回。
15. **为什么读可能读到旧数据？** Follower 异步应用 COMMIT；强一致需 `sync()` 或读 Leader。
16. **Observer 与 Follower 的区别？** Observer 不参与投票与 quorum 计算，只扩展读能力与跨机房部署。
17. **ZK 锁的实现要点？** 临时顺序节点 + 判断是否最小 + 只监听前驱 + 会话到期自动释放。
18. **ZK 锁的局限？** 写吞吐低、会话过期会丢锁；关键资源要加幂等与 fencing token。
19. **注册中心为什么倾向 AP？** 可用性优先，客户端缓存与重试可容忍短暂旧数据，避免协调服务不可用拖垮全站。
20. **Eureka 自我保护机制？** 续约成功率低于阈值（默认 85%）时停止剔除实例，防止误删。
22. **3/5/7 节点的容错能力？** 3 容忍 1、5 容忍 2、7 容忍 3，quorum 为 ⌊n/2⌋+1。
23. **ZK 会不会脑裂？** 不会出现双 Leader 提交写（多数派相交）；代价是少数派分区拒绝服务。
24. **常用四字命令？** ruok、srvr/stat、mntr、conf、cons、wchs/wchc、dump、isro、dirs。

## 背诵卡片
1. ZK 是分布式协调服务：小数据、强一致、读多写少、带通知。
2. ZNode 树形命名空间，路径即全局名字。
3. 单 ZNode 数据默认上限 1MB，业务应远小于此。
4. 节点类型：持久、临时、顺序、持久顺序、临时顺序，3.5+ 有容器与 TTL 节点。
5. 临时节点绑定会话，会话超时自动删除，且不能有子节点。
6. Stat 中 version/cversion/aversion 分别管数据、子节点、ACL。
7. version 用于 CAS：setData/delete 带版本，不匹配抛 BadVersionException。
8. 数据全量常驻内存，靠事务日志 + 快照持久化。
9. 会话超时在 2×tickTime 与 20×tickTime 之间，常见 10~30s。
10. 心跳间隔约为会话超时的 1/3。
11. 会话过期 = 临时节点 + Watcher 全部失效，必须重建。
12. Watcher 一次性、异步、不带数据，必须"先注册再读"。
13. Watcher 事件类型：Created/Deleted/DataChanged/ChildrenChanged/None。
14. 会话过期后本地 Watcher 不会恢复，需要重建 ZNode 与监听。
15. 惊群 = 大量客户端同时被唤醒，用顺序节点 + 只监听前驱解决。
16. ZAB 三阶段：发现（选举）、同步、广播。
17. zxid = epoch（高 32 位）+ 事务计数（低 32 位），全局单调递增。
18. 选举规则：先比 zxid，再比 myid，需多数票。
19. Leader 必须是多数派中数据最新的节点，保证已提交事务不丢。
20. 写必须经 Leader，多数派 ACK 后才提交（类 2PC 的原子广播）。
21. 读走本地内存，可能读到旧数据；强一致要 sync() 或读 Leader。
22. 写吞吐受 Leader 与多数派 fsync 限制，量级在万级 TPS 以内。
23. Observer 不投票，用于扩展读与跨机房部署。
24. ZK 保证顺序一致性、原子性、单一视图、可靠性、实时性。
25. 分布式锁：临时顺序节点 + 只监听前驱 + 会话超时自动释放。
26. ZK 锁强一致但吞吐低，Redis 锁性能高但需幂等与 fencing token。
27. Leader 选举用 LeaderLatch（不重选）或 LeaderSelector（自动重选）。
28. 典型场景：配置、注册发现、选主、命名、集群管理、锁。
29. Dubbo/Kafka 2.x/HBase 都用 ZK；Kafka 3.3+ 用 KRaft 取代 ZK。
30. quorum = ⌊n/2⌋+1：3 容忍 1、5 容忍 2、7 容忍 3。
31. 集群必须奇数，且跨机架/可用区部署避免同时失去多数派。
32. ZK 不会双 Leader 提交（多数派相交），少数派分区直接拒绝服务。
33. 四字命令：ruok、srvr/stat、mntr、conf、cons、wchs、dump、isro、dirs。
34. 默认只放行 srvr，其他四字命令需要配置白名单。
35. 事务日志与快照要分盘，autopurge 默认不清理（purgeInterval=0）。
36. 核心监控指标：Mode、可用节点数、延迟、OutstandingRequests、watch 数、连接数、磁盘。
37. Curator 提供重试策略、连接状态监听与锁/选举/缓存 Recipes。
38. 客户端必须配置全部节点地址，并带本地缓存与超时熔断。
39. ZK 与 etcd 都是 CP；Nacos 支持 AP + CP 双模式；Eureka 是 AP。
40. ZK 只放协调数据，不放业务数据；写频繁的场景应改用 Nacos/DB/MQ。
