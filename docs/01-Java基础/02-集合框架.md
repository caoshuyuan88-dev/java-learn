## 1. 集合接口与选型基础

### 1.1 四类核心接口

| 接口 | 主要语义 | 是否允许重复 | 常见实现 |
| --- | --- | --- | --- |
| `List` | 有序、可按索引访问 | 允许 | `ArrayList`、`LinkedList`、`CopyOnWriteArrayList` |
| `Set` | 元素不重复 | 不允许 | `HashSet`、`LinkedHashSet`、`TreeSet` |
| `Map` | key-value 映射，key 不重复 | value 可重复 | `HashMap`、`LinkedHashMap`、`TreeMap`、`ConcurrentHashMap` |
| `Queue`/`Deque` | 队列、双端队列或优先级队列 | 通常允许 | `ArrayDeque`、`PriorityQueue`、`BlockingQueue` |

`Map` 不继承 `Collection`。`Collection` 表示元素集合，`Map` 表示键值映射，两者的遍历入口也不同。

常见顺序语义：

- `HashMap`、`HashSet`：不保证迭代顺序。
- `LinkedHashMap`、`LinkedHashSet`：维护插入顺序；`LinkedHashMap` 也可以维护访问顺序。
- `TreeMap`、`TreeSet`：按自然顺序或 `Comparator` 排序。
- “当前看起来有序”不等于“API 承诺有序”，不要依赖 `HashMap` 的迭代顺序。

### 1.2 `Comparable` 与 `Comparator`

| 维度 | `Comparable<T>` | `Comparator<T>` |
| --- | --- | --- |
| 定义位置 | 类型自身 | 类型外部 |
| 方法 | `compareTo` | `compare` |
| 排序策略 | 通常只有一个自然顺序 | 可以有多种业务排序 |
| 典型场景 | `String`、`Integer` | 按用户年龄、时间、优先级排序 |

`TreeMap`/`TreeSet` 用比较结果判断两个 key 是否相同：`compareTo` 或 `compare` 返回 `0` 就视为同一个 key，不是再调用 `equals`。因此比较器应尽量与 `equals` 保持一致，否则会出现 `HashSet` 能同时放入两个对象、`TreeSet` 却只保留一个的差异。

### 1.3 集合线程安全的基本边界

- `ArrayList`、`HashMap` 等普通集合没有并发安全保证。
- `Collections.synchronizedList/map` 是“每个方法一把锁”，复合操作和迭代仍需外部同步。
- `CopyOnWriteArrayList` 适合读多写极少，不是通用的并发 List。
- `ConcurrentHashMap` 适合并发 Map，但“单个方法线程安全”不代表任意业务流程天然原子。

例如，下面的“先判断再新增”不是一个原子操作：

```java
if (!map.containsKey(key)) {
    map.put(key, value);
}
```

需要原子语义时使用 `putIfAbsent`、`computeIfAbsent`、`compute`、`merge` 或 `replace` 等方法。

### 1.4 基础面试问答

**Q1：`Collection` 与 `Collections` 有什么区别？**<br>
**A：** `Collection` 是集合根接口；`Collections` 是提供排序、包装、空集合等静态方法的工具类。

**Q2：`Map` 为什么不属于 `Collection`？**<br>
**A：** `Collection` 的基本单位是单个元素，`Map` 的基本单位是 key-value 映射；`Map` 通过 `keySet`、`values`、`entrySet` 提供集合视图。

**Q3：为什么不能只凭 `HashMap` 当前输出顺序判断它有序？**<br>
**A：** 迭代顺序是哈希分布、容量、扩容和 JDK 实现共同产生的结果，不属于 `HashMap` 的契约，版本或数据变化都可能改变它。

## 2. ArrayList：数组、扩容与 fail-fast（重点）

### 2.1 数据结构与核心特征

`ArrayList` 的核心字段可以抽象为：

```java
transient Object[] elementData;
private int size;
```

它保存的是**对象引用数组**，不是把对象内容内嵌到数组中。因此：

- `get(index)` 平均为 O(1)；
- 尾部 `add` 均摊 O(1)；
- 中间插入或删除需要移动后续引用，通常为 O(n)；
- 扩容只复制引用，不复制引用指向的对象，是浅拷贝意义上的复制。

`ArrayList` 没有容量和大小的混淆：

- `size()` 是当前元素个数；
- capacity 是底层数组长度；
- `new ArrayList<>(1000)` 是预留容量，不会放入 1000 个元素。

### 2.2 初始化和扩容

现代 JDK 中，默认构造的 `ArrayList` 通常采用懒初始化：构造时不立即分配默认数组，第一次添加元素时才分配默认容量（JDK 8 及常见实现为 10）。显式指定容量则可以减少扩容和数组复制：

```java
List<Order> orders = new ArrayList<>(expectedCount);
```

典型扩容逻辑可概括为：

```java
int oldCapacity = elementData.length;
int newCapacity = oldCapacity + (oldCapacity >> 1); // 约 1.5 倍
if (newCapacity < minCapacity) {
    newCapacity = minCapacity;
}
elementData = Arrays.copyOf(elementData, newCapacity);
```

扩容步骤：

1. 计算本次操作所需的最小容量；
2. 如果现有数组放不下，计算新容量；
3. 分配更大的新数组；
4. 复制旧数组中的引用；
5. 让 `elementData` 指向新数组。

为什么不每次只增加一个位置？因为这样会反复分配和复制，连续添加 n 个元素的总复制成本会接近 O(n²)。几何扩容使连续添加的总复制成本保持在 O(n)，所以尾部添加是均摊 O(1)，但单次扩容仍是 O(n)。

`ensureCapacity` 适合已知规模的批量添加，`trimToSize` 可以收缩冗余容量，但频繁调用会抵消扩容优化，不应当作为常规操作。

### 2.3 插入、删除和 `remove` 陷阱

```java
List<Integer> numbers = new ArrayList<>(List.of(10, 20, 30));

numbers.remove(1);                    // 删除下标 1 的元素，即 20
numbers.remove(Integer.valueOf(30));  // 删除值 30
```

原因是 `List<Integer>` 同时存在 `remove(int index)` 和 `remove(Object o)`。整数字面量优先匹配基本类型参数，因此 `remove(1)` 是按下标删除。

删除中间元素后，后续引用会整体左移；删除大量元素时，批量 `removeIf` 往往比循环逐个删除更合适：

```java
numbers.removeIf(value -> value < 20);
```

已知要按索引删除多个元素时，可以倒序删除，避免前面删除导致后续索引变化：

```java
for (int i = list.size() - 1; i >= 0; i--) {
    if (shouldRemove(list.get(i))) {
        list.remove(i);
    }
}
```

### 2.4 fail-fast 的原理与边界

`ArrayList` 维护结构性修改计数 `modCount`。迭代器创建时保存 `expectedModCount`，迭代过程中发现两者不一致，通常抛出 `ConcurrentModificationException`：

```java
Iterator<String> iterator = list.iterator();
while (iterator.hasNext()) {
    if (shouldRemove(iterator.next())) {
        iterator.remove(); // 同步更新迭代器状态，正确删除
    }
}
```

也可以使用：

```java
list.removeIf(this::shouldRemove);
```

fail-fast 有三个重要边界：

1. 它是“尽早发现错误”的调试保护，不是并发安全机制；
2. 单线程直接调用 `list.remove()` 也可能触发 CME；
3. 不能把“没有抛 CME”理解为“并发访问安全”，检测本身不是强同步保证。

`for-each` 本质上会使用迭代器，因此下面的代码是错误用法：

```java
for (String value : list) {
    if (shouldRemove(value)) {
        list.remove(value); // 不应这样写
    }
}
```

### 2.5 `subList` 是视图，不是副本

```java
List<String> all = new ArrayList<>(List.of("a", "b", "c"));
List<String> part = all.subList(1, 3);
part.clear(); // all 也会变成 ["a"]
```

`subList` 与原列表共享底层数据或结构信息，因此：

- 修改子列表会影响父列表；
- 父列表发生结构性修改后，子列表后续操作可能抛 CME；
- 长期保存一个小 `subList` 可能间接持有整个大列表，需复制后再保存：

```java
List<String> snapshot = new ArrayList<>(all.subList(1, 3));
```

### 2.6 ArrayList 高频问答

**Q1：`ArrayList` 扩容为什么通常是 1.5 倍？**<br>
**A：** 减少扩容次数和总复制成本，同时比 2 倍扩容更节省瞬时空间；具体增长策略属于 JDK 实现细节，不应当当作接口契约。

**Q2：`new ArrayList<>(1000)` 会创建 1000 个元素吗？**<br>
**A：** 不会，只是预留能够容纳约 1000 个元素的数组空间，`size()` 仍然是 0。

**Q3：`ArrayList` 线程安全吗？**<br>
**A：** 不安全。多个线程并发写可能产生数据丢失、状态不一致或异常；需要根据场景使用外部锁、同步包装、COW 或其它并发结构。

**Q4：为什么 `LinkedList` 不一定比 `ArrayList` 更适合插入？**<br>
**A：** 链表虽然在已知节点位置插入是 O(1)，但先定位节点可能是 O(n)，且节点对象和指针跳转带来额外内存与缓存开销。大多数业务 List 默认选 `ArrayList`。

### 2.7 ArrayList 自测题

**1. `new ArrayList<>(1000)` 后立即调用 `size()` 是多少？为什么？**<br>
**答案：** 0。<br>
**解析：** 构造参数表示 capacity，不是元素个数；只有 `add` 后 `size` 才增加。

**2. 为什么连续尾部添加总体上是均摊 O(1)，但扩容那一次是 O(n)？**<br>
**答案：** 扩容需要分配新数组并复制所有旧引用，是 O(n)；但扩容按几何级数增长，分摊到大量添加操作后总复制次数是 O(n)。

**3. `List<Integer>.remove(1)` 删除什么？**<br>
**答案：** 删除下标 1 的元素。<br>
**解析：** 它匹配 `remove(int)`；按值删除应写 `remove(Integer.valueOf(1))`。

## 3. HashMap：哈希定位、树化与扩容（重点）

### 3.1 数据结构

JDK 8 及以后，`HashMap` 可以抽象为：

```text
table 数组
  ├─ 空桶
  ├─ 单个 Node
  ├─ 多个 Node 组成的链表
  └─ 达到条件后转换为红黑树
```

数组负责快速定位桶，链表或红黑树负责处理同桶冲突。平均情况下 `put/get` 接近 O(1)，极端哈希冲突下链表可能退化到 O(n)，树化后查询约为 O(log n)。

### 3.2 hash 扰动和桶下标

典型扰动函数：

```java
static final int hash(Object key) {
    int h;
    return key == null ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

桶下标通常为：

```java
index = (n - 1) & hash;
```

其中 `n` 是数组长度。容量设计为 2 的幂，有三个主要好处：

1. `(n - 1) & hash` 可以用位运算代替取模；
2. 容量扩为 2 倍后，一个元素只可能留在原下标，或移动到“原下标 + oldCapacity”；
3. 扩容时不需要重新计算完整 hash，只需检查 `hash & oldCapacity`。

高位扰动是因为小容量数组只使用 hash 的低位；让高位参与低位计算，可以降低一些低位分布很差的 key 产生的碰撞。

### 3.3 key 的 `equals`/`hashCode` 契约

`HashMap` 查找一个 key 时大致需要同时满足：

```text
hash 相同
且 key == 查找对象
或 key.equals(查找对象)
```

因此必须遵守：

> 如果两个对象 `equals`，它们的 `hashCode` 必须相同；反过来 hashCode 相同不要求 equals。

key 最好使用不可变类型。如果 key 放入 Map 后，参与 `equals` 或 `hashCode` 的字段发生变化，Map 可能仍保存着该节点，但新 hash 已经定位不到原桶：

```java
Map<UserKey, String> map = new HashMap<>();
UserKey key = new UserKey("A");
map.put(key, "value");
key.setCode("B"); // 修改参与 hash 的字段，后续 get 可能取不到
```

`HashMap` 允许一个 `null` key，`null` 的 hash 按 0 处理；允许多个 `null` value。

### 3.4 关键参数

| 参数 | 常见值 | 含义 |
| --- | --- | --- |
| 默认初始容量 | 16 | 首次实际初始化时的常见容量 |
| 默认负载因子 | 0.75 | `threshold = capacity * loadFactor` |
| `TREEIFY_THRESHOLD` | 8 | 桶中节点达到条件时尝试树化 |
| `UNTREEIFY_THRESHOLD` | 6 | 缩容或拆分后节点较少时退化为链表 |
| `MIN_TREEIFY_CAPACITY` | 64 | 容量小于 64 时优先扩容而不是树化 |

这些是 HotSpot/JDK 实现中的常量，不是 `Map` 接口承诺。链表达到 8 也不意味着必然树化：还要看当前 table 容量是否至少为 64。

负载因子越低，桶越稀疏、冲突概率越低，但浪费的数组空间更多；越高则相反。0.75 是时间和空间的经验折中，不是数学上的唯一最优值。

### 3.5 `put` 流程

以 JDK 8+ 的典型实现为例：

1. 计算 key 的扰动 hash；
2. table 为空时初始化；
3. 根据 `(n - 1) & hash` 定位桶；
4. 桶为空，直接放入新节点；
5. 桶不为空，先检查首节点是否就是目标 key；
6. 如果是树节点，在红黑树中查找或插入；
7. 如果是链表，顺序查找；找到则覆盖 value，否则追加新节点；
8. 新增节点后检查是否需要树化或扩容。

`put` 返回旧值，不能通过返回值区分“旧值不存在”和“旧值本身为 null”；需要区分时使用 `containsKey`，或者在业务上禁止 null value。

### 3.6 为什么扩容容量必须是 2 的幂

假设旧容量为 16，新容量为 32。某个节点原来位于桶 `j`，扩容后只需要看一位：

```java
if ((hash & oldCapacity) == 0) {
    新下标仍为 j;
} else {
    新下标为 j + oldCapacity;
}
```

因此扩容时可以把旧链表拆成低位链和高位链，不必为每个节点重新做完整取模。这个优化同时减少了扩容成本和实现复杂度。

### 3.7 扩容与容量规划

扩容通常需要：

1. 分配 2 倍容量的新 table；
2. 遍历旧 table；
3. 将每个桶中的节点拆分并放入新 table；
4. 更新 threshold 和 table 引用。

扩容是 O(n) 的集中成本，且会暂时占用新旧数组空间。已知元素数量时应提前规划：

```java
int expectedMappings = 10_000;
int capacity = (int) (expectedMappings / 0.75f) + 1;
Map<String, Order> orders = new HashMap<>(capacity);
```

注意：构造参数是容量提示，实际实现会向上取整到合适的 2 的幂；第一次 `put` 时才可能真正分配 table。对于极端边界和不同 JDK，容量公式应以实际测试为准。

### 3.8 JDK 7 与 JDK 8 的重要差异

| 维度 | JDK 7 | JDK 8+ |
| --- | --- | --- |
| 冲突结构 | 链表 | 链表，达到条件可树化 |
| 插入方式 | 头插 | 典型实现为尾插 |
| 扩容风险 | 并发扩容可能形成环 | 不再有 JDK 7 头插导致的典型环 |
| 并发安全 | 不安全 | 仍然不安全 |

“JDK 8 改尾插”不是说 `HashMap` 变成线程安全，而是降低了特定扩容成环问题。并发写仍然可能丢数据、覆盖更新、size 不准确或造成结构状态不可预测。

### 3.9 HashMap 高频问答

**Q1：为什么 `HashMap` 的容量通常是 2 的幂？**<br>
**A：** 便于用位运算定位桶，并让扩容后的节点只需在原位置和原位置加旧容量之间二选一。

**Q2：链表长度达到 8 就一定变成红黑树吗？**<br>
**A：** 不一定。还要满足 table 容量至少为 64；容量较小时通常优先扩容。

**Q3：负载因子为什么常用 0.75？**<br>
**A：** 它是空间占用与哈希冲突概率之间的经验折中，具体场景可以通过容量规划和压测调整。

**Q4：为什么可变对象不适合做 key？**<br>
**A：** 修改参与 hash 的字段会改变查找位置，但节点仍在旧桶中，导致 `get`、`containsKey` 或 `remove` 可能找不到它。

**Q5：`HashMap` 是线程安全的吗？**<br>
**A：** 不是。JDK 8 解决了典型的头插成环问题，但没有解决并发写的数据竞争和复合操作原子性问题。

### 3.10 HashMap 自测题

**1. 为什么 `HashMap` 需要同时比较 hash 和 equals？**<br>
**答案：** hash 用于快速定位桶，equals 用于在同桶节点中确认逻辑相等。<br>
**解析：** 不同对象可能发生 hash 冲突，所以 hash 相同不能直接判定 key 相同。

**2. `HashMap` 扩容后为什么节点只可能留在原位置或移动 `oldCapacity`？**<br>
**答案：** 新旧容量相差 2 倍，新的下标只多出一位二进制判断。<br>
**解析：** 检查 `(hash & oldCapacity)` 即可决定留在低位链还是移动到高位链。

**3. 把 key 放入 Map 后修改其 hash 字段，为什么可能“有值却取不到”？**<br>
**答案：** 新 hash 定位到了另一个桶，而旧节点仍在原桶。<br>
**解析：** Map 不会自动迁移因 key 内容变化而改变位置的节点。

## 4. HashMap 的线程安全边界

### 4.1 并发使用会发生什么

普通 `HashMap` 的以下操作都不能直接在多线程间共享：

- 多线程 `put` 可能互相覆盖，造成数据丢失；
- `size` 的更新可能丢失；
- 扩容、树化等结构调整可能与其他线程交错；
- `containsKey` 后再 `put` 不是原子操作；
- 迭代期间修改可能抛 CME，也可能读到不符合业务要求的状态。

不同 JDK 的具体表现不同，但结论不变：**不要通过观察到“测试没问题”来推断线程安全**。

### 4.2 替代方案

| 场景 | 选择 |
| --- | --- |
| 单线程或外部统一加锁 | `HashMap` |
| 极低并发，简单共享 | `Collections.synchronizedMap` |
| 高并发读写 | `ConcurrentHashMap` |
| 需要不可变快照 | 复制后使用 `Map.copyOf` 或不可变 Map |
| 需要严格事务边界 | 业务锁、数据库事务或专门并发结构 |

`Collections.synchronizedMap` 的迭代必须手动加锁：

```java
Map<String, Integer> map =
        Collections.synchronizedMap(new HashMap<>());

synchronized (map) {
    for (Map.Entry<String, Integer> entry : map.entrySet()) {
        use(entry);
    }
}
```

## 5. ConcurrentHashMap：高并发 Map（重点）

### 5.1 设计目标

`ConcurrentHashMap` 不是“给 HashMap 外面套一把锁”，它的目标是：

- 允许并发读取；
- 不让所有写操作竞争同一把全局锁；
- 对空桶插入使用 CAS；
- 对同一桶的冲突写入进行局部同步；
- 扩容时允许其它线程协助迁移；
- 为常用复合操作提供原子 API。

它禁止 `null` key 和 `null` value，因为：

```java
V value = map.get(key);
```

返回 `null` 时，需要明确表示“key 不存在”，否则无法区分“key 存在但 value 为 null”。在并发场景下再用 `containsKey` 二次判断也不能构成可靠的原子语义。

### 5.2 JDK 7 与 JDK 8+ 的结构差异

| 维度 | JDK 7 | JDK 8+ |
| --- | --- | --- |
| 顶层结构 | `Segment[]` + 每段哈希表 | `Node[]` + 链表/红黑树 |
| 写入同步 | Segment 继承 `ReentrantLock` 的分段锁 | 空桶 CAS，同桶冲突时锁桶首节点 |
| 并发粒度 | 受段数限制，默认并发度常被记为 16 | 细化到桶，理论并发粒度更细 |
| 冲突结构 | 链表 | 链表和红黑树 |
| 扩容 | 各段独立扩容 | 多线程协助扩容 |

面试中说“CHM 使用分段锁”通常只适用于 JDK 7；JDK 8+ 的典型实现不是 Segment 分段锁。

### 5.3 JDK 8+ 的 `put` 流程

一次典型的 `put` 可以按下面理解：

1. key 或 value 为 null 时抛出 NPE；
2. table 尚未初始化时，线程通过 CAS 竞争初始化权；
3. 目标桶为空时，使用 CAS 放入新节点，不需要锁；
4. 目标桶首节点的 hash 为 `MOVED` 时，说明正在扩容，当前线程协助迁移；
5. 目标桶非空且未迁移时，锁住桶首节点；
6. 在链表或红黑树中查找、覆盖或插入；
7. 更新计数，并根据阈值触发或协助扩容。

这里的 `synchronized (firstNode)` 是桶级锁，不是锁住整个 Map。不同桶之间通常可以并发写；同一桶发生冲突时才会竞争。

### 5.4 为什么 `get` 通常不加锁

JDK 8+ 的典型实现通过 volatile 语义保证 table、节点 value 和 next 指针的可见性。节点插入后不会原地移动；扩容时旧桶会放入 `ForwardingNode`，读线程遇到它就转到新 table 查询。

所以读路径通常可以：

```text
读取当前 table
→ 定位桶
→ 遍历链表或查红黑树
→ 遇到 ForwardingNode 时转移到新 table
```

这解释了“读通常无锁”，但不应简化为“CHM 所有操作都无锁”：写冲突桶会锁，扩容也会进行同步和 CAS。

### 5.5 协助扩容

扩容不是由一个线程独占完成。迁移线程会在旧 table 中划分任务范围，其它发现扩容的线程可以领取一段任务并迁移。旧桶迁移完成后用 `ForwardingNode` 标识，避免读线程继续把它当作普通链表。

协助扩容的价值是把扩容成本分摊到多个并发线程，但它不能消除扩容本身的内存和 CPU 成本。容量仍应根据预计映射数量合理规划。

### 5.6 计数与 `size`

CHM 通常使用类似 `baseCount + CounterCell[]` 的分散计数方案，降低多个线程更新同一个计数变量的竞争。并发变化期间，`size()` 反映的是某个时刻附近的观察结果，不应当把它当成整个业务操作的锁。

如果业务要求“判断数量后再执行动作”具备严格原子性，需要使用外部同步、专门的计数器或把状态设计成一个原子更新操作；不能依赖：

```java
if (map.size() < limit) {
    map.put(key, value);
}
```

### 5.7 原子复合操作

推荐使用 Map 提供的原子 API：

```java
ConcurrentHashMap<String, LongAdder> counters = new ConcurrentHashMap<>();
counters.computeIfAbsent("login", key -> new LongAdder()).increment();

map.putIfAbsent(key, value);
map.computeIfPresent(key, (k, oldValue) -> update(oldValue));
map.merge(key, 1, Integer::sum);
map.remove(key, expectedValue); // 只有 value 仍匹配时才删除
```

注意事项：

- `computeIfAbsent` 的映射函数不要递归修改同一个 Map；
- 映射函数应短小、无阻塞、无外部副作用；
- 返回 `null` 表示不建立映射；
- `compute`/`merge` 的函数可能在桶锁范围内执行，不能在里面做耗时操作；
- `LongAdder` 适合高并发累加，但 `sum()` 不是一个全局锁保护下的精确快照。

### 5.8 弱一致迭代器

CHM 的迭代器通常是弱一致的：

- 不要求遍历结果是某个瞬间的完整快照；
- 允许并发修改；
- 不因并发结构修改抛 CME；
- 可能看到部分新数据，也可能看不到遍历开始后的更新。

它适合监控、统计、清理等允许近似观察的场景；需要一致快照时，应显式复制并接受复制成本。

### 5.9 ConcurrentHashMap 高频问答

**Q1：CHM 是完全无锁的吗？**<br>
**A：** 不是。空桶插入通常用 CAS，读通常无锁，但同桶冲突写会锁桶首节点，初始化和扩容也需要 CAS 与同步。

**Q2：为什么 CHM 禁止 null？**<br>
**A：** `get` 返回 null 时必须能唯一表示 key 不存在，禁止 null value 可以避免状态歧义。

**Q3：CHM 的并发度为什么比 JDK 7 的 Segment 更细？**<br>
**A：** JDK 8+ 以桶为更细的冲突隔离单位，只有访问同一桶的写线程才主要竞争；但实际并发能力仍受哈希分布、CPU、锁竞争和扩容影响。

**Q4：`putIfAbsent` 和 `containsKey` + `put` 有什么区别？**<br>
**A：** `putIfAbsent` 是原子的；后者分两步执行，中间可能被其他线程插入。

**Q5：为什么不能在 `computeIfAbsent` 中递归更新同一个 Map？**<br>
**A：** 映射函数执行时可能处于相关桶的同步区域，递归修改会造成递归更新、死锁风险或实现抛出异常。

### 5.10 ConcurrentHashMap 自测题

**1. CHM 如何做到不同桶之间并发写？**<br>
**答案：** 空桶使用 CAS，同桶冲突时只锁定对应桶的首节点，而不是整个 Map。<br>
**解析：** 锁粒度从全表缩小到冲突桶，实际效果仍取决于 hash 分布。

**2. CHM 扩容时为什么其它线程要参与迁移？**<br>
**答案：** 把集中式扩容成本分摊到多个正在访问 Map 的线程，减少单个线程长时间承担迁移开销。<br>
**解析：** 线程遇到 `ForwardingNode` 会转移或协助扩容；这不代表扩容没有成本。

**3. 为什么 `if (map.get(k) == null) map.put(k, v)` 不是并发安全的“只初始化一次”？**<br>
**答案：** 多个线程可能同时读到 null，然后都执行 put。<br>
**解析：** 应使用 `putIfAbsent` 或 `computeIfAbsent`。

## 6. 其它 List：按场景复习

### 6.1 LinkedList

`LinkedList` 是双向链表，同时实现 `List` 和 `Deque`：

| 操作 | `ArrayList` | `LinkedList` |
| --- | --- | --- |
| 随机访问 | O(1) | O(n) |
| 尾部添加 | 均摊 O(1) | O(1) |
| 已知节点位置插入/删除 | 移动后续元素 | O(1) |
| 内存和缓存局部性 | 较好 | 节点开销大、指针跳转多 |

实际项目中：

- 普通列表默认 `ArrayList`；
- 栈和双端队列优先 `ArrayDeque`；
- 不要因为“链表插入 O(1)”就默认选择 `LinkedList`，还要计算定位成本。

### 6.2 CopyOnWriteArrayList

写操作大致是“加锁 → 复制数组 → 修改副本 → 发布新数组”，读操作读取已发布数组，迭代器通常持有创建时的快照。

适合：

- 读远多于写；
- 数据量不大；
- 允许迭代期间看旧快照；
- 监听器、路由配置、黑白名单等。

不适合高频写或大集合，因为每次写都可能复制整个数组并制造较多短命对象。其迭代器不支持 `remove`、`set`、`add`。

## 7. LinkedHashMap、HashSet 与 TreeMap

### 7.1 LinkedHashMap 与简单 LRU

`LinkedHashMap` 在哈希表之外维护双向链表：

- 默认维护插入顺序；
- 构造时传 `accessOrder = true` 可维护访问顺序；
- 重写 `removeEldestEntry` 可实现最简单的容量淘汰。

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(capacity, 0.75f, true);
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

这只是单线程或外部同步下的简单 LRU，不是线程安全缓存。`accessOrder = true` 时，`get` 也可能修改链表顺序，因此“读操作”不一定是只读操作。生产环境通常使用 Caffeine 等成熟缓存实现。

### 7.2 HashSet、LinkedHashSet、TreeSet

- `HashSet` 内部以 `HashMap` 的 key 保存元素，value 是一个共享占位对象；
- `LinkedHashSet` 在此基础上维护插入顺序；
- `TreeSet` 基于 `TreeMap`，按比较器排序并支持范围操作；
- `HashSet` 去重依赖 `hashCode` 和 `equals`；
- `TreeSet` 去重依赖比较结果是否为 0。

### 7.3 TreeMap

`TreeMap` 使用红黑树，查询、插入和删除通常为 O(log n)，适合：

- 按 key 排序遍历；
- `floorKey`、`ceilingKey` 等邻近查询；
- `subMap`、`headMap`、`tailMap` 范围查询。

这些范围方法返回视图，不是副本。自然排序下通常不接受 null key。比较器与 equals 不一致时，TreeMap 可能把业务上认为不同的对象当成同一个 key。

## 8. 不可变集合、视图与常见陷阱

### 8.1 `Arrays.asList`

```java
String[] array = {"a", "b"};
List<String> view = Arrays.asList(array);
view.set(0, "x"); // 会修改 array[0]
view.add("c");    // UnsupportedOperationException
```

它是定长数组视图：允许 `set`，不允许改变长度。对基本类型数组尤其容易误用：

```java
List<int[]> wrong = Arrays.asList(new int[]{1, 2, 3});
System.out.println(wrong.size()); // 1，元素是整个 int[]
```

### 8.2 `List.of`、`List.copyOf` 与不可变

`List.of` 和 `List.copyOf` 返回不可变集合，通常拒绝 null，不能通过返回对象修改元素。它们和 `Collections.unmodifiableList` 有区别：

- `unmodifiableList` 是原集合的只读视图，原集合变化时视图可能跟着变化；
- `List.copyOf` 是独立的不可变副本，不会因为原集合后续修改而变化。

如果需要一个可变副本：

```java
List<String> copy = new ArrayList<>(source);
```

## 9. Queue、Deque 与 BlockingQueue

### 9.1 普通队列

`ArrayDeque` 通常是单线程栈/队列的首选，基于循环数组，禁止 null：

```java
Deque<String> deque = new ArrayDeque<>();
deque.offerLast("a");
deque.pollFirst();
deque.push("top");
deque.pop();
```

`PriorityQueue` 是堆，不保证迭代顺序；只有 `poll` 才按优先级取出。`remove(Object)` 通常需要线性查找，不是所有操作都是 O(log n)。

### 9.2 异常返回值与特殊值返回值

| 操作 | 出错/无元素时抛异常 | 出错/无元素时返回特殊值 |
| --- | --- | --- |
| 插入 | `add` | `offer` |
| 删除队首 | `remove` | `poll` |
| 查看队首 | `element` | `peek` |

### 9.3 BlockingQueue 选型

| 实现 | 特征 | 常见场景 |
| --- | --- | --- |
| `ArrayBlockingQueue` | 有界数组 | 需要背压的生产者-消费者 |
| `LinkedBlockingQueue` | 可指定容量，默认容量很大 | 需特别注意伪无界和内存风险 |
| `SynchronousQueue` | 零容量，直接交接 | 任务直接移交线程 |
| `PriorityBlockingQueue` | 无界优先级队列 | 优先级任务 |
| `DelayQueue` | 按到期时间出队 | 延迟任务、重试 |

生产环境的队列通常应显式设置容量，并配合拒绝、降级或监控策略；默认“几乎无界”只会把压力转移成内存增长。

## 10. 集合选型与性能边界

| 需求 | 常用选择 | 关键理由 |
| --- | --- | --- |
| 普通列表 | `ArrayList` | 连续数组、随机访问快 |
| 栈/双端队列 | `ArrayDeque` | 低开销、操作清晰 |
| 哈希映射 | `HashMap` | 平均 O(1)，单线程使用 |
| 并发哈希映射 | `ConcurrentHashMap` | 桶级并发和原子复合 API |
| 只读配置 | `Map.copyOf`、`List.copyOf` | 明确不可变边界 |
| 读多写极少列表 | `CopyOnWriteArrayList` | 读快，接受写复制 |
| 插入顺序 Map | `LinkedHashMap` | 维护链表顺序 |
| 范围查询 | `TreeMap` | 有序 key 和导航 API |
| 生产者-消费者 | 有界 `BlockingQueue` | 阻塞和背压语义明确 |

性能不能只看 Big-O：

- `ArrayList` 的连续内存通常有更好的缓存局部性；
- `LinkedList` 的节点对象会增加引用和对象头开销；
- `HashMap` 的 table 和 Node 都消耗内存，元素较少时额外开销可能很明显；
- 装箱集合会为对象和引用付出成本，极端数值场景可评估 fastutil、Eclipse Collections 等原始类型集合；
- 预估容量可以减少扩容，但过度预留也会浪费内存。

## 11. 综合自测题（含答案与解析）

**1. ArrayList 和 LinkedList 如何选择？**<br>
**答案：** 普通列表默认 `ArrayList`，需要双端队列优先 `ArrayDeque`，只有明确的链表节点操作场景才考虑 `LinkedList`。<br>
**解析：** LinkedList 的插入 O(1) 需要已知节点位置；如果还要定位，整体仍可能是 O(n)，而且缓存局部性较差。

**2. `ArrayList` 扩容为什么不是每次加一个元素的容量？**<br>
**答案：** 几何扩容可以让连续添加的总复制成本保持 O(n)，避免 O(n²) 的反复复制。

**3. `HashMap` 为什么要求 key 的 `equals` 相等时 hashCode 必须相等？**<br>
**答案：** 两个逻辑相等的 key 必须落在同一个桶，Map 才能在桶内通过 equals 找到它。

**4. 链表长度达到 8 后为什么可能仍不树化？**<br>
**答案：** table 容量不足 64 时，典型实现优先扩容；树化还受 JDK 版本和实现细节影响。

**5. 为什么不能依赖 HashMap 的遍历顺序？**<br>
**答案：** 顺序不是接口契约，会受 hash、容量、扩容和 JDK 实现影响。

**6. 普通 HashMap 在 JDK 8 以后是否线程安全？**<br>
**答案：** 不是。JDK 8 改善了并发扩容成环问题，但仍可能丢数据、size 不准和复合操作竞争。

**7. `containsKey` 后 `put` 与 `putIfAbsent` 的区别？**<br>
**答案：** 前者是两个独立操作，后者对“不存在则写入”提供原子语义。

**8. CHM 为什么禁止 null？**<br>
**答案：** 让 `get` 返回 null 可以唯一表示 key 不存在，避免并发语义歧义。

**9. CHM 的 `get` 为什么通常不加锁？**<br>
**答案：** 依靠 volatile 可见性、不可移动节点和扩容时的 `ForwardingNode` 转发实现无锁读路径。

**10. CHM 是不是完全无锁？**<br>
**答案：** 不是。空桶写常用 CAS，同桶冲突写会锁桶，初始化和扩容也需要同步。

**11. `computeIfAbsent` 中为什么不应修改同一个 Map？**<br>
**答案：** 映射函数可能在相关桶同步区域内执行，递归修改会导致递归更新、异常或死锁风险。

**12. `Arrays.asList(new int[]{1, 2, 3}).size()` 为什么是 1？**<br>
**答案：** 可变参数接收到的是一个 `int[]` 整体，基本类型数组被当成单个元素；它不是 `List<Integer>`。

**13. `subList` 为什么可能导致大列表无法及时回收？**<br>
**答案：** 子列表通常持有父列表或其底层数组的引用，长期保存小视图可能间接保留整个大列表。

**14. TreeSet 和 HashSet 的去重依据有什么不同？**<br>
**答案：** HashSet 使用 hashCode + equals；TreeSet 使用比较结果是否为 0。

**15. 线程池为什么不应无脑使用默认 LinkedBlockingQueue？**<br>
**答案：** 默认容量非常大，任务堆积时可能持续占用内存而不是及时背压；生产环境应显式设置有界容量并制定拒绝策略。

## 12. 背诵卡片

1. 普通 List 默认 `ArrayList`，栈/双端队列优先 `ArrayDeque`。
2. ArrayList 是引用数组；随机访问 O(1)，扩容复制引用。
3. ArrayList 默认构造通常懒初始化，首次添加常见容量为 10；扩容策略是实现细节。
4. `remove(int)` 按下标，`remove(Object)` 按值。
5. `modCount` 检测结构性修改，fail-fast 不是线程安全。
6. `subList` 是视图；需要独立结果就 `new ArrayList<>(subList)`。
7. HashMap = table + 链表/红黑树；平均 `put/get` 接近 O(1)。
8. HashMap 通过 hash 定位桶，再通过 equals 确认 key。
9. 容量为 2 的幂便于位运算和高效扩容拆分。
10. 链表达到 8 不一定树化，还要看 table 容量等条件。
11. 可变 key 修改 hash 字段后可能“放得进去、取不出来”。
12. HashMap 不保证顺序，也不保证线程安全。
13. CHM JDK 7 是 Segment 分段锁；JDK 8+ 是 CAS + 桶级同步 + 协助扩容。
14. CHM 禁止 null；读通常无锁，写冲突仍可能加锁。
15. 并发复合操作优先 `putIfAbsent`、`computeIfAbsent`、`merge`、`remove(key,value)`。
16. CHM 迭代器弱一致，不提供一致快照。
17. LinkedHashMap 的访问序可以实现简单 LRU，但不等于线程安全缓存。
18. TreeMap 适合排序和范围查询，范围方法通常返回视图。
19. `Arrays.asList` 是定长数组视图，`List.of` 是不可变集合。
20. 阻塞队列生产环境优先显式设置容量，避免伪无界队列掩盖压力。
