## 1. 继承体系与接口契约

### 1.1 核心原理
| 顶层接口 | 有序性 | 允许重复 | 允许 null | 主要实现 |
| --- | --- | --- | --- | --- |
| `List` | 有（索引/插入序） | 是 | 是 | ArrayList、LinkedList、Vector、CopyOnWriteArrayList |
| `Set` | HashSet 无序、LinkedHashSet 插入序、TreeSet 排序 | 否 | 是（TreeSet 否） | HashSet、LinkedHashSet、TreeSet |
| `Queue`/`Deque` | FIFO / 优先级 / 双端 | 是 | ArrayDeque 否 | ArrayDeque、LinkedList、PriorityQueue |
| `Map` | HashMap 无序、LinkedHashMap 插入或访问序、TreeMap 排序 | key 不重复 | HashMap 是、Hashtable/CHM 否 | HashMap、LinkedHashMap、TreeMap、ConcurrentHashMap |

两套根接口：`Collection`（元素集合）与 `Map`（键值对），**Map 不属于 Collection**。`AbstractXxx` 提供骨架实现，`Collections` 是工具类（`sort`、`unmodifiableList`、`synchronizedMap`、`emptyList`）。

`Comparable` vs `Comparator`：

| 维度 | Comparable | Comparator |
| --- | --- | --- |
| 位置/方法 | 类自身实现 `compareTo` | 外部比较器 `compare` |
| 排序策略 | 自然排序，只有一种 | 可传多种策略 |
| 包 | `java.lang` | `java.util` |
| 适用 | `Integer`/`String`/`BigDecimal` | 业务对象动态排序 |

`TreeSet`/`TreeMap` 判定重复用 `compareTo == 0`（不是 equals）；`BigDecimal` 的 compareTo 与 equals 语义不同（scale 差异），做 TreeMap key 时与 HashMap 行为不一致。

### 1.2 面试问答
**Q1：`Collection` 与 `Collections` 的区别？** A：前者是集合根接口，后者是静态工具类。
**Q2：`Iterator` 与 `Iterable` 的关系？** A：`Iterable.iterator()` 是 for-each 的基础，for-each 编译后就是 Iterator 遍历，因此遍历中修改集合会抛 CME。
**Q3：`Collections.synchronizedList` 能保证线程安全吗？** A：单个方法安全，但复合操作与迭代仍需外部 `synchronized(list)`，且全表一把锁性能差。
**Q4：`TreeMap` 为什么不能有 null key？** A：需要调用 `compareTo`/`compare`，null 会 NPE（自然排序下）。

### 1.3 高频追问与陷阱
- 陷阱：`Vector` 全方法 `synchronized`，锁粒度大且复合操作仍非原子，属历史遗留类。
- 陷阱：`Collections.unmodifiableList` 是**视图**，原集合被修改时不可变视图也会变。
- 错误回答："`Map` 继承自 `Collection`"；"TreeSet 用 equals 去重"。

### 1.5 一句话速记
- List 有序可重复、Set 不重复、Map 键不重复、Queue 队首队尾。
- `TreeMap/TreeSet` 去重依据是 `compareTo == 0`。

## 2. ArrayList 扩容与 fail-fast

### 2.1 核心原理
底层 `Object[] elementData`；JDK 8 起懒初始化，第一次 `add` 分配容量 **10**。

```java
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);          // 1.5 倍
    if (newCapacity - minCapacity < 0) newCapacity = minCapacity; // addAll 场景兜底
    if (newCapacity - MAX_ARRAY_SIZE > 0) newCapacity = hugeCapacity(minCapacity);
    elementData = Arrays.copyOf(elementData, newCapacity);       // 复制，O(n)
}
```
1.5 倍是空间与复制次数的折中：扩容 k 次总拷贝约 3n（几何级数），远优于每次 +1；且比 2 倍更容易复用旧块之后的内存。`Arrays.copyOf` 是**浅拷贝**。

`modCount` 记录结构性修改次数，迭代器持有 `expectedModCount`，不一致即抛 `ConcurrentModificationException`（**单线程遍历中直接 remove 同样触发**）。

```java
Iterator<Integer> it = list.iterator();
while (it.hasNext()) if (it.next() == 1) it.remove();  // 迭代器 remove 会同步 expectedModCount
list.removeIf(x -> x == 1);                            // JDK 8+ 推荐
for (int i = list.size() - 1; i >= 0; i--) if (list.get(i) == 1) list.remove(i);  // 倒序删除
```

### 2.2 面试问答
**Q1：`new ArrayList<>(1000)` 与默认构造后 add 1000 个的差异？** A：前者一次分配；后者经历 10→15→22→…→1234 约 12 次扩容与数组复制。
**Q2：fail-fast 与 fail-safe 的区别？** A：fail-fast（ArrayList/HashMap）用 `modCount` 校验立即失败；fail-safe（COW/CHM）遍历快照或弱一致视图，不抛异常但可能读旧数据。
**Q3：`remove(int)` 与 `remove(Object)` 的区别？** A：`List<Integer>` 中 `remove(1)` 删下标，`remove(Integer.valueOf(1))` 删值，装箱歧义是高频线上问题。
**Q4：遍历中删倒数第二个元素会抛 CME 吗？** A：`hasNext()` 先返回 false 提前退出，可能不抛 —— 但不能依赖，属未定义行为。
**Q5：`subList` 是什么？** A：视图，修改子列表会影响父列表，父列表结构性修改后子列表操作抛 CME；长期持有子视图会阻止大列表回收。

### 2.3 高频追问与陷阱
- 陷阱：`ensureCapacity`/`trimToSize` 用于手动优化容量；已知规模务必指定初始容量。
- 陷阱：ArrayList 的元素遍历用索引最快，LinkedList 必须用迭代器（`get(i)` 是 O(n)）。
- 错误回答："ArrayList 扩容 2 倍"；"扩容 1.5 倍是为了线程安全"。

### 2.5 一句话速记
- 懒初始化，首次 add 分配 10；扩容 `old + (old >> 1)`，靠 `Arrays.copyOf`。
- `modCount` 与 `expectedModCount` 不一致即 CME；删除用迭代器或 `removeIf`。

## 3. LinkedList 与 CopyOnWriteArrayList

### 3.1 核心原理
`LinkedList` 是双向链表（`Node{item, prev, next}`）且实现 `Deque`。

| 维度 | ArrayList | LinkedList |
| --- | --- | --- |
| 随机访问 `get(i)` | O(1) | O(n)（按 i 与 size/2 决定从头还是尾找） |
| 头插/头删 | O(n) | O(1) |
| 尾部 add | 均摊 O(1) | O(1) |
| 内存 | 数组 + 最多 50% 冗余容量 | 每元素多 2 个引用 |
| 缓存局部性 | 好 | 差（指针跳转） |
| 结论 | 默认选择 | 频繁头尾操作或需 Deque 时 |

实测中即使中间插入，`ArrayList` 也常优于 `LinkedList`（内存连续性）；队列/栈场景 `ArrayDeque` 通常比 `LinkedList` 更快。

`CopyOnWriteArrayList`：写操作加 `ReentrantLock`，复制新数组、在新数组修改、`setArray` 发布（`array` 是 volatile）；读完全无锁。

```java
public boolean add(E e) {
    synchronized (lock) {
        Object[] es = getArray(), newEs = Arrays.copyOf(es, es.length + 1);
        newEs[es.length] = e;
        setArray(newEs);     // volatile 写发布新数组
        return true;
    }
}
```

### 3.2 面试问答
**Q1：COW 适合什么场景？** A：读多写极少（配置、监听器列表、黑白名单）；写是 O(n) 复制且内存翻倍，写频繁会频繁 GC。
**Q2：COW 的"弱一致性"意味着什么？** A：迭代器拿到创建时刻的数组快照，遍历期间的写不可见，**不抛 CME**；迭代器的 add/remove/set 全抛 `UnsupportedOperationException`。
**Q3：COW 为什么不需要给数组元素加 volatile？** A：数组引用 `array` 是 volatile，`setArray` 与读之间有 happens-before；数组内容在发布前已构建完成，属安全发布。
**Q4：`CopyOnWriteArraySet` 呢？** A：基于 COW List 实现，`add` 需遍历查重，写性能更差。

### 3.3 高频追问与陷阱
- 陷阱：COW 每次写产生新数组，大数组 + 高频写是 OOM 诱因。
- 陷阱：`LinkedList` 允许 null，`ArrayDeque` 禁止 null（直接 NPE）。
- 错误回答："LinkedList 插入删除一定比 ArrayList 快"（忽略定位成本与缓存局部性）。

### 3.5 一句话速记
- 默认 ArrayList；头尾操作用 `ArrayDeque`；LinkedList 的优势场景有限。
- COW：写加锁复制、读无锁、弱一致、只适合读多写极少。

## 4. HashMap 结构与阈值全解

### 4.1 核心原理
结构：数组 + 链表 + 红黑树（JDK 8）。

```java
static final int hash(Object key) {                    // 扰动函数
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
// index = (n - 1) & hash
```
**容量为 2 的幂的三个原因**：① `hash & (n-1)` 等价取模但用位运算；② 扩容为 2n 时元素新位置只有"原位置 j"或"j + oldCap"两种；③ 迁移无需重算 hash。构造器传 20 会经 `tableSizeFor` 向上取整为 32（5 次右移或运算）。

| 常量 | 值 | 含义 |
| --- | --- | --- |
| `DEFAULT_INITIAL_CAPACITY` | 16 | 默认容量 |
| `DEFAULT_LOAD_FACTOR` | 0.75 | 空间与冲突的折中；源码注释称链表长度达 8 的概率约 6e-8（泊松） |
| `TREEIFY_THRESHOLD` | 8 | 链表长度 ≥ 8 且 table ≥ 64 时树化 |
| `UNTREEIFY_THRESHOLD` | 6 | 树节点 ≤ 6 退化链表（留缓冲避免边界反复转换） |
| `MIN_TREEIFY_CAPACITY` | 64 | 低于此容量优先扩容而非树化 |

**put 流程**：① table 空则 `resize()` 初始化（16，阈值 12）；② `(n-1)&hash` 定位桶，空桶直接放入；③ 首节点 hash 与 key 相等则覆盖；④ 树节点走 `putTreeVal`；⑤ 否则遍历链表，找到覆盖，否则**尾插**，`binCount >= 7`（链表达 8）时 `treeifyBin`；⑥ `++size > threshold` 则 `resize()`。

**resize 的高低位拆分**：用 `loHead/loTail` 与 `hiHead/hiTail` 两条链，判断 `(e.hash & oldCap) == 0`：为 0 留在 j，否则移到 `j + oldCap`。JDK 7 则逐元素重算下标并使用**头插法**。

### 4.2 面试问答
**Q1：JDK 7 为什么并发扩容会死循环？** A：两个线程同时 `transfer`，头插法使链表反转，线程 A 挂起期间 B 完成扩容，A 继续操作可能形成 `A→B→A` 环形链表，后续 get 遍历 100% CPU。JDK 8 改尾插 + 高低位拆分，不再成环。
**Q2：为什么默认容量 16？** A：太小频繁扩容，太大浪费空间，16 是经验值；阿里手册建议按预估元素数显式指定。
**Q3：允许 null key 吗？** A：允许且只能一个，null 的 hash 固定为 0，落在桶 0。
**Q4：为什么树化阈值是 8、退化是 6？** A：8 来自泊松分布（正常哈希几乎不可能达到），6 与 8 之间留缓冲避免 7/8 边界反复转换。
**Q5：`new HashMap<>(1000)` 容量是 1000 吗？** A：不是，会被取整为 1024，且真实阈值在第一次 put 后为 `容量 * 0.75`。

### 4.3 高频追问与陷阱
- 陷阱：链表达 8 但 table < 64 时只扩容不树化。
- 陷阱：key 应为不可变类型，修改参与 hashCode 的字段会导致"放进去取不出来"。
- 陷阱：HashMap 迭代顺序在 JDK 7 与 JDK 8 下不同，依赖顺序即 bug。
- 错误回答："扩容后下标翻倍"；"链表到 8 一定树化"。

### 4.4 代码/配置示例
```java
int cap = (int) (expected / 0.75f) + 1;      // 预估容量公式
Map<String, Order> map = new HashMap<>(cap);
// JDK 19+ 更直观：HashMap.newHashMap(numMappings)
```

### 4.5 一句话速记
- 数组+链表+红黑树；扰动 `h ^ (h >>> 16)`；下标 `(n-1) & hash`。
- 容量 2 的幂、负载因子 0.75、树化 8/容量 64、退化 6；resize 按 `hash & oldCap` 分高低位。

## 5. HashMap 线程不安全的具体表现

### 5.1 核心原理
| 版本 | 表现 | 机理 |
| --- | --- | --- |
| JDK 7 | **扩容死循环**、数据丢失 | 头插法 + 并发 `transfer` 形成环形链表 |
| JDK 8 | 数据丢失、size 不准 | 尾插不成环，但并发写同一桶会互相覆盖；`++size` 丢失更新；扩容期间写入旧 table 的对象丢失 |
| JDK 8 | 结构不一致 | 树化/退化并发执行时链表与树状态错乱 |

**结论：多线程一律用 `ConcurrentHashMap`**，或用 `Collections.synchronizedMap`（性能差）。

### 5.2 面试问答
**Q1：JDK 8 还有死循环吗？** A：扩容不再成环，所以没有死循环；但数据丢失与 size 不准仍然存在，且并发树化可能抛 `ClassCastException` 之类的结构异常。
**Q2：为什么 `size` 会不准？** A：`size` 是普通 int，`++size` 非原子，并发丢失更新。
**Q3：并发下还会出现什么问题？** A：一个线程在 `resize` 迁移，另一个线程写入旧 table，新 table 建立后该写入丢失。
**Q4：可以用 `Collections.synchronizedMap` 吗？** A：可以但全表一把锁、复合操作与迭代仍需外部同步，性能远低于 `ConcurrentHashMap`，仅极低并发场景可接受。

### 5.3 高频追问与陷阱
- 追问"为什么 JDK 8 改成尾插" → 根因是头插的环，其次保持遍历顺序不再反转（但迭代顺序仍不保证）。
- 错误回答："JDK 8 的 HashMap 线程安全了"。

### 5.5 一句话速记
- JDK 7 头插 → 并发扩容死循环；JDK 8 尾插 → 仍丢数据、size 不准。
- 多线程场景一律 `ConcurrentHashMap`。

## 6. ConcurrentHashMap

### 6.1 核心原理
| 维度 | JDK 7 | JDK 8+ |
| --- | --- | --- |
| 结构 | Segment 数组 + HashEntry 数组 + 链表 | Node 数组 + 链表 + 红黑树 |
| 锁 | 分段锁（Segment 继承 ReentrantLock），默认 16 段 | 桶级 CAS + `synchronized`（锁桶首节点） |
| 并发度 | 等于段数，扩容不能扩段 | 等于桶数量，可动态扩容 |
| size | 段内 count 累加，尝试 2 次后加锁 | `baseCount` + `CounterCell[]`（类似 LongAdder） |
| 空桶写 | 需段锁 | CAS 无锁写 |
| 树化 | 无 | 同 HashMap（8 / 6 / 64） |

**JDK 8 put 流程**：① key/value 为 null 直接 NPE；② table 空则 `initTable`（CAS 把 `sizeCtl` 从 0 改 -1，失败者 yield 自旋）；③ 桶空则 `casTabAt` 写入（**无锁**）；④ 首节点 `hash == MOVED(-1)` 说明在扩容，当前线程 `helpTransfer` **协助扩容**；⑤ 否则 `synchronized (f)` 锁桶首节点后插入，链表达 8 且容量 ≥ 64 则树化；⑥ `addCount(1L, binCount)` 更新计数并判断扩容。

**get 为什么无锁**：`table`、`Node.val`、`Node.next` 都是 volatile（保证可见性）；节点插入后不再移动；扩容时旧桶挂 `ForwardingNode`（hash = MOVED = -1）标记，`get` 遇到则到新 table 查。因此读路径无需加锁。

**协助扩容**：扩容时用 volatile 的 `transferIndex` 划分任务区间，各线程 CAS 抢占一段（stride）迁移，`sizeCtl` 用 `(rs << RESIZE_STAMP_SHIFT) + 2` 记录参与线程数。

**size 弱一致**：`sumCount()` = baseCount + 所有 CounterCell 的累加，并发下为近似值；`CounterCell` 用 `@Contended` 填充避免伪共享。需要精确值必须外部加锁；`mappingCount()` 返回 long 避免 int 溢出，语义仍是估计。

### 6.2 面试问答
**Q1：JDK 8 为什么放弃分段锁？** A：段数固定（16）限制并发度；段内仍是数组+链表，粒度偏大；内存碎片多。JDK 8 用 CAS + 桶级 synchronized 把并发度提到桶数量级，并复用红黑树；且 JDK 8 的 synchronized 有锁升级优化，性能足够。
**Q2：为什么禁止 null？** A：`get` 返回 null 无法区分"key 不存在"与"value 为 null"，并发下也无法用 `containsKey` 二次确认。
**Q3：弱一致迭代器有什么用？** A：`forEach`、`keySet().iterator()` 可能看到或漏掉新元素，但绝不抛 CME，适合统计、监控、清理；需要一致快照就自行拷贝。
**Q4：`computeIfAbsent` 有什么坑？** A：映射函数必须幂等无副作用（JDK 8 实现可能多次调用）；在函数内递归修改同一个 map 可能死锁或抛 `IllegalStateException: Recursive update`；返回 null 不写入任何映射。
**Q5：多线程遍历并删除怎么做？** A：用 `map.remove(k, v)`（原子）或 `computeIfPresent`，或 `entrySet().removeIf(...)`（CHM 的视图支持原子删除）。

### 6.3 高频追问与陷阱
- 追问"`sizeCtl` 含义" → 0 未初始化、-1 初始化中、-N 表示 N-1 个线程在扩容、正数为下次扩容阈值。
- 陷阱：`Collections.synchronizedMap` 全表一把锁，性能比 CHM 差一个量级。
- 错误回答："CHM 用分段锁"（那是 JDK 7）；"CHM 完全无锁"（写冲突桶仍加锁）。

### 6.4 代码/配置示例
高并发计数：`counters.computeIfAbsent(key, k -> new LongAdder()).increment();`，比 AtomicLong 的 CAS 冲突低得多（见 [并发编程](./03-并发编程.md)）。

### 6.5 一句话速记
- JDK 7 分段锁（默认 16 段）；JDK 8 CAS + synchronized 锁桶头 + 红黑树 + 协助扩容。
- get 无锁靠 volatile 与 ForwardingNode；size 弱一致（baseCount + CounterCell）。

## 7. LinkedHashMap 与手写 LRU

### 7.1 核心原理
`LinkedHashMap extends HashMap`，节点扩展 `before/after` 双向指针，维护一条独立的双向链表（HashMap 预留的 `afterNodeAccess`/`afterNodeInsertion` 钩子在 LinkedHashMap 中被重写）。

| 模式 | `accessOrder` | 链表顺序 | 用途 |
| --- | --- | --- | --- |
| 插入序（默认） | false | 按插入顺序 | 顺序敏感的迭代 |
| 访问序 | true | 每次 get/put 后移到尾部 | LRU 缓存 |

```java
public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    public LruCache(int capacity) {
        super(capacity, 0.75f, true);      // accessOrder = true
        this.capacity = capacity;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;          // 插入后判断，超过则删链表头（最老）
    }
}
```
`LinkedHashSet` 是 `LinkedHashMap` 的包装（value 为常量 `PRESENT`）。

### 7.2 面试问答
**Q1：为什么 LinkedHashMap 能保证顺序？** A：重写 HashMap 的钩子方法，在 before/after 指针上维护顺序（HashMap 中这些钩子是空实现，为子类扩展预留）。
**Q2：`accessOrder = true` 时 get 的成本？** A：get 会修改链表指针（`afterNodeAccess`），**破坏只读语义**，所以并发读也不安全，且 get 会改 `modCount`，遍历期间 get 可能触发 CME。
**Q3：不继承怎么实现 LRU？** A：`HashMap` + 自维护双向链表（head/tail），即 LeetCode 146 的标准写法，get/put 均 O(1)，删除时 map 与链表两处同步。
**Q4：生产环境 LRU 用什么？** A：Caffeine（W-TinyLFU，命中率优于 LRU，Spring Cache 默认）、Guava Cache；Redis 用 `allkeys-lru`/`allkeys-lfu`（见 [Redis 高可用与缓存治理](../02-数据库/05-Redis高可用与缓存治理.md)）。纯 LRU 的缺陷是偶发批量扫描会冲掉热点。

### 7.3 高频追问与陷阱
- 陷阱：`removeEldestEntry` 里的 `size()` 是插入后的值，条件写 `> capacity`。
- 陷阱：`super(capacity, 0.75f, true)` 的初始容量过小会触发 resize，放大并发不安全性。
- 错误回答："LinkedHashMap 是线程安全的 LRU"。

### 7.5 一句话速记
- LinkedHashMap = HashMap + 双向链表；`accessOrder=true` + `removeEldestEntry` 即 LRU。
- 手写 LRU = HashMap 存节点 + 双向链表维护顺序；生产用 Caffeine。

## 8. TreeMap 与 HashSet 的关系

### 8.1 核心原理
`TreeMap` 用红黑树实现，`get/put/remove` 均 O(log n)，key 有序（自然序或 Comparator）。红黑树五条性质：根黑、叶（NIL）黑、红节点子节点必黑、任意节点到其所有叶子路径黑节点数相同、节点非红即黑；最长路径 ≤ 最短路径 2 倍，近似平衡。

常用 API：`firstKey/lastKey`、`floorKey/ceilingKey`（≤ / ≥）、`higherKey/lowerKey`（< / >）、`subMap/headMap/tailMap`（**都是视图**）、`descendingMap`。

`HashSet` 内部就是一个 `HashMap`（元素作 key，value 是静态常量 `PRESENT`），`add` 返回 `map.put(e, PRESENT) == null`；`TreeSet` 包装 `TreeMap`。

### 8.2 面试问答
**Q1：HashSet 怎么去重？** A：基于 `hashCode + equals`（TreeSet 基于 `compareTo`）；两个逻辑相等但 hashCode 不同的对象会被当成两个元素。
**Q2：怎么实现范围查询？** A：用 `TreeMap.subMap/floorKey`，或 Redis ZSet（分布式）；纯 HashMap 无法做范围查询。
**Q3：`subMap` 的返回是视图吗？** A：是，修改子映射影响原映射，结构修改后可能抛 CME。
**Q4：`LinkedHashSet` 与 `HashSet` 与 `TreeSet` 怎么选？** A：只需去重选 HashSet；需插入顺序选 LinkedHashSet；需排序或范围查询选 TreeSet（O(log n) 略慢）。

### 8.3 高频追问与陷阱
- 陷阱：`Map.of`/`Set.of`（JDK 9+）元素顺序不保证（内部随机化以防哈希碰撞攻击），不要依赖迭代顺序。
- 陷阱：`TreeMap` 中 `BigDecimal` 的 `compareTo` 与 `equals` 不一致会造成"看起来重复"的行为差异。
- 错误回答："HashSet 是有序的"。

### 8.5 一句话速记
- TreeMap 红黑树 O(log n) 且 key 有序，支持 floor/ceiling/subMap。
- HashSet = HashMap 的 key 集合；TreeSet 包装 TreeMap。

## 9. Arrays.asList / List.of / subList 的坑

### 9.1 核心原理
| 特性 | `Arrays.asList(arr)` | `List.of(...)`（JDK 9+） |
| --- | --- | --- |
| 底层 | **原数组的视图** | 独立不可变集合 |
| set | 支持（改原数组） | 不支持，抛 `UnsupportedOperationException` |
| add/remove | 抛 `UnsupportedOperationException`（定长） | 抛 `UnsupportedOperationException` |
| null 元素 | 允许 | **不允许**（抛 NPE） |
| 与原数组 | 双向影响 | 无关联 |

```java
String[] arr = {"a", "b"};
List<String> l = Arrays.asList(arr);
arr[0] = "z";                     // l 变为 [z, b]
List<String> copy = new ArrayList<>(Arrays.asList(arr));   // 可变副本
int size = Arrays.asList(new int[]{1, 2, 3}).size();       // 1！得到 List<int[]>，需 stream().boxed()
```
数组转 List 的正确姿势：`Arrays.stream(arr).boxed().collect(Collectors.toList())`；List 转数组：`list.toArray(new String[0])`（JDK 11+ 推荐 `list.toArray(String[]::new)`），不要 `(String[]) list.toArray()`（返回 Object[] 导致 CCE）。

### 9.2 面试问答
**Q1：为什么 `Arrays.asList` 不能 add？** A：返回 `java.util.Arrays$ArrayList` 内部类，底层是定长数组视图，只能 set 与原数组共享修改。
**Q2：`Collections.unmodifiableList` 与 `List.of` 的区别？** A：前者是视图（原集合变化可见），后者是独立不可变集合；要真正不可变且带防护用 `List.copyOf`（JDK 10+）或 Guava `ImmutableList`。
**Q3：`Arrays.asList(int[])` 为什么 size 是 1？** A：基本类型数组不会自动装箱成 `Integer[]`，整个数组被当作单个元素。
**Q4：不可变集合的取舍？** A：适合常量集合、方法返回值（防调用方修改），且线程安全可共享；代价是每次修改需新建。

### 9.3 高频追问与陷阱
- 陷阱：`List.of(1, null)` 直接 NPE，与 `Arrays.asList` 行为不同。
- 陷阱：`subList` 持有父列表引用，长期持有大列表的子视图会造成内存泄漏。
- 错误回答："`Arrays.asList` 返回的就是 ArrayList"。

### 9.5 一句话速记
- `Arrays.asList` 是定长视图（可 set、连原数组、允许 null）；`List.of` 不可变、禁 null、无关联。
- `asList(new int[]{...})` 的 size 是 1，必须 `boxed()`。

## 10. Queue 家族与 BlockingQueue 选型

### 10.1 核心原理
Queue 两套方法：抛异常版本 `add/remove/element`，返回特殊值版本 `offer/poll/peek`；`BlockingQueue` 增加阻塞版本 `put/take` 与超时版本 `offer(e,timeout,unit)`、`poll(timeout,unit)`。

| 实现 | 结构 | 容量 | 有序性 | 适用场景 |
| --- | --- | --- | --- | --- |
| `ArrayDeque` | 循环数组（2 的幂，2 倍扩容） | 可扩容 | FIFO/栈 | 单线程队列或栈首选，禁止 null |
| `LinkedList` | 双向链表 | 无界 | FIFO | 需 null 元素时 |
| `PriorityQueue` | 二叉小顶堆（数组） | 可扩容 | 优先级 | 定时任务、Top-K |
| `ConcurrentLinkedQueue` | 链表 + CAS | 无界 | FIFO | 高并发无界队列（注意 OOM） |
| `ArrayBlockingQueue` | 数组 | **有界，必须指定** | FIFO | 线程池有界队列首选，单锁 |
| `LinkedBlockingQueue` | 链表 | 默认 `Integer.MAX_VALUE`（伪无界） | FIFO | 线程池默认队列（**内存溢出风险**），双锁 |
| `LinkedBlockingDeque` | 双向链表 | 可指定 | 双端 | 工作窃取式任务 |
| `PriorityBlockingQueue` | 堆 | 无界 | 优先级 | 带优先级任务调度 |
| `SynchronousQueue` | 无容量（配对交接） | 0 | — | `newCachedThreadPool` |
| `DelayQueue` | `PriorityQueue` + 延迟 | 无界 | 按到期时间 | 订单超时、缓存过期、重试退避 |
| `LinkedTransferQueue` | 链表 | 无界 | FIFO | `transfer()` 直接交给消费者 |

`DelayQueue` 元素须实现 `Delayed`（`getDelay` + `compareTo`），队首未到期时 `take` 用 `Condition.awaitNanos` 精确等待。

### 10.2 面试问答
**Q1：为什么线程池用 `LinkedBlockingQueue` 有风险？** A：默认容量 `Integer.MAX_VALUE`（伪无界），生产建议 `new ArrayBlockingQueue<>(capacity)`。
**Q2：`SynchronousQueue` 的特点？** A：不存储元素，`put` 必须等 `take` 配对交接，支持公平/非公平；配合无限线程池实现"来一个任务开一个线程"。
**Q3：`PriorityQueue` 的迭代顺序有序吗？** A：不保证，是堆的层序遍历，只有 `poll` 才按优先级出队。
**Q4：怎么实现延迟任务？** A：单机用 `DelayQueue` 或 `ScheduledThreadPoolExecutor`；分布式用时间轮（Netty `HashedWheelTimer`）、MQ 延迟消息（见 [消息队列与 RocketMQ](../04-中间件/01-消息队列与RocketMQ.md)）、Redis ZSet 轮询。
**Q5：`ConcurrentLinkedQueue.size()` 为什么慢？** A：需要遍历统计 O(n)，并发下还可能不准，建议用 `isEmpty()`。

### 10.3 高频追问与陷阱
- 陷阱：`ArrayDeque` 禁止 null，`LinkedList` 允许；用错会 NPE。
- 陷阱：`PriorityQueue.remove(Object)` 是 O(n)，只有 offer/poll 是 O(log n)。
- 错误回答："`LinkedBlockingQueue` 有界"（默认无界，须显式指定容量）。

### 10.4 代码/配置示例
```java
DelayQueue<Retry> dq = new DelayQueue<>();        // Retry 实现 Delayed
dq.put(new Retry("order-1", now + 30_000));      // take() 阻塞到最早元素到期
```

### 10.5 一句话速记
- 抛异常组：add/remove/element；特殊值组：offer/poll/peek。
- 有界优先 `ArrayBlockingQueue`；`LinkedBlockingQueue` 默认无界；`SynchronousQueue` 零容量；`DelayQueue` 延迟。

## 11. 集合选型与内存占用

### 11.1 核心原理
| 需求 | 首选 | 理由 |
| --- | --- | --- |
| 通用列表 | `ArrayList` | 连续内存、随机访问 O(1) |
| 频繁头尾/栈 | `ArrayDeque` | 快且省内存 |
| 去重 | `HashSet` | 平均 O(1) |
| 去重且有序 | `LinkedHashSet` / `TreeSet` | 插入序 / 排序 |
| 通用 Map | `HashMap` | 平均 O(1) |
| LRU / 顺序敏感 | `LinkedHashMap(accessOrder=true)` | 内建淘汰钩子 |
| 范围查询 | `TreeMap` | O(log n) + floor/ceiling |
| 读多写极少并发 | `CopyOnWriteArrayList` | 读无锁 |
| 高并发读写 | `ConcurrentHashMap` | 桶级锁 |
| 高并发计数 | `ConcurrentHashMap` + `LongAdder` | 减少 CAS 冲突 |
| 生产者消费者 | `BlockingQueue` | 阻塞语义内建 |

内存占用（64 位压缩指针粗略估算）：`ArrayList` 引用 4B/元素 + 数组头 16B + 最多 50% 冗余容量；`HashMap` 每条目约 32B（Node 头 12B + hash/key/value/next 各 4B + 对齐）加 table 每桶 4B，**小 Map 的开销比例极高**（装 3 个元素也占 16 桶的数组）。装箱差距巨大：`int[]` 4B/元素，`Integer[]` 约 16B 对象 + 4B 引用。

### 11.2 面试问答
**Q1：1 万个元素怎么选初始容量？** A：`HashMap` 用 `10000/0.75+1 ≈ 13334`（实际提升到 16384 避免扩容）；`ArrayList` 用 `new ArrayList<>(10000)`。
**Q2：怎么减少 Map 内存占用？** A：预估容量、key 用紧凑类型、超大 key 场景换原始类型集合（fastutil、Eclipse Collections）避免装箱。
**Q3：遍历 Map 的推荐方式？** A：需要 k/v 用 `entrySet()` 一次遍历；需删除或更新用 `forEach`/`computeIfPresent`/`removeIf`；避免 `keySet()` + `get(k)`（两次查找）。
**Q4：返回空集合用哪个？** A：`Collections.emptyList()` 或 `List.of()`（单例、零分配、不可变，调用方误改会立即暴露）。

### 11.3 高频追问与陷阱
- 陷阱：依赖 HashMap 迭代顺序的代码是 bug（跨 JDK 版本顺序不同）。
- 陷阱：修改 HashSet 中元素的参与 hash 的字段后，该元素"找不到"（无法 remove）。
- 错误回答："堆越大集合就越省内存"；"HashMap 遍历有序"。

### 11.5 一句话速记
- 默认 ArrayList + HashMap；顺序/排序/LRU 分别用 LinkedHashMap、TreeMap、LinkedHashMap。
- HashMap 约 32B/条目；原始类型集合能省 4~5 倍内存；依赖 HashMap 顺序即 bug。

## 自测题（含答案要点）

1. ArrayList 默认容量与首次分配时机？— 10；JDK 8 起懒初始化，第一次 add。
2. 扩容公式与系数？— `old + (old >> 1)`，1.5 倍，不足 minCapacity 时取其值。
3. fail-fast 的原理？— `modCount` 与迭代器持有的 `expectedModCount` 不一致即抛 CME，单线程也会触发。
4. 遍历中删除元素的正确方式？— `Iterator.remove()`、`removeIf`、倒序索引删除。
5. CopyOnWriteArrayList 的写流程？— 加锁 → 复制新数组 → 新数组写入 → `setArray` 发布；读无锁读 volatile 引用。
6. HashMap 扰动函数的作用？— `h ^ (h >>> 16)` 让高位参与 `(n-1)&hash` 的下标计算，降低碰撞。
7. 容量为什么必须是 2 的幂？— 位运算取模更快；扩容后元素只有两个可能位置；无需重算 hash。
8. 负载因子 0.75 的依据？— 空间与冲突折中；配合泊松分布使链表长 8 的概率约 6e-8。
9. 树化与退化阈值？为什么不对称？— 8 且容量 ≥ 64 树化；≤ 6 退化；留缓冲避免边界反复转换。
10. resize 如何重新分布元素？— `(hash & oldCap) == 0` 留原位 j，否则移到 j + oldCap，lo/hi 两条链完成。
11. JDK 7 并发扩容死循环的原因？— 头插法反转链表 + 并发 transfer 形成环，get 时死循环。
12. JDK 8 HashMap 并发 put 仍有哪些问题？— 同桶覆盖、size 丢失更新、扩容期间写入旧 table 丢数据。
13. CHM JDK 7 与 JDK 8 的核心差别？— 分段锁（16 段）→ CAS + synchronized 锁桶首节点 + 红黑树 + 协助扩容。
14. CHM 的 get 为什么无锁？— table/val/next 为 volatile；节点插入后不移动；扩容用 ForwardingNode 标记旧桶。
15. CHM 的 size 能精确判断吗？— 不能，baseCount + CounterCell 累加为弱一致估计值。
16. `computeIfAbsent` 的注意事项？— 函数须幂等无副作用；勿在函数内递归改同一 map；返回 null 不写入。
17. 手写 LRU 的关键构造与钩子？— `super(capacity, 0.75f, true)` + 重写 `removeEldestEntry` 返回 `size() > capacity`。
18. `Arrays.asList("a","b").add("c")` 会怎样？`Arrays.asList(new int[]{1,2,3}).size()` 是多少？— 前者抛 `UnsupportedOperationException`（定长视图）；后者为 1，元素是整个 int[]，需 `boxed()`。
19. LinkedList 与 ArrayList 的选型结论？— 默认 ArrayList；队列/栈用 ArrayDeque；LinkedList 优势场景有限。
20. 场景：`Set<User>` 加了 100 个用户实际只剩 60 个，为什么？服务 GC 频繁且老年代持续上涨怎么验证缓存泄漏？— 前者是 User 未重写 equals/hashCode；后者用 `jstat -gc` 看回收后老年代是否下降，dump + MAT 支配树找持有链。

## 背诵卡片

1. ArrayList 默认 10、懒初始化；扩容 1.5 倍 `old + (old >> 1)`。
2. `Arrays.copyOf` 是浅拷贝，只复制引用。
3. `modCount != expectedModCount` → CME；删除用 `Iterator.remove`/`removeIf`。
4. `remove(int)` 删下标，`remove(Object)` 删值，注意装箱歧义。
5. LinkedList 是双向链表且实现 Deque；随机访问 O(n)。
6. 头尾操作优先 `ArrayDeque`，通常快于 LinkedList。
7. COW：写加锁复制、读无锁、迭代弱一致、迭代器不支持修改。
8. COW 只适合读多写极少，写频繁会内存翻倍 + 频繁 GC。
9. HashMap = 数组 + 链表 + 红黑树（JDK 8）。
10. 扰动：`h ^ (h >>> 16)`；下标 `(n-1) & hash`。
11. 容量 2 的幂：位运算取模、扩容只挪一半、无需重算 hash。
12. 负载因子 0.75；链表长 8 的概率约 6e-8（泊松）。
13. 树化：链表 ≥ 8 且容量 ≥ 64；退化 ≤ 6。
14. 默认容量 16、阈值 12；`tableSizeFor` 向上取 2 的幂。
15. JDK 8 尾插，JDK 7 头插（并发死循环）。
16. resize 拆分：`(hash & oldCap) == 0` 留原位，否则 + oldCap。
17. HashMap 允许一个 null key，hash 计 0 落桶 0。
18. HashMap 线程不安全：丢数据、size 错、扩容丢写。
19. CHM JDK 7：Segment 分段锁，默认 16 段。
20. CHM JDK 8：CAS 写空桶 + synchronized 锁桶头 + 红黑树。
21. CHM get 无锁：volatile + ForwardingNode（hash = MOVED = -1）。
22. CHM 计数：baseCount + CounterCell 数组，size 弱一致。
23. CHM 协助扩容：transferIndex 分段抢任务。
24. CHM 与 Hashtable 都禁止 null key/value。
25. `computeIfAbsent` 的函数要幂等，勿递归改同一 map。
26. CHM 迭代器弱一致，不抛 CME。
27. LinkedHashMap：`accessOrder=true` + `removeEldestEntry` = LRU。
28. 手写 LRU = HashMap + 双向链表，get/put 均 O(1)。
29. TreeMap 红黑树 O(log n)，支持 floor/ceiling/subMap 视图。
30. HashSet 就是 HashMap 的 key 集合，value 是常量 PRESENT。
31. TreeSet/TreeMap 去重靠 `compareTo == 0`，不是 equals。
32. `Arrays.asList` 是定长视图，set 会改原数组，add 抛异常。
33. `List.of` 不可变、禁 null、与原数组无关。
34. `int[]` 用 `Arrays.asList` 得到 size=1 的 `List<int[]>`。
35. `new ArrayList<>(Arrays.asList(a))` 才得到可变副本。
36. `Collections.unmodifiableList` 是视图，原集合仍可改；`subList` 同理且持有父引用易泄漏。
37. Queue：add/remove/element 抛异常；offer/poll/peek 返回特殊值。
38. 有界队列优先 `ArrayBlockingQueue`；`LinkedBlockingQueue` 默认无界；`DelayQueue` 按到期时间出队，`PriorityQueue` 迭代无序。
