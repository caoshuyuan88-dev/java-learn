## 0. 知识地图

## 0.1 先建立三个判断维度

遇到并发问题，不要先问“应该用哪把锁”，而应按下面三个问题定位：

1. **可见性**：一个线程写入的数据，另一个线程能否及时看到？
2. **原子性**：一个业务操作执行过程中，是否可能被其他线程插入或覆盖？
3. **有序性**：编译器、CPU 或 JIT 重排后，是否可能让其他线程观察到不符合预期的顺序？

工具的对应关系可以先这样记：

| 问题 | 常见工具 | 能解决什么 |
| --- | --- | --- |
| 独立状态发布 | `volatile` | 可见性、有序性 |
| 复合读改写 | `synchronized`、`Lock`、CAS 循环 | 原子性，并建立可见性 |
| 多线程计数 | `AtomicLong`、`LongAdder` | 原子更新；后者适合高竞争统计 |
| 任务并发限制 | `Semaphore`、有界线程池 | 限制资源并发，不等同于数据互斥 |
| 线程间传递结果 | `Future`、`CompletableFuture`、队列 | 等待、组合和异常传播 |

例如，`volatile` 能让 `stop` 标志及时可见，但不能保护 `count++`；`Semaphore` 能限制同时访问数据库的线程数，但不能保证两个线程修改同一订单时互斥。

### 0.2 先用一个生活例子理解并发

假设两名员工同时处理同一张订单：

- **可见性**：员工 A 改了订单状态，员工 B 能不能看到最新状态？
- **原子性**：库存只剩 1 件时，两个员工同时扣库存，会不会都认为自己扣成功？
- **有序性**：A 先填写“已付款”，再填写“已发货”；B 看到“已发货”时，能不能保证也看到“已付款”？

Java 中的普通共享变量，就像放在员工各自桌面上的工作副本。没有同步措施时，一个员工修改后的内容可能还没有及时同步给另一个员工。锁像“同一把办公室钥匙”，同一时间只有拿到钥匙的人可以修改；`volatile` 更像“公共公告栏”，适合发布一个简单状态，但不能把“读取、计算、写回”三步合成一个不可打断的动作。

因此可以先记住：

```text
volatile：告诉别人“最新状态是什么”
锁/CAS：保证“这件事只能完整地做一次”
线程池：控制“同时允许多少人干活”
```

## 1. JMM、happens-before 与重排序

### 1.1 核心原理
JMM（Java Memory Model，Java 内存模型）不是一块真的叫“主内存”的硬件，也不是让所有线程排队执行。它更像一套**并发交通规则**：规定一个线程修改的数据，什么条件下另一个线程必须看到；还规定哪些代码顺序不能被编译器或 CPU 改乱。

为什么需要这套规则？因为多线程运行时，每个 CPU 核心可能有自己的缓存，编译器和 CPU 也会为了性能调整指令顺序。单线程看起来正确的代码，放到多个线程中，如果没有同步关系，就可能出现：

- 一个线程一直看不到另一个线程的新值；
- 两个线程同时修改，后写入的结果覆盖前面的结果；
- 另一个线程看到“后一步已经完成”，却没看到“前一步的数据”。

学习 JMM 时可以把“线程工作内存”理解成线程手里的临时副本，把共享变量理解成大家共同使用的数据。这个类比有助于理解可见性，但不要把它机械地等同于某一级 CPU 缓存。

下面这个停止标志就可能无法可靠停止：

```java
class Worker implements Runnable {
    private boolean running = true;

    @Override
    public void run() {
        while (running) {
            doWork();
        }
    }

    void stop() {
        running = false;
    }
}
```

改为 `private volatile boolean running` 后，写入和后续读取之间建立了可见性关系。若循环还要更新共享统计值，则需要另外的原子工具或锁。

**happens-before 八条**：① 程序顺序（同线程内前 hb 后）；② 监视器锁（unlock hb 后续同一锁 lock）；③ volatile（写 hb 后续读）；④ 线程启动（`start()` hb 新线程全部操作）；⑤ 线程终止（线程内操作 hb 其他线程 `join()` 返回）；⑥ 中断（`interrupt()` hb 检测到中断）；⑦ 对象终结（构造器结束 hb `finalize()` 开始）；⑧ 传递性。

#### happens-before 到底是什么：给线程之间“盖章”

`happens-before`（简称 hb）可以理解为线程之间的一枚“同步印章”。

如果操作 A happens-before 操作 B，表示 Java 允许 B 开始依赖 A 的结果，并且保证：

1. A 的结果对 B 可见；
2. 在允许的程序观察中，A 的效果不能被重排到 B 之后；
3. 它不要求 A 和 B 在真实时间上紧邻，也不要求两个线程停止并排执行。

最简单的记法是：

```text
A 做完并盖章
→ B 看到这枚章
→ B 可以依赖 A 的结果
```

可以把它理解成一条“同步边”：

```text
线程 A：写入共享数据 → 解锁
                         │ happens-before
线程 B：加锁           → 读取共享数据
```

示例：

```java
class MessageBox {
    private String message;

    void publish(String value) {
        synchronized (this) {
            message = value;
        }
    }

    String read() {
        synchronized (this) {
            return message;
        }
    }
}
```

当线程 A 执行完 `publish` 中的解锁，线程 B 随后成功获取同一个对象的锁时，A 对 `message` 的写入对 B 可见。

用人话说就是：

```text
A：拿钥匙 → 修改订单 → 放回钥匙
B：拿到同一把钥匙 → 读取订单
```

B 拿到钥匙这一刻，就意味着 B 可以看到 A 在放钥匙之前完成的修改。关键不是“B 一定在 A 之后启动”，而是两人使用了同一把锁。

volatile 也可以建立同类关系：

```java
class Config {
    private int port;
    private volatile boolean ready;

    void init() {
        port = 8080;
        ready = true; // volatile 写
    }

    int port() {
        if (ready) {  // volatile 读
            return port; // 能看到 init 中对 port 的写入
        }
        return -1;
    }
}
```

线程 B 读到 `ready == true` 时，线程 A 在 volatile 写之前对 `port` 的写入也对 B 可见。

可以把 `ready` 想成“公告栏上的完成通知”：

```text
A：先把 port 配好 → 最后在公告栏写 ready = true
B：先看到 ready = true → 再读取 port
```

这个模式成立的前提是：先写普通字段，最后写 volatile 标志；读取方先读 volatile 标志，再读普通字段。

没有 hb 关系时，即使代码在单线程下看起来顺序正确，另一个线程也不能依赖它观察到同样的顺序：

```java
data = new byte[1024];
ready = true; // 如果 ready 不是 volatile，也没有锁或其它同步
```

另一个线程可能看不到最新的 `ready`，也不能依赖它在看到 `ready` 后一定能看到完整的 `data`。因此，“代码写在前面”不等于“另一个线程一定先看到”。

最后再强调一次：happens-before 不是“时间先后证明”，而是“同步保证”。它不负责让线程排队，只负责在存在同步关系时，让后续线程能可靠地看到前面线程应该发布的结果。

hb 只保证可见性与顺序性，**不要求串行**：不违反 hb 与单线程语义（as-if-serial）时编译器与 CPU 可任意重排序。重排序三类：编译器、指令级并行、内存系统。

不要把 hb 记成“前一个方法返回后，后一个线程才开始执行”。它表达的是一种可见性与排序约束。例如 `unlock` happens-before 后续对同一把锁的 `lock`，但两个线程仍可能在其它代码上并行执行。

安全发布的常见方式包括：

- 在静态初始化器中创建对象；
- 正确初始化的 `final` 字段；
- 通过 `volatile` 引用发布；
- 通过锁、并发容器、线程启动或 `Future` 传递；
- 不把未完成构造的 `this` 发布给其它线程。

只把对象引用保存到普通共享字段，不代表对象内部状态已经安全发布。

### 1.2 面试问答
**Q1：为什么需要 JMM？** A：多核 CPU 有缓存、写缓冲与乱序执行，直接暴露硬件模型无法写出可移植的并发代码；JMM 用 hb 规则标准化被禁止的重排序。
**Q2：同线程内 `x=1; y=x;` 会读到 y=0 吗？** A：不会，程序顺序规则 + as-if-serial 保证单线程语义不变。
**Q3：`i++` 原子吗？** A：不原子，编译为 getfield/iadd/putfield 三步，并发丢失更新；用 AtomicInteger、LongAdder 或锁。
**Q4：hb 与原子性的关系？** A：hb 不含原子性；`volatile i++` 仍不安全，可见性不能替代互斥。

### 1.3 高频追问与陷阱
- 陷阱：非 volatile 的 `long`/`double` 读写在部分平台会拆成两次 32 位操作，可能非原子。
- 陷阱：hb 不是"操作已执行完"，只是可见性与顺序约束。
- 陷阱：`volatile` 只保护同一个变量的读写，不能自动保护由多个变量组成的不变量。
- 错误回答："volatile 变量的所有操作都是原子的"。

### 1.4 用一个反例区分三种性质

```java
volatile int count;

count++; // 仍然不是原子操作
```

它实际包含：

```text
读取 count
→ 加 1
→ 写回 count
```

两个线程都可能先读到 0，然后分别写回 1，最终结果为 1 而不是 2。`volatile` 保证每次读写具有可见性和顺序约束，但没有把三个步骤合并成一个不可分割操作。

如果只需要递增统计，可以使用：

```java
AtomicInteger count = new AtomicInteger();
count.incrementAndGet();
```

如果只关心高并发统计结果、允许读取期间存在并发变化，可以使用 `LongAdder`；如果需要精确的当前值或序列号，优先使用 `AtomicLong`。

### 1.5 一句话速记
- hb 核心：程序顺序、锁、volatile、start、join（+中断、终结、传递）。
- hb 保证可见性与有序性，不保证原子性，也不等于串行执行。

## 2. volatile 与内存屏障

### 2.1 核心原理
`volatile` 是 Java 提供的一个轻量级“状态发布工具”。它最适合这样的场景：

```text
一个线程负责改变状态
其它线程只负责观察状态
```

例如“任务是否停止”“配置是否加载完成”“服务是否启动完毕”。把字段声明为 `volatile` 后，Java 会保证其它线程读取这个字段时，不会长期停留在旧值上，并且相关的读写顺序不会被随意打乱。

它有三个核心作用：

1. **可见性**：一个线程写入后，其它线程读取时能看到新值；
2. **有序性**：volatile 写之前的相关操作，不能被随意挪到 volatile 写之后；
3. **不保证复合操作原子性**：`i++` 仍然是读、改、写三步，多个线程仍可能互相覆盖。

不要把“写立即刷主内存”理解成某个固定硬件动作。更准确的说法是：对同一个 volatile 变量的写入与后续读取之间，JMM 建立了可见性和顺序约束。

| 屏障 | 作用 |
| --- | --- |
| LoadLoad | 禁读读重排 |
| StoreStore | 禁写写重排 |
| LoadStore | 禁读写重排 |
| StoreLoad | 禁写读重排（最贵，x86 用 `lock` 前缀实现） |

在抽象层面，volatile 写需要保证写之前的普通写不能被重排到 volatile 写之后，volatile 读之后的普通读写不能被重排到 volatile 读之前。具体屏障指令由 JVM、CPU 架构和 JIT 决定，不应把 `StoreStore + 写 + StoreLoad` 当成所有平台都完全相同的机器指令序列。x86 内存模型较强，但 Java 程序仍应按 JMM 规则编写，不能依赖 x86 的“看起来正常”。

**DCL 单例必须加 volatile**：`new` 被拆成"分配内存 → 执行 `<init>` → 写引用"，重排后另一线程在第一次检查看到非 null 就返回**半初始化对象**；volatile 禁止该重排。更优写法是静态内部类 holder 或枚举单例。
```java
private static volatile Singleton instance;      // volatile 不可省略
if (instance == null) { synchronized (Singleton.class) { if (instance == null) instance = new Singleton(); } }
```

#### 为什么已经有锁，还需要 volatile

关键在于这段代码有**两次检查**：

```java
if (instance == null) {       // 第一次检查：锁外
    synchronized (Singleton.class) {
        if (instance == null) { // 第二次检查：锁内
            instance = new Singleton();
        }
    }
}
return instance;
```

锁只保护进入 `synchronized` 代码块的线程。第一次检查和最后的 `return instance` 都可能在锁外执行，因此锁不能自动保证所有线程在锁外读取 `instance` 时看到最新值。

`volatile` 在这里解决两个问题：

1. **保证可见性**：线程 A 创建并写入 `instance` 后，线程 B 在锁外第一次检查时能看到最新引用，而不是继续看到 `null`；
2. **禁止不安全发布**：`new Singleton()` 可以抽象成：

   ```text
   分配内存
   → 执行构造器
   → 把引用赋给 instance
   ```

   没有 volatile 时，JIT/CPU 可能让“把引用赋给 instance”在观察效果上先于构造器完成。线程 B 如果看到 `instance != null`，可能直接返回一个还没有完全初始化的对象。volatile 保证引用发布时，构造器之前的写入对后续读取可见。

锁和 volatile 的职责不同：

```text
synchronized：保护锁内的代码，同一时间只允许一个线程进入
volatile：保证这个字段的读写可见，并约束相关重排序
```

如果把所有读取也放进同一把锁中，确实可以不使用 volatile：

```java
static Singleton getInstance() {
    synchronized (Singleton.class) {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
```

但这种写法每次获取单例都要竞争锁。DCL 的目的正是让初始化完成后，大多数读取走锁外快速路径；既然存在锁外读取，就需要 `volatile` 保证安全发布。

更容易维护的替代方案是静态内部类：

```java
class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    static Singleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

`Holder` 只有在 `getInstance()` 首次调用时才初始化，类初始化的线程安全由 JVM 保证，不需要手写双重检查锁。

### 2.1.1 什么情况下不要用 volatile

下面几类需求，单独使用 volatile 不够：

```java
volatile int stock = 1;

if (stock > 0) {
    stock--; // 多线程下可能被两个线程同时执行
}
```

原因是“判断库存”和“扣减库存”不是一个整体。此时应使用锁、CAS 循环、数据库原子更新，或重新设计成线程安全的并发结构。

同样，下面的两个字段也不能只靠分别声明 volatile 来保持整体一致：

```java
volatile int min;
volatile int max;
```

如果业务要求 `min <= max` 始终成立，需要用锁保护一次性更新，或者构造一个包含两个字段的不可变对象，再通过一个 volatile 引用整体发布。

一句话判断：

```text
只观察一个简单状态 → 可以考虑 volatile
需要“先判断再修改” → volatile 不够
需要同时修改多个字段 → volatile 不够
```

### 2.2 面试问答
**Q1：volatile 能替代 synchronized 吗？** A：不能，它不解决复合操作的原子性（check-then-act、读-改-写必须用锁或 CAS）。
**Q2：性能如何？** A：读几乎无额外开销；写有 StoreLoad 屏障成本，比普通写慢但远快于锁。
**Q3：哪些场景用 volatile？** A：状态标志位、DCL 单例引用、一次性安全发布、独立观察（统计值）。
**Q4：`volatile int[] arr` 保证元素可见吗？** A：`volatile` 修饰的是数组引用，不是每个元素；它能保证“换了一份数组引用”对其它线程可见，但不能把 `arr[i]++` 变成原子操作。需要原子数组语义时使用 `AtomicIntegerArray`。
**Q5：volatile 能保证多个字段的一致性吗？** A：不能。例如 `min` 和 `max` 必须同时更新时，仅把两个字段都声明为 volatile 仍可能被其它线程观察到中间状态，应使用锁、不可变快照或一次性替换对象引用。

### 2.3 高频追问与陷阱
- 陷阱：不加 volatile 的 DCL 在 x86 上常"看起来正常"，但在 ARM（含 Apple M 系列）会暴露，是偶发 Bug 的典型来源。
- 陷阱：volatile 写密集会因缓存行频繁失效降低性能。
- 错误回答："volatile 让线程串行执行"；"volatile 能代替锁保证原子性"。

### 2.4 一句话速记
- volatile：可见 + 有序（禁重排），不保证原子。
- DCL 的 instance 必须 volatile；更推荐静态 holder 或枚举单例。

## 3. synchronized 与锁升级

### 3.1 核心原理
用法：修饰实例方法（锁 this）、静态方法（锁 Class）、代码块（锁指定对象）。字节码：同步块编译为 `monitorenter`/`monitorexit`（异常路径由编译器补第二个 monitorexit）；同步方法用 `ACC_SYNCHRONIZED` 标志。

#### synchronized 用人话理解

把 `synchronized` 想成一把“只有一个人能拿到的钥匙”：

```java
class Inventory {
    private int stock = 1;

    synchronized boolean sell() {
        if (stock <= 0) {
            return false;
        }
        stock--;
        return true;
    }
}
```

两个线程同时调用 `sell()` 时，只有一个线程能进入方法。它完成“检查库存 + 扣减库存”后，另一个线程才进入，因此不会两个线程都把最后一件商品卖出去。

但锁保护的不是“方法名”，而是**锁对象**：

```java
class Demo {
    synchronized void instanceMethod() {} // 锁 this

    synchronized static void staticMethod() {} // 锁 Demo.class

    void block() {
        synchronized (this) {}              // 锁 this
        synchronized (new Object()) {}      // 每次都是新锁，几乎没有互斥效果
    }
}
```

实例锁和类锁不是同一把锁。两个不同对象的实例方法可以并发执行；静态同步方法锁的是整个类对象，会影响所有实例。

选择锁对象时，推荐使用外部无法拿到的专用对象：

```java
private final Object lock = new Object();

void update() {
    synchronized (lock) {
        // 保护共享状态
    }
}
```

不要用字符串常量、包装类缓存对象或公开对象作为业务锁，否则其它代码可能意外拿到同一把锁，造成无关业务互相阻塞。

| 历史锁状态 | Mark Word（64 位） | 标志位 |
| --- | --- | --- |
| 无锁 | hashCode + age + 0 | 01 |
| 偏向锁 | 线程 ID + epoch + age + 1 | 01 |
| 轻量级锁 | 指向栈中 Lock Record 的指针 | 00 |
| 重量级锁 | 指向 ObjectMonitor 的指针 | 10 |

#### 锁状态到底是怎样流转的？

面试中常说的“锁升级”，主要是 **JDK 14 及更早 HotSpot 实现中的优化模型**（JDK 8 最常作为教材版本）。它想解决的问题很朴素：

```text
没人竞争时，不要付出太多成本；
只有竞争越来越激烈时，才使用更重的阻塞和唤醒机制。
```

可以先记住这条历史主线：

```text
无锁
  │ 第一次进入 synchronized
  ▼
偏向锁
  │ 出现第二个线程竞争，需要撤销偏向
  ▼
轻量级锁
  │ CAS 重试失败、竞争持续或自旋不划算
  ▼
重量级锁（ObjectMonitor）
```

这条箭头描述的是一种**典型的优化方向**，不是 Java 语言规范要求的固定流程。下面按历史 HotSpot 模型拆开看。

##### 第 1 步：无锁状态

对象刚创建时，尚未被 `synchronized` 保护。对象头中的 Mark Word 可以保存对象的运行时信息，例如对象哈希码、GC 年龄等。

```java
Object lock = new Object(); // 此时通常还没有因为它产生锁竞争
```

这里的“无锁”不是说对象不能加锁，而是说当前还没有建立锁记录或关联的监视器。

##### 第 2 步：偏向锁——默认相信还是同一个线程

如果一个锁长期只有线程 A 使用，每次进入都执行完整的加锁流程其实很浪费。因此历史 HotSpot 会让对象“偏向”线程 A：

```text
第一次：线程 A 获取锁
后续：仍然是线程 A 获取锁
      只需确认对象仍然偏向 A，通常不需要反复 CAS
```

偏向锁适合“一个线程反复进入同一个临界区、几乎没有竞争”的场景。它不是让多个线程同时进入，而是省略同一线程重复获取锁时的一部分开销。

如果线程 B 也来获取这个对象的锁，B 不能直接使用 A 的偏向。虚拟机需要先确认 A 是否仍在临界区：

```text
线程 B 发现对象偏向线程 A
    ├─ A 已经退出临界区：撤销偏向，允许 B 重新竞争
    └─ A 仍在临界区：撤销偏向，进入更通用的轻量级竞争流程
```

这个过程称为**偏向锁撤销**，可能需要在安全点处理线程状态，因此竞争场景下偏向锁不一定划算。

##### 第 3 步：轻量级锁——在用户态短暂自旋

撤销偏向后，线程会尝试使用轻量级锁。可以把它理解成：

```text
先不要立刻把线程挂起；
大家在 CPU 上短暂试几次；
如果锁很快释放，就直接拿到，避免线程阻塞和唤醒。
```

线程进入同步块时，会在线程栈中创建一条 **Lock Record（锁记录）**，然后通过 CAS 尝试把对象头中的 Mark Word 替换为指向这条锁记录的指针：

```text
对象 Mark Word：
    原来的对象信息
          │ CAS
          ▼
    指向线程栈中 Lock Record
```

如果 CAS 成功，线程获得轻量级锁；如果 CAS 失败，说明有其他线程已经占用或正在竞争。失败线程可能进行自适应自旋：

```text
锁持有时间很短 → 自旋等待，期待马上成功
锁持有时间较长 → 继续自旋只是在浪费 CPU
```

自旋不是无限循环，HotSpot 会根据历史竞争情况调整自旋次数。自旋期间，线程仍然占用 CPU，只是没有进入操作系统阻塞状态。

##### 第 4 步：重量级锁——竞争激烈时进入 ObjectMonitor

当竞争持续、CAS 多次失败，或者虚拟机判断自旋的收益不值得时，锁会膨胀为重量级锁。此时对象头会关联一个 `ObjectMonitor`，竞争线程按照管程规则排队：

```text
线程 A：获得 ObjectMonitor，执行临界区
线程 B：获取失败，进入等待队列
线程 C：获取失败，进入等待队列
线程 A：退出临界区，释放并唤醒/竞争等待线程
线程 B/C：被唤醒后重新竞争，不保证 B 一定先拿到
```

常见的 HotSpot 术语包括：

- `_owner`：当前持有监视器的线程；
- `_EntryList`：等待进入监视器、竞争锁的线程；
- `_WaitSet`：调用 `wait()` 后释放锁、等待条件通知的线程；
- `_count`：可重入次数等相关状态。

要注意：`_EntryList` 中的线程不是“被唤醒后直接获得锁”，而是被唤醒后还要重新竞争；`notify()` 唤醒的是条件等待线程，和普通的锁竞争队列不是一回事。

##### 用一张图记住完整过程

```text
无锁
  │ 线程 A 第一次进入
  ▼
偏向 A
  │ 线程 A 再次进入：快速通过
  │ 线程 B 进入：撤销偏向
  ▼
轻量级锁
  │ CAS 竞争
  ├─ 成功：进入临界区
  ├─ 短暂失败：自旋等待
  └─ 持续失败/竞争激烈：锁膨胀
              ▼
        重量级锁 ObjectMonitor
              │
        失败线程阻塞/排队
```

##### 这是不是“锁越升级越快”？

不是。更准确的说法是：

| 状态 | 适合场景 | 主要代价 |
| --- | --- | --- |
| 无锁 | 尚未竞争 | 没有加锁成本，但也没有互斥保护 |
| 偏向锁（历史实现） | 长期由同一线程使用 | 竞争出现时撤销可能有额外成本 |
| 轻量级锁 | 临界区很短、线程竞争不激烈 | 自旋会消耗 CPU |
| 重量级锁 | 竞争激烈、临界区较长 | 阻塞/唤醒和上下文切换成本较高 |

所以锁升级不是为了让重量级锁更快，而是让虚拟机根据竞争程度选择更合适的实现。锁竞争的根本解决办法仍然是缩短临界区、减少共享状态和降低并发冲突，而不是期待 JVM 自动“升级优化”。

##### 新版本 JDK 必须怎样回答？

回答面试题时最好分两层：

1. **历史模型**：JDK 14 及更早版本常讲无锁、偏向锁、轻量级锁、重量级锁，以及偏向撤销、CAS、自旋和锁膨胀。
2. **现代边界**：偏向锁在 JDK 15 默认禁用（JEP 374），并在 JDK 18 移除。现代 JDK 不能再把偏向锁当成当前运行时一定存在的状态。

因此，不能说“所有 JDK 都严格按照偏向锁 → 轻量级锁 → 重量级锁升级”。更稳妥的面试表述是：

> 这是 HotSpot 历史版本中对 `synchronized` 的一种锁优化模型；偏向锁已经从新版本 HotSpot 移除。Java 代码真正可以依赖的是 `synchronized` 的互斥、可见性、可重入和异常自动释放语义，而不是 Mark Word 的具体位布局或某个锁状态一定出现。

##### JDK 15 以后应该怎样理解锁状态？

简单来说，去掉偏向锁后，可以把现代 JDK 的典型路径记成：

```text
无锁
  │ 线程进入 synchronized，CAS 尝试获取
  ▼
轻量级锁（线程栈中的锁记录/快速路径）
  │ 竞争失败，短暂自旋
  ▼
重量级锁（ObjectMonitor）
  │
线程阻塞、唤醒并重新竞争
```

也就是说，面试中可以直接回答：

> JDK 15 以后默认不再使用偏向锁，典型流程可以理解为“无锁 → 轻量级锁 → 重量级锁”。无竞争或低竞争时优先走 CAS 等快速路径；竞争持续时先自旋，收益不高后再膨胀为 ObjectMonitor。JDK 18 起偏向锁实现被移除，因此不能再把“偏向锁”当作当前 JDK 的正常状态。

需要注意两个细节：

- **JDK 15–17**：偏向锁默认禁用，但仍属于过渡阶段；不要把“默认禁用”和“已经完全移除”混为一谈。
- **JDK 18+**：偏向锁已移除，教材中的“偏向锁撤销”只应作为历史知识理解。

另外，“轻量级锁 → 重量级锁”也不是业务代码可以直接观察或依赖的固定状态机。锁竞争结束后，监视器还可能在合适时机被回收或重新使用，所以面试时说“典型升级路径”比说“永远不可逆”更严谨。

#### 常见锁优化

除了前面讲的锁状态变化，JIT 还可能根据代码运行情况对加锁方式进行优化。下面三种最常被问到。

##### 1. 锁消除：确定没有别人能看到，就不加锁

如果一个锁对象只在当前线程内部使用，其他线程根本拿不到它，那么加锁就没有实际意义。JIT 可以通过**逃逸分析**确认对象没有逃出当前方法或线程后，消除相关的锁操作。

```java
void buildMessage() {
    StringBuffer buffer = new StringBuffer(); // 只在当前方法中使用
    buffer.append("hello");
    buffer.append(" java");
}
```

`StringBuffer` 的方法本身带同步，但如果 `buffer` 没有被返回、保存到共享字段或传给其他线程，JIT 可能判断它不会发生竞争，从而消除不必要的加锁。

注意：锁消除是 JIT 的运行时优化，不是编译器看到 `synchronized` 就无条件删除。只要对象可能逃逸到其他线程，锁仍然必须保留。

##### 2. 锁粗化：多次加锁合并成一次

如果代码在一个循环中反复对同一个对象加锁和解锁，频繁进入和退出临界区可能比业务操作本身还贵。JIT 可能把多次连续的加锁合并成一次：

```java
for (String item : items) {
    synchronized (lock) {
        process(item);
    }
}
```

在确认这样做不会破坏并发语义时，可能优化成：

```java
synchronized (lock) {
    for (String item : items) {
        process(item);
    }
}
```

这样减少了加解锁次数，但也会让锁持有时间变长，其他线程需要等待更久。因此锁粗化并不等于“临界区越大越好”；如果循环中包含耗时操作或不需要共享保护的代码，应该由开发者主动缩小临界区。

##### 3. 自适应自旋：先等一小会儿，避免立即阻塞

轻量级锁竞争时，线程不一定马上进入操作系统阻塞状态，而是先在 CPU 上循环尝试获取锁，这就是自旋：

```text
锁马上释放 → 自旋几次可能直接拿到锁
锁长时间不释放 → 自旋只会白白消耗 CPU
```

“自适应”表示 JVM 不采用固定次数，而是参考过去的竞争结果动态调整：

- 过去经常很快拿到锁：适当多自旋；
- 过去自旋经常失败：少自旋，尽快阻塞；
- 竞争激烈或临界区很长：自旋收益低，更可能膨胀为重量级锁。

自旋适合临界区很短的场景，不适合持锁执行网络请求、磁盘 IO 或长时间计算的场景。自旋期间线程仍然占用 CPU，所以它不是“免费等待”。

| 优化方式 | 核心想法 | 适合情况 | 主要风险 |
| --- | --- | --- | --- |
| 锁消除 | 确认锁对象不会被其他线程看到，直接去掉锁 | 线程私有对象 | 不能误判对象逃逸 |
| 锁粗化 | 多次连续加锁合并为一次 | 短操作密集循环 | 锁持有时间变长 |
| 自适应自旋 | 先短暂占用 CPU 等待，避免阻塞唤醒 | 锁很快释放 | 竞争激烈时浪费 CPU |

这三种优化的目标可以这样记：

```text
能不加锁，就锁消除；
能少加几次，就锁粗化；
锁马上释放，就先自旋。
```

**偏向锁 JDK 15 默认禁用（JEP 374）、JDK 18 移除**。

| 维度 | synchronized | ReentrantLock |
| --- | --- | --- |
| 实现/释放 | JVM 管程 / 自动（异常也释放） | AQS / 必须 finally unlock |
| 公平性 | 只有非公平 | 可选 |
| 中断与超时 | 不支持 | `lockInterruptibly`、`tryLock(timeout)` |
| 条件队列 | 一个 wait/notify | 多个 Condition |

`synchronized` 和 `ReentrantLock` 的核心差异，不是“一个快一个慢”，而是控制能力不同：

- 只需要进入临界区、自动释放锁：优先 `synchronized`；
- 需要超时放弃、响应中断、公平策略或多个等待条件：使用 `ReentrantLock`；
- 使用 `ReentrantLock` 时必须严格遵守 `lock → try → finally unlock`。

### 3.2 面试问答
**Q1：可重入吗？** A：可重入，ObjectMonitor 用 `_owner` + `_count` 记录持有者与重入次数。
**Q2：为什么 JDK 15 弃用偏向锁？** A：撤销需安全点级停顿、代价大；现代应用大量用 JUC，synchronized 多在低竞争短临界区；维护成本高。
**Q3：`wait` 与 `sleep` 的区别？** A：wait 释放锁、须在同步块中、靠 notify/超时唤醒；sleep 不释放锁、到时自动醒。
**Q4：为什么推荐 `notifyAll`？** A：`notify` 随机唤醒一个，若条件不满足会继续等待，可能丢信号。
**Q5：轻量级锁竞争失败后一定立刻升级为重量级锁吗？** A：不一定。线程可能先进行自适应自旋；当竞争持续、自旋收益较低或需要阻塞等待时，才可能发生锁膨胀。
**Q6：重量级锁是不是由 `synchronized` 直接创建的？** A：不能简单这样说。`synchronized` 是语言级同步语义，HotSpot 会根据实现和竞争情况选择内部路径；`ObjectMonitor` 是一种 HotSpot 实现细节。
**Q7：`_EntryList` 和 `_WaitSet` 有什么区别？** A：前者是等待进入监视器、竞争锁的线程，后者是调用 `wait()` 后释放锁、等待条件通知的线程；被 `notify` 唤醒后还要重新竞争锁。

正确的条件等待应围绕共享条件使用同一把锁，并在 `while` 中重新检查：

```java
final Object lock = new Object();
final Queue<String> queue = new ArrayDeque<>();

String take() throws InterruptedException {
    synchronized (lock) {
        while (queue.isEmpty()) {
            lock.wait();
        }
        String value = queue.remove();
        lock.notifyAll();
        return value;
    }
}

void put(String value) {
    synchronized (lock) {
        queue.add(value);
        lock.notifyAll();
    }
}
```

`while` 不是为了“防止 notify 丢失”这么简单，而是因为线程被唤醒后仍需重新竞争锁，条件可能已经被其它线程改变；同时规范允许虚假唤醒。生产代码也可以直接使用 `BlockingQueue`，避免手写等待/通知协议。

### 3.3 高频追问与陷阱
- 陷阱：锁对象用 `Integer`/`String` 常量会因常量池共享导致无关代码互锁，应用专属 `private final Object lock`。
- 陷阱：静态 synchronized 方法与实例 synchronized 方法是两把不同的锁。
- 陷阱：`wait` 必须放在 while 循环里防虚假唤醒；`wait/notify` 须在同步块内调用。
- 错误回答："现代所有 JDK 都会按偏向→轻量→重量升级"（偏向锁已在新版本移除）。

### 3.4 一句话速记
- 历史上常用“偏向 → 轻量级 → 重量级”描述 HotSpot 优化，现代 JDK 不应依赖具体锁状态。
- 优化：锁消除、锁粗化、自适应自旋。

## 4. CAS、Atomic 家族与 LongAdder

### 4.1 核心原理
CAS 是 CPU 原语（x86 的 `cmpxchg` + `lock` 前缀），含内存地址 V、期望值 A、新值 B，仅当 V == A 才写入 B；Java 通过 `Unsafe.compareAndSwapInt` 暴露（JDK 9+ 推荐 `VarHandle`）。

#### CAS 用人话理解

CAS 像“我只在柜台上的号码仍然是 10 时，才把它改成 11”：

```text
当前值仍是我刚才看到的 10？
是 → 改成 11，成功
否 → 有人先改过，失败，重新读取再决定
```

它不把线程挂起，而是失败后重试，所以低竞争时很轻量，高竞争时可能大家都在反复重试。

手写一个 CAS 递增循环可以帮助理解 Atomic 类：

```java
AtomicInteger counter = new AtomicInteger();
int oldValue;
int newValue;
do {
    oldValue = counter.get();
    newValue = oldValue + 1;
} while (!counter.compareAndSet(oldValue, newValue));
```

如果 CAS 失败，说明其它线程已经修改了值，当前线程重新读取并重试。高竞争下，大量线程反复失败会消耗 CPU，因此“无锁”不等于“没有等待”或“没有成本”。

**三大问题**：① **ABA**（A→B→A，CAS 认为未变）→ `AtomicStampedReference`（版本号）或 `AtomicMarkableReference`；② **自旋开销** → LongAdder 分段、退让、限次自旋；③ **只能保证单个变量** → 多变量加锁或封装为 `AtomicReference`。

ABA 可以这样理解：

```text
线程 A 看到 value = A，准备改成 C
线程 B 把 A 改成 B，又改回 A
线程 A 发现现在仍是 A，于是 CAS 成功
```

如果业务只关心最终数值，ABA 可能没有影响；如果业务还关心“期间是否发生过变化”，就需要版本号。

Atomic 家族：`AtomicInteger/Long/Reference`、`AtomicIntegerArray`、`AtomicIntegerFieldUpdater`（字段须 volatile）、`LongAdder/DoubleAdder`。

#### AtomicLong 与 LongAdder：一个柜台还是多个柜台？

两者都能实现线程安全的计数，但解决的问题不同：

```text
AtomicLong：所有线程竞争同一个值，读取直接得到当前值。
LongAdder：把计数分散到多个 Cell，读取时再把各个位置加起来。
```

##### AtomicLong：一个共享值，所有线程竞争同一个 CAS

`AtomicLong` 内部可以先粗略理解为一个 `volatile long`，更新时使用 CAS：

```text
读取当前值 old
计算新值 old + 1
CAS：如果当前值仍然是 old，就改成 old + 1
CAS 失败：重新读取并重试
```

```java
AtomicLong sequence = new AtomicLong();
long id = sequence.incrementAndGet();
long current = sequence.get();
```

所有线程都修改同一个内存位置。低竞争时它简单、直接；高竞争时，很多线程会同时争抢同一个 CAS 位置，失败重试次数增加。

##### LongAdder：分散热点，最后汇总

`LongAdder` 内部可以粗略理解为：

```text
base
cells[0]
cells[1]
cells[2]
...
```

没有明显竞争时更新 `base`；发生竞争后，不同线程尽量分散到不同的 Cell：

```text
线程 A → cells[0] += 1
线程 B → cells[2] += 1
线程 C → cells[1] += 1
```

读取时执行：

```text
sum() = base + cells[0] + cells[1] + cells[2] + ...
```

```java
LongAdder requestCount = new LongAdder();
requestCount.increment();
long total = requestCount.sum();
```

它和 `ConcurrentHashMap` 的计数思路类似，都是通过分散热点降低高并发下的竞争；Cell 还会通过填充尽量避免伪共享。

##### 两者的区别

| 维度 | AtomicLong | LongAdder |
| --- | --- | --- |
| 内部结构 | 一个共享值 | `base + Cell[]` |
| 更新方式 | 所有线程竞争同一个 CAS | 多个线程分散更新 |
| 低并发 | 简单直接 | 优势不明显 |
| 高并发 | CAS 冲突较多 | 统计吞吐量通常更高 |
| 读取 | `get()`，O(1)，当前值明确 | `sum()`，需要汇总多个 Cell |
| 读取语义 | 更适合精确读取 | 弱一致，不是严格瞬时快照 |
| 内存占用 | 较小 | 较大 |
| 典型场景 | 序列号、余额、状态判断 | QPS、访问次数、监控统计 |

`LongAdder.sum()` 期间可能仍有线程更新不同的 Cell，因此它不保证读取结果对应某一个瞬间的绝对值。它适合“最终统计大致准确、写入吞吐优先”的场景，不适合库存、余额或生成唯一序列号。

```text
需要精确的当前值，选 AtomicLong；
只关心高并发累加统计，选 LongAdder。
```

### 4.2 面试问答
**Q1：CAS 是乐观锁吗？** A：是乐观锁思想（无锁 + 失败重试），与数据库 version 更新、Redis WATCH 同源。
**Q2：ABA 一定会出 bug 吗？** A：只在"值不能表达状态全貌"时有害，如无锁栈节点被踢出又重新入栈导致指针错乱；金额自增通常无害。
**Q3：LongAdder 代价是什么？** A：求和需遍历所有 Cell 且弱一致，不能当精确计数器。
**Q4：`@Contended` 的作用？** A：填充到缓存行长度（一般 64B），避免不同 Cell 落在同一缓存行产生伪共享。
**Q5：什么时候选 AtomicLong，什么时候选 LongAdder？** A：需要每次读取都具有较强的精确语义、生成序列号或作为状态判断时选 AtomicLong；只做高并发累加统计、允许 `sum()` 期间存在并发变化时选 LongAdder。LongAdder 不能直接替代 AtomicLong。

### 4.3 高频追问与陷阱
- 陷阱：`AtomicIntegerFieldUpdater` 要求字段 volatile 且不能 private/static/final。
- 陷阱：CAS 失败重试有 CPU 与内存屏障开销，并非零成本。
- 错误回答："CAS 没有锁所以没有并发开销"。

### 4.4 一句话速记
- CAS 三值 V/A/B，CPU 原语；问题 = ABA、自旋开销、仅单变量。
- 高并发统计用 `LongAdder`；需要精确读才用 `AtomicLong`。

## 5. AQS 与 ReentrantLock

### 5.1 核心原理
AQS（AbstractQueuedSynchronizer）不是一把锁，而是一个为同步器提供排队、阻塞和唤醒模板的框架。核心可以分成三部分：

1. **`volatile int state`**：在 `ReentrantLock` 中表示持有状态/重入次数，在 `CountDownLatch` 中表示剩余计数，在 `Semaphore` 中表示可用许可数；
2. **CLH 变体双向同步队列**：获取失败的线程进入队列，通过 `LockSupport.park/unpark` 挂起和唤醒；
3. **Condition 条件队列**：等待条件的线程暂时离开同步队列，`signal` 后再转回同步队列竞争锁。

子类只需要定义“如何尝试获取”和“如何释放”：独占模式实现 `tryAcquire/tryRelease`，共享模式实现 `tryAcquireShared/tryReleaseShared`。因此 ReentrantLock、CountDownLatch、Semaphore 的排队机制相似，但 `state` 的业务含义不同。

#### AQS 用人话理解

AQS 可以理解成“排队取号系统”：

1. 线程先尝试直接办理；
2. 办不了，就把自己放进等待队列；
3. 不一直占用 CPU 空转，而是暂时 `park` 休息；
4. 前面的线程释放资源后，唤醒后继线程；
5. 被唤醒的线程还要重新竞争，不能认为被唤醒就一定拿到锁。

`ReentrantLock` 是独占办理窗口；`CountDownLatch` 是等柜台上的计数归零；`Semaphore` 是有限数量的入场券。它们复用排队机制，但 `state` 的含义不同。

```java
final boolean nonfairTryAcquire(int acquires) {   // 非公平锁核心
    int c = getState();
    if (c == 0) {
        if (compareAndSetState(0, acquires)) { setExclusiveOwnerThread(Thread.currentThread()); return true; }
    } else if (Thread.currentThread() == getExclusiveOwnerThread()) { setState(c + acquires); return true; }
    return false;
}
```
公平锁在 `state == 0` 时先调 `hasQueuedPredecessors()`，有更早等待者则不抢。`tryAcquire` 失败后进入 `acquireQueued` 自旋检查前驱是否 head 且可获取，否则 park。

### 5.2 面试问答
**Q1：非公平锁为什么吞吐更高？** A：刚释放锁的线程可能立即又抢到，省去唤醒队列线程 + 上下文切换 + 再次阻塞的往返；代价是理论饥饿。
**Q2：`Condition.await` 做了什么？** A：加入条件队列 → 完全释放锁 → park → 被 signal 后移到同步队列重新竞争锁 → 恢复原 state。
**Q3：为什么 `await` 要放在 while 循环里？** A：防虚假唤醒，以及"被唤醒后条件又不满足"（多个等待者竞争同一条件）。
**Q4：`LockSupport.park` 与 `Object.wait` 的区别？** A：park 无需持锁、以线程为对象、支持中断返回、有许可机制（unpark 先于 park 不丢信号）。

`Condition` 的典型生产者-消费者写法如下。每个条件队列对应一个明确条件，避免所有等待者共享一个 `wait/notify` 队列：

```java
final ReentrantLock lock = new ReentrantLock();
final Condition notEmpty = lock.newCondition();
final Condition notFull = lock.newCondition();
final Deque<String> queue = new ArrayDeque<>();
final int capacity = 100;

String take() throws InterruptedException {
    lock.lockInterruptibly();
    try {
        while (queue.isEmpty()) {
            notEmpty.await();
        }
        String value = queue.removeFirst();
        notFull.signal();
        return value;
    } finally {
        lock.unlock();
    }
}
```

`await` 会释放当前锁，唤醒后重新竞争锁并恢复执行；因此它必须在持有对应 `Lock` 时调用，且条件必须使用 `while` 检查。

### 5.3 高频追问与陷阱
- 陷阱：`ReentrantLock` 必须在 finally 中 unlock 且次数匹配，否则抛 `IllegalMonitorStateException`。
- 陷阱：无参 `tryLock()` 立即返回且忽略公平性，只有超时版本遵守公平策略。
- 错误回答："AQS 里线程是忙等"（实为 park 挂起，仅在检查条件时短暂自旋）。

### 5.4 一句话速记
- AQS = volatile state + CLH 双向队列 + Condition 条件队列，子类实现独占/共享模板方法。
- 非公平锁 state=0 时直接 CAS 抢锁；公平锁先查 `hasQueuedPredecessors()`。

## 6. 读写锁与 StampedLock

### 6.1 核心原理
`ReentrantReadWriteLock` 用一个 state：**高 16 位读锁数量、低 16 位写锁重入次数**（读锁最多 65535）。读读共享，读写/写写互斥，读锁与写锁都可重入；**写锁可降级为读锁，读锁不能升级为写锁**（两个读线程同时升级会死锁）；非公平下写锁优先防饥饿。锁降级顺序：持写锁 → 获取读锁 → 释放写锁，用于保证"修改后立即可读"。

**StampedLock（JDK 8+）**：写锁、悲观读锁、乐观读（不加锁）。
```java
long stamp = sl.tryOptimisticRead();
double x = this.x, y = this.y;
if (!sl.validate(stamp)) {                     // 读取期间有人写过 → 退化为悲观读
    stamp = sl.readLock(); try { x = this.x; y = this.y; } finally { sl.unlockRead(stamp); }
}
```

| 维度 | ReentrantReadWriteLock | StampedLock |
| --- | --- | --- |
| 乐观读 | 无 | 有 |
| 可重入 | 有 | **无**（误用会死锁） |
| Condition | 有 | 无 |
| 适用 | 读多写少 | 读极多写极少 |

读写锁的价值是：多个读线程可以同时读，但写线程需要独占。

```java
final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
final Map<String, String> cache = new HashMap<>();

String get(String key) {
    rw.readLock().lock();
    try {
        return cache.get(key);
    } finally {
        rw.readLock().unlock();
    }
}

void put(String key, String value) {
    rw.writeLock().lock();
    try {
        cache.put(key, value);
    } finally {
        rw.writeLock().unlock();
    }
}
```

如果写操作频繁、读操作很短，读写锁的状态管理和线程协调成本可能抵消并发读收益，不能只看“读多写少”四个字，必须结合压测。

StampedLock 的乐观读不是“读到的数据一定正确”，而是“先快速读，最后验证期间有没有写入”。验证失败必须重新读取：

```java
long stamp = lock.tryOptimisticRead();
int value = sharedValue;
if (!lock.validate(stamp)) {
    stamp = lock.readLock();
    try {
        value = sharedValue;
    } finally {
        lock.unlockRead(stamp);
    }
}
```

### 6.2 面试问答
**Q1：为什么读锁不能升级为写锁？** A：两个读线程同时要求升级会互相等待形成死锁，故设计上禁止；只能释放读锁后重新获取写锁（期间状态可能变化，需重新校验）。
**Q2：锁降级的作用？** A：保证修改后立即可见，同时降级后允许其他读线程并发读，减少写锁占用时间。
**Q3：乐观读失败率高会怎样？** A：退化为悲观读，多一次 validate 与重新加锁，可能比 ReadWriteLock 更慢。
**Q4：为什么 StampedLock 不支持重入？** A：乐观读与 stamp 机制若支持重入会使状态管理复杂化，是作者明确的性能换约束取舍。

### 6.3 高频追问与陷阱
- 陷阱：读多写多或临界区极短时，读写锁不一定优于 ReentrantLock（额外状态判断开销）。
- 陷阱：StampedLock 写锁不可重入，同线程连续 `writeLock()` 会死锁；stamp 必须成对使用。
- 错误回答："读锁写锁能同时持有，所以一定更快"。

### 6.4 一句话速记
- 读写锁 state 高 16 位读、低 16 位写；可降级不可升级。
- StampedLock 乐观读 + validate 最快，但不可重入、无 Condition。

## 7. 并发工具类对比

### 7.1 核心原理
| 工具 | 语义 | 可重用 | 计数方式 | 场景 |
| --- | --- | --- | --- | --- |
| `CountDownLatch` | 等 N 个任务完成 | 否（一次性） | 递减到 0 | 并行加载后汇总 |
| `CyclicBarrier` | N 线程到齐后一起继续 | 是（可 reset） | 递增到 parties | 分阶段计算、并发测试 |
| `Semaphore` | 控制并发许可数 | 是 | acquire/release | 限流、资源池 |
| `Phaser`（JDK 7） | 多阶段屏障，可动态注册 | 是 | 阶段号 | 复杂分阶段任务 |
| `Exchanger` | 两线程交换数据 | 是 | — | 双缓冲 |

这三个工具都可以借助 AQS 的排队机制，但 `state` 的业务含义不同：

| 工具 | AQS 模式 | `state` 表示 | 获取失败后的行为 |
| --- | --- | --- | --- |
| `ReentrantLock` | 独占模式 | 当前线程的重入次数 | 进入同步队列，等待独占锁 |
| `CountDownLatch` | 共享模式 | 剩余计数 | 等待计数归零 |
| `Semaphore` | 共享模式 | 剩余许可数 | 等待其他线程释放许可 |

#### ReentrantLock：保护一个临界区

`ReentrantLock` 内部记录当前持有者和重入次数。第一次获取时 `state` 从 `0` 变成 `1`，同一线程再次获取时递增；释放时递减到 `0` 才真正唤醒其他竞争线程。

```java
private final ReentrantLock lock = new ReentrantLock();

void update() {
    lock.lock();
    try {
        // 同一时间只允许一个线程执行
        updateSharedState();
    } finally {
        lock.unlock();
    }
}
```

它支持 `tryLock`、超时获取、响应中断和多个 `Condition`，但必须保证 `lock` 与 `unlock` 次数匹配，并且把 `unlock` 放在 `finally` 中。

#### CountDownLatch：等待计数归零

`CountDownLatch` 的 `state` 是剩余计数。`countDown()` 通过 CAS 将计数减一；减到 `0` 后，AQS 以共享模式唤醒等待者。`await()` 在计数不为 `0` 时进入队列等待。

```java
CountDownLatch latch = new CountDownLatch(3);

for (int i = 0; i < 3; i++) {
    pool.execute(() -> {
        try {
            doWork();
        } finally {
            latch.countDown();
        }
    });
}

latch.await(2, TimeUnit.SECONDS);
```

它只能递减，不能恢复，因此是一次性的。`countDown()` 不要求由调用 `await()` 的线程执行；任务完成后应放在 `finally` 中，避免异常导致等待方永久等待。

#### Semaphore：获取和归还许可

`Semaphore` 的 `state` 是可用许可数。`acquire()` 在许可足够时通过 CAS 减少 `state`，许可为 `0` 时进入队列；`release()` 增加 `state` 并唤醒等待者。

```java
private final Semaphore semaphore = new Semaphore(10);

void callDownstream() throws InterruptedException {
    semaphore.acquire();
    try {
        // 最多允许 10 个线程同时访问下游
        request();
    } finally {
        semaphore.release();
    }
}
```

许可不是线程所有权：获取许可的线程和归还许可的线程不必是同一个。但业务代码通常仍应遵循“谁获取、谁在 finally 中归还”的约定。`tryAcquire` 失败时不能调用 `release()`，否则会凭空增加许可数量。

区别要点：Latch 由**其他线程** `countDown`、等待线程 `await`，用完作废；Barrier 由**到达者自己** `await`，最后一个到达者执行 `barrierAction`，超时会 `BrokenBarrierException` 并破坏屏障；Semaphore 的 release 不必由获取者调用。

用三个问题区分它们：

- **CountDownLatch**：我在等几件事情全部完成吗？例如等待 3 个服务初始化。
- **CyclicBarrier**：一组线程要不要在同一个阶段集合后再一起继续？例如并行计算的每一轮。
- **Semaphore**：同时最多允许几个人使用资源？例如最多 20 个线程访问下游接口。

`Semaphore` 使用时要把释放放在成功获取之后：

```java
if (semaphore.tryAcquire(100, TimeUnit.MILLISECONDS)) {
    try {
        callRemoteService();
    } finally {
        semaphore.release();
    }
}
```

如果 `tryAcquire` 失败，不能调用 `release`，否则许可数量会被错误增加。
```java
CountDownLatch latch = new CountDownLatch(3);
pool.execute(() -> { try { results[i] = query(i); } finally { latch.countDown(); } });   // countDown 必须放 finally
latch.await(2, TimeUnit.SECONDS);                                                          // 必须带超时
```

### 7.2 面试问答
**Q1：CountDownLatch 为什么不能重用？** A：内部 AQS state 只能递减到 0，无重置机制；CyclicBarrier 有 `reset()` 与代机制。
**Q2：Semaphore 怎么限流？** A：`new Semaphore(n)` + 进出 acquire/release，即最多 n 个并发；这是单机限流，分布式限流用 Redis + Lua 或 Sentinel（见 [Nginx 与网关限流](../04-中间件/05-Nginx与网关限流.md)）。
**Q3：`await()` 不设超时的风险？** A：某任务异常未 countDown 则等待线程永久挂起，线程池被占满，表现为接口全部超时。
**Q4：与 `join()` 的区别？** A：join 需持有 Thread 引用且等线程结束；Latch 可在任务内任意位置 countDown，更灵活。

### 7.3 高频追问与陷阱
- 陷阱：`CyclicBarrier.reset()` 会让正在等待的线程抛 `BrokenBarrierException`。
- 陷阱：`tryAcquire` 失败无需 release，成功后必须放 finally release。
- 错误回答："CyclicBarrier 一次性、CountDownLatch 可重用"（正好相反）。

### 7.4 一句话速记
- Latch 一次性递减、Barrier 可循环递增、Semaphore 控许可、Phaser 多阶段。
- `countDown` 放 finally，`await` 必带超时。

## 8. ThreadLocal 与内存泄漏

### 8.1 核心原理
每个 `Thread` 持有 `ThreadLocal.ThreadLocalMap threadLocals`（**方向不能搞反**）。Map 用开放地址法，**key 是 ThreadLocal 的弱引用，value 是强引用**：`Thread → ThreadLocalMap → Entry[] → Entry{WeakReference<ThreadLocal> key, Object value}`。

**泄漏链路**：ThreadLocal 外部强引用消失 → key 被 GC 变成 null → value 仍被 Entry 强引用，而 Entry 挂在长存活线程（线程池核心线程）上 → value 永不回收。`get/set/remove` 会顺手 `expungeStaleEntry` 清理部分 stale entry，但不可靠，**必须显式 remove 并放 finally**。`ThreadLocal` 建议声明为 `static final`。

`InheritableThreadLocal` 在**创建子线程时**复制父线程值，线程池的线程是复用的，故子线程可能拿到上一次任务的脏值。**TransmittableThreadLocal（TTL）** 通过包装 Runnable/Callable：提交时捕获快照、执行前 replay、执行后 restore，解决线程池跨线程传递上下文（链路追踪 traceId 场景），用法 `TtlRunnable.get(r)` 或 `TtlExecutors.getTtlExecutorService(pool)`。

#### ThreadLocal 用人话理解

普通共享变量像“所有员工共用一张表”，需要加锁；ThreadLocal 像“每个员工自己的抽屉”：

- 线程之间不会争抢同一个 value；
- 一个线程修改自己的 value，不会影响其它线程；
- 但它也不会自动把数据传给线程池中的下一个任务；
- 线程池线程会复用，所以上一个请求放进去的东西可能被下一个请求读到。

因此 ThreadLocal 适合保存当前请求的上下文、线程封闭对象和格式化器，不适合保存需要多个线程共同维护的库存、余额或全局计数。

推荐的 ThreadLocal 使用模板：

```java
private static final ThreadLocal<RequestContext> CONTEXT = new ThreadLocal<>();

void handle(Request request) {
    try {
        CONTEXT.set(buildContext(request));
        doBusiness();
    } finally {
        CONTEXT.remove();
    }
}
```

`static final` 让 ThreadLocal key 长期存在，`finally` 确保正常返回、异常和提前退出时都清理 value。需要注意，`remove()` 只清理当前线程；它不会清理其它线程中的副本。

### 8.2 面试问答
**Q1：为什么 key 用弱引用？** A：让 ThreadLocal 对象无外部引用时可被回收；代价是产生 stale entry，靠 remove 与探测清理。
**Q2：为什么 value 不用弱引用？** A：业务正在使用的对象可能被 GC 掉，语义错误；value 需在 key 存活期保持强引用。
**Q3：与 synchronized 的关系？** A：前者空间换时间（每线程副本、无竞争），后者时间换空间（排队、共享变量），不能用于共享状态一致性。
**Q4：`SimpleDateFormat` 的解法？** A：每次 new（昂贵）、ThreadLocal 包装（注意 remove）、**改用 `DateTimeFormatter`（JDK 8+ 不可变线程安全，推荐）**。
**Q5：ThreadLocal 能解决共享状态一致性吗？** A：不能。它让每个线程拥有自己的副本，适合上下文和线程封闭对象；如果多个线程必须看到同一个余额或库存，仍需锁、CAS 或数据库事务。

### 8.3 高频追问与陷阱
- 陷阱：Tomcat 线程池 + ThreadLocal 存用户上下文且忘 remove，会导致"用户 A 看到用户 B 数据"的数据串号故障。
- 陷阱：`InheritableThreadLocal` 在线程池下无效，必须用 TTL。
- 错误回答："ThreadLocal 持有 Map，key 是 Thread"。

### 8.4 一句话速记
- 结构：Thread → ThreadLocalMap → Entry(弱 key, 强 value)；key 是 ThreadLocal。
- 泄漏根因：key 被回收 + value 强引用 + 线程长存活；必须 finally remove。
- 线程池跨线程传递上下文用 TTL（捕获 → replay → restore）。

## 9. 线程池原理与调优

### 9.1 核心原理
```java
new ThreadPoolExecutor(corePoolSize, maximumPoolSize, keepAliveTime, unit,
                       workQueue, threadFactory, handler);
```
**execute 四步**：① `workerCount < corePoolSize` → 建核心线程执行；② 否则 `workQueue.offer` 入队，成功后二次检查（池已关闭则移除并拒绝，工作线程为 0 则补一个）；③ 入队失败（队列满）→ 建非核心线程；④ 仍失败（≥ max）→ 拒绝策略。

**关键坑**：队列无界或过大时第 ③ 步永不发生，`maximumPoolSize` 形同虚设，任务全在队列里排队导致延迟飙升/OOM。

| 拒绝策略 | 行为 | 适用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 需要感知失败 |
| `CallerRunsPolicy` | 提交线程自己执行 | 削峰反压（会阻塞主线程） |
| `DiscardPolicy` | 静默丢弃 | 可丢任务的埋点 |
| `DiscardOldestPolicy` | 丢最老任务后重试 | 只关心最新数据 |

**为什么不用 Executors**：`newFixedThreadPool`/`newSingleThreadExecutor` 用容量 `Integer.MAX_VALUE` 的 `LinkedBlockingQueue` → 堆积 OOM；`newCachedThreadPool`/`newScheduledThreadPool` 的 max 为 `Integer.MAX_VALUE` → 线程无限创建。

**核心线程数**：CPU 密集 `N+1`；IO 密集 `2N` 或 `N×(1+等待时间/计算时间)`；上限受下游约束（不超过 DB 连接池的 2~3 倍），必须压测确认。

线程数公式只是起点，不是配置答案。更实用的估算过程是：

1. 先区分 CPU 时间和等待时间；
2. 计算任务平均/分位耗时和目标吞吐；
3. 检查数据库连接池、HTTP 连接池、限流器等下游容量；
4. 使用有界队列给系统施加背压；
5. 压测并观察吞吐、P99、队列长度、拒绝数和 CPU 利用率。

如果一个任务会同步等待下游，线程池线程数可以超过 CPU 核数，但不能超过下游真正能处理的并发能力。把线程数无限增大通常只会增加排队、上下文切换和下游超时。

**监控与关闭**：`getActiveCount`、`getQueue().size()`、`getCompletedTaskCount`、`getPoolSize` 等；用 `beforeExecute/afterExecute/terminated` 钩子采集耗时与异常。关闭流程 `shutdown()` → `awaitTermination(30s)` → 超时 `shutdownNow()`。调参用 `setCorePoolSize`/`setMaximumPoolSize` 支持运行时动态修改（接配置中心）。

**ScheduledThreadPoolExecutor**：基于 `DelayedWorkQueue`；`scheduleAtFixedRate`（固定频率，耗时任务会追赶）vs `scheduleWithFixedDelay`（上次结束后再等 delay，推荐）；**任务抛异常会取消后续调度**。

**ForkJoinPool 工作窃取**：空闲线程从其他线程队列尾部窃取任务，适合可递归分解的 CPU 密集计算（`parallelStream` 底层）；`commonPool` 并行度默认 CPU 核数 - 1，**不要在其中跑 IO 或阻塞任务**。

#### 线程池用人话理解

线程池可以看成一个“有固定员工、候客区和拒绝规则的办公室”：

```text
任务来了
→ 还有核心员工空闲/可创建？交给核心员工
→ 核心员工已满？先进入队列
→ 队列满了？再增加临时员工
→ 临时员工也达到上限？执行拒绝策略
```

所以 `maximumPoolSize` 不是“任务一多马上扩到最大线程数”。如果队列是无界的，任务会一直排队，根本走不到创建非核心线程的分支。

线程池配置至少要回答四个问题：

1. 任务是 CPU 密集还是需要等待 IO？
2. 队列最多允许积压多少任务？
3. 队列满时，是拒绝、降级、丢弃还是让提交者执行？
4. 下游数据库、HTTP 连接池和限流器能承受多少并发？

例如订单写库和日志上报不应共用一个无限队列。日志堆积不能拖垮订单主流程，通常应拆分线程池，并分别设置容量、线程名、监控和拒绝策略。

### 9.2 面试问答
**Q1：线程怎么复用？** A：`runWorker` 循环 `while (task != null || (task = getTask()) != null)`，队列空时用 `poll(keepAliveTime)` 或 `take()` 阻塞。
**Q2：核心线程会超时回收吗？** A：默认不会，`allowCoreThreadTimeOut(true)` 可开启（须先设 keepAliveTime > 0）。
**Q3：`submit` 与 `execute` 区别？** A：`submit` 返回 Future 并把异常封装，不调 `get()` 就完全静默丢失；`execute` 的异常抛到 `UncaughtExceptionHandler` 并替换工作线程。
**Q4：线程池任务抛异常会怎样？** A：`execute` 提交的任务抛异常会导致工作线程死亡并被替换（`processWorkerExit`）；`submit` 则静默封装在 Future 里。
**Q5：核心线程数过大为什么更慢？** A：上下文切换与缓存失效、下游资源竞争加剧、每线程约 1MB 栈内存。
**Q6：怎么隔离业务？** A：按业务线拆多个线程池，核心业务与旁路业务（日志、通知）必须分开，避免一个慢业务打满共享池导致全线不可用。

### 9.3 高频追问与陷阱
- 追问：想"先扩容再排队" → 自定义拒绝策略在队列满时再尝试建线程、用 `SynchronousQueue`、或 Tomcat/EagerThreadPool 这类扩容优先实现。
- 陷阱：必须自定义 `ThreadFactory` 命名，否则 jstack 里全是 `pool-1-thread-N` 无法定位。
- 陷阱：`ScheduledThreadPoolExecutor` 任务异常会终止后续调度；`prestartAllCoreThreads()` 可预热。
- 错误回答："`newCachedThreadPool` 会复用线程所以不会 OOM"（峰值无上限）。

### 9.4 代码/配置示例
```java
new ThreadPoolExecutor(8, 16, 60L, TimeUnit.SECONDS, new ArrayBlockingQueue<>(200),
    r -> new Thread(r, "order-pool-" + SEQ.getAndIncrement()),      // 必须命名
    (r, ex) -> { log.error("rejected, queue={}", ex.getQueue().size()); throw new RejectedExecutionException("busy"); });
```

### 9.5 一句话速记
- 7 参数：core、max、keepAlive+unit、queue、factory、handler。
- 执行顺序：核心线程 → 入队 → 非核心线程 → 拒绝；无界队列会让 max 失效。
- CPU 密集 N+1、IO 密集 2N 或 `N×(1+等待/计算)`；必须自定义线程名 + 有界队列。
- 优雅关闭：shutdown → awaitTermination → shutdownNow。

## 10. CompletableFuture 编排

### 10.1 核心原理
| 类别 | 方法 | 说明 |
| --- | --- | --- |
| 创建 | `supplyAsync`/`runAsync` | 默认 commonPool，**生产必传自定义池** |
| 转换/消费 | `thenApply`/`thenAccept`/`thenRun` | Function / Consumer / Runnable |
| 扁平化 | `thenCompose` | 返回 CompletionStage 时用（否则嵌套 Future） |
| 合并 | `thenCombine`/`thenAcceptBoth` | 两个独立 Future 结果合并 |
| 多任务 | `allOf`/`anyOf` | 全部完成 / 任一完成 |
| 异常 | `exceptionally`/`handle`/`whenComplete` | 兜底 / 统一处理 / 仅记录 |
| 超时 | `orTimeout`/`completeOnTimeout`（JDK 9+） | 超时控制 |

命名规律：`thenXxx` 接上一个结果；`xxxAsync` 表示切换线程（用指定或默认池）；`xxxBoth`/`xxxCombine` 处理两个结果；`xxxEither` 处理先完成者。**非 Async 版本由完成上游任务的线程执行**，阻塞逻辑必须用 `xxxAsync(..., pool)`。
```java
CompletableFuture<UserDetail> f = CompletableFuture.supplyAsync(() -> userSvc.get(id), bizPool)
        .thenCombine(CompletableFuture.supplyAsync(() -> orderSvc.list(id), bizPool), UserDetail::new)
        .orTimeout(800, TimeUnit.MILLISECONDS)          // JDK 9+
        .exceptionally(e -> UserDetail.fallback(id))    // 整体兜底 + 降级
        .whenComplete((r, e) -> log.info("done"));      // 不改结果，仅记录
f.join();                                               // 抛非受检 CompletionException
```

#### CompletableFuture 用人话理解

`CompletableFuture` 就像一张“未来结果单”：

- 现在拿不到结果，先拿到一张单据；
- 结果完成后，继续执行下一步；
- 两张单据都完成后，可以合并；
- 某一步失败，可以转入兜底流程。

```java
CompletableFuture<String> user =
        CompletableFuture.supplyAsync(() -> loadUser(), pool);

CompletableFuture<String> orders =
        user.thenCompose(id ->
                CompletableFuture.supplyAsync(() -> loadOrders(id), pool));
```

这里用 `thenCompose` 是因为“根据用户 ID 查询订单”本身又返回一个 Future。若使用 `thenApply`，结果会变成嵌套结构：

```text
thenApply   → Future<Future<String>>
thenCompose → Future<String>
```

非 `Async` 方法可能由完成上一步的线程继续执行；如果下一步包含阻塞 IO，应该使用带自定义线程池的 `xxxAsync` 版本，避免占用完成回调的线程。

方法选择可以用一个具体例子区分：

```java
ExecutorService pool = Executors.newFixedThreadPool(8);

CompletableFuture<User> userFuture =
        CompletableFuture.supplyAsync(() -> loadUser(), pool);

CompletableFuture<List<Order>> ordersFuture =
        userFuture.thenCompose(user ->
                CompletableFuture.supplyAsync(
                        () -> loadOrders(user.id()), pool));

CompletableFuture<Summary> summaryFuture =
        userFuture.thenCombine(ordersFuture, Summary::new);
```

- `thenApply`：把 `T` 转换成普通的 `R`；
- `thenCompose`：把 `T` 转换成 `CompletionStage<R>` 后扁平化，适合串联异步调用；
- `thenCombine`：等待两个相互独立的 Future，再合并两个结果；
- `allOf`：只表达“全部完成”，不会自动返回 `List<T>`，需要自行收集每个 Future；
- `anyOf`：返回第一个完成的结果，但结果类型是 `Object`，需要自行转换。

`orTimeout` 和 `completeOnTimeout` 只改变 Future 的完成状态，不会自动中断已经开始执行的底层任务。真正需要取消时，还要让底层 HTTP、数据库或业务代码支持超时/中断，否则可能出现“上层已经超时，底层任务仍占用线程和连接”的资源泄漏。

### 10.2 面试问答
**Q1：`thenApply` 与 `thenCompose` 的区别？** A：`thenApply` 会把返回的 Future 再包一层；`thenCompose` 扁平化，等价 flatMap。
**Q2：异常三方法怎么选？** A：`exceptionally` 仅异常时给兜底值；`handle` 无论正常异常都执行且能改结果；`whenComplete` 不改结果仅记录。
**Q3：`allOf` 遇到异常会怎样？** A：任一子任务异常则整体立即异常完成，其余任务继续在后台跑（不取消），结果被丢弃；需要容忍部分失败就先给每个任务加 `handle` 再 `allOf`。
**Q4：并行流为什么危险？** A：默认用 `ForkJoinPool.commonPool()`（并行度 = CPU-1、全局共享），IO 会阻塞所有并行流使用者；解决：自定义 `ForkJoinPool` 提交，或改用 CompletableFuture + 业务池。

### 10.3 高频追问与陷阱
- 陷阱：`orTimeout` 只让 Future 超时完成，**不中断底层任务**。
- 陷阱：链上异常会跳过后续普通阶段，直接找 `exceptionally`/`handle`；`join`/`get` 会阻塞业务线程，应尽量返回 Future 让上层组合。
- 错误回答："`thenApply` 一定会新起线程"。

### 10.4 一句话速记
- 创建必传自定义线程池；组合用 `thenCompose`/`thenCombine`/`allOf`。
- 异常三件套：`exceptionally`、`handle`、`whenComplete`；`orTimeout` 不取消任务。

## 11. 线程生命周期、interrupt 与死锁排查

### 11.1 核心原理
六态：`NEW` → `RUNNABLE` →（`BLOCKED` 等 synchronized 锁 / `WAITING` 无超时等待 / `TIMED_WAITING` 超时等待）→ `TERMINATED`。注意 Java 的 `RUNNABLE` **包含操作系统层面的 IO 阻塞**（jstack 里等 IO 的线程也是 RUNNABLE）。进入 WAITING：`wait()`、`join()`、`park()`；TIMED_WAITING：`sleep`、`wait(timeout)`、`parkNanos`；BLOCKED：等 monitor。

**interrupt 正确用法**：`interrupt()` 不强制终止线程，而是发送一个“请尽快结束”的协作信号。线程正在运行普通代码时，中断只会设置中断标志；线程需要通过 `isInterrupted()` 检查并主动退出。`sleep`、`wait`、`join` 被中断时会抛出 `InterruptedException`，并清除中断标志；`LockSupport.park()` 被中断时通常只是返回，不抛 `InterruptedException`，也不会自动清除标志。普通 IO 阻塞是否响应中断取决于具体 API，不能一概而论，通常还要配置超时或关闭底层资源。捕获 `InterruptedException` 后，如果当前方法不能继续向上抛出，通常应调用 `Thread.currentThread().interrupt()` 恢复中断位。

#### interrupt 用人话理解

`interrupt()` 更像“请你尽快收工”的通知，不是拔电源：

```java
while (!Thread.currentThread().isInterrupted()) {
    doWork();
}
```

线程是否真正结束，取决于任务代码是否检查这个通知并退出。可以把中断分成三步：

```text
发送方：目标线程.interrupt()
目标线程：收到中断信号
业务代码：检查信号、停止接收新任务、清理资源、结束执行
```

`interrupt()` 调用本身不要求目标线程当场停止，也不保证目标线程一定会结束。目标线程可能正在执行普通代码，也可能正处于可中断阻塞中。

#### 1. 运行普通代码：检查 isInterrupted()

如果线程没有调用 `sleep`、`wait`、`join` 等可中断阻塞方法，`interrupt()` 通常只负责设置标志位。业务循环需要主动检查：

```java
void calculate() {
    while (!Thread.currentThread().isInterrupted()) {
        calculateOneBatch();
    }

    // 跳出循环后执行必要的清理
    closeResources();
}
```

也可以在循环内部检查并返回：

```java
void consume(List<Message> messages) {
    for (Message message : messages) {
        if (Thread.currentThread().isInterrupted()) {
            return;
        }
        handle(message);
    }
}
```

`isInterrupted()` 是实例方法，只读取标志位，不清除它。`Thread.interrupted()` 是静态方法，读取当前线程的中断位后会清除它，除非确实需要“读取并消费”这个信号，否则不要随意调用。

#### 2. 阻塞在 sleep/wait/join：捕获异常并恢复中断

这些方法被中断时会抛出 `InterruptedException`。抛异常的同时，中断位已经被清除，因此不能只记录日志：

```java
try {
    Thread.sleep(10_000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt(); // 恢复信号，交给上层或线程池处理
    return;                             // 当前任务结束
}
```

为什么要恢复？因为 `InterruptedException` 清除了当前线程的中断位。如果本层捕获后不恢复，上层调用者再检查 `isInterrupted()` 时会误以为没有发生中断。

如果当前方法允许继续向上抛出异常，也可以不在本层恢复，而是把异常交给上层：

```java
void waitForTask() throws InterruptedException {
    taskQueue.take();
}
```

这里由上层决定是重试、恢复中断并退出，还是转换成业务异常。关键是不能无声吞掉中断。

#### 3. 阻塞在 LockSupport.park：检查中断位

`LockSupport.park()` 与 `sleep` 不同：被中断时一般直接返回，不抛 `InterruptedException`，中断位仍然保持为 `true`：

```java
void waitForSignal() {
    while (!ready()) {
        LockSupport.park();
        if (Thread.currentThread().isInterrupted()) {
            return;
        }
    }
    useResult();
}
```

这也是 AQS、`ReentrantLock` 等工具处理线程等待的基础之一。实际使用中优先使用高级并发工具，不要直接依赖 `park()` 编写复杂同步协议。

#### 4. 线程池任务：不要把中断吞掉

线程池中的工作线程会被复用。任务如果捕获中断后继续执行，可能导致取消任务失败；如果清除中断后直接把线程永久退出，又可能影响线程池的正常管理。常见任务写法是恢复中断并结束当前任务：

```java
class ImportTask implements Runnable {
    @Override
    public void run() {
        try {
            while (!Thread.currentThread().isInterrupted()) {
                importOneBatch();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            closeResources();
        }
    }
}
```

提交方可以使用 `Future.cancel(true)` 请求中断，但这仍然是协作式取消：

```java
Future<?> future = pool.submit(new ImportTask());

// 请求任务取消；底层任务是否及时结束，取决于任务是否响应中断
future.cancel(true);
```

`cancel(true)` 不等于强制杀死线程。如果任务正在执行不可中断的计算，或者底层 API 不响应中断，它仍可能继续运行一段时间。

#### 5. IO 阻塞：中断和超时要一起设计

不能简单地说“IO 阻塞一定不响应中断”。不同 API 的行为不同：

- `BlockingQueue.take()`、`SocketChannel` 等部分 NIO API 支持中断或会抛出相关异常；
- 传统 `InputStream.read()`、某些数据库驱动和第三方客户端，可能不会因为 `interrupt()` 立即返回；
- 这类任务通常还需要连接超时、读取超时，并在取消时关闭 socket、连接或请求句柄。

例如网络请求不能只依赖线程中断：

```java
void request() {
    try (Socket socket = new Socket()) {
        socket.connect(address, 1_000); // 连接超时
        socket.setSoTimeout(2_000);     // 读取超时
        readResponse(socket);
    } catch (SocketTimeoutException e) {
        // 超时后释放资源并结束
    } catch (IOException e) {
        // 记录 IO 错误
    }
}
```

如果任务需要被取消，应同时设计“中断信号 + 底层资源关闭 + 超时兜底”，而不是只调用 `interrupt()`。

#### 常见错误与正确做法

| 错误写法 | 问题 | 推荐做法 |
| --- | --- | --- |
| `interrupt()` 后认为线程立即死亡 | 中断是协作式请求，不是强杀 | 任务主动检查并退出 |
| `catch (InterruptedException e) {}` | 清除了中断信号，取消可能失效 | 恢复中断或继续向上抛 |
| 捕获后只打印日志继续循环 | 任务可能反复执行，无法停止 | 清理资源并结束当前任务 |
| 用 `Thread.interrupted()` 做普通检查 | 读取后会清除标志 | 普通检查使用 `isInterrupted()` |
| 只给 IO 任务调用 `interrupt()` | 底层 API 可能不响应 | 配置超时并关闭底层资源 |

最重要的判断口诀是：

```text
普通运行：检查 isInterrupted()
可中断阻塞：捕获 InterruptedException，恢复或上抛
park：返回后检查中断位
外部 IO：中断之外，还要超时和关闭资源
```

推荐的可中断任务模板：

```java
void consume() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            Message message = queue.take();
            handle(message);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        // 记录、清理资源，然后让任务结束
    } finally {
        closeResources();
    }
}
```

不要捕获 `InterruptedException` 后什么也不做。恢复中断位可以把取消信号继续交给上层；如果当前层能够直接结束任务，也可以在清理后返回。

**死锁四条件**：互斥、请求并保持、不可剥夺、循环等待；破坏任一即可，实践中最易破坏**循环等待**（统一加锁顺序）。

**排查**：`jps -l` 取 PID → `jstack -l <pid>`（JVM 自动打印 `Found one Java-level deadlock`，含线程名、持有/等待的锁与代码行号）→ Arthas `thread -b`（直接找阻塞其他线程的线程）或 `thread -n 3` → 修正加锁顺序或改用 `tryLock(timeout)`。

避免死锁的常见设计是统一锁顺序。例如所有代码都先锁 id 较小的账户，再锁 id 较大的账户：

```java
void transfer(Account a, Account b, int amount) {
    Account first = a.id() < b.id() ? a : b;
    Account second = first == a ? b : a;
    synchronized (first) {
        synchronized (second) {
            doTransfer(a, b, amount);
        }
    }
}
```

如果无法建立全局顺序，可以使用 `ReentrantLock.tryLock(timeout)`，失败时释放已获得的锁并退避重试；但这要求业务操作具有可重试和幂等设计。

### 11.2 面试问答
**Q1：`Thread.stop()` 为什么废弃？** A：强制终止会让线程在任意位置抛出 `ThreadDeath`，虽然通常会经过 `finally`，但共享数据可能只更新了一半，释放锁后其它线程会观察到不一致状态；替代方案是 interrupt + 标志位。
**Q2：怎么优雅终止线程？** A：volatile 标志位让循环退出；阻塞中则 interrupt 打断；线程池用 shutdown/shutdownNow；socket 阻塞需关闭 socket 或设超时。
**Q3：`BLOCKED` 与 `WAITING` 区别？** A：BLOCKED 在等 synchronized monitor；WAITING 是 park/wait/join。线程池全部 WAITING 在 `LinkedBlockingQueue.take()` 是典型现象。
**Q4：活锁与饥饿？** A：活锁 = 都在运行但无人推进（用随机退避解决）；饥饿 = 某线程长期拿不到资源（非公平锁、优先级不当）。

### 11.3 高频追问与陷阱
- 陷阱：`catch (InterruptedException e) { }` 不恢复中断位是最常见错误。
- 陷阱：`Thread.interrupted()` 是静态方法且会**清除**标志位，`isInterrupted()` 只读取。
- 错误回答："interrupt() 会停止线程"。

### 11.4 一句话速记
- 六态：NEW/RUNNABLE/BLOCKED/WAITING/TIMED_WAITING/TERMINATED；RUNNABLE 含 IO 阻塞。
- interrupt 只置标志位，捕获 InterruptedException 后必须恢复中断位。
- 死锁四条件：互斥、请求并保持、不可剥夺、循环等待；用 `jstack -l` 或 `thread -b` 定位。

## 12. JDK 21 虚拟线程

### 12.1 核心原理
虚拟线程（Loom，JDK 19/20 预览、**JDK 21 正式**）是 JVM 调度的用户态线程，由少量**载体线程（平台线程）**承载：① 执行阻塞操作（sleep、`BlockingQueue.take`、Socket IO）时用 `Continuation` 把栈帧从载体线程**卸载**，载体线程去跑其他虚拟线程，IO 就绪后挂回（可能换载体线程）；② **栈在堆上**按需增长（`-Xss` 不作为虚拟线程栈大小配置），可创建百万级；③ 调度器是专用 `ForkJoinPool`，并行度默认等于 CPU 核数；④ JDK 21 中 `synchronized` 内阻塞可能钉住载体线程，JDK 24 的 JEP 491 已改善这类 pinning，但外部锁、JNI 等场景仍需单独评估。

| 维度 | 平台线程 | 虚拟线程 |
| --- | --- | --- |
| 调度/栈 | 操作系统 / 约 1MB 预留 | JVM / 堆上按需增长 |
| 数量级 | 数千 | 百万级 |
| 池化 | 需要 | **不要池化** |
| 适用 | CPU 密集 | **IO 密集**、高并发请求 |

#### 虚拟线程用人话理解

平台线程像“昂贵的正式员工”：数量少、创建和栈空间成本较高。虚拟线程像“轻量任务单”：可以创建很多张，遇到网络等待时暂时挂起，把载体线程让给其它任务，网络有结果后再继续。

它解决的是：

```text
大量任务同时等待 IO 时，不必为每个等待任务长期占用一个平台线程
```

它没有解决：

```text
CPU 不够、数据库连接不够、远程服务处理能力不够
```

因此虚拟线程可以提高 IO 密集型场景的并发能力，但仍需连接池、`Semaphore`、超时和限流保护下游。虚拟线程也不是“把线程池参数调大”的替代品，通常不需要池化虚拟线程本身，但仍需要限制业务资源的并发访问。

### 12.2 面试问答
**Q1：虚拟线程提升的是什么？** A：IO 阻塞型任务的并发吞吐，不降低单任务延迟、不提升 CPU 算力；它把"用线程数换并发"变成用廉价线程换并发，让同步阻塞代码获得异步级并发能力。
**Q2：与 Reactor 的关系？** A：虚拟线程是"有栈协程"的 JVM 实现，写法同普通线程；Reactor 是响应式回调，背压精确但可读性差。Spring Boot 3.2 起 `spring.threads.virtual.enabled=true` 即可让 Tomcat 使用虚拟线程。
**Q3：为什么不要池化？** A：创建成本极低，池化收益消失，且线程复用会引入 ThreadLocal 脏数据。
**Q4：什么时候退化？** A：`synchronized` 内阻塞（钉住载体线程）、JNI 阻塞、ThreadLocal 存大对象被百万线程放大、CPU 密集任务。
**Q5：结构化并发解决什么？** A：`StructuredTaskScope`（JDK 21 预览）让子任务生命周期绑定作用域：`ShutdownOnFailure` 任一失败即取消其余，`ShutdownOnSuccess` 取最快成功者，避免孤儿任务与异常黑洞。
**Q6：`ScopedValue` 与 ThreadLocal 的区别？** A：ScopedValue 不可变、有明确作用域，作用域结束即失效，专为虚拟线程设计以避免内存放大；代价是不能在作用域内修改。

### 12.3 高频追问与陷阱
- 陷阱：虚拟线程**不是限流手段**，限流仍需 `Semaphore` 或网关；CPU 密集任务用虚拟线程更慢。
- 陷阱：在虚拟线程里用 ThreadLocal 缓存大对象 → 内存爆炸，应改 `ScopedValue`。
- 版本注意：`-Djdk.tracePinnedThreads=full` 可打印钉住堆栈；JDK 24 已改善 `synchronized` 导致的典型 pinning，但 JNI 和某些外部调用仍需单独评估。
- 错误回答："虚拟线程可以替代线程池的一切"。

### 12.4 一句话速记
- 虚拟线程 = JVM 调度 + 栈在堆 + 阻塞时卸载；IO 密集收益大，CPU 密集无收益。
- 不要池化；JDK 21 重点避免在 `synchronized` 内阻塞，JDK 24+ 仍需关注 JNI、外部调用和资源限制。

## 自测题（含答案要点）

1. happens-before 至少说出 5 条？— 程序顺序、监视器锁、volatile、线程 start、join（+中断、终结、传递）。
2. `volatile int count; count++` 线程安全吗？— 不安全，volatile 不保证复合操作原子性。
3. DCL 单例为什么需要 volatile？— 禁止"分配→写引用→初始化"重排，防其他线程读到半初始化对象。
4. 锁升级如何理解？— 偏向→轻量级→重量级是历史 HotSpot 优化模型；偏向锁已在新 JDK 移除，业务只能依赖 synchronized 的互斥、可见性和可重入语义。
5. 偏向锁在哪些版本废弃/移除？— JDK 15 默认禁用（JEP 374）、JDK 18 移除。
6. CAS 的三个问题与解法？— ABA（AtomicStampedReference）、自旋开销（LongAdder/退让）、单变量限制（AtomicReference 或加锁）。
7. 为什么 LongAdder 比 AtomicLong 快？代价是什么？— base + Cell[] 分散 CAS 热点；代价是 sum() 弱一致且需遍历。
8. AQS 的 state 在 ReentrantLock/CountDownLatch/Semaphore 中分别表示什么？— 重入次数 / 剩余计数 / 可用许可数。
9. 非公平锁为什么吞吐更高？— 省去唤醒队列线程与上下文切换，新线程可抢到刚释放的锁。
10. 写锁降级的正确顺序？— 持写锁 → 获取读锁 → 释放写锁；读锁不能升级为写锁（会死锁）。
11. StampedLock 乐观读的要点？— tryOptimisticRead 取 stamp → 读 → validate 失败则退化为悲观读；不可重入、无 Condition。
12. CountDownLatch 与 CyclicBarrier 的三点区别？— 一次性 vs 可重用；countDown 由其他线程调 vs await 由参与者调；等待方 vs 参与者互相等待。
13. ThreadLocal 内存泄漏的根本原因？— key 弱引用被回收、value 强引用挂在长存活线程的 ThreadLocalMap 上。
14. 线程池 7 个参数与 execute 四步流程？— core、max、keepAlive+unit、queue、factory、handler；核心线程 → 入队 → 非核心线程 → 拒绝。
15. 为什么不建议用 Executors？— Fixed/Single 用无界 LinkedBlockingQueue 会 OOM；Cached/Scheduled 的 max 为 Integer.MAX_VALUE 会无限建线程。
16. `submit` 提交的任务抛异常会怎样？— 异常被封装进 Future，不调 get() 即静默丢失。
17. CPU 密集与 IO 密集的核心线程数怎么估？— CPU 密集 N+1；IO 密集 2N 或 N×(1+等待/计算)，受下游连接池约束。
18. ScheduledThreadPoolExecutor 任务抛异常的后果？`thenApply` 与 `thenCompose` 的区别？— 前者会取消后续调度（必须 try-catch 包裹）；后者扁平化，而 thenApply 会嵌套 CompletableFuture。
19. 虚拟线程适合什么场景？为什么不要池化？— IO 密集任务并发；创建成本极低，池化收益消失且引入状态残留。
20. 场景：接口 RT 从 50ms 涨到 5s、CPU 不高，dump 显示大量线程 WAITING 在 `LinkedBlockingQueue.take()`，怎么排查？— 说明任务已消费完，瓶颈在下游（DB/Redis/HTTP）或上游提交不足；继续查是否有线程 BLOCKED 在锁上、下游连接池是否耗尽，结合慢 SQL 与 RT 监控定位。

## 重点题详细解析

**1. 为什么 `volatile int count; count++` 仍然会丢失更新？**

**答案：** `volatile` 只保证单次读写的可见性和有序性，`count++` 是“读、改、写”三个步骤，不是一个原子操作。

**解析：**

```text
线程 A 读取 0
线程 B 读取 0
线程 A 写入 1
线程 B 写入 1
```

最终结果是 1。需要使用 `AtomicInteger.incrementAndGet()`、锁或其它能够把整个读改写过程作为一个原子操作的方案。

**2. DCL 单例中的 `volatile` 到底防止了什么？**

**答案：** 防止对象引用发布到共享变量之前，构造过程尚未完成。

**解析：** `new Singleton()` 至少包含分配内存、执行构造器、把引用写入 `instance` 等步骤。若发生不安全重排序，线程 B 可能看到非 null 的 `instance`，但对象字段还没有初始化完成。volatile 让引用写入与后续读取建立可见性和有序性。静态内部类通常更简单，因为类初始化由 JVM 保证线程安全。

**3. `synchronized` 和 `ReentrantLock` 如何选择？**

**答案：** 只有基本互斥时优先 `synchronized`；需要可中断获取、超时、公平策略或多个条件队列时选择 `ReentrantLock`。

**解析：** `synchronized` 自动释放锁，异常路径不容易忘记解锁；`ReentrantLock` 能调用 `lockInterruptibly`、`tryLock` 和创建多个 `Condition`，但必须在 `finally` 中准确调用对应次数的 `unlock`。不要为了“看起来高级”而无条件使用显式锁。

**4. 为什么 `wait()` 必须放在 `while` 而不是 `if` 中？**

**答案：** 被唤醒只代表可以重新竞争锁，不代表业务条件仍然成立。

**解析：** 线程被唤醒后，可能先被其它线程抢到锁并消费了资源；规范也允许虚假唤醒。因此必须重新检查条件。`BlockingQueue` 已经封装了这套等待/唤醒协议，业务代码优先使用它。

**5. CAS 没有阻塞锁，为什么高竞争时仍可能很慢？**

**答案：** CAS 失败后通常需要循环重试，重试会消耗 CPU，并导致缓存行在多个核心之间反复转移。

**解析：** 低竞争下 CAS 能避免线程挂起和上下文切换；高竞争下所有线程争抢同一个变量，失败重试成本可能超过锁。`LongAdder` 通过分散热点到多个 Cell 提高统计吞吐，但换来了 `sum()` 非严格瞬时一致。

**6. AQS 中的 `state` 为什么在不同工具里含义不同？**

**答案：** AQS 只提供状态保存和排队模板，具体含义由子类定义。

**解析：** 在 `ReentrantLock` 中，state 通常表示重入次数；在 `CountDownLatch` 中表示剩余计数；在 `Semaphore` 中表示剩余许可。理解 AQS 的关键不是死记某个字段，而是掌握“尝试获取失败 → 入队 → park → 被唤醒后重新竞争”的通用流程。

**7. 为什么线程池必须使用有界队列和明确的拒绝策略？**

**答案：** 队列无界会把过载请求无限积压，最终表现为延迟飙升或 OOM；拒绝策略则是系统施加背压的最后一道边界。

**解析：** 线程池不是越大越好。应根据任务耗时、目标吞吐、CPU、下游连接池和内存设置容量，并监控队列长度、拒绝数和任务 P99。`CallerRunsPolicy` 能产生反压，但会阻塞提交线程，必须确认调用方可以承受。

**8. `submit` 的异常为什么容易丢失？**

**答案：** `submit` 会把任务异常保存到 `Future` 中，只有调用 `get()` 或检查完成状态时才会暴露。

**解析：** 如果只提交任务、不保存 Future，也不在任务内部记录异常，业务日志中可能完全看不到失败。对不需要结果但必须感知异常的任务，可使用 `execute` 配合命名线程和 `UncaughtExceptionHandler`，或在 Runnable 内显式处理异常。

**9. ThreadLocal 的 key 为什么是弱引用，value 却是强引用？**

**答案：** 弱 key 允许 ThreadLocal 对象本身在没有外部引用时回收；value 仍需在 key 存活期间保持业务对象有效。

**解析：** key 被回收后会形成 stale entry，value 仍可能被长生命周期线程持有。线程池线程不会随着一次请求结束而销毁，因此必须在请求边界的 `finally` 中调用 `remove()`。ThreadLocal 不是自动清理机制。

**10. `CompletableFuture.orTimeout` 为什么不能解决底层资源占用？**

**答案：** 它只让 Future 以超时异常完成，不会自动停止已经运行的 HTTP、数据库或业务任务。

**解析：** 如果底层调用不支持超时或中断，可能出现上层请求已经返回、底层线程仍占用线程池和连接池的情况。超时设计必须贯穿调用链，并结合取消、连接超时、读取超时和资源释放。

**11. 虚拟线程能否替代限流和线程池？**

**答案：** 不能。虚拟线程降低了创建和阻塞等待的成本，但不会增加 CPU、数据库或远程服务的处理能力。

**解析：** IO 密集型任务可以使用大量虚拟线程，但仍需用 `Semaphore`、连接池和网关限流保护下游；CPU 密集任务仍受核心数限制。虚拟线程也不应通过 ThreadLocal 保存大对象，更不能把“线程数多”当成“系统容量无限”。

3. as-if-serial 保单线程语义，hb 保跨线程可见性。
4. volatile：可见 + 禁重排，不保证原子性。
5. `volatile i++` 不安全；非 volatile 的 long/double 读写可能非原子。
6. DCL 单例的 instance 必须 volatile。
7. 内存屏障：LoadLoad、StoreStore、LoadStore、StoreLoad（最贵）。
8. 锁升级：无锁 → 偏向 → 轻量级 → 重量级（不可逆）。
9. 偏向锁 JDK 15 废弃、JDK 18 移除。
10. 轻量级锁靠 CAS 把 Mark Word 指向栈中 Lock Record。
11. 重量级锁进入 ObjectMonitor，`_EntryList` / `_WaitSet`。
12. 锁优化：锁消除（逃逸分析）、锁粗化、自适应自旋。
13. synchronized 可重入，靠 ObjectMonitor 的 `_count`。
14. `wait` 释放锁、`sleep` 不释放；`wait` 必须在 while 循环中。
15. CAS 三值 V/A/B，CPU 原语，乐观锁思想。
16. CAS 三问题：ABA、自旋开销、单变量。
17. ABA 用 AtomicStampedReference / AtomicMarkableReference 解决。
18. LongAdder = base + Cell[]（@Contended 防伪共享），统计首选。
19. AtomicLong 读精确 O(1)，LongAdder 读弱一致 O(n)。
20. AQS = volatile state + CLH 双向队列 + Condition 条件队列。
21. ReentrantLock 默认非公平；公平锁先查 `hasQueuedPredecessors()`。
22. AQS 节点状态：CANCELLED(1)、SIGNAL(-1)、CONDITION(-2)、PROPAGATE(-3)。
23. 读写锁 state 高 16 位读、低 16 位写；可降级不可升级。
24. StampedLock 乐观读 + validate，不可重入、无 Condition。
25. CountDownLatch 一次性，CyclicBarrier 可重用，Semaphore 控许可，Phaser 多阶段。
26. `countDown` 放 finally，`await` 必带超时。
27. ThreadLocal 结构：Thread → ThreadLocalMap → Entry(弱 key, 强 value)。
28. ThreadLocal 泄漏根因：key 被回收 + 线程长存活；必须 finally remove。
29. 线程池 7 参数：core/max/keepAlive+unit/queue/factory/handler。
30. execute 顺序：核心线程 → 队列 → 非核心线程 → 拒绝策略。
31. 无界队列会让 maximumPoolSize 失效，任务堆积后 OOM。
32. 四种拒绝策略：Abort（默认）、CallerRuns、Discard、DiscardOldest。
33. Executors 四个工厂方法都有无界队列或无限线程问题。
34. CPU 密集 N+1；IO 密集 2N 或 N×(1+等待/计算)。
35. 线程池必须自定义线程名 + UncaughtExceptionHandler。
36. 优雅关闭：shutdown → awaitTermination → shutdownNow。
37. ScheduledThreadPoolExecutor 任务抛异常会终止后续调度。
38. CompletableFuture 必须传自定义线程池，避免占满 commonPool。
39. thenApply 嵌套、thenCompose 扁平化；orTimeout 不取消任务。
40. 虚拟线程：栈在堆、阻塞即卸载、不要池化；JDK 21 需关注 synchronized pinning，JDK 24+ 仍需关注 JNI 和下游资源限制。
