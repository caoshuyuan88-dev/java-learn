# 第一阶段 Java 基础面试场景问答

> **定位**：把 01～05 篇的知识转换成真实面试中的“问题—回答—追问—项目落地”。
>
> **项目背景**：互联网 CRM SaaS 系统，采用微服务架构，部署在阿里云。本文中的项目化回答是可替换模板，面试时应替换成自己的真实模块、指标和技术选型，不能虚构没有做过的内容。
>
> **回答原则**：先说结论，再讲原理，最后结合项目说明为什么这样设计。

## 0. 面试回答总方法

### 0.1 一个好答案的四层结构

```text
第一句：直接回答结论
第二层：解释底层原理
第三层：说明项目中的使用场景
第四层：补充边界、风险和取舍
```

例如面试官问“为什么用 ConcurrentHashMap”：

> 我会在需要高并发读写、且 key-value 存储在进程内的场景使用它。JDK 8 中它通过 CAS 加桶级同步避免整表加锁，读操作通常不加锁，因此比 Hashtable 并发性能更好。在 CRM 服务中可以用于本地短期配置缓存或幂等请求标记，但不能把它当成跨实例共享缓存；多实例场景仍要用 Redis，并处理过期、淘汰和一致性问题。

### 0.2 项目回答的边界

不要把“Java 基础题”回答成架构口号：

- 问 `HashMap`，先讲哈希、桶、链表/红黑树和扩容，再讲它在项目中的适用边界。
- 问线程池，先讲任务队列、线程数、拒绝策略，再讲 CRM 中异步导入、消息消费或报表任务。
- 问 GC，先讲对象生命周期和停顿原因，再讲阿里云实例的日志、监控和排查流程。
- 问 Stream，先讲惰性求值和短路，再说明为什么核心链路不滥用并行流。

## 1. 项目介绍与 Java 基础总览

### Q1：请介绍一下你做过的项目，并说明 Java 基础知识体现在哪里？

**参考回答：**

> 我参与的是互联网 CRM SaaS 系统，面向多个租户提供客户、联系人、商机、跟进记录、权限和报表等能力。系统按业务拆分为多个微服务，通过 HTTP/RPC 和消息队列进行通信，服务部署在阿里云，通常会配合负载均衡、数据库、Redis、对象存储和监控系统。
>
> Java 基础主要体现在几个方面：业务对象使用面向对象和封装；客户列表、权限集合和配置缓存使用集合框架；请求处理、异步任务和消息消费涉及线程池、并发容器和锁；服务运行问题通过 JVM、GC、线程栈和堆分析排查；批量查询和报表转换中会使用 Stream，但核心路径会关注性能和可读性。

**追问：你负责的模块如何体现这些知识？**

回答时按真实经历补充：

```text
业务模块：客户/联系人/商机/权限/导入导出
高频接口：列表查询、客户详情、批量更新
异步任务：Excel 导入、报表生成、通知推送
公共能力：租户上下文、幂等校验、本地配置缓存
线上排查：日志、监控、线程栈、GC 日志、慢 SQL
```

### Q2：Java 对象从 `new` 到可用，经历了什么？

**参考回答：**

> 首先确认类是否已经加载、链接和初始化；然后在堆上分配对象内存，通常优先在线程本地分配缓冲区 TLAB 中完成；接着把对象内存初始化为零值，设置对象头，再执行实例字段的显式初始化和构造器。父类构造完成后，才继续子类的字段初始化和构造器。

```text
类准备好
→ 分配内存
→ 默认值初始化
→ 设置对象头
→ 父类实例初始化与构造
→ 子类字段显式初始化
→ 子类构造器
```

**项目结合：**

> 例如收到一个客户创建请求时，DTO、领域对象和返回对象都会产生短生命周期对象。正常情况下它们在 Eden 区分配，处理完成后没有引用就会被 Minor GC 回收。不会因为“对象使用完了”就立刻手动释放 Java 对象，而是让 GC 根据可达性处理。

**高频追问：字段默认值和显式赋值有什么区别？**

> 默认值是对象内存清零阶段产生的，例如 `int` 是 `0`、引用是 `null`；显式字段初始化和构造器代码属于初始化逻辑，在默认值之后执行。父类构造器执行时，子类字段可能还只有默认值，因此构造器中调用可重写方法存在风险。

### Q3：Java 是值传递还是引用传递？

**参考回答：**

> Java 只有值传递。传递基本类型时复制值；传递对象时复制的是对象引用的值，所以方法可以通过这个引用修改对象内部状态，但不能让调用方变量指向另一个对象。

```java
void change(Customer customer) {
    customer.setName("new");       // 调用方能看到对象内部变化
    customer = new Customer();     // 只修改了方法内的副本
}
```

**项目结合：**

> 在服务层传递客户对象时，如果多个方法共享同一个可变对象，容易出现隐式修改。边界层通常使用 DTO，关键对象尽量通过明确的返回值传递，避免一个方法修改另一个方法持有的状态。

### Q4：`String` 为什么不可变？项目中有什么好处？

**参考回答：**

> `String` 内部内容不可修改，任何拼接、替换都会产生新的字符串。不可变带来字符串常量池复用、线程安全、哈希值可缓存，以及作为 `HashMap` key 时不会因为内容变化导致定位失效。

```java
String tenantId = "tenant-a";
String another = new String("tenant-a");
tenantId.equals(another); // true
tenantId == another;     // 通常为 false
```

> 在 CRM 中，租户标识、权限编码、状态编码等适合用 `String` 表示。拼接大量导入数据时不应在循环中反复使用 `+`，应使用 `StringBuilder` 或直接交给序列化组件。

**追问：`StringBuilder` 和 `StringBuffer` 怎么选？**

> 单线程拼接选 `StringBuilder`，它不加同步，性能更好；多个线程共享同一个可变字符串缓冲区才考虑 `StringBuffer`，但更推荐调整设计避免共享可变对象。`String` 适合不可变结果，不能把它和 `StringBuilder` 当成同一类工具。

### Q5：`==`、`equals` 和 `hashCode` 有什么区别？

**参考回答：**

> `==` 对基本类型比较值，对引用类型比较是否是同一个对象；`equals` 默认也是比较引用，但很多类会重写为逻辑相等；`hashCode` 用于哈希容器的快速定位。约定是：两个对象 `equals` 为 true，`hashCode` 必须相同。

**项目结合：**

> 客户对象如果作为 `HashSet` 元素或 `HashMap` key，必须基于稳定字段正确重写 `equals/hashCode`。通常不把会变化的“客户状态”放进 key 的相等性判断，否则对象放入集合后字段变化，可能再也找不到。

### Q6：为什么金额不能直接用 `double`？

**参考回答：**

> `double` 是二进制浮点数，很多十进制小数无法精确表示，例如 `0.1`。金额计算应使用 `BigDecimal`，并明确舍入规则。

```java
BigDecimal total = price
        .multiply(quantity)
        .setScale(2, RoundingMode.HALF_UP);
```

> CRM 的合同金额、回款金额和报表汇总必须统一精度、舍入模式和币种，否则单笔看似很小的误差会在汇总后放大。构造 `BigDecimal` 时优先使用字符串或 `BigDecimal.valueOf`。

## 2. 面向对象、泛型、异常与框架基础

### Q7：重载和重写有什么区别？

**参考回答：**

> 重载发生在同一个类或继承体系中，方法名相同但参数列表不同，编译期根据静态类型和参数选择；重写要求子类方法签名兼容父类方法，运行期根据实际对象类型动态分派。返回值不能单独作为重载条件。

**项目结合：**

> 例如统一的客户查询接口可以定义抽象方法，不同数据源实现自己的查询逻辑；调用方依赖接口，运行时由具体实现完成动态分派。重载则适合提供不同参数形式的便捷入口，但不应让重载造成参数含义不清。

### Q8：接口和抽象类怎么选择？

**参考回答：**

> 接口表达“能做什么”，适合定义能力和替换点；抽象类表达“是什么”，适合复用状态、模板流程和公共代码。一个类可以实现多个接口，但只能继承一个类。

```java
interface CustomerExporter {
    byte[] export(List<Customer> customers);
}

abstract class AbstractExporter {
    protected void validate(List<Customer> customers) {
        // 公共校验
    }
}
```

> 在微服务中，接口常用于定义外部依赖和策略，抽象类适合沉淀多个实现共有的模板步骤。不要为了“看起来面向对象”而大量增加继承层次。

### Q9：泛型擦除是什么？为什么不能 `new T()`？

**参考回答：**

> Java 泛型主要在编译期提供类型检查，编译后大部分类型参数会被擦除为上界或 `Object`。运行时通常不知道 `T` 的具体类型，所以不能直接 `new T()`，也不能直接判断 `List<String>` 和 `List<Integer>` 的泛型参数。

```java
class Repository<T> {
    private final Supplier<T> factory;

    Repository(Supplier<T> factory) {
        this.factory = factory;
    }
}
```

> 项目中的通用 Repository、分页结果和接口返回对象可以使用泛型减少强制类型转换，但不能误以为泛型信息在运行时完整存在。集合参数遵循 PECS：生产者用 `? extends`，消费者用 `? super`。

### Q10：受检异常和非受检异常怎么处理？

**参考回答：**

> 受检异常要求编译期显式处理，通常表示调用方有机会恢复；非受检异常继承 `RuntimeException`，常表示参数错误、状态错误或程序缺陷。异常处理应在有能力恢复或转换的边界处理，不能简单地到处 `catch (Exception)`。

**项目结合：**

> Controller 层可以把领域异常转换成统一错误码和响应；基础设施异常应保留原始原因并记录必要上下文；批量导入不能因为一条数据失败就静默吞掉异常，而应返回失败行号、原因和整体处理状态。

### Q11：为什么推荐 try-with-resources？

**参考回答：**

> 它会在退出代码块时自动关闭实现 `AutoCloseable` 的资源，即使业务代码抛异常也能执行关闭，并且能正确保留 suppressed exception。

```java
try (InputStream input = Files.newInputStream(path)) {
    return input.readAllBytes();
}
```

> CRM 的 Excel 导入、对象存储文件下载和数据库流式读取都要明确资源生命周期。不能只依赖 GC 关闭文件、连接或响应体。

### Q12：反射、动态代理在项目中有什么作用？

**参考回答：**

> 反射允许程序在运行时读取类、字段、方法和注解信息；动态代理可以在不修改目标类的情况下，在方法调用前后增加逻辑。Spring 的依赖注入、事务、权限、日志和 RPC 框架都大量使用这些机制。

> 在 CRM 中，权限注解可以描述“某个接口需要什么权限”，拦截器或 AOP 在调用前读取注解并校验租户和角色。反射带来灵活性，但会降低类型安全、增加调试复杂度，因此业务代码不应滥用。

### Q13：JDK 动态代理和 CGLIB 有什么区别？

**参考回答：**

> JDK 动态代理要求目标对象实现接口，代理对象通过接口调用；CGLIB 通过生成子类代理具体类，不能代理 `final` 类或 `final` 方法。实际使用由框架根据目标类型和配置决定。

> 如果一个 CRM 服务通过接口暴露业务能力，JDK 代理更自然；如果需要代理没有接口的具体类，才考虑基于子类的方式。排查事务未生效时，要关注是否绕过代理直接调用了同类内部方法。

## 3. 集合框架场景题

### Q14：`ArrayList` 的底层结构和扩容过程是什么？

**参考回答：**

> `ArrayList` 底层是动态数组，按索引读取是 O(1)，中间插入和删除需要移动后续元素。它默认懒初始化，第一次添加元素时才创建数组；容量不足时申请更大的数组并复制旧元素，JDK 8 常见扩容约为原容量的 1.5 倍。

> CRM 批量导入如果预计有 10 万条数据，应尽量预估容量，减少多次扩容和数组复制。但容量规划不能代替分页或流式处理，否则仍可能一次性占满堆内存。

### Q15：`ArrayList` 为什么不是线程安全的？如何处理？

**参考回答：**

> 多线程同时修改时，可能发生数据覆盖、size 不一致或数组扩容竞争。单纯读共享列表可以安全得多，但如果存在并发写，必须明确同步策略。

```java
List<String> list = Collections.synchronizedList(new ArrayList<>());
```

> 如果写少读多且数据量适合复制，可以考虑 `CopyOnWriteArrayList`；如果是单线程局部变量，直接使用 `ArrayList`。不能因为用了同步容器，就认为遍历和复合操作天然全部安全。

### Q16：`HashMap` 如何定位一个 key？

**参考回答：**

> 先对 key 的 hash 做扰动，再根据数组长度计算桶下标。桶内可能是链表，冲突严重且满足条件时会树化为红黑树。查找时先比较哈希，再通过 `equals` 确认 key。

```text
key.hashCode()
→ hash 扰动
→ (n - 1) & hash
→ 定位桶
→ 比较 hash 和 equals
```

> 因此 `equals/hashCode` 契约不正确会直接导致 CRM 权限缓存、配置 Map 或去重逻辑失效。

### Q17：为什么 `HashMap` 扩容时不重新计算所有 hash？

**参考回答：**

> 容量通常翻倍，新的桶下标只比旧下标多看一位 hash。元素要么留在原位置，要么移动到“原位置 + 旧容量”，因此可以利用 `hash & oldCapacity` 快速拆分，减少计算。

> 如果导入任务需要构造很大的临时 Map，可以按预计数量设置初始容量，减少扩容期间的复制和停顿，但仍要防止不受控的输入导致内存问题。

### Q18：为什么 `HashMap` 的默认负载因子常见是 0.75？

**参考回答：**

> 负载因子越低，碰撞越少、查询更快，但浪费更多数组空间；越高则节省空间但碰撞增加。0.75 是时间和空间之间的经验折中，不是性能保证。

### Q19：`HashMap` 在并发场景有什么问题？

**参考回答：**

> 它没有为并发读写提供完整保证。并发扩容、覆盖写入和复合操作都可能产生错误结果。即使某些单次读在实践中不容易出错，也不能据此把它当线程安全容器。

> 多实例 CRM 服务的共享数据不能放在本地 `HashMap` 中解决一致性问题；本地 Map 只适合实例内缓存，跨实例应使用 Redis 或数据库，并考虑失效和更新策略。

### Q20：`ConcurrentHashMap` 为什么比 `Hashtable` 更适合并发？

**参考回答：**

> JDK 8 的 `ConcurrentHashMap` 使用数组、链表/红黑树、CAS 和桶级同步。读取通常不需要锁，不同桶的写操作可以并行；`Hashtable` 的大多数方法都对整张表加锁，并发度较低。

```java
ConcurrentHashMap<String, Long> counters = new ConcurrentHashMap<>();
counters.merge("lead-created", 1L, Long::sum);
```

> 但 `ConcurrentHashMap` 的复合业务逻辑仍要使用 `compute`、`merge` 等原子方法，不能把 `get` 和 `put` 分开后假设整体原子。

### Q21：为什么 `ConcurrentHashMap` 不允许 null key 和 null value？

**参考回答：**

> 并发读取时，`null` 既可能表示“没有映射”，也可能表示“映射值就是 null”，会破坏无锁读语义和结果判断，因此禁止使用 null。

### Q22：`ArrayList`、`LinkedList`、`ArrayDeque` 如何选？

**参考回答：**

> 默认优先 `ArrayList`，因为连续数组有较好的缓存局部性和随机访问性能；`LinkedList` 只有在已经持有节点位置、且确实频繁做链表两端或中间操作时才有优势；栈和队列优先 `ArrayDeque`，通常比 `Stack` 和 `LinkedList` 更合适。

### Q23：`CopyOnWriteArrayList` 适合什么场景？

**参考回答：**

> 它写入时复制整个数组，读操作不加锁，适合读多写极少、列表规模可控的场景，例如实例内的监听器列表或不频繁变化的配置快照。大量写入或大列表不适合，会产生复制和内存压力。

### Q24：`subList` 有什么坑？

**参考回答：**

> `subList` 通常是原列表的视图，不是独立副本。原列表结构变化可能导致视图失效，子列表修改也会影响原列表。需要独立结果时使用 `new ArrayList<>(list.subList(...))`。

## 4. 并发编程与线程池场景题

### Q25：并发问题要从哪三个维度分析？

**参考回答：**

> 先看可见性：一个线程的修改能否被另一个线程看到；再看原子性：复合操作是否会被打断；最后看有序性：重排序后是否可能观察到错误顺序。`volatile` 主要解决可见性和部分有序性，不保证 `count++` 的原子性。

### Q26：`synchronized` 和 `ReentrantLock` 怎么选？

**参考回答：**

> `synchronized` 语法简单，异常时自动释放锁，适合大多数简单互斥；`ReentrantLock` 提供可中断获取、超时获取、公平锁、多个条件队列等能力，但必须在 `finally` 中释放。

```java
lock.lock();
try {
    updateCustomer();
} finally {
    lock.unlock();
}
```

> CRM 中更新同一客户的实例内临界区可以使用锁；跨服务、跨实例的订单或客户状态不能只依赖 JVM 锁，应使用数据库条件更新、分布式锁或幂等设计。

### Q27：AQS 是什么？`CountDownLatch` 和 `Semaphore` 有什么区别？

**参考回答：**

> AQS 是基于同步状态和等待队列构建同步器的框架。`CountDownLatch` 用共享状态表示剩余任务数，计数归零后等待者继续，适合“一次性等待”；`Semaphore` 用许可数限制同时访问资源的线程数，许可可以反复获取和释放。

```java
CountDownLatch latch = new CountDownLatch(3);
// 三个任务完成后 latch.countDown()
latch.await();
```

> 例如报表接口需要并行查询三个数据源，可以用 latch 等待结果；限制同一实例同时执行的导出任务数量，则更适合 semaphore 或有界线程池。

### Q28：AtomicLong 和 LongAdder 有什么区别？

**参考回答：**

> `AtomicLong` 只有一个值，使用 CAS 更新，适合低竞争且需要立即读取精确值的计数；`LongAdder` 在竞争激烈时把计数分散到多个 Cell，更新时减少 CAS 冲突，读取时汇总，因此更适合统计吞吐量，但 `sum()` 不是严格事务快照。

> CRM 的接口 QPS、访问次数等监控统计可以使用 LongAdder；如果是严格的序列号、余额或库存，不应因为性能而用 LongAdder 替代原子业务逻辑。

### Q29：ThreadLocal 的作用和内存风险是什么？

**参考回答：**

> ThreadLocal 为每个线程提供独立变量副本，适合保存请求上下文、格式化器或 traceId 等线程隔离数据。在线程池中线程会复用，如果使用后不清理，可能发生数据串请求或对象长期占用。

```java
try {
    TENANT_ID.set(tenantId);
    service.handle();
} finally {
    TENANT_ID.remove();
}
```

> ThreadLocalMap 的 key 是弱引用，但 value 仍可能在线程存活期间保留，因此“key 被回收”不等于“value 立即释放”。线程池任务必须在 finally 中清理。

### Q30：interrupt 正确用法是什么？

**参考回答：**

> `interrupt()` 不会强制杀死线程，而是设置中断标志。线程运行中需要主动检查 `isInterrupted()`；阻塞在 `sleep`、`wait`、`join` 时通常抛出 `InterruptedException` 并清除标志，捕获后如果不能继续处理，应恢复中断状态。

```java
try {
    queue.take();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

> 线程池关闭、任务取消、服务下线时应正确传递中断信号。不能捕获异常后什么都不做，否则上层无法知道任务已被取消。

### Q31：线程池七个核心参数如何设置？

**参考回答：**

> 核心参数包括核心线程数、最大线程数、空闲存活时间、时间单位、工作队列、线程工厂和拒绝策略。设置不能只背公式，还要结合任务类型、下游容量、响应时间和压测结果。

```text
CPU 密集型：线程数接近 CPU 核数
IO 密集型：可适当增加，但受数据库/HTTP 下游容量限制
有界队列：防止请求无限堆积
明确拒绝策略：让过载可观测、可降级
自定义线程名：方便线上排查
```

> CRM 的 Excel 导入、报表生成和通知推送不能共用一个无限队列线程池，否则报表任务堆积可能拖垮在线请求。应按任务类型隔离线程池，并设置队列上限、超时和监控。

### Q32：什么情况下使用 CompletableFuture？

**参考回答：**

> 它适合组合多个异步任务、处理依赖关系和统一异常传播。例如客户详情页需要并行查询客户基本信息、跟进记录和标签，可以并行发起，再组合结果。但要明确使用哪个线程池，不能无意识地把阻塞 IO 丢进公共 ForkJoinPool。

```java
CompletableFuture<Customer> customer =
        CompletableFuture.supplyAsync(() -> queryCustomer(), ioPool);
CompletableFuture<List<Tag>> tags =
        CompletableFuture.supplyAsync(() -> queryTags(), ioPool);

return customer.thenCombine(tags, CustomerView::of);
```

## 5. JVM、类加载与 GC 面试题

### Q33：JVM 运行时数据区有哪些？

**参考回答：**

> 程序计数器、虚拟机栈和本地方法栈通常是线程私有；堆和方法区/元空间通常是线程共享。对象实例主要在堆中，类元数据主要在元空间，直接内存由 JVM 外部的本地内存管理。

> 线上看到“堆没满但进程 OOM”，还要考虑元空间、直接内存、线程栈、JNI 或容器内存限制，不能只盯着 `-Xmx`。

### Q34：JIT 是什么？

**参考回答：**

> Java 代码先编译成字节码，JVM 运行时会识别热点方法和热点循环，用即时编译器把它们编译成机器码，并通过内联、逃逸分析、锁消除等优化提高性能。因此 Java 程序可能在预热后变快。

> 压测时要先预热，不能只看程序刚启动几秒的结果。线上服务发布后也要关注启动阶段的延迟和流量预热策略。

### Q35：垃圾回收如何判断对象是否还能使用？

**参考回答：**

> 现代 JVM 主要从 GC Roots 出发做可达性分析。能从 GC Roots 访问到的对象暂时存活，访问不到的对象才可能被回收。GC Roots 包括栈中的引用、静态字段、常量和 JNI 引用等。

> “对象没有引用”是直觉说法，严格判断是从 Roots 不可达。即使对象不可达，也不保证马上回收。

### Q36：为什么新生代通常分为 Eden 和两个 Survivor？

**参考回答：**

> 新对象先进入 Eden，Minor GC 后存活对象复制到一个 Survivor 区，下一次回收时再在两个 Survivor 之间来回复制，另一个作为空的目标区。这样可以避免在同一区域内处理大量碎片，并根据年龄决定是否晋升老年代。

```text
Eden + From
    ↓ Minor GC
To（存活对象）
    ↓ 下一次 GC 交换 From/To
达到年龄或空间不足
    ↓
+ 老年代
```

### Q37：三色标记、记忆集和卡表解决什么问题？

**参考回答：**

> 三色标记把对象分为白、灰、黑，用于并发标记阶段；并发标记时对象关系可能变化，需要写屏障处理漏标。记忆集记录跨区域引用，卡表是记录脏区域的粗粒度结构，G1 的 RSet 进一步记录哪些 Region 可能引用当前 Region。

> 记忆口诀：记忆集是总称，卡表记“哪里变脏”，RSet 记“谁指向我”。

### Q38：CMS、G1、ZGC 怎么简单区分？

**参考回答：**

> CMS 重点是低停顿老年代回收，但存在碎片和并发模式失败风险；G1 把堆划分为 Region，按收益优先回收，兼顾吞吐和可预测停顿；ZGC 通过更多并发阶段和着色指针等机制，把停顿控制在很低水平，适合大堆和低延迟场景。具体选择要看 JDK 版本、堆大小、延迟目标和压测结果。

### Q39：如何排查线上频繁 Full GC？

**参考回答：**

```text
1. 先看监控：堆使用、老年代、GC 次数、停顿时间、进程内存
2. 看 GC 日志：谁在触发 Full GC、晋升是否过快、是否分配失败
3. 看对象：jmap/堆转储分析大对象和引用链
4. 看代码：缓存无上限、ThreadLocal、静态集合、监听器、连接资源
5. 结合流量和发布记录回溯
6. 修复根因后压测和灰度验证
```

> 阿里云环境中还要结合实例规格、容器限制、监控告警和发布批次判断，不能只靠临时增大堆内存。增大堆可能只是延迟故障。

### Q40：双亲委派模型的完整过程是什么？

**参考回答：**

> 类加载器收到加载请求后，先检查自己的缓存；缓存没有，就把请求交给父加载器；父加载器继续向上委派，直到最顶层；如果父加载器都找不到，再由当前加载器调用 `findClass` 自己查找、定义和加载。类初始化通常是后续步骤，不等于加载本身。

```text
当前缓存
→ 父加载器
→ 父的父加载器
→ 顶层加载器
→ 父加载失败
→ 当前加载器 findClass
→ 定义 Class
→ 按需初始化
```

> 这样可以保证核心类优先由 Bootstrap 等可信加载器加载，避免应用自定义一个同名核心类替换 JDK 类。插件化、容器隔离和 SPI 场景可能需要打破或调整默认委派，但必须明确类可见性和安全边界。

## 6. Java 8～21 与 Stream 场景题

### Q41：Stream 和普通循环的区别是什么？

**参考回答：**

> 普通循环关注“如何遍历和控制”，Stream 关注“数据经过哪些转换步骤”。Stream 的中间操作是惰性的，没有终端操作就不执行；通常一个元素会沿着流水线处理，并且 `limit`、`findFirst`、`anyMatch` 等可以短路。

```java
List<String> ids = customers.stream()
        .filter(Customer::isActive)
        .map(Customer::getId)
        .distinct()
        .limit(100)
        .toList();
```

> CRM 的查询结果转换、去重、分组适合 Stream；复杂业务分支、需要多个 `break/continue`、大量修改外部状态时，普通循环更清晰。

### Q42：`map` 和 `flatMap` 的区别是什么？

**参考回答：**

> `map` 是一个输入对应一个输出，形状从 `Stream<T>` 变成 `Stream<R>`；`flatMap` 是一个输入对应一个流，最后把多个流摊平成一个流，适合“一对多”展开。

```java
// 客户 → 客户名称
customers.stream().map(Customer::getName);

// 客户 → 多个标签 → 所有标签
customers.stream()
        .flatMap(customer -> customer.getTags().stream())
        .distinct();
```

### Q43：`collect` 和 `reduce` 有什么区别？

**参考回答：**

> `reduce` 把多个元素逐步合并成一个值，例如求和；`collect` 通常把元素放入集合、分组结果或统计容器，适合可变容器归集。复杂归集优先使用成熟 Collector，避免手动修改共享集合。

### Q44：`orElse` 和 `orElseGet` 有什么区别？

**参考回答：**

> `orElse` 的默认表达式会立即执行，即使 Optional 有值；`orElseGet` 只有为空时才调用 Supplier。默认值计算昂贵或有副作用时使用 `orElseGet`。

### Q45：并行流适合线上 CRM 服务吗？

**参考回答：**

> 不能因为数据量大就直接使用并行流。并行流默认使用公共 ForkJoinPool，适合 CPU 密集、数据量足够大、任务独立且无共享状态的计算；数据库、HTTP、文件等阻塞 IO 会占满公共线程，影响其他任务。核心链路通常优先串行 Stream、专用线程池或批量 SQL。

### Q46：`record`、`sealed`、模式匹配解决什么问题？

**参考回答：**

> `record` 适合表达不可变数据载体，自动生成构造器、访问器、`equals/hashCode/toString`；`sealed` 限制允许的子类，适合封闭的领域层次；模式匹配减少类型判断和强制转换样板代码。

> 在接口返回 DTO、事件对象和结果封装中可以考虑 record，但要结合序列化框架、字段兼容和团队 JDK 版本。新语法不是目的，减少错误和样板代码才是目的。

### Q47：如果项目从 JDK 8 升级到 JDK 17，你会怎么做？

**参考回答：**

```text
1. 盘点运行时、编译插件、依赖和基础镜像
2. 检查内部 API、反射访问、Java EE 模块和 TLS/编码变化
3. 升级框架与测试工具，先让构建通过
4. 用真实流量或压测验证 GC、启动、延迟和线程池
5. 灰度发布并保留回滚方案
```

> 对微服务系统要逐个服务验证，而不是一次性切全量。重点检查容器启动参数、监控探针、序列化兼容、连接池、JVM GC 选择和阿里云镜像中的 JDK 版本。

## 7. 综合项目场景题

### Q48：客户列表接口突然变慢，你如何排查？

**参考回答：**

> 先确认是所有租户还是单个租户，是平均延迟还是 P99 变差。再看应用监控、线程池、GC、数据库慢查询、Redis 命中率和下游调用耗时。若线程池队列堆积，判断是否有阻塞 IO 或任务突增；若 GC 停顿增加，检查是否一次加载大量客户数据或缓存无界增长；若数据库慢，检查分页、索引和返回字段。
>
> Java 基础层面重点关注：是否使用 `ArrayList` 保存过大的全量结果、是否在循环中重复字符串拼接、是否错误使用并行流、是否有锁竞争或 `ConcurrentHashMap` 复合操作不当。修复后用压测和灰度验证，而不是直接扩大机器规格。

### Q49：批量导入 100 万客户数据如何设计？

**参考回答：**

> 不会一次性把 100 万行全部放入内存。文件上传到对象存储后，任务服务按块或流式读取，校验和转换后批量写库；任务状态持久化，失败行记录原因，处理过程可重试、可取消、可观测。
>
> 实现上使用有界线程池隔离导入任务，控制数据库并发；集合按批次创建并及时释放；金额和日期使用正确类型；幂等键防止重复导入；跨服务进度通过数据库或 Redis 记录，不能依赖 ThreadLocal 或本地 Map。

### Q50：如何保证“创建客户”接口幂等？

**参考回答：**

> 由调用方提供幂等键，服务端在数据库建立唯一约束或幂等记录。请求到达时先查询状态，处理中返回处理中，已成功返回原结果，失败按策略允许重试。真正写入和幂等记录要在同一事务边界或通过可靠状态机保证一致性。
>
> `ConcurrentHashMap` 只能保证单实例内的并发访问，阿里云上服务通常多实例部署，不能用它代替数据库唯一约束或 Redis 分布式方案。

### Q51：多个服务同时修改客户状态，如何避免覆盖？

**参考回答：**

> 首先明确状态机和合法迁移；数据库更新使用版本号或条件更新，例如 `where id = ? and version = ?`，成功后版本加一；冲突时返回重试或人工处理。跨服务通知使用可靠消息和幂等消费。
>
> JVM 锁只在单个进程内有效，不能解决多实例和服务间并发。若确需分布式锁，要设置过期、续期、释放校验和故障兜底，不能把锁当作唯一一致性方案。

### Q52：线上 CPU 飙高但请求量没有明显增加，你怎么处理？

**参考回答：**

```text
1. 记录实例、进程和时间范围，确认是否单实例
2. 用 top/jstack 找高 CPU 线程并映射到 Java 线程
3. 看是否死循环、异常重试、锁自旋、正则灾难回溯
4. 看 GC 是否频繁，是否大量对象分配
5. 对比最近发布、配置和流量变化
6. 先隔离或降级，再修复并回归验证
```

> 不能只通过重启掩盖问题。重启可以恢复服务，但要保留线程栈、GC 日志和请求样本，保证后续能定位根因。

### Q53：你如何设计一个可靠的 SaaS 租户上下文？

**参考回答：**

> 请求进入网关或服务后解析租户标识，完成鉴权和合法性校验，再把租户上下文传递给业务层和下游调用。线程池异步任务不能默认继承请求线程上下文，应显式传参或使用经过审查的上下文传递机制；任务结束必须清理 ThreadLocal。
>
> 数据库查询必须把租户条件作为强制边界，不能只依赖调用方记得拼接；缓存 key 也必须包含租户维度，避免数据串租户。日志和链路追踪应带 tenantId，但要注意敏感信息脱敏。

## 8. 面试中的反例与易错点

| 错误说法 | 更准确的说法 |
| --- | --- |
| Java 传引用 | Java 只有值传递，对象场景传递的是引用值 |
| `volatile` 保证原子性 | `volatile` 不保证复合读改写原子性 |
| `HashMap` 扩容就是翻倍复制 | 常见是容量翻倍，并利用 hash 高位拆分桶 |
| `ConcurrentHashMap` 所有操作都原子 | 单次方法有并发语义，跨方法复合逻辑仍需设计 |
| ThreadLocal key 是弱引用所以不会泄漏 | key 可能被回收，但 value 仍可能在线程中滞留 |
| GC 会立刻回收无引用对象 | 不可达只是具备回收资格，何时回收由 GC 决定 |
| 并行流一定比循环快 | 受任务粒度、拆分、线程池和共享状态影响 |
| 微服务里加 synchronized 就能保证一致性 | JVM 锁只覆盖单实例，跨实例要用持久化或分布式方案 |
| 增大堆就能解决 OOM | 先区分堆、元空间、直接内存、线程栈和泄漏根因 |
| 捕获中断异常后直接忽略 | 应处理取消逻辑，不能继续时恢复中断位 |

## 9. 一分钟背诵卡片

```text
对象：分配、清零、对象头、父类、字段、构造器
String：不可变、常量池、StringBuilder
equals：逻辑相等；hashCode：哈希定位；二者必须一致
泛型：编译期检查、运行期擦除；PECS
异常：在能处理的边界转换，不能静默吞掉
ArrayList：动态数组、随机访问快、扩容复制
HashMap：扰动、桶、链表/红黑树、扩容
CHM：CAS、桶级同步、无锁读、不能解决跨实例一致性
并发：可见性、原子性、有序性
volatile：可见性和有序性，不保证 count++
AQS：状态 + 队列；Latch 一次性等待，Semaphore 限制并发
线程池：有界队列、隔离、命名、拒绝、监控
ThreadLocal：线程隔离，线程池必须 remove
JVM：栈线程私有，堆共享，元空间存类元数据
GC：Roots 可达性；Eden → Survivor → 老年代
三色：白灰黑；记忆集/RSet 处理跨 Region 引用
双亲委派：缓存 → 父加载器 → 自己查找 → 定义 → 初始化
Stream：数据源 → 中间操作 → 终端操作；惰性、短路
项目回答：单实例锁不等于分布式一致性，本地缓存不等于共享缓存
```
