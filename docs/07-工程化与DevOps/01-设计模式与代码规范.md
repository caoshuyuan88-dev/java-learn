## 1. 设计原则（SOLID + 迪米特 + 合成复用）

### 1.1 核心原理

- **单一职责（SRP）**：一个类只有一个引起它变化的原因；判断标准是"变更来源是否唯一"，不是代码行数。
- **开闭原则（OCP）**：对扩展开放、对修改关闭；落地只有三条路——抽象化 + 多态 + 配置化（策略/工厂/SPI/规则引擎），本质是"新增分支不改已有类"。
- **里氏替换（LSP）**：子类可替换父类且不破坏语义；反例是子类抛父类未声明的异常、把 `isEmpty()` 反转成 `isNotEmpty()`。
- **接口隔离（ISP）**：接口小而专；落地是拆接口 + Java 8 `default` 方法。**依赖倒置（DIP）**：高层依赖抽象，落地是构造器注入接口 + Spring IoC。
- **迪米特法则（LoD）**：只和朋友说话，反例 `order.getUser().getAddress().getCity()`，正解 `order.getUserCity()`；**合成复用（CRP）**：优先组合/委托，继承是编译期强耦合且 `protected` 破坏封装。

### 1.2 面试问答

- **Q1：开闭原则和高扩展性是一回事吗？** A：结论——开闭是高扩展性的一种实现约束，要求扩展点被抽象化并预留插槽、新增功能只做加法；原因是不改已有类即无回归风险；边界是不是所有代码都要预留扩展点，尺度是"需求未来 6 个月内是否可预期会变"。
- **Q2：依赖倒置与"面向接口编程"的区别？** A：结论——面向接口是手段，DIP 规范的是依赖方向（高层 → 抽象 ← 低层）；原因是加个 `interface` 但不改变依赖方向不叫 DIP；边界是接口只被唯一实现且不会替换时属形式主义，判断依据是"是否存在多实现或测试替身的真实需求"。
- **Q3：你违反过哪条原则？** A：结论——准备一个真实故事比背概念有效；原因是用此题判断你是否有设计层面的反思能力；边界是故事要含"当时为什么这么写、后来怎么拆、收益多少"，例如 3000 行 God Class 按 SRP 拆成下单/计价/通知后，新人改动风险明显下降。

### 1.3 高频追问与陷阱

- "组合一定优于继承"是错的：内部复用用组合，多态扩展用继承，只有满足 LSP 的真子集语义才继承。
- `default` 方法解决接口隔离的同时带来菱形继承冲突，必须显式 `Interface.super.method()`。
- 只答"我严格遵守 SOLID"会被追问细节；承认权衡（如为性能放弃一次抽象）反而加分。

### 1.4 示例

```java
// 反例：新增支付方式必须改本方法（违反 OCP）
if ("ALI".equals(type)) {...} else if ("WECHAT".equals(type)) {...}
// 正例：抽象 + 多态 + 容器注入
public interface PayChannel { String type(); void pay(BigDecimal amount); }
```
### 1.5 一句话速记

SOLID = 接口要小、职责要单、子类别乱来、依赖要抽象、扩展靠多态；再加迪米特少链式调用、合成复用少继承。

### 2.2 面试问答

- **Q1：为什么单例、代理、策略、责任链频率最高？** A：结论——它们同时具备"框架源码可验证"与"业务可落地"两个特征；原因是问模式的真实目的是考察你是否理解 Spring 的运行机制与扩展点；边界是只背意图却说不出源码入口（`Proxy.newProxyInstance`、`ReflectiveMethodInvocation.proceed`）等于没答到点。
- **Q2：原型模式 `clone()` 会踩什么坑？** A：结论——浅拷贝导致引用字段被共享；原因是 `Object.clone()` 是字段级位拷贝，`List` 字段仍指向同一实例；边界是深拷贝用序列化/JSON 往返或逐字段拷贝，`ArrayList.clone()` 拷贝了数组本身但元素仍共享。
- **Q3：哪些模式面试时不该硬套业务？** A：结论——解释器、备忘录、中介者；原因是它们主要出现在工具与 DSL 场景，硬套会显得为了用模式而用模式；边界是能说清"我在 SpEL/正则/线程池调度里见过它的影子"即可。

### 2.3 高频追问与陷阱

- `java.util.Observable` 在 Java 9 已废弃（非接口、语义弱），别当正例；Spring 的 `ApplicationEvent` 才是现代写法。
- 享元的经典例子是 `Integer.valueOf` 的 -128~127 缓存，可用 `-XX:AutoBoxCacheMax` 调上界。

### 2.4 示例

```java
// 享元：缓存区间内 == 成立，因此包装类比较永远用 equals
Integer a = 127, b = 127;  System.out.println(a == b); // true
Integer c = 128, d = 128;  System.out.println(c == d); // false
```
### 2.5 一句话速记

创建型管"怎么造"、结构型管"怎么拼"、行为型管"怎么动"；单例、代理、策略、责任链、模板方法是五大必答款。

## 3. 单例模式与重点模式深挖

### 3.1 核心原理

单例五种写法对比（核心结论：**枚举最安全，静态内部类最实用**）：

| 写法 | 懒加载 | 线程安全 | 反射可破坏 | 反序列化可破坏 | 性能 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 饿汉 `static final` | 否 | 是（类加载期保证） | 可（构造器判空可挡） | 可（需 `readResolve`） | 高 | 简单可靠 |
| 懒汉 `synchronized` 方法 | 是 | 是 | 可 | 可 | 低 | 不推荐 |
| DCL + `volatile` | 是 | 是 | 可 | 可 | 高 | 经典答案 |
| 静态内部类 | 是 | 是（`<clinit>` 机制） | 可 | 可 | 高 | 生产首选 |
| 枚举 `enum` | 否 | 是 | 不可 | 不可 | 高 | 最安全 |

DCL 的 `volatile` 不是"防多线程同时进同步块"，而是**禁止 `new` 的三步（分配内存、初始化、赋引用）重排序**——否则其他线程可能读到引用非 null 但字段全为默认值的"半初始化对象"。JDK 5 起 JMM 修复 volatile 语义，该写法才正确。

其余重点模式的边界（面试只需说清"用哪个、为什么不用另一个"）：

| 模式组 | 关键结论 |
| --- | --- |
| 工厂方法 vs 抽象工厂 | 前者管一个产品维度；后者管"一族必须配套"的产品（如方言的 Connection/Command/TypeHandler），只有一个维度时用简单工厂即可 |
| 建造者 | 参数 > 4 个、必填与选填混合、要求不可变时分步构建；`@Builder` 不生成必填校验，收口仍在构造器 |
| 静态 / JDK 动态 / CGLIB 代理 | 静态代理手写、无接口限制；JDK 动态代理要求目标类实现接口（`$Proxy0` 必须 `extends Proxy`）；CGLIB 靠继承生成子类，final 类/方法不可代理；Spring Boot 2.0+ 默认 CGLIB |
| 装饰器 / 适配器 / 外观 | 装饰器接口不变只增强（可嵌套）；适配器把接口转换成目标类型求兼容；外观新增统一入口以简化子系统调用 |
| 策略 | 算法族可替换；落地是 `Map<String, Strategy>` + Spring 注入或"枚举 + 函数式接口"；分支 ≤ 3 且稳定时不要抽象 |
| 模板方法 | 骨架固定、钩子可变；`JdbcTemplate` 保证连接一定释放，回调（`RowMapper`）弱化继承耦合 |
| 观察者 | `publishEvent` + `@EventListener` 默认同步；异步需 `@Async` 或 `taskExecutor`；一致性场景用 `@TransactionalEventListener(AFTER_COMMIT)` |
| 责任链 | 四大载体：Servlet Filter、Spring MVC 拦截器、Netty Pipeline、MyBatis 插件；AOP 的 `ReflectiveMethodInvocation.proceed()` 是标准实现 |
| 享元 / 组合 / 状态机 | 享元共享不可变对象省内存；组合统一处理树形叶子与容器；状态机把迁移显式建模，替代散落的 `if (status == X)` |

### 3.2 面试问答

- **Q1：单例怎么防反射破坏？** A：结论——普通类无法完全防，只能在构造器抛异常，枚举天然免役；原因是 `Constructor.setAccessible(true).newInstance()` 会绕过私有构造，判空防御仍可被"反射把静态字段置空再 new"绕过，而 `Constructor.newInstance` 对 `Modifier.ENUM` 直接抛 `IllegalArgumentException`；边界是还要注意 `Unsafe` 等极端手段不在讨论范围。
- **Q2：Spring 的 Bean 是单例吗？** A：结论——是"容器级单例"，不是 JVM 级单例；原因是实例缓存在 `DefaultSingletonBeanRegistry.singletonObjects`（`ConcurrentHashMap`），同一 JVM 可有多个容器各持一份，原型 scope 更是多份；边界是因多线程共享，Bean 必须无状态或状态只读，这就是不建议在 Controller 里放成员变量的原因。
- **Q3：三级缓存和单例什么关系？** A：结论——三级缓存是"提前暴露半成品单例"以解决循环依赖；原因是 `singletonFactories` 放可生成早期引用/代理的 `ObjectFactory`、`earlySingletonObjects` 放早期引用、`singletonObjects` 放成品，A 依赖 B 时 A 先入工厂再填充 B；边界是构造器注入的循环依赖无法解决、prototype 的循环依赖直接抛 `BeanCurrentlyInCreationException`，且 Spring Boot 2.6+ 默认禁止循环依赖（`spring.main.allow-circular-references=false`）。
- **Q4：`subList` 与 `Arrays.asList` 的坑？** A：结论——共同点是"返回视图而非独立集合"；原因是 `Arrays.asList` 由数组支撑、长度固定，`set` 生效但 `add`/`remove` 抛 `UnsupportedOperationException`，`subList` 由父列表支撑、原列表结构性修改触发 `ConcurrentModificationException` 且 `subList().clear()` 会删除原列表区间；边界是要副本统一用 `new ArrayList<>(...)`，Java 9+ 的 `List.of` 完全不可变且拒绝 null。

### 3.3 高频追问与陷阱

- CGLIB 代理的 Bean 构造器会被调用两次（目标实例一次、代理子类一次），构造器有副作用要注意；`invoke` 里写成 `method.invoke(proxy, args)` 会无限递归。
- `@Transactional` 失效三因：自调用（走 `this` 绕过代理）、`private`/`final` 方法拦截不到、对象未被 Spring 管理；修复用自注入（配 `@Lazy`）、拆 Bean 或 `AopContext.currentProxy()`（需 `exposeProxy=true`）。
- 责任链没有终止条件会死循环（Handler 把请求又丢回链头），必须显式约定"谁负责终止"；`@EventListener` 方法返回非 void 且非 null 时返回值会被当作新事件继续发布，用 `void` 规避。

### 3.4 示例

```java
// 生产首选：静态内部类（懒加载 + 线程安全 + 无锁）；枚举写法最安全
public final class IdGenerator {
    private IdGenerator() {}
    private static class Holder { private static final IdGenerator INSTANCE = new IdGenerator(); }
    public static IdGenerator getInstance() { return Holder.INSTANCE; }
}
// 枚举单例：public enum Singleton { INSTANCE; }
```
### 3.5 一句话速记

饿汉简单、DCL 要 volatile、内部类最优、枚举不可破；装饰器不改接口、适配器改接口、外观开前门；策略换算法、模板定骨架、责任链串处理、状态机管流转。

## 4. Spring 中的模式清单与项目表达

### 4.1 核心原理

| 模式 | Spring 中的落点 | 说明 |
| --- | --- | --- |
| 工厂 | `BeanFactory`、`FactoryBean`、`ApplicationContext` | `getBean` 是工厂方法；`FactoryBean` 交给用户自定义创建 |
| 单例 | `DefaultSingletonBeanRegistry` | `singletonObjects` 缓存；`@Scope("prototype")` 可关掉 |
| 代理 | `JdkDynamicAopProxy`、`ObjenesisCglibAopProxy` | AOP 运行期织入载体 |
| 模板方法 | `JdbcTemplate`、`RedisTemplate`、`AbstractApplicationContext.refresh` | 固定流程 + 回调接口 |
| 观察者 | `ApplicationEventPublisher`、`SimpleApplicationEventMulticaster` | `publishEvent` 一对多通知 |
| 适配器 | `HandlerAdapter`、`AdvisorAdapter` | 让不同类型的 Controller/Advice 走统一入口 |
| 装饰器 | `HttpServletRequestWrapper`、`TransactionAwareCacheDecorator` | 同接口增强 |
| 策略 | `InstantiationStrategy`、`ResourceLoader` | 运行期选择实现 |
| 委派 | `DispatcherServlet`、`DelegatingFilterProxy` | 只做编排不做事 |
| 建造者 | `BeanDefinitionBuilder`、`UriComponentsBuilder` | 分步构建复杂对象 |

### 4.2 面试问答

- **Q1：`DispatcherServlet` 体现了哪些模式？** A：结论——外观 + 委派 + 适配器 + 策略 + 责任链；原因是它作为前端控制器统一入口（外观），处理器映射交给 `HandlerMapping` 的多个实现（策略），请求处理交给 `HandlerAdapter`（适配器，屏蔽 `@Controller`/`HttpRequestHandler`/Servlet 的差异），拦截器用 `HandlerExecutionChain` 串成责任链；边界是它本身极"薄"，这正是外观模式要求的。
- **Q2：为什么 Spring 大量用模板方法而非装饰器？** A：结论——因为需要"固定不可变流程 + 开放可变步骤"；原因是 `JdbcTemplate` 必须保证连接一定释放（`finally` 中），装饰器无法保证流程不被绕过；边界是模板方法的代价是继承耦合，Spring 5 后用回调接口（`RowMapper`、`StatementCallback`）弱化继承，本质是"模板方法 + 策略"。
- **Q3：`@Autowired` 属于依赖注入还是依赖倒置？** A：结论——它是依赖倒置原则的实现手段，"依赖注入"是具体技术名词；原因是 DIP 规定高层依赖抽象、容器负责把实现塞进来；边界是字段注入无法用 `final`、不利单测，Spring 官方推荐构造器注入（Spring 4.3+ 单构造器可省略 `@Autowired`）。

### 4.3 高频追问与陷阱

- 背"Spring 用了 XX 模式"却没有源码坐标一追问就露馅；至少记住 5 个类：`DefaultSingletonBeanRegistry`、`JdkDynamicAopProxy`、`HandlerAdapter`、`JdbcTemplate`、`SimpleApplicationEventMulticaster`。
- `BeanFactory` 与 `ApplicationContext` 的区别：后者是超集，启动即预实例化单例、支持事件与国际化，前者延迟初始化。

### 4.4 示例

```text
"你项目中用过什么设计模式"四段式模板：
问题：订单履约后需通知 6 个下游（积分/优惠券/消息/ERP/数据/风控），早期在 OrderService 串行调用，
      任一下游超时都拖慢主流程（平均 320ms）。
方案：改为发布领域事件 OrderPaidEvent，各下游实现 ApplicationListener，慢调用改异步；
      一致性关键路径（积分）用 @TransactionalEventListener(AFTER_COMMIT) 保证事务提交后执行。
收益：主流程降到 45ms；新增下游零改动 OrderService；下游故障可独立降级（线程池隔离）。
代价：链路由同步变异步后失败需补偿（本地消息表 + 定时重投）；日志需 TraceId 串联。
加分项：主动给出"不该用模式"的反例（两值映射用 switch 更直观），并说明只允许引入一层间接、避免套娃。
```

### 4.5 一句话速记

Spring 记忆锚点：单例缓存、AOP 代理、模板方法定流程、适配器抹差异、事件做解耦、DispatcherServlet 只委派；讲项目用"痛点—方案—收益—代价"。

## 5. DDD 基础与 Java 项目落地

### 5.1 核心原理

| 概念 | 定义要点 | 落地做法 |
| --- | --- | --- |
| 限界上下文 | 同一术语在不同上下文含义不同，边界内模型自洽 | 按业务能力拆模块/微服务，如"交易"与"库存"上下文 |
| 聚合根 | 一致性边界的唯一入口，外部只能经它访问内部实体 | 一个聚合一个仓储，事务不跨聚合，用 ID 引用其他聚合 |
| 实体 | 有唯一标识、生命周期内标识不变 | `equals/hashCode` 基于 ID |
| 值对象 | 无标识、不可变、以属性值判等 | `Money`、`Address`、`DateRange`，Java 16+ 用 `record` |
| 领域事件 | 聚合内发生、其他上下文关心的事实 | `OrderPaidEvent`，与事务提交绑定发布 |
| 仓储 / 领域服务 | 聚合的持久化抽象 / 跨聚合业务规则 | `OrderRepository.findById()` 返回整个聚合；转账在领域服务编排 |

**贫血 vs 充血**：贫血=只有 getter/setter、业务全在 Service（当前主流，配 MyBatis 最顺手）；充血=行为与数据内聚（更贴近 DDD，但 ORM 映射与团队习惯成本高）。工程结论是核心复杂域（计价、状态流转）充血、CRUD 辅助域贫血，不必全量 DDD。

**分层 vs 六边形**：传统四层（Controller/Service/DAO/Entity）依赖自上而下；六边形（端口-适配器）让领域层居中、不依赖框架，外部通过入站端口（Controller/MQ 消费者）与出站端口（Repository/外部 API）适配，测试时可直接替换适配器。

### 5.2 面试问答

- **Q1：聚合根设计的核心约束？** A：结论——一个事务只修改一个聚合；原因是聚合是一致性边界，跨聚合强一致会引入分布式事务、牺牲可用性（见 [分布式事务](../05-分布式与架构/02-分布式事务.md)）；边界是必须跨聚合一致时用领域事件 + 最终一致，并接受短暂不一致。
- **Q2：值对象用什么实现？** A：结论——Java 16+ 首选 `record`，低版本用 `final` 类 + `equals/hashCode`（Lombok `@Value`）；原因是值对象要求不可变与结构相等，而 `record` 自动生成这两者；边界是 `record` 不能继承，字段若是可变引用（如 `List`）需 `List.copyOf` 防御。
- **Q3：六边形架构怎么落地？为什么不建议全量 DDD？** A：结论——按依赖方向划分模块：`domain`（纯 POJO、零框架依赖）→ `application`（用例编排、依赖 domain 接口）→ `infrastructure`（MyBatis/HTTP 实现 domain 端口），编译期依赖箭头全部指向 domain；原因是全量 DDD 的成本集中在建模沟通、聚合拆分与 DTO 转换，而它解决的是业务复杂度而非技术复杂度；边界是 CRUD 型系统与中小项目可退化为单模块 + 包结构分层，收益基本相同。

### 5.3 高频追问与陷阱

- 把 Service 命名成 `XxxDomainService` 却仍在里面直接写 SQL——这不是领域服务，只是换名字。
- 领域对象直接作为接口出入参（`@RequestBody` 绑领域实体）会外泄内部模型，必须用 DTO。
- `Entity`/`PO`/`DTO`/`VO` 职责：PO 对应表结构、DTO 跨层或跨服务传输、VO 面向前端；转换建议用 MapStruct，避免 `BeanUtils.copyProperties`（浅拷贝、反射慢、字段改名不报错）。

### 5.4 示例

```java
// 值对象 + 充血聚合：不变量由对象自己保证
public record Money(long cents, String currency) {
    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("币种不一致");
        return new Money(cents + other.cents, currency);
    }
}
public void pay(String payNo) {              // 聚合根 Order 的方法
    if (status != OrderStatus.INIT) throw new IllegalStateException("订单状态不允许支付");
    this.status = OrderStatus.PAID;
    registerEvent(new OrderPaidEvent(id, payNo));
}
```

### 5.5 一句话速记

限界上下文划边界、聚合根管一致性（一事务一聚合）、实体看 ID、值对象不可变、核心域充血 + 辅助域贫血。

## 6. 代码规范（阿里巴巴 Java 开发手册重点）

### 6.1 核心原理

| 模块 | 高频强制规约 | 原因 |
| --- | --- | --- |
| 命名 | 类 `UpperCamelCase`；方法/参数/成员/局部 `lowerCamelCase`；常量全大写下划线；抽象类 `Abstract`/`Base` 前缀；异常类 `Exception` 结尾；POJO 布尔字段不加 `is` 前缀 | `isXxx` 在部分序列化框架与 RPC 中会被剥离，产生 `success`/`isSuccess` 不一致 |
| 常量 | 不允许魔法值直接出现在代码中；`long` 用大写 `L` | 便于统一修改；小写 `l` 与数字 `1` 易混 |
| OOP | `equals` 用常量在前或先判空；整型包装类比较一律 `equals`；`BigDecimal` 用 `String` 构造或 `valueOf`；POJO 属性用包装类型、局部变量用基本类型 | 包装类缓存区间外 `==` 为 false；`new BigDecimal(0.1)` 有精度丢失 |
| 集合 | `Arrays.asList` 是定长视图、不可增删；`subList` 是视图；`HashMap` 初始化给容量；遍历 `Map` 用 `entrySet`；`foreach` 内不可 `remove`；`Collectors.toMap` 必须处理 key 冲突与 null value | 避免运行时异常与并发修改异常 |
| 并发 | 线程池禁止用 `Executors` 创建，必须 `ThreadPoolExecutor` 显式指定参数并命名线程；`SimpleDateFormat` 线程不安全；`ThreadLocal` 用完必须 `remove`；`HashMap` 线程不安全 | 无界队列或无限线程会 OOM；`ThreadLocal` 不 remove 在线程池下泄漏并串数据 |
| 控制语句 | `switch` 每个 `case` 必须 `break`/`return` 或注释说明 fallthrough；`if-else` 超 3 层用卫语句或策略；循环体内避免定义对象与 `try-catch` | 可读性与性能 |
| 注释 | 类、类属性、类方法用 `/** */`，方法内用 `//`；枚举字段必须有注释 | 生成 API 文档与 IDE 提示 |
| 异常 | 不用异常控制流程；`catch` 区分稳定与非稳定代码；`finally` 中禁止 `return`；事务方法内吞异常会导致不回滚 | 语义清晰、不丢异常 |
| 日志 | SLF4J 门面 + 占位符；`trace/debug` 不做字符串拼接；异常日志打印堆栈；禁止 `System.out`；生产禁开 debug | 性能与可定位性 |
| MySQL 建表 | 表名/字段名小写下划线、不用复数；必备 `id`、`create_time`、`update_time`；金额/小数用 `decimal` 不用 `float/double`；字段尽量 `NOT NULL` + 默认值 | 统一风格、避免精度丢失与 NULL 统计遗漏 |
| 索引 | 唯一索引 `uk_字段名`、普通索引 `idx_字段名`；`varchar` 建索引必须指定长度；超过三张表禁止 `join` | 命名可读、索引长度可预估 |
| SQL | 禁止 `SELECT *`；不要用 `count(列名)`/`count(常量)` 代替 `count(*)`；`IN` 值数量控制在 1000 以内；互联网场景禁止外键与级联 | 便于覆盖索引与执行计划稳定、避免锁扩散 |

分歧提示：字段 `NOT NULL` 与"索引列允许 NULL"业界实践不一（允许 NULL 的唯一索引可存多条 NULL）。主流结论是按项目基线统一；若 DBA 要求允许 NULL，业务层必须统一判空策略并写入规范文档。细节见 [MySQL体系结构与索引](../02-数据库/01-MySQL体系结构与索引.md)。

### 6.2 面试问答

- **Q1：为什么禁止用 `Executors` 创建线程池？** A：结论——默认工厂方法会创建队列或线程数无界的池，高负载必然 OOM；原因是 `newFixedThreadPool`/`newSingleThreadExecutor` 用容量 `Integer.MAX_VALUE` 的 `LinkedBlockingQueue`、任务堆积到 OOM，`newCachedThreadPool`/`newScheduledThreadPool` 的 `maximumPoolSize` 是 `Integer.MAX_VALUE`、线程无限创建直到 OOM；边界是必须显式 `new ThreadPoolExecutor(core, max, keepAlive, unit, new ArrayBlockingQueue<>(cap), namedFactory, rejectedHandler)`，并把 `activeCount`/`queueSize` 暴露到监控告警。
- **Q2：`SimpleDateFormat` 为什么线程不安全？** A：结论——内部可变成员 `calendar` 保存中间状态，多线程共享会相互覆盖，产生错误日期甚至 `NumberFormatException`；原因是 `parse`/`format` 都写同一个 `Calendar`；边界是首选 `DateTimeFormatter`（不可变、线程安全），次选每次 new（有开销），再次 `ThreadLocal`（必须 `remove`），`static` 的 `SimpleDateFormat` 是经典线上事故。
- **Q3：`Collectors.toMap` 最常见的两个坑？** A：结论——value 为 null 抛 NPE、key 重复抛 `IllegalStateException`；原因是内部走 `Map.merge`，其 value 不允许 null；边界是 key 冲突用四参版本 `toMap(k, v, (a, b) -> a)`，value 可能为 null 时先 `filter(Objects::nonNull)` 或手工 `forEach` 构建 `HashMap`。

### 6.3 高频追问与陷阱

- `foreach` 中 `remove` 抛 `ConcurrentModificationException`，正解是 `Iterator.remove()`、`removeIf` 或先收集再批量删。
- `HashMap` 建议 `initialCapacity = (int)(size / 0.75f) + 1`；`Objects.equals(a, b)` 内部已判空，比 `a.equals(b)` 少一个 NPE 风险。
- `Integer.parseInt(null)` 抛 `NumberFormatException` 而非 NPE（源码在 `Character.digit` 处抛）；`String.split` 接收正则，`.` `|` `$` 需转义。

### 6.4 示例

```java
// 线程池标准写法（CallerRunsPolicy 形成背压，任务不丢）
ThreadFactory tf = new ThreadFactoryBuilder().setNameFormat("order-pool-%d").build();
ExecutorService pool = new ThreadPoolExecutor(8, 16, 60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(512), tf, new ThreadPoolExecutor.CallerRunsPolicy());
// 日期格式化线程安全
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
```

### 6.5 一句话速记

命名规范、常量无魔法值、包装类用 equals、`asList`/`subList` 是视图、线程池必须手写 `ThreadPoolExecutor`、日期用 `DateTimeFormatter`。

## 7. 异常与日志最佳实践

### 7.1 核心原理

- 受检异常适合"调用方能恢复"的场景，运行时异常适合编程错误与不可恢复故障；工程主流是业务异常统一继承 `RuntimeException`（不污染方法签名）+ 全局 `@RestControllerAdvice` 转统一响应体。
- 异常分层：`BusinessException`（可预期、带错误码、记 WARN 不打堆栈）、`SystemException`（不可预期、记 ERROR + 堆栈 + 告警）、框架校验异常（`MethodArgumentNotValidException` 等）。
- 日志级别：ERROR 需人工干预；WARN 可自愈或需关注；INFO 关键业务节点与出入参摘要；DEBUG 调试细节（生产关闭）；TRACE 极细粒度。
- 日志规范：结构化 JSON、必含 `traceId`、禁止大对象/大集合全量打印（截断 + 长度上限）、敏感信息脱敏、用异步 Appender 避免阻塞业务线程。

### 7.2 面试问答

- **Q1：为什么不要用异常控制流程？** A：结论——性能与语义双输；原因是构造异常要 `fillInStackTrace` 遍历栈、比返回码贵几个数量级，且用异常表达正常分支会让调用方无法区分预期与故障，最终演变成 `catch (Exception e) {}` 吞异常；边界是真正的异常（`NoSuchElementException`）与框架回调（`InterruptedException`）该抛就抛，判断标准是"这是否为调用方应当处理的正常结果"。
- **Q2：`log.error(e.getMessage())` 有什么问题？** A：结论——丢失堆栈，线上只看到一句话无法定位；原因是 `getMessage()` 只是字符串，异常类型、`cause` 起因链、抛出位置全丢；边界是正确写法 `log.error("下单失败, orderId={}", orderId, e)`——异常必须是最后一个参数且不占位符，否则 SLF4J 会把它当普通参数而不打印堆栈。
- **Q3：TraceId 怎么串起来？** A：结论——入口生成后放入 `MDC`，日志 Pattern 输出 `%X{traceId}`，跨线程与跨服务用 Header 透传；原因是 `MDC` 底层是 `ThreadLocal` 的 Map，线程池提交任务时不会自动继承；边界是异步场景用 `TaskDecorator` 包装 `Runnable` 或改用 `TransmittableThreadLocal`（TTL），跨服务用 W3C `traceparent` 或 `X-Trace-Id`，OpenTelemetry 会自动注入。
- **Q4：全局异常处理要注意什么？** A：结论——不能把系统异常原样返回前端，且要区分 HTTP 状态码与业务错误码；原因是异常堆栈会泄露表名、包路径等内部结构；边界是按类型分级映射（参数异常→400、业务异常→200 + 业务码、未知异常→500 并返回可追踪 `traceId`），并务必有兜底 `Exception` 分支，否则容器会给前端返回 HTML 错误页。

### 7.3 高频追问与陷阱

- `catch (Exception e) { return null; }` 吞异常是 Code Review 必拒项；`finally` 中 `return` 会覆盖返回值并吞掉异常。
- `try-with-resources` 中 `close()` 抛异常会抑制（suppressed）原异常，排查要看 `e.getSuppressed()`。
- 事务方法内捕获异常不抛出会导致不回滚（默认只对 `RuntimeException` 回滚），可用 `@Transactional(rollbackFor = Exception.class)`；`OutOfMemoryError` 属 `Error`，定位靠 `-XX:+HeapDumpOnOutOfMemoryError`，详见 [JVM与GC调优](../01-Java基础/04-JVM与GC调优.md)。

### 7.4 示例

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<Void>> handleUnknown(Exception e) {
    String traceId = MDC.get("traceId");
    log.error("系统异常 traceId={}", traceId, e);          // 堆栈作为最后一个参数
    return ResponseEntity.status(500)
        .body(Result.fail("SYSTEM_ERROR", "系统繁忙, 请联系客服 traceId=" + traceId));
}
```
### 7.5 一句话速记

不吞异常、不用异常控制流程、业务异常继承 `RuntimeException`、`log.error` 堆栈放最后、TraceId 靠 `MDC` + `TaskDecorator` 透传、全局兜底不返回堆栈。

## 8. 单元测试、Code Review 与重构

### 8.1 核心原理

- **JUnit 5 注解**：`@Test`、`@BeforeEach`/`@AfterEach`、`@BeforeAll`/`@AfterAll`（`static`）、`@DisplayName`、`@Disabled`、`@Nested`、`@Tag`、`@Timeout`、`@ExtendWith`、参数化 `@ParameterizedTest` + `@ValueSource`/`@CsvSource`/`@MethodSource`。
- **Mockito**：`@ExtendWith(MockitoExtension.class)`、`@Mock`、`@Spy`、`@InjectMocks`、`@Captor`；`when(x).thenReturn/thenThrow/thenAnswer`、`doReturn().when(spy).m()`（spy 与 void 方法必须用 do 系列）、`verify(x, times(2))`、`verifyNoMoreInteractions()`、`InOrder`；匹配器 `any()`/`eq()`/`argThat()`。断言推荐 AssertJ。
- **测试金字塔**：单元（多、快、无 IO）→ 集成（`@SpringBootTest` 切片 / Testcontainers）→ E2E（少）。JaCoCo 看分支覆盖率比行覆盖率更有意义，团队门槛常见 60%~80%，不建议强制 100%；TDD 是"红—绿—重构"，核心价值是驱动接口设计与可测试性。
- **常见坏味道**：重复代码、过长方法、过大的类、过长参数列表、发散式变化、霰弹式修改、依恋情结、数据泥团、基本类型偏执、`switch` 语句、平行继承体系、冗赘类、夸夸其谈通用性、临时字段、消息链、中间人、不恰当的暴露。
- **常用重构手法**：提取方法/变量/类、内联、搬移方法或字段、以多态取代条件、以策略或状态取代类型码、引入参数对象、以对象取代数组、以工厂方法取代构造器、以组合取代继承、封装字段与集合、卫语句取代嵌套条件。

### 8.2 面试问答

- **Q1：怎么写一个好单元测试？** A：结论——AAA 结构（Arrange-Act-Assert）+ 一个用例只断言一个行为 + 测试名描述业务规则；原因是可读性与失败定位速度，失败时应能从名字判断哪条规则被破坏；边界是不要 mock 被测类的所有协作者（会造成"测实现细节"，重构即红），只对跨越边界（DB/HTTP/时间）的东西打桩。
- **Q2：静态方法和 `new` 出来的对象怎么测？** A：结论——这是可测试性设计信号，应把它们包到实例方法或注入的接口后面；原因是静态与 `new` 不可替换，测试只能依赖真实环境；边界是时间用 `Clock` 注入而非 `System.currentTimeMillis()`、随机数注入 `RandomGenerator`、外部依赖包成 `XxxClient` 接口，无法改造的遗留三方静态工具才用 Mockito 3.4+ 的 `mockStatic` 并记为技术债。
- **Q3：集成测试用什么方案？覆盖率怎么定？** A：结论——数据库首选 Testcontainers（Docker 真库），求快可用 H2（方言有差异），Spring 用 `@SpringBootTest` + 切片测试减少 Bean 加载，覆盖率核心域 80%+、工具类与 DTO 豁免；原因是 H2 与 MySQL 在函数、默认值、索引行为上不一致、关键 SQL 必须真库验证，而覆盖率与缺陷率只有弱相关、强拉高会催生无断言测试；边界是更有效的补充指标是"新增代码覆盖率（diff coverage）"与变异测试（PIT）。

### 8.3 高频追问与陷阱

- `@Spy` 默认调用真实方法，打桩必须用 `doReturn().when()`，否则真实方法先被执行；`@BeforeAll` 必须 `static`（除非类上标 `@TestInstance(PER_CLASS)`）。
- `ArgumentMatchers` 与具体值混用时所有参数都必须用匹配器，否则 `InvalidUseOfMatchersException`。
- 测试方法上的 `@Transactional` 在未 flush 前查不到数据，用 `flush()/clear()` 或 `@Sql` 准备数据。

### 8.4 示例

```java
@ExtendWith(MockitoExtension.class)

    @Mock OrderRepository orderRepository;
    @InjectMocks OrderService orderService;

    @Test
    @DisplayName("已支付订单再次支付应抛出业务异常")
    void pay_shouldThrow_whenOrderAlreadyPaid() {
        when(orderRepository.findById(1L)).thenReturn(Optional.of(new Order(1L, OrderStatus.PAID)));
        assertThatThrownBy(() -> orderService.pay(1L, "ALI"))
            .isInstanceOf(BusinessException.class).hasMessageContaining("状态不允许支付");
        verify(payChannelFactory, never()).get(anyString());   // 未产生副作用
    }
}
```

## 自测题（含答案要点）

1. **DCL 单例为什么必须加 `volatile`？** —— 禁止 `new` 的分配/初始化/赋引用重排序，避免读到半初始化对象；JDK 5+ JMM 修复后该写法才正确。
2. **枚举单例为什么不能被反射破坏？** —— `Constructor.newInstance` 对 `Modifier.ENUM` 直接抛 `IllegalArgumentException`；序列化走 `Enum.valueOf`。
3. **Spring Bean 单例与 GoF 单例的差异？** —— 容器级（`singletonObjects` 缓存）而非 JVM 级，同 JVM 多容器可多实例，故 Bean 必须无状态。
4. **JDK 动态代理与 CGLIB 的边界？** —— JDK 需接口（代理类继承 `Proxy`）；CGLIB 继承目标类、不能 final 类/方法；Spring Boot 2.0+ 默认 CGLIB。
5. **`@Transactional` 自调用为什么失效？** —— 增强在代理对象上，`this.method()` 绕过代理；修复用自注入、拆 Bean 或 `AopContext.currentProxy()`。
6. **装饰器与适配器的本质区别？** —— 装饰器保持接口不变做增强；适配器把接口转换成目标类型求兼容。
7. **`Arrays.asList` 与 `List.of` 的区别？** —— 前者是数组视图（可 `set` 不可增删、允许 null）；后者完全不可变且拒绝 null。
8. **策略模式消除 if-else 的边界？** —— 分支持续增长、单支逻辑复杂才抽象；多字段组合条件应用决策表/规则引擎。
9. **AOP 拦截器链为什么是责任链？** —— `ReflectiveMethodInvocation` 持游标索引，`proceed()` 递归调用下一个 `MethodInterceptor`，不调 `proceed` 即截断。
10. **`ApplicationEvent` 默认同步还是异步？一致性怎么办？** —— 默认同步；异步加 `@Async` 或 `taskExecutor`；一致性场景用 `@TransactionalEventListener(AFTER_COMMIT)`。
11. **聚合根的核心约束？** —— 一个事务只修改一个聚合；跨聚合用领域事件 + 最终一致。
12. **为什么禁止 `Executors` 创建线程池？** —— 无界队列（`LinkedBlockingQueue`）或最大线程 `Integer.MAX_VALUE`，高负载 OOM。
13. **`log.error(e.getMessage())` 的问题与正确写法？** —— 丢堆栈；`log.error("msg x={}", v, e)`，异常放最后且不占位符。
14. **TraceId 跨线程池丢失的原因与解法？** —— `MDC` 基于 `ThreadLocal`，不随任务传递；用 `TaskDecorator` 或 TTL，跨服务走 Header 传播。
15. **`Collectors.toMap` 的两个坑？** —— value 为 null 抛 NPE；key 重复抛 `IllegalStateException`（用合并函数解决）。

## 背诵卡片

1. SOLID = 单一职责、开闭、里氏替换、接口隔离、依赖倒置。
2. 开闭原则三手段：抽象化、多态、配置化。
3. 迪米特法则：只和朋友说话，别写 `a.getB().getC().getD()`。
4. 合成复用原则：内部复用用组合，多态扩展用继承。
5. 创建型五模式：单例、工厂方法、抽象工厂、建造者、原型。
6. 结构型七模式：代理、装饰器、适配器、外观、桥接、组合、享元。
7. 行为型十一模式：策略、模板方法、观察者、责任链、状态、命令、迭代器、中介者、备忘录、访问者、解释器。
8. 单例五写法：饿汉、懒汉、DCL+volatile、静态内部类、枚举。
9. DCL 的 volatile 是防指令重排，不是防并发进入同步块。
10. 静态内部类单例靠 `<clinit>` 的 JVM 加锁保证线程安全与懒加载。
11. 枚举单例是唯一防反射 + 防反序列化破坏的写法。
12. Spring Bean 是容器级单例，存在 `singletonObjects`（ConcurrentHashMap）。
13. 三级缓存：`singletonFactories` / `earlySingletonObjects` / `singletonObjects`。
14. 构造器注入的循环依赖无法解决；Spring Boot 2.6+ 默认禁止循环依赖。
15. 工厂方法管一个维度，抽象工厂管一族配套产品。
16. `BeanFactory` 是容器，`FactoryBean` 是用户自定义创建逻辑的工厂。
17. 建造者用于参数多、有必填、要求不可变的对象；`@Builder` 不生成必填校验。
18. JDK 动态代理前提是目标类有接口，生成 `$Proxy0`；CGLIB 靠继承，final 类/方法无法代理。
19. Spring Boot 2.0+ AOP 默认 `proxy-target-class=true`，统一 CGLIB。
20. JDK 动态代理抛出的异常被 `InvocationTargetException` 包裹，必须解包。
21. 装饰器同接口增强，适配器转换接口，外观简化入口。
22. `Collections.synchronizedList` 迭代时仍需手动同步块。
23. `Integer` 缓存 -128~127，包装类比较一律 equals。
24. 策略模式最优落地：`Map<String, Strategy>` + Spring 注入。
25. 模板方法固化流程，回调接口弱化继承耦合。
26. `ApplicationEvent` 默认同步，异步需 `@Async` + `@EnableAsync`。
27. 责任链四大载体：Servlet Filter、Spring MVC 拦截器、Netty Pipeline、MyBatis 插件。
28. `DispatcherServlet` = 外观 + 委派 + 适配器 + 策略 + 责任链。
29. 讲设计模式用四段式：痛点—方案—收益—代价。
30. DDD 四件套：限界上下文、聚合根、实体、值对象；一个事务只修改一个聚合。
31. 线程池必须手写 `ThreadPoolExecutor`，禁止 `Executors`。
32. 日期格式化用 `DateTimeFormatter`，不用 `SimpleDateFormat`。
33. `ThreadLocal` 用完必须 remove，否则线程池下泄漏并串数据。
34. `log.error("x={}", v, e)` —— 异常放最后且不用占位符。
35. `Collectors.toMap` 遇 null value 抛 NPE，key 重复抛 `IllegalStateException`。
36. 测试金字塔：单元多、集成中、E2E 少；优先看分支覆盖率。
37. `@Spy` 打桩必须用 `doReturn().when()`，否则真实方法先执行。
38. 重构触发信号是坏味道；重构手法之首是提取方法与以多态取代条件。
39. 评审绝不放过：空 catch、无超时外部调用、`SELECT *`。
40. 被问"你如何保证代码质量"：规约 + 单测 + 评审 + CI 门禁 + 监控闭环。
